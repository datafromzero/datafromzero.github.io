## Research: a prompt recipe for data work that reduces slop and hallucination — vendor guidance, evidence, and limits

*Compiled 2026-11-22 from primary sources only: the four vendors' own prompting documentation, peer-reviewed papers, and preprints labelled as preprints. Every fact is as of the date its page was opened — 2026-11-22 throughout. Figures are quoted as published; where a figure was not on the page opened, this report says so. This is a follow-up to #113.*

## Summary

All four vendors agree on the skeleton of a good data prompt: put the real material in the prompt, clearly delimited; restrict the answer to that material; give the model an explicit way to say the answer is not there; ground claims in quotes or citations; use examples; and let tools or code — not the model's head — do computation. The research evidence backs only part of that skeleton on data tasks: giving the schema with explicit schema linking, few-shot examples chosen by similarity, decomposition into steps that operate on the data, and writing code that is then run all have measured effects on SQL, table or arithmetic benchmarks. Other popular items have evidence against them or none: persona prompting does not improve accuracy, emotional/expert prompting failed replication, strict JSON schemas imposed during reasoning can wreck it, and asking the model to check its own work degrades accuracy unless the check runs against something external (execution results). Two widely taught rules have also expired: scripted chain-of-thought is now discouraged by every vendor for reasoning models, and Anthropic has removed assistant prefilling from its current models. Finally, the limits are as important as the recipe: models fabricate citations and invent schema columns even when explicitly told not to, so the recipe's last step is not a prompt at all — it is the human verification that C38 teaches.

## Findings

**Finding 1 — The context pack is vendor consensus, with one unresolved layout disagreement.** All four vendors say: supply the material the answer must come from, delimited and labelled (Anthropic: XML tags, documents at the top of the prompt; OpenAI: Markdown/XML sections in a developer message ordered Identity → Instructions → Examples → Context; Google: context first, question last for long inputs; Microsoft: labelled chunks with source metadata, context before the query, tabular/TSV format as the token-efficient way to include rows). No vendor publishes a literal "schema + sample rows" recipe — that specific shape is a synthesis of their general guidance, and the placement rules genuinely differ (top vs last vs bookended). Sources: Anthropic *Prompting best practices*; OpenAI *Prompt engineering* and *GPT-4.1 prompting guide*; Google *Prompt design strategies*; Microsoft *Prompt engineering techniques* and *Prompt engineering for RAG* (all opened 2026-11-22).

**Finding 2 — "Give the model an out" is the strongest single consensus.** Anthropic's hallucination page leads with explicitly permitting "I don't know"; OpenAI's GPT-4.1 guide gives a fixed fallback sentence for context-only answering, and its Structured Outputs guide warns that a schema without an escape hatch produces hallucinated values to fill it; Microsoft names "no fallback behaviour" an anti-pattern across three documents; Google's Gemini 3 strict-grounding clause says the same. But see Finding 11: the out is vendor consensus, not a measured data-task effect. Sources as in Finding 1, plus Anthropic *Reduce hallucinations* and OpenAI *Structured outputs*.

**Finding 3 — "Code computes, the model narrates" has both the clearest vendor statement and the strongest evidence.** Google's Gemini guide explicitly routes any arithmetic, counting or calculation to its code execution tool. Anthropic documents pairing retrieval with code execution so the model writes Python instead of computing in prose; OpenAI's current guides say use tools rather than guess (its older "use code execution for accurate calculations" tactic could not be verified — the GPT-4-era guide page no longer exists on OpenAI's domain). Evidence: PAL (Gao et al., ICML 2023) — writing Python and executing it beat PaLM-540B chain-of-thought by an absolute 15 points on GSM8K and 40 points on GSM-HARD (Codex). Caveat: on messy real tables, program-aided answering was *below* direct QA in Chain-of-Table's baselines (PaLM 2, WikiTQ) — code helps most when the table is clean and the question computational.

**Finding 4 — Decompose into steps that operate on the data; generic text chain-of-thought is unreliable on tables.** DIN-SQL (Pourreza & Rafiei, NeurIPS 2023): decomposing text-to-SQL into schema linking → classification → generation → self-correction improved simple few-shot "by roughly 10%", reaching 85.3 execution accuracy on the Spider test set (GPT-4). Chain-of-Table (Wang et al., ICLR 2024): reasoning as a chain of executed table operations beat direct QA by 8.69 points on TabFact and 6.72 on WikiTableQuestions (PaLM 2) — while vanilla text CoT *hurt* GPT-3.5 on TabFact (65.37 vs 70.45 direct). A meta-analysis of 100+ papers (Sprague et al., ICLR 2025) finds CoT's benefits concentrated in math, logic and symbolic tasks, with much smaller gains elsewhere.

**Finding 5 — Few-shot examples: selection matters, weaker models can be hurt, and vendor defaults disagree.** DAIL-SQL (Gao et al., PVLDB 2024): with examples selected by question+query-skeleton similarity and well organised, GPT-4's Spider-dev execution accuracy rose from 72.3% to 83.5%; the same paper reports examples *reduced* accuracy for GPT-3.5-class models. On table QA, few-shot gains were near zero for the strongest model tested (Chain-of-Table, Table 1). Vendor defaults: Google says *always* include few-shot examples; Anthropic recommends 3–5; OpenAI's reasoning guidance says zero-shot first; Microsoft's RAG guidance prescribes 2–3 examples *including one that demonstrates declining to answer* — the single most transferable example-design idea for data work.

**Finding 6 — Scripted chain-of-thought has been retired for reasoning models — by all four vendors.** OpenAI's reasoning best practices: "Avoid chain-of-thought prompts." Anthropic: steer with an effort parameter and general instructions, not prescriptive step plans — and its self-check instruction, helpful on other models, should be *removed* for its newest Opus, which over-verifies. Google: Gemini thinking models reason internally; control is via `thinking_level`/`thinking_budget`. Microsoft's techniques page warns its own classic techniques are not recommended for reasoning models and attaches an Acceptable Use Policy warning to extracting their reasoning. Both vendors' general-audience guides still teach classic CoT without the caveat — a learner reading only those gets outdated advice. Related generational casualty: Anthropic's assistant **prefilling** is unsupported from the Claude 4.6 generation onward.

**Finding 7 — Quotes/citations before or with the answer: strong vendor advice, no data-task trial.** Anthropic's signature pattern: extract word-for-word quotes first, then answer grounded in them, one citation per claim, retracting unsupported claims. Microsoft argues the mechanism explicitly — a fabricated answer then requires two errors (the claim and a bad citation) — and prescribes inline citations next to claims. Google teaches grounding-by-prompt plus a strict-grounding clause. No peer-reviewed study found measures this pattern's effect on data-task accuracy; verdict: vendor advice only, albeit from three vendors with a plausible mechanism.

**Finding 8 — Structured output is two different decisions, and one of them has evidence against the strict version.** (a) *Format of the input context*: OpenAI's GPT-4.1 testing found JSON particularly poor for embedding many documents; Microsoft recommends tables/TSV for rows. (b) *Format of the output*: both Anthropic and OpenAI (and Google) offer schema-constrained decoding that guarantees valid structure — but Tam et al. (EMNLP 2024) show strict JSON schemas imposed *while the model reasons* can collapse accuracy (Claude 3 Haiku on GSM8K: 86.51 → 23.44; the model put the answer key before the reasoning key in 100% of GPT-3.5's JSON responses). Their mitigation — answer in natural language first, then convert to the format (NL-to-Format) — performed nearly identically to unrestricted text. Google adds that several schema constraints are silently unenforced in its implementation, so values still need client-side validation. Rule the evidence supports: reason loosely, format afterwards.

**Finding 9 — Role and audience: vendors recommend them for style; the accuracy claim has evidence against it.** All four vendors endorse assigning a role and naming the audience. But Zheng et al. (*Findings of EMNLP 2024*) tested 162 personas across 4 model families on 2,410 MMLU questions: personas did not improve accuracy over no-persona controls, and picking the "best" persona did no better than random. Teach role/audience as tone-and-format steering, never as an accuracy technique.

**Finding 10 — Verification works only when it is external; the model's self-check and the user's challenge both fail.** Huang et al. (ICLR 2024): intrinsic self-correction *lowered* accuracy on every benchmark tested (GPT-4 GSM8K 95.5 → 91.5 → 89.0 across rounds); earlier positive results traced to oracle labels. DIN-SQL's generic self-correction hurt GPT-4 (−3.3) while a gentle variant helped (+0.9). What works is correction against an external signal: self-debugging with execution feedback improved Spider by 2–3% and by 9% on the hardest queries (Chen et al., ICLR 2024), and self-consistency voting over execution results added +5.84 on BIRD dev (CHASE-SQL, ICLR 2025) — though its oracle bound (+19.78) shows the most consistent answer is often wrong. And Sharma et al. (Anthropic, preprint 2023) show models abandon correct answers when the user pushes back: "Are you sure?" is a pressure technique, not verification.

**Finding 11 — Abstention prompts: no data-task evidence, and the general evidence is sobering.** No study found measures whether "answer only if sure" reduces hallucinated numbers on SQL, table or statistics tasks. AbstentionBench (Kirichenko et al., preprint 2025; 20 datasets, >35,000 unanswerable questions, 20 frontier models) calls abstention "an unsolved problem": scale barely helps, reasoning fine-tuning *degraded* abstention by 24% on average (as reported), and a crafted system prompt helped "in practice" without fixing the underlying inability. Kalai et al. (OpenAI/Georgia Tech, preprint 2025) explain why: training and benchmarks reward guessing over "I don't know". Teach the out as hygiene (Finding 2), not as a guarantee.

**Finding 12 — Grounding with real rows: strongly motivated, never cleanly measured.** BIRD (Li et al., NeurIPS 2023) is designed on the finding that database *values*, not schema alone, drive text-to-SQL accuracy — yet its best model (ChatGPT, arXiv v3) reached only 40.08% execution accuracy vs 92.96% human. CHASE-SQL's record BIRD pipeline (73.01% dev) retrieves actual values into the prompt, but its isolated contribution is not stated in the paper. Chain-of-Table shows that past a few thousand tokens, *how* rows are selected and transformed matters more than *that* they were provided. No clean controlled trial (same questions, data supplied vs withheld) was found for data tasks.

**Finding 13 — The reality check: even the full recipe leaves most hard data work unsolved.** DSBench (Jing et al., ICLR 2025): the best agent solved 34.12% of realistic data-analysis tasks. DABstep (Egg et al., preprint 2025): the best agent reached 14.55% on the hardest payment-industry data tasks. A recipe that ends in confidence would mis-teach; the recipe must end in verification.

## "Slop" (H3): definition and features

**Reference definition.** Merriam-Webster (its 2025 Word of the Year, announced on its own site): slop is "digital content of low quality that is produced usually in quantity by means of artificial intelligence." The work-specific variant, "workslop" (Niederhoffer et al., BetterUp Labs + Stanford, *Harvard Business Review*, September 2025): AI-generated work content that masquerades as good work but lacks the substance to advance the task. (The programme's own pages report its survey sample inconsistently — 1,150 vs 1,004 respondents — so its percentages should be quoted with care.)

**There is no agreed academic definition.** A 2026 *Social Epistemology* explication states this explicitly. The most usable academic feature set is Kommers et al.'s three prototypical properties (cited in Baltes, Cheong & Treude, preprint 2026): **superficial competence** (a veneer of quality over a lack of substance), **asymmetry of effort** (cheap to produce, costly to review), and **mass producibility**. Silbey & Hartzog's law working paper (2026) adds negligible producer care and degradation of the domain. Features named across the folk-conceptualisation and developer-discussion literatures — formulaic structure, generic content, invented specifics, overconfident tone — appear in no single validated checklist; anyone presenting one as settled is overstating the literature.

**Padding has a mechanism.** Singhal et al. (COLM 2024): RLHF reward gains are largely driven by increased response length — a purely length-based reward reproduced most of PPO's downstream gains — so verbosity is a training artifact, not a misunderstanding the prompt can talk the model out of.

**Which prompt instructions reduce slop? Honest answer: untested.** No peer-reviewed study found tests anti-slop style instructions against slop features as an outcome. Vendor guides recommend specificity and explicit constraints, but those are vendor claims. The defensible lesson: length and format instructions can trim surface verbosity (with unreliable compliance — see H4), but the reliable counter to slop is the human verification step, not a better adjective in the prompt.

## What a prompt cannot fix (H4)

1. **Invented citations.** Walters & Wilder (*Scientific Reports*, 2023): asked to write short papers with at least five real scholarly citations, GPT-3.5 fabricated 55% of its citations and GPT-4 18%; of citations to works that exist, 43% / 24% contained substantive errors. Asking the model whether its citation is correct does not fix this — it often answers wrongly.
2. **Invented schema elements.** Hasan (ACL 2026 SurgLLM workshop): across 1,200 schema–model instances, 39–54% of structured outputs contained at least one semantic hallucination — columns not in the schema, joins on nonexistent tables — despite the schema being in the prompt. Spider 2.0's enterprise schemas cut o1 Preview from 91.2% (Spider) to 21.3% (as cited in a vendor preprint — the citation, not the lesson, is vendor-sourced).
3. **Silent constraint failure.** IFEval (Zhou et al., preprint 2023): with 25 types of mechanically checkable instructions, one failed constraint fails the whole prompt — and failures grow with the number of simultaneous constraints (length + format + content + exclusions), exactly the kind a beginner will not notice.
4. **Missing knowledge.** Kalai et al. (preprint 2025): hallucination is produced by training and evaluation incentives that reward guessing; Xu et al. (preprint 2024) argue formally that no computable LLM used as a general problem solver can eliminate it. No wording repeals either result.
5. **Self-verification and user pressure.** Per Finding 10: the model cannot reliably check itself, and it folds when challenged — so neither "check your work" nor "are you sure?" is a verification step.
6. **The checker's own skill.** Buçinca, Malaya & Gajos (Proc. ACM HCI, 2021; N=199): people accept wrong AI suggestions, explanations do not reduce overreliance (and may increase it), and only cognitive forcing (decide before seeing the AI's answer) helped. Puppart & Aru (preprint 2025): students adopted incorrect ChatGPT recommendations 52.1% of the time, and a short AI-literacy text did not significantly reduce it. Implication for the C37/C38 balance: C37 can make output *easier* to check (quotes, code, structure); it cannot make the checking happen. That is C38's job, and it is why Part 6's thesis — the fundamentals are the detectors — is load-bearing.
