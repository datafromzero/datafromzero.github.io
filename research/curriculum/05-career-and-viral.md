# Career and Viral: What to Learn, What to Prove, and How the Path Spreads

Data From Zero is organized as one linear path: Excel, then one complete SQL block, then Python, then an advanced core, then one of five tracks — Data Analyst, Data Engineer, Data Scientist, Analytics Engineer, and ML/AI Engineer.

This file covers the career layer around that path and the positioning layer around the site. The career layer answers two questions: what does the job market actually ask for, and what evidence convinces a hiring manager that a learner can do the work? The positioning layer answers a third: why would learners find, share, and return to a free path when large paid platforms already exist?

Scope boundary, stated once and applied throughout: this file is about **what to learn and what to prove**. It defines skills, interview formats, project evidence, and certification alignment. It is not a resume, cover-letter, application, or job-search workflow, and no part of the research package claims to cover that workflow. Learners still need application materials elsewhere; what this curriculum controls is whether, when they are tested, they can perform, and whether, when their work is opened, it holds up.

All demand figures below name their sample. Samples differ by region, role mix, year, and collection method, so figures are never blended into a single average. Access date for all web sources cited in the underlying research is 2026-11-15, with verification re-checks the same day.

## 1. Job-Market Demand: Excel and SQL at the Top, Python Next

### 1.1 The corrected headline

SQL is **#1 or #2 in every named sample** opened in this research. Excel is also **#1 or #2 in every named sample**. Which one leads depends on the sample. Any stronger claim — in particular, that SQL leads in every sample — is false on the research's own evidence and must not be used.

The clearest counterexample is also the most concrete sample:

| Sample | What was counted | Excel | SQL | Python | Notes |
|---|---|---|---|---|---|
| AccioJob, 328 job descriptions | Mixed data roles: Data Analyst, Business Analyst, Data Engineer, Data Scientist | **81%** (267 of 328) | **60%** (197 of 328) | 41% | Excel first, SQL second. Power BI at 43% in the same sample. Not a pure analyst sample. |
| 365 Data Science analysis, via Traecta | Data analyst postings | 54% | 73% | — | SQL first, Excel second in this sample. |
| Statssy analysis | 141,529 LinkedIn postings, Jan 2024–Dec 2025, 12 regions | 68% | About 73% on average across regions; 81% for the US alone | — | SQL first on average, Excel close behind. Regional variation is large. |
| 365 Data Science outlook, newer Glassdoor US sample | 1,355 Glassdoor US postings | 41.3% | Around half | — | Included to show figures move by year and source. Do not treat 54% or 73% as permanent constants. |

Read together, named samples for Excel and SQL span roughly **41–81%** of postings, depending on skill, sample, and year. That span is the honest form of the finding. A second-hand pair quoted from a podcast transcript is **dropped** from this package: it could not be re-verified from an opened primary page, and the named samples above already make the point without it.

### 1.2 Python, BI tools, and surveys

- **Python in analyst postings: use 40–50% from named samples.** The AccioJob sample puts Python at 41% of its 328 mixed-role descriptions. The Traecta transition guide describes Python as mentioned in approximately 40–50% of postings. A lower endpoint sometimes quoted for Python appears in no page opened during verification and is not used here. For analyst roles Python is third, behind Excel and SQL. For data scientist roles the order changes and Python moves first — which is why Python sits third in the shared path but carries much more weight inside the Data Scientist and ML/AI tracks.
- **BI tools:** Power BI reaches 43% in the AccioJob sample; across the samples opened, BI tools (Power BI and Tableau together) sit roughly in the 20–43% range. The lesson is not a specific percentage. It is that a visible-output tool — a dashboard a manager can open — is a recurring hiring requirement, not an optional extra.
- **Survey corroboration, kept separate from postings:** Stack Overflow's 2025 Developer Survey, as quoted on an opened comparison page, puts SQL at 58.6% and Python at 57.9% usage among all respondents. That is developer usage, not analyst job postings, and the two measures should never be merged. HackerRank's 2025 Developer Skills Report, via the same transition-guide source, ranks SQL first by employer invite volume, with demand growth reported at 25.5% year over year.
- **AI mentions:** One opened comparison cites Indeed Hiring Lab (September 2025) reporting 39% of data and analytics postings in India mentioning AI. That figure is regional and is used here only for shape: AI is a fast-growing mention and the loudest marketing theme on incumbent homepages, while Excel and SQL remain the largest entry-level hiring topics for the audience this path serves. AI therefore belongs in the curriculum as an applied layer on a working base — verification, retrieval, and tool use threaded through the path — not as the entry door that replaces that base.

### 1.3 What the demand evidence does and does not justify

The Excel → SQL → Python order stands, but on two legs, not one:

1. **Market leg (corrected):** Excel and SQL are effectively tied at the top of analyst demand, with order varying by sample; Python follows for analysts and leads for scientists. Starting with either Excel or SQL is market-defensible.
2. **Learning-sequence leg:** Excel is the fastest first win for the path's core audience — workers who already live in spreadsheets — because it builds on an existing mental model (tables, formulas, summaries) before introducing a query language and then a programming language. That pedagogical argument holds regardless of which of Excel or SQL tops a given sample.

Do not cite a false unanimity to defend the order. The corrected #1-or-#2 formulation is strong enough.

Salary context for the home market, from a Vietnamese career guide opened in the research: entry-level data analyst roles in Ho Chi Minh City and Hanoi are listed at 10–16 million VND per month for fresher and junior positions. Against that income, annual subscriptions priced in the hundreds of US dollars are a structural barrier, not a minor inconvenience — a point that returns in Section 5.

## 2. The Interview Layer: How Hiring Actually Tests

Hiring does not test topics in syllabus order. It tests judgment under ambiguity, on messy data, against a clock, out loud. Platforms mostly test recognition and reproduction on clean data, untimed and silently. Almost every gap below traces back to that difference. A curriculum that teaches the same beginner topics inside hiring-shaped tasks closes most of the gap without adding new topics.

### 2.1 SQL interviews: ten patterns and a five-rung ladder

Four independent interview sources converge on the same structure. A typical data SQL interview hands the candidate a small schema and a business-flavored prompt, watches the query being written live or in a timed assessment, and scores reasoning as much as result: clarifying the definition, stating the output grain, handling ties, duplicates, and null values out loud, and writing readable structure with common table expressions instead of one nested block. PostgreSQL is the safe default dialect in the guidance opened, because interviews usually grade logic over dialect trivia and allow lookup leeway on date and time syntax.

**The ten pattern families** (ordered by when they tend to appear in a loop):

1. **Filtered retrieval** — return or count rows meeting layered conditions, including conditions in another table, in text, or in time.
2. **Aggregation and conditional aggregation** — summarize by group; compute several metrics in one pass; turn conditions into metrics with conditional logic inside aggregates.
3. **Joins, including negative and self-referential cases** — combine tables without inflating counts; find rows with no match; compare rows within the same table (for example employees against managers).
4. **Top-N and ranking per group** — pick the best, nth, or top few rows inside each group, with an explicit tie policy. The choice among row-number, rank, and dense-rank behavior is the test.
5. **Time comparison** — rolling averages, lagged and lead comparisons, and bucketing by day, week, or month.
6. **Retention, funnel, and cohort logic** — define a cohort by first event, then measure return or progression in later periods or steps.
7. **Deduplication and latest-row-per-group** — collapse repeated records to one trustworthy row per entity, deliberately, not by sprinkling distinct as a patch.
8. **Pivoting and reshaping** — turn rows into columns, or the reverse, so output matches the report shape asked for.
9. **Set and coverage logic** — prove completeness or overlap across sets, including division-style questions such as customers who bought at least one item from every category.
10. **Performance follow-up** — after a working query, explain how it survives real volume: prune columns, pre-aggregate before joining, reason about indexing. Rarely an opener for analyst roles; a common follow-up, and a larger topic for engineering loops.

**Consistent traps across sources:** joining two many-sided tables before aggregating and inflating counts; three different answers from counting all rows, counting a column, and counting distinct values; confusing filtering before grouping with filtering after grouping; ranking functions that differ only on ties; and a correct query at the wrong grain — one row per order when the question asked for one row per customer per month.

**Difficulty ladder:**

- **L1 Fluency** — single-table filtering, sorting, simple aggregates, one straightforward join, on clean data with a fully specified prompt.
- **L2 Analyst core** — multi-table joins, grouped aggregation with post-group filtering, conditional aggregation, date bucketing, anti-joins. Most analyst screens are decided here.
- **L3 Window fluency** — top-N per group, nth event per user, rolling averages, lag/lead comparisons, deduplication. Tie and duplicate handling must be stated, not assumed.
- **L4 Multi-step reasoning** — retention and cohorts, funnels, coverage logic, two- or three-stage queries where the grain changes between stages, on data containing duplicates, late events, or nulls.
- **L5 Judgment and scale** — the metric itself is ambiguous and must be defined before any SQL is written, or the follow-up concerns performance and design.

Role calibration from the opened role map: Data Analyst and BI Analyst loops sit at Easy–Medium overall; Product Analyst at Medium, adding experiment interpretation; Data Scientist at Medium–Hard, adding statistics, Python, and case work; Analytics Engineer and Data Engineer at Medium–Hard, adding modeling, warehousing, and pipeline reasoning. The SQL core (L1–L3) is shared by all five tracks; roles diverge at L4–L5.

A fixed drill set builds real fluency and is necessary, but it is not sufficient: real prompts replace a precise instruction with a vague business problem that first requires defining the metric, the comparison period, and the minimum data needed to judge. The repair adopted for this curriculum is a four-step lesson loop for every pattern: solve the clean version, re-solve after the schema is mutated with duplicates and nulls, explain the metric in two plain sentences, and retry the same pattern under a short timer.

### 2.2 Excel hiring tests: three formats, ten task types

There is no single standard Excel test. Employers use three formats:

1. **Short multiple-choice screens** — what a formula returns, which reference type survives copying, which feature solves a stated problem. Timed in minutes; tests recognition and speed.
2. **Hands-on simulations** — perform the task inside a spreadsheet-like environment; the system checks the resulting state.
3. **Live or take-home workbook tasks** — work through a real file, watched live or submitted, where the deliverable is a workbook another person can audit, reuse, and trust.

A learner trained only to pick the right menu item is prepared for the first format and exposed in the other two.

**The ten task types:**

1. Tidy and total a list — sort, filter, and total over the correct range, with live formulas rather than hand rearrangement.
2. Fix a broken sheet — find entry errors such as a date stored as text, correct them without breaking formatting, make the sheet print correctly.
3. Look values up across sheets — bring a price or attribute in by code, including codes that do not match, and handle the not-found case deliberately instead of leaving raw errors.
4. Summarize with a PivotTable and answer in words — build the pivot and state the finding. Classic trap: the pivot shows a count instead of a sum because the amount column is stored as text.
5. Clean a messy export — split combined fields, trim stray spaces, remove duplicates on the right key columns, keep the raw data intact.
6. Conditional logic and conditional totals — row-level decisions, plus filtered counts and totals. Argument-order differences between singular and plural conditional functions are a standard trap.
7. References under copying — relative, absolute, and mixed references; predict what a formula becomes when copied down or across. This is the difference between one correct cell and a correct column.
8. Dates, text, and numbers as data — date arithmetic, text joining and extraction, rounding, percentage change with correct order of operations.
9. Presentation layer — a chart chosen for the question, conditional formatting that updates with the data, validation, and labeled outputs another person can follow.
10. Audit and extend a small model (advanced, finance-leaning) — find hard-coded numbers inside formulas, broken references, and inconsistent formulas; explain each error's effect; extend the model consistently; add a scenario switch driven from assumptions held in one place.

**How Excel work is scored:** accuracy (outputs match, right ranges, no missed rows), method (formulas stay live and update when data changes; no hand-typed totals), and clarity (labeled outputs, consistent layout, nothing hidden). Red flags are the mirror image: numbers typed over formulas, describing a PivotTable without being able to build one on the supplied data, unlabeled outputs, stray test calculations left in the file, and unhandled lookup errors. Most employer tests sit at intermediate business level, and pace — not peak difficulty — is what separates scores.

### 2.3 Analytics case questions: six families

The case round tests metric judgment, not calculation. Calculating the wrong thing correctly is scored as a failure. Prompts are intentionally ambiguous — terms such as active user, retention, and engagement are left undefined on purpose — and the expected first move is clarification, not code.

1. **Define the metric** — measure the success of a feature, product, or checkout page. Scored on starting from user and business goals, naming one primary metric plus guardrail metrics that must not degrade, and matching the metric to the goal.
2. **Diagnose a movement** — a metric dropped last week; what do you do? Scored on a fixed order: verify the signal is real (tracking change, outage, holiday, definition change), segment (platform, region, channel, device, new versus returning), locate the funnel step or driver, form a testable hypothesis, recommend a next step.
3. **Design an experiment** — test a new flow or feature. Scored on hypothesis, randomization unit, primary and guardrail metrics, sample-size and duration reasoning including covering a full weekly cycle, success criteria stated in advance, and pitfalls such as stopping early on a first significant result.
4. **Judge a trade-off or read a result** — engagement rose but revenue fell; ship it? Or: the experiment shows a lift; do you believe it? Scored on weighing short against long term, checking data and randomization before celebrating, and proposing an explicit decision rule.
5. **Interpret given work** — the interviewer supplies a query, table, or chart and asks what it calculates, whether it measures the right thing, and what is wrong with the definition. Reading other people's analysis critically, in reverse.
6. **Funnel, retention, and cohort reasoning in spoken form** — where users drop, whether a cohort is genuinely healthier, separating true return behavior from acquisition growth.

Underneath cases C3 and C4 sits a statistics-in-words layer: explaining a p-value in plain language including what it is not, hypothesis tests, confidence intervals, and power intuition — assessed as spoken explanations, not derivations. The recurring machine-learning trap at this level is evaluating a rare-event model by accuracy, where predicting the majority class every time scores highly; precision, recall, and error costs must replace accuracy.

Two adjacent rounds complete the picture. In the **project deep-dive**, interviewers probe why a candidate chose an approach, what the data problems were, how the result was validated, and what they would do differently — a project the candidate cannot explain in depth should not be presented at all. In the **behavioral and stakeholder round**, the test is walking through a past analysis starting from the business question rather than the tools, pushing back on a flawed data request by reframing it, and passing, after any technical answer, the follow-up: so what does this mean for the business?

### 2.4 The Python round and the take-home

For analyst and scientist roles, the Python round is largely the SQL patterns translated into pandas, performed live on a small dataset and judged on idiomatic vectorized code as well as correct output: selection and boolean masking; merge as the join, with relationship validation, origin indicators, and predicting the output row count before running — including row multiplication from duplicate keys on both sides; groupby as a system, including transform for group-level values broadcast back to rows (filling a missing value with its own group's mean rather than the global mean, which gives materially different results) and grouped ranking and lag (an ungrouped shift leaks the previous customer's last value into the next customer's first row); reshaping, where pivot refuses duplicate pairs and pivot-table aggregates them; share-of-total and top-N per group with an explicit tie policy; and cleaning, type awareness, and vectorization over row-wise loops. Engineering tracks add pipeline-shaped work: ingesting messy files and nested payloads, validating keys, snapshot diffing, and writing output a rerun cannot break.

**Take-homes** cut across all four formats above and are a genre with learnable conventions:

- **Shape:** a dataset plus business questions, completed asynchronously. Employers commonly state **2–5 hours of expected effort**, with a return window of about **2–3 days**; actual candidate time often runs longer. Deliverables vary across SQL, a notebook or script, charts, and a short report or slides, often followed by a live walkthrough.
- **Prevalence and trend:** an analysis of over 10,000 interview experiences reported by Interview Query finds **25% of data science interviews still include a take-home**, with some companies phasing traditional take-homes out or replacing them with live case studies as generative AI tools spread. Take-homes should be taught as a current, changing format — not presented as universal or permanent.
- **What is graded:** scoping to the stated time; understanding the data before analyzing it, with quality problems named and logged rather than silently cleaned; answering the question asked; and ending in next steps and a business recommendation. A detailed walkthrough source budgets a four-hour exercise across profiling, staging and quality checks, analysis, validation, communication, and documentation — keeping source files untouched, declaring grain and keys per table, and validating grain reconciliation before interpreting results.
- **Failure modes:** over-building an analysis nobody asked for, polish over answer, an ambitious half-finished submission instead of a finished careful answer to the main question, and work that cannot be re-run or defended line by line in the follow-up conversation.

### 2.5 The gap table, compressed

Fifteen gaps were cataloged in the underlying research. The three critical ones are not advanced topics; they are beginner topics taught with the judgment layer stripped out:

- **Metric definition (critical):** platforms give the metric in the exercise statement; hiring requires choosing, defining, and defending it before computing.
- **Ambiguity (critical):** platform prompts are fully specified with one intended answer; hiring prompts are deliberately vague, and clarifying questions and stated assumptions are scored behavior.
- **Data cleanliness (critical):** platforms supply clean, typed, deduplicated tables; hiring supplies duplicates, nulls, text-stored numbers, late events, and many-to-many joins that inflate totals — and spotting and handling them is the test.

The remaining gaps, in brief: grain discipline; ties, nulls, and edge cases; narration out loud; time pressure; cross-tool translation (the same pattern demanded in SQL, Excel, and pandas); reading and repairing others' work; workbook and code craft; experiment literacy; statistics in words; the take-home genre itself; performance follow-ups; and dialect and version realism. The curriculum response is placement, not volume: a timed hiring simulation at the end of the Excel block, pattern-organized SQL with a grain-first ritual and definition-first retention lessons, pandas taught explicitly as a second representation of the SQL patterns, a dedicated cases module in the advanced core, and two full take-home simulations across the path with their grading lenses published as the lesson.

## 3. Projects and Portfolio: Proof of Work, by Track

### 3.1 The cross-track rule

Every track source states the same rule in some form: **proof of work outweighs credentials, depth outweighs count, and a live or runnable artifact outweighs a description.** A hiring manager may spend only about 30 seconds on an initial portfolio review, looking for immediate evidence the candidate can solve a real problem, explain their thinking, and show results that matter to stakeholders. The three screening pillars are technical competence, business acumen, and communication.

The consensus count is **3–5 polished, well-documented projects**, recurring independently across analyst, science, and platform sources. The one deliberate exception is Data Engineering, where the bar is **2–3 deep projects**. For ML/AI Engineering, one portfolio guide reports a pattern of **4–6 deployed projects** spanning retrieval, an agentic workflow, an MLOps or deployment project, and one fine-tune as consistently landing interviews. Counts are targets for depth, not quotas to fill with clones.

GitHub hygiene is part of the evidence for every technical track: a small number of pinned, well-organized repositories with clear READMEs, meaningful commit history, and no clutter of tutorial repositories burying the real work. For engineering roles the profile is treated as due diligence — the resume is the pitch, the repository is the verification.

### 3.2 What platforms assign, and why it is not enough

Platform work falls into four patterns:

- **Short guided browser projects** (DataCamp pattern): scoped tasks on pre-loaded data, from about 30 minutes to about 1 hour for guided SQL projects, with the task, dataset, and success check all supplied. Structural limit: the learner practices execution inside a known frame rather than framing a problem, and datasets that cannot be downloaded leave finished work trapped inside the platform. The platform's own portfolio guidance names the fix — add a business question, a table description or diagram, each query with output and a one-line finding, a limitations paragraph, and one change made beyond the brief — and advises that three projects with clear write-ups outweigh twelve that stop at the last query.
- **Longer guided projects on downloadable, messy data** (Dataquest pattern): realistic scenarios on real, messy, downloadable datasets, commonly 4–8 hours for beginner projects, rebuildable locally and publishable with documentation. This pattern transfers; the 3–5 polished-project standard is stated here as well.
- **Certificate capstones** (Coursera/IBM pattern): one integrative end project. The older science shape runs a full methodology loop once, on a supplied problem. The newer engineering shape additionally demands governance, operations planning, and an architecture narrative — much closer to what engineering hiring screens for.
- **Competition work** (Kaggle pattern): nothing is assigned; value depends entirely on selection and presentation. Guidance converges on preferring Featured and substantially prized competitions, choosing by target industry and problem type, studying top teams' post-competition write-ups and then building an independent implementation, and treating a finish in roughly the top 10–20% as a strong signal — with the documented process (validation design, what was tried and what failed) worth more than the rank alone. Repeated beginner datasets with near-identical notebooks are the single most recognizable weak portfolio pattern.

Across all four patterns, assigned work reliably provides a clean starting point, a defined question, a bounded dataset, and a checkable endpoint. It reliably under-provides choosing the question, sourcing one's own data, handling production-like breakage, deploying or operating the result, working through version control and review, and writing for a non-technical decision-maker.

### 3.3 Per-track hiring bars

**Data Analyst.** Screened for visible fluency — SQL first as the near-universal requirement, plus Excel or Sheets, one BI tool (Tableau or Power BI are the recurring pair), and increasingly Python — and for at least one full-cycle project: question, data, cleaning and querying, visualization, insight, recommendation. Minimum shape: at least one SQL project, one Python project, and one dashboard project, plus a published dashboard a non-technical reader can use and a README stating what was done, what data was used, and what was found. Visible messy-data work carries disproportionate weight, because cleaning is a large share of real analyst work and the skill most underrepresented in beginner portfolios. Weak framing loses: a title that reads like a manager's question beats a title that names a dataset.

**Data Engineer.** Screened for 2–3 deep projects that mimic a real pipeline end to end — a real problem statement, realistic messy or multi-source data, and a multi-stage design from ingestion through transformation and storage to serving — over many shallow demos. Reviewers scan a recognizable stack (orchestration, distributed processing, transformation and modeling, a cloud warehouse, Git) for how tools were applied, not merely that they appear. Engineering quality is scored directly: modular code, a reproducibility file or container definition, error handling and logging, and thought about reruns, mid-pipeline failure, and duplicate prevention. Reliability evidence is expected: validation and quality checks, tests, retry and failure handling, backfill thinking, and incremental loading rather than full reloads. The README is read before the code; a sparse README ends the review.

**Data Scientist.** Portfolios are scored on five dimensions: problem framing (a specific problem with a named stakeholder, decision, and success definition); data realism (messy, multi-source, or self-collected data with documented cleaning — repeated use of the most common beginner datasets is named in multiple sources as an instant negative signal); evaluation rigor (an appropriate metric rather than accuracy alone on imbalanced data, a baseline, proper validation, error analysis, and honest limits); deployment thinking (packaging, an API, a dashboard, or at minimum a credible account of implementation, retraining, and monitoring — notebook-only work is the standard failure mode); and communication (a case-study narrative a non-specialist can follow quickly). Impact outweighs leaderboard score, domain coherence outweighs scatter, and Kaggle work should be presented as Problem–Solution–Impact with validation strategy documented. Interview-focused guidance prefers 1–2 deeply told stories within the broader 3–5 range.

**Analytics Engineer.** The narrowest and most legible bar of the five. One serious dbt project beats three shallow ones. The expected shape is precise: a public dataset loaded into a cloud warehouse, a layered project (staging per source, intermediate where needed, marts per business area), tests on every primary key plus custom tests where warranted, model documentation, a published repository whose README explains the modeling decisions, and optionally a BI layer proving the models serve real queries. Modeling fundamentals come before tool features — grain, facts and dimensions, surrogate keys, and star-schema trade-offs are what interviewers probe, and a project whose grain is wrong fails regardless of advanced features. Tests and documentation are the screening filter: a dbt project with no tests is read as a tutorial copy. The surrounding workflow — Git with branches and pull requests, code review, CI checks — is what separates the role from an analyst who writes SQL. Current roadmap extensions add a metrics or semantic layer with a KPI dictionary, a data-quality incident project, and a funnel or cohort mart.

**ML/AI Engineer.** The dividing line is unambiguous: **deployed systems beat notebooks.** A portfolio that stops at a notebook with a high accuracy number says nothing about running a model in production, and a notebook-only portfolio loses quickly to one clickable live API. Expected proof, in maturity order: a model wrapped in an API with input validation and a health endpoint, containerized and deployed to a reachable target with the live URL at the top of the README; experiment tracking with logged runs and a model registry; data and model versioning with a reproducible pipeline; automated tests and CI that can fail a build on a quality drop; an orchestrated training pipeline that registers a new model only on improvement; and monitoring for drift, performance, latency, and cost with alerting and a retraining trigger. For LLM work specifically, employers ship retrieval over proprietary data far more often than custom fine-tunes, because retrieval is cheaper and easier to update — so a strong portfolio leads with production-quality retrieval (chunking, a real vector database, reranking, and an evaluation harness), includes an agentic workflow with tool use, and adds one fine-tune to prove training-loop understanding, with guardrails, structured-output validation, prompt versioning, and per-request cost tracking throughout. Evaluation rigor is a hiring requirement, not a bonus. Kubernetes is explicitly unnecessary at portfolio stage; a clean container plus CI/CD deployment is sufficient.

### 3.4 The ten gaps between assigned and expected

1. **Problem framing** — supplied versus self-chosen and scoped, with stakeholder and decision named.
2. **Data realism** — clean, single-source, sometimes non-downloadable versus messy, multi-source, self-collected, with documented cleaning.
3. **Originality** — the same project completed by every learner in a cohort versus work that does not look identical to hundreds of other applicants.
4. **Deployment and operations** — ends at a notebook or in-platform dashboard versus a live artifact with container, CI/CD, monitoring, or an incident plan. Critical for ML/AI; high for Data Engineering.
5. **Engineering workflow** — solo browser work versus Git history, branches and pull requests, tests, CI, and a reproducible environment. Critical for Analytics Engineering, Data Engineering, and ML/AI.
6. **Testing and data quality** — output matches the expected answer versus visible tests on keys and logic, quality checks, validation gates, and failure handling.
7. **Evaluation and honesty** — a single headline metric versus baseline, appropriate metric, validation design, error analysis, and a limitations paragraph.
8. **Communication for decision-makers** — code and charts as the deliverable versus a case-study narrative readable in about two minutes: summary, finding in business terms, recommendation, limitations.
9. **Architecture and trade-offs** — rarely required versus a diagram plus written reasoning about grain, layering, tool choice, and cost.
10. **Domain coherence** — projects scattered across unrelated sample domains versus two or three projects aimed at one target industry, forming a narrative.

Three gaps drive the design below. The **transfer gap**: any project that cannot be exported to a public repository with a README fails its portfolio purpose by construction. The **beyond-the-brief gap**: the single change a learner makes beyond the supplied brief is what distinguishes their project from every other completer's, so assigned work needs a mandatory open extension. The **production gap**: for the three engineering-leaning tracks, the screened skills — orchestration, testing, CI, serving, monitoring — are precisely the skills most guided projects omit.

### 3.5 The capstone ladder for Data From Zero

Design rules for all tracks:

- **Four rungs per track.** Rung 1: guided core (supplied question and data). Rung 2: messy-data rebuild (same skill, self-sourced or deliberately dirty data). Rung 3: end-to-end build (full track workflow, with tests, evaluation, and documentation as appropriate). Rung 4: capstone (self-framed problem, deployed or published artifact, case-study write-up). Learners publish Rungs 2–4; Rung 1 is practice.
- **One portfolio packet at every published rung:** public repository; README opening with a one-sentence business problem; architecture or workflow diagram where relevant; how-to-run instructions; results in business terms; a limitations paragraph; and a beyond-the-brief note stating what the learner chose or changed.
- **One domain thread per learner,** picked early and carried through at least Rungs 3–4, so the finished portfolio reads as a coherent story for one industry's hiring managers.
- **Review like a hiring manager:** a two-minute scan test first (can a reviewer state the problem, approach, and result from the README alone?), then a deep review against the track bar in Section 3.3.

**Data Analyst ladder.** Rung 1: guided SQL and exploration — a supplied business question set on one dataset, then a Python exploration of a second. Rung 2: messy-data cleaning story — combine two inconsistent sources, document every cleaning decision, analyze the combined result. Rung 3: dashboard plus recommendation — an interactive dashboard paired with a one-page written finding ending in a recommendation. Capstone: end-to-end business case study in the target industry — SQL extraction, Python analysis, dashboard, and a stakeholder-style presentation (memo, slides, short recorded walkthrough) stating the decision the work informs and how success would be measured.

**Data Engineer ladder.** Rung 1: ingestion and ETL basics — an API ingestion pipeline into a relational database with validation and error handling, plus an automated file ETL that detects new files, validates schema, rejects bad files, and logs status. Rung 2: warehouse build — a dimensional model (facts, dimensions, star schema) with a diagram and the business questions the warehouse must answer. Rung 3: orchestrated, incremental pipeline — orchestration, incremental loading with idempotent reruns, quality checks, retries and failure alerts, a layered raw-to-cleaned-to-business-ready layout, containerized for reproducibility. Capstone: end-to-end data platform — multi-source, on a cloud warehouse or lakehouse (free tier acceptable), with transformation layer, tests, CI checks, monitoring, architecture diagram, a serving layer, and an operations note covering what breaks, how it is detected, and how it is recovered. A streaming extension is the stretch variant.

**Data Scientist ladder.** Rung 1: full methodology loop, guided — one supplied problem through collection, wrangling, exploration, visualization, modeling, evaluation, and a stakeholder report. Rung 2: real-data rebuild — the same loop on self-sourced or multi-source messy data in the target industry, graded primarily on data realism and evaluation rigor. Rung 3: domain modeling project — a deeper second project in the same industry (forecasting, churn, or recommendation), documented as a Problem–Solution–Impact case study; a carefully chosen completed Featured competition, rebuilt independently with a full write-up, may substitute. Capstone: deployed decision product — a self-framed problem delivered as something a decision-maker can use (an API, an interactive dashboard, or a scheduled report), with a deployment and monitoring note and a final presentation to a non-technical audience.

**Analytics Engineer ladder.** Rung 1: SQL engineering drills — advanced SQL on a warehouse (deduplication, window functions, incremental logic, duplicate-row debugging) with formatted, reviewed code in Git from the start. Rung 2: first dbt project — single source, staging and marts layers, primary-key tests, model documentation, running against a cloud warehouse free tier. Rung 3: multi-source modeling project — staging per source, intermediate layer, marts per business area, snapshots or incremental models where warranted, a full test suite, published documentation and lineage, a CI check on pull requests, and a README defending grain and key choices. Capstone: one serious analytics platform — warehouse load, layered dbt project, a metrics or semantic layer with a KPI dictionary (definitions, owners, caveats), a data-quality component (tests, freshness, an incident write-up), and a BI layer proving the models serve real business questions. Done deeply, this single capstone is the portfolio.

**ML/AI Engineer ladder.** Rung 1: tracked, versioned modeling — a classifier trained with experiment tracking across logged runs, the best model registered, data and model under version control with a reproducible pipeline definition. Rung 2: served model — an API with input validation and a health endpoint, containerized, with automated tests and CI that can fail on a quality regression, deployed to a live URL linked from the README. Rung 3: production loop — an orchestrated training pipeline (validate, train, evaluate against the current best, register only on improvement), monitoring for drift, latency, and cost with alerting, and a retraining trigger. Capstone: a shipped AI system in one primary shape — a production retrieval system over a real document set (the default recommendation), an agentic system with tool use and production guardrails, or a classical ML platform with CI/CD, continuous training, and a monitored endpoint. Every capstone variant adds an architecture diagram, one measurable operating result (latency, cost, or quality), and a short recorded demo; retrieval- or agent-based capstones add one fine-tuning build as a supporting project.

Deliberate exclusions: no rung's only artifact is a notebook or a platform-internal page; the most overused beginner datasets are reserved, if used at all, for ungraded practice, never for portfolio rungs; project counts are published as the ranges above and assessed by depth against the track rubric, not tallied; and the case-study README is a graded deliverable at every published rung, because communication is a screened dimension in every track.

## 4. Certification Map: What the Big Exams Test, and How the Path Aligns

Certifications are used here as public blueprints — checklists of what established issuers consider testable — never as lesson sources, and alignment never promises exam readiness from any single module. Eight certifications were mapped in full in the underlying research. Prices, durations, and scores are stated only where an official page or exam guide opened in the research stated them; where verification could not confirm a figure from an official page, the figure is labeled or omitted, by design.

### 4.1 The eight certifications in brief

**1. Google Data Analytics Professional Certificate (Google, via Coursera) — entry level.** A multi-course program, not a single proctored exam. The Coursera program page describes nine courses and over 180 hours of instruction, completable in under six months at under 10 hours per week, at $49 per month in the United States and Canada after a free trial. (Other Google and review pages state different course counts and hour totals for this program; the figures here are the Coursera program page's own.) It tests the full analyst workflow — framing a question, preparing and cleaning data in spreadsheets and SQL, analyzing, and sharing findings with visualizations, dashboards, and presentations, primarily with Tableau — plus introductory Python for analysis. The current program teaches Python and explicitly does not cover R. Its capstone-style case study is the only end-to-end portfolio artifact required by any certification in this map. It does not emphasize deep statistics, machine learning, pipelines, or cloud platforms.

**2. Microsoft Office Specialist: Excel Associate, Exam MO-210 (Microsoft, via Certiport) — associate level.** A performance-based exam taken live inside Excel. Five domains, with weightings confirmed from Microsoft's official skills outline: manage worksheets and workbooks (25–30%); manage data cells and ranges (25–30%); manage tables and table data (10–15%); perform operations using formulas and functions (15–20%), including references, basic aggregations, IF, text functions, and dynamic-array functions; and manage charts (15–20%). The balance is the signal: workbook management and cell and range handling together outweigh formulas — file hygiene, formatting, and navigation are certifiable skills, not assumed background. The official certification page confirms scheduling through Certiport and preparation guidance of about 150 hours of instruction and hands-on experience, and states that price is based on the country or region where the exam is proctored. **No fixed US voucher price is stated as an official fact in this package** — secondary-guide figures for a voucher price are not republished here, because official pages give no fixed US price and secondary sources disagree. A passing score of 700 and a 50-minute duration are reported **per secondary guides**; neither was visible on the official MO-210 pages opened during verification, so neither is stated here as an official fact. A separate Expert exam (MO-211) covers advanced formulas, macros, PivotTables, and advanced charts; Associate is the baseline target, Expert topics are a later stretch — notably, PivotTables and lookups, which analysts need immediately, sit in the Expert direction and must be taught as post-Associate skills without misleading learners about what Associate covers.

**3. Microsoft PL-300: Power BI Data Analyst (Microsoft) — associate level.** The clearest public blueprint for a complete BI workflow in one tool. Four domains from Microsoft Learn's study guide (skills measured as of April 20, 2026): prepare the data (25–30%), including Power Query transformation and building fact and dimension tables; model the data (25–30%), including relationships, a common date table, and DAX measures with time intelligence; visualize and analyze the data (25–30%), including storytelling, usability, and pattern-finding such as grouping, forecasting, and outlier detection; and manage and secure Power BI (15–20%), including workspaces, refresh scheduling, workspace roles, row-level security, and sensitivity labels. Candidates are expected to be proficient with Power Query and DAX. A score of 700 or greater is required to pass, per the study guide. Three domains weighted equally means visualization skill alone is explicitly not enough.

**4. Microsoft DP-900: Azure Data Fundamentals (Microsoft) — fundamentals level.** A concepts exam, not a hands-on analyst exam. Four domains from the study guide (skills measured as of July 21, 2026): describe core data concepts (25–30%) — data shapes, file formats, transactional versus analytical workloads, and the responsibilities of data roles; identify considerations for relational data (20–25%) — normalization, common SQL statements and database objects; describe considerations for non-relational data (15–20%); and describe an analytics workload (25–30%) — ingestion and processing, analytical stores, batch versus streaming, and visualization concepts. A score of 700 or greater is required to pass, per the study guide. Its durable value is vendor-neutral: the concept spine underneath the Azure product names is exactly the conceptual layer a beginner needs before any cloud console is opened.

**5. AWS Certified Data Engineer — Associate, DEA-C01 (AWS) — associate level.** The heaviest pipeline credential in the map, aimed at candidates with the equivalent of 2–3 years of data engineering experience including 1–2 years hands-on with AWS services. Format from the exam guide: multiple-choice and multiple-response questions, 50 scored plus 15 unscored, scaled scoring from 100 to 1,000, minimum passing score 720. Domains: data ingestion and transformation (34%); data store management (26%); data operations and support (22%); and data security and governance (18%). Supporting knowledge named in the guide includes Git, networking, storage and compute concepts, and SQL on AWS services. The guide explicitly places machine learning training and inference, language-specific programming syntax, and drawing business conclusions out of scope — a useful boundary marker between engineering and analysis roles. This certification belongs at the end of a data engineering track, not in a beginner path.

**6. AWS Certified Cloud Practitioner, CLF-C02 (AWS) — foundational level.** Overall AWS Cloud knowledge, independent of a specific job role, for a target candidate with up to six months of AWS exposure. The AWS CLF-C02 exam guide itself (cited here directly, not via any proxy copy) states four domains with weightings verified from the guide text: Cloud Concepts **24%**, Security and Compliance **30%**, Cloud Technology and Services **34%**, and Billing, Pricing, and Support **12%**, each as a share of scored content; 50 scored questions plus 15 unscored; and a minimum passing score of 700. Coding, designing cloud architecture, troubleshooting, implementation, and load and performance testing are explicitly out of scope. Data work is tested only as service recognition inside Cloud Technology and Services — identifying which service family fits a described analytics or AI/ML need. **No price is published in this package for CLF-C02:** neither the guide nor an official AWS page opened during verification stated one, and duration is likewise unverified. Treat this certification as evidence that employers value basic cloud vocabulary for non-engineering staff — at most, a short, late, optional service-recognition explainer. It should not shape the depth of any lesson.

**7. Google Cloud Associate Data Practitioner (Google Cloud) — associate level.** The closest cloud-vendor analogue to a working analyst-plus-practitioner role. Format from the official certification page: 2 hours, $125 registration fee plus tax where applicable, 50–60 multiple-choice and multiple-select questions, 3-year validity, no prerequisites, and 6 or more months working with data on Google Cloud recommended. Google does not state a numeric passing score on the opened pages, so none is given. Domains from the official exam guide: data preparation and ingestion (about 30%); data analysis and presentation (about 27%), including SQL in BigQuery, notebooks, Looker dashboards, and introductory machine learning through BigQuery ML and AutoML; data pipeline orchestration (about 18%); and data management (about 25%), including least-privilege access, lifecycle rules, and encryption. Notably, introductory ML is tested through SQL rather than Python model code.

**8. Google Cloud Professional Data Engineer (Google Cloud) — professional level.** The ceiling of a data engineering track, not its starting point. Five sections from the official exam guide (version 4.2): designing data processing systems (about 22%) — security and compliance, reliability, flexibility, and migrations; ingesting and processing data (about 25%) — batch and streaming pipelines and their deployment; storing data (about 20%) — storage selection by access pattern, cost, and performance, warehouse and lake design; preparing and using data for analysis (about 15%) — visualization preparation, data preparation for ML including unstructured data for embeddings and retrieval-augmented generation, and data sharing; and maintaining and automating workloads (about 18%) — cost optimization, repeatable orchestration, monitoring, and fault tolerance. Even at professional level, analysis preparation is the smallest domain; the center of gravity is design judgment under constraints. Format details not stated in the opened guide — fee, duration, question count — are not claimed here.

### 4.2 What the cross-certification matrix shows

- **No single certification covers the whole beginner-to-job path.** Analyst credentials barely touch cloud engineering; engineering credentials barely touch storytelling, and the AWS engineering guide excludes drawing business conclusions outright. Following only one blueprint leaves a visible hole.
- **Cleaning, SQL, and modeling recur everywhere hands-on work is tested.** Every hands-on certification in the map rewards profiling and fixing data, querying with SQL, and structuring data into tables with clear relationships. Those are safe universal bets for core curriculum time.
- **Security and governance grow with level; they do not start at zero.** Beginner material frames ethics, privacy, and appropriate sharing; associate material adds access control and row-level security; professional material adds encryption keys, sovereignty, and federated governance. The topic should spiral, not appear once.

### 4.3 Alignment recommendations

1. **Anchor the Excel block to the MO-210 blueprint, then go one step past it.** Use the five domains as the completeness checklist, weight practice the way the exam does (more time on workbooks, formatting, and ranges than on exotic formulas), and add PivotTables and lookups immediately after, flagged honestly as post-Associate, Expert-direction skills. A timed, live-in-Excel practical of about 50 minutes mirrors the credential's format without using any of its tasks — with the duration understood as per secondary guides, as noted above.
2. **Make the single SQL block satisfy three blueprints at once.** The same block can serve the Google certificate's query-to-clean-and-analyze workflow, DP-900's relational concepts (features, normalization, common statements and objects), and the Google Associate Data Practitioner's expectation of writing SQL in a warehouse to answer a business question. Add one relational-versus-non-relational decision lesson, and end the block with a warehouse-style exercise on a larger read-only dataset with a short written conclusion.
3. **Position Python as the Google certificate now does — after spreadsheets and SQL.** Python for analysis in notebooks, as a productivity upgrade on problems learners have already solved in Excel and SQL, with no cloud SDKs, pipeline frameworks, or model training in the first block. End the core path with one end-to-end case — question, preparation, cleaning, analysis, visualization, recommendation — repeating the Google certificate's strongest design choice and producing the artifact employers can actually inspect.
4. **Build the advanced core around the PL-300 workflow, taught tool-neutrally first.** Connect and profile, clean and transform, model as facts and dimensions with a date table, calculate measures, visualize for self-service use, then publish with refresh and access control. Name the concepts (star schema, measure versus column, row-level security) tool-neutrally so lessons survive a tool change, and do not skip the final domain — refresh, distribution, roles, row-level security, and sensitivity labels are the topics self-taught analysts most often miss entirely. PL-300's pattern-finding layer (grouping and binning, reference lines, forecasting, outlier detection) serves as the curriculum's applied statistics moment at this stage.
5. **Add one vendor-neutral cloud concepts module before any cloud track.** The reusable spine on which DP-900 and the Google associate exam agree: data shapes and file formats, transactional versus analytical workloads, relational versus non-relational stores, batch versus streaming, warehouse and lake patterns, ETL versus ELT, lifecycle and archiving, least-privilege access, and encryption at rest and in transit. After that module, each vendor track is a thin mapping layer — same concepts, that vendor's service names. Cloud Practitioner-level material stays in its place: a short vocabulary explainer, clearly labeled as vocabulary, not skill.
6. **Reserve pipeline engineering for the Data Engineering track, at full weight.** Both engineering certifications put ingestion and transformation first (34% for AWS Data Engineer; about 25% for Google Professional Data Engineer, with design and storage adding most of the rest). Open the track with pipelines — batch and streaming ingestion, transformation, orchestration and scheduling, cataloging and schema management, quality checks, monitoring and logging, cost and performance tuning — teach storage selection as a decision under constraints, and treat governance (authentication, authorization, encryption, privacy, lineage, audit logging) as engineering work, not an appendix. Mark the role boundary early, using the AWS guide's scope line as the teaching point in paraphrase: engineering exams do not test drawing business conclusions or training ML models.
7. **Introduce machine learning the way the Google associate blueprint does — through SQL and use cases first.** Identify a use case, create and train a model with SQL, evaluate it, use it for prediction, and register it. Defer feature engineering at scale, embeddings, and retrieval preparation to professional-direction material, where the Google Professional Data Engineer guide places them. Treat AI visuals and assistant features as a literacy topic — what they do, when to distrust them — not as a substitute for choosing a visual or writing a measure.
8. **Spiral security, ethics, and governance across every stage.** Excel and SQL stage: file hygiene, not sharing raw personal data, documenting sources. Python and BI stage: access control on shared reports, row-level security, sensitivity labels. Cloud and engineering stage: least-privilege access, encryption keys and data residency, lifecycle and deletion rules, backup and recovery. Revisiting the same dataset with stronger controls teaches governance as a property of the work.
9. **Use blueprints as checklists, never as lesson sources — and recheck them on a fixed cycle.** Publish a mapping from each module to the certification domains it supports, and where a module claims alignment, add a checkpoint in the certification's format: timed practical for Excel, scenario-based questions for cloud concepts, an end-to-end modeled report for BI, a pipeline design exercise for engineering. Two blueprints in this map carry skills dates within the last year (PL-300 as of April 20, 2026; DP-900 as of July 21, 2026), so any alignment claim older than about twelve months should be treated as stale until reverified against the issuer's current study guide.

Gaps the certifications leave, which this curriculum can own: serious inferential statistics (no beginner or associate certification in the map tests it); reproducibility and version control (only the AWS engineering guide names Git as expected background); genuinely messy real files, sourced and documented with a data diary rather than cleaned inside a tidy sandbox; and communication for non-analysts, rewarded explicitly by only two of the eight blueprints.

## 5. Positioning and Viral Lessons

### 5.1 What incumbents promise, and who is left out

- **DataCamp** promises interactive in-browser coding from lesson one, a path for every goal, career tracks, and exam certifications. Its free tier is the first chapter of every course only. Use one dated price formulation everywhere: **list price about $28 per month billed annually; the pricing page simultaneously promotes an $11 per month special price** (read 2026-11-15). DataCamp's own pages state different catalog and track hour totals in different places, so no single total is presented in this package as the total. Instruction is in English; subtitles do not teach a learner to read an English error message or write an English query comment.
- **Coursera** promises university and brand-name credentials and career outcomes. Its free mode is a preview without the credential, and its format is video-lecture-first — learners who need doing more than watching, and learners for whom the certificate is not the point, are underserved.
- **Dataquest** promises learning without videos, code from lesson one, real datasets, and honest time estimates. Content is in English only, and it offers enrollment in a path rather than a map of everything.
- **freeCodeCamp** is 100% free as a public charity, with courses, projects, and certifications. Its core curriculum is developer-first, its data science offering is one branch among many measured in years, and it offers no spreadsheet on-ramp for Office workers.
- **Codecademy** promises interactive lessons, guided paths, and portfolio projects behind a free tier that comparisons describe as a funnel to its paid tier. Courses are in English only.
- **Udemy** is a marketplace: any topic, any instructor, frequent discount pricing. A catalog of thousands of near-duplicate courses is the opposite of one committed order, and quality varies by instructor.
- **roadmap.sh** offers free, community-created visual roadmaps — click a node, read about the topic. It teaches nothing itself: nodes link out to scattered, mostly English resources, with no datasets, no drills, and no local job-market layer.

The underserved audiences follow directly. **Non-English-first learners**, with Vietnamese as the beachhead, pay a double tax — learning the skill and the language of instruction at once — while local supply is paid academies and text roadmaps without interactive practice. **Career switchers from business and Office backgrounds**, the most repeated beginner story in the discussion syntheses, hold a real asset (spreadsheet fluency and business context) that developer-first platforms treat as zero; one transition guide frames the route at 3–6 months if the path builds on the Excel they already have instead of restarting them as generic beginners. **Learners who need job tasks, not theory or certificates** repeat one verdict across discussions: certificates alone do not get people hired; demonstrable work does. **Learners defeated by choice itself** ask not what SQL is but what to learn first and in what order — and the named failure mode, weeks jumping between courses with no order and no deadlines, is the most common drop-off pattern in the team's own learner listening as well. And **learners in price-excluded markets generally** face the same US-dollar subscription wall across Southeast Asia, South Asia, Africa, and Latin America.

### 5.2 What actually gets shared: seven mechanics

1. **A picture of the whole journey.** A static roadmap image is screenshot-able, printable, and forwardable in a way a course catalog never is. The developer-roadmap repository behind roadmap.sh showed about 372,000 stars on its page when opened for this research, and its README ships share badges for major social platforms — the project asks to be shared. The artifact that spreads is the map, not the lesson.
2. **Free, ordered, and open — creators amplify it for you.** A free ordered path is content other creators can make videos about. The OSSU data-science curriculum repository stands at about 22K stars (November 2026), and creator videos walking viewers through free curriculum repositories reliably field one dominant comment request: the link. (For scale, the companion OSSU computer-science repository stands at about 211K stars, November 2026 — counts are date-stamped approximations because live counters drift weekly.) Distribution of this kind cannot be bought; it is earned by being safely recommendable.
3. **No account, no paywall, no upsell at the moment of need.** Free practice resources earn their place in recommendation lists with the same reasoning: short explanation, exercise against a real database, instant feedback — and no signup ambush that would embarrass the person who recommended them.
4. **A public commitment device with a named handle.** The long-running 100-days-of-coding pattern has two rules — practice at least an hour daily, post progress publicly every day — plus encouraging two others. Within 18 months it grew from one person's commitment to thousands of posts a day, and every learner's progress post is a small advertisement for the system. A named, time-boxed challenge turns learners into the distribution channel.
5. **A downloadable, checkable artifact.** Roadmap guides built around a free downloadable PDF, and checklists and progress trackers generally, convert a web page into a file that lives on the learner's machine and gets forwarded.
6. **An outcome you can show, not a badge you can list.** A finished project — a dashboard, a public notebook, a written-up analysis — is itself shareable content that advertises the path that produced it. Certificates are screenshots; projects are stories. This is the sharing corollary of Section 3's hiring rule.
7. **Public-good framing lowers the social cost of sharing.** A charity or open-license model makes sharing feel like helping, not marketing. Data From Zero's license for the whole repository is CC BY 4.0: anyone may legally re-share and re-teach the material, which no subscription platform can permit.

Discussion evidence behind these mechanics is paraphrased, pattern-level material gathered through search excerpts and aggregating articles; each pattern above repeats across at least two independent sources, but none of it is a population statistic, and it is used here as positioning judgment, not as market measurement.

### 5.3 Five positioning moves incumbents cannot copy quickly

1. **Vietnamese-first, not subtitled.** Build the path natively in Vietnamese — explanations and analogies in Vietnamese, job vocabulary kept in English — with the English edition as the parallel track. Incumbents cannot copy this quickly because their content factories are English-first pipelines whose non-English offer tops out at subtitles over English exercises, or English only outright. Retooling thousands of interactive exercises into native instruction is a rebuild, not a toggle, and a single home market that is too small to justify that rebuild at subscription price points is exactly the right size to be a focused site's home market.
2. **The whole path free, with no account and no funnel, as a stated public good.** Not a free tier: the entire Excel → SQL → Python → tracks path, drills and projects included, readable and usable without signup, under CC BY 4.0. Incumbents cannot copy this because their revenue is the paywall — a first-chapter free tier and a preview-without-credential free mode are deliberate sampling funnels, and matching everything-free would cannibalize the subscription base that funds them. The one large exception needed a charity model and a decade, and still offers no data-first, Excel-first path.
3. **One committed order with deadlines and pass/fail checkpoints — an anti-catalog.** Exactly one path, in one order, with week-sized stages and a you-may-proceed-when-you-can-do-this gate at each stage. Marketplaces and broad catalogs cannot copy this because they monetize breadth; telling learners to ignore most of the catalog contradicts the catalog pitch. The order itself is validated by the corrected demand evidence in Section 1 (Excel and SQL at the top, order sample-dependent, with the sequence defended on learning grounds) and by the finding that order is the first beginner question.
4. **Job tasks and a portfolio as the finish line, localized to the home job market.** Every stage ends in a workplace artifact — a monthly sales report, a churn query, a dashboard a manager could read — and the path's finish line is the project evidence of Section 3, with examples, datasets, and salary expectations drawn from the local market rather than US medians. Incumbents cannot copy this quickly because they sell certificates and cannot demote certificates below portfolios without devaluing their own product, and because per-country editorial localization is work their global templates do not do.
5. **An open, forkable roadmap with a named public challenge on top.** Publish the roadmap as an open artifact that teachers, creators, and learners can fork, translate, and correct, and run a recurring named cohort challenge in the public-progress pattern of mechanic 4, so learners distribute the path themselves. Incumbent content lives inside closed platforms optimized for enrollment, not remixing. The open-roadmap engine is proven at large scale, but the leading open roadmap stays a map of links — it does not teach, drill, or localize. The open position is the gap between a map that does not teach and teaching that is paywalled and English-only: an open map that actually teaches, in the learner's language, for free.

### 5.4 Honest limits

Incumbent learner counts are the organizations' own homepage claims and are reported as claims, not audited figures. List prices rotate with promotions, which is why Section 5.1 fixes one dated formulation instead of quoting whichever price a given page happens to show. No search-trend data is claimed anywhere in this file: trend tooling could not be opened during the research, and job-market evidence was used instead — arguably the better signal for a careers-first site, but a trends pass remains an open follow-up. And the demand table in Section 1 should be rebuilt, not merely re-dated, at each curriculum cycle: its own rows show that shares move materially between samples only a year or two apart.
