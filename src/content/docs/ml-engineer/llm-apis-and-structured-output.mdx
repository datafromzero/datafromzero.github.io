## The question

The help box of the site should send each question to the lesson that answers it. A model can do that in one request, if its reply is something code can read and trust. *How do you send the request, get JSON that code can check, and know what each request costs?* Four of the 16 questions, with the lesson that answers each:

| question | lesson |
|---|---|
| Why does WHERE customer_id = NULL never return a row? | null-handling |
| What is the difference between WHERE and HAVING? | group-by-having |
| Can I filter on the result of a window function in WHERE? | window-functions |
| Which WHEN wins when two tests are both true? | case-expressions |

By the end you can read the counts a reply carries, set the temperature, require and validate JSON, keep prompts as versioned code with a test, and say whether a prompt fits a budget.

**Match.** In [*Data from an API and from a database*](/python/apis-and-web-data/) a request went out and a status code and JSON came back. A request to a model is the same shape: messages and settings go out, and text and token counts come back.

**Diverge.** A weather API gives the same answer to the same request. A model may not, and a reply that looks like JSON may not be JSON. Units 2 and 3 are about that.

</Aside>

### 1. A request and its reply

**Idea.** A request is a list of *messages*, each with a role (`system` for the rules, `user` for the question, `assistant` for earlier replies) and a text, plus settings such as the longest reply allowed. The reply carries two counts: the *prompt tokens* the model read and the *completion tokens* it wrote. A hosted API usually returns the same two counts and prices them separately (no provider was checked for this lesson).

**Try it:** send one question, then print the tokens of the message alone, the prompt tokens of the request and the completion tokens, and the text the model really reads.

```python
messages = [{"role": "user", "content": "In one sentence, what does COALESCE do in SQL?"}]
reply = chat(messages, max_new_tokens=60)
print(reply["text"])
print(len(tok(messages[0]["content"])["input_ids"]), reply["prompt_tokens"], reply["completion_tokens"])
print(tok.apply_chat_template(messages, tokenize=False, add_generation_prompt=True))
```

**Predict:** The message below is a number of tokens. How many tokens will the request count, and how many will the model write? Will the request be more or less than the message?

### 2. Temperature

**Idea.** The model scores every token that could come next. `chat` turns sampling off at temperature 0, which the Hugging Face docs call greedy decoding: the model takes the highest score every time. Above 0 it samples from the scores, and a higher temperature spreads the choice; `do_sample` switches sampling on. The model's repository has a `generation_config.json`; at the pinned revision it holds token numbers and no sampling values, and `chat` passes its own settings, so no reply depends on that file.

**Try it:** ask for the name of a cafe five times with five seeds, at temperature 0 and at 1.0.

```python
request = [{"role": "user", "content": "Suggest a name for a small cafe that sells coffee and SQL books. Reply with the name only."}]
for temperature in [0.0, 1.0]:
    names = [chat(request, max_new_tokens=12, temperature=temperature, seed=seed)["text"].strip() for seed in range(5)]
    print(temperature, len(set(names)), names)
```

**Predict:** How many different replies will each set of five hold?

<details>
<summary>Reveal the result</summary>

```text
0.0 1 ['Cafe SQL', 'Cafe SQL', 'Cafe SQL', 'Cafe SQL', 'Cafe SQL']
1.0 5 ['SQL Brew', 'Cozy SQL Nest', 'CoffeeCode Corner', 'CoffeeSQL', 'Code Brew Café']
```

</details>

*Why:* The columns are the temperature, the number of different replies, and the five replies. At 0 all five are the same name; at 1.0 the five seeds gave five different names. The temperature did not change what the model knows, only how much its choice varies. Use 0 when code or a test depends on the reply being the same next time, and a higher value only when variety is the point.

### 3. Ask for JSON, then check it

**Idea.** Code needs a reply it can parse, so there are two steps: ask for JSON in the prompt, and check the reply against a *schema*, a description of the fields and the values allowed. Pydantic's `model_validate_json` parses and checks a JSON string in one call; a failure raises a `ValidationError`, and each error has a type, listed on its error-types page. A reply can fail in two ways: it is not JSON, or it is JSON that breaks the schema, with a value that is not allowed or a field that is missing. After a failure, `repair` sends the model its own reply and the type of the error once. The Granite model card lists text extraction and function calling among the capabilities of the model and makes no promise about valid JSON, so the checking is the job of the code.

**Try it:** route the 16 questions with two versions of the prompt, check every reply with `Route`, count the error types and the failed replies that still name the right lesson in their raw text, and then give each failed reply of v2 one more try.

```python
class Route(BaseModel):
    lesson: Literal[tuple(LESSONS)]                                           # one of the eight names, nothing else
    reason: str


PROMPTS = {
    "v1": "Reply with JSON only, with the keys lesson and reason. The lesson is the name of the SQL lesson that answers the question.",
    "v2": "You route learner questions to lessons. Reply with JSON only, like {\"lesson\": \"ctes\", \"reason\": \"one short sentence\"}. "
          "The value of lesson must be exactly one of: " + ", ".join(LESSONS) + ".",
}


def checked(reply):
    """The reply with the lesson it names, or the type of its error."""
    try:
        return {**reply, "lesson": Route.model_validate_json(reply["text"]).lesson, "error": None}
    except ValidationError as problem:
        return {**reply, "lesson": None, "error": problem.errors()[0]["type"]}


def ask(version, question, temperature=0.0):
    """One routing request with the prompt of a version."""
    return checked(chat([{"role": "system", "content": PROMPTS[version]}, {"role": "user", "content": question}], max_new_tokens=80, temperature=temperature))


def repair(version, question, first):
    """One more try for a reply that failed: the model sees its own reply and the type of the error."""
    messages = [{"role": "system", "content": PROMPTS[version]}, {"role": "user", "content": question}, {"role": "assistant", "content": first["text"]},
                {"role": "user", "content": f"That reply failed the check ({first['error']}). Reply again with the JSON only."}]
    return checked(chat(messages, max_new_tokens=80))


def named(row):
    """The lesson a reply names, read from its raw text (None when the text is not JSON)."""
    try:
        return json.loads(row["text"]).get("lesson")
    except ValueError:
        return None


def failures(version):
    """The error types of a version, counted, and how many of its failed replies still name the right lesson."""
    rows = runs[version]
    return dict(Counter(r["error"] for r in rows if r["error"])), sum(named(r) == e for r, e in zip(rows, EXPECTED) if r["error"])


runs = {version: [ask(version, question) for question in QUESTIONS] for version in ["v1", "v2"]}
for version, rows in runs.items():
    print(version, sum(r["error"] is None for r in rows), "pass,", sum(r["lesson"] == e for r, e in zip(rows, EXPECTED)), "right lesson,", sorted({r["error"] for r in rows if r["error"]}))
for version in runs:
    print(version, *failures(version))
for row in runs["v1"][:2]:
    print(row["error"], row["completion_tokens"], repr(row["text"][:48]))
failed = [i for i, row in enumerate(runs["v2"]) if row["error"]]
fixes = {i: repair("v2", QUESTIONS[i], runs["v2"][i]) for i in failed}                # one more try for each failed reply
for i, second in fixes.items():
    print(runs["v2"][i]["error"], "->", second["error"], second["lesson"] == EXPECTED[i])
```

**Predict:** How many of the 16 replies will pass the `Route` check for each version, and how many will name the right lesson?

literal_error 42 '{\n  "lesson": "Replace NULL with Default Value",'

*Why:* The first two lines give the version, the replies that pass, the replies that name the right lesson, and the error types. The two lines after that show the first two replies of v1: the error type, the completion tokens and the start of the reply. Version v1 passes none of its 16 replies, with two error types: `json_invalid` (the text is not JSON, 4 replies) and `literal_error` (JSON, but a value that is not allowed, 12 replies); none of its failed replies names the right lesson. Both replies shown name a lesson that is not on the list ("Understanding NULL Values in SQL", "Replace NULL with Default Value"), and the first one is also cut off at 80 completion tokens, the limit that `ask` sets, before its JSON closes, so for the parser it is not JSON. ### 4. Prompts as code, tests and a budget

**Idea.** A prompt is code: keep each version under a name (a dictionary here, a file in a repository), run the same test on every change and keep the numbers. The test is the 16 questions with the lesson that answers each. A budget is set before the measurement. This one is an invented budget, not a real product's: a help box with 400,000 questions a month and $90 a month for routing allows $0.225 for 1,000 requests. The prices in the cell are assumed, $1.00 per million prompt tokens and $5.00 per million completion tokens, not any provider's: replace them with the row of your provider's pricing page and check it again before you rely on it.

**Try it:** change one phrase of v2, so that the reason has at most 8 words, run the test on the new version, and print for v2 and v3 the replies that pass, the right lessons, the mean tokens, the cost of 1,000 requests, whether it fits the budget and the median seconds, then the error types of v3.

```python
PROMPTS["v3"] = PROMPTS["v2"].replace("one short sentence", "at most 8 words")         # the change under test
runs["v3"] = [ask("v3", question) for question in QUESTIONS]

PRICE_IN, PRICE_OUT = 1.00, 5.00                                           # dollars per million tokens: assumed for this lesson, not any provider's price
BUDGET = 90 / 400_000 * 1000                                               # an invented budget (400,000 questions a month, $90 for routing), in dollars for 1,000 requests
for version in ["v2", "v3"]:
    rows = runs[version]
    prompt_mean = statistics.mean(r["prompt_tokens"] for r in rows)
    completion_mean = statistics.mean(r["completion_tokens"] for r in rows)
    cost = (prompt_mean * PRICE_IN + completion_mean * PRICE_OUT) / 1_000_000 * 1000
    print(version, sum(r["error"] is None for r in rows), sum(r["lesson"] == e for r, e in zip(rows, EXPECTED)), round(prompt_mean), round(completion_mean),
          round(cost, 3), cost <= BUDGET, round(statistics.median(r["seconds"] for r in rows), 1))
print("v3", *failures("v3"))
```

**Predict:** Which of v2 and v3 fits the budget, and does v3 still name the right lesson as often as v2?

*Why:* The columns are the version, the replies that pass, the right lessons, the mean prompt tokens, the mean completion tokens, the dollars for 1,000 requests, whether that fits the budget, and the median seconds. Version v2 passes 11, names 9 lessons right, uses about 100 prompt tokens and 22 completion tokens, and costs $0.211, under the $0.225. Version v3 passes 5 and names 3 right, uses 102 and 12 tokens, costs $0.159, also within the budget, and its median request takes 5.1 seconds against 10.2 for v2 on this machine (yours will differ, which is the reason to measure). Both fit the budget, so the budget does not choose between them. The shorter reason cut the completion tokens by almost half because the model left the reason out: the last line shows that v3 has 11 failures, all of the type `missing`, and that all 11 still name the right lesson in their raw text, which the count of right lessons does not credit. A saving that fails 11 replies is not a saving until the schema or the prompt is changed and the test is run again.

A hosted API usually takes the same three things: the messages, the settings and a key (no provider was checked for this lesson). The last cell of the notebook shows where they go for any provider whose address, headers and field names you copy from its documentation; it does nothing until you fill them in, and no exercise needs it. Read the status of the response before its body: the Requests documentation says that a successful `r.json()` does not show that the response succeeded.

<Aside type="tip" title="Remember">

- A request is messages and settings; the reply carries the prompt tokens and the completion tokens, and the model reads more than you typed.
- Temperature 0 repeats; a higher temperature varies. Tests and parsers want 0.
- Validate every reply against a schema, and count a reply as passing only when it does; a valid reply is not yet a right one.
- Keep prompts as named versions, run the same test on each change, and read passes, right answers and cost together.
- A budget is set from the product (volume and allowance) before the measurement; seconds depend on the machine.

**Common trap:** a model that was asked for JSON returns JSON. The first version passed none of its 16 replies: 12 named a lesson that is not on the list, and 4 were cut off before the JSON closed.

</Aside>
