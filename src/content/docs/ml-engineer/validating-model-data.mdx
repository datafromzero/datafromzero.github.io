## The question

The pipeline of lesson MLE1 scored a region it had never seen without a word. Data will not always arrive clean: a system upstream slips, a field does not arrive, a channel appears that nobody told the model about. *What do we check before training and before scoring, and what do we do with what fails?* Four rows of a table that went wrong, made for this lesson:

| user_id | channel | platform | region | sessions_7d | active_days_7d | onboarded |
|---:|---|---|---|---:|---:|---:|
| 10990 | app_store | ios | north_america | -1 | 1 | 1 |
| 11142 | tiktok | web | europe | 0 | 1 | 1 |
| 11829 | organic_search |  | north_america | 0 | 1 | 1 |
| 11043 | app_store | android | north_america | 1 | 1 | 2 |

By the end you can write a schema for a table and a model for a request, say what to refuse, set aside or repair, and keep one contract for both sides.

<Aside type="note" title="You already know this">

**Match.** In [*Data leakage*](/core/data-leakage/) (C20) you asked of every column whether it was known at the prediction moment. A schema asks the same kind of question of every value: is it allowed to be here?

**Diverge.** C20 judged columns once, by reading. A schema is code that runs on every batch and every request, so the judging does not depend on someone looking.

</Aside>

### 1. A schema for the table

**Idea.** A pandera `DataFrameSchema` lists, for each column, the type it must have and the checks it must pass; `validate` runs them against a table. The `lazy` argument of `validate` decides what happens at the first failure. Read the schema below against the real table before you trust it: `active_days_7d` goes up to 8, not 7, because a seven-day window that starts at a time of day touches eight calendar dates.

```python
# The values the model learned. They are listed once, and both the schema and the request model read these lists.
CHANNELS = ["app_store", "organic_search", "paid_search", "paid_social", "referral"]
PLATFORMS = ["android", "ios", "web"]
REGIONS = ["asia_pacific", "europe", "latin_america", "north_america"]

table_schema = pa.DataFrameSchema(
    {
        "user_id": pa.Column(int, unique=True),
        "channel": pa.Column(str, pa.Check.isin(CHANNELS)),
        "platform": pa.Column(str, pa.Check.isin(PLATFORMS)),
        "region": pa.Column(str, pa.Check.isin(REGIONS)),
        "sessions_7d": pa.Column(int, pa.Check.ge(0)),
        "expenses_7d": pa.Column(int, pa.Check.ge(0)),
        "recent_3d": pa.Column(int, pa.Check.ge(0)),
        "active_days_7d": pa.Column(int, pa.Check.in_range(0, 8)),
        "onboarded": pa.Column(int, pa.Check.isin([0, 1])),
        "saw_paywall": pa.Column(int, pa.Check.isin([0, 1])),
        "bought_plus": pa.Column(int, pa.Check.isin([0, 1])),
        "churned": pa.Column(int, pa.Check.isin([0, 1])),
    },
)
```

### 2. A model for one request

**Idea.** A pydantic model is a class of typed fields; building one from a dictionary validates it and raises a `ValidationError` that lists each field that failed. A field can carry constraints: `Literal[...]` names the allowed values and `Field(ge=0)` a lower bound. The lists are the ones the schema uses.

```python
class ChurnRequest(BaseModel):
    """One request to score: the ten columns the model reads, and nothing else."""

    model_config = ConfigDict(extra="forbid")

    channel: Literal[*CHANNELS]
    platform: Literal[*PLATFORMS]
    region: Literal[*REGIONS]
    sessions_7d: int = Field(ge=0)
    expenses_7d: int = Field(ge=0)
    recent_3d: int = Field(ge=0)
    active_days_7d: int = Field(ge=0, le=8)
    onboarded: int = Field(ge=0, le=1)
    saw_paywall: int = Field(ge=0, le=1)
    bought_plus: int = Field(ge=0, le=1)
```

### 3. Refuse, set aside or repair

**Idea.** A bad row has three possible answers. *Repair* it by a rule written down and counted. *Quarantine* it: set it aside in a file with its reasons, and train on the rest. *Reject* the batch when the fault is in the whole table (a wrong type, a missing column) or too many rows fail. `triage` below repairs first, with one rule, then checks, then quarantines what still fails.

```python
def repair(table):
    """The one repair rule we trust: text columns in lower case with no spaces at the ends. Returns the table and how many rows it changed."""
    fixed = table.copy()
    changed = pd.Series(False, index=table.index)
    for column in TEXT_COLUMNS:
        cleaned = table[column].str.strip().str.lower()
        changed |= cleaned.notna() & (cleaned != table[column])
        fixed[column] = cleaned
    return fixed, int(changed.sum())
```

```python
def triage(table, max_share=MAX_SHARE):
    """Repair, then quarantine the rows that still fail; raise BatchRejected when the batch itself is wrong."""
    fixed, repaired = repair(table)
    cases = failure_cases(fixed)
    if cases["index"].isna().any():
        raise BatchRejected("a check failed on a whole column, not on rows")
    bad = sorted(cases["index"].astype(int).unique())
    if len(bad) / len(table) > max_share:
        raise BatchRejected(f"{len(bad):,} of {len(table):,} rows fail, more than {max_share:.0%}")
    return Triage(fixed.drop(index=bad), fixed.loc[bad], repaired, cases)
```

### 4. One contract for both sides

**Idea.** The allowed values of `channel`, `platform` and `region` are what the pipeline learned in training, and they are listed once, in `contract.py`; the schema and the request model both read those lists. What can drift apart is the list and the model. A test can hold them together: it fits the pipeline and compares what its encoder learned with the lists.

```python
def test_schema_and_request_model_read_the_same_lists():
    allowed = {"channel": CHANNELS, "platform": PLATFORMS, "region": REGIONS}
    for column, values in allowed.items():
        assert list(get_args(ChurnRequest.model_fields[column].annotation)) == values


def test_the_lists_are_what_the_model_learned():
    X_train, X_test, y_train, y_test = split(load_table())
    learned = build_pipeline().fit(X_train, y_train)["prep"].named_transformers_["cat"].categories_
    assert [list(values) for values in learned] == [CHANNELS, PLATFORMS, REGIONS]
```

<Aside type="tip" title="Remember">

- A schema is code that runs on every batch: types, ranges, allowed values and uniqueness, written once.
- `lazy=True` reports every failed check; without it validation stops at the first.
- pydantic converts when it can: say whether the service takes `"3"` for 3.
- Repair by a written, counted rule; quarantine the rest with its reasons; reject the batch when a whole column or too many rows fail.
- The allowed values are what the model learned: keep one list, and a test that compares it with the fitted pipeline.

**Common trap:** a table that passes every check it has been given. The checks are the ones someone wrote.

</Aside>

```python
from pydantic import ValidationError, model_validator

from ml_starter.config import FEATURES
from ml_starter.contract import ChurnRequest
from ml_starter.data import load_table

valid = load_table().iloc[0][FEATURES].to_dict()
requests = [
    valid,
    {**valid, "sessions_7d": 1, "expenses_7d": 1, "active_days_7d": 3},
    {**valid, "sessions_7d": 1, "expenses_7d": 2, "active_days_7d": 3},
]


class StrictRequest(ChurnRequest):
    @model_validator(mode="after")
    def active_days_need_events(self):
        if self.active_days_7d > self.sessions_7d + self.expenses_7d:
            raise ValueError("more active days than events")
        return self


def accepted(request):
    try:
        StrictRequest(**request)
        return True
    except ValidationError:
        return False


answer_2 = [accepted(request) for request in requests]
print(answer_2)
```
