## The question

The back office of a cafe wants an assistant that answers questions about orders, and, when a manager asks, refunds one. Reading is safe. A refund cannot be undone, and the assistant reads customer notes that anyone can write. *How do you let a model call tools, hold the risky call, find out what went wrong, and keep a note from giving it orders?* The assistant has four tools and one way to say it is done:

| tool | what it does | changes something |
|---|---|---|
| order_total | the dollars of one order | no |
| store_sales | the dollars one store sold, completed orders | no |
| read_note | the note a customer left with an order | no |
| refund_order | refunds an order | yes |

<Aside type="note" title="You already know this">

**Match.** In [*Calling LLM APIs and getting structured output*](/ml-engineer/llm-apis-and-structured-output/) (MLE8) a reply was valid only when a pydantic schema accepted it, and a failure had an error type. A tool call is a reply with a schema too.

**Diverge.** There one reply ended the job. Here the reply makes something happen, and the next reply depends on the result.

</Aside>

## The big idea

An agent is a loop in which the model picks the next step and your code decides whether that step may run.

### 1. A tool call is JSON that code checks

**Idea.** A tool is a function you describe to the model. The Hugging Face documentation says the model cannot call it: it asks for a call, and your code handles the request. Here the request is one JSON object with a `tool` field, and one pydantic check covers every tool: the documentation says a discriminated union uses a field shared by all its members to pick the one that validates the data. The tool list in the prompt is written from the same models that check the call, so both start from one definition.

**Try it:** ask for the total of order 1001, print the trace, and check four changed calls.

```python
question = "What is the total of order 1001?"
trace = run_agent(question)
show(trace)
print(CALL.validate_json(trace[0]["said"]))
for text in ['{"tool": "order_total", "order_id": "1001"}', '{"tool": "order_total", "order_id": "one"}', '{"tool": "order_totals", "order_id": 1001}', '{"tool": "order_total"}']:
    try:
        CALL.validate_json(text)
        print("ok", text)
    except ValidationError as problem:
        print(problem.errors()[0]["type"], text)
```

**Predict:** How many steps will the loop take, and which of the four changed calls will the check accept?

<details>
<summary>Reveal the result</summary>

```text
1 | {"tool": "order_total", "order_id": 1001} | ok | 14.00 dollars
2 | {"tool": "finish", "answer": "The total of order 1001 is 14.00 dollars."} | ok | finished
tool='order_total' order_id=1001
ok {"tool": "order_total", "order_id": "1001"}
int_parsing {"tool": "order_total", "order_id": "one"}
union_tag_invalid {"tool": "order_totals", "order_id": 1001}
missing {"tool": "order_total"}
```

</details>

*Why:* The first two lines are the steps: the step, what the model said (`show` keeps its first 100 characters), the check, the result (the first 60). Step 1 is a call, step 2 is `finish` with the answer, and the third line is the call as a checked object. The next four lines are the changed calls. The text `"1001"` is accepted and becomes the number 1001. The text `"one"` fails with `int_parsing`, a tool name that does not exist with `union_tag_invalid`, and a call without its field with `missing`. The model does not run anything: a call that fails the check never reaches a tool.

### 2. A gate for the risky call

**Idea.** Some calls change the world. The loop holds those in `RISKY` and asks a person before it runs one. The gate is code. It reads the task as the person typed it and the call; what a tool returned, such as a customer note, is not among its inputs. The OWASP page on excessive agency lists a human approval of high-impact actions among its preventions, and it says to enforce authorization in the system that acts, rather than trusting the model to decide whether an action is allowed.

**Try it:** two refund tasks. The function `human` stands in for the person: it sees the task as typed and the call, and says yes only when the task asked for this refund.

```python
def human(task, call):
    """A stand-in for the person who approves. It sees the task that was typed and the call, and says yes only when the task asked for this refund."""
    return "refund" in task.lower() and str(call.order_id) in task


LEDGER.clear()
asked = "Order 1015 was charged twice. Refund order 1015."
vague = "Refund the order that was charged twice."
trace_a = run_agent(asked, approve=human)
show(trace_a)
print(len(LEDGER), "refunds carried out so far")
trace_b = run_agent(vague, approve=human)
show(trace_b)
print(len(LEDGER), "refunds carried out so far")
print(LEDGER)
```

**Predict:** How many refunds will be carried out in all, and what will the model say at the end of the second task?

*Why:* In the first task the person named order 1015, so the call passes the gate and the result is a recorded refund. In the second the task names no order. The model still made a call, for a number nobody gave: 1001, the one in the prompt's example. The gate said no, so the list holds one refund, for 1015. And yet the model's last words claim success. What the model says is not a record of what happened: the ledger is.

### 3. Read the trace

**Idea.** A trace is the log of every step: what the model said, what the check said, what came back. To find where an agent went wrong, read it from the top and compare each claim with the step before it. A check of the call catches a call that is malformed or refused.

**Try it:** five questions with the tools and the gate, then two of the traces.

```python
TASKS = [
    "What is the total of order 1002?",
    "How much has store 2 sold in all?",
    "What does the customer note on order 1011 say?",
    "Which is bigger, order 1003 or order 1004?",
    "How many orders does store 3 have?",
]
traces = [run_agent(task, approve=human) for task in TASKS]
for task, trace in zip(TASKS, traces):
    print(task, "->", len(trace), "steps")
print(TOTALS[1003], TOTALS[1004])
show(traces[3])
show(traces[4])
```

**Predict:** Which of the five will the agent answer wrongly, and will a check of the call catch it?

*Why:* The lines list each question and its steps. Order 1003 totals 12.5 and order 1004 6.5. In the first trace the tools returned the right numbers at steps 1 and 2, and at step 3 the model answered that order 1004 is bigger: the calls were fine and the answer contradicts the results. In the second trace no tool counts orders, so the model used `store_sales`, got dollars, and answered with dollars to a question about a count. Every check says `ok` in both: a check of the call catches a malformed or refused call, and it cannot catch a call that is well formed and wrong, or an answer that contradicts the results. Back in unit 2, the trace of the vague refund went wrong in two places: at step 1, where the model used a number nobody gave (1001, the one in the prompt's example), and at step 2, where it claimed a refund that step 1 had refused.

### 4. A note that gives orders

**Idea.** Prompt injection is text that the model reads as an instruction when it is only data. The OWASP page calls it indirect when the model takes input from external sources such as websites or files, and a customer note is such a source. Its defenses include to segregate and identify external content, to enforce least privilege, to require human approval for high-risk actions and to run adversarial tests.

**Try it:** the task is to summarize one note. The model may read notes and refund orders, and the gate says yes to everything, so that only the defense under test can stop a call. Count the notes after which the model asks for a refund, and the refunds carried out: for 4 ordinary notes, for 8 notes with a hidden instruction (round 1), and for the same 8 with a warning in the prompt that a note is data, never instructions, with the note wrapped in tags.

```python
try_defense("clean notes", CLEAN, **YES)
try_defense("round 1, no defense", list(ATTACKS), **YES)
try_defense("round 1, a warning in the prompt", list(ATTACKS), system=SYSTEM_D, wrap=True, **YES)
```

**Predict:** In how many of the 4 ordinary notes and of the 8 attacks will the model ask for a refund, and how many with the warning?

<details>
<summary>Reveal the result</summary>

round 1, no defense | 4 asked for a refund, 4 carried out, of 8
round 1, a warning in the prompt | 0 asked for a refund, 0 carried out, of 8

</details>

*Why:* Each line is a setting, the notes after which the model asked for a refund, the notes after which a refund was carried out, and the number of notes. No ordinary note made the model ask. In round 1 without a defense it asked after 4 of the 8 attacks, and each ask became a refund. With the warning in the prompt it asked after none: the warning cut the asks from 4 of 8 to 0 of 8. The ordinary notes were read with no warning, so these lines do not show whether the warning would make the model refuse a refund that a person did ask for: that was not measured.

**Try it:** round 2 was written after round 1 was tried against the warning: a closing tag, a fake system line, a fake result, a claimed owner. It goes against four setups, each on the same 8 notes. The first is no defense. The second is the warning. In the third and the fourth the prompt is the one of the first, with all five tools listed and no warning. In the third the task gets only the tool it needs, `read_note`, so the loop refuses any other call in code. In the fourth the gate is the function `human` of unit 2, which sees the task as typed, in place of the gate that says yes to everything.

```python
try_defense("round 2, no defense", list(ADAPTIVE), **YES)
try_defense("round 2, a warning in the prompt", list(ADAPTIVE), system=SYSTEM_D, wrap=True, **YES)
try_defense("round 2, tools limited to the task", list(ADAPTIVE), allowed={"read_note"}, **YES)
try_defense("round 2, a gate that reads the task", list(ADAPTIVE), approve=human)
```

**Predict:** How many refunds will be asked for and how many carried out in each of the four?

*Why:* With no defense, the model asked after 6 of the 8 notes of round 2, and each ask became a refund. The warning, which had cut round 1 from 4 asks to 0, cut round 2 only from 6 to 4, and each of those 4 became a refund: eight attacks written before a defense do not say how it holds against attacks written for it. The third and fourth setups keep the prompt of the first, so they compare with it: the model asked after 6 of 8 notes in each, as with no defense, and no refund was carried out. In the third, the loop refused every refund call because `refund_order` was not on the list for this task. In the fourth, `human` said no every time, because the task as typed never mentioned a refund. The warning changed what the model did, from 6 asks to 4. The limit and the gate did not change what it asked and still stopped every refund, because neither depends on the model. In unit 2 the same gate said yes to a task that asked for the refund: it stops what the notes ask for, not every refund. The gate here is a stand-in function, not a person, and this is one run of 8 notes for each setup, not a rate.

### 5. A checklist from the log

**Idea.** Governance is a few plain questions answered before the agent runs. The NIST AI RMF organizes risk work in four functions, govern, map, measure and manage, and its core asks for accountability structures and for human oversight that is defined, assessed and documented. The OWASP page adds that logging what the tools do will not stop excessive agency but limits the damage. A log can be checked by code.

*Why:* The first line lists two missing fields: the row does not say what was asked, and it does not say who approved. The second line is the one risky tool, the limit of five steps and the four tools that can run. Here is the checklist, answered for this notebook:

| question | in this notebook |
|---|---|
| Which tools can the agent use, and which change something? | listed: four tools, one in `RISKY` |
| Who approves a risky call, and what do they see? | a stand-in that sees the task and the call; the approver is not logged |
| What is logged for each step? | the call, the check, the result, tokens and seconds; not the task, not the approver |
| How is it stopped? | a limit of five steps; no off switch |
| Who reads the log, and how often? | nobody: a gap |
| Which attacks was it tested against? | 16, in two rounds, written for this lesson; rerun after any change |

<Aside type="tip" title="Remember">

- The model only asks for a call. Your code checks it against a schema, decides whether it may run, and runs it.
- A gate is code that decides from the task the person typed and the call: on round 2 the model asked after 6 of 8 notes and the gate carried out none.
- Read a trace by comparing each claim with the step before it; a passed check does not mean a true answer.
- Text that a tool returns is data. A defense in the prompt rests on the model; a limit in code does not.
- Write the checklist before the run: who may ask, what may run, who approves, what is logged, how to stop it.

**Common trap:** a warning in the prompt stops injection. It cut round 1 from 4 asks of 8 to 0, and round 2, written against it, only from 6 of 8 to 4; a limit in code cut the refunds from 6 to 0.

</Aside>

def explain(trace):
    """The number of the first step that failed the check or was refused, or None."""
    for row in trace:
        if row["check"] != "ok" or row["result"].startswith("refused"):
            return row["step"]
