## Warm-up

Answer from memory before you open anything. Then click to check.

1. A clean code in A2 reads `S2-1001-MOBILE`. Write the formula that returns the order number, 1001, as a
   number.

   <details>
   <summary>Answer</summary>

   **`=VALUE(MID(A2,4,4))`**. `MID` cuts four characters from position 4 and returns text; `VALUE` makes
   it a number.

   </details>

2. Name the four moves of the cleaning workflow, in order.

   <details>
   <summary>Answer</summary>

   Keep raw untouched; profile before you fix; fix on a copy, one step at a time; reconcile and log.
   Today's tool does the third move so that it can be run again.

   </details>

3. A colleague in Europe sends a CSV where the amounts look like `12,50` and the fields are separated by
   semicolons. Which two import settings have to change from the usual?

   <details>
   <summary>Answer</summary>

   The **delimiter** (semicolon, not comma) and the **locale** used to read numbers and dates, because a
   comma is a decimal mark there, not a thousands separator.

   </details>

## The question

Every Monday the till system drops a new export. Cleaning it by hand takes the morning, and last Monday you
skipped a step and nobody noticed for a week. The owner asks:

> Can you set this up so that next Monday's file takes one click, and the numbers still match the till
> report?

Here are the first lines of the first file, `till-export.csv` (a **·** marks a space):

```text
till_code,ordered_at,total_usd,status,cashier_notes
··S2-1001-Mobile··,2026-01-01 08:02:00,14.00,COMPLETED··,
··S1-1002-Mobile,2026-01-01 15:38:00,12.50,·COMPLETED,
·s2-1003-mobile··,2026-01-01 15:47:00,12.50,Completed,"spilled, remade"
```

The till report for this file says **1,500 orders, 1,499 completed and 1 canceled, worth \$18,958.00**. The
file has 1,515 data rows, because some orders were sent twice. By the end of this lesson you will have a
query that turns the file into a clean table of exactly those 1,500 orders, and that does the same on the
bigger file that arrives next week.

**Power Query** is the tool in Excel that reads data from a file, shapes it, and loads the result into a
sheet. Everything you do in its editor is recorded as a **step**, in order. Microsoft's page says the editor
"keeps track of everything you do with the data by recording and labelling each transformation, or step",
and that when you refresh, "each step runs automatically". The list of steps is the **Applied steps** pane,
and it reads as a recipe: the source, then each change, top to bottom. Your list may have a step or two
more than the picture, because Power Query sometimes adds a step of its own, such as a type change after
a split.

Three things make this different from the formulas of the last lessons:

- **The recipe is saved, and it runs again.** Replace the file, press Refresh, and the same steps run on
  the new rows.
- **The source is never changed.** The CSV file stays exactly as it arrived.
- **Types and locale are decisions you make.** The editor can guess the type of each column, but Microsoft's
  page says inference can be wrong, so we choose on purpose.

## Worked example

Question: **turn the 1,515-row file into 1,500 clean orders, and then refresh it with next week's file.**
Open Excel and follow along.

1. **Say what one row is, and what the totals should be.** One row of the clean table is one order. The till
   report says 1,500 orders, 1,499 completed and 1 canceled, \$18,958.00.
   *Why first:* a recipe without a target cannot be checked.

2. **Keep the file where it can be replaced.** Save `excel-power-query-basics-orders.csv` into a folder of
   your own as `till-export.csv`.
   *Why this name:* the query remembers the file's path. Next week's file will have to take this name in
   this folder (you will see why in the Check yourself exercise).

3. **Import on purpose.** In a new workbook, **Data > From Text/CSV**, pick `till-export.csv`. In the preview
   window set **Delimiter** to **Comma** and **Data Type Detection** to the option that turns detection off
   (**Do not detect data types**), then choose **Transform Data**. Microsoft's pages list these choices (file origin, delimiter, and detection
   based on the first 200 rows, on the entire data set, or off, which makes every column text). Off
   means nothing is guessed, and we set each type in step 9.
   *Why:* a wrong guess is silent. Setting the types yourself puts the choice in the recipe.

4. **Read the first steps.** The **Applied steps** pane on the right shows **Source** and **Promoted Headers**.
   Click each and look at the preview. All the columns are text.

5. **Trim, then lowercase.** Select the `till_code` and `status` columns (click one header, then Ctrl+click
   the other). Use the **Format** menu on the **Transform** tab to choose **Trim**, and then
   again to choose **lowercase**. Two new steps appear. `··S2-1001-Mobile··` becomes `s2-1001-mobile` and
   `COMPLETED··` becomes `completed`.
   *Why:* the same reasons as in the formula lessons: positions and matches break on stray spaces, and
   Microsoft's pages say Power Query is **case-sensitive**.

6. **Split the code.** Select `till_code`, then **Split Column > By Delimiter** (it is under the **Split
   column** menu on the **Home** tab and in the **Text Column** group on **Transform**). Choose **Custom**
   and type `-`, **Each occurrence of the delimiter**. You get three columns named `till_code.1`,
   `till_code.2` and `till_code.3`.
   *Why:* each column then holds one fact. The names with a dot and a number are what Microsoft's page
   says the new columns are called.

7. **Rename the new columns** to `store`, `order_id` and `payment` (double-click a header).

8. **Remove what you do not need.** Select `cashier_notes`, then **Remove Columns** on the **Home** tab.
   *Why:* free-text notes would only get in the way of the table you are building.

9. **Set the types.** One column at a time, use the icon at the left of the header: `store`, `payment` and
   `status` stay **Text**, `order_id` is **Whole Number**, `ordered_at` is **Date/Time**, and `total_usd`
   is **Decimal Number**. This is the step Microsoft calls **Changed Type**.
   *Why now, and not earlier:* a number that still had its spaces or its hyphens would fail to convert.

10. **Remove duplicates on the key.** Select `order_id`, then **Home > Remove Rows > Remove Duplicates**.
    *Why only `order_id`:* it identifies an order, as in the cleaning workflow. Microsoft's page warns
    that Power Query "doesn't guarantee that it keeps the first instance" of a duplicate. Here it does not
    matter: the repeated rows in this file are exact copies, so every copy is the same row.

11. **Load.** **Home > Close & Load**. Excel puts the table on a new sheet.

12. **Reconcile.** On the new sheet, select the `order_id` column's values: the status bar shows
    **Count: 1500**. Select `total_usd`: **Sum: 18958**. Count the statuses with a filter or with
    `=COUNTIFS(...,"completed")`: **1499 completed and 1 canceled**. All three match the till report.

13. **Change the file, then refresh.** Close nothing. In your folder, replace `till-export.csv` with
    `excel-power-query-basics-orders-update.csv` renamed to `till-export.csv` (the full export of all
    1,800 orders, plus 20 repeated rows). Back in Excel: **Data > Refresh All**. The table now has
    **1,800** rows, `total_usd` sums to **22754.25**, and the statuses are **1,799 completed and 1
    canceled**. You did not touch a step.

That answers the owner: **yes. Cleaned once, refreshed with one click, and both files reconcile: 1,500 orders
(\$18,958.00) and then 1,800 orders (\$22,754.25).**

<details>
<summary>Explain it in your own words: why did we set the data types after trimming, splitting and
renaming, and not at the start?</summary>

Because a type is a promise about what is in the column. Before the trim and the split, `till_code` still
held spaces and three facts, and `order_id` did not exist yet. Setting the types last means every value
already looks like what its type expects.

</details>

<Aside type="note" title="If you only have Google Sheets">
Google Sheets has no Power Query. The nearest route is to bring the CSV in with **File > Import**, then do
the same cleaning with the formulas from the text and cleaning-workflow lessons: the formulas are your
recipe. To run it on a new file, import that file as a new sheet and point the formulas at it. That is more
manual than a refresh, which is the whole point of Power Query. The practice workbook's `raw_orders_export`
sheet holds the first file's rows so you can try it.
</Aside>

1. One row is one order, and the key is `order_id`.

Now finish it: add one step that keeps only the rows whose `status` is `completed`, and reconcile.

<details>
<summary>Hint</summary>

Open the query (double-click it in the **Queries & Connections** pane). Click the **last step** before you
add anything, so the new step goes at the end. How do you filter a column in the editor? Look at the

</details>

<details>
<summary>Half-solution</summary>

Click the arrow on the `status` column, clear the tick next to `canceled`, and choose OK. The new step is added to the

</details>

<Solution>

1. In the editor, click the last applied step (**Removed Duplicates**). Click the filter arrow on `status` and
   clear the tick next to `canceled`. A step called something like **Filtered Rows** appears at the end of the list.
2. **Close & Load**. With the first file in place the table has **1,499** rows and `total_usd` sums to

3. Replace `till-export.csv` with the update file and **Refresh All**. The table has **1,799** rows and the

</Solution>

## On your own

<Exercise id="excel-power-query-basics-2">

**Import the Harbor export from a European computer.** `excel-power-query-basics-harbor-eu.csv` was saved
on a computer set to a European region: the fields are separated by semicolons, amounts are written
with a decimal comma (`9,00`), and dates are day/month/year (`01/04/2026`). Harbor opened on April 1, 2026.
The till report for this file says **355 orders, worth \$4,606.25**, and the file has a few repeated rows.

Before you import anything, write one sentence on `recipe` saying what the result should look like: how
many rows, what one row is, which columns and types, and how you will check the import. Then build the
query with the same recipe as before, and reconcile.

<details>
<summary>Hint</summary>

Two settings changed from the worked example. One is on the import window, the other is where the type
of a column is set. Remember the Microsoft example of dates in day/month/year order read with a United
States locale: what happened to the dates with a day above 12?

</details>

<details>
<summary>Half-solution</summary>

Expected output: *"355 rows, one per order, with `store`, `order_id`, `payment`, `ordered_at` as a real
date and time, `total_usd` as a number, and `status`."* Choose the **semicolon** as the delimiter. For
`ordered_at` and `total_usd`, change the type **using locale** (right-click the column, **Change Type >
Using Locale**) and pick a locale that writes dates the way the file does and a locale that writes
decimals with a comma. Then check the sum before you trust anything.

</details>

<Solution>

The sentence: *"355 rows, one per order; store, order_id, payment (text), ordered_at (date/time), total_usd
(decimal number), status; checked against 355 orders and \$4,606.25, and no date before April 1 or after June 30."*

1. **From Text/CSV**, delimiter **Semicolon**, Data Type Detection **Do not detect data types**, **Transform Data**.
2. The same steps as before: trim and lowercase `till_code` and `status`, split `till_code` on `-`, rename,
   remove `cashier_notes`, then types.
3. For types, `ordered_at`: **Change Type > Using Locale**, type **Date/Time**, locale **English
   (United Kingdom)** (Microsoft's own example uses that locale for day/month/year dates). `total_usd`:
   **Using Locale**, type **Decimal Number**, a locale that uses a decimal comma, such as **German (Germany)**.
   `order_id` is a **Whole Number**.
4. **Remove Duplicates** on `order_id`: **355** rows remain from 360.
5. **Reconcile:** `total_usd` sums to **4606.25**. The earliest `ordered_at` is **2026-04-01** and the latest
   **2026-06-30**, so nothing is before Harbor's opening or after the end of the data.

**What goes wrong with the default (United States) locale:** a date such as `14/04/2026` has no month 14, so
Power Query shows an error: **219** of the 355 dates have a day above 12. The other **136** have a day of 12 or
less, such as `08/04/2026`, which reads as August 4 with no error at all. Of those, 74 land after June 30. That
is why the check on the earliest and latest date, and on the sum, is part of the recipe and not an extra.

</Solution>

</Exercise>

## Check yourself

1. Without looking back: what does the **Applied steps** list contain, and what happens to it when you press
   Refresh?

   <details>
   <summary>Answer</summary>

   Every transformation you made, in order, from the **Source** step down. On refresh Power Query reads the
   source again and runs each step on whatever it now contains.

   </details>

<Exercise id="excel-power-query-basics-3">

**Spot the flaw.** A colleague builds the query on `till-export.csv` (1,500 rows after cleaning). The next
Monday, the new file arrives as `till-export-monday.csv` in the same folder. She presses **Refresh All** and
the table still has 1,500 rows. She concludes: *"Refresh is broken, I will clean the new file by hand."*
What went wrong?

<details>
<summary>Hint</summary>

Click the **Source** step in the applied steps. What does it point to?

</details>

<details>
<summary>Half-solution</summary>

A query reads the file it was built on, by its path. Which file did it read on Monday?

</details>

<Solution>

Refresh was not broken: it ran every step again, on the **old file**. The **Source** step holds the path
and name of the file the query was built on, so it read `till-export.csv` again, and that file had not
changed. Her new file has another name, so the query never saw it.

Two fixes. Either save the new export over the old name (what we did in the worked example), or change the
**Source** step: Microsoft's pages show that you can edit it in the applied steps pane and point it at the new file.
Then press **Refresh All**: the table has **1,800** rows when the update file is the source. The same check
as ever: a row count that does not change when the data should have changed is a reason to look at the
source, not at the tool.
