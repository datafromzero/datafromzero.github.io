   <details>
   <summary>Answer</summary>

A cell has two values: the one it **shows** and the one it **stores**. The formula bar shows what is
stored. A number format only changes how the stored number is drawn: 14.25 shown with no decimals
reads 14, but every formula still uses 14.25.

A **text-number** looks like a number but is text, so `SUM`, `AVERAGE` and a sort treat it as text:
`SUM` ignores text, and `COUNT` does not count it. Dates are numbers underneath, a count of days,
and a column sorts and filters as dates only when every date is stored that way. A **text-date**
looks like a date and is text.

Three checks, none of which trusts your eyes:

- **`=ISNUMBER(D2)`** gives TRUE for a number or a real date and FALSE for text. It does not convert
  anything, so even a number in quotation marks counts as text.
- **`COUNT` against `COUNTA`** on a column. `COUNT` counts the numbers, `COUNTA` counts every
  filled cell. If they differ, the difference is the number of text cells.
- **Look for a day above 12.** In an imported date such as 13/01/2026 the first number cannot be a
  month, so the file writes the day first. A date whose first two numbers are both 12 or less is
  ambiguous and can be silently swapped.

By default numbers sit on the right of a cell and text on the left, so a column with both sides is a
warning sign. Treat it as a clue, not proof: alignment can be changed by formatting. `ISNUMBER` is the
test.

## Worked example

Question: **what did Campus really take in January, and can we trust the dates?** Open the practice
file and follow along.

1. **Copy the data to `calc`.** Select everything on `raw_export_campus_jan`, copy it, and paste it in
   cell **A1** of `calc`.
   *Why:* the raw sheet stays as it arrived, and every check below is made on the copy.

2. **Compare what a cell shows with what it stores.** Click **D2**: the cell shows `14.00` on the
   left, and the formula bar shows `14.00`. Click **D5**: the cell shows `11.00` on the right, and the
   formula bar shows `11`. Then try it yourself in a spare cell on `calc`: type `14.25`, press the
   Decrease Decimal button twice, and the cell shows 14 while the formula bar still shows 14.25.
   *Why:* D5 is a number drawn with two decimals, and D2 is text that happens to look the same. The
   side of the cell and the formula bar already tell the two apart, but you cannot check 114 cells
   by eye.

3. **Test every cell.** Type `is_number` in **E1** and `=ISNUMBER(D2)` in **E2**. Fill down to **E115**.
   E2 to E4 say FALSE and E5 says TRUE.
   *Why:* `ISNUMBER` gives a yes or no for each row, so the problem becomes a column you can scan.

4. **Count them.** To the right, in **G1** type `check` and in **H1** `value`, then fill in:

   | G | H | Result |
   |---|---|---:|
   | `numbers_in_total` | `=COUNT(D2:D115)` | 73 |
   | `filled_in_total` | `=COUNTA(D2:D115)` | 114 |
   | `sum_as_it_stands` | `=SUM(D2:D115)` | 923.75 |

   *Why:* `COUNTA` agrees with the manager's 114 orders, so no row is missing. `COUNT` finds only 73
   numbers, so **41** of the totals are text, and `SUM` skips them.

5. **Convert, in a new column.** Type `total_number` in **F1** and `=VALUE(D2)` in **F2**. Fill down to
   **F115**. In **G5** type `real_total`, in **H5** `=SUM(F2:F115)`. It shows **1518.75**.
   *Why a new column:* the original stays visible, so you can compare. `VALUE` turns text that looks
   like a number into a number, and leaves a real number as it is. In Excel you can also select the
   text cells and choose **Convert to Number** from the error indicator (the small warning symbol)
   that appears beside them. That changes the cells in place, so use it on a copy.

6. **Check the total.** The manager said \$1,518.75, and the converted column gives **1518.75**. The
   difference from the first sum, 595.00, is exactly what the 41 text totals add up to. All 41 are
   `mobile` orders.

7. **Now the dates.** In **G6** type `real_dates` and in **H6** `=COUNT(B2:B115)`: **46**. In **G7** type
   `filled_dates` and in **H7** `=COUNTA(B2:B115)`: **114**. So **68** dates are text. Scroll to
   them: the first is `13/01/2026` on row 48, the last is `31/01/2026` on row 115.
   *Why this matters:* a day above 12 cannot be a month, so this file writes the day first. Yet 46
   cells were turned into real dates, which means the computer that opened the file read those the
   other way round.

8. **Find the swap.** In **G8** type `earliest_real_date` with `=MIN(B2:B115)` in **H8**, and in **G9**
   `latest_real_date` with `=MAX(B2:B115)` in **H9**. If a cell shows a five-digit number, format it as
   a date. The earliest is January 1, 2026. The latest is **December 1, 2026**.
   *Why:* this is a January export, so every date must fall in January. A date in December proves the
   swap: `12/01/2026` meant January 12 and was read as December 1. Of the 46 real dates, 44 are wrong.
   The two on January 1 are right only by luck, because day and month are both 1.

Answer: **the right total is \$1,518.75** (the converted column), and **the dates are not safe**: 68 are
text, 46 are real dates, and 44 of those are the wrong day. Do not sort, filter or group this
export by date.

<details>
<summary>Explain it in your own words: why did you count the text cells before you converted anything?</summary>

Because the counts tell you how big the problem is and where it sits, and the same counts prove the
fix afterwards. If the converted column had given a count of 73 again, the conversion would have
done nothing. Fixing first and measuring later leaves you guessing.

</details>

<Aside type="note" title="Why did the dates swap? Regional settings">
A CSV file stores only characters. Whoever opens it decides what `02/01/2026`, `1.500` or `1,500`
mean, using the settings of their own computer. Microsoft says that opening a CSV directly makes
Excel use its current default data format settings to read each column.

| The characters | Read as "dot decimal, comma thousands" | Read as "comma decimal, dot thousands" |
|---|---|---|
| `1.500` | 1.5 | 1500 |
| `1,500` | 1500 | 1.5 |
| `1.500,25` | not a number | 1500.25 |

Do not guess which setting your computer uses. Check it. Excel on Windows uses the separators of the
Windows regional settings, unless you clear **Use system separators** under **File > Options >
Advanced**. Google Sheets keeps a locale (a region and language setting) for each spreadsheet, under **File > Settings > General >
Locale**, and changing it changes the default currency, date and number formats for everyone using that
file. To bring a CSV into Excel under your control, use **Data > From Text/CSV**: you pick the
delimiter (the character that separates the columns, such as a comma) and see a preview before
anything is loaded. The safest dates in a shared file are written
year first, such as `2026-01-13`, which nobody can read the wrong way round.
</Aside>

**Spot the flaw.** A colleague opens the Campus January export and writes: *"I selected the `total_usd`

<Solution>

1. **The Count is not a test for numbers.** The status bar's Count counts the cells that are filled,
   text included, and Excel offers a separate Numerical Count that counts only cells holding
   numbers. 114 means 114 filled cells. `=COUNT(D2:D115)` gives 73, so 41 amounts are text.
2. **Readable is not right.** The cell shows how a date is drawn, not what it is. `02/01/2026` in row 4 is
   stored as February 1, and the earliest and latest real dates (`MIN` and `MAX`) are January 1 and
   December 1, outside a January export. A day above 12, such as `13/01/2026`, which is text, shows that
   the file writes the day first.

Count the numbers with `COUNT` against `COUNTA`, and test the dates with `ISNUMBER`, `MIN` and `MAX`.

</Solution>
