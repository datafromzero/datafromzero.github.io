## The question

Priya, who runs the budgeting app `app-events`, writes:

> Three tests finished. Which of them can I ship? One line each, and tell me what it is worth in money.

In each test a coin put every new signup into control or the variant. "Bought" means a Plus purchase within 14 days of signing up.

| test | what changed | people | bought, control | bought, variant |
|---|---|---:|---:|---:|
| `paywall_v2` | a redesigned paywall | 5,419 | 343 of 2,706 | 415 of 2,713 |
| `welcome_tips` | tips on the first screens | 4,968 | 304 of 2,449 | 306 of 2,519 |
| `signup_flow_v2` | a new signup screen | 5,481 | 272 of 2,878 | 292 of 2,603 |

   <details>
   <summary>answer</summary>

   Count the people in each group against the planned split. A sample-ratio test with p below 0.0005 voids the test.

   </details>

2. In [*Comparing two groups*](/core/comparing-groups/#3-the-size-of-the-gap-next-to-the-p-value) (C9), what does the interval of a gap tell you that its p-value does not?

   <details>
   <summary>answer</summary>

   How big the gap could be: the range of effects the data cannot rule out.

   </details>

## The big idea

Read a test in a fixed order: the checks that can void it, the effect in the units of the decision, the rule written before launch, then a memo that ends in a decision.

## Learn by doing

About 50 minutes, 3 ideas: the pre-flight, the effect in people and dollars, the memo. The extractions are read-only (run them on `app-events`); the editors use their results.

### 1. Check before you read

**Idea.** A *pre-flight check* is a test of the test, run before any effect is read. Three can void a result: the split (C14), the *balance* (do the groups hold the same kinds of people?) and the *window* (has every person had the whole follow-up?). The Microsoft Research page says that every test should pass the sample-ratio check before it is analyzed.

Split p-values, repeated from C14: 0.92 for `paywall_v2`, 0.32 for `welcome_tips`, 0.0002 for `signup_flow_v2`. Window: the last signup of each test plus 14 days (March 22, May 10 and June 21) came before the export on July 1.

The balance check compares each group's mix of signup platforms, counted by this extraction:

```sql
-- read-only: runs on app-events (the editors of this page hold only cafe-sales)
SELECT a.experiment, a.variant AS arm, e.platform, COUNT(*) AS people
FROM experiment_assignments a
JOIN events e ON e.user_id = a.user_id AND e.event_name = 'signup_complete'
GROUP BY a.experiment, a.variant, e.platform
ORDER BY a.experiment, a.variant, e.platform;
```

**Try it:** the largest gap, in points, between the platform shares of the two groups.

<RunSQL query={`WITH c(experiment, arm, platform, people) AS (
  VALUES ('paywall_v2', 'control', 'android', 827), ('paywall_v2', 'control', 'ios', 921), ('paywall_v2', 'control', 'web', 958),
         ('paywall_v2', 'variant', 'android', 818), ('paywall_v2', 'variant', 'ios', 895), ('paywall_v2', 'variant', 'web', 1000),
         ('welcome_tips', 'control', 'android', 815), ('welcome_tips', 'control', 'ios', 864), ('welcome_tips', 'control', 'web', 770),
         ('welcome_tips', 'variant', 'android', 802), ('welcome_tips', 'variant', 'ios', 895), ('welcome_tips', 'variant', 'web', 822),
         ('signup_flow_v2', 'control', 'android', 1020), ('signup_flow_v2', 'control', 'ios', 1070), ('signup_flow_v2', 'control', 'web', 788),
         ('signup_flow_v2', 'variant', 'android', 656), ('signup_flow_v2', 'variant', 'ios', 1187), ('signup_flow_v2', 'variant', 'web', 760)

s AS (
  SELECT experiment, arm, platform, 100.0 * people / SUM(people) OVER (PARTITION BY experiment, arm) AS share
  FROM c
),

  SELECT experiment, platform,
         MAX(share) FILTER (WHERE arm = 'variant') - MAX(share) FILTER (WHERE arm = 'control') AS gap
  FROM s
  GROUP BY experiment, platform

**Predict:** two tests differ by about a point or less, because chance moves a share by that much. How large is the gap of the third: about 3, 5 or 10 points?

Expected: 3 rows, 2 columns.

*Why:* the other two tests differ by 1.4 and 1.5 points; the third is far larger. A test that fails a pre-flight check gets no effect read; Exercise 2 finds where its groups differ.

### 2. The effect in the units of the decision

**Idea.** A decision uses people and money, not points, so convert: *per 1,000 signups*, with the same interval. For money, define the metric first: *revenue per signup* is the list price of the plan a person bought within 14 days, \$7.99 monthly or \$59.99 annual, and \$0 for no purchase. Few people buy the annual plan, but each is worth about eight monthly buyers.

The extraction for `paywall_v2` counts the people and, for the buyers, the plan; the editors below use its counts.

```sql
-- read-only: runs on app-events
WITH first_plan AS (
  SELECT subscription_id, user_id, MIN(started_on) AS started_on, MIN_BY(plan, updated_at) AS plan_at_start
  FROM subscriptions
  GROUP BY subscription_id, user_id
),
bought AS (
  SELECT DISTINCT ON (a.user_id) a.user_id, f.plan_at_start
  FROM experiment_assignments a
  JOIN events p ON p.user_id = a.user_id AND p.event_name = 'purchase'
   AND p.event_ts >= a.assigned_at AND p.event_ts < a.assigned_at + INTERVAL 14 DAY
  JOIN first_plan f ON f.user_id = a.user_id AND f.started_on = CAST(p.event_ts AS DATE)
  WHERE a.experiment = 'paywall_v2'
  ORDER BY a.user_id, p.event_ts
)
SELECT a.variant, COUNT(*) AS n,
       COUNT(*) FILTER (WHERE b.plan_at_start = 'plus_monthly') AS monthly,
       COUNT(*) FILTER (WHERE b.plan_at_start = 'plus_annual') AS annual
FROM experiment_assignments a
LEFT JOIN bought b USING (user_id)
WHERE a.experiment = 'paywall_v2'
GROUP BY a.variant
ORDER BY a.variant;
```

**Try it:** the gap in buyers per 1,000 signups, with its 95 percent interval (the gap plus or minus 1.96 standard errors).

<RunSQL query={`WITH g(arm, n, buyers) AS (
  VALUES ('control', 2706, 343), ('variant', 2713, 415)
),
r AS (
  SELECT c.buyers * 1.0 / c.n AS p0, t.buyers * 1.0 / t.n AS p1, c.n AS n0, t.n AS n1
  FROM g c JOIN g t ON c.arm = 'control' AND t.arm = 'variant'
)
SELECT ROUND(1000 * (p1 - p0)) AS extra_buyers_per_1000,
       ROUND(1000 * (p1 - p0 - 1.96 * SQRT(p0 * (1 - p0) / n0 + p1 * (1 - p1) / n1))) AS low,
       ROUND(1000 * (p1 - p0 + 1.96 * SQRT(p0 * (1 - p0) / n0 + p1 * (1 - p1) / n1))) AS high
FROM r;`} />

Expected: 1 row, 3 columns.

**Try it.** Now the money. Each person's revenue is 0, 7.99 or 59.99, so the mean and the variance follow from the three counts.

<RunSQL query={`WITH arms(arm, n, monthly, annual) AS (
  VALUES ('control', 2706, 262, 81), ('variant', 2713, 312, 103)
),
m AS (
  SELECT arm, n,
         (7.99 * monthly + 59.99 * annual) / n AS mean,
         (7.99 * 7.99 * monthly + 59.99 * 59.99 * annual) / n AS mean_sq
  FROM arms
),
v AS (
  SELECT arm, n, mean, (mean_sq - mean * mean) * n / (n - 1) AS var FROM m
)
SELECT ROUND(c.mean, 2) AS control, ROUND(t.mean, 2) AS variant,
       ROUND(t.mean - c.mean, 2) AS gap,
       ROUND(t.mean - c.mean - 1.96 * SQRT(c.var / c.n + t.var / t.n), 2) AS low,
       ROUND(t.mean - c.mean + 1.96 * SQRT(c.var / c.n + t.var / t.n), 2) AS high
FROM v c JOIN v t ON c.arm = 'control' AND t.arm = 'variant';`} />

**Predict:** the buyer gap has an interval clear of zero. Will the interval of the dollar gap per signup sit as clearly above zero?

Expected: 1 row, 5 columns.

*Why:* 26 more buyers per 1,000 signups (8 to 45), but \$0.63 more revenue per signup (\$0.04 to \$1.21): its low end is 4 cents, so the money gain barely clears zero. Per 1,000 signups the dollar gap is \$627, from \$42 to \$1,212. Nothing is wrong with the data: a value that jumps between a few sizes (two prices, one rare) spreads the estimate, so the dollar figure is noisier than the buyer count.

### 3. The rule, then the memo

**Idea.** The rule of C14 was written before launch: ship if the lift is at least 2 points, its interval stays above 0 and the cancel guardrail's interval stays below +5 points; drop if even the top of the lift's interval is below 2 points or the bottom of the guardrail's interval is above +5; otherwise keep running. No new analysis here: C14's numbers go beside that rule and into a memo that ends in a decision. The guardrail, from C14: of the buyers, 48 of 343 in control and 75 of 415 in the variant canceled within 30 days, a gap of +4.1 points (-1.1 to +9.3).

> **Decision:** keep `paywall_v2` running; do not ship it yet.
> **Context:** you asked whether to ship the redesigned paywall, tested on 5,419 signups from January 12 to March 8.
> **Tension:** more people bought, but the money gain barely clears zero and the guardrail cannot rule out too high a rise in cancellations.
> **Evidence:** the split was fair (p = 0.92) and the groups matched within 1.5 points. Per 1,000 signups, 26 more people bought Plus within 14 days (8 to 45) and first-purchase revenue rose \$627 (\$42 to \$1,212). Among buyers, 4.1 points more canceled within 30 days (-1.1 to +9.3); the limit is +5.
> **Recommendation:** extend the test until the top of the guardrail interval is below +5; then ship if the lift still clears 2 points, and drop if the bottom of that interval passes +5.

*Why:* the lift passes (26 per 1,000 is 2.6 points, interval above 0) but the guardrail's top, +9.3, is above the limit, so the rule says keep running. The last line says what would change the decision.

<Aside type="tip" title="Remember">

- Pre-flight first: split, balance and window. A failed check voids the test.
- Give the effect in the units of the decision, with its interval.
- Read against the rule written before launch, never against the p-value alone.
- End with a memo: a decision, the evidence and what would change it.

**Common trap:** reading a win off the dashboard before counting the groups.

</Aside>

## Finish it

<Exercise id="data-analyst-ab-test-readout-1">

**The rule on all three tests.** Apply the lift part of C14's rule: *void* if the split p-value is below 0.0005; otherwise *lift passes* if the gap is at least 2 points and its interval stays above 0, *drop* if even the top of the interval is below 2 points, else *keep running*. The editor gives each gap and its plus-or-minus margin in points. Add a `verdict` column. Expected: 3 rows, 4 columns.

<RunSQL query={`SELECT test, ROUND(gap, 1) AS gap_points, ROUND(margin, 1) AS plus_or_minus
FROM (
  SELECT test, split_p, 100 * (b1 * 1.0 / n1 - b0 * 1.0 / n0) AS gap,
         196 * SQRT((b0 * 1.0 / n0) * (1 - b0 * 1.0 / n0) / n0 + (b1 * 1.0 / n1) * (1 - b1 * 1.0 / n1) / n1) AS margin
  FROM (VALUES ('paywall_v2', 2706, 343, 2713, 415, 0.92),
               ('welcome_tips', 2449, 304, 2519, 306, 0.32),
               ('signup_flow_v2', 2878, 272, 2603, 292, 0.0002)) AS t(test, n0, b0, n1, b1, split_p)
) AS g
ORDER BY test;`} />

<details>
<summary>Hint</summary>

A `CASE` takes the first true branch, so test the split first. The interval is `gap - margin` to `gap + margin`.

</details>

<details>
<summary>Half-solution</summary>

```sql
CASE WHEN split_p < 0.0005 THEN 'void'
     WHEN ... THEN 'lift passes'
     ...
```

</details>

<Solution>

Add this column to the `SELECT`:

```sql
       CASE WHEN split_p < 0.0005 THEN 'void'
            WHEN gap >= 2 AND gap - margin > 0 THEN 'lift passes'
            WHEN gap + margin < 2 THEN 'drop'
            ELSE 'keep running' END AS verdict
```

`paywall_v2`: 2.6 plus or minus 1.8 (0.8 to 4.5 before rounding): the lift passes, the guardrail is still to read. `welcome_tips`: -0.3 plus or minus 1.8 (-2.1 to 1.6): *drop*, because the top is below the bar of 2 points. A flat result is not "no effect": the data allow anything from 2.1 fewer to 1.6 more buyers per 100 signups, and rule out only a lift as large as the bar. `signup_flow_v2`: 1.8 plus or minus 1.6: *void*, because its split fails before any interval is read.

</Solution>

</Exercise>

**Spot the flaw.** A colleague writes: "Inside the `paywall_v2` lift, web stands out: 202 of 1,000 variant people bought against 143 of 958 in control, an interval clear of zero; iOS and Android are not. So the redesign works on web: ship it to web only."

<RunSQL query={`SELECT platform,

<Solution>

The query gives web 5.3 points plus or minus 3.4, iOS 1.4 plus or minus 3.2 and Android 0.6 plus or minus 2.9. Test web minus iOS:

```sql
WITH g AS (
  SELECT platform, b1 * 1.0 / n1 - b0 * 1.0 / n0 AS gap,
         (b0 * 1.0 / n0) * (1 - b0 * 1.0 / n0) / n0 + (b1 * 1.0 / n1) * (1 - b1 * 1.0 / n1) / n1 AS var
  FROM (VALUES ('ios', 921, 120, 895, 129), ('web', 958, 143, 1000, 202)) AS p(platform, n0, b0, n1, b1)
)
SELECT ROUND(100 * (w.gap - i.gap), 1) AS web_minus_ios_points,
```
