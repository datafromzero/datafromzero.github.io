## The question

This is the sixth lesson of the dashboard project, after [*A KPI dictionary and a metrics layer*](/data-analyst/metrics-and-kpi-dictionary/) (DA11). Dana's dashboard is a published workbook made from a file, and every Monday you reload it from a fresh export. Four loads could arrive, and on the screen each one looks like a dashboard.

| load | what went wrong |
|---|---|
| `ok` | nothing |
| `harbor_stopped` | Harbor's feed stopped on June 23 |
| `doubled` | the export was loaded twice |
| `in_cents` | the last day of one cafe arrived in cents |

By the end you have three checks and know what each one misses.

## The big idea

A dashboard is right today only if something checks it every time it refreshes: is it fresh, is it complete, and does it add up to the source.

## Learn by doing

About 50 minutes, 4 ideas: freshness, rows and totals, a change request, owners. The SQL runs in the page. Run each block after the ones above it.

### 1. Freshness: how old is the newest row

**Idea.** A *freshness check* compares the age of the newest row with what you expect. Decide what it looks at: the table, or each cafe. The Tableau Public FAQ says it supports only extracted data, and that automatic refresh works only for Google Sheets, every 24 hours: for a CSV or an Excel file it "is not supported". So the freshness line of Dana's screen is yours to compute and paste each time.

**Try it.** This block builds the source lines (completed orders, order 2075 counted as 2 units) and the four loads, then asks each load for its newest order of the whole table and of the cafe furthest behind.

<RunSQL query={`CREATE OR REPLACE TABLE source_lines AS
SELECT oi.order_item_id AS line_id, o.order_id, s.store_name AS store, o.ordered_at,
       (CASE WHEN oi.order_item_id = 6952 THEN 2 ELSE oi.quantity END) * p.unit_price_usd - oi.discount_usd AS amount
FROM orders o
JOIN order_items oi ON oi.order_id = o.order_id
JOIN products p ON p.product_id = oi.product_id
JOIN stores s ON s.store_id = o.store_id
WHERE o.status = 'completed';

CREATE OR REPLACE TABLE loads AS
SELECT l.load_name, s.line_id, s.order_id, s.store, s.ordered_at,
       CASE WHEN l.load_name = 'in_cents' AND s.store = 'Campus' AND CAST(s.ordered_at AS DATE) = DATE '2026-06-30'
            THEN s.amount * 100 ELSE s.amount END AS amount
FROM source_lines s
CROSS JOIN (VALUES ('ok'), ('harbor_stopped'), ('doubled'), ('doubled'), ('in_cents')) AS l(load_name)
WHERE NOT (l.load_name = 'harbor_stopped' AND s.store = 'Harbor' AND s.ordered_at >= '2026-06-24');

WITH per_cafe AS (
  SELECT load_name, store, MAX(ordered_at) AS newest FROM loads GROUP BY load_name, store
)
SELECT load_name, MAX(newest) AS table_newest, MIN(newest) AS stalest_cafe_newest
FROM per_cafe
GROUP BY load_name
ORDER BY load_name;`} />

**Predict:** which loads pass if you ask only for the newest order of the table, and which if you ask for the cafe furthest behind?

Expected: 4 rows, 3 columns.

*Why:* every load has its newest order on June 30 at 16:30, so a table-level check passes all four. The cafe furthest behind is Harbor in `harbor_stopped`, whose last order is June 23 at 14:02; in the other three it is Campus at 12:10 on June 30. A rule that works: every cafe has an order on the last day. The same query writes the screen's line, and it should print the cafe with the oldest data, not the table.

### 2. Rows and totals: is it complete, and does it add up

**Idea.** A *row-count check* compares the rows loaded with the rows the source holds under the same filter. A *reconciliation* compares a total with the source's total. They look at different things.

**Try it.** Run unit 1 first. For each load, how many rows and what total are off against the source?

<RunSQL query={`SELECT load_name,
       COUNT(*) AS rows_loaded,
       COUNT(*) - (SELECT COUNT(*) FROM source_lines) AS rows_off,
       ROUND(SUM(amount), 2) AS total_loaded,
       ROUND(SUM(amount) - (SELECT SUM(amount) FROM source_lines), 2) AS total_off
FROM loads
GROUP BY load_name
ORDER BY load_name;`} />

**Predict:** which load passes the row count and still gets the total wrong?

Expected: 4 rows, 5 columns.

*Why:* `in_cents` has the right 3,286 rows and a total \$2,029.50 too high: Campus's three lines of June 30 add to \$20.50, and a hundred times that adds \$2,029.50 more. `doubled` has 3,286 rows too many, and `harbor_stopped` 51 too few and \$383.00 less. Each failure has a first check that sees it, and the total sees all three.

### 4. Who owns each number

**Idea.** A check nobody owns is a log nobody reads. Beside each card, write who says what it means, who runs the checks, when, and what happens when one fails.

| card | meaning | checks | runs | when one fails |
|---|---|---|---|---|
| Revenue | Dana, entry version 1 | the analyst: freshness, rows, total | each Monday, before publishing | the old workbook stays up; Dana gets a message |

The owner is a name, not a team. Gross sales gets its own row, with its own entry; the checks, the owner of the checks and the time stay the same. The row is the page you open when a number is questioned.

<Aside type="tip" title="Remember">

- Check freshness for each cafe, not for the table.
- A row count and a total see different failures: run both.
- A change request: assess with old and new side by side, version, tell.
- Give each card an owner, a time and an action.

**Common trap:** trusting the screen because the numbers look like numbers.

</Aside>

**Spot the flaw.** A colleague writes a total check that "returns the cafes whose loaded total differs from the source; no rows means pass". She runs it on `load_empty`, a load whose job wrote nothing, and sees no rows.

<RunSQL query={`CREATE OR REPLACE TABLE load_empty AS SELECT * FROM source_lines WHERE false;

SELECT l.store, ROUND(SUM(l.amount), 2) AS loaded, s.source_total
FROM load_empty l
JOIN (SELECT store, ROUND(SUM(amount), 2) AS source_total FROM source_lines GROUP BY store) s ON s.store = l.store
GROUP BY l.store, s.source_total
HAVING ROUND(SUM(l.amount), 2) <> s.source_total;`} />

Run unit 1 first. Expected: no rows. Say why the silence is wrong, and write a version that cannot pass on an empty load.

<Solution>

An empty load has no cafes to compare, so the query finds nothing wrong: a check that is silent when it passes is also silent when it found nothing to check. Start from the source and keep every cafe:

```sql
SELECT s.store, COALESCE(l.loaded, 0) AS loaded, s.source_total
FROM (SELECT store, ROUND(SUM(amount), 2) AS source_total FROM source_lines GROUP BY store) s
LEFT JOIN (SELECT store, ROUND(SUM(amount), 2) AS loaded FROM load_empty GROUP BY store) l ON l.store = s.store
WHERE COALESCE(l.loaded, 0) <> s.source_total;
```

It returns 3 rows, one for each cafe, each with 0 loaded.

</Solution>
