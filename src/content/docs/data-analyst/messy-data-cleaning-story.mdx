## The big idea

Clean in layers you can name (profile, standardize, merge, log, reconcile), and finish only when every dollar of difference between the sources has a reason.

## Learn by doing

About 30 minutes, 4 ideas: profile, standardize, merge, log and reconcile. The editors hold a slice of the processor file, May 1 (11 rows, from the full file); each unit builds on the view of the unit before, so run them in order.

### 1. Profile before you fix

**Idea.** A *conflict* is the same thing written two ways. Profile each source column by column, and count what looks wrong before you change anything. The profile of the slice is one row of counts.

**Try it:** build the slice as a view and profile it.

<RunSQL query={`CREATE OR REPLACE VIEW raw_may1 AS
SELECT * FROM (VALUES
  ('ST-000919', 'TEST-0005', 'Old Town', '05/01/2026 14:00', '$0.01', 'TEST'),
  ('ST-000920', 'ORD-2068', 'Harbor', '05/01/2026 14:38', '$4.25', 'SALE'),
  ('ST-000921', 'ORD-2069', 'CAMPUS', '05/01/2026 14:49', '$3.25', 'SALE'),
  ('ST-000922', 'ORD-2070', 'campus ', '05/01/2026 16:05', '$9.25', 'SALE'),
  ('ST-000923', 'ORD-2072', 'Campus', '05/01/2026 17:10', '$16.75', 'SALE'),
  ('ST-000923', 'ORD-2072', 'Campus', '05/01/2026 17:10', '$16.75', 'SALE'),
  ('ST-000924', 'ORD-2074', 'Old Town ', '05/01/2026 20:08', '$9.50', 'SALE'),
  ('ST-000925', 'ORD-2075', 'old town', '05/01/2026 20:25', '$30.50', 'SALE'),
  ('ST-000926', 'ORD-2076', 'Old Town', '05/01/2026 22:18', '$13.75', 'SALE'),
  ('ST-000927', 'ORD-2077', NULL, '05/01/2026 22:39', '$7.00', 'SALE'),
  ('ST-000928', 'ORD-2078', 'Old Town ', '05/02/2026 00:39', '$18.50', 'SALE')
) AS t(settlement_id, order_ref, merchant, settled_at, amount, type);

SELECT COUNT(*) AS row_count,
       COUNT(DISTINCT settlement_id) AS ids,
       COUNT(DISTINCT merchant) AS spellings,
       COUNT(*) FILTER (WHERE merchant IS NULL) AS blank_merchant,
       COUNT(*) FILTER (WHERE type = 'TEST') AS tests
FROM raw_may1;`} />

**Predict:** the till has 3 stores. How many different merchant spellings does the slice use?

Expected: 1 row, 5 columns.

*Why:* 7 spellings for 3 stores (case, a trailing space, an alias), 11 rows but 10 ids (one exact copy), 1 blank merchant and 1 test payment. Three more conflicts need no count: the key is `ORD-2075` where the till says 2075; money is text with a dollar sign; time is UTC text, `05/02/2026 00:39` for an order the till stamps May 1 at 5:39 p.m.

### 2. Standardize in a copy

**Idea.** *Standardize* each conflict with one rule, written as a column of a new view, so the raw rows stay as they came. Exact copies go with `SELECT DISTINCT`, which compares every column. A *mapping table* sends every spelling to the store key, after `TRIM` and `LOWER`, so an alias is one more row. `strptime` turns the time text into a timestamp; its `%m/%d/%Y %H:%M` reads the processor's format.

**Try it:** run unit 1 first, then build the clean copy.

<RunSQL query={`CREATE OR REPLACE VIEW settled_clean AS
WITH d AS (
  SELECT DISTINCT * FROM raw_may1 WHERE type <> 'TEST'
),
store_map(name, store_id) AS (
  VALUES ('old town', 1), ('campus', 2), ('berkeley campus', 2), ('harbor', 3), ('alameda harbor', 3)
)
SELECT d.settlement_id,
       CAST(REPLACE(d.order_ref, 'ORD-', '') AS INTEGER) AS order_id,
       m.store_id,
       strptime(d.settled_at, '%m/%d/%Y %H:%M') AS settled_utc,
       CAST(REPLACE(d.amount, '$', '') AS DECIMAL(10, 2)) AS amount
FROM d
LEFT JOIN store_map m ON m.name = LOWER(TRIM(d.merchant));

SELECT * FROM settled_clean ORDER BY order_id;`} />

**Predict:** how many rows come out, and which row has no store?

Expected: 9 rows, 5 columns.

*Why:* 11 rows become 10 (the copy) and then 9 (the test payment). Order 2077 has no store: the merchant was blank, and the mapping has nothing to match. Do not guess it; the till knows.

### 3. Merge, then prove what the join did

**Idea.** A *validated merge* joins on the key and then shows what the join did: matched pairs, rows in one source only, and pairs whose values disagree. A `FULL JOIN` keeps both unmatched sides. Check also anything that should be constant: here the gap in hours between the till's time and the processor's.

**Try it:** run units 1 and 2 first. The till side is the card and mobile orders of May 1.

<RunSQL query={`WITH till AS (
  SELECT o.order_id, o.store_id, o.ordered_at,
         SUM(oi.quantity * p.unit_price_usd - oi.discount_usd) AS amount
  FROM orders o
  JOIN order_items oi ON oi.order_id = o.order_id
  JOIN products p ON p.product_id = oi.product_id
  WHERE o.status = 'completed'
    AND o.payment_method IN ('card', 'mobile')
    AND CAST(o.ordered_at AS DATE) = DATE '2026-05-01'
  GROUP BY o.order_id, o.store_id, o.ordered_at
)
SELECT COALESCE(t.order_id, s.order_id) AS order_id,
       t.store_id AS till_store, s.store_id AS processor_store,
       t.amount AS till_amount, s.amount AS processor_amount,
       DATE_DIFF('hour', t.ordered_at, s.settled_utc) AS hours_gap,
       CASE WHEN t.order_id IS NULL THEN 'only in processor file'
            WHEN s.order_id IS NULL THEN 'only in till'
            WHEN s.amount <> t.amount THEN 'amounts differ'
            ELSE 'match' END AS status
FROM till t
FULL JOIN settled_clean s ON s.order_id = t.order_id
ORDER BY order_id;`} />

**Predict:** of the 10 till orders, how many get `match`? What are the others?

Expected: 10 rows, 7 columns.

*Why:* 8 match; order 2073 (Campus, \$13.50) is only in the till; order 2075 differs, \$197.00 in the till and \$30.50 at the processor. The till line has 20 Turkey Sandwiches, \$185.00; the processor charged 2, \$18.50: the extra zero of the dataset README, now with evidence from a second source. The hours gap is 7 on every matched row, so the processor's clock is UTC; the till's local time is the one to keep, and the file's order 2078 falls on May 2 only in UTC. Order 2077 takes its store from the till.

### 4. The log, and every dollar of difference

**Idea.** A *cleaning log* has one line per decision: the rule, and the rows or dollars it touched. Its twin is the *reconciliation*: both totals, the difference, and each part of it named, until nothing is unexplained. This is the full file.

| step | rule | rows | dollars |
|---|---|---|---:|
| 1 | exact copies removed with `DISTINCT` | 1,557 to 1,520 | -447.00 |
| 2 | 6 test payments dropped | 1,520 to 1,514 | -0.06 |
| 3 | no dollar sign means cents: divided by 100 | 3 rows | none |
| 4 | 12 spellings mapped to 3 stores; 29 blank merchants take the till's store | 1,514 | none |
| 5 | processor time not used: the till's local time is kept (gap 8 hours to March 7, 7 from March 8) | 1,514 | none |
| 6 | order 2075: quantity 20 corrected to 2 on the till | 1 line | -166.50 |
| 7 | 33 till orders missing from the file: kept, the till is the sale | 33 orders | 416.50 |

**Try it:** the till's total for card and mobile orders is the sum of its orders; the cleaned processor total is \$19,006.75 over 1,514 payments, and 9 order numbers are the isolated misses.

<RunSQL query={`WITH till AS (
  SELECT o.order_id, o.store_id, CAST(o.ordered_at AS DATE) AS d,
         SUM(oi.quantity * p.unit_price_usd - oi.discount_usd) AS amount
  FROM orders o
  JOIN order_items oi ON oi.order_id = o.order_id
  JOIN products p ON p.product_id = oi.product_id
  WHERE o.status = 'completed' AND o.payment_method IN ('card', 'mobile')
  GROUP BY o.order_id, o.store_id, CAST(o.ordered_at AS DATE)
),
x AS (
  SELECT (SELECT SUM(amount) FROM till) AS till_total,
         19006.75 AS processor_total,
         (SELECT SUM((oi.quantity - 2) * p.unit_price_usd)
          FROM order_items oi JOIN products p ON p.product_id = oi.product_id
          WHERE oi.order_item_id = 6952) AS order_2075,
         (SELECT SUM(amount) FROM till
          WHERE store_id = 3 AND d BETWEEN DATE '2026-05-18' AND DATE '2026-05-24') AS harbor_week,
         (SELECT SUM(amount) FROM till
          WHERE order_id IN (1179, 1328, 1626, 1775, 1924, 2073, 2222, 2520, 2669)) AS nine_orders
)
SELECT 'till minus processor' AS line, till_total - processor_total AS dollars FROM x
UNION ALL SELECT 'order 2075: 18 sandwiches not charged', order_2075 FROM x
UNION ALL SELECT 'Harbor May 18 to 24: nothing exported', harbor_week FROM x
UNION ALL SELECT 'nine other orders not exported', nine_orders FROM x
UNION ALL SELECT 'left unexplained', till_total - processor_total - order_2075 - harbor_week - nine_orders FROM x;`} />

**Predict:** which of the three named causes is the largest?

Expected: 5 rows, 2 columns.

*Why:* the \$583.00 gap is Harbor's week, \$263.25 (24 orders), then order 2075, \$166.50, then nine orders, \$153.25, and nothing is left unexplained. The sources do not agree and neither is "right": the till holds every sale, and the processor corrected one entry. With the correction the till's card and mobile total is \$19,423.25, and the trusted table follows the till.

**Try it.** The table the dashboard chapters use, one row per sold line, with the 2075 correction and a label for walk-in orders:

<RunSQL query={`CREATE OR REPLACE VIEW sales_clean AS
SELECT oi.order_item_id AS line_id, o.order_id, o.ordered_at, CAST(o.ordered_at AS DATE) AS order_date,
       s.store_name AS store, p.product_name AS product, p.category,
       CASE WHEN oi.order_item_id = 6952 THEN 2 ELSE oi.quantity END AS quantity,
       p.unit_price_usd AS unit_price, oi.discount_usd AS discount,
       (CASE WHEN oi.order_item_id = 6952 THEN 2 ELSE oi.quantity END) * p.unit_price_usd - oi.discount_usd AS amount,
       o.payment_method, COALESCE(c.loyalty_tier, 'walk-in') AS loyalty_tier
FROM orders o
JOIN order_items oi ON oi.order_id = o.order_id
JOIN products p ON p.product_id = oi.product_id
JOIN stores s ON s.store_id = o.store_id
LEFT JOIN customers c ON c.customer_id = o.customer_id
WHERE o.status = 'completed';

SELECT COUNT(*) AS lines, COUNT(DISTINCT order_id) AS orders, SUM(amount) AS revenue FROM sales_clean;`} />

Expected: 1 row, 3 columns: 3,286 lines, 1,799 orders, revenue \$22,582.75 (\$22,749.25 as recorded, before the correction). Chapter 4 exports this table to a file.

<Aside type="tip" title="Remember">

- Profile first, count what is wrong, change nothing yet.
- Standardize in a copy; a mapping table holds every spelling, and `DISTINCT` removes only exact copies.
- A merge is not finished until you have counted matched, one-sided and disagreeing rows.
- A log line names a rule and what it touched; a reconciliation ends at 0.00 unexplained.

**Common trap:** agreeing on the grand total while errors of opposite sign hide inside it.

</Aside>

<Solution>

```sql
WITH p AS (
  SELECT CAST(REPLACE(order_ref, 'ORD-', '') AS INTEGER) AS order_id,
         CASE WHEN amount LIKE '$%' THEN CAST(REPLACE(amount, '$', '') AS DECIMAL(10, 2))
              ELSE CAST(amount AS DECIMAL(10, 2)) / 100 END AS amount
  FROM (SELECT DISTINCT * FROM raw_jun3 WHERE type <> 'TEST')
),
till AS (
  SELECT o.order_id, o.store_id, SUM(oi.quantity * pr.unit_price_usd - oi.discount_usd) AS amount
  FROM orders o
  JOIN order_items oi ON oi.order_id = o.order_id
  JOIN products pr ON pr.product_id = oi.product_id
  WHERE o.status = 'completed' AND o.payment_method IN ('card', 'mobile')
    AND CAST(o.ordered_at AS DATE) = DATE '2026-06-03'
  GROUP BY o.order_id, o.store_id
)
SELECT t.store_id AS store, SUM(t.amount) AS till, SUM(p.amount) AS processor, SUM(t.amount) - SUM(p.amount) AS difference
FROM till t
JOIN p ON p.order_id = t.order_id
GROUP BY t.store_id
ORDER BY t.store_id;
```

Three Campus amounts have no dollar sign: they are cents (`1700` is \$17.00), a unit mismatch. Left as dollars they would make Campus's day \$4,425.00. Treated as cents the stores read \$69.50, \$44.25 and \$19.50 on both sides, a difference of 0.00 each. Order 2482 sits on June 4 in the processor's UTC, which is why the join uses the order number and not the date.

</Solution>

**Spot the flaw.** A colleague finishes: "I removed the test payments, fixed the cents and compared totals. The processor file adds up to \$19,453.75 and the till to \$19,589.75, so they agree within 0.7 percent. Reconciled." The three parts of the gap are \$447.00 for 37 exact copies still in the file, -\$416.50 for 33 orders missing from it and -\$166.50 for order 2075.

<RunSQL query={`SELECT 19589.75 - 19453.75 AS difference,
       ROUND(100 * (19589.75 - 19453.75) / 19589.75, 2) AS percent;`} />

Expected: 1 row, 2 columns. Run it, then use the three parts to show what the small difference hides, and say what is wrong with the method.

<Solution>

The query gives \$136.00, 0.69 percent. The parts, with their signs, add up to the same number:

```sql
SELECT 447.00 - 416.50 - 166.50 AS net, 447.00 + 416.50 + 166.50 AS gross_errors;
```

The net is -136.00 only because errors of opposite sign cancel: the gross size of the errors is \$1,030.00, a wrong order and 70 rows that are wrong in count. A grand total is the weakest test: it agrees whenever the errors cancel. The method needs the checks of units 3 and 4: row counts on both sides, the unmatched orders and every difference named.

</Solution>

</Exercise>
