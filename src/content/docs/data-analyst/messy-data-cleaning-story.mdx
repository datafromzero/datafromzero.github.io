## The question

This is chapter 1 of the dashboard project. Dana asks:

> Before we build a dashboard, I need numbers I can defend. The till says card and mobile sales came to \$19,589.75. The payment processor sends a file. Which one is right, and can I have one table I can trust?

The sources are the till (`orders`, `order_items`, `products`) and the processor's export: one row per card or mobile payment, never cash. Its first rows:

| settlement_id | order_ref | merchant | settled_at | amount | type |
|---|---|---|---|---|---|
| ST-000001 | TEST-0001 | Old Town | 01/01/2026 15:00 | \$0.01 | TEST |
| ST-000002 | ORD-1001 | CAMPUS | 01/01/2026 16:02 | \$14.00 | SALE |
| ST-000003 | ORD-1002 | Old Town␠ | 01/01/2026 23:38 | \$12.50 | SALE |

The whole file, [`settlements.csv`](https://raw.githubusercontent.com/datafromzero/datafromzero.github.io/v0.3.0/datasets/cafe-sales/v1/extras/settlements.csv), has 1,557 rows. The till holds 1,547 completed card or mobile orders, order 2075 included as recorded.

## The big idea

Clean in layers you can name (profile, standardize, merge, log, reconcile), and finish only when every dollar of difference between the sources has a reason.

## Learn by doing

About 60 minutes, 4 ideas: profile, standardize, merge, log and reconcile. The editors hold a slice of the file (May 1, 11 rows); run the units in order, each builds on the view before. Unit 4 uses the whole file on your computer.

### 1. Profile before you fix

**Idea.** A *conflict* is the same thing written two ways. Profile each source column by column, and count what looks wrong before you change anything.

**Try it:** build the slice as a view and profile it.

<RunSQL query={`CREATE OR REPLACE VIEW raw_may1 AS
SELECT * FROM (VALUES
  ('ST-000919', 'TEST-0005', 'Old Town', '05/01/2026 14:00', '$0.01', 'TEST'),
  ('ST-000920', 'ORD-2068', 'Harbor', '05/01/2026 14:38', '$4.25', 'SALE'),
  ('ST-000921', 'ORD-2069', 'CAMPUS', '05/01/2026 14:49', '$3.25', 'SALE'),
  ('ST-000922', 'ORD-2070', 'campus ', '05/01/2026 16:05', '$9.25', 'SALE'),
  ('ST-000923', 'ORD-2072', 'Campus', '05/01/2026 17:10', '$16.75', 'SALE'),
  ('ST-000923', 'ORD-2072', 'Campus', '05/01/2026 17:10', '$16.75', 'SALE'),
  ('ST-000924', 'ORD-2074', 'Old Town ', '05/01/2026 20:08', '$9.50', 'SALE'),
  ('ST-000925', 'ORD-2075', 'old town', '05/01/2026 20:25', '$30.50', 'SALE'),
  ('ST-000926', 'ORD-2076', 'Old Town', '05/01/2026 22:18', '$13.75', 'SALE'),
  ('ST-000927', 'ORD-2077', NULL, '05/01/2026 22:39', '$7.00', 'SALE'),
  ('ST-000928', 'ORD-2078', 'Old Town ', '05/02/2026 00:39', '$18.50', 'SALE')
) AS t(settlement_id, order_ref, merchant, settled_at, amount, type);

SELECT COUNT(*) AS row_count,
       COUNT(DISTINCT settlement_id) AS ids,
       COUNT(DISTINCT merchant) AS spellings,
       COUNT(*) FILTER (WHERE merchant IS NULL) AS blank_merchant,
       COUNT(*) FILTER (WHERE type = 'TEST') AS tests
FROM raw_may1;`} />

**Predict:** the till has 3 stores. How many different merchant spellings does the slice use?

Expected: 1 row, 5 columns.

*Why:* 7 spellings for 3 stores (case and trailing spaces), 11 rows but 10 ids (one exact copy), 1 blank merchant and 1 test payment. Three more conflicts need no count: the key is `ORD-2075` where the till says 2075; money is text with a dollar sign; time is UTC text, `05/02/2026 00:39` for an order the till stamps May 1 at 5:39 p.m.

### 2. Standardize in a copy

**Idea.** *Standardize* each conflict with one rule, written as a column of a new view, so the raw rows stay as they came. Exact copies go with `SELECT DISTINCT`, which compares every column. A *mapping table* sends every spelling, after `TRIM` and `LOWER`, to the store key; an alias is one more row. `strptime` turns the time text into a timestamp; its `%m/%d/%Y %H:%M` reads the processor's format.

**Try it:** run unit 1 first, then build the clean copy.

<RunSQL query={`CREATE OR REPLACE VIEW settled_clean AS
WITH d AS (
  SELECT DISTINCT * FROM raw_may1 WHERE type <> 'TEST'
),
store_map(name, store_id) AS (
  VALUES ('old town', 1), ('campus', 2), ('berkeley campus', 2), ('harbor', 3), ('alameda harbor', 3)
)
SELECT d.settlement_id,
       CAST(REPLACE(d.order_ref, 'ORD-', '') AS INTEGER) AS order_id,
       m.store_id,
       strptime(d.settled_at, '%m/%d/%Y %H:%M') AS settled_utc,
       CAST(REPLACE(d.amount, '$', '') AS DECIMAL(10, 2)) AS amount
FROM d
LEFT JOIN store_map m ON m.name = LOWER(TRIM(d.merchant));

SELECT * FROM settled_clean ORDER BY order_id;`} />

**Predict:** how many rows come out, and which row has no store?

Expected: 9 rows, 5 columns.

*Why:* 11 rows become 10 (the copy) and then 9 (the test payment). Order 2077 has no store: the merchant was blank, and the mapping has nothing to match. The till knows it.

### 3. Merge, then prove what the join did

**Idea.** A *validated merge* joins on the key and then shows what the join did: matched pairs, rows in one source only, and pairs whose values disagree. A `FULL JOIN` keeps both unmatched sides. Check anything that should be constant, here the gap in hours between the till's time and the processor's.

**Try it:** run units 1 and 2 first. The till side is the card and mobile orders of May 1.

<RunSQL query={`WITH till AS (
  SELECT o.order_id, o.store_id, o.ordered_at,
         SUM(oi.quantity * p.unit_price_usd - oi.discount_usd) AS amount
  FROM orders o
  JOIN order_items oi ON oi.order_id = o.order_id
  JOIN products p ON p.product_id = oi.product_id
  WHERE o.status = 'completed'
    AND o.payment_method IN ('card', 'mobile')
    AND CAST(o.ordered_at AS DATE) = DATE '2026-05-01'
  GROUP BY o.order_id, o.store_id, o.ordered_at
)
SELECT COALESCE(t.order_id, s.order_id) AS order_id,
       t.store_id AS till_store, s.store_id AS processor_store,
       t.amount AS till_amount, s.amount AS processor_amount,
       DATE_DIFF('hour', t.ordered_at, s.settled_utc) AS hours_gap,
       CASE WHEN t.order_id IS NULL THEN 'only in processor file'
            WHEN s.order_id IS NULL THEN 'only in till'
            WHEN s.amount <> t.amount THEN 'amounts differ'
            ELSE 'match' END AS status
FROM till t
FULL JOIN settled_clean s ON s.order_id = t.order_id
ORDER BY order_id;`} />

**Predict:** of the 10 till orders, how many get `match`? What are the others?

Expected: 10 rows, 7 columns.

*Why:* 8 match; order 2073 (Campus, \$13.50) is only in the till; order 2075 differs, \$197.00 in the till and \$30.50 at the processor. The till line has 20 Turkey Sandwiches (\$185.00), the processor charged 2 (\$18.50): the README's extra zero, confirmed by a second source. The hours gap is 7 on every matched row, so the processor's clock is UTC; keep the till's local time (order 2078 falls on May 2 only in UTC). Order 2077 takes its store from the till.

### 4. The log, and every dollar of difference

**Idea.** A *cleaning log* has one line per decision: the rule, and the rows or dollars it touched. Its twin is the *reconciliation*: both totals, the difference, and each part of it named, until nothing is unexplained. This log is for the whole file; unit 1's profile query on it (`read_csv('settlements.csv', all_varchar = true)` in place of `raw_may1`) gives its first lines.

| step | rule | rows | dollars |
|---|---|---|---:|
| 1 | exact copies removed with `DISTINCT` | 1,557 to 1,520 | -447.00 |
| 2 | 6 test payments dropped | 1,520 to 1,514 | -0.06 |
| 3 | no dollar sign means cents: divided by 100 | 3 rows | none |
| 4 | 12 spellings mapped to 3 stores; 29 blank merchants take the till's store | 1,514 | none |
| 5 | processor time not used: the till's local time is kept (gap 8 hours to March 7, 7 from March 8) | 1,514 | none |
| 6 | order 2075: quantity 20 corrected to 2 on the till | 1 line | -166.50 |
| 7 | 33 till orders missing from the file: kept, the till is the sale | 33 orders | 416.50 |

**Try it:** the editors hold only a slice, so run this read-only block in DuckDB on your computer ([`cafe-sales.sql`](https://raw.githubusercontent.com/datafromzero/datafromzero.github.io/v0.3.0/datasets/cafe-sales/v1/cafe-sales.sql) first, in the folder that holds [`settlements.csv`](https://raw.githubusercontent.com/datafromzero/datafromzero.github.io/v0.3.0/datasets/cafe-sales/v1/extras/settlements.csv)). It cleans the file as the log says and splits the gap.

```sql
CREATE OR REPLACE VIEW processor AS
SELECT DISTINCT CAST(REPLACE(order_ref, 'ORD-', '') AS INTEGER) AS order_id,
       CAST(CASE WHEN amount LIKE '$%' THEN CAST(REPLACE(amount, '$', '') AS DECIMAL(10, 2))
                 ELSE CAST(amount AS DECIMAL(10, 2)) / 100 END AS DECIMAL(10, 2)) AS amount
FROM read_csv('settlements.csv', all_varchar = true)
WHERE type <> 'TEST';

WITH till AS (
  SELECT o.order_id, o.store_id, CAST(o.ordered_at AS DATE) AS d,
         SUM(oi.quantity * p.unit_price_usd - oi.discount_usd) AS amount
  FROM orders o
  JOIN order_items oi ON oi.order_id = o.order_id
  JOIN products p ON p.product_id = oi.product_id
  WHERE o.status = 'completed' AND o.payment_method IN ('card', 'mobile')
  GROUP BY o.order_id, o.store_id, CAST(o.ordered_at AS DATE)
),
pairs AS (
  SELECT t.store_id, t.d, t.amount AS till_amount, p.amount AS processor_amount, p.order_id IS NULL AS missing
  FROM till t
  LEFT JOIN processor p ON p.order_id = t.order_id
),
causes AS (
  SELECT CASE WHEN NOT missing THEN 'amount differs'
              WHEN store_id = 3 AND d BETWEEN DATE '2026-05-18' AND DATE '2026-05-24' THEN 'missing, Harbor May 18 to 24'
              ELSE 'missing, any other order' END AS cause,
         COUNT(*) FILTER (WHERE missing OR till_amount <> processor_amount) AS orders,
         SUM(till_amount - COALESCE(processor_amount, 0)) AS dollars
  FROM pairs
  GROUP BY 1
),
gap AS (SELECT SUM(till_amount) - (SELECT SUM(amount) FROM processor) AS dollars FROM pairs)
SELECT cause, orders, dollars FROM causes
UNION ALL SELECT 'till minus processor', NULL, dollars FROM gap
UNION ALL SELECT 'left unexplained', NULL, (SELECT dollars FROM gap) - (SELECT SUM(dollars) FROM causes);
```

**Predict:** which of the three named causes is the largest?

Expected: 5 rows, 3 columns, in any order.

*Why:* the \$583.00 gap is Harbor's week, \$263.25 (24 orders), then the one amount that differs, order 2075, \$166.50, then nine other missing orders, \$153.25, and nothing is left unexplained. Neither source is "right": the till holds every sale, and the processor corrected one entry. With the correction the till's total is \$19,423.25, and the trusted table follows the till.

<RunSQL query={`CREATE OR REPLACE VIEW sales_clean AS
SELECT oi.order_item_id AS line_id, o.order_id, o.ordered_at, CAST(o.ordered_at AS DATE) AS order_date,
       s.store_name AS store, p.product_name AS product, p.category,
       CASE WHEN oi.order_item_id = 6952 THEN 2 ELSE oi.quantity END AS quantity,
       p.unit_price_usd AS unit_price, oi.discount_usd AS discount,
       (CASE WHEN oi.order_item_id = 6952 THEN 2 ELSE oi.quantity END) * p.unit_price_usd - oi.discount_usd AS amount,
       o.payment_method, COALESCE(c.loyalty_tier, 'walk-in') AS loyalty_tier
FROM orders o
JOIN order_items oi ON oi.order_id = o.order_id
JOIN products p ON p.product_id = oi.product_id
JOIN stores s ON s.store_id = o.store_id
LEFT JOIN customers c ON c.customer_id = o.customer_id
WHERE o.status = 'completed';

SELECT COUNT(*) AS lines, COUNT(DISTINCT order_id) AS orders, SUM(amount) AS revenue FROM sales_clean;`} />

Expected: 1 row, 3 columns: 3,286 lines, 1,799 orders, revenue \$22,582.75 (\$22,749.25 as recorded, before the correction). Chapter 4 uses it as a downloadable file, `sales_clean.csv`.

<Aside type="tip" title="Remember">

- Profile first, count what is wrong, change nothing yet.
- Standardize in a copy; `DISTINCT` removes only exact copies.
- Count matched, one-sided and disagreeing rows after a merge.
- A log line names a rule and what it touched; a reconciliation ends at 0.00 unexplained.

**Common trap:** stopping at the first check that passes.

</Aside>

<summary>Half-solution</summary>

<Solution>

```sql
WITH p AS (
  SELECT merchant AS store,
         CAST(strptime(settled_at, '%m/%d/%Y %H:%M') - INTERVAL 7 HOUR AS DATE) AS local_day,
         CAST(CASE WHEN amount LIKE '$%' THEN CAST(REPLACE(amount, '$', '') AS DECIMAL(10, 2))
                   ELSE CAST(amount AS DECIMAL(10, 2)) / 100 END AS DECIMAL(10, 2)) AS amount
  FROM raw_jun3
),
till AS (
  SELECT s.store_name AS store, SUM(oi.quantity * pr.unit_price_usd - oi.discount_usd) AS amount
  FROM orders o
  JOIN stores s ON s.store_id = o.store_id
  JOIN order_items oi ON oi.order_id = o.order_id
  JOIN products pr ON pr.product_id = oi.product_id
  WHERE o.status = 'completed' AND o.payment_method IN ('card', 'mobile')
    AND CAST(o.ordered_at AS DATE) = DATE '2026-06-03'
  GROUP BY s.store_name
)
SELECT t.store, t.amount AS till, SUM(p.amount) AS processor, t.amount - SUM(p.amount) AS difference
FROM till t
JOIN p ON p.store = t.store AND p.local_day = DATE '2026-06-03'
GROUP BY t.store, t.amount
ORDER BY t.store;
```

Three Campus amounts have no dollar sign: they are cents (`1700` is \$17.00), a unit mismatch. Left as dollars they would make Campus's day \$4,425.00. Treated as cents the stores read \$44.25, \$19.50 and \$69.50 on both sides, a difference of 0.00 each. One Harbor payment, stamped `06/04/2026 00:16`, is June 3 in the till's time: without the shift, Harbor's processor total reads \$13.00 against the till's \$19.50.

</Solution>

**Spot the flaw.** A colleague finishes: "I removed the test payments, fixed the cents and compared totals. The processor file adds up to \$19,453.75 and the till to \$19,589.75, so they agree within 0.7 percent. Reconciled." Measured as the processor file minus the till, the three parts of the gap are +\$447.00 for 37 exact copies still in the file, -\$416.50 for 33 orders missing from it and -\$166.50 for order 2075.

<RunSQL query={`SELECT 19589.75 - 19453.75 AS difference,
       ROUND(100 * (19589.75 - 19453.75) / 19589.75, 2) AS percent;`} />

Expected: 1 row, 2 columns. Run it, then use the three parts to show what the small difference hides, and say what is wrong with the method.

<Solution>

The query gives \$136.00, 0.69 percent (the till minus the processor). The parts, measured the other way round, add up to the same size with the opposite sign:

```sql
SELECT 447.00 - 416.50 - 166.50 AS net, 447.00 + 416.50 + 166.50 AS gross_errors;
```

The net, -136.00, is the same gap seen from the processor's side, and it is small only because errors of opposite sign cancel: the gross size of the errors is \$1,030.00, a wrong order and 70 rows that are wrong in count. A grand total is the weakest test: it agrees whenever the errors cancel. The method needs row counts on both sides, the unmatched orders and every difference named.

</Solution>

</Exercise>
