## The question

This is the fifth lesson of the dashboard project, after [*Build and publish your first dashboard*](/data-analyst/first-bi-dashboard/) (DA10). On Monday two people open two dashboards built from the same tables. Both tiles are called Revenue.

| tile | built by | Revenue reads |
|---|---|---:|
| the cafe's | you, in DA10 | \$22,582.75 |
| the accountant's | the accountant | \$22,671.75 |

Dana asks which one is right. Neither has a bug. By the end you can say why, write the one definition that settles it, and prove that both tiles read it.

## Warm-up

Try each one from memory, then open the answer. Forgot? Follow the link back to that part of the lesson: looking back is part of the review.

1. In [*Defining a metric before you compute it*](/core/defining-metrics/#the-big-idea) (C12), what are the four parts of a metric? Write them for "average order value in April, completed orders".

   <details>
   <summary>answer</summary>

   A numerator, a denominator, a unit and a window. Here: the dollars of completed orders in April, divided by the number of those orders, in dollars per order, for April 1 to 30.

   </details>

2. In [*Build and publish your first dashboard*](/data-analyst/first-bi-dashboard/#2-the-three-cards) (DA10), what did the Revenue card add up, and over which rows?

   <details>
   <summary>answer</summary>

   Quantity times price minus the discount, over the lines of completed orders, with order 2075 counted as 2 units.

   </details>

## Learn by doing

About 55 minutes, 4 ideas: two numbers with one name, the entry, the layer, the test. The SQL runs in the page. Run each block after the ones above it.

### 1. Two numbers with one name

**Idea.** A *KPI* (key performance indicator) is a number someone watches to make a decision. A name is not a definition: "revenue" can mean everything the tills rang up, or only the money the cafe kept. Both are plausible, and the accountant used the first.

**Try it.** The view `lines` holds every order line with the extra zero of order 2075 already set to 2 units. Compute both rules for each cafe: *gross sales* (every order, list price, no discounts) and *net sales* (completed orders only, list price minus the line discount).

<RunSQL query={`CREATE OR REPLACE VIEW lines AS
SELECT o.order_id, o.status, s.store_name AS store, CAST(o.ordered_at AS DATE) AS order_date,
       p.category, oi.order_item_id, oi.quantity AS quantity_recorded,
       CASE WHEN oi.order_item_id = 6952 THEN 2 ELSE oi.quantity END AS quantity,
       p.unit_price_usd AS unit_price, oi.discount_usd AS discount,
       (CASE WHEN oi.order_item_id = 6952 THEN 2 ELSE oi.quantity END) * p.unit_price_usd AS list_amount
FROM orders o
JOIN order_items oi ON oi.order_id = o.order_id
JOIN products p ON p.product_id = oi.product_id
JOIN stores s ON s.store_id = o.store_id;

SELECT store,
       ROUND(SUM(list_amount), 2) AS gross_sales,
       ROUND(SUM(list_amount - discount) FILTER (WHERE status = 'completed'), 2) AS net_sales
FROM lines
GROUP BY store
ORDER BY store;`} />

**Predict:** what makes up the difference between the two rules, and do they rank the cafes in the same order?

Expected: 3 rows, 3 columns.

*Why:* the totals are \$22,671.75 and \$22,582.75, \$89.00 apart: \$84.00 of discounts on 168 lines and the \$5.00 of the one canceled order, a Mocha at Campus. The order of the cafes holds under both rules, and on gross sales Campus leads Old Town by \$4.50.

### 2. Pick one, then write it down

**Idea.** Pick the definition from the decision it feeds. Dana decides where promotion money goes, and a discount or a canceled order is money she did not keep, so *revenue* means net sales; the other rule keeps its own name, gross sales. Then write the entry once. A *KPI entry* names the question, the rule, the grain, the owner and the caveats. A third choice hides in the data: order 2075.

**Try it.** Net sales for each cafe, with order 2075 as it was typed and as the entry will count it:

<RunSQL query={`SELECT store,
       ROUND(SUM(quantity_recorded * unit_price - discount), 2) AS as_recorded,
       ROUND(SUM(quantity * unit_price - discount), 2) AS corrected
FROM lines
WHERE status = 'completed'
GROUP BY store
ORDER BY store;`} />

**Predict:** which cafe sold the most, as recorded and corrected?

Expected: 3 rows, 3 columns.

*Why:* as recorded, Old Town is first with \$9,144.25; corrected, Campus is first with \$8,998.75, \$21.00 ahead of Old Town. The 18 extra sandwiches move \$166.50, nearly twice the \$89.00 between the two rules, so the entry must say how order 2075 is treated.

```text
KPI: Net sales (the Revenue card)
Question: how much money did the cafes keep from the orders they filled?
Rule: sum of quantity x unit price - line discount, over lines of completed orders.
Grain: one order line; shown by day, cafe and category.
Caveat: order 2075 (line 6952) was typed as 20 units and counts as 2.

```

The defense is three sentences: the decision it serves, the rule that follows from it, and what the other rule would have shown instead.

### 3. Define it once, in a layer

**Idea.** A <Term id="glossary-semantic-layer">metrics layer</Term> (also called a *semantic layer*) is the one place where the rule is code, and every dashboard asks it for the metric by name. In DuckDB the small version is a view, which the documentation says "defines a view of a query" and is "not physically materialized".

**Try it.** Save the rule as the view `net_sales`, then ask it for three cuts:

<RunSQL query={`CREATE OR REPLACE VIEW net_sales AS
SELECT order_id, store, order_date, category, quantity * unit_price - discount AS net_sales
FROM lines
WHERE status = 'completed';

SELECT 'store' AS cut, store AS name, ROUND(SUM(net_sales), 2) AS net_sales FROM net_sales GROUP BY store
UNION ALL
SELECT 'category', category, ROUND(SUM(net_sales), 2) FROM net_sales GROUP BY category
UNION ALL
SELECT 'all', 'all', ROUND(SUM(net_sales), 2) FROM net_sales
ORDER BY cut, name;`} />

**Predict:** what do the three store rows add up to, and the four category rows?

Expected: 8 rows, 3 columns.

*Why:* both add up to \$22,582.75, the row for all. Any cut of the layer carries the same rule, so a chart by store and a card cannot disagree about it.

At company scale this is a product category. As of November 23, 2026, Google's Looker documentation says LookML is "the language that is used in Looker to create semantic data models", and describes writing a SQL expression once and reusing it. The documentation of <Term id="glossary-dbt">dbt</Term> (a tool for organizing SQL models, taught in [*A dbt project, from source to mart*](/data-engineer/dbt-project-and-first-model/) (DE9)) says its Semantic Layer, powered by MetricFlow (the part that builds the SQL for each metric), helps you "define and manage the logic for your company's metrics". There a semantic model has entities (join keys), dimensions (ways to slice) and simple metrics, defined in YAML (a plain-text format for settings, written as indented lines). Neither is needed for this course: the idea is one definition, named, and read by every tool.

### 4. Prove two dashboards agree

**Idea.** Two dashboards agree when two routes to the number, each built from the entry and not from each other, match in every cell to the cent. Dashboard A reads the layer. The accountant's sheet adds up each order first, then adds the orders by cafe and month.

**Try it.** Compare the 15 cafe-months. The second row gives the sheet her old rule instead: all orders at list price.

<RunSQL query={`WITH a AS (
  SELECT store, strftime(order_date, '%Y-%m') AS month, ROUND(SUM(net_sales), 2) AS net_sales
  FROM net_sales
  GROUP BY store, month
),
order_totals AS (
  SELECT o.store_id, o.status, strftime(o.ordered_at, '%Y-%m') AS month,
         SUM((CASE WHEN oi.order_item_id = 6952 THEN 2 ELSE oi.quantity END) * p.unit_price_usd) AS rung_up,
         SUM((CASE WHEN oi.order_item_id = 6952 THEN 2 ELSE oi.quantity END) * p.unit_price_usd - oi.discount_usd) AS kept
  FROM orders o
  JOIN order_items oi ON oi.order_id = o.order_id
  JOIN products p ON p.product_id = oi.product_id
  GROUP BY o.order_id, o.store_id, o.status, month
),
b AS (
  SELECT s.store_name AS store, t.month,
         ROUND(SUM(t.kept) FILTER (WHERE t.status = 'completed'), 2) AS net_sheet,
         ROUND(SUM(t.rung_up), 2) AS gross_sheet
  FROM order_totals t
  JOIN stores s ON s.store_id = t.store_id
  GROUP BY s.store_name, t.month
)
SELECT 'net sales rule' AS sheet_rule, COUNT(*) AS cells,
       COUNT(*) FILTER (WHERE a.net_sales IS DISTINCT FROM b.net_sheet) AS cells_that_differ
FROM a FULL JOIN b USING (store, month)
UNION ALL
SELECT 'gross sales rule', COUNT(*),
       COUNT(*) FILTER (WHERE a.net_sales IS DISTINCT FROM b.gross_sheet)
FROM a FULL JOIN b USING (store, month);`} />

**Predict:** how many of the 15 cells differ under each rule?

Expected: 2 rows, 3 columns.

*Why:* none differ under the net sales rule, and all 15 differ under the gross rule, because every cafe-month holds a discounted line. A test that can fail tells you something when it passes; one that reads the same view twice does not. Write the result and its date under the entry.

- A name is not a definition: write the rule, the grain, the owner and the caveats.
- Pick the definition from the decision, and give the other rule its own name.
- Define the metric once, in a layer; every cut then carries the same rule.

**Discount rate, two ways.** Dana asks for a "discount rate" card. One reading is money: the discount dollars as a percent of gross sales on completed orders. The other is frequency: the percent of completed lines that carry a discount. The editor gives the first. Add the second, then say which one the card should show and why. Run unit 1 first. Expected: 1 row, 2 columns.

<RunSQL query={`SELECT ROUND(100 * SUM(discount) / SUM(quantity * unit_price), 2) AS pct_of_money
FROM lines
WHERE status = 'completed';`} />

<details>
<summary>Hint</summary>

Count the lines with a discount above 0 and divide by all lines of completed orders. `COUNT(*) FILTER (WHERE ...)` counts only the rows that pass the test.

</details>

<details>
<summary>Half-solution</summary>

```sql
SELECT ROUND(100 * SUM(discount) / SUM(quantity * unit_price), 2) AS pct_of_money,
       ROUND(100.0 * COUNT(*) FILTER (WHERE ...) / COUNT(*), 2) AS pct_of_lines
```

</details>

<Solution>

```sql
SELECT ROUND(100 * SUM(discount) / SUM(quantity * unit_price), 2) AS pct_of_money,
       ROUND(100.0 * COUNT(*) FILTER (WHERE discount > 0) / COUNT(*), 2) AS pct_of_lines
FROM lines
WHERE status = 'completed';
```

0.37 percent of the money and 5.11 percent of the lines. Both are true: a few lines carry a discount, and each is small. For Dana, who budgets promotions in dollars, the card shows the money reading and is named "Discount, percent of gross sales"; the entry says that the frequency reading exists and is called "Share of lines discounted".

</Solution>

</Exercise>

**An entry for active customers.** A customer is active if they ordered recently, but "recently" is the definition. Before you run anything, write as comments the entry's rule and the one thing it must state besides a window. Then count the customers with a completed order in the 30, 60 and 90 days that end on June 30, 2026, a customer being a row with a `customer_id`. Run unit 1 first. Expected: your entry, then 3 rows, 2 columns.

<RunSQL query={`-- Write your entry and your query here, then press Run.`} />

<details>
<summary>Hint</summary>

The window starts at `DATE '2026-06-30' - INTERVAL 29 DAY` for 30 days, and so on. Count `DISTINCT customer_id` from `orders` for each window, and join the three rows with `UNION ALL`.

</details>

<details>
<summary>Half-solution</summary>

Expected output in words: *"Three rows, from a window of 30 days to one of 90; the counts grow a little, and the last one is as large as it can get."*

```sql
SELECT 30 AS window_days, COUNT(DISTINCT customer_id) AS customers
FROM orders
WHERE status = 'completed' AND ordered_at >= DATE '2026-06-30' - INTERVAL 29 DAY
UNION ALL
...
```

</details>

<Solution>

```sql
SELECT 30 AS window_days, COUNT(DISTINCT customer_id) AS customers
FROM orders
WHERE status = 'completed' AND ordered_at >= DATE '2026-06-30' - INTERVAL 29 DAY
UNION ALL
SELECT 60, COUNT(DISTINCT customer_id)
FROM orders
WHERE status = 'completed' AND ordered_at >= DATE '2026-06-30' - INTERVAL 59 DAY
UNION ALL
SELECT 90, COUNT(DISTINCT customer_id)
FROM orders
WHERE status = 'completed' AND ordered_at >= DATE '2026-06-30' - INTERVAL 89 DAY
ORDER BY window_days;
```

134, 142 and 144 customers. The entry besides the window must state the *as-of date*: a count "in the last 30 days" changes every day it is run. A 90-day window holds all 144 customers who completed an order, so it separates no one from the rest, and the entry should choose 30 and say that the walk-in order, which has no `customer_id`, is not a customer.

</Solution>

</Exercise>

**Spot the flaw.** A colleague builds a second dashboard with a hand-typed lookup from store id to name (1 is Campus, 2 is Old Town, 3 is Harbor). She tests it against the layer on the grand total, and writes: "Both read \$22,582.75. The dashboards agree."

<RunSQL query={`WITH a AS (
  SELECT store, ROUND(SUM(net_sales), 2) AS net_sales FROM net_sales GROUP BY store
),
b AS (
  SELECT CASE o.store_id WHEN 1 THEN 'Campus' WHEN 2 THEN 'Old Town' ELSE 'Harbor' END AS store,
         ROUND(SUM((CASE WHEN oi.order_item_id = 6952 THEN 2 ELSE oi.quantity END) * p.unit_price_usd - oi.discount_usd), 2) AS net_sales
  FROM orders o
  JOIN order_items oi ON oi.order_id = o.order_id
  JOIN products p ON p.product_id = oi.product_id
  WHERE o.status = 'completed'
  GROUP BY o.store_id
)
SELECT (SELECT SUM(net_sales) FROM a) AS layer_total, (SELECT SUM(net_sales) FROM b) AS sheet_total;`} />

Run unit 3 first. Expected: 1 row, 2 columns. Run it, then compare the two sheets by cafe and say what is wrong with the test.

<Solution>

The totals are both 22,582.75. By cafe they are not:

```sql
SELECT a.store, a.net_sales AS layer, b.net_sales AS sheet
FROM a JOIN b USING (store);
```

(with the same two CTEs above the query) shows Campus at 8,998.75 in the layer and 8,977.75 in the sheet, and Old Town at 8,977.75 against 8,998.75: the two names are swapped, because the real ids are 1 for Old Town and 2 for Campus. A grand total cannot see a label mistake, since the same money is added in any order. Test at the grain the dashboard shows: the cafe, the month, or the category.

</Solution>
