In *GROUP BY and HAVING* (S8) each group got one number. The owner's reports usually want several numbers per group, side by side, like the columns of a PivotTable. You build them by putting a `CASE` inside `SUM` and `COUNT`. Every query on this page runs in the page itself, on **cafe-sales**, the invented three-cafe chain we use from Excel to Python.

## The question

The owner of the cafes asks:

> For each cafe, how many orders were paid by card, by mobile and by cash? And what share of each cafe's orders is mobile?

In S8 you got the counts as a long list, one row per store and payment method. The first three of those nine rows:

| store_id | payment_method | orders |
|---:|---|---:|
| 1 | card | 421 |
| 1 | cash | 91 |
| 1 | mobile | 217 |

The owner wants one row per store, with a column for each method, like the PivotTable of *Summarize with a PivotTable*
(E15) with `payment_method` in Columns.

## The big idea

**Conditional aggregation** puts a `CASE` (S6) inside an aggregate (S7): each row says what it adds to a column, so one
pass over the rows can fill several columns side by side.

{/* CONCEPT: concept-conditional-agg */}

## Learn by doing

Five small steps. Press Run on each query as you meet it.

### 1. One conditional column

Inside a group, the `CASE` is worked out on one row at a time, and the aggregate then adds up what the rows gave it.
`SUM(CASE WHEN test THEN 1 ELSE 0 END)` gives 1 to the rows that pass and 0 to the others, and adds them up. To add up an
amount instead of counting, put the amount where the 1 is: `SUM(CASE WHEN test THEN quantity ELSE 0 END)`.

**Try it**. Grain: *one row per store*.

<RunSQL query={`SELECT store_id,
       COUNT(*) AS orders,
       SUM(CASE WHEN payment_method = 'card' THEN 1 ELSE 0 END) AS card
FROM orders
GROUP BY store_id
ORDER BY store_id;`} />

Expected: 3 rows, 3 columns: store 1 has 729 orders and 421 card, store 2 has 716 and 400, store 3 has 355 and 180.
*Excel:* `COUNTIFS` on the payment column; with an amount instead of the 1 it is `SUMIFS` (both E7).

*Why:* for each order the `CASE` gives 1 if it was paid by card and 0 if not, and `SUM` adds the 1s inside each store's
group. `COUNT(*)` has no `CASE`: it counts all of the store's orders, so it sits beside the card count as the whole.

### 2. The same column, the other way

`COUNT(CASE WHEN test THEN 1 END)` has no `ELSE`, so the rows that fail the test give `NULL` (S6), and `COUNT` skips
`NULL` (S7). It gives the same number as the `SUM` form. Use it for the other two methods.

**Try it**. Grain: *one row per store*.

<RunSQL query={`SELECT store_id,
       COUNT(*) AS orders,
       SUM(CASE WHEN payment_method = 'card' THEN 1 ELSE 0 END) AS card,
       COUNT(CASE WHEN payment_method = 'mobile' THEN 1 END) AS mobile,
       COUNT(CASE WHEN payment_method = 'cash' THEN 1 END) AS cash
FROM orders
GROUP BY store_id
ORDER BY store_id;`} />

Expected: 3 rows, 5 columns. Store 1 reads 729, 421, 217, 91. *Excel:* the PivotTable with `payment_method` in Columns.

*Why:* three rows now, instead of nine. Pick one form and keep it. (DuckDB's `FILTER` clause, `SUM(x) FILTER (WHERE
test)`, is a shorter way to write the same columns; this lesson keeps `CASE`, as in S6.)

This is the result, with the expression that fills each column. The last row is the whole table, which you query in unit 5.

<details>
<summary>Explain it in your own words: why does the mobile column need no <code>ELSE</code>, and the card column does?</summary>

Picture a store with no card orders at all. The `COUNT` form still returns 0, because it counts nothing. A `SUM` over
rows that all gave `NULL` would return `NULL`, an empty cell where a 0 belongs, so the `ELSE 0` keeps every row a number.

</details>

### 3. A percentage, with its denominator named

A percentage is a part divided by a whole. The whole is the **denominator**, the number you divide by. Both are
aggregates over the same group, and which rows are in the whole changes the answer, so name them before you write the
query. Here the part is the store's mobile orders, and the whole is *all orders of that store, canceled included*.

**Try it**. Grain: *one row per store*.

<RunSQL query={`SELECT store_id,
       COUNT(*) AS orders,
       COUNT(CASE WHEN payment_method = 'mobile' THEN 1 END) AS mobile,
       ROUND(100.0 * COUNT(CASE WHEN payment_method = 'mobile' THEN 1 END) / COUNT(*), 1) AS mobile_pct
FROM orders
GROUP BY store_id
ORDER BY store_id;`} />

Expected: 3 rows, 4 columns; `mobile_pct` reads 29.8, 29.2 and 33.8. *Excel:* the share of the row total (E16).

*Why:* part over whole, as E16 asked. `100.0 *` puts the result on a scale of 0 to 100, and `ROUND(..., 1)` keeps one
decimal.

### 4. Divide safely with `NULLIF`

Sometimes a group has nothing to take a share of. The first quarter is January to March, and Harbor opened on April 1,
so it has no orders in it and its denominator is 0.

**Try it**. Run this and read Harbor's last column.

<RunSQL query={`SELECT store_id,
       COUNT(CASE WHEN ordered_at < '2026-04-01' THEN 1 END) AS q1_orders,
       COUNT(CASE WHEN ordered_at < '2026-04-01' AND payment_method = 'mobile' THEN 1 END) AS q1_mobile,
       ROUND(100.0 * COUNT(CASE WHEN ordered_at < '2026-04-01' AND payment_method = 'mobile' THEN 1 END)
             / COUNT(CASE WHEN ordered_at < '2026-04-01' THEN 1 END), 1) AS q1_mobile_pct
FROM orders
GROUP BY store_id
ORDER BY store_id;`} />

Expected: 3 rows, 4 columns. Harbor's last column shows `nan`, short for "not a number": it is 0 divided by 0. (Some tools print it as `-nan`.)
*Excel:* the `#DIV/0!` of *Formula errors and auditing* (E12), where `=IF(D5=0,"no lines",C5/D5)` guards the same
division.

Now wrap the denominator in `NULLIF(..., 0)`:

<RunSQL query={`SELECT store_id,
       COUNT(CASE WHEN ordered_at < '2026-04-01' THEN 1 END) AS q1_orders,
       COUNT(CASE WHEN ordered_at < '2026-04-01' AND payment_method = 'mobile' THEN 1 END) AS q1_mobile,
       ROUND(100.0 * COUNT(CASE WHEN ordered_at < '2026-04-01' AND payment_method = 'mobile' THEN 1 END)
             / NULLIF(COUNT(CASE WHEN ordered_at < '2026-04-01' THEN 1 END), 0), 1) AS q1_mobile_pct
FROM orders
GROUP BY store_id
ORDER BY store_id;`} />

Expected: 3 rows, 4 columns. Old Town reads 364, 104 and 28.6, Campus reads 354, 99 and 28.0, and Harbor reads 0, 0 and
`NULL`.

*Why:* `NULLIF(x, 0)` returns `NULL` when `x` is 0 and `x` otherwise, and dividing by `NULL` gives `NULL`. An empty cell
is the honest answer when there was nothing to take a share of.

### 5. Check the totals

**Try it**:

<RunSQL query={`SELECT COUNT(*) AS orders,
       SUM(CASE WHEN payment_method = 'card' THEN 1 ELSE 0 END) AS card,
       COUNT(CASE WHEN payment_method = 'mobile' THEN 1 END) AS mobile,
       COUNT(CASE WHEN payment_method = 'cash' THEN 1 END) AS cash
FROM orders;`} />

Expected: 1 row, 4 columns: 1800, 1001, 546 and 253. *Why:* this is the grand-total row of the pivot, and it matches the
card, mobile and cash counts of *A cleaning workflow you can defend* (E13). The columns of unit 2 add up to it (421 +
400 + 180 = 1,001), and so do the rows (421 + 217 + 91 = 729). The quarter counts of unit 4 add up to 364 + 354 + 0 =
718, the January to March total of *Dates as numbers* (E11): 242 + 218 + 258.

<Aside type="tip" title="Remember">

- `SUM(CASE WHEN test THEN 1 ELSE 0 END)` and `COUNT(CASE WHEN test THEN 1 END)` give the same count.
- One `CASE` column per category, with `GROUP BY` for the rows, is a pivot in one query.
- A percentage is part over whole: name the rows in the whole first.
- Wrap a denominator that can be 0 in `NULLIF(..., 0)`.

**Common trap: "a `CASE` inside an aggregate filters rows, like `WHERE`."** Every row still goes into the aggregate;
the `CASE` only decides what that row adds. That is why `COUNT(*)` can sit beside a card count in one result row: store
1 shows 729 orders next to its 421 card orders. A `WHERE` on the payment method would change every column.

</Aside>

Now finish it: add the second column for orders on or after April 1.

<details>
<summary>Hint</summary>

The second column is the first one with the other test. Orders on or after April 1 have `ordered_at >= '2026-04-01'`.

</details>

<details>
<summary>Half-solution</summary>

```sql
SELECT store_id,
       COUNT(CASE WHEN ordered_at < '2026-04-01' THEN 1 END) AS q1_orders,
       COUNT(CASE WHEN ordered_at ... '2026-04-01' THEN 1 END) AS q2_orders
FROM ...
GROUP BY ...
ORDER BY ...;
```

</details>

<Solution>

```sql
SELECT store_id,
       COUNT(CASE WHEN ordered_at < '2026-04-01' THEN 1 END) AS q1_orders,
       COUNT(CASE WHEN ordered_at >= '2026-04-01' THEN 1 END) AS q2_orders
FROM orders
GROUP BY store_id
ORDER BY store_id;
```

The result is store 1 with 364 and 365, store 2 with 354 and 362, and store 3 with 0 and 355. Together they add up to
718 + 1,082 = 1,800 orders. Harbor's 0 is a real zero: a `COUNT` of nothing is 0, not `NULL`.

**Spot the flaw.** A colleague builds the card and mobile columns with `COUNT` and an `ELSE 0`. The query runs without
an error, and the colleague says the table looks right:

<RunSQL query={`SELECT store_id,
       COUNT(CASE WHEN payment_method = 'card' THEN 1 ELSE 0 END) AS card,
       COUNT(CASE WHEN payment_method = 'mobile' THEN 1 ELSE 0 END) AS mobile
FROM orders
GROUP BY store_id
ORDER BY store_id;`} />

Expected: 3 rows, 3 columns. Run it and compare each column with the store's order count. What do you notice, and why?
Then fix it.

<Solution>

Both columns equal the store's whole order count: 729, 716 and 355 in each. `ELSE 0` gives the failing rows a 0, and a
0 is a value, not `NULL`, so `COUNT` counts every row. Either drop the `ELSE` or switch to `SUM`:

```sql
SELECT store_id,
       SUM(CASE WHEN payment_method = 'card' THEN 1 ELSE 0 END) AS card,
       COUNT(CASE WHEN payment_method = 'mobile' THEN 1 END) AS mobile
FROM orders
GROUP BY store_id
ORDER BY store_id;
```

Expected: 3 rows, 3 columns: card 421, 400 and 180, mobile 217, 209 and 120. A check that would have caught it: the card and
mobile columns cannot both equal the number of orders.

</Solution>
