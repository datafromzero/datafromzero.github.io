**Conditional aggregation** puts a `CASE` inside an aggregate. For each row, the `CASE` decides whether the row counts
toward this column; the aggregate then adds up the rows inside each group. There are two forms for a count:

- `SUM(CASE WHEN test THEN 1 ELSE 0 END)` gives 1 to the rows that pass and 0 to the others, and adds them up.
- `COUNT(CASE WHEN test THEN 1 END)` has no `ELSE`, so the other rows become `NULL` (S6), and `COUNT` skips `NULL` (S7).

Both give the same number. To add up an amount instead of counting, put the amount where the 1 is, for example
`SUM(CASE WHEN test THEN quantity ELSE 0 END)`.

| SQL | In Excel |
|---|---|
| `COUNT(CASE WHEN payment_method = 'card' THEN 1 END)` | `COUNTIFS` with the payment condition (E7) |
| `SUM(CASE WHEN test THEN quantity ELSE 0 END)` | `SUMIFS` (E7) |
| `GROUP BY store_id` plus one `CASE` column per method | PivotTable: `store` in Rows, `payment_method` in Columns (E15) |
| `100.0 * part / COUNT(*)` | the share of the row total in a pivot (E16) |

DuckDB also has a shorter way to write the same thing, the `FILTER` clause. This lesson keeps `CASE`, the form you
already know from S6.

## Worked example

Question: **for each cafe, how many orders by card, mobile and cash, and what share of the orders is mobile?** Run the
notebook's setup cell, then one cell per step. Each step starts with the grain and shows the shape of the result to
expect.

1. **One conditional column.** Grain: *one row per store*.

   ```sql
   SELECT store_id,
          COUNT(*) AS orders,
          SUM(CASE WHEN payment_method = 'card' THEN 1 ELSE 0 END) AS card
   FROM orders
   GROUP BY store_id
   ORDER BY store_id;
   ```

   Expected: 3 rows, 3 columns: store 1 has 729 orders and 421 card, store 2 has 716 and 400, store 3 has 355 and 180.
   *Excel:* `COUNTIFS` on the payment column. *Why:* for each order the `CASE` gives 1 if it was paid by card and 0 if not,
   and `SUM` adds the 1s inside each store's group. `COUNT(*)` beside it is the whole of the store's orders.

2. **The other two columns, with the other form.**

   ```sql
   SELECT store_id,
          COUNT(*) AS orders,
          SUM(CASE WHEN payment_method = 'card' THEN 1 ELSE 0 END) AS card,
          COUNT(CASE WHEN payment_method = 'mobile' THEN 1 END) AS mobile,
          COUNT(CASE WHEN payment_method = 'cash' THEN 1 END) AS cash
   FROM orders
   GROUP BY store_id
   ORDER BY store_id;
   ```

   Expected: 3 rows, 5 columns. Store 1 reads 729, 421, 217, 91. *Excel:* the PivotTable with `payment_method` in
   Columns. *Why:* three rows now, instead of nine. The mobile and cash columns have no `ELSE`, so rows that fail the
   test are `NULL` and `COUNT` skips them. Pick one form and keep it.

3. **A percentage, with its denominator named.** The part is the store's mobile orders. The whole is *all orders of
   that store, canceled included*.

   ```sql
   SELECT store_id,
          COUNT(*) AS orders,
          COUNT(CASE WHEN payment_method = 'mobile' THEN 1 END) AS mobile,
          ROUND(100.0 * COUNT(CASE WHEN payment_method = 'mobile' THEN 1 END) / COUNT(*), 1) AS mobile_pct
   FROM orders
   GROUP BY store_id
   ORDER BY store_id;
   ```

   Expected: 3 rows, 4 columns; `mobile_pct` reads 29.8, 29.2 and 33.8. *Excel:* the share of the row total (E16).
   *Why:* a percentage is part divided by whole, and a different whole gives a different number: say which one in a
   sentence before you write the query, as E16 asked. `100.0 *` puts the result on a scale of 0 to 100, and
   `ROUND(..., 1)` keeps one decimal.

4. **Divide safely with `NULLIF`.** The first quarter is January to March. Harbor opened on April 1, so it has no
   orders in it, and its denominator is 0. Run this and read Harbor's last column:

   ```sql
   SELECT store_id,
          COUNT(CASE WHEN ordered_at < '2026-04-01' THEN 1 END) AS q1_orders,
          COUNT(CASE WHEN ordered_at < '2026-04-01' AND payment_method = 'mobile' THEN 1 END) AS q1_mobile,
          ROUND(100.0 * COUNT(CASE WHEN ordered_at < '2026-04-01' AND payment_method = 'mobile' THEN 1 END)
                / COUNT(CASE WHEN ordered_at < '2026-04-01' THEN 1 END), 1) AS q1_mobile_pct
   FROM orders
   GROUP BY store_id
   ORDER BY store_id;
   ```

   Expected: 3 rows, 4 columns. Harbor's last column is not a number (DuckDB 2.0 prints `-nan`), the result of 0 divided by
   0. *Excel:* the `#DIV/0!` of *Formula errors and auditing* (E12), where `=IF(D5=0,"no lines",C5/D5)` guards the same division. Now wrap the denominator in `NULLIF(..., 0)`:

   ```sql
   SELECT store_id,
          COUNT(CASE WHEN ordered_at < '2026-04-01' THEN 1 END) AS q1_orders,
          COUNT(CASE WHEN ordered_at < '2026-04-01' AND payment_method = 'mobile' THEN 1 END) AS q1_mobile,
          ROUND(100.0 * COUNT(CASE WHEN ordered_at < '2026-04-01' AND payment_method = 'mobile' THEN 1 END)
                / NULLIF(COUNT(CASE WHEN ordered_at < '2026-04-01' THEN 1 END), 0), 1) AS q1_mobile_pct
   FROM orders
   GROUP BY store_id
   ORDER BY store_id;
   ```

   Expected: 3 rows, 4 columns. Old Town reads 364, 104 and 28.6, Campus reads 354, 99 and 28.0, and Harbor reads 0, 0
   and `NULL`. *Why:* `NULLIF(x, 0)` returns `NULL` when `x` is 0 and `x` otherwise, and dividing by `NULL` gives `NULL`.
   An empty cell is the honest answer when there was nothing to take a share of.

5. **Verify.**

   ```sql
   SELECT COUNT(*) AS orders,
          SUM(CASE WHEN payment_method = 'card' THEN 1 ELSE 0 END) AS card,
          COUNT(CASE WHEN payment_method = 'mobile' THEN 1 END) AS mobile,
          COUNT(CASE WHEN payment_method = 'cash' THEN 1 END) AS cash
   FROM orders;
   ```

   Expected: 1 row, 4 columns: 1800, 1001, 546 and 253. *Why:* this is the grand-total row of the pivot, and it matches
   the card, mobile and cash counts of *A cleaning workflow you can defend* (E13). The columns of step 2 add up to it
   (421 + 400 + 180 = 1,001), and so do the rows (421 + 217 + 91 = 729). The quarter counts of step 4 add up to
   364 + 354 + 0 = 718, the January to March total of *Dates as numbers* (E11): 242 + 218 + 258.

<details>
<summary>Explain it in your own words: why does the mobile column need no <code>ELSE</code>, and the card column does?</summary>

The mobile column uses `COUNT`, which skips `NULL`, so rows that fail the test can be `NULL`. The card column uses `SUM`,
which would add up `NULL`s as nothing but return `NULL` for a store with no card orders, so the `ELSE 0` keeps every
row a number.

</details>

<details>

<Exercise id="sql-conditional-aggregation-3">

**Spot the flaw.** A colleague builds the card and mobile columns with `COUNT` and an `ELSE 0`. The query runs without
an error, and the colleague says the table looks right:

```sql
SELECT store_id,
       COUNT(CASE WHEN payment_method = 'card' THEN 1 ELSE 0 END) AS card,
       COUNT(CASE WHEN payment_method = 'mobile' THEN 1 ELSE 0 END) AS mobile
FROM orders
GROUP BY store_id
ORDER BY store_id;
```

Expected: 3 rows, 3 columns. Run it and compare each column with the store's order count. What do you notice, and why?
Then fix it.

<Solution>

Both columns equal the store's whole order count: 729, 716 and 355 in each. `ELSE 0` gives the failing rows a 0, and a
0 is a value, not `NULL`, so `COUNT` counts every row. Either drop the `ELSE` or switch to `SUM`:

```sql
SELECT store_id,
       SUM(CASE WHEN payment_method = 'card' THEN 1 ELSE 0 END) AS card,
       COUNT(CASE WHEN payment_method = 'mobile' THEN 1 END) AS mobile
FROM orders
GROUP BY store_id
ORDER BY store_id;
```

Expected: 3 rows, 3 columns: card 421, 400 and 180, mobile 217, 209 and 120. A check that would have caught it: the card and
mobile columns cannot both equal the number of orders.

</Solution>
