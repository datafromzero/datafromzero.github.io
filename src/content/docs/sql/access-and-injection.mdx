## The question

A partner who runs the Harbor cafe asks for a feed of its orders, and the cafe also has a small web form where staff look up a store by name. Two worries:

> Can the partner see only Harbor, and not who our customers are? And what if someone types something strange into the lookup form?

The `stores` table behind the form is small:

| store_id | store_name | city | opened_on |
|---:|---|---|---|
| 1 | Old Town | Oakland | 2023-05-12 |
| 2 | Campus | Berkeley | 2024-09-03 |
| 3 | Harbor | Alameda | 2026-04-01 |

## The big idea

Two habits keep data safe: give each person only the access the job needs, and never let typed text become part of the query's own wording.

## Learn by doing

Four small steps. Press Run on the blocks that run; read the others.

### 1. Show only some columns and rows

**Idea.** A view can leave out columns and, with a `WHERE`, rows. The partner reads the view and never the table. Leaving out `customer_id` matters: a customer number is a pseudonym, a stand-in for a name, and *Data types, units and how data was collected* (C1) showed that a pseudonymous id still counts as personal data, because anyone who holds the list that links ids to people can undo it.

**Predict:** the partner's view lists five columns of `orders` for store 3. How many orders will it show, and from how many different stores?

**Try it:**

<RunSQL query={`CREATE OR REPLACE VIEW harbor_orders AS
SELECT order_id, store_id, ordered_at, status, payment_method
FROM orders
WHERE store_id = 3;
SELECT COUNT(*) AS orders, COUNT(DISTINCT store_id) AS stores FROM harbor_orders;`} />

Expected: 1 row, 2 columns. *Why:* the `WHERE` is inside the view, so every reader gets Harbor's rows and nothing else.

**Predict:** the partner asks the view for `customer_id`. What happens?

<RunSQL query={`SELECT customer_id FROM harbor_orders;`} />

Expected: one outcome, either rows or an error message. *Why:* it is an error saying `customer_id` is not found, because the view never listed it. A view is a convenient shape; whether it is a lock depends on the database. The next unit shows one where it is.

### 2. Roles, grants and least privilege

**Idea.** Some databases keep accounts. In PostgreSQL a **role** is an account or a group of accounts. A **privilege** is permission to do one thing to one object, such as `SELECT` on a view. `GRANT` gives a privilege and `REVOKE` takes it back. **Least privilege** means starting from no access and granting only what the job needs. The PostgreSQL documentation: "For most kinds of objects, the initial state is that only the owner (or a superuser) can do anything with the object."

DuckDB keeps no accounts: its security page says it "executes SQL with the full privileges of the user running it". The editor shows it:

<RunSQL query={`GRANT SELECT ON harbor_orders TO harbor_partner;`} />

Expected: an error saying there is a syntax error at or near "GRANT". SQLite has none either: its documentation says the commands would be meaningless for an embedded engine that only uses the operating system's file permissions.

**Read only.** PostgreSQL 16, with the `orders` table of cafe-sales in a schema called `cafe`. The first lines make the view of unit 1 and point the session at the schema:

```sql
SET search_path TO cafe;
CREATE VIEW harbor_orders AS
SELECT order_id, store_id, ordered_at, status, payment_method
FROM orders WHERE store_id = 3;

CREATE ROLE harbor_partner LOGIN;
GRANT USAGE ON SCHEMA cafe TO harbor_partner;
GRANT SELECT ON harbor_orders TO harbor_partner;

SET ROLE harbor_partner;
SELECT COUNT(*) FROM harbor_orders;
SELECT COUNT(*) FROM orders;
SELECT customer_id FROM harbor_orders;
DELETE FROM harbor_orders;
```

**Predict:** which of the four statements will the partner's role be allowed to run?

<details>
<summary>Reveal the result</summary>

Run on PostgreSQL 16, in the order written:

```text
SELECT COUNT(*) FROM harbor_orders;       355
SELECT COUNT(*) FROM orders;              ERROR:  permission denied for table orders
SELECT customer_id FROM harbor_orders;    ERROR:  column "customer_id" does not exist
DELETE FROM harbor_orders;                ERROR:  permission denied for view harbor_orders
```

After `REVOKE SELECT ON harbor_orders FROM harbor_partner;`, even the first statement fails with `permission denied for view harbor_orders`.

</details>

*Why:* the role holds one privilege, `SELECT` on the view. It cannot read the table, even though the view reads it, and it cannot change anything. The OWASP cheat sheet gives the same advice for applications: grant the account only `SELECT` on a view that omits the sensitive fields, and note that "PostgreSQL normally checks underlying table access using the view owner's privileges".

### 3. How a query built from strings breaks

**Idea.** **SQL injection** happens when text that came from outside becomes part of the SQL text itself. The OWASP definition: "A SQL injection attack occurs when untrusted data (usually strings) becomes part of a query's SQL syntax, modifying the logic of the SQL request." The risky habit is gluing a typed value into a query with `||` or `+`.

To see it safely, the editor plays both parts. `build_query` plays the application, gluing a typed store name into a query. DuckDB's `query()` then runs the text it is given, as a badly written application would; its documentation warns that it "allows invoking arbitrary queries". It reads only the `stores` table here.

**Predict:** staff type `Campus`; then someone types `x' OR '1'='1`. What will the two glued query texts look like?

**Try it:**

<RunSQL query={`CREATE OR REPLACE MACRO build_query(name) AS
  'SELECT store_id, store_name FROM stores WHERE store_name = ''' || name || '''';
SELECT build_query('Campus') AS typed_campus,
       build_query('x'' OR ''1''=''1') AS typed_trick;`} />

Expected: 1 row, 2 columns. *Why:* in SQL a doubled quote inside a string stands for one quote, so the second argument is the text `x' OR '1'='1`. Glued in, the typed quote closes the string early and the rest becomes part of the `WHERE`.

**Predict:** the application now runs each text. How many rows does the second one return?

**Try it:**

<RunSQL query={`SELECT * FROM query(build_query('Campus'));`} />

<RunSQL query={`SELECT * FROM query(build_query('x'' OR ''1''=''1'));`} />

Expected: each 2 columns (`store_id`, `store_name`). *Why:* the first finds Campus; the second returns every store, because `'1'='1'` is true on every row and the `OR` turned the lookup into "everything". Here the damage is a list of public store names. With a real account that can read customer tables or change data, the same trick reads or changes those, as OWASP warns: depending on the privileges, an attack can read data, modify it, and even run administration commands. The two lessons meet here: least privilege limits the damage.

### 4. The fix: send the value separately

**Idea.** A **parameterized query** keeps the query's wording and the value apart: the query has a placeholder (`$1` or `?`), and the value travels on its own. The OWASP advice: "Define the SQL structure separately from its data values and bind those values through the database API." DuckDB's documentation: prepared statements are "useful for preventing SQL injections".

**Predict:** the same two typed texts, now sent as values. How many rows will each return?

**Try it:**

<RunSQL query={`PREPARE find_store AS
  SELECT store_id, store_name FROM stores WHERE store_name = $1;
EXECUTE find_store('Campus');`} />

<RunSQL query={`EXECUTE find_store('x'' OR ''1''=''1');`} />

Expected: each 2 columns. *Why:* the first gives Campus. The second looks for a store literally named `x' OR '1'='1`, and there is none, so no rows: the database can only treat the typed text as a value, and the quote is just a character. Run the second block after the first, because `find_store` stays prepared until you leave the page.

**Read only.** In an application the same idea is a placeholder and a separate value. Python with DuckDB, and with its built-in `sqlite3`:

```python
con.execute("SELECT store_id, store_name FROM stores WHERE store_name = ?", [name])
cur.execute("SELECT store_id, store_name FROM stores WHERE store_name = ?", (name,))
```

With `name = "x' OR '1'='1"` both returned no rows, and the glued version of the same lookup returned all three stores. The Python documentation advises always using placeholders instead of string formatting to bind Python values to SQL statements, to avoid SQL injection attacks.

A placeholder stands for a value only, never a table name, a column name or `ASC`. OWASP's answer for those is to map the user's choice to a short list of fixed words that your code owns and reject anything else, and to keep binding every value even after you validate it.

<Aside type="tip" title="Remember">

- Share through a view that lists only the columns and rows the reader needs, and remember it is a lock only where the database grants on the view instead of the table.
- A role starts with nothing: `GRANT` what the job needs, `REVOKE` what it no longer does.
- Never glue typed text into a query. Send values as parameters.
- A placeholder is for values. For table or column names, choose from a fixed list.

**Common trap: "I removed the name, so the data is safe to share."** A customer number or a city and a signup day can still point to a person. Share the fewest columns, and keep the list that links ids to people away from the people who do not need it.

</Aside>

## Check yourself

Without looking back: what does least privilege mean, and what is the one thing a placeholder cannot stand for?

<details>
<summary>Answer</summary>

Start with no access and grant only what the job needs. A placeholder stands for a value, not a table name, a column name or a keyword such as `ASC`.

</details>

<Exercise id="sql-access-and-injection-3">

**Spot the flaw.** Staff want to choose how the store list is sorted, and a developer tries to pass the column as a parameter.

<RunSQL query={`PREPARE sorted AS SELECT store_name, opened_on FROM stores ORDER BY $1;`} />

Expected from that query: an error saying the parameter is not supported in the `ORDER BY` clause. The developer's next idea is to glue the typed column name into the query text instead. Why is that the wrong way out, and what is the right one?

<Solution>

A placeholder stands for a value, never for a column name or a keyword, which is why the database refuses it here. Gluing the typed name into the text would reopen the hole of unit 3: the typed text becomes part of the query. OWASP's answer for structure is an allow-list: map the user's choice to a few fixed words that your own query holds, and ignore anything else.

```sql
PREPARE sorted_stores AS
  SELECT store_name, opened_on FROM stores
  ORDER BY CASE WHEN $1 = 'opened' THEN opened_on END DESC,
           CASE WHEN $1 = 'name' THEN store_name END;
EXECUTE sorted_stores('opened');
EXECUTE sorted_stores('x; DROP TABLE stores');
```

The first run lists Harbor, Campus, Old Town (newest first). The second text matches no choice, so the rows come back unsorted and nothing else runs.

</Solution>

</Exercise>
