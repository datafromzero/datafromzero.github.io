A **join chain** writes one `JOIN` after another. Each one pairs the rows so far with the next table, and each `ON` may
name any table already in the chain. After every join, ask two questions: *is the key unique in the table I just added?*
and *what is one row now?* If the key is unique there, the row count and the grain stay put. If it repeats, rows are
added (S21).

A **self-join** joins a table to itself. Write the table twice with two different aliases, one for each role: here `c`
is the customer and `r` is the customer who referred them. The `ON` links a foreign key of one copy to the primary key
of the other: `c.referred_by = r.customer_id`. Without two aliases DuckDB cannot tell the copies apart and stops with a
`Binder Error`. A customer with an empty `referred_by` pairs with nobody, because an empty value never equals anything.

## Worked example

Question: **can SQL rebuild E7's Campus coffee figure, and who referred customer 144?** Run the notebook's setup cell,
then one cell per step. Each step gives the shape of the result to expect.

1. **Predict the rows of the chain.** Before you run it: start from `order_items` and add `orders`, `products` and
   `stores`, each on a key that is unique on the added side. How many rows will you get?

   ```sql
   SELECT COUNT(*) AS joined_rows
   FROM order_items AS oi
   INNER JOIN orders AS o ON oi.order_id = o.order_id
   INNER JOIN products AS p ON oi.product_id = p.product_id
   INNER JOIN stores AS s ON o.store_id = s.store_id;
   ```

   Expected: 1 row, 1 column. *Why:* **3287**, the lines of `order_items`. `order_id` is unique in `orders`,
   `product_id` in `products` and `store_id` in `stores`, so no join adds or drops a line. One row is still one line,
   now with its store, status, category and price. The `stores` join uses `o.store_id`: an `ON` may name any table in
   the chain.

2. **Rebuild E7.** Campus, coffee, completed orders, March.

   ```sql
   SELECT COUNT(*) AS lines,
          SUM(oi.quantity * p.unit_price_usd - oi.discount_usd) AS sales_usd
   FROM order_items AS oi
   INNER JOIN orders AS o ON oi.order_id = o.order_id
   INNER JOIN products AS p ON oi.product_id = p.product_id
   INNER JOIN stores AS s ON o.store_id = s.store_id
   WHERE s.store_name = 'Campus'
     AND p.category = 'coffee'
     AND o.status = 'completed'
     AND o.ordered_at >= DATE '2026-03-01'
     AND o.ordered_at < DATE '2026-04-01';
   ```

   Expected: 1 row, 2 columns: `112 | 706.25`. *Excel:* E7's `COUNTIFS` and `SUMIFS` with the same four conditions.
   *Why:* the rows are completed orders only. Canceled order 1461 is a Campus order from March 1 with a 5.00 coffee
   line: leave out the status condition and you get 113 lines and 711.25. The extra-zero line of order 2075 is an Old
   Town order from May, so it is not in this slice.

3. **Check one customer by hand.** Customer 144 has few orders. Start the chain at `customers` this time:

   ```sql
   SELECT o.order_id, p.product_name, oi.quantity,
          oi.quantity * p.unit_price_usd - oi.discount_usd AS line_amount_usd
   FROM customers AS c
   INNER JOIN orders AS o ON o.customer_id = c.customer_id
   INNER JOIN order_items AS oi ON oi.order_id = o.order_id
   INNER JOIN products AS p ON oi.product_id = p.product_id
   WHERE c.customer_id = 144
   ORDER BY oi.order_item_id;
   ```

   Expected: 4 rows, 4 columns. Add the four amounts by hand before you go on. *Why:* the grain is a line again: the
   first join made it one row per order, the second made it one row per line. Now total the same chain in SQL:

   ```sql
   SELECT SUM(oi.quantity * p.unit_price_usd - oi.discount_usd) AS spend_usd
   FROM customers AS c
   INNER JOIN orders AS o ON o.customer_id = c.customer_id
   INNER JOIN order_items AS oi ON oi.order_id = o.order_id
   INNER JOIN products AS p ON oi.product_id = p.product_id
   WHERE c.customer_id = 144;
   ```

   Expected: 1 row, 1 column: `17.25`. By hand: 4.50 + 4.25 + 5.00 + 3.50 = 17.25. Two orders, both completed.

4. **Join the table to itself.** Before you run it: 150 customers. How many referred customers pair with a referrer?

   ```sql
   SELECT COUNT(*) AS pairs
   FROM customers AS c
   INNER JOIN customers AS r ON c.referred_by = r.customer_id;
   ```

   Expected: 1 row, 1 column. *Why:* **30**. `c` is the customer and `r` the same table in the role of referrer. The 120
   customers whose `referred_by` is empty pair with nobody, so the inner join leaves them out.

5. **Look at the pairs.**

   ```sql
   SELECT c.customer_id AS customer,
          c.loyalty_tier AS customer_tier,
          r.customer_id AS referrer,
          r.loyalty_tier AS referrer_tier
   FROM customers AS c
   INNER JOIN customers AS r ON c.referred_by = r.customer_id
   WHERE c.customer_id IN (6, 30, 34, 144)
   ORDER BY c.customer_id;
   ```

   Expected: 4 rows, 4 columns. *Why:* customer 144 was referred by customer 86, as in the table of the question.
   Customer 24 is the referrer of both 30 and 34: one to many again, now inside a single table. The second picture shows
   the same rows. That answers the owner.

6. **Verify.** The chain returned E7's 112 lines and 706.25, and customer 144's 17.25 matches the hand total. The pairs
   should equal the customers with a filled `referred_by`:

   ```sql
   SELECT COUNT(referred_by) AS referred_customers FROM customers;
   ```

   Expected: 1 row, 1 column: `30`, as in step 4. `COUNT(column)` skips empty values (S7).

<details>
<summary>Explain it in your own words: why does the chain keep all 3,287 lines, while the self-join returns only 30 of 150 customers?</summary>

In the chain every line has exactly one partner in each added table. In the self-join, 120 customers have an empty
`referred_by`, and an empty value pairs with nobody, so an inner join drops them. A `LEFT JOIN` (S20) would keep all
150, with `NULL` for the referrer.

</details>

**Spot the flaw.** A colleague wants each referred customer next to the tier of the customer who referred them, and
runs this:

```sql
SELECT c.customer_id AS customer,
       r.customer_id AS referrer,
       r.loyalty_tier AS referrer_tier
FROM customers AS c
INNER JOIN customers AS r ON c.customer_id = r.referred_by;
```

Expected from that query: 30 rows, 3 columns, as in step 4. Its row for customer 3 reads `3 | 6 | bronze`. The picture showed
that customer 6 was referred by customer 3, who is gold. What went wrong, and what is the right query?

<Solution>

`c.customer_id = r.referred_by` says that `r` was referred by `c`, the opposite of the plan. The column called
`customer` holds the referrer, and `referrer_tier` holds the tier of the referred customer. The row count is 30 either
way, so the count cannot catch it; a pair you know can. Link the foreign key of `c`, the customer, to the key of `r`:

```sql
SELECT c.customer_id AS customer,
       r.customer_id AS referrer,
       r.loyalty_tier AS referrer_tier
FROM customers AS c
INNER JOIN customers AS r ON c.referred_by = r.customer_id;
```

Expected: 30 rows, 3 columns, and the row for customer 6 reads `6 | 3 | gold`.

</Solution>
