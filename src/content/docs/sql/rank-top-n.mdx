## How it works

A **rank** is a number that a window function writes beside each row to show its place inside a group. Every row stays
and one column is added, as in *Window functions: keep the rows, add the context* (S14). **Ties** are rows with the same
value in the order you chose, and the three ranking functions differ only in how they number ties.

1. `PARTITION BY` and `ORDER BY` inside `OVER` fence and order the rows as in S14, so each cafe is numbered on its own,
   from 1.
2. The function goes down each group's ordered rows and writes a number on each. In the picture above, four of
   Harbor's customers tie, and the three columns number them, and the rows after them, differently.

The rules:

- `ROW_NUMBER` never repeats a number, so tied rows still get different ones. To decide which gets which, add a
  **tie-breaker**: a further `ORDER BY` column, such as `customer_id`, that tells the rows apart. The numbers are then
  the same on every run.
- `RANK` gives tied rows the same number and then skips ahead. DuckDB's documentation defines it as the row number of
  the first row in the tie. Chai Latte and Cold Brew both cost \$4.75, at places 5 and 6 when the products are sorted
  from dearest to cheapest. `RANK` gives both a 5, and the next price, \$4.50, gets 7.
- `DENSE_RANK` also gives tied rows the same number but leaves no gaps, because it counts groups of tied rows. The same
  two products share a 5, and \$4.50 gets 6.
- Name the **tie policy** before you write a top-N query: what should happen to rows that tie at the cut-off? Each of
  the three functions is one answer.

**Excel.** Sorting a table (E5, *Tables, sorting and filtering*) puts rows in rank order by hand; Excel's `RANK` returns
that position without sorting, and tied numbers get the same rank.

**A common misconception: "a tie means something is wrong with the data."** Chai Latte and Cold Brew are both priced
\$4.75 and nothing is wrong. Equal values are normal, which is why the ranking functions have a rule for them.

## Worked example

Question: **who are each cafe's three most frequent customers, exactly three per cafe?** The `per_customer` stage
counts all orders with a customer, canceled included; the one canceled order is its customer's only order, far from
the top. Run the setup cell, then one cell per step.

1. **Look at Harbor's top rows.**

   ```sql
   WITH per_customer AS (
     SELECT store_id, customer_id, COUNT(*) AS orders
     FROM orders
     WHERE customer_id IS NOT NULL
     GROUP BY store_id, customer_id
   )
   SELECT customer_id, orders
   FROM per_customer
   WHERE store_id = 3
   ORDER BY orders DESC, customer_id
   LIMIT 8;
   ```

   Read it: *for Harbor, list customers by number of orders, most first, lower id first on a tie*. Expected:
   8 rows, 2 columns: one customer with 11 orders, four tied at 10, then three at 9. *Excel:* sort the Harbor rows by
   orders, largest first. *Why:* the whole `per_customer` stage has 306 rows. Look at one cafe first, because the ties
   are the difficulty.

2. **Number the rows three ways.** Predict first: what will `RANK` show for the three customers with 9 orders?

   <details>
   <summary>Prediction</summary>

   6 for all three. The four tied customers hold places 2 to 5, so the next place is 6. `DENSE_RANK` shows 3, the next
   number after 2.

   </details>

   ```sql
   WITH per_customer AS (
     SELECT store_id, customer_id, COUNT(*) AS orders
     FROM orders
     WHERE customer_id IS NOT NULL
     GROUP BY store_id, customer_id
   )
   SELECT customer_id, orders,
          ROW_NUMBER() OVER (ORDER BY orders DESC, customer_id) AS row_num,
          RANK()       OVER (ORDER BY orders DESC) AS rnk,
          DENSE_RANK() OVER (ORDER BY orders DESC) AS dense_rnk
   FROM per_customer
   WHERE store_id = 3
   ORDER BY orders DESC, customer_id
   LIMIT 8;
   ```

   Expected: 8 rows, 5 columns, as in the first picture. *Excel:* `RANK` for the middle column. *Why:* `ROW_NUMBER` needs
   `customer_id` in its `ORDER BY` to break the tie, and numbers the four tied customers 2 to 5. `RANK` and
   `DENSE_RANK` give them all 2. The `WHERE store_id = 3` runs before the ranking, which is fine here.

3. **Rank inside each cafe and keep the top 3.**

   ```sql
   WITH per_customer AS (
     SELECT store_id, customer_id, COUNT(*) AS orders
     FROM orders
     WHERE customer_id IS NOT NULL
     GROUP BY store_id, customer_id
   ),
   ranked AS (
     SELECT store_id, customer_id, orders,
            ROW_NUMBER() OVER (PARTITION BY store_id
                               ORDER BY orders DESC, customer_id) AS row_num
     FROM per_customer
   )
   SELECT store_id, customer_id, orders, row_num
   FROM ranked
   WHERE row_num <= 3
   ORDER BY store_id, row_num;
   ```

   Read it: *number each cafe's customers by orders, then keep numbers 1 to 3*. Expected: 9 rows, 4 columns, three for each
   cafe. Harbor's three are customers 104, 7 and 13: customers 77 and 103 tie with 7 and 13 on 10 orders and lose
   only on the lower-id rule. *Why:* `PARTITION BY store_id` restarts the numbering for each cafe, and the numbering
   sits in its own stage, `ranked`, so the final `WHERE` can use it.

4. **See why it needs a second stage.** This query puts the filter next to the window function. Run it:

   ```sql
   WITH per_customer AS (
     SELECT store_id, customer_id, COUNT(*) AS orders
     FROM orders
     WHERE customer_id IS NOT NULL
     GROUP BY store_id, customer_id
   )
   SELECT store_id, customer_id, orders,
          ROW_NUMBER() OVER (PARTITION BY store_id
                             ORDER BY orders DESC, customer_id) AS row_num
   FROM per_customer
   WHERE row_num <= 3;
   ```

   Expected: an error that starts with `Binder Error`. *Why:* the window function runs after `WHERE` and `HAVING`
   (*How a query runs: the order of the clauses*, S12), so the filter cannot see `row_num` yet. The first line of the
   error reads `Binder Error: WHERE clause cannot contain window functions!`. A second stage, a CTE (*Readable queries
   with CTEs*, S13), finishes the ranking first, and the next stage can filter on it.

5. **Try `RANK` for the same job.**

   ```sql
   WITH per_customer AS (
     SELECT store_id, customer_id, COUNT(*) AS orders
     FROM orders
     WHERE customer_id IS NOT NULL
     GROUP BY store_id, customer_id
   ),
   ranked AS (
     SELECT store_id, customer_id, orders,
            RANK() OVER (PARTITION BY store_id ORDER BY orders DESC) AS rnk
     FROM per_customer
   )
   SELECT store_id, customer_id, orders, rnk
   FROM ranked
   WHERE rnk <= 3
   ORDER BY store_id, rnk, customer_id;
   ```

   Expected: 13 rows, 4 columns: 4 rows more than step 3. *Why:* `RANK` gives tied customers the same number, so every
   customer tied inside the top three stays: Old Town keeps 3 rows, Campus 5 (three tie for third place on 24 orders)
   and Harbor 5 (four tie for second). `DENSE_RANK` would keep 4, 5 and 10, because it counts places, not rows. With
   three cards per cafe, only `ROW_NUMBER` fits the policy.

6. **Verify one row per group.**

   ```sql
   WITH per_customer AS (
     SELECT store_id, customer_id, COUNT(*) AS orders
     FROM orders
     WHERE customer_id IS NOT NULL
     GROUP BY store_id, customer_id
   ),
   ranked AS (
     SELECT store_id, customer_id, orders,
            ROW_NUMBER() OVER (PARTITION BY store_id
                               ORDER BY orders DESC, customer_id) AS row_num
     FROM per_customer
   ),
   top3 AS (
     SELECT store_id, customer_id, orders, row_num
     FROM ranked
     WHERE row_num <= 3
   )
   SELECT store_id, COUNT(*) AS rows_kept
   FROM top3
   GROUP BY store_id
   ORDER BY store_id;
   ```

   Expected: 3 rows, 2 columns, with `3` in every row of `rows_kept`. *Why:* the policy promised three rows per cafe, and a
   count per cafe checks it: 3 cafes times 3 is the 9 rows of step 3.

7. **The DuckDB shortcut: `QUALIFY`.** The two-stage form works in any database with window functions, which the
   DuckDB documentation says major SQL databases have. DuckDB also has `QUALIFY`, which filters on a window function
   the way `HAVING` filters on an aggregate, without the extra stage:

   ```sql
   WITH per_customer AS (
     SELECT store_id, customer_id, COUNT(*) AS orders
     FROM orders
     WHERE customer_id IS NOT NULL
     GROUP BY store_id, customer_id
   )
   SELECT store_id, customer_id, orders,
          ROW_NUMBER() OVER (PARTITION BY store_id
                             ORDER BY orders DESC, customer_id) AS row_num
   FROM per_customer
   QUALIFY row_num <= 3
   ORDER BY store_id, row_num;
   ```

   Expected: 9 rows, 4 columns, the same rows as step 3. Learn the two-stage form first.

<details>
<summary>Explain it in your own words: why did RANK return more rows than ROW_NUMBER in step 5?</summary>

`ROW_NUMBER` always gives different numbers, so exactly three rows have numbers 1 to 3. `RANK` gives the same number
to tied rows, so a tie at the cut-off puts more than three rows at rank 3 or better, and all of them stay.

</details>

WITH per_product AS (
  SELECT product_id, SUM(quantity) AS units
  FROM order_items
  GROUP BY product_id

ranked AS (
  SELECT product_id, units,

Keep every customer who ties for first place.

Before you run anything, write one sentence in the first cell: how many rows do you expect, and what do you do with a
tie for first place? Then write the query.

Expected: 3 columns. The count covers orders of any status; the walk-in
order makes no difference, because it cannot reach first place.

<details>
<summary>Hint</summary>

Count orders by payment method and customer, rank inside each payment method, and keep rank 1. Which function keeps
every tied row?

</details>

<details>
<summary>Half-solution</summary>

Expected output: *"Three payment methods, one row each, plus one extra row for every tie at first place; each row shows
the method, the customer and the customer's order count."*

</details>

<Solution>

```sql
WITH per_method AS (
  SELECT payment_method, customer_id, COUNT(*) AS orders
  FROM orders
  WHERE customer_id IS NOT NULL
  GROUP BY payment_method, customer_id
),
ranked AS (
  SELECT payment_method, customer_id, orders,
         RANK() OVER (PARTITION BY payment_method ORDER BY orders DESC) AS rnk
  FROM per_method
)
SELECT payment_method, customer_id, orders
FROM ranked
WHERE rnk = 1
ORDER BY payment_method, customer_id;
```

| payment_method | customer_id | orders |
|---|---:|---:|
| card | 11 | 20 |
| cash | 104 | 8 |
| mobile | 54 | 11 |
| mobile | 83 | 11 |

Customer 11 used a card most often (20 orders), customer 104 cash (8) and customers 54 and 83 tie for mobile with 11
each. `RANK() = 1` keeps both, which was the policy; `ROW_NUMBER() = 1` would have dropped one silently.

</Solution>

</Exercise>

## Check yourself

1. Without looking back: four customers tie for second place with 10 orders and the next customer has 9. What do
   `ROW_NUMBER`, `RANK` and `DENSE_RANK` give that next customer, if the first customer had 11 orders?

   <details>
   <summary>Answer</summary>

   `ROW_NUMBER` gives 6, one more than the last of the four rows numbered 2 to 5. `RANK` gives 6 as well, because
   the four tied rows share place 2 and the next place is 6. `DENSE_RANK` gives 3. (In Harbor's data three customers
   have 9 orders: `ROW_NUMBER` numbers them 6, 7 and 8, while `RANK` gives all three 6 and `DENSE_RANK` all three 3.)

   </details>

2. Why can you not write `WHERE row_num <= 3` in the same `SELECT` that defines `row_num` with `ROW_NUMBER()`?

   <details>
   <summary>Answer</summary>

   Window functions run after `WHERE` and `HAVING`, so at the time `WHERE` runs, `row_num` does not exist yet. Compute
   it in a CTE, then filter in the next stage (or use `QUALIFY` in DuckDB).

   </details>

**Spot the flaw.** The owner has exactly three gift cards for each cafe. A colleague runs this query for the winners.
It runs and returns the right kind of table:

```sql
WITH per_customer AS (
  SELECT store_id, customer_id, COUNT(*) AS orders
  FROM orders
  WHERE customer_id IS NOT NULL
  GROUP BY store_id, customer_id
),
ranked AS (
  SELECT store_id, customer_id, orders,
         RANK() OVER (PARTITION BY store_id ORDER BY orders DESC) AS rnk
  FROM per_customer
)
SELECT store_id, customer_id, orders
FROM ranked
WHERE rnk <= 3
ORDER BY store_id, orders DESC, customer_id;
```

Expected: a table with 3 columns. Count the rows of each cafe, find the flaw and fix it.

<Solution>

The result has 13 rows, not 9: Old Town has 3, but Campus and Harbor have 5. `RANK()` gives tied customers the same
number, so every customer tied inside the top three stays: three tie for third at Campus, four for second at Harbor.
The policy was *exactly three*, so the function must be `ROW_NUMBER()` with a tie-breaker, as in step 3. The row count
per cafe, step 6, would have caught it. After the fix: 9 rows, 4 columns.

</Solution>
