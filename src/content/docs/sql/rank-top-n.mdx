## The question

The owner of the cafes asks:

> We have three gift cards for each cafe. Who are each cafe's three most frequent customers?

Orders per customer and cafe, for the top of Harbor (store 3):

| customer_id | orders |
|---:|---:|
| 104 | 11 |
| 7 | 10 |
| 13 | 10 |
| 77 | 10 |
| 103 | 10 |

Customers 7, 13, 77 and 103 all have 10 orders, so "the top three" of Harbor is not obvious.

## Warm-up

From memory first, then click to check.

1. In `SUM(orders) OVER (PARTITION BY store_id ORDER BY day)` (*Window functions: keep the rows, add the context*,
   S14), which part restarts the total for each cafe, and which part makes it a running total?

   <details>
   <summary>Answer</summary>

   `PARTITION BY store_id` restarts the total for each cafe. `ORDER BY day` orders each cafe's rows, so each total
   covers the rows up to it.

   </details>

2. Write the query that gives one row per store and customer with the number of orders, leaving out the walk-in order
   that has no customer (*GROUP BY and HAVING*, S8, and *NULL: unknown is not zero*, S4). Expected: 306 rows, 3 columns.

   <details>
   <summary>Answer</summary>

   ```sql
   SELECT store_id, customer_id, COUNT(*) AS orders
   FROM orders
   WHERE customer_id IS NOT NULL
   GROUP BY store_id, customer_id;
   ```

   The grain is one row per store and customer. It becomes the `per_customer` stage below.

   </details>

## The big idea

A ranking function numbers the rows inside each group, best first, and every row stays; the real choice is what to do
when two rows tie.

## Learn by doing

Five small steps. Each gives you one idea, then you try it in the editor.

Every query starts with the `per_customer` stage from the warm-up. It counts all orders with a customer, canceled
included; the one canceled order is its customer's only order, far from the top.

### 1. Meet the ties

A **rank** is a number that a window function writes beside each row to show its place inside a group. Every row stays
and one column is added, as in S14. **Ties** are rows with the same value in the order you chose.

**Try it:** Harbor's eight top customers, lower id first on a tie.

<RunSQL query={`WITH per_customer AS (
  SELECT store_id, customer_id, COUNT(*) AS orders
  FROM orders
  WHERE customer_id IS NOT NULL
  GROUP BY store_id, customer_id
)
SELECT customer_id, orders
FROM per_customer
WHERE store_id = 3
ORDER BY orders DESC, customer_id
LIMIT 8;`} />

Read it: *for Harbor, list customers by number of orders, most first, lower id first on a tie*. Expected: 8 rows, 2
columns: one customer with 11 orders, four tied at 10, then three at 9. *Excel:* sort the Harbor rows by orders, largest
first (E5, *Tables, sorting and filtering*). *Why:* the whole `per_customer` stage has 306 rows. Look at one cafe first,
because the ties are the difficulty.

### 2. Number the rows three ways

Before you write a top-N query, name the **tie policy**: what should happen to rows that tie at the cut-off? Each
ranking function is one answer, and they differ only in how they number ties.

- `ROW_NUMBER` never repeats a number, so tied rows still get different ones. To decide which gets which, add a
  **tie-breaker**: a further `ORDER BY` column, such as `customer_id`, that tells the rows apart. The numbers are then the
  same on every run.
- `RANK` gives tied rows the same number and then skips ahead. DuckDB's documentation defines it as the row number of the
  first row in the tie. Chai Latte and Cold Brew both cost \$4.75, at places 5 and 6 when the products are sorted from
  dearest to cheapest. `RANK` gives both a 5, and the next price, \$4.50, gets 7.
- `DENSE_RANK` also gives tied rows the same number but leaves no gaps, because it counts groups of tied rows. The same
  two products share a 5, and \$4.50 gets 6.

*Excel:* the `RANK` function returns a row's position without sorting, and tied numbers get the same rank.

**Try it.** Predict first: what will `RANK` show for the three customers with 9 orders?

<details>
<summary>Prediction</summary>

6 for all three. The four tied customers hold places 2 to 5, so the next place is 6. `DENSE_RANK` shows 3, the next
number after 2.

</details>

<RunSQL query={`WITH per_customer AS (
  SELECT store_id, customer_id, COUNT(*) AS orders
  FROM orders
  WHERE customer_id IS NOT NULL
  GROUP BY store_id, customer_id
)
SELECT customer_id, orders,
       ROW_NUMBER() OVER (ORDER BY orders DESC, customer_id) AS row_num,
       RANK()       OVER (ORDER BY orders DESC) AS rnk,
       DENSE_RANK() OVER (ORDER BY orders DESC) AS dense_rnk
FROM per_customer
WHERE store_id = 3
ORDER BY orders DESC, customer_id
LIMIT 8;`} />

Expected: 8 rows, 5 columns. *Why:* `ROW_NUMBER` numbers the four tied customers 2 to 5 only because `customer_id` breaks
the tie; `RANK` and `DENSE_RANK` give them all 2. The `WHERE store_id = 3` runs before the ranking, which is fine here.

### 3. Number inside each cafe, keep three

`PARTITION BY store_id` restarts the numbering for each cafe, as in S14. The owner has exactly three cards per cafe, so
the policy is *exactly three rows*: `ROW_NUMBER` with the tie-breaker, then keep the numbers 1 to 3.

**Try it:**

<RunSQL query={`WITH per_customer AS (
  SELECT store_id, customer_id, COUNT(*) AS orders
  FROM orders
  WHERE customer_id IS NOT NULL
  GROUP BY store_id, customer_id
),
ranked AS (
  SELECT store_id, customer_id, orders,
         ROW_NUMBER() OVER (PARTITION BY store_id
                            ORDER BY orders DESC, customer_id) AS row_num
  FROM per_customer
)
SELECT store_id, customer_id, orders, row_num
FROM ranked
WHERE row_num <= 3
ORDER BY store_id, row_num;`} />

Read it: *number each cafe's customers by orders, then keep numbers 1 to 3*. Expected: 9 rows, 4 columns, three for each
cafe. Harbor's three are customers 104, 7 and 13: customers 77 and 103 tie with 7 and 13 on 10 orders and lose only on
the lower-id rule. The picture shows the restart on products: each category is numbered on its own, from 1.

### 4. Filter in the next stage

A window function runs after `WHERE` and `HAVING` (*How a query runs: the order of the clauses*, S12), so a filter in the
same `SELECT` cannot see its result. Finish the ranking in one stage, a CTE (*Readable queries with CTEs*, S13), and
filter in the next.

**Try it.** This query puts the filter next to the window function:

<RunSQL query={`WITH per_customer AS (
  SELECT store_id, customer_id, COUNT(*) AS orders
  FROM orders
  WHERE customer_id IS NOT NULL
  GROUP BY store_id, customer_id
)
SELECT store_id, customer_id, orders,
       ROW_NUMBER() OVER (PARTITION BY store_id
                          ORDER BY orders DESC, customer_id) AS row_num
FROM per_customer
WHERE row_num <= 3;`} />

Expected: an error that says `WHERE clause cannot contain window functions!`.

The two-stage form works in any database with window functions, which the DuckDB documentation says major SQL databases
have. DuckDB also has `QUALIFY`, which filters on a window function the way `HAVING` filters on an aggregate, without
the extra stage. Learn the two-stage form first.

**Try it:**

<RunSQL query={`WITH per_customer AS (
  SELECT store_id, customer_id, COUNT(*) AS orders
  FROM orders
  WHERE customer_id IS NOT NULL
  GROUP BY store_id, customer_id
)
SELECT store_id, customer_id, orders,
       ROW_NUMBER() OVER (PARTITION BY store_id
                          ORDER BY orders DESC, customer_id) AS row_num
FROM per_customer
QUALIFY row_num <= 3
ORDER BY store_id, row_num;`} />

Expected: 9 rows, 4 columns, the same rows as unit 3.

### 5. Check the policy

A policy is a promise, so test it. First swap `RANK` into the same job.

**Try it:**

<RunSQL query={`WITH per_customer AS (
  SELECT store_id, customer_id, COUNT(*) AS orders
  FROM orders
  WHERE customer_id IS NOT NULL
  GROUP BY store_id, customer_id
),
ranked AS (
  SELECT store_id, customer_id, orders,
         RANK() OVER (PARTITION BY store_id ORDER BY orders DESC) AS rnk
  FROM per_customer
)
SELECT store_id, customer_id, orders, rnk
FROM ranked
WHERE rnk <= 3
ORDER BY store_id, rnk, customer_id;`} />

Expected: 13 rows, 4 columns: 4 rows more than unit 3.

<details>
<summary>Explain it in your own words: why did <code>RANK</code> return more rows than <code>ROW_NUMBER</code> in this unit?</summary>

Old Town has no tie at the cut-off, so it keeps 3 rows. At Campus, three customers tie on 24 orders for third place:
`ROW_NUMBER` hands them 3, 4 and 5, so only one passes `row_num <= 3`, while `RANK` hands all three a 3, so Campus keeps
5 rows. Harbor also keeps 5: four customers tie for second place.

</details>

Now count the rows of the `ROW_NUMBER` version for each cafe.

**Try it:**

<RunSQL query={`WITH per_customer AS (
  SELECT store_id, customer_id, COUNT(*) AS orders
  FROM orders
  WHERE customer_id IS NOT NULL
  GROUP BY store_id, customer_id
),
ranked AS (
  SELECT store_id, customer_id, orders,
         ROW_NUMBER() OVER (PARTITION BY store_id
                            ORDER BY orders DESC, customer_id) AS row_num
  FROM per_customer
),
top3 AS (
  SELECT store_id, customer_id, orders, row_num
  FROM ranked
  WHERE row_num <= 3
)
SELECT store_id, COUNT(*) AS rows_kept
FROM top3
GROUP BY store_id
ORDER BY store_id;`} />

Expected: 3 rows, 2 columns, with `3` in every row of `rows_kept`. *Why:* 3 cafes times 3 is the 9 rows of unit 3.

<Aside type="tip" title="Remember">

- A rank is a number beside each row for its place in a group; ties are rows with the same value.
- Name the tie policy first: `ROW_NUMBER` never repeats, `RANK` shares a number and skips, `DENSE_RANK` shares and never
  skips.
- `PARTITION BY` restarts the numbering for each group.
- Filter on a rank in the next stage (or with `QUALIFY`), then count the rows of each group.

**Common trap: "a tie means something is wrong with the data."** Equal values are normal: Chai Latte and Cold Brew both
cost \$4.75, and four of Harbor's customers have 10 orders. A top-N query that ignores ties returns more rows than promised.

</Aside>

## Check yourself

1. Without looking back: four customers tie for second place with 10 orders and the next customer has 9. What do
   `ROW_NUMBER`, `RANK` and `DENSE_RANK` give that next customer, if the first customer had 11 orders?

   <details>

   `ROW_NUMBER` gives 6, one more than the last of the four rows numbered 2 to 5. `RANK` gives 6 as well, because

   have 9 orders: `ROW_NUMBER` numbers them 6, 7 and 8, while `RANK` gives all three 6 and `DENSE_RANK` all three 3.)

   </details>

2. Why can you not write `WHERE row_num <= 3` in the same `SELECT` that defines `row_num` with `ROW_NUMBER()`?

   <details>
   <summary>Answer</summary>

   Window functions run after `WHERE` and `HAVING`, so at the time `WHERE` runs, `row_num` does not exist yet. Compute
   it in a CTE, then filter in the next stage (or use `QUALIFY` in DuckDB).

   </details>
