## The big idea

An **index** is a sorted shortcut to rows: instead of reading every row to find one, the database looks the value up and
goes straight to the rows.

{/* CONCEPT: concept-index */}

## Learn by doing

Four small steps. Ignore the times in a plan.

### 1. Read a plan

Before it runs a query, the database writes a **query plan**: the steps it will take, in order. `EXPLAIN` prints the plan
without running the query. `EXPLAIN ANALYZE` runs it and prints the plan with measured numbers. For a table with a filter,
the plan shows a **scan**; the simplest is the **full scan**, which the plan calls `Sequential Scan`: read the rows one
after another and test the filter on each.

**Try it** (copy the table). You add indexes to a copy, and a table made this way starts with no rules and no indexes (S31).

<RunSQL query={`CREATE TABLE orders_ix AS SELECT * FROM orders;`} />

Expected: 1 row, 1 column: the 1,800 rows copied.

**Try it** (a plan, not run). The plan arrives as text in one cell of the output. Find the `Type:` line in it.

<RunSQL query={`EXPLAIN SELECT * FROM orders_ix WHERE order_id = 1001;`} />

Expected: a plan with one scan: `Type: Sequential Scan`, the columns it outputs, the `Filters:` test on `order_id` and `~1 row`.
*Why:* the `~` marks an estimate, because the query was not run. A scan with a filter is the plan of every `WHERE` on a table
with no index.

**Try it** (a plan, run). Before you run it: which `Type:` will it show, and will the row count still be a guess?

<RunSQL query={`EXPLAIN ANALYZE SELECT * FROM orders_ix WHERE order_id = 1001;`} />

Expected: a time, then a scan with `Type: Sequential Scan`, the filter and `1 row`. *Why:* now the row count is real: the
engine read every row of the table and kept 1.

### 2. Make an index

An index is a sorted structure that holds one column's values and, beside each, the position of its rows, like the
alphabetic index at the back of a book. The picture is a model: DuckDB's real structure is an ART, an adaptive radix tree.
`CREATE INDEX` builds one, and DuckDB also builds one for each `PRIMARY KEY` and `UNIQUE` column. DuckDB has a second kind
for free: **min-max indexes** (zonemaps), created for you on columns of the general-purpose types, which let it skip any
**row group** (a horizontal slice of a table's rows) whose min-max range does not contain the filter value.

ART indexes exist mainly to enforce keys and to speed up point lookups and very highly selective queries, under 0.1% of the
rows. That is guidance: the engine's rule for an index scan is 2,048 rows or 0.1% of the table, whichever is larger.

### 3. The filter has to fit the index

DuckDB tries an index scan for equality (`=`) and `IN` conditions, and only for an index defined on one plain column, not on
an expression.

**Try it** (a function of the column). Before you run it: the index on `order_id` exists. Will this filter use it?

<RunSQL query={`EXPLAIN ANALYZE SELECT * FROM orders_ix WHERE CAST(order_id AS VARCHAR) = '1001';`} />

Expected: `Type: Sequential Scan` and `1 row`, although the index exists. *Why:* the index holds `order_id` values, not their
text. A filter on a function of the column must compute the function for every row, so it scans them all. Write the plain
filter, as in unit 2, to keep the index useful.

**Try it** (a composite index). An index can span two columns, written `ON table (a, b)`.

<RunSQL query={`CREATE INDEX idx_orders_store_payment ON orders_ix (store_id, payment_method);`} />

<RunSQL query={`EXPLAIN ANALYZE SELECT * FROM orders_ix WHERE store_id = 3 AND payment_method = 'card';`} />

Expected: a scan, and above it a projection step. *Why:* the plan scans every row (`Type: Sequential Scan`) and returns 180
rows, so DuckDB did not use the composite index: it spans two columns, not one plain column. An index on `store_id` alone is used for `store_id = 3`. The composite
index was built and kept up to date for nothing.

### 4. An index has a price, and never changes the answer

An index slows down loading and updates, so changes on an indexed table perform worse, and it can take a significant share
of DuckDB's memory. An ART index does not change how fast joins, aggregations or sorts run. *Excel:* `XLOOKUP` (E8, *Bring
in a value by key with XLOOKUP*) has a binary-search mode that relies on the lookup list being sorted, and returns invalid
results if it is not. By analogy, sorted order saves reading, and keeping the order is the upkeep: the bargain an index
makes.

**Try it** (same answer, with and without the index). Before you run it: how many rows should differ?

<RunSQL query={`SELECT COUNT(*) AS differing_rows FROM (
  (SELECT * FROM orders WHERE order_id = 1001 EXCEPT SELECT * FROM orders_ix WHERE order_id = 1001)
  UNION ALL
  (SELECT * FROM orders_ix WHERE order_id = 1001 EXCEPT SELECT * FROM orders WHERE order_id = 1001)
);`} />

Expected: 1 row, 1 column. *Why:* each `EXCEPT` lists rows that one side has and the other lacks, and `UNION ALL` joins the two
lists. The count is **0**: the indexed copy returns exactly the original row. An index changes how a row is found, never
which rows qualify.

<details>
<summary>Explain it in your own words: why does this check run EXCEPT in both directions?</summary>

One `EXCEPT` lists only the rows its first query has and its second lacks. If the indexed copy returned an extra row,
that direction would still count 0 differences. Running it both ways and adding the lists catches a missing row and an
extra one.

</details>

<Aside type="tip" title="Remember">

- `EXPLAIN` shows the plan; `EXPLAIN ANALYZE` runs the query and shows what happened. Read the `Type:` line.
- An ART index serves a plain `=` or `IN` filter on its one column, mostly for a few rows.
- An index costs upkeep and memory, and never changes which rows come back.

**Common trap: "an index makes every query faster, so index every column."** An ART index mainly serves highly selective
lookups, and it costs upkeep and memory all the time.

</Aside>

```sql
EXPLAIN ANALYZE SELECT * FROM orders_ex2 WHERE customer_id = 15;
EXPLAIN ANALYZE SELECT * FROM orders_ex2 WHERE CAST(customer_id AS VARCHAR) = '15';
EXPLAIN ANALYZE SELECT * FROM orders_ex2 WHERE status = 'canceled';
```

(a) is an `Index Scan` with 16 rows: the filter is the indexed column. (b) is a `Sequential Scan` with 16 rows: the function wraps
the column. (c) is a `Sequential Scan` with 1 row: nothing is indexed on `status`, and the one canceled order is found by
reading all of them. Check (a) against (b) with the symmetric `EXCEPT` of unit 4; it returns 0: the rewrite changes the way
the rows are found, not which rows.

</Solution>

</Exercise>

## Check yourself

Without looking back: explain an index with the book-index picture, and say which kind of index DuckDB builds without being asked.

<details>
<summary>Answer</summary>

An index is a short sorted list of one column's values with pointers to the rows, like a book's index of terms with page
numbers: you look in the list instead of reading everything. It costs upkeep on every insert and update. DuckDB builds
min-max (zonemap) indexes on its own, and an ART index for each primary key and `UNIQUE` column.

</details>
