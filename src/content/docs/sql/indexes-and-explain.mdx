## How it works

An **index** is a shortcut to rows: a sorted structure, kept apart from the table, that holds one column's values and,
beside each, the position of its rows. In the picture above, the list on the right is an index on `customer_id`, like the
alphabetic index at the back of a book. The picture is a model: DuckDB's real structure is an ART, an adaptive radix tree.

Before it runs a query, the engine writes a **query plan**: the steps it will take, in order. `EXPLAIN` prints the plan
without running the query; `EXPLAIN ANALYZE` runs it and prints the plan with measured numbers. For a table with a filter,
the engine chooses between two scans:

1. **Full scan** (`Sequential Scan`): read the rows one after another and test the filter on each. DuckDB stores a table
   in **row groups**, horizontal slices of its rows; each cafe table fits in one, so a full scan reports `1 / 1`. In the
   picture above, customer 15 needs all six rows read.
2. **Index scan**: look the value up in the sorted structure, take the row positions beside it, and read only those rows.
   In the picture above: one entry, then rows 1 and 6.

The engine, not you, makes the choice. The rules:

- DuckDB has two kinds of index. **Min-max indexes** (zonemaps) are created for you on columns of the general-purpose
  types. **ART indexes** come from `CREATE INDEX`, and DuckDB also builds one for each `PRIMARY KEY` and `UNIQUE` column.
- ART indexes exist mainly to enforce keys and to speed up point lookups and very highly selective queries, under 0.1%
  of the rows.
- DuckDB tries an index scan for equality (`=`) and `IN` conditions, and only for an index on one column with no
  expression inside it.
- An ART index does not change how fast joins, aggregations or sorts run.
- An index has a price: every insert, update and delete must change it too, and it can take a significant share of memory.

**Excel.** `XLOOKUP` (E8, *Bring in a value by key with XLOOKUP*) has a binary-search mode that relies on the lookup list
being sorted, and returns invalid results if it is not. Sorted order saves reading, and keeping the order is the upkeep:
the bargain an index makes.

**A common misconception: "an index makes every query faster, so index every column."** An ART index serves highly
selective lookups, leaves joins, aggregations and sorts as they were, and costs upkeep and memory all the time.

## Worked example

Question: **will an index help the till's lookup of one order?** Run the notebook's setup cell, then one cell per
step. Each step gives the shape of the result to expect. Ignore the times in a plan.

1. **Copy `orders` so you can add indexes.**

   ```sql
   CREATE TABLE orders_ix AS SELECT * FROM orders;
   ```

   Expected: a `Count` table, 1 row, 1 column. *Why:* indexes go on the copy, and a table made this way starts with no
   rules and no indexes (S31).

2. **Read a plan without running it.**

   ```sql
   EXPLAIN SELECT * FROM orders_ix WHERE order_id = 1001;
   ```

   Expected: a box drawing with one `Seq Scan` box: `Table: memory.main.orders_ix`, `Type: Sequential Scan`, the
   columns it outputs, `Filters: order_id = 1001` and `~1 row`. *Why:* the `~` marks an estimate, because the query
   was not run. A scan with a filter is the plan of every `WHERE` on a table with no index.

3. **Run it and read what happened.**

   ```sql
   EXPLAIN ANALYZE SELECT * FROM orders_ix WHERE order_id = 1001;
   ```

   Expected: a `Summary` box with a time, then a `Table Scan` box with `Type: Sequential Scan`, `Row Groups Scanned:
   1 / 1` and `1 row`. *Why:* now the row count is real: the engine read one row group, all of the table, and
   kept 1 row.

4. **Create the index and run it again.**

   ```sql
   CREATE INDEX idx_orders_order_id ON orders_ix (order_id);
   EXPLAIN ANALYZE SELECT * FROM orders_ix WHERE order_id = 1001;
   ```

   Expected: the same boxes, now with `Type: Index Scan`, `Row Groups Scanned: 0 / 1` and `1 row`. *Why:* the engine
   went to the row through the index, so no group was scanned in the ordinary way. In DuckDB 2.0.0 the plain `EXPLAIN`
   of this query still prints `Sequential Scan`: only `EXPLAIN ANALYZE` shows what was used. The answer to the owner:
   yes, for a lookup of one row by key. DuckDB already builds this index for a primary key.

5. **A filter that cannot use the index.**

   ```sql
   EXPLAIN ANALYZE SELECT * FROM orders_ix WHERE CAST(order_id AS VARCHAR) = '1001';
   ```

   Expected: `Type: Sequential Scan`, `Row Groups Scanned: 1 / 1` and `1 row`, although the index exists. *Why:* the
   index holds `order_id` values, not their text. A filter on a function of the column must compute the function for
   every row, so it scans them all. Write the plain filter, as in step 4, to keep the index useful.

6. **A composite index.** An index can span two columns, written `ON table (a, b)`.

   ```sql
   CREATE INDEX idx_orders_store_payment ON orders_ix (store_id, payment_method);
   EXPLAIN ANALYZE SELECT * FROM orders_ix WHERE store_id = 3 AND payment_method = 'card';
   ```

   Expected: a `Table Scan` box, and above it a `Projection` box. *Why:* the plan scans every row and returns 180
   rows, so DuckDB did not use the composite index: only an index on one column qualifies (How it works).
   An index on `store_id` alone is used for `store_id = 3`. The composite index was built and kept up to date for nothing.

7. **Verify: the same answer with and without the index.**

   ```sql
   SELECT COUNT(*) AS differing_rows FROM (
     (SELECT * FROM orders WHERE order_id = 1001 EXCEPT SELECT * FROM orders_ix WHERE order_id = 1001)
     UNION ALL
     (SELECT * FROM orders_ix WHERE order_id = 1001 EXCEPT SELECT * FROM orders WHERE order_id = 1001)
   );
   ```

   Expected: 1 row, 1 column. *Why:* each `EXCEPT` lists rows that one side has and the other lacks, and `UNION ALL` joins the
   two lists. The count is 0: the indexed copy returns exactly the original row. An index changes how a row is found,
   never which rows qualify.

<details>
<summary>Half-solution</summary>

<Solution>

```sql
EXPLAIN ANALYZE SELECT * FROM orders_ex2 WHERE customer_id = 15;
EXPLAIN ANALYZE SELECT * FROM orders_ex2 WHERE CAST(customer_id AS VARCHAR) = '15';
EXPLAIN ANALYZE SELECT * FROM orders_ex2 WHERE status = 'canceled';
```

(a) is an `Index Scan` with 16 rows: the filter is the indexed column. (b) is a `Sequential Scan` with 16 rows: the function wraps
the column. (c) is a `Sequential Scan` with 1 row: nothing is indexed on `status`, and the one canceled order is found by
reading all of them. Check (a) against (b) with the symmetric `EXCEPT` of step 7; it returns 0: the rewrite changes the way
the rows are found, not which rows.

</Solution>

## Check yourself

Without looking back: explain an index with the book-index picture, and say which kind of index DuckDB builds without being asked.

<details>
<summary>Answer</summary>

An index is a short sorted list of one column's values with pointers to the rows, like a book's index of terms with page
numbers: you look in the list instead of reading everything. It costs upkeep on every insert and update. DuckDB builds
min-max (zonemap) indexes on its own, and an ART index for each primary key and `UNIQUE` column.

</details>
