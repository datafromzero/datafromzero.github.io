## How it works

Two more kinds of window function (*Window functions: keep the rows, add the context*, S14) work on **neighbors**: `LAG`
and `LEAD` copy a value from another row of the list, and an aggregate over a **frame**, a set of rows around the
current one, works on a sliding window. Every row stays and one column is added. The pictures above show both ideas.

1. Build the series first: one row per period, such as a month, from `GROUP BY`.
2. `ORDER BY` inside `OVER` lines the rows up. "Above" and "below" mean earlier and later in that order, and each
   `PARTITION BY` group is a separate list.
3. `LAG(x)` writes beside each row the value of `x` from the row above, and `LEAD(x)` the value from the row below.
4. A frame function takes the current row and the rows around it, as many as `ROWS BETWEEN` says, works out `AVG` over
   just those rows, and writes the answer beside the current row. The window then moves down one row.

The rules:

- `LAG(x, n, default)` reaches `n` rows back and `LEAD` reaches `n` rows forward; `n` is 1 if you leave it out. With no
  row that far away you get `NULL`, unless the third argument supplies a `default`.
- `LAG` and `LEAD` count rows, not calendar time, and never reach into another partition.
- `ROWS BETWEEN 6 PRECEDING AND CURRENT ROW` counts rows: the current one and the six before it.
- `RANGE` measures distance in values instead. With dates it takes an `INTERVAL`, as in
  `RANGE BETWEEN INTERVAL 6 DAYS PRECEDING AND CURRENT ROW`, which DuckDB's documentation uses "to handle any missing
  days". *Complete time series and recursive CTEs* (S27) fills the gaps instead.

**Excel.** A reference to the cell above, copied down, moves down with the row, and so does a range such as `B2:B8`
(E3, *Relative and absolute references*); that is how a sheet does `LAG` and a moving average.

**A common misconception: "a 7-row frame is a 7-day average."** The two agree only while every day has a row. Suppose
April 2 had no orders and so no row: the frame of April 4 would still hold seven rows, and it would reach back to March
28, eight calendar days. The `RANGE` form above would hold six rows, March 29 to April 4.

With months in A2 to A7 and orders in B2 to B7, a sheet does it like this:

| SQL | Reads as | In Excel or Google Sheets |
|---|---|---|
| `LAG(orders) OVER (ORDER BY month)` | the value one row up | a reference to the cell above, such as `=B2` in row 3 |
| `orders - LAG(orders) OVER (...)` | the change from the row above | `=B3-B2` |
| `(orders - prev_orders) * 100.0 / prev_orders` | the percent change | `=(B3-B2)/B2` |
| `AVG(orders) OVER (ORDER BY day ROWS BETWEEN 6 PRECEDING AND CURRENT ROW)` | a 7-row moving average | `=AVERAGE(B2:B8)`, copied down |

In the sheet, the first data row has no row above, so you start the formula one row lower; SQL gives that row a
`NULL`.

## Worked example

Question: **how much did orders change from month to month, for the chain and for each cafe, and is the daily trend
smooth?** Run the setup cell, then one cell per step.

1. **Build the monthly table.**

   ```sql
   WITH monthly AS (
     SELECT CAST(DATE_TRUNC('month', ordered_at) AS DATE) AS month, COUNT(*) AS orders
     FROM orders
     GROUP BY month
   )
   SELECT month, orders
   FROM monthly
   ORDER BY month;
   ```

   Expected: 6 rows, 2 columns, the table from the question. *Excel:* a PivotTable of orders by month. *Why:* a window
   function needs a clean series first: one row per month, in an order you can name. The `monthly` stage starts each
   monthly query.

2. **Look at the row above and the row below.**

   ```sql
   WITH monthly AS (
     SELECT CAST(DATE_TRUNC('month', ordered_at) AS DATE) AS month, COUNT(*) AS orders
     FROM orders
     GROUP BY month
   )
   SELECT month, orders,
          LAG(orders)  OVER (ORDER BY month) AS prev_orders,
          LEAD(orders) OVER (ORDER BY month) AS next_orders
   FROM monthly
   ORDER BY month;
   ```

   Read it: *beside each month, put the orders of the month before and the month after*. Expected: 6 rows, 4 columns;
   January has `NULL` in `prev_orders` and June has `NULL` in `next_orders`. *Excel:* the cell above and the cell
   below. *Why:* `ORDER BY month` inside `OVER` defines "before" and "after".

3. **Compute the change and the percent change.**

   ```sql
   WITH monthly AS (
     SELECT CAST(DATE_TRUNC('month', ordered_at) AS DATE) AS month, COUNT(*) AS orders
     FROM orders
     GROUP BY month
   ),
   with_prev AS (
     SELECT month, orders, LAG(orders) OVER (ORDER BY month) AS prev_orders
     FROM monthly
   )
   SELECT month, orders, prev_orders,
          orders - prev_orders AS change,
          ROUND((orders - prev_orders) * 100.0 / NULLIF(prev_orders, 0), 1) AS pct_change
   FROM with_prev
   ORDER BY month;
   ```

   Expected: 6 rows, 5 columns. The change from February to March is 40 orders, or 18.3 percent of February's 218. *Excel:*
   `=B3-B2` and `=(B3-B2)/B2`. *Why:* the percent change uses the previous month as the denominator, so always say
   "compared with the month before". The first row stays `NULL`, because arithmetic with `NULL` gives `NULL`.
   `NULLIF(prev_orders, 0)` turns a zero denominator into `NULL`: in DuckDB 2.0.0 a division by zero returns
   `inf`, which is no percentage. The `with_prev` stage lets two columns share the `LAG`.

4. **Compare inside each cafe.**

   ```sql
   WITH monthly AS (
     SELECT store_id, CAST(DATE_TRUNC('month', ordered_at) AS DATE) AS month, COUNT(*) AS orders
     FROM orders
     GROUP BY store_id, month
   ),
   with_prev AS (
     SELECT store_id, month, orders,
            LAG(orders) OVER (PARTITION BY store_id ORDER BY month) AS prev_orders
     FROM monthly
   )
   SELECT store_id, month, orders, prev_orders,
          ROUND((orders - prev_orders) * 100.0 / NULLIF(prev_orders, 0), 1) AS pct_change
   FROM with_prev
   ORDER BY store_id, month;
   ```

   Expected: 15 rows, 5 columns. Harbor's April has `NULL`: it has no row for March, since it opened on April 1. *Excel:* the
   same formulas, restarted for each cafe. *Why:* `PARTITION BY store_id` makes each cafe its own series. The answer to the owner: the chain grew 35.3 percent
   in April, but that is Harbor's 123 first orders; Old Town fell 7.5 percent and Campus 17.6 percent.

5. **Smooth the daily series.** Predict first: what will the 7-day average show on January 1, the first day of the
   data?

   <details>
   <summary>Prediction</summary>

   4.0, just that day's orders. The frame is cropped to the rows that exist, so on January 1 the average has one value,
   and on January 7 it has seven.

   </details>

   ```sql
   WITH daily AS (
     SELECT CAST(ordered_at AS DATE) AS day, COUNT(*) AS orders
     FROM orders
     GROUP BY day
   ),
   smoothed AS (
     SELECT day, orders,
            ROUND(AVG(orders) OVER (ORDER BY day
                                    ROWS BETWEEN 6 PRECEDING AND CURRENT ROW), 2) AS avg_7_days
     FROM daily
   )
   SELECT day, orders, avg_7_days
   FROM smoothed
   WHERE day BETWEEN '2026-03-30' AND '2026-04-07'
   ORDER BY day;
   ```

   Expected: 9 rows, 3 columns, the days around the jump in early April (second picture). *Excel:* `=AVERAGE(B2:B8)` copied
   down. *Why:* the frame is the current day and the six rows before it. The date filter comes after the `smoothed`
   stage: a `WHERE` in the same query would remove the earlier days before the average could see them. Rows are days
   here because all 181 days from January 1 to June 30 have orders. The first seven rows, to check the cropped start:

   ```sql
   WITH daily AS (
     SELECT CAST(ordered_at AS DATE) AS day, COUNT(*) AS orders
     FROM orders
     GROUP BY day
   )
   SELECT day, orders,
          ROUND(AVG(orders) OVER (ORDER BY day ROWS BETWEEN 6 PRECEDING AND CURRENT ROW), 2) AS avg_7_days
   FROM daily
   ORDER BY day
   LIMIT 7;
   ```

   Expected: 7 rows, 3 columns. The first six averages use fewer than seven days; the window is full from the
   seventh row.

6. **Meet the `LAST_VALUE` trap.** Predict first: what will `last_default` show on the March row?

   <details>
   <summary>Prediction</summary>

   258, March's own orders. With an `ORDER BY` and no frame, the frame ends at the current row (and its peers), so the
   last value of the frame is the current row.

   </details>

   ```sql
   WITH monthly AS (
     SELECT CAST(DATE_TRUNC('month', ordered_at) AS DATE) AS month, COUNT(*) AS orders
     FROM orders
     GROUP BY month
   )
   SELECT month, orders,
          LAST_VALUE(orders) OVER (ORDER BY month) AS last_default,
          LAST_VALUE(orders) OVER (ORDER BY month
                                   ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING) AS last_whole
   FROM monthly
   ORDER BY month;
   ```

   Expected: 6 rows, 4 columns. *Why:* the default frame stops at the current row, so the last row of the frame is the row
   itself. Widening the frame to `ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING` reaches the end of the
   series. `FIRST_VALUE` shows no trap, because the frame always starts at the first row.

7. **Verify.**

   ```sql
   WITH monthly AS (
     SELECT CAST(DATE_TRUNC('month', ordered_at) AS DATE) AS month, COUNT(*) AS orders
     FROM orders
     GROUP BY month
   )
   SELECT SUM(orders) AS total_orders
   FROM monthly;
   ```

   Expected: 1 row, 1 column: `1800`. The monthly counts add up to every order in the dataset, so no row was lost on the
   way. The changes of step 3 reconcile too: -24 + 40 + 91 + 31 - 27 = 111, which is June's 353 minus January's 242.
   And the percent change of March by hand, 40 / 218, is 18.3 percent, the same as the query.

<summary>Explain it in your own words: why is January's change NULL, and why is that better than 0?</summary>

January has no month before it. `NULL` says "no value"; a `0` would claim that orders did not change.

</details>

Expected: 4 rows, 3 columns. Look at the first row, find the flaw and fix it.

<Solution>

March's `change` is `NULL`, not 40. `WHERE` runs before the window function, so February is already gone when `LAG`
looks for the row above, and March becomes the first row of the series. Compute `LAG` in a stage and filter in the
next one, as in step 3:

```sql
WITH monthly AS (
  SELECT CAST(DATE_TRUNC('month', ordered_at) AS DATE) AS month, COUNT(*) AS orders
  FROM orders
  GROUP BY month
),
with_prev AS (
  SELECT month, orders, LAG(orders) OVER (ORDER BY month) AS prev_orders
  FROM monthly
)
SELECT month, orders, orders - prev_orders AS change
FROM with_prev
WHERE month >= '2026-03-01'
ORDER BY month;
```

|---|---:|---:|
| 2026-03-01 | 258 | 40 |
| 2026-04-01 | 349 | 91 |
| 2026-05-01 | 380 | 31 |
| 2026-06-01 | 353 | -27 |

Expected after the fix: 4 rows, 3 columns, and March shows +40.
