This lesson works on one table, `orders`: first on its monthly counts, then on its daily counts. Each query runs in the
editor on this page, with the five tables of **cafe-sales**, the invented three-cafe chain we use from Excel to
Python.

## The question

The owner of the cafes asks:

> Orders went from 218 in February to 258 in March. How much did they grow each month, and is the chain really
> growing, or is it just the new cafe?

The monthly counts, the table we will compare row with row:

| month | orders |
|---|---:|
| 2026-01-01 | 242 |
| 2026-02-01 | 218 |
| 2026-03-01 | 258 |
| 2026-04-01 | 349 |
| 2026-05-01 | 380 |
| 2026-06-01 | 353 |

## Warm-up

From memory first, then click to check.

1. Write a query that counts the orders of each month (*Working with dates and time*, S11, and *GROUP BY and HAVING*,
   S8). Expected: 6 rows, 2 columns.

   <details>
   <summary>Answer</summary>

   ```sql
   SELECT CAST(DATE_TRUNC('month', ordered_at) AS DATE) AS month, COUNT(*) AS orders
   FROM orders
   GROUP BY month
   ORDER BY month;
   ```

   The counts are 242, 218, 258, 349, 380 and 353, which add to the 1,800 orders of the dataset.

   </details>

2. In *Window functions: keep the rows, add the context* (S14), what is the default frame when the `OVER` has an
   `ORDER BY` and nothing else?

   <details>
   <summary>Answer</summary>

   From the first row of the block to the current row, including every row that ties with it on the `ORDER BY` value.

   </details>

## Learn by doing

Five small steps. Each gives you one idea, then you try it in the editor.

### 1. The row above, the row below

Window functions need a clean series first: one row per period, here one per month, from `GROUP BY`. `LAG(x)` then writes
beside each row the value of `x` from the row above, and `LEAD(x)` the value from the row below. "Above" and "below"
follow the `ORDER BY` inside `OVER`.

`LAG(x, n, default)` reaches `n` rows back, and `LEAD` reaches `n` rows forward; `n` is 1 if you leave it out. With no row
that far away you get `NULL`, unless the third argument supplies a `default`.

**Try it:** the monthly series. Every monthly query below starts with this `monthly` stage.

<RunSQL query={`WITH monthly AS (
  SELECT CAST(DATE_TRUNC('month', ordered_at) AS DATE) AS month, COUNT(*) AS orders
  FROM orders
  GROUP BY month
)
SELECT month, orders
FROM monthly
ORDER BY month;`} />

Expected: 6 rows, 2 columns, the table from the question. *Excel:* a PivotTable of orders by month.

**Try it:** beside each month, the orders of the month before and the month after.

<RunSQL query={`WITH monthly AS (
  SELECT CAST(DATE_TRUNC('month', ordered_at) AS DATE) AS month, COUNT(*) AS orders
  FROM orders
  GROUP BY month
)
SELECT month, orders,
       LAG(orders)  OVER (ORDER BY month) AS prev_orders,
       LEAD(orders) OVER (ORDER BY month) AS next_orders
FROM monthly
ORDER BY month;`} />

Expected: 6 rows, 4 columns; January has `NULL` in `prev_orders` and June has `NULL` in `next_orders`. *Excel:* a
reference to the cell above, such as `=B2` in row 3, copied down, moves down with the row (E3, *Relative and absolute
references*); `LEAD` is the cell below.

### 2. Change and percent change

The change is a row's value minus the one above it. The percent change divides by the previous month, so always say
"compared with the month before". In DuckDB 2.0.0 a division by zero returns `inf`, which is no percentage, so
`NULLIF(prev_orders, 0)` turns a zero denominator into `NULL`.

**Try it:**

<RunSQL query={`WITH monthly AS (
  SELECT CAST(DATE_TRUNC('month', ordered_at) AS DATE) AS month, COUNT(*) AS orders
  FROM orders
  GROUP BY month
),
with_prev AS (
  SELECT month, orders, LAG(orders) OVER (ORDER BY month) AS prev_orders
  FROM monthly
)
SELECT month, orders, prev_orders,
       orders - prev_orders AS change,
       ROUND((orders - prev_orders) * 100.0 / NULLIF(prev_orders, 0), 1) AS pct_change
FROM with_prev
ORDER BY month;`} />

Expected: 6 rows, 5 columns. The change from February to March is 40 orders, or 18.3 percent of February's 218. *Excel:*
`=B3-B2` and `=(B3-B2)/B2`. *Why:* the `with_prev` stage lets two columns share the `LAG`. The picture shows the same table.

`LAG` and `LEAD` never reach into another group. So `PARTITION BY store_id` gives each cafe its own series.

**Try it:**

<RunSQL query={`WITH monthly AS (
  SELECT store_id, CAST(DATE_TRUNC('month', ordered_at) AS DATE) AS month, COUNT(*) AS orders
  FROM orders
  GROUP BY store_id, month
),
with_prev AS (
  SELECT store_id, month, orders,
         LAG(orders) OVER (PARTITION BY store_id ORDER BY month) AS prev_orders
  FROM monthly
)
SELECT store_id, month, orders, prev_orders,
       ROUND((orders - prev_orders) * 100.0 / NULLIF(prev_orders, 0), 1) AS pct_change
FROM with_prev
ORDER BY store_id, month;`} />

Expected: 15 rows, 5 columns. Harbor's April has `NULL`: it has no row for March, since it opened on April 1. *Excel:* the
same formulas, restarted for each cafe. The answer to the owner: the chain grew 35.3 percent in April, but that is
Harbor's 123 first orders; Old Town fell 7.5 percent and Campus 17.6 percent.

<details>
<summary>Explain it in your own words: why is January's change NULL, and why is that better than 0?</summary>

A `0` would say that the month before had zero orders, and January would then show a jump of 242. `NULL` says "no
value", and the arithmetic stays `NULL`.

</details>

### 3. A moving average

A frame function averages the current row and the rows around it, as many as `ROWS BETWEEN` says, writes the answer
beside the current row, and then the window moves down one row. `ROWS BETWEEN 6 PRECEDING AND CURRENT ROW` counts rows:
the current one and the six before it. Like `LAG`, it counts rows, not calendar time.

**Try it:** the days around the jump in early April.

<RunSQL query={`WITH daily AS (
  SELECT CAST(ordered_at AS DATE) AS day, COUNT(*) AS orders
  FROM orders
  GROUP BY day
),
smoothed AS (
  SELECT day, orders,
         ROUND(AVG(orders) OVER (ORDER BY day
                                 ROWS BETWEEN 6 PRECEDING AND CURRENT ROW), 2) AS avg_7_days
  FROM daily
)
SELECT day, orders, avg_7_days
FROM smoothed
WHERE day BETWEEN '2026-03-30' AND '2026-04-07'
ORDER BY day;`} />

Expected: 9 rows, 3 columns. *Excel:* `=AVERAGE(B2:B8)` copied down. *Why:* rows are days here because all 181 days from
January 1 to June 30 have orders. On April 4, the day of the jump, 18 orders average out to 10.29: the frame holds March 29
to April 4, 72 orders in all.

`RANGE` measures distance in values instead of counting rows. DuckDB's documentation uses `RANGE` with an `INTERVAL` of
days "to handle any missing days"; ours is `RANGE BETWEEN INTERVAL 6 DAYS PRECEDING AND CURRENT ROW`. *Complete time
series and recursive CTEs* (S28) fills the gaps instead.

**Try it.** Predict first: what will the 7-day average show on January 1, the first day
of the data?

<details>
<summary>Prediction</summary>

4.0, just that day's orders. The frame is cropped to the rows that exist, so on January 1 the average has one value,
and on January 7 it has seven.

</details>

<RunSQL query={`WITH daily AS (
  SELECT CAST(ordered_at AS DATE) AS day, COUNT(*) AS orders
  FROM orders
  GROUP BY day
)
SELECT day, orders,
       ROUND(AVG(orders) OVER (ORDER BY day ROWS BETWEEN 6 PRECEDING AND CURRENT ROW), 2) AS avg_7_days
FROM daily
ORDER BY day
LIMIT 7;`} />

Expected: 7 rows, 3 columns. The first six averages use fewer than seven days; the window is full from the seventh row.

### 4. The `LAST_VALUE` trap

`LAST_VALUE` returns the last value of the frame. If you write no frame, the default frame of S14 applies.

**Try it.** Predict first: what will `last_default` show on the March row?

<details>
<summary>Prediction</summary>

258, March's own orders. With an `ORDER BY` and no frame, the frame ends at the current row (and its peers), so the
last value of the frame is the current row.

</details>

<RunSQL query={`WITH monthly AS (
  SELECT CAST(DATE_TRUNC('month', ordered_at) AS DATE) AS month, COUNT(*) AS orders
  FROM orders
  GROUP BY month
)
SELECT month, orders,
       LAST_VALUE(orders) OVER (ORDER BY month) AS last_default,
       LAST_VALUE(orders) OVER (ORDER BY month
                                ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING) AS last_whole
FROM monthly
ORDER BY month;`} />

Expected: 6 rows, 4 columns. *Why:* widening the frame to `ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING`
reaches the end of the series. `FIRST_VALUE` shows no trap, because the frame always starts at the first row.

### 5. Check the numbers

**Try it:**

<RunSQL query={`WITH monthly AS (
  SELECT CAST(DATE_TRUNC('month', ordered_at) AS DATE) AS month, COUNT(*) AS orders
  FROM orders
  GROUP BY month
)
SELECT SUM(orders) AS total_orders
FROM monthly;`} />

Expected: 1 row, 1 column: `1800`. The monthly counts add up to every order in the dataset, so no row was lost on the
way. The changes of unit 2 reconcile too: -24 + 40 + 91 + 31 - 27 = 111, which is June's 353 minus January's 242. And the
percent change of March by hand, 40 / 218, is 18.3 percent, the same as the query.

<Aside type="tip" title="Remember">

- Build the series first. `LAG` and `LEAD` read the row above and below, in the order of the `ORDER BY` inside `OVER`.
- With no row that far away you get `NULL`, or the default you pass; `NULLIF` guards a division.
- `ROWS BETWEEN` counts rows; `RANGE` measures distance in values.
- `LAST_VALUE` needs a wider frame than the default to see the end of the series.

**Common trap: "a 7-row frame is a 7-day average."** The two agree only while every day has a row. Suppose April 2 had no
orders and so no row: the frame of April 4 would still hold seven rows, and it would reach back to March 28, eight
calendar days. The `RANGE` form above would hold six rows, March 29 to April 4.

</Aside>

## Finish it

<Exercise id="sql-lag-lead-moving-windows-1">

**Compared with the same weekday last week.** Expected: 7 rows, 4 columns: the day, its orders, the orders of the same
weekday a week earlier, and the change.

The first steps are done for you: the `daily` stage, and a `compared` stage that does not compare anything yet. The
query lists the week of April 4 to 10.

<RunSQL query={`WITH daily AS (
  SELECT CAST(ordered_at AS DATE) AS day, COUNT(*) AS orders
  FROM orders
  GROUP BY day
),
compared AS (
  SELECT day, orders
  FROM daily
)
SELECT day, orders
FROM compared
WHERE day BETWEEN '2026-04-04' AND '2026-04-10'
ORDER BY day;`} />

Now finish it: in `compared`, add a column `same_day_last_week` with the orders seven rows earlier, and in the last
`SELECT`, add the change from that value.

<details>
<summary>Hint</summary>

`LAG` takes a second argument for how many rows to look back. A week is seven rows because each row is a day.

</details>

<details>
<summary>Half-solution</summary>

```sql
LAG(orders, ...) OVER (ORDER BY day) AS same_day_last_week;
```

</details>

<Solution>

```sql
WITH daily AS (
  SELECT CAST(ordered_at AS DATE) AS day, COUNT(*) AS orders
  FROM orders
  GROUP BY day
),
compared AS (
  SELECT day, orders,
         LAG(orders, 7) OVER (ORDER BY day) AS same_day_last_week
  FROM daily
)
SELECT day, orders, same_day_last_week,
       orders - same_day_last_week AS change
FROM compared
WHERE day BETWEEN '2026-04-04' AND '2026-04-10'
ORDER BY day;
```

<Solution>

```sql
WITH monthly AS (
  SELECT CAST(DATE_TRUNC('month', ordered_at) AS DATE) AS month, COUNT(*) AS orders
  FROM orders
  GROUP BY month
)
SELECT month, orders,
       ROUND(AVG(orders) OVER (ORDER BY month
                               ROWS BETWEEN 1 PRECEDING AND 1 FOLLOWING), 1) AS avg_3_months
FROM monthly
ORDER BY month;
```

**Spot the flaw.** A colleague wants the change from February to March, and the months after it. The query runs:

<RunSQL query={`WITH monthly AS (
  SELECT CAST(DATE_TRUNC('month', ordered_at) AS DATE) AS month, COUNT(*) AS orders
  FROM orders
  GROUP BY month
)
SELECT month, orders,
       orders - LAG(orders) OVER (ORDER BY month) AS change
FROM monthly
WHERE month >= '2026-03-01'
ORDER BY month;`} />

Expected: 4 rows, 3 columns. Look at the first row, find the flaw and fix it.

<Solution>

March's `change` is `NULL`, not 40. `WHERE` runs before the window function, so February is already gone when `LAG`
looks for the row above, and March becomes the first row of the series. Compute `LAG` in a stage and filter in the
next one, as in unit 2:

```sql
WITH monthly AS (
  SELECT CAST(DATE_TRUNC('month', ordered_at) AS DATE) AS month, COUNT(*) AS orders
  FROM orders
  GROUP BY month
),
with_prev AS (
  SELECT month, orders, LAG(orders) OVER (ORDER BY month) AS prev_orders
  FROM monthly
)
SELECT month, orders, orders - prev_orders AS change
FROM with_prev
WHERE month >= '2026-03-01'
ORDER BY month;
```

| month | orders | change |
|---|---:|---:|
| 2026-03-01 | 258 | 40 |
| 2026-04-01 | 349 | 91 |
| 2026-05-01 | 380 | 31 |
| 2026-06-01 | 353 | -27 |

Expected after the fix: 4 rows, 3 columns, and March shows +40.

</Solution>

</Exercise>
