## The question

The loyalty manager asks:

> Which order came from a customer with no loyalty card? And how many orders did customers other than customer 7 place?

An empty `customer_id` cell in a sheet would mean a walk-in. Three rows of the `orders` table:

| order_id | customer_id | store_id | ordered_at | status | payment_method |
|---:|---:|---:|---|---|---|
| 1334 | 9 | 1 | 2026-02-13 16:33:00 | completed | cash |
| 1335 | NULL | 1 | 2026-02-14 08:59:00 | completed | mobile |
| 1336 | 70 | 2 | 2026-02-14 09:21:00 | completed | mobile |

The second question has a trap.

## Warm-up

Answer from memory before you open anything. Then click to check.

1. In *Filtering rows with WHERE* (S3) you combined tests. Write a query that counts the orders of Campus (`store_id`
   2) that were paid by card or cash.

   <details>
   <summary>Answer</summary>

   ```sql
   SELECT COUNT(*) AS orders
   FROM orders
   WHERE store_id = 2 AND payment_method IN ('card', 'cash');
   ```

   </details>

2. In Excel or Google Sheets (*Numbers are not numbers until you check*, E4), the cell C7 inside `=AVERAGE(C2:C20)` is
   empty. Does `AVERAGE` treat it as a 0?

   <details>
   <summary>Answer</summary>

   No. An empty cell inside the range is skipped, so the average is taken over the cells that hold numbers. A real 0 is
   counted; an empty cell is not.

   </details>

## The big idea

A cell with no value is stored as **NULL**, SQL's mark for "unknown", and any test that touches an unknown value comes
out unknown too.

## Learn by doing

Five small steps. Press Run under each query. Each one works on its own, so you can come back to any step.

### 1. Find the missing value

`IS NULL` is the test for a missing value, and `IS NOT NULL` is its opposite. Both answer true or false, never NULL (the
comparison operators page). Any other comparison with NULL returns NULL, even `NULL = NULL` (DuckDB's NULL values page).

**Try it**:

<RunSQL query={`SELECT * FROM orders WHERE customer_id IS NULL;`} />

Read it: *show the orders whose customer is missing*. Expected: 1 row, 6 columns: order 1335, the walk-in. *Excel:* look
for the empty cell in the customer column. That answers the first question.

**Try it.** Now the test a spreadsheet habit suggests:

<RunSQL query={`SELECT * FROM orders WHERE customer_id = NULL;`} />

Expected: 0 rows, 6 columns, and no error.

*Why:* `customer_id = NULL` is NULL for every row, so `WHERE` drops them all (S3).

### 2. NULL inside a WHERE

`AND`, `OR` and `NOT` work with three answers: true, false and NULL. `NULL AND false` is false, `NULL OR true` is true,
but `NOT NULL` is NULL (the logical operators page). To keep the unknown rows on purpose, ask for them with `IS NULL`.

**Try it.** Before you run the two counts: will they add up to 1,800?

<RunSQL query={`SELECT COUNT(*) AS orders FROM orders WHERE customer_id <> 7;`} />

<RunSQL query={`SELECT COUNT(*) AS orders FROM orders WHERE customer_id = 7;`} />

Expected: 1 row, 1 column each: `1786` and `13`.

*Why:* they make 1,799, one short. A test that gives NULL drops the row just as false does (S3), so a filter on one value
can lose the rows that have no value at all. The first picture shows the same effect on customers 1 to 8 (the figure uses
`referred_by`): neither `= 3` nor `<> 3` keeps a NULL.

### 3. NULL is not zero

A cell can hold a real 0 or an empty text, and a missing value is neither. Most aggregate functions skip NULL (DuckDB's
NULL values page).

**Try it.** Before you run it: which of the three answers is true?

<RunSQL query={`SELECT 0 IS NULL AS zero_is_null, '' IS NULL AS empty_text_is_null, NULL IS NULL AS null_is_null;`} />

Expected: 1 row, 3 columns.

*Why:* only `NULL IS NULL` is true. 0 is a number and `''` is a text with no characters: both are values, and NULL is no
value at all. That is the difference between a real 0 and an empty cell in E4.

**Try it.** Customers 1 to 8: only customer 6 has a referrer, customer 3.

<RunSQL query={`SELECT AVG(referred_by) AS average_referrer
FROM customers
WHERE customer_id <= 8;`} />

Expected: 1 row, 1 column: the value 3, the one value that exists. If NULL counted as 0, the average would be 3 / 8 = 0.375.
*Excel:* the nearest thing to NULL is an empty cell, and `AVERAGE` skips it: Microsoft Support says "those values are
ignored". A SQL aggregate skips NULL the same way, but a comparison does not skip it: it answers NULL.

### 4. NOT IN and a NULL in the list

`x NOT IN (list)` means `NOT (x IN (list))`. When the list holds a NULL, a value that is not in it gets NULL, not true
(DuckDB's `IN` page).

**Try it.** You paste a list of customers who already got a thank-you card from a sheet column with an
empty cell. Which of customers 1 to 8 still need one? First the list without the gap, then with it. Before you run the
second query: how many rows will it return?

<RunSQL query={`SELECT customer_id
FROM customers
WHERE customer_id <= 8 AND customer_id NOT IN (1, 3, 7);`} />

<RunSQL query={`SELECT customer_id
FROM customers
WHERE customer_id <= 8 AND customer_id NOT IN (1, 3, 7, NULL);`} />

Expected: 1 column each, and no error.

*Why:* the first list leaves 5 customers and the second leaves none. `5 NOT IN (1, 3)` is true, but `5 NOT IN (1, 3, NULL)`
is NULL. For customer 2, the test asks whether 2 equals 1, 3, 7 or NULL: three false answers and one NULL give NULL. Keep
NULLs out of the list; later lessons show safer ways to compare two tables.

### 5. Replace NULL with a default, and check

`COALESCE(x, d)` returns the first of its arguments that is not NULL, so it gives `d` when `x` is missing (the utility
functions page).

**Try it**:

<RunSQL query={`SELECT customer_id, referred_by, COALESCE(referred_by, 0) AS referrer_id
FROM customers
WHERE customer_id <= 8
ORDER BY customer_id;`} />

Expected: 8 rows, 3 columns. *Excel:* an `IF` that tests for an empty cell (E6). *Why:* a missing referrer shows as 0.
That is safe here only because no customer has the id 0; keep the original column in the result too, so you can still
tell *nobody* from a real referrer. The default must have the column's type: `COALESCE(referred_by, 'nobody')` fails with
`Could not convert string 'nobody' to INT32`, and the lesson *Computed columns and data types*
shows how to change a type.

Check the walk-in against the total.

**Try it**:

<RunSQL query={`SELECT COUNT(*) AS orders FROM orders WHERE customer_id IS NOT NULL;`} />

Expected: 1 row, 1 column: `1799`. The one walk-in of unit 1 and these 1,799 make the 1,800 orders you counted in S1.
The groups reconcile.

<Aside type="tip" title="Remember">

- NULL means unknown: test it with `IS NULL`, never with `=` or `<>`.
- A comparison with NULL gives NULL, and `WHERE` keeps only true.
- NULL is not 0 or empty text, and most aggregates skip it.
- A NULL in a `NOT IN` list leaves no rows.
- `COALESCE(x, d)` swaps a NULL for a default of the column's type.

**Common trap: "a missing value counts as 0 in a total or an average."** Most SQL aggregate functions ignore NULL (DuckDB's
NULL values page), so the average of unit 3 is 3.0, not 0.375.

</Aside>
