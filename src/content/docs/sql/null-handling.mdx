**NULL** means *unknown*: the value is missing, not zero and not an empty text. It is not a number you can compare.
Any comparison with NULL, including `NULL = NULL`, gives NULL, and a `WHERE` keeps a row only when its condition is
true, so a NULL result drops the row (first picture). `AND` and `OR` can sometimes still give an answer, as in the second
picture: `NULL AND false` is false, and `NULL OR true` is true. The tools:

| SQL | Reads as | In Excel |
|---|---|---|
| `x IS NULL` | the value is missing | an empty cell |
| `x IS NOT NULL` | the value is there | a cell that holds something |
| `COALESCE(x, d)` | `x`, or `d` when `x` is missing | an `IF` that tests for an empty cell (E6) |

## Worked example

Question: **which order has no customer, and how many orders did customers other than customer 7 place?** Run the
notebook's setup cell, then one cell per step. Each step gives the shape of the result to expect.

1. **Find the missing value.**

   ```sql
   SELECT * FROM orders WHERE customer_id IS NULL;
   ```

   Read it: *show the orders whose customer is missing*. Expected: 1 row, 6 columns: order 1335, the walk-in. *Excel:*
   look for the empty cell in the customer column. *Why:* `IS NULL` is the test for a missing value. That answers the
   first question.

2. **Try `= NULL`.**

   ```sql
   SELECT * FROM orders WHERE customer_id = NULL;
   ```

   Expected: 0 rows, 6 columns, and no error. *Why:* `customer_id = NULL` is NULL for every row, so `WHERE` drops them all.
   DuckDB's documentation says any comparison with NULL returns NULL, including `NULL = NULL`.

3. **Meet the first trap.**

   ```sql
   SELECT COUNT(*) AS orders FROM orders WHERE customer_id <> 7;
   ```

   ```sql
   SELECT COUNT(*) AS orders FROM orders WHERE customer_id = 7;
   ```

   Expected: 1 row, 1 column each: `1786` and `13`. *Why:* 1786 + 13 is 1,799, not 1,800. The walk-in order has no
   customer, so `customer_id <> 7` is NULL for it, not true, and the row is dropped.

4. **Ask for the unknown on purpose.**

   ```sql
   SELECT COUNT(*) AS orders
   FROM orders
   WHERE customer_id <> 7 OR customer_id IS NULL;
   ```

   Expected: 1 row, 1 column: `1787`. *Why:* the walk-in is a customer other than customer 7, so say so: `OR ... IS NULL`
   brings its row back. That answers the second question: **1,787 orders**, counting the walk-in and the one canceled order.

5. **See that NULL is not 0 and not empty text.**

   ```sql
   SELECT 0 IS NULL AS zero_is_null, '' IS NULL AS empty_text_is_null, NULL IS NULL AS null_is_null;
   ```

   Expected: 1 row, 3 columns: false, false, true. *Why:* 0 is a number and `''` is a text with no characters; both are
   values. NULL is no value at all. This is the E4 difference between a real 0 and an empty cell. DuckDB's documentation says most aggregate functions ignore NULL, which
   the lesson *Counting and summing: aggregate functions* shows.

6. **Meet the second trap: NOT IN.** You paste a list of customers who already got a thank-you card from a sheet column with an
   empty cell. Which of customers 1 to 8 still need one? First the list without the gap, then with it:

   ```sql
   SELECT customer_id
   FROM customers
   WHERE customer_id <= 8 AND customer_id NOT IN (1, 3, 7);
   ```

   ```sql
   SELECT customer_id
   FROM customers
   WHERE customer_id <= 8 AND customer_id NOT IN (1, 3, 7, NULL);
   ```

   Expected: 5 rows, 1 column, and then 0 rows, 1 column, with no error. *Why:* for customer 2, the test asks whether 2 equals 1, 3, 7 or
   NULL. The first three answers are false, the last is NULL, so the answer is NULL, and `NOT` of NULL is NULL. DuckDB's `IN` page says
   a value that is not in the list gives NULL when the list holds a NULL. So `NOT IN` never keeps a row once a NULL sits in the list.
   Keep NULLs out of the list; later lessons show safer ways to compare two tables.

7. **Replace NULL with a default.**

   ```sql
   SELECT customer_id, referred_by, COALESCE(referred_by, 0) AS referrer_id
   FROM customers
   WHERE customer_id <= 8
   ORDER BY customer_id;
   ```

   Expected: 8 rows, 3 columns. *Why:* `COALESCE` returns the first value that is not NULL, so a missing referrer shows as 0.
   That is safe here only because no customer has the id 0; keep the original column in the result too, so you can still tell *nobody* from a
   real referrer. The default must have the column's type: `COALESCE(referred_by, 'nobody')` fails with
   `Conversion Error: Could not convert string 'nobody' to INT32`, and the lesson *Computed columns and data types* shows how to change a type.

8. **Verify.**

   ```sql
   SELECT COUNT(*) AS orders FROM orders WHERE customer_id IS NOT NULL;
   ```

   Expected: 1 row, 1 column: `1799`. The one walk-in of step 1 and these 1,799 make the 1,800 orders you counted in S1.
   The groups reconcile.

<details>
<summary>Explain it in your own words: why does the filter "customer is not 7" not return the walk-in order?</summary>

The walk-in has no customer, so asking whether it is different from 7 has no answer: the result is NULL, and `WHERE` keeps
only rows whose condition is true. To keep the row, ask for it with `OR customer_id IS NULL`.

</details>
