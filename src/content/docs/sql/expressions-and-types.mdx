This lesson builds on *Filtering rows with WHERE* (S3). So far you have shown stored columns. A query can also calculate
new ones, and every value it works with has a **type**: whole number, decimal, text or date. Press **Run** under any query
on this page.

## The question

The owner is planning a happy hour and asks:

> Take 20 percent off every coffee and tea. What is each item's happy-hour price, to the cent, and can we trust the
> numbers?

In a sheet you would add a column with a formula like `=C2*0.8`. In SQL you write the formula in the `SELECT`. Four of the
ten coffee and tea rows of `products`:

| product_id | product_name | category | unit_price_usd |
|---:|---|---|---:|
| 1 | Espresso | coffee | 3.00 |
| 6 | Cold Brew | coffee | 4.75 |
| 7 | Green Tea | tea | 3.25 |
| 8 | Chai Latte | tea | 4.75 |

   <details>
   <summary>Answer</summary>

   The stored value, `14.25`. A cell has two values: the one it shows and the one it stores, and the formula bar shows
   what is stored.

   </details>

2. In *Filtering rows with WHERE* (S3), write the test that keeps prices from 3.50 to 4.50, both included, in two
   ways.

   <details>
   <summary>Answer</summary>

   `unit_price_usd BETWEEN 3.50 AND 4.50`, or `unit_price_usd >= 3.50 AND unit_price_usd <= 4.50`.

   </details>

new column, and the **type** of the numbers decides what the answer looks like.

## Learn by doing

Five small steps. Press Run under each query. Each one works on its own, so you can come back to any step.

### 1. Calculate a column, and mind the order

An expression combines columns, numbers and operators, and `AS` names the result. The table itself is not changed. When
an expression has several operators, brackets come first, then `*`, `/`, `//` and `%`, then `+` and `-`: in DuckDB,
`2 + 3 * 4` is 14.

**Try it**:

<RunSQL query={`SELECT product_name, unit_price_usd, unit_price_usd * 0.80 AS happy_price_usd
FROM products
WHERE category IN ('coffee', 'tea');`} />

Read it: *take the price times 0.80, for the coffees and teas*. Expected: 10 rows, 3 columns. *Excel:* a new column with
`=C2*0.8`, filled down as in E2: SQL needs no filling, the expression runs for every row. Look at the new column: it shows
four decimals. Unit 2 explains.

**Try it.** The pair price of two items with a 0.50 coupon, and the same calculation with the brackets in the wrong place:

<RunSQL query={`SELECT product_name,
       unit_price_usd * 2 - 0.50 AS pair_price_usd,
       unit_price_usd * (2 - 0.50) AS wrong_pair_usd
FROM products
WHERE product_id <= 3;`} />

Expected: 3 rows, 3 columns.

*Why:* brackets come first, so the second column multiplies the price by 1.5, not by 2. Write the brackets whenever you
are unsure.

### 2. Read the types, and cast to exact cents

Every value has a type, and the types of the inputs decide the type of the answer. `DESCRIBE` shows the type of each
column. A price is a `DECIMAL(6,2)`: exact, up to 6 digits, 2 after the point. Other common types are `INTEGER` (whole
numbers, like `quantity`), `VARCHAR` (text) and `DATE` and `TIMESTAMP` (`ordered_at` is a `TIMESTAMP`). DuckDB's numeric
types page says adding, subtracting or multiplying two decimals gives another decimal, wide enough to hold the exact
answer.

**Try it.** The types of a table, then of a query's result:

<RunSQL query={`DESCRIBE products;`} />

<RunSQL query={`DESCRIBE SELECT product_name, unit_price_usd, unit_price_usd * 0.80 AS happy_price_usd
FROM products
WHERE category IN ('coffee', 'tea');`} />

Expected: 4 rows, 6 columns, and then 3 rows, 6 columns. Read the `column_name` and `column_type` columns. *Excel:* the
formula bar and the format of a cell (E4).

*Why:* the two decimals of 0.80 and the two of the price make four in the exact answer, so the result type has four.

To get cents, change a type on purpose with `CAST(x AS type)` (or `x::type`).

**Try it**:

<RunSQL query={`SELECT product_name, unit_price_usd,
       CAST(unit_price_usd * 0.80 AS DECIMAL(6,2)) AS happy_price_usd
FROM products
WHERE category IN ('coffee', 'tea');`} />

Expected: 10 rows, 3 columns, with two decimals.

*Why:* here every result is already whole cents, so the cast loses nothing. When a result has more decimals than the type
allows, a cast rounds, so look at the numbers before you cast money.

### 3. Why money is not DOUBLE

`DOUBLE` is a **floating-point** type, a second number format next to `DECIMAL`. Unit 2 kept the price a `DECIMAL`; here
the same price goes through `DOUBLE` first.

**Try it.** Before you run it: will every result show clean cents?

<RunSQL query={`SELECT product_name, CAST(unit_price_usd AS DOUBLE) * 0.80 AS happy_price_double
FROM products
WHERE category IN ('coffee', 'tea');`} />

Expected: 10 rows, 2 columns. *Excel:* Microsoft's page says "Excel stores numbers using double-precision": a
floating-point format, as approximate as `DOUBLE`. In SQL you choose the type per column; for money, `DECIMAL`.

*Why:* `DOUBLE` stores an approximation: DuckDB's numeric types page says such calculations are "only approximate", and
that exact money amounts need `DECIMAL`. 4 of the 10 results show stray digits: Cold Brew gives 3.8000000000000003 instead
of 3.80. The picture lines up the same calculation in three types; only the decimal keeps the cents exact.

### 4. Division: `/`, `//` and `%`

`/` keeps the fraction, `//` drops it (integer division), and `%` is the remainder: `9 / 4` is 2.25, `9 // 4` is 2 and
`9 % 4` is 1 (DuckDB's numeric functions page). Dividing a decimal gives a floating-point number, not a decimal (the
numeric types page).

**Try it.** The three lines of order 1001. Before you run it: what will each of the three new columns show for a line
with quantity 1?

<RunSQL query={`SELECT order_item_id, quantity,
       quantity / 2 AS halved,
       quantity // 2 AS pairs,
       quantity % 2 AS single
FROM order_items
WHERE order_id = 1001;`} />

Expected: 3 rows, 5 columns. Order 1001 does not contain the extra-zero line (order 2075).

*Why:* each operator treats the leftover differently, as the picture shows. `quantity / 2.0` avoids integer division
anywhere.

### 5. Cast text, and check

A cast turns text into a number or a date, and a number into text. Dates are written year-month-day, as in DuckDB's date
documentation. When the value does not fit the type, the query stops with an error. `TRY_CAST` is the gentler version: it returns NULL, a
missing value, instead.

**Try it**:

<RunSQL query={`SELECT CAST('4.50' AS DECIMAL(6,2)) AS price,
       CAST('2026-03-31' AS DATE) AS day,
       CAST(1001 AS VARCHAR) AS order_text;`} />

Expected: 1 row, 3 columns. *Excel:* a number stored as text (E4).

**Try it.** `TRY_CAST` on text that is not a number:

<RunSQL query={`SELECT TRY_CAST('abc' AS INTEGER) AS result;`} />

Expected: 1 row, 1 column, holding NULL.

Now check the happy-hour prices. Take the 20 percent off the price and compare with the cents you cast. A mismatch would
show up as a row:

<RunSQL query={`SELECT product_name
FROM products
WHERE category IN ('coffee', 'tea')
  AND unit_price_usd - CAST(unit_price_usd * 0.80 AS DECIMAL(6,2)) <> unit_price_usd * 0.20;`} />

Expected: 0 rows, 1 column: for all 10 items, the price minus the happy-hour price equals 20 percent of the price. Check
one by hand: 3.00 times 0.80 is 2.40.

<Aside type="tip" title="Remember">

- An expression runs once for every row: brackets first, then `*`, `/`, `//` and `%`, then `+` and `-`.
- The types of the inputs decide the type of the answer; `DESCRIBE` shows them.
- Money is `DECIMAL`, which is exact; `DOUBLE` is only approximate.
- `/` keeps the fraction, `//` drops it, `%` is the remainder.
- `CAST` changes a type on purpose, and fails when the value does not fit.

**Common trap: "a stray digit far to the right of the decimal point is harmless, so `DOUBLE` is fine for money."** On
screen it may be, but a comparison sees it. `0.1::DOUBLE + 0.2::DOUBLE = 0.3::DOUBLE` is false (the sum is
0.30000000000000004), while the plain `0.1 + 0.2 = 0.3` is true, because DuckDB reads plain decimal literals as
`DECIMAL`.

</Aside>

SELECT product_name, unit_price_usd,

**Price a pair from a text price list.** A supplier sent a price list in which every column is text. Run this block
first: it creates the table `price_list_text` and shows it.

<RunSQL query={`CREATE OR REPLACE TABLE price_list_text (
  item VARCHAR,
  price_text VARCHAR,
  valid_from_text VARCHAR
);
INSERT INTO price_list_text VALUES
  ('Espresso', '3.00', '2026-07-01'),
  ('Latte', '4.50', '2026-07-01'),
  ('Chai Latte', '4.75', '2026-07-15'),
  ('Croissant', '3.25', '2026-07-15');
SELECT * FROM price_list_text;`} />

The pair price of an item is two items minus a 0.50 coupon. Show the item, its pair price as an exact decimal named
`pair_price_usd`, and the day the price starts as a date named `valid_from`.

Before you run anything, write one sentence (a line that starts with `--` works in the editor): what will the query
return, and what type is each column? Then check the types of `price_list_text` with `DESCRIBE`, and write the query.

Expected shape, to check your sentence against: 4 rows, 3 columns. A first try that multiplies `price_text` directly
stops with an error; read it before you fix it.

<RunSQL query={`-- Write your query here, then press Run.`} />

<details>
<summary>Hint</summary>

`DESCRIBE price_list_text` tells you the type of every column. Cast `price_text` to a decimal and `valid_from_text` to a
date, as in unit 5, then use the pair calculation of unit 1.

</details>

<details>
<summary>Half-solution</summary>

Expected output: *"Four rows with three columns each: the item, a decimal pair price, and a date. The text columns become a decimal and a date."*

</details>

<Solution>

```sql
SELECT item,
       CAST(price_text AS DECIMAL(6,2)) * 2 - 0.50 AS pair_price_usd,
       CAST(valid_from_text AS DATE) AS valid_from
FROM price_list_text;
```

The result is Espresso 5.50 (July 1), Latte 8.50 (July 1), Chai Latte 9.00 (July 15) and Croissant 6.00 (July 15). `DESCRIBE`
shows `VARCHAR` for all three source columns. That is why multiplying `price_text` directly stops with an error that asks for explicit type casts: cast first, then calculate. The result column
`pair_price_usd` is a decimal with two decimals, so the cents survive.

</Solution>

</Exercise>

<Exercise id="sql-expressions-and-types-3">

**Spot the flaw.** A colleague wants half of each line's quantity in order 1001, with decimals such as 0.5, and runs this
query. It gives a table with no error:

<RunSQL query={`SELECT order_item_id, quantity, quantity // 2 AS half_the_quantity
FROM order_items
WHERE order_id = 1001;`} />

Expected: 3 rows, 3 columns. Compare the result with the quantities: is `half_the_quantity` really half? Then fix the query.

<Solution>

`//` is integer division, so it drops the fraction: the lines with quantity 1 give 0 instead of 0.5. Use `/`, which keeps it:

```sql
SELECT order_item_id, quantity, quantity / 2 AS half_the_quantity
FROM order_items
WHERE order_id = 1001;
```

Expected: 3 rows, 3 columns: 0.5, 0.5 and 1.0. In a database where `/` divides whole numbers as whole numbers, write `quantity / 2.0`
to get the same result.

</Solution>

</Exercise>
