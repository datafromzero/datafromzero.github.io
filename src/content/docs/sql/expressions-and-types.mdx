decimal, text, date. The type decides what a calculation gives back, and a wrong type gives wrong cents without an error.

An **expression** is a calculation in the `SELECT`: it takes columns and numbers and returns a value for every row, and
`AS` names the result (S2). The operators are `+`, `-`, `*`, `/` and `%`; the second picture adds `//`. A type name
comes after `CAST(x AS ...)`:

| Type | Holds | Example |
|---|---|---|
| `INTEGER` | whole numbers | `quantity`: 1, 2, 3 |
| `DECIMAL(6,2)` | exact decimals, up to 6 digits, 2 after the point | `unit_price_usd`: 4.75 |
| `DOUBLE` | approximate decimals | `4.75` stored as a float |
| `VARCHAR` | text | `product_name`: Latte |
| `DATE` and `TIMESTAMP` | a day, a day and time | `ordered_at` is a `TIMESTAMP` |

## Worked example

Question: **what is each coffee and tea item's happy-hour price, to the cent?** Run the notebook's setup cell, then one
cell per step. Each step gives the shape of the result to expect.

1. **Calculate a column.**

   ```sql
   SELECT product_name, unit_price_usd, unit_price_usd * 0.80 AS happy_price_usd
   FROM products
   WHERE category IN ('coffee', 'tea');
   ```

   Read it: *take the price times 0.80, for the coffees and teas*. Expected: 10 rows, 3 columns. *Excel:* a new column
   with `=C2*0.8`. *Why:* the expression runs once per row, and `AS` names the result. The table is not changed. Look at
   the new column: it shows four decimals. Step 3 explains.

2. **Mind the order of operations.** The pair price of two items with a 0.50 coupon, and the same calculation with the
   brackets in the wrong place:

   ```sql
   SELECT product_name,
          unit_price_usd * 2 - 0.50 AS pair_price_usd,
          unit_price_usd * (2 - 0.50) AS wrong_pair_usd
   FROM products
   WHERE product_id <= 3;
   ```

   Expected: 3 rows, 3 columns. *Why:* multiplication and division come before addition and subtraction, as in a
   sheet formula, and brackets come first. This is standard SQL, and the results show it: the second column
   multiplies the price by 1.5, not by 2. Write the brackets whenever you are unsure.

3. **Read the types.** The schema of a table, then the types of a query's result:

   ```sql
   DESCRIBE products;
   ```

   ```sql
   DESCRIBE SELECT product_name, unit_price_usd, unit_price_usd * 0.80 AS happy_price_usd
   FROM products
   WHERE category IN ('coffee', 'tea');
   ```

   Expected: 4 rows, 6 columns, and then 3 rows, 6 columns. Read the `column_name` and `column_type` columns: `unit_price_usd`
   is `DECIMAL(6,2)`, and `happy_price_usd` is `DECIMAL(9,4)`. *Excel:* the formula bar and the format of a cell (E4).
   *Why:* `DECIMAL` stores exact decimals; multiplying two of them gives a decimal with as many digits as the exact answer
   needs, according to DuckDB's documentation, so the two decimals of 0.80 and the two of the price become four.

4. **Cast to exact cents.**

   ```sql
   SELECT product_name, unit_price_usd,
          CAST(unit_price_usd * 0.80 AS DECIMAL(6,2)) AS happy_price_usd
   FROM products
   WHERE category IN ('coffee', 'tea');
   ```

   Expected: 10 rows, 3 columns, with two decimals. *Why:* `CAST(x AS type)` converts a value to another type (the short form is `x::type`),
   and `DECIMAL(6,2)` is the type of a price. Here every result is already whole cents, so the cast loses nothing. When a result has
   more decimals than the type allows, a cast rounds, so look at the numbers before you cast money.

5. **See why money is not DOUBLE.**

   ```sql
   SELECT product_name, CAST(unit_price_usd AS DOUBLE) * 0.80 AS happy_price_double
   FROM products
   WHERE category IN ('coffee', 'tea');
   ```

   Expected: 10 rows, 2 columns. *Why:* `DOUBLE` stores an approximation, and 4 of the 10 results show stray digits: Cold Brew gives
   3.8000000000000003 instead of 3.80. DuckDB's documentation says that adding, subtracting and multiplying `DOUBLE` values is only
   approximate, and to use `DECIMAL` for monetary amounts. One detail to remember: dividing a decimal gives a `DOUBLE`.

6. **Meet integer division.**

   ```sql
   SELECT order_item_id, quantity,
          quantity / 2 AS halved,
          quantity // 2 AS pairs,
          quantity % 2 AS single
   FROM order_items
   WHERE order_id = 1001;
   ```

   Expected: 3 rows, 5 columns (the second picture). *Why:* in DuckDB, `/` keeps the fraction (`1 / 2` is 0.5) and `//` is integer
   division, which drops it (`1 // 2` is 0). `%` is the remainder. Order 1001 does not contain the extra-zero line (order 2075).
   `quantity / 2.0` avoids integer division anywhere.

7. **Cast text to a number or a date, and back.**

   ```sql
   SELECT CAST('4.50' AS DECIMAL(6,2)) AS price,
          CAST('2026-03-31' AS DATE) AS day,
          CAST(1001 AS VARCHAR) AS order_text;
   ```

   Expected: 1 row, 3 columns. *Excel:* a number stored as text (E4). *Why:* text can be turned into a number or a date,
   and a number into text. Dates are written year-month-day, as in DuckDB's date documentation. Text that does not fit stops the query
   with an error, which is better than a wrong number.

8. **Verify.** Take the 20 percent off the price and compare with the cents you cast. A mismatch would show up as a row:

   ```sql
   SELECT product_name
   FROM products
   WHERE category IN ('coffee', 'tea')
     AND unit_price_usd - CAST(unit_price_usd * 0.80 AS DECIMAL(6,2)) <> unit_price_usd * 0.20;
   ```

   Expected: 0 rows, 1 column: for all 10 items, the price minus the happy-hour price equals 20 percent of the price. Check one by hand: 3.00
   times 0.80 is 2.40.

<details>
<summary>Explain it in your own words: why is `DECIMAL(6,2)` a better type for a price than `DOUBLE`?</summary>

`DECIMAL(6,2)` stores the price exactly, to the cent, and adding, subtracting and multiplying decimals stays exact.
`DOUBLE` stores an approximation, so a price like 3.80 can come back as 3.8000000000000003.

</details>

<Exercise id="sql-expressions-and-types-3">

**Spot the flaw.** A colleague wants half of each line's quantity in order 1001, with decimals such as 0.5, and runs this
query. It gives a table with no error:

```sql
SELECT order_item_id, quantity, quantity // 2 AS half_the_quantity
FROM order_items
WHERE order_id = 1001;
```

Expected: 3 rows, 3 columns. Compare the result with the quantities: is `half_the_quantity` really half? Then fix the query.

<Solution>

`//` is integer division, so it drops the fraction: the lines with quantity 1 give 0 instead of 0.5. Use `/`, which keeps it:

```sql
SELECT order_item_id, quantity, quantity / 2 AS half_the_quantity
FROM order_items
WHERE order_id = 1001;
```

Expected: 3 rows, 3 columns: 0.5, 0.5 and 1.0. In a database where `/` divides whole numbers as whole numbers, write `quantity / 2.0`
to get the same result.

</Solution>
