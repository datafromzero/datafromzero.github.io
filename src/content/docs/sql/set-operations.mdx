## The question

The owner of the cafes asks:

> Harbor opened on April 1. Of the customers who ordered there, how many had already ordered at the other two cafes, and
> how many are new to us? And which customers have tried every kind of product?

Three customers, and whether each was seen before April and at Harbor:

| customer_id | ordered before April | ordered at Harbor |
|---:|---|---|
| 1 | yes | no |
| 2 | yes | yes |
| 13 | no | yes |

## Warm-up

From memory first, then click to check.

1. In *Subqueries and EXISTS* (S23), write the query that counts the customers who have at least one order.

   <details>
   <summary>Answer</summary>

   ```sql
   SELECT COUNT(*) AS ordered
   FROM customers c
   WHERE EXISTS (SELECT 1 FROM orders o WHERE o.customer_id = c.customer_id);
   ```

   It returns `145`; the other 5 customers never ordered.

   </details>

2. In S23, why did `customer_id NOT IN (SELECT customer_id FROM orders)` return no rows?

   <details>
   <summary>Answer</summary>

   The list holds an empty `customer_id` (the walk-in order 1335). With a `NULL` in the list, `NOT IN` never becomes
   true. Keep that in mind: an empty value can also slip into a set.

   </details>

## The big idea

A **set operation** takes two lists of rows, such as the customers from two queries, and keeps whole rows by where they appear: in both lists, in either, or in only one.

## Learn by doing

Five small steps. Each gives you one idea, then you try it in the editor under it.

### 1. Write the two lists

Call the customers who ordered before April **A**, and the ones who ordered at Harbor **B**. Each is a **set**: a list where every customer appears once, which is what `DISTINCT` gives. "Ordered" means any order, the canceled one included.

The walk-in order 1335 (February 14) has no customer, so its `customer_id` is empty (`NULL`). A leaves it out with `IS NOT NULL`.

**Try it**: list A.

<RunSQL query={`SELECT DISTINCT customer_id
FROM orders
WHERE ordered_at < DATE '2026-04-01' AND customer_id IS NOT NULL
ORDER BY customer_id;`} />

Expected: 97 rows, 1 column. Now list B.

<RunSQL query={`SELECT DISTINCT customer_id
FROM orders
WHERE store_id = 3
ORDER BY customer_id;`} />

Expected: 90 rows, 1 column.

*Why:* a set has no repeats, so each query gives one row per customer. Without the `IS NOT NULL`, A would hold one empty row.

### 2. In both, or in only one

`INTERSECT` keeps the rows found in both lists. `EXCEPT` keeps the rows of the first list that are not in the second, so swapping the lists changes the answer. It is the anti join of S20 and S23, written as sets.

Both compare whole rows, and two `NULL`s count as the same row here, unlike in `=` (S19).

**Try it**: in both A and B.

<RunSQL query={`SELECT customer_id FROM orders
WHERE ordered_at < DATE '2026-04-01' AND customer_id IS NOT NULL
INTERSECT
SELECT customer_id FROM orders
WHERE store_id = 3
ORDER BY customer_id;`} />

Expected: 60 rows, 1 column; the first is customer 2. *Why:* the `ORDER BY` goes last and sorts the whole result.

**Try it**: in A but not in B.

<RunSQL query={`SELECT customer_id FROM orders
WHERE ordered_at < DATE '2026-04-01' AND customer_id IS NOT NULL
EXCEPT
SELECT customer_id FROM orders
WHERE store_id = 3
ORDER BY customer_id;`} />

Expected: 37 rows, 1 column; the first is customer 1. Now swap the two queries, for B without A.

<RunSQL query={`SELECT customer_id FROM orders
WHERE store_id = 3
EXCEPT
SELECT customer_id FROM orders
WHERE ordered_at < DATE '2026-04-01' AND customer_id IS NOT NULL
ORDER BY customer_id;`} />

Expected: 30 rows, 1 column; the first is customer 13. *Why:* the 30 are Harbor customers not seen before April: new to us. The 37 never came to Harbor.

One more, to see the `NULL` rule.

<RunSQL query={`SELECT NULL INTERSECT SELECT NULL;`} />

Expected: 1 row, 1 column. *Why:* the two empty values count as one row, so `INTERSECT` keeps it. With `=` they would never match.

### 3. Stack the lists

`UNION` stacks two lists and removes repeated rows. `UNION ALL` stacks them exactly as they are. `INTERSECT` and `EXCEPT` also remove repeats (the documentation calls this set semantics): only the `ALL` variants keep them. That is why unit 2 needed no `DISTINCT`.

**Try it**. You saw 60 customers in both lists. Before you run these two: how many rows will each return?

<RunSQL query={`SELECT COUNT(*) AS union_rows
FROM (
  SELECT DISTINCT customer_id FROM orders
  WHERE ordered_at < DATE '2026-04-01' AND customer_id IS NOT NULL
  UNION
  SELECT DISTINCT customer_id FROM orders WHERE store_id = 3
);`} />

<RunSQL query={`SELECT COUNT(*) AS union_all_rows
FROM (
  SELECT DISTINCT customer_id FROM orders
  WHERE ordered_at < DATE '2026-04-01' AND customer_id IS NOT NULL
  UNION ALL
  SELECT DISTINCT customer_id FROM orders WHERE store_id = 3
);`} />

Expected: 1 row, 1 column each: 127 and 187. *Excel:* `UNIQUE` (E19, *Spilling results with FILTER, SORT and UNIQUE*) is the repeat-removing half of `UNION`: put one list under the other, and `UNIQUE` over the pasted range keeps each value once.

*Why:* `UNION ALL` does not look for repeats, so use it when you want every row, or when the parts cannot overlap.

<details>
<summary>Explain it in your own words: why is 187 more than 127?</summary>

187 is 97 + 90, every row of both lists. The 60 customers who are in both lists are in that sum twice, so taking the repeats out removes 60 rows: 127.

</details>

### 4. Line up the columns

Set operations match columns by position, not by name. Both queries need the same number of columns, and the result takes its names from the first query. When the types differ, DuckDB casts where it can; for `UNION`, the documentation says it throws an error when it cannot.

**Try it**: a total row under the three stores.

<RunSQL query={`SELECT s.store_name, COUNT(*) AS orders
FROM orders o
JOIN stores s ON s.store_id = o.store_id
GROUP BY s.store_name
UNION ALL
SELECT 'All stores', COUNT(*)
FROM orders
ORDER BY orders;`} />

Expected: 4 rows, 2 columns; the last is `All stores`, 1800. *Why:* both queries give text, then a number.

Now give one query a different number of columns.

<RunSQL query={`SELECT 1 AS a, 2 AS b
UNION ALL
SELECT 3;`} />

Expected: an error saying that set operations need the same number of result columns.

### 5. "Every" is a count

For a long or changing list, "every" is easier as a count than as a chain of `INTERSECT`s. Count the different categories each customer bought with `COUNT(DISTINCT …)`, and compare with the number of categories on the menu.

**Try it**: customers who bought from every category, completed orders only.

<RunSQL query={`SELECT o.customer_id, COUNT(DISTINCT p.category) AS categories
FROM orders o
JOIN order_items oi ON oi.order_id = o.order_id
JOIN products p ON p.product_id = oi.product_id
WHERE o.status = 'completed' AND o.customer_id IS NOT NULL
GROUP BY o.customer_id
HAVING COUNT(DISTINCT p.category) = (SELECT COUNT(DISTINCT category) FROM products)
ORDER BY o.customer_id;`} />

Expected: 111 rows, 2 columns. *Why:* the joins repeat a category once per line, so `DISTINCT` counts each once (S21). The number to reach comes from a scalar subquery (S23), so a fifth category would not break the query.

<Aside type="tip" title="Remember">

- A set operation compares whole rows from two queries.
- `INTERSECT`: in both. `EXCEPT`: in the first only, so the order matters. `UNION`: in either, once. `UNION ALL`: every row, repeats kept.
- Columns line up by position, and the names come from the first query.
- For "every", compare `COUNT(DISTINCT …)` with the total.

**Common trap: "`UNION` is a join."** A join pairs rows and puts the columns of two tables side by side. `UNION` puts one result under the other: the columns stay those of the first query, and only the rows change.

</Aside>

   <details>
   <summary>Answer</summary>

<Exercise id="sql-set-operations-3">

**Spot the flaw.** A colleague wants the customer and store pairs that appear both before and after April, and writes:

<RunSQL query={`SELECT customer_id, store_id FROM orders WHERE ordered_at < DATE '2026-04-01'
INTERSECT
SELECT store_id, customer_id FROM orders WHERE ordered_at >= DATE '2026-04-01'
ORDER BY customer_id, store_id;`} />

Expected from that query: 2 rows, 2 columns, with no error. What went wrong, and what is the right result?

<Solution>

Both columns are integers, so DuckDB lines them up by position without complaint: it compares the first query's `customer_id`
with the second query's `store_id`, and `store_id` with `customer_id`. The question it answers, "is there a row after
April where the store number is this customer and the customer number is this store?", is nonsense that two rows happen
to satisfy. Put the columns in the same order:

```sql
SELECT customer_id, store_id FROM orders WHERE ordered_at < DATE '2026-04-01'
INTERSECT
SELECT customer_id, store_id FROM orders WHERE ordered_at >= DATE '2026-04-01'
ORDER BY customer_id, store_id;
```

Expected: 92 rows, 2 columns. A mismatch of counts raises an error; a swap of same-typed columns gives a plausible wrong
answer, so read the column lists side by side.

</Solution>
