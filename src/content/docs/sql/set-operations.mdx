A join pairs rows; a **set operation** stacks or compares whole results: customers in one list, in the other, in both,
or in only one. It works on customers because a customer is the same row of the same table in every list.

Python. Each query sits between `con.sql("""` and `""").show()`: only the text inside the triple quotes is SQL. The

## Warm-up

Answer from memory before you open anything. Then click to check.

1. In *Subqueries and EXISTS* (S23), write the query that counts the customers who have at least one order.

   <details>
   <summary>Answer</summary>

   ```sql
   SELECT COUNT(*) AS ordered
   FROM customers c
   WHERE EXISTS (SELECT 1 FROM orders o WHERE o.customer_id = c.customer_id);
   ```

   It returns `145`; the other 5 customers never ordered.

   </details>

2. In S23, why did `customer_id NOT IN (SELECT customer_id FROM orders)` return no rows?

   <details>
   <summary>Answer</summary>

   The list holds an empty `customer_id` (the walk-in order 1335). With a `NULL` in the list, `NOT IN` never becomes
   true. Keep that in mind: an empty value can also slip into a set.

   </details>

## The question

The owner of the cafes asks:

> Harbor opened on April 1. Of the customers who ordered there, how many had already ordered at the other two cafes, and
> how many are new to us? And which customers have tried every kind of product?

For three customers, were they seen before April, and at Harbor?

| customer_id | ordered before April | ordered at Harbor |
|---:|---|---|
| 1 | yes | no |
| 2 | yes | yes |
| 13 | no | yes |

By the end you will have both counts, the customers who tried everything, and the rule for lining up the columns of two
queries.

Call the customers who ordered before April **A**, and those who ordered at Harbor **B**.

| Operator | Returns | Duplicates |
|---|---|---|
| `A UNION B` | rows in A, in B or in both | removed |
| `A UNION ALL B` | every row of A, then every row of B | kept |
| `A INTERSECT B` | rows in both | removed |
| `A EXCEPT B` | rows of A that are not in B | removed |

- **Columns match by position.** The DuckDB documentation says the queries need the same number of columns, matches them by
  position and takes the result's names from the first query. Types are cast when that is possible, and the operation
  fails when it is not. The names of the second query play no part. (`UNION BY NAME` matches by name; it is not used here.)
- **Order matters for `EXCEPT`**: `A EXCEPT B` is not `B EXCEPT A`. It is the anti join of S20 and S23, written as sets.
- **Coverage** ("every category") is a different pattern: count the different categories each customer bought, and keep
  those whose count equals the number of categories. The second picture shows it.

## Worked example

Question: **how many Harbor customers had ordered before April, how many had not, and who bought from every category?**
Run the notebook's setup cell, then one cell per step. Each step gives the shape of the result to expect. "Ordered"
means any order, the canceled one included, and the sets hold customers: the walk-in order 1335 (February 14) has no
customer, so set A filters it out.

1. **Write the two sets as two queries.** A:

   ```sql
   SELECT DISTINCT customer_id
   FROM orders
   WHERE ordered_at < DATE '2026-04-01' AND customer_id IS NOT NULL
   ORDER BY customer_id;
   ```

   Expected: 97 rows, 1 column. B:

   ```sql
   SELECT DISTINCT customer_id
   FROM orders
   WHERE store_id = 3
   ORDER BY customer_id;
   ```

   Expected: 90 rows, 1 column. *Why:* a set has no repeats, so each query gives one row per customer. Without the
   `IS NOT NULL`, set A would hold one empty row.

2. **INTERSECT: in both.**

   ```sql
   SELECT customer_id FROM orders
   WHERE ordered_at < DATE '2026-04-01' AND customer_id IS NOT NULL
   INTERSECT
   SELECT customer_id FROM orders
   WHERE store_id = 3
   ORDER BY customer_id;
   ```

   Expected: 60 rows, 1 column; the first is customer 2. *Why:* `INTERSECT` removes duplicates itself, so no `DISTINCT`
   is needed. The `ORDER BY` goes last and sorts the whole result.

3. **EXCEPT, in both directions.** The first returns A without B:

   ```sql
   SELECT customer_id FROM orders
   WHERE ordered_at < DATE '2026-04-01' AND customer_id IS NOT NULL
   EXCEPT
   SELECT customer_id FROM orders
   WHERE store_id = 3
   ORDER BY customer_id;
   ```

   Expected: 37 rows, 1 column; the first is customer 1. Swap the two queries for B without A: 30 rows, 1 column; the
   first is customer 13. *Why:* the 30 are Harbor customers not seen before April: new to us. The 37 never came to Harbor.

4. **UNION and UNION ALL.** Count the stacked rows of the two de-duplicated sets, once with each operator:

   ```sql
   SELECT COUNT(*) AS union_rows
   FROM (
     SELECT DISTINCT customer_id FROM orders
     WHERE ordered_at < DATE '2026-04-01' AND customer_id IS NOT NULL
     UNION
     SELECT DISTINCT customer_id FROM orders WHERE store_id = 3
   );
   ```

   Replace `UNION` with `UNION ALL` and run it again. Expected: 1 row, 1 column each time. *Why:* `UNION` gives each
   customer once: 127. `UNION ALL` stacks the lists as they are, so a customer in both appears twice: 187, which is
   97 + 90. It does not look for duplicates, so use it when you want every row, or when the parts cannot overlap.

5. **Line up the columns: a total row.**

   ```sql
   SELECT s.store_name, COUNT(*) AS orders
   FROM orders o
   JOIN stores s ON s.store_id = o.store_id
   GROUP BY s.store_name
   UNION ALL
   SELECT 'All stores', COUNT(*)
   FROM orders
   ORDER BY orders;
   ```

   Expected: 4 rows, 2 columns; the last is `All stores`, 1800. *Why:* both queries give text, then a number; the
   names come from the first. A different number of columns stops with `Binder Error: Set operations can only apply to
   expressions with the same number of result columns`. The same count in a different order does not stop: Exercise 3.

6. **Coverage: bought from every category.** Completed orders only.

   ```sql
   SELECT o.customer_id, COUNT(DISTINCT p.category) AS categories
   FROM orders o
   JOIN order_items oi ON oi.order_id = o.order_id
   JOIN products p ON p.product_id = oi.product_id
   WHERE o.status = 'completed' AND o.customer_id IS NOT NULL
   GROUP BY o.customer_id
   HAVING COUNT(DISTINCT p.category) = (SELECT COUNT(DISTINCT category) FROM products)
   ORDER BY o.customer_id;
   ```

   Expected: 111 rows, 2 columns. *Why:* the joins repeat a category once per line, so `DISTINCT` counts each once (S21).
   The number to reach comes from a scalar subquery (S23), so a fifth category would not break the query.

7. **Verify.** The four sizes of steps 1 to 4 in one row:

   ```sql
   WITH before_april AS (
     SELECT DISTINCT customer_id FROM orders
     WHERE ordered_at < DATE '2026-04-01' AND customer_id IS NOT NULL
   ),
   at_harbor AS (
     SELECT DISTINCT customer_id FROM orders WHERE store_id = 3
   )
   SELECT (SELECT COUNT(*) FROM before_april) AS a,
          (SELECT COUNT(*) FROM at_harbor) AS b,
          (SELECT COUNT(*) FROM (SELECT * FROM before_april INTERSECT SELECT * FROM at_harbor)) AS in_both,
          (SELECT COUNT(*) FROM (SELECT * FROM before_april UNION SELECT * FROM at_harbor)) AS in_either;
   ```

   Expected: 1 row, 4 columns: `97 | 90 | 60 | 127`. Answer: **of the 90 Harbor customers, 60 had ordered before April and
   30 had not.** Checks: 97 + 90 − 60 = 127; 60 + 37 = 97 and 60 + 30 = 90.

   For coverage, count the customers by how many categories they bought:

   ```sql
   SELECT categories, COUNT(*) AS customers
   FROM (
     SELECT o.customer_id, COUNT(DISTINCT p.category) AS categories
     FROM orders o
     JOIN order_items oi ON oi.order_id = o.order_id
     JOIN products p ON p.product_id = oi.product_id
     WHERE o.status = 'completed' AND o.customer_id IS NOT NULL
     GROUP BY o.customer_id
   ) AS per_customer
   GROUP BY categories
   ORDER BY categories;
   ```

   Expected: 4 rows, 2 columns: 1 category 4 customers, 2 categories 9, 3 categories 20, 4 categories 111. They add up to
   144, the 145 customers who ordered minus customer 42, whose only order was canceled.

<details>
<summary>Explain it in your own words: why is 187 more than 127?</summary>

`UNION ALL` keeps a customer once for each list that holds them. The 60 customers in both lists are counted twice;
`UNION` counts them once, and 187 − 60 = 127.

</details>

## Check yourself

Without looking back: what do `UNION`, `UNION ALL`, `INTERSECT` and `EXCEPT` return, and how does DuckDB line up the
columns?

<details>
<summary>Answer</summary>

`UNION`: rows in either, once each. `UNION ALL`: every row of both, duplicates kept. `INTERSECT`: rows in both.
`EXCEPT`: rows of the first that are not in the second. The queries need the same number of columns, matched by position,
with the names of the first.

</details>

<Exercise id="sql-set-operations-3">

**Spot the flaw.** A colleague wants the customer and store pairs that appear both before and after April, and writes:

```sql
SELECT customer_id, store_id FROM orders WHERE ordered_at < DATE '2026-04-01'
INTERSECT
SELECT store_id, customer_id FROM orders WHERE ordered_at >= DATE '2026-04-01';
```

Expected from that query: 2 rows, 2 columns, with no error. What went wrong, and what is the right result?

<Solution>

Columns match by position, not by name. Both columns are integers, so DuckDB compares the first query's `customer_id`
with the second query's `store_id`, and `store_id` with `customer_id`. The question it answers, "is there a row after
April where the store number is this customer and the customer number is this store?", is nonsense that two rows happen
to satisfy. Put the columns in the same order:

```sql
SELECT customer_id, store_id FROM orders WHERE ordered_at < DATE '2026-04-01'
INTERSECT
SELECT customer_id, store_id FROM orders WHERE ordered_at >= DATE '2026-04-01';
```

Expected: 92 rows, 2 columns. A mismatch of counts raises an error; a swap of same-typed columns gives a plausible wrong
answer, so read the column lists side by side.

</Solution>

</Exercise>
