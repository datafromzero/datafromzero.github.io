## The question

The owner of the cafes asks:

> In the first week of January, how many orders did each cafe take each day, how many so far, and what share of the
> day's orders did each cafe take?

Only the two older cafes are open in January: store 1 is Old Town and store 2 is Campus (Harbor, store 3, opens on
April 1). Grouping by day and store gives one row per day and cafe. The top of that table:

| day | store_id | orders |
|---|---:|---:|
| 2026-01-01 | 1 | 2 |
| 2026-01-01 | 2 | 2 |
| 2026-01-02 | 1 | 3 |
| 2026-01-02 | 2 | 4 |

There are 14 rows: 7 days times 2 cafes. In Excel you would add a running-total column and a share column beside
these rows, and no row would go away. A **window function** does the same in SQL. By the end you will have both
columns, and you will know why a running total can show the same number on two rows.

`GROUP BY` collapses: seven rows go in, one comes out. A window function keeps all seven and adds a value computed
from related rows. The part after `OVER` describes which rows are related:

- `PARTITION BY store_id` splits the rows into groups, one block per cafe. The function works inside each block.
  Leave it out and the whole result is one block; `OVER ()` with nothing inside means exactly that.
- `ORDER BY day` inside `OVER` puts each block in order and makes the function work from the first row up to the
  current row. That is a running total.
- The **frame** is the set of rows the function uses for the current row. With an `ORDER BY` and nothing else
  written, DuckDB's default frame runs from the first row of the block to the current row, including every row that
  ties with the current row on the `ORDER BY` value (its peers). Step 6 shows what that means.

Window functions run after `WHERE` and `GROUP BY` (*How a query runs: the order of the clauses*, S12), so they add
columns and never remove rows. The same ideas exist in the spreadsheet; this table assumes the columns day, store_id
and orders in A, B and C, with data in rows 2 to 15:

| SQL | Reads as | In Excel or Google Sheets |
|---|---|---|
| `SUM(orders) OVER (PARTITION BY store_id)` | the cafe's total beside every row | `=SUMIF($B$2:$B$15,B2,$C$2:$C$15)` |
| `SUM(orders) OVER (PARTITION BY store_id ORDER BY day)` | a running total inside each cafe | `=SUM(C$2:C2)`, copied down and restarted at each cafe's first row |
| `orders * 100.0 / SUM(orders) OVER (PARTITION BY day)` | the row's share of its day | `=C2/SUMIF($A$2:$A$15,A2,$C$2:$C$15)` |

The `$` locks part of a reference when you copy a formula: in `C$2` the row stays 2, so the range `C$2:C2` grows by
one row as you copy it down. `SUM` and `SUMIF` exist in both Excel and Google Sheets.

## Worked example

Question: **for the first week of January, what share of each day did each cafe take, and how many orders had each
cafe taken by the end of each day?** Run the notebook's setup cell, then one cell per step. Each step names the Excel
action it replaces and the shape of the result to expect.

1. **Collapse with `GROUP BY`.**

   ```sql
   SELECT store_id, COUNT(*) AS orders
   FROM orders
   WHERE ordered_at >= '2026-01-01' AND ordered_at < '2026-01-08'
   GROUP BY store_id
   ORDER BY store_id;
   ```

   Read it: *count the week's orders for each store*. Expected: 2 rows, 2 columns: store 1 with 26 orders and store 2
   with 24. *Excel:* a COUNTIF for each store. *Why:* this is the collapsed view, 50 orders in 2 rows. Keep both
   numbers for step 7.

2. **Keep the rows with a window function.**

   ```sql
   SELECT order_id, store_id,
          COUNT(*) OVER (PARTITION BY store_id) AS store_orders
   FROM orders
   WHERE ordered_at >= '2026-01-01' AND ordered_at < '2026-01-08'
   ORDER BY order_id
   LIMIT 5;
   ```

   Read it: *beside each order, put the number of orders of its store this week*. Expected: 5 rows, 3 columns; order 1001
   was taken at store 2, so `store_orders` shows 24 beside it. *Excel:* the SUMIF column from the table above.
   *Why:* `OVER (PARTITION BY store_id)` leaves every row in place and adds the group's count. `WHERE` runs first, so
   only the week's orders are counted; `LIMIT` runs last, so it only trims the display.

3. **Build the daily table.**

   ```sql
   WITH daily AS (
     SELECT CAST(ordered_at AS DATE) AS day, store_id, COUNT(*) AS orders
     FROM orders
     WHERE ordered_at >= '2026-01-01' AND ordered_at < '2026-01-08'
     GROUP BY day, store_id
   )
   SELECT day, store_id, orders
   FROM daily
   ORDER BY day, store_id;
   ```

   Expected: 14 rows, 3 columns, the table from the question. *Why:* the grain is one row per day and cafe (*Readable
   queries with CTEs*, S13). `CAST(ordered_at AS DATE)` drops the time of day and keeps the date (*Working with dates
   and time*, S11). Steps 4 to 6 start with this same `daily` stage, and the notebook repeats it in each cell.

4. **Add each cafe's share of the day.**

   ```sql
   WITH daily AS (
     SELECT CAST(ordered_at AS DATE) AS day, store_id, COUNT(*) AS orders
     FROM orders
     WHERE ordered_at >= '2026-01-01' AND ordered_at < '2026-01-08'
     GROUP BY day, store_id
   )
   SELECT day, store_id, orders,
          SUM(orders) OVER (PARTITION BY day) AS day_total,
          ROUND(orders * 100.0 / SUM(orders) OVER (PARTITION BY day), 1) AS share_pct
   FROM daily
   ORDER BY day, store_id;
   ```

   Read it: *beside each row, put the day's total orders, and this row's percent of it*. Expected: 14 rows, 5 columns. On
   January 1 each cafe has 50.0 percent; on January 6 Old Town has 71.4 percent (5 of 7 orders). *Excel:* the
   SUMIF share column. *Why:* `PARTITION BY day` makes the two rows of one day a block, so the denominator is the
   day's total. `100.0` and `ROUND(..., 1)` give a percent with one decimal.

5. **Add a running total for each cafe.**

   ```sql
   WITH daily AS (
     SELECT CAST(ordered_at AS DATE) AS day, store_id, COUNT(*) AS orders
     FROM orders
     WHERE ordered_at >= '2026-01-01' AND ordered_at < '2026-01-08'
     GROUP BY day, store_id
   )
   SELECT store_id, day, orders,
          SUM(orders) OVER (PARTITION BY store_id ORDER BY day) AS running_total
   FROM daily
   ORDER BY store_id, day;
   ```

   Expected: 14 rows, 4 columns; store 1 ends at 26 and store 2 at 24. *Excel:* `=SUM(C$2:C2)` copied down, restarted at
   each cafe. *Why:* `PARTITION BY store_id` restarts the total for each cafe, and `ORDER BY day` makes each row's
   total the sum of the rows up to its own day.

6. **Predict the default frame, then run it.** On January 1 both cafes have 2 orders. Before you run the query,
   predict what `default_frame` will show on each of those two rows.

   <details>
   <summary>Prediction</summary>

   Both rows show 4. `ORDER BY day` cannot tell the two January 1 rows apart: they are peers, and the default frame
   includes all peers of the current row, so each row's frame holds both rows (2 + 2). `row_by_row` breaks the tie
   with `store_id` and counts rows, so it shows 2 and then 4.

   </details>

   ```sql
   WITH daily AS (
     SELECT CAST(ordered_at AS DATE) AS day, store_id, COUNT(*) AS orders
     FROM orders
     WHERE ordered_at >= '2026-01-01' AND ordered_at < '2026-01-08'
     GROUP BY day, store_id
   )
   SELECT day, store_id, orders,
          SUM(orders) OVER (ORDER BY day) AS default_frame,
          SUM(orders) OVER (ORDER BY day, store_id
                            ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW) AS row_by_row
   FROM daily
   ORDER BY day, store_id;
   ```

   Expected: 14 rows, 5 columns. *Why:* the two columns differ on the first row of each day, because there are two cafes
   and so two peers a day. `default_frame` answers "how many orders by the end of this day", the same on both rows. `row_by_row`
   answers "how many orders by this row", which depends on the tie-breaker you chose. Pick the one your question
   needs.

7. **Verify.** Four checks, no new query. Steps 3 to 6 all return 14 rows, as the daily table has: a window function
   never changes the row count. In step 5 the last running totals, 26 and 24, equal the counts of step 1. In step 4 the two
   shares of each day add to 100 (January 2: 42.9 and 57.1). And the last row of step 6 shows 50 in both columns: 26 + 24, every order
   of the week.

<details>
<summary>Explain it in your own words: why does step 2 return 5 rows when step 1 returned 2?</summary>

`GROUP BY` replaces the rows of a group by one summary row. `OVER (PARTITION BY ...)` computes the same summary but
copies it beside each original row, so no row disappears. `LIMIT 5` then keeps five of them.

</details>

Expected output: *"Three payment methods, each with one row for every day it has orders, and a running total that

<Solution>

```sql
WITH daily AS (
  SELECT CAST(ordered_at AS DATE) AS day, payment_method, COUNT(*) AS orders
  FROM orders
  WHERE ordered_at >= '2026-01-01' AND ordered_at < '2026-01-08'
  GROUP BY day, payment_method
)
SELECT payment_method, day, orders,
       SUM(orders) OVER (PARTITION BY payment_method ORDER BY day) AS running_total
FROM daily
ORDER BY payment_method, day;
```

The result has 17 rows: card has 6 (no card order on January 1), cash has 4 (its first order is on January 4) and
mobile has 7. The last running totals are 24, 7 and 19, which add to 50, the orders of the week. A running total over
these rows skips days that have no row. To show those days with a zero you would first build a complete list of days;
*Complete time series and recursive CTEs* (S27) does that.

</Solution>

## Check yourself

1. Without looking back: how does a window function differ from `GROUP BY`, and what do `PARTITION BY` and `ORDER BY`
   inside `OVER` do?

   <details>
   <summary>Answer</summary>

   `GROUP BY` returns one row per group; a window function keeps every row and adds a value computed over its group.
   `PARTITION BY` picks the group, and `ORDER BY` orders the rows inside it, so the function can work from the first
   row to the current one.

   </details>

2. `SUM(orders) OVER (ORDER BY day)` runs over rows where two rows share a day. What do those two rows show?

   <details>
   <summary>Answer</summary>

   The same number: the total through the end of that day. The two rows are peers, and the default frame includes
   every peer of the current row.

   </details>
