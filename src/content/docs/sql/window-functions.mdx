## The question

The owner of the cafes asks:

> In the first week of January, how many orders did each cafe take each day, how many so far, and what share of the
> day's orders did each cafe take?

Only the two older cafes are open in January: store 1 is Old Town and store 2 is Campus (Harbor, store 3, opens on
April 1). Count the orders for each day and cafe and you get 14 rows: 7 days times 2 cafes. The top of that table:

| day | store_id | orders |
|---|---:|---:|
| 2026-01-01 | 1 | 2 |
| 2026-01-01 | 2 | 2 |
| 2026-01-02 | 1 | 3 |
| 2026-01-02 | 2 | 4 |

In Excel you would add a running-total column and a share column beside these rows, and no row would go away. SQL can
do that too.

## The big idea

`GROUP BY` squeezes rows together. A **window function** does the same sums and counts but keeps every row: it writes
the answer in a new column beside them.

## Learn by doing

Five small steps. Run the notebook's setup cell first, then the cells named in each step.

### 1. Keep the rows

A window function works out a value for each row from related rows. `OVER (PARTITION BY store_id)` says which rows
are related: it fences the rows into blocks (SQL calls them **partitions**), one per store, and the function never looks outside
the current row's block. Fencing does not merge anything; that is `GROUP BY`'s job. Leave `PARTITION BY` out and the whole result is one
block.

**Try it** (notebook step 1): first the collapsed view, one row per store.

<RunSQL query={`SELECT store_id, COUNT(*) AS orders
FROM orders
WHERE ordered_at >= '2026-01-01' AND ordered_at < '2026-01-08'
GROUP BY store_id
ORDER BY store_id;`} />

Expected: 2 rows, 2 columns: store 1 with 26 orders and store 2 with 24. *Excel:* one `COUNTIF` per store. Keep both
numbers for unit 5.

**Try it** (notebook step 2): now the same count, beside every order.

<RunSQL query={`SELECT order_id, store_id,
       COUNT(*) OVER (PARTITION BY store_id) AS store_orders
FROM orders
WHERE ordered_at >= '2026-01-01' AND ordered_at < '2026-01-08'
ORDER BY order_id
LIMIT 5;`} />

Read it: *beside each order, put the number of orders of its store this week*. Expected: 5 rows, 3 columns; order 1001
was taken at store 2, so `store_orders` shows 24 beside it. *Excel:* the same `COUNTIF` filled down beside every row.

*Why:* `WHERE` runs first, so only the week's orders are counted; `LIMIT` runs last, so it only trims the display.

### 2. A share of the day

You choose the block. `PARTITION BY day` fences the two rows of each day together, so a sum beside each row is that
day's total.

**Try it** (notebook step 3). First the table to work on, one row per day and cafe (*Readable queries with CTEs*, S13).
`CAST(ordered_at AS DATE)` drops the time of day and keeps the date (*Working with dates and time*, S11). Every query
from here on starts with this `daily` stage, and the notebook repeats it in each cell.

<RunSQL query={`WITH daily AS (
  SELECT CAST(ordered_at AS DATE) AS day, store_id, COUNT(*) AS orders
  FROM orders
  WHERE ordered_at >= '2026-01-01' AND ordered_at < '2026-01-08'
  GROUP BY day, store_id
)
SELECT day, store_id, orders
FROM daily
ORDER BY day, store_id;`} />

Expected: 14 rows, 3 columns, the table from the question.

**Try it** (notebook step 4): add each cafe's share of the day.

<RunSQL query={`WITH daily AS (
  SELECT CAST(ordered_at AS DATE) AS day, store_id, COUNT(*) AS orders
  FROM orders
  WHERE ordered_at >= '2026-01-01' AND ordered_at < '2026-01-08'
  GROUP BY day, store_id
)
SELECT day, store_id, orders,
       SUM(orders) OVER (PARTITION BY day) AS day_total,
       ROUND(orders * 100.0 / SUM(orders) OVER (PARTITION BY day), 1) AS share_pct
FROM daily
ORDER BY day, store_id;`} />

Read it: *beside each row, put the day's total orders, and this row's percent of it*. Expected: 14 rows, 5 columns. On
January 1 each cafe has 50.0 percent; on January 6 Old Town has 71.4 percent (5 of 7 orders).

*Excel:* with day, store_id and orders in columns A, B and C (data in rows 2 to 15), `=SUMIF($A$2:$A$15,A2,$C$2:$C$15)`
filled down gives every row its day's total, and `=C2/SUMIF($A$2:$A$15,A2,$C$2:$C$15)` is the share. `SUMIFS`, the
version with several conditions, is *Conditional totals with SUMIFS and COUNTIFS* (E7).

*Why:* `100.0` and `ROUND(..., 1)` give a percent with one decimal.

### 3. A running total

Until now every row read its whole block. Add `ORDER BY day` inside `OVER` and the block is sorted, for this
calculation only, and each row reads less: its **frame**, the part of the block the function reads for the current
row. Only aggregates and a few other functions use a frame. With an `ORDER BY` and nothing else, the frame runs from
the block's first row to the current row. Here is the frame of January 4.

<RunSQL query={`WITH daily AS (
  SELECT CAST(ordered_at AS DATE) AS day, store_id, COUNT(*) AS orders
  FROM orders
  WHERE ordered_at >= '2026-01-01' AND ordered_at < '2026-01-08'
  GROUP BY day, store_id

SELECT store_id, day, orders,
       SUM(orders) OVER (PARTITION BY store_id ORDER BY day) AS running_total
FROM daily
ORDER BY store_id, day;`} />

Expected: 14 rows, 4 columns; store 1 ends at 26 and store 2 at 24. *Excel:* `=SUM(C$2:C2)` copied down, restarted at
each cafe's first row, is a frame that grows. The `$` locks part of a reference when you copy a formula: in `C$2` the
row stays 2, so the range `C$2:C2` grows by one row as you copy it down. `SUM` and `SUMIF` exist in both Excel and
Google Sheets.

*Why:* `PARTITION BY store_id` restarts the total for each cafe, and `ORDER BY day` makes each row's total the sum of
the rows up to its own day. `SUM` used as a window function skips `NULL` values.

### 4. Ties and the default frame

Written out in full, the frame from unit 3 is `RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW`. "Current row" includes
every row tied with it on the `ORDER BY` value: its **peers**.

**Try it** (notebook step 6). On January 1 both cafes have 2 orders. Before you run the query, predict what
`default_frame` will show on each of those two rows.

<details>
<summary>Prediction</summary>

Both rows show 4: each row's frame holds both January 1 rows (2 + 2). `row_by_row` breaks the tie with `store_id` and
counts rows, so it shows 2 and then 4.

</details>

<RunSQL query={`WITH daily AS (
  SELECT CAST(ordered_at AS DATE) AS day, store_id, COUNT(*) AS orders
  FROM orders
  WHERE ordered_at >= '2026-01-01' AND ordered_at < '2026-01-08'
  GROUP BY day, store_id
)
SELECT day, store_id, orders,
       SUM(orders) OVER (ORDER BY day) AS default_frame,
       SUM(orders) OVER (ORDER BY day, store_id
                         ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW) AS row_by_row
FROM daily
ORDER BY day, store_id;`} />

Expected: 14 rows, 5 columns. *Why:* the two columns differ on the first row of each day, because there are two cafes
and so two peers a day. `default_frame` answers "how many orders by the end of this day", the same on both rows.
`row_by_row` answers "how many orders by this row", which depends on the tie-breaker you chose. Pick the one your
question needs.

### 5. Check the numbers

No new query. Check four things:

- Notebook steps 3 to 6 all return 14 rows, as the daily table has.
- The last running totals (step 5), 26 and 24, equal the counts from step 1.
- The two shares of each day (step 4) add to 100: January 2 has 42.9 and 57.1.
- The last row of step 6 shows 50 in both columns: 26 + 24, every order of the week.

<Aside type="tip" title="Remember">

- A window function keeps every row and adds a column.
- `PARTITION BY` picks the block, `ORDER BY` sorts it, and the frame says which rows count.
- No `ORDER BY` in `OVER`: the frame is the whole block. With one: from the first row to the current row, ties included.

**Common trap: "I can filter on a window result with `WHERE`."** Windows run after `WHERE` and `HAVING` (*How a query
runs: the order of the clauses*, S12), so neither can see a window result: DuckDB answers `Binder Error: WHERE clause
cannot contain window functions!`. Compute the window in a CTE (S13) and filter in the next step. (`QUALIFY` also
exists; it comes later.)

</Aside>

## Check yourself

1. Without looking back: how does a window function differ from `GROUP BY`, and what do `PARTITION BY` and `ORDER BY`
   inside `OVER` do?

   <details>
   <summary>Answer</summary>

   `GROUP BY` returns one row per group; a window function keeps every row and adds a value computed over its group.
   `PARTITION BY` picks the group, and `ORDER BY` orders the rows inside it, so the function can work from the first
   row to the current one.

   </details>

2. `SUM(orders) OVER (ORDER BY day)` runs over rows where two rows share a day. What do those two rows show?

   <details>
   <summary>Answer</summary>

   The same number: the total through the end of that day. The two rows are peers, and the default frame includes
   every peer of the current row.

   </details>
