## Warm-up

Answer from memory before you open anything. Then click to check.

1. In *LEFT JOIN and finding rows with no match* (S20), write the query that lists the customers who never ordered.

   <details>
   <summary>Answer</summary>

   ```sql
   SELECT c.customer_id
   FROM customers c
   LEFT JOIN orders o ON o.customer_id = c.customer_id
   WHERE o.order_id IS NULL
   ORDER BY c.customer_id;
   ```

   It returns 5 rows: customers 140, 147, 148, 149 and 150.

   </details>

2. In *GROUP BY and HAVING* (S8), write the query that lists the customers with more than 20 orders and their order counts.

   <details>
   <summary>Answer</summary>

   ```sql
   SELECT customer_id, COUNT(*) AS orders
   FROM orders
   GROUP BY customer_id
   HAVING COUNT(*) > 20;
   ```

   `HAVING` filters the groups after they are counted. It returns 25 rows.

   </details>

## How it works

A **subquery** is a `SELECT` in parentheses inside another query, the outer query. The outer query reads its result as
one value, a list, a yes-or-no or a table, depending on where the subquery sits. Conceptually:

1. A subquery that uses nothing from the outer query is self-contained, so it can run on its own: check it alone first.
   Think of its result as worked out first and handed to the outer query.
2. The outer query then uses that result where the subquery sits: against one value, against a list, as a yes-or-no,
   or as a table in `FROM`. The first picture above shows a list.
3. A **correlated** subquery uses a column of the outer row. It cannot run alone, because it needs that row's value.
   Conceptually it runs once for every outer row, with the value as a parameter. In the second picture,
   `c.customer_id` changes with each row.
4. DuckDB need not do it literally: it detects a `NOT EXISTS` that is an anti join and plans it as a join.

The rules:

- A scalar subquery must return one value. If it returns more than one, DuckDB raises an error.
- `IN` and `EXISTS` ask a yes-or-no question of each outer row and keep or drop it, so they add no rows. `IN` asks
  whether the row's value is in the list. `EXISTS` asks whether the subquery returns at least one row, and `NOT EXISTS`
  asks whether it returns none.
- Which columns an `EXISTS` subquery lists makes no difference; only whether it returns a row. That is why `SELECT 1`
  is common.
- A derived table is a subquery in `FROM`. The outer query treats it as a table, so it has a grain of its own (S18).

| Kind | Where it sits | The inner query returns |
|---|---|---|
| Scalar | anywhere one value fits: `WHERE`, `HAVING`, the `SELECT` list | one row and one column |
| `IN` | after `x IN` | one column, any number of rows: a list |
| `EXISTS` | after `EXISTS` or `NOT EXISTS` | any rows: only "is there at least one?" matters |
| Derived table | in `FROM`, with a name | a whole table |

**Excel.** A scalar subquery is like a cell holding `=AVERAGE(...)` that other formulas point to. `EXISTS` is the
question a lookup answers: did `XLOOKUP` (E8, *Bring in a value by key with XLOOKUP*) find the key, or fall back to its
not-found text?

**A common misconception: "a `NOT EXISTS` really runs its inner query once for every row."** The per-row picture is
how to read it, not always how DuckDB runs it. When a `NOT EXISTS` expresses an anti join, DuckDB plans it as a join
(step 4 above).

## Worked example

Question: **how many customers ordered at Harbor, how many never ordered, and how many order more than average?** Run
the notebook's setup cell, then one cell per step. Each step gives the shape of the result to expect. Counts cover all
1,800 orders, the canceled one included; the walk-in order 1335 has no customer, so it belongs to none.

1. **IN: write the inner query alone first.**

   ```sql
   SELECT customer_id
   FROM orders
   WHERE store_id = 3
   ORDER BY customer_id
   LIMIT 8;
   ```

   Expected: 8 rows, 1 column. *Why:* the inner query must make sense on its own. Customer 5 repeats because each row
   is an order, not a customer.

   Now put it in parentheses after `IN`:

   ```sql
   SELECT customer_id, signup_date, loyalty_tier
   FROM customers
   WHERE customer_id IN (
     SELECT customer_id
     FROM orders
     WHERE store_id = 3
   )
   ORDER BY customer_id
   LIMIT 6;
   ```

   Expected: 6 rows, 3 columns; the first is customer 2. *Why:* the outer query asks one thing of each customer: is
   your id in the list? The grain stays one row per customer.

2. **NOT EXISTS: customers with no order.**

   ```sql
   SELECT customer_id, signup_date, loyalty_tier
   FROM customers c
   WHERE NOT EXISTS (
     SELECT 1
     FROM orders o
     WHERE o.customer_id = c.customer_id
   )
   ORDER BY customer_id;
   ```

   Expected: 5 rows, 3 columns. *Why:* `c` and `o` are aliases, and `o.customer_id = c.customer_id`
   is what makes it correlated. The same five customers as in the warm-up.

3. **Read a correlated subquery in the `SELECT` list.** Do not write this yet; run it and read it.

   ```sql
   SELECT c.customer_id,
          (SELECT COUNT(*) FROM orders o WHERE o.customer_id = c.customer_id) AS orders
   FROM customers c
   WHERE c.customer_id BETWEEN 138 AND 142
   ORDER BY c.customer_id;
   ```

   Expected: 5 rows, 2 columns. *Why:* for each customer, the inner query counts that customer's orders, so customer 140
   shows 0. This is the second picture as a number.

4. **A derived table: the average of a count.** `AVG(COUNT(*))` is not allowed, so make the counts a table first.

   ```sql
   SELECT ROUND(AVG(orders), 2) AS avg_orders, MAX(orders) AS max_orders
   FROM (
     SELECT customer_id, COUNT(*) AS orders
     FROM orders
     WHERE customer_id IS NOT NULL
     GROUP BY customer_id
   ) AS per_customer;
   ```

   Expected: 1 row, 2 columns: `12.41` and `29`. *Why:* the inner query has grain one row per customer; the outer
   query summarizes it. It is the same idea as a CTE (S13) written inside `FROM`. The filter drops the walk-in order.

5. **Scalar: customers above the average.** The average from step 4, in one value:

   ```sql
   SELECT ROUND(COUNT(customer_id) * 1.0 / COUNT(DISTINCT customer_id), 2) AS avg_orders
   FROM orders;
   ```

   Expected: 1 row, 1 column: `12.41`. *Why:* 1,799 orders that name a customer, over 145 different customers. Both counts
   skip the empty `customer_id` (S7). Now use it in `HAVING`:

   ```sql
   SELECT customer_id, COUNT(*) AS orders
   FROM orders
   WHERE customer_id IS NOT NULL
   GROUP BY customer_id
   HAVING COUNT(*) > (
     SELECT ROUND(COUNT(customer_id) * 1.0 / COUNT(DISTINCT customer_id), 2)
     FROM orders
   )
   ORDER BY orders DESC, customer_id
   LIMIT 5;
   ```

   Expected: 5 rows, 2 columns; the first three have 29 orders. Without `LIMIT 5` the query has 68 rows. *Why:* the inner
   query runs once and gives a single number that each group is compared with.

6. **Verify.** One row of four scalar subqueries:

   ```sql
   SELECT
     (SELECT COUNT(*) FROM customers
      WHERE customer_id IN (SELECT customer_id FROM orders WHERE store_id = 3)) AS at_harbor,
     (SELECT COUNT(*) FROM customers c
      JOIN orders o ON o.customer_id = c.customer_id
      WHERE o.store_id = 3) AS join_rows,
     (SELECT COUNT(*) FROM customers c
      WHERE EXISTS (SELECT 1 FROM orders o WHERE o.customer_id = c.customer_id)) AS ordered,
     (SELECT COUNT(*) FROM customers c
      WHERE NOT EXISTS (SELECT 1 FROM orders o WHERE o.customer_id = c.customer_id)) AS never;
   ```

   Expected: 1 row, 4 columns: `90 | 355 | 145 | 5`. Answer: **90 customers ordered at Harbor, 5 never ordered, and 68
   order more than the average customer's 12.41.** Checks: 145 + 5 = 150 customers; the join gives 355 rows, one per
   Harbor order, while `IN` gives 90, one per customer; and the 5 are the same customers as the anti join of S20.

<details>
<summary>Explain it in your own words: why does the join give 355 rows and IN only 90?</summary>

The join pairs a customer with every order, so a customer with five Harbor orders appears five times. `IN` only asks
whether the id is in the list, so a customer appears at most once, however long the list repeats it.

</details>

**Which customers placed an order but never a completed one?** Work in the Exercise 2 cells.

Before you run anything, write one sentence in the first cell: which customers you expect, and how they differ from the
five who never ordered. Then write the query with `EXISTS` and `NOT EXISTS`. Try the `NOT EXISTS` half alone as well and
compare.

Expected shape, to check your sentence against: a list of customer ids, 1 column. The status of an order is `completed`
or `canceled`.

<details>
<summary>Hint</summary>

Two conditions on the same customer: an order exists, and no completed order exists. Each is a correlated subquery
like step 2; the second adds `AND o.status = 'completed'`.

</details>

<details>
<summary>Half-solution</summary>

Expected output: *"One id column. The customers who have at least one order, none of them completed."*

```sql
SELECT customer_id
FROM customers c
WHERE EXISTS (...)
  AND NOT EXISTS (...);
```

</details>

<Solution>

```sql
SELECT customer_id
FROM customers c
WHERE EXISTS (
  SELECT 1 FROM orders o WHERE o.customer_id = c.customer_id
)
AND NOT EXISTS (
  SELECT 1 FROM orders o WHERE o.customer_id = c.customer_id AND o.status = 'completed'
);
```

One customer: **42**, whose only order is the canceled order 1461. With the `NOT EXISTS` half alone you get 6 rows: 42
and the five who never ordered. The `EXISTS` half separates "never ordered" from "never completed".

</Solution>

</Exercise>

## Check yourself

Without looking back: name the four kinds of subquery and say what the inner query returns in each.

<details>
<summary>Answer</summary>

Scalar: one value. `IN`: one column, a list. `EXISTS`: any rows, only whether there are some. Derived table: a whole
table in `FROM`, with a name.

</details>

<Exercise id="sql-subqueries-3">

**Spot the flaw.** A colleague wants the customers who never ordered, and writes:

```sql
SELECT customer_id
FROM customers
WHERE customer_id NOT IN (SELECT customer_id FROM orders);
```

Expected from that query: 0 rows, 1 column. The warm-up showed there are 5 such customers. What went wrong, and how do
you fix it?

<Solution>

The inner list contains an empty value: order 1335 has no `customer_id`. For a customer that is not in the list, `IN`
gives `NULL` (unknown) instead of `false` when the list holds a `NULL`, as the DuckDB documentation notes, so `NOT IN`
never becomes true and no row survives. DuckDB's FROM page adds that an anti join matches `NOT IN` except that
it ignores `NULL` values from the right table.

Two fixes:

```sql
SELECT customer_id
FROM customers
WHERE customer_id NOT IN (SELECT customer_id FROM orders WHERE customer_id IS NOT NULL);
```

or `NOT EXISTS`, which has no such trap. Both give 5 rows, 1 column: 140, 147, 148, 149 and 150.

</Solution>

</Exercise>
