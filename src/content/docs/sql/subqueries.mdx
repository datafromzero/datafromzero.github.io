## The question

The owner of the cafes asks:

> Harbor opened in April. How many of our 150 loyalty customers have ordered there? How many have never ordered
> anywhere? And how many order more often than the average customer?

The first rows of `customers`:

| customer_id | signup_date | loyalty_tier |
|---:|---|---|
| 1 | 2025-06-04 | bronze |
| 2 | 2025-06-04 | silver |
| 3 | 2025-06-06 | gold |

Each answer needs facts from `orders`, so each needs a second query inside the first.

## Warm-up

Try each one from memory, then open the answer. Forgot? Follow the link back to that part of the lesson: looking back is part of the review.

1. In [*LEFT JOIN and finding rows with no match*](/sql/left-join-anti-join/#2-find-the-rows-with-no-partner) (S21), write the query that lists the customers who never ordered.

   <details>
   <summary>Answer</summary>

   ```sql
   SELECT c.customer_id
   FROM customers c
   LEFT JOIN orders o ON o.customer_id = c.customer_id
   WHERE o.order_id IS NULL
   ORDER BY c.customer_id;
   ```

   It returns 5 rows: customers 140, 147, 148, 149 and 150.

   </details>

2. In [*GROUP BY and HAVING*](/sql/group-by-having/#4-having-clears-groups-after-the-count) (S8), write the query that lists the customers with more than 20 orders and their order counts.

   <details>
   <summary>Answer</summary>

   ```sql
   SELECT customer_id, COUNT(*) AS orders
   FROM orders
   GROUP BY customer_id
   HAVING COUNT(*) > 20;
   ```

   `HAVING` filters the groups after they are counted. It returns 25 rows.

   </details>

## The big idea

A **subquery** is a query inside a query: the inner one hands the outer one a value, a list, a yes or no, or a whole table.

### 1. IN: ask against a list

You write a subquery in parentheses; the query around it is the outer query. A subquery that uses nothing from the outer
query is self-contained, so it can run alone: check it alone first.

Think of its result as worked out first and handed to the outer query. `IN` then asks of each outer row whether its value
is in that list, and keeps or drops the row, so it adds no rows.

**Try it**: the inner query, alone.

<RunSQL query={`SELECT customer_id
FROM orders
WHERE store_id = 3
ORDER BY customer_id
LIMIT 8;`} />

Expected: 8 rows, 1 column. *Why:* the inner query must make sense on its own. Customer 5 repeats because each row is an
order, not a customer.

Now put it in parentheses after `IN`.

<RunSQL query={`SELECT customer_id, signup_date, loyalty_tier
FROM customers
WHERE customer_id IN (
  SELECT customer_id
  FROM orders
  WHERE store_id = 3
)
ORDER BY customer_id
LIMIT 6;`} />

Expected: 6 rows, 3 columns; the first is customer 2. *Why:* the outer query asks one thing of each customer: is your id
in the list? The grain stays one row per customer.

### 2. EXISTS: a yes or no for each row

`EXISTS` asks whether the inner query returns at least one row, and `NOT EXISTS` whether it returns none. Which columns an
`EXISTS` subquery lists makes no difference; only whether it returns a row. That is why `SELECT 1` is common.

The inner query below mentions a column of the outer row, `c.customer_id`. A subquery that does is **correlated**: it
cannot run alone, because it needs that row's value. Picture it running once for every outer row, with that row's value
filled in.

*Excel:* `EXISTS` is the question a lookup answers: did `XLOOKUP` (E8, *Bring in a value by key with XLOOKUP*) find the
key, or fall back to its not-found text?

**Try it**: customers with no order.

<RunSQL query={`SELECT customer_id, signup_date, loyalty_tier
FROM customers c
WHERE NOT EXISTS (
  SELECT 1
  FROM orders o
  WHERE o.customer_id = c.customer_id
)
ORDER BY customer_id;`} />

Expected: 5 rows, 3 columns. *Why:* `c` and `o` are aliases, short names as in joins. For each customer, the inner query asks
whether an order carries that customer's id. The same five customers as in the warm-up.

**Try it**: read a correlated subquery in the `SELECT` list. Do not write this yet; run it and read it.

<RunSQL query={`SELECT c.customer_id,
       (SELECT COUNT(*) FROM orders o WHERE o.customer_id = c.customer_id) AS orders
FROM customers c
WHERE c.customer_id BETWEEN 138 AND 142
ORDER BY c.customer_id;`} />

Expected: 5 rows, 2 columns. *Why:* for each customer, the inner query counts that customer's orders, so customer 140 shows
0. The picture shows the same run as a table.

### 3. A derived table: a subquery in FROM

A **derived table** is a subquery in `FROM`, with a name. The outer query treats it as a table, so it has a grain of its
own (S18). Say you want the average of each customer's order count: `AVG(COUNT(*))` stops with the message `aggregate
function calls cannot be nested`, so make the counts a table first.

**Try it**: the average of a count.

<RunSQL query={`SELECT ROUND(AVG(orders), 2) AS avg_orders, MAX(orders) AS max_orders
FROM (
  SELECT customer_id, COUNT(*) AS orders
  FROM orders
  WHERE customer_id IS NOT NULL
  GROUP BY customer_id
) AS per_customer;`} />

Expected: 1 row, 2 columns: `12.41` and `29`. *Why:* the inner query has grain one row per customer; the outer query
summarizes it. It is the same idea as a CTE (S13) written inside `FROM`. The filter drops the walk-in order.

### 4. A scalar subquery: one value

A **scalar** subquery returns one value, so it can sit anywhere one value fits: in `WHERE`, in `HAVING` or in the
`SELECT` list. If it returns more than one value, DuckDB raises an error. *Excel:* it is like a cell holding
`=AVERAGE(...)` that other formulas point to.

**Try it**: the average from unit 3, in one value.

<RunSQL query={`SELECT ROUND(COUNT(customer_id) * 1.0 / COUNT(DISTINCT customer_id), 2) AS avg_orders
FROM orders;`} />

Expected: 1 row, 1 column: `12.41`. *Why:* 1,799 orders that name a customer, over 145 different customers. Both counts
skip the empty `customer_id` (S7). Now use it in `HAVING`:

<RunSQL query={`SELECT customer_id, COUNT(*) AS orders
FROM orders
WHERE customer_id IS NOT NULL
GROUP BY customer_id
HAVING COUNT(*) > (
  SELECT ROUND(COUNT(customer_id) * 1.0 / COUNT(DISTINCT customer_id), 2)
  FROM orders
)
ORDER BY orders DESC, customer_id
LIMIT 5;`} />

Expected: 5 rows, 2 columns; the first three have 29 orders. Without `LIMIT 5` the query has 68 rows. *Why:* the inner
query runs once and gives a single number that each group is compared with.

### 5. Check the three answers

One row of four scalar subqueries gives the three answers and two checks.

**Try it**: the check.

<RunSQL query={`SELECT
  (SELECT COUNT(*) FROM customers
   WHERE customer_id IN (SELECT customer_id FROM orders WHERE store_id = 3)) AS at_harbor,
  (SELECT COUNT(*) FROM customers c
   JOIN orders o ON o.customer_id = c.customer_id
   WHERE o.store_id = 3) AS join_rows,
  (SELECT COUNT(*) FROM customers c
   WHERE EXISTS (SELECT 1 FROM orders o WHERE o.customer_id = c.customer_id)) AS ordered,
  (SELECT COUNT(*) FROM customers c
   WHERE NOT EXISTS (SELECT 1 FROM orders o WHERE o.customer_id = c.customer_id)) AS never;`} />

Expected: 1 row, 4 columns: `90 | 355 | 145 | 5`. Answer: **90 customers ordered at Harbor, 5 never ordered, and 68
order more than the average customer's 12.41.** Checks: 145 + 5 = 150 customers; the join gives 355 rows, one per
Harbor order, while `IN` gives 90, one per customer; and the 5 are the same customers as the anti join of S21.

<details>
<summary>Explain it in your own words: why does the join give 355 rows and IN only 90?</summary>

Count the partners a customer can find. A join builds one row for every matching order, so a customer with five Harbor
orders turns into five rows. `IN` asks one yes-or-no question per customer, so no customer can turn into more than one
row, however often the list repeats the id.

</details>

<Aside type="tip" title="Remember">

- Scalar: one value, anywhere one value fits. `IN`: one column, a list. `EXISTS`: any rows; only "is there at least one?" matters.
- Derived table: a whole table in `FROM`, with a name and a grain of its own.
- Write the inner query alone and check it before you nest it. A correlated one needs an outer row, so read it row by row.

**Common trap: "a `NOT EXISTS` really runs its inner query once for every row."** The per-row picture is how to read it,
not always how DuckDB runs it. When a `NOT EXISTS` expresses an anti join, DuckDB can plan it as a join.

</Aside>

<Exercise id="sql-subqueries-3">

**Spot the flaw.** A colleague wants the customers who never ordered, and writes:

<RunSQL query={`SELECT customer_id
FROM customers
WHERE customer_id NOT IN (SELECT customer_id FROM orders);`} />

Expected from that query: 0 rows, 1 column. The warm-up showed there are 5 such customers. What went wrong, and how do
you fix it?

<Solution>

The inner list contains an empty value: order 1335 has no `customer_id`. For a customer that is not in the list, `IN`
gives `NULL` (unknown) instead of `false` when the list holds a `NULL`, as the DuckDB documentation notes, so `NOT IN`
never becomes true and no row survives. DuckDB's FROM page adds that an anti join matches `NOT IN` except that
it ignores `NULL` values from the right table.

Two fixes:

```sql
SELECT customer_id
FROM customers
WHERE customer_id NOT IN (SELECT customer_id FROM orders WHERE customer_id IS NOT NULL);
```

or `NOT EXISTS`, which has no such trap. Both give 5 rows, 1 column: 140, 147, 148, 149 and 150.

</Solution>
