## The question

The owner of the cafes asks:

> How many orders have we taken since January? And which teas do we sell, the most expensive first?

In E1 and E5 you answered questions like these with a status bar, a filter and a sort. The same cafe-sales data also
lives in a database, and this lesson answers both questions there, in SQL. The top of the `products` table:

| 1 | Espresso | coffee | 3.00 |
| 2 | Americano | coffee | 3.50 |

## The big idea

A **database** keeps your data in **tables**, grids like a sheet with a header row, and **SQL** is the language you use
to question it: you write one question, a **query**, and the database builds a new **result table** with just the rows
and columns you asked for.

## Learn by doing

Five small steps. Press Run under each query. Each one works on its own, so you can come back to any step.

### 1. See a whole table

The `products` table has one row for each menu item. `SELECT *` means show every column, and `FROM products` names the
table. Read it as a sentence: *show every column from products*.

**Try it.** The editor already holds the query. Press **Run**, or press Ctrl+Enter (on a Mac,
Cmd+Enter).

<RunSQL query={`SELECT * FROM products;`} />

Expected: 16 rows, 4 columns, the same grid as the products sheet. *Excel:* open the sheet.

**Now type.** Change `products` to `stores` in the editor and press Run again. The **Tables** button in the editor lists
all five tables. You can also write `select * from stores` in lowercase: capitals on keywords are only for readers.

*Why:* look at a table before you question it.

### 2. Peek and pick

Some tables are long: `orders` has 1,800 rows. `LIMIT 5` keeps only the first five rows of the result. Without a sort,
which five is not promised: the results can come back in a different order each time, as the DuckDB documentation warns.

**Try it**:

<RunSQL query={`SELECT * FROM orders LIMIT 5;`} />

Expected: 5 rows, 6 columns; the first row is order 1001. *Excel:* look at the top of the sheet.

Now ask for fewer columns. Name them after `SELECT`, in the order you want them, with commas between.

**Try it**:

<RunSQL query={`SELECT product_name, unit_price_usd FROM products;`} />

Expected: 16 rows, 2 columns. *Excel:* hide the other columns.

*Why:* you choose what you see: which columns, and how many rows.

### 3. Keep only some rows

`WHERE` keeps only the rows that pass a test. Text goes in single quotes: `category = 'tea'` compares with the text
tea. `WHERE` can use any column of the table, shown or not.

A query only reads. DuckDB's page says `SELECT` retrieves rows, and the result is a new table: the stored one stays as
it was.

**Try it.** Before you run it: how many of the 16 rows pass?

<RunSQL query={`SELECT product_name, unit_price_usd
FROM products
WHERE category = 'tea';`} />

Read it: *keep only the rows whose category is tea*. Expected: 2 columns. *Excel:* filter `category` to `tea`. Microsoft Support says a filter "hides rows that you do not want displayed",
so the sheet still holds them. A query hides nothing: it builds a separate table.

*Why:* `WHERE` compares each row's `category` with the text tea and keeps the match: Green Tea, Chai Latte and Iced
Lemon Tea. Numbers and column names take no quotes. The picture shows the same filter in the sheet.

### 4. Sort, and the order SQL reads

`ORDER BY` sorts the rows. `DESC` means descending, highest first. Without it the order is ascending, lowest first.

**Try it**:

<RunSQL query={`SELECT product_name, unit_price_usd
FROM products
WHERE category = 'tea'
ORDER BY unit_price_usd DESC;`} />

Expected: 3 rows, 2 columns, highest price first: Chai Latte 4.75, Iced Lemon Tea 3.75, Green Tea 3.25. *Excel:* sort
largest to smallest. That answers the owner's second question. The picture reads the query as a sentence.

SQL reads in a different order from how you write it: the table, then the filter, then the columns, and last the sort
and the limit. Follow one query through those steps.

**Try it**:

<RunSQL query={`SELECT product_name
FROM products
WHERE category = 'coffee'
ORDER BY product_name
LIMIT 2;`} />

1. `FROM products` starts with all 16 rows.
2. `WHERE` drops the rows that fail its test: seven coffee rows are left.
3. `SELECT` keeps the named column, `product_name`.
4. `ORDER BY` sorts the rows that are left, and `LIMIT 2` keeps the first two.

Expected: 2 rows, 1 column: Americano and Cappuccino.

### 5. Count, and check

`COUNT(*)` counts rows. One row of `orders` is one order, so the row count is the number of orders. `AS orders` names the
result column.

**Try it**:

<RunSQL query={`SELECT COUNT(*) AS orders FROM orders;`} />

Expected: 1 row, 1 column: `1800`. *Excel:* the status bar Count. That answers the first question: **1,800 orders**,
the one canceled order included.

Check the answers against the sheet. The 1,800 equals the Count you read in E1, and the three teas match rows 8, 9 and
10 that the filter keeps. Two tools, one dataset, the same answers.

<Aside type="tip" title="Remember">

- SQL reads `FROM`, then `WHERE`, then `SELECT`, and `ORDER BY` and `LIMIT` last, whatever order you write them in.
- A query only reads: the stored table never changes.
- Text values go in single quotes; numbers and column names do not.
- `WHERE` can use any column, shown or not.
- `LIMIT` without `ORDER BY` has no promised rows.

**Common trap: "the query runs from the top, so `SELECT` picks the columns before `WHERE` looks at the rows."** The lines
are a sentence for you to read; the engine starts at `FROM`. So `SELECT product_name FROM products WHERE unit_price_usd > 5`
works although `unit_price_usd` is not in the result.

</Aside>

**Run it, read the message, fix it.** A colleague wants the teas and runs this query. It gives an error, not a table:

<RunSQL query={`SELECT product_name FROM products WHERE category = tea;`} />

Expected: an error, not a table. The message names the problem; use it to fix the query.

<Solution>

Without quotes, SQL reads `tea` as the name of a column, finds no such column in `products`, and stops. The error reads
`Referenced column "tea" not found in FROM clause!`, and it names the column it could not find. `tea` is a value, and text values go in single quotes
(the DuckDB documentation: string literals are delimited by single quotes):

```sql
SELECT product_name FROM products WHERE category = 'tea';
```

Expected: 3 rows, 1 column. Text must match exactly: with a capital, `'Tea'`, the query runs but returns 0 rows,
because the data says `tea`.
