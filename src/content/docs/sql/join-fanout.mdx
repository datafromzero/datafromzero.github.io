## The question

The owner of the cafes asks:

> How much did orders that contained coffee bring in, and how much did orders without coffee? Count whole orders: an
> order with a Cold Brew and a croissant is a coffee order, and its full value counts.

A result called `order_totals` has one row per order: its total in dollars, the sum of its lines as in S19. Unit 1 builds
it. Its first rows:

| order_id | order_total_usd |
|---:|---:|
| 1001 | 14.00 |
| 1002 | 12.50 |
| 1003 | 12.50 |
| 1004 | 6.50 |

To know which orders hold coffee you need the lines and their products.

## The big idea

A join copies an order's total onto each of its lines, so adding the totals counts every order once per line, unless you shrink the lines to one row per order first.

## Learn by doing

Five small steps. Press Run on each query. Every figure covers all
1,800 orders, the canceled one included, and includes the extra-zero line of order 2075.

### 1. Take a control total first

Before you join anything, take a **control total**: a figure you work out first, from rows you can name, that every later
step must reproduce. Here it is the dollars of all orders, from `order_totals`. Its grain, what one row is, is one order.

**Try it**: build `order_totals`.

<RunSQL query={`WITH order_totals AS (
  SELECT oi.order_id,
         SUM(oi.quantity * p.unit_price_usd - oi.discount_usd) AS order_total_usd
  FROM order_items AS oi
  INNER JOIN products AS p ON oi.product_id = p.product_id
  GROUP BY oi.order_id
)
SELECT COUNT(*) AS orders,
       COUNT(DISTINCT order_id) AS distinct_ids,
       SUM(order_total_usd) AS total_usd
FROM order_totals;`} />

Expected: 1 row, 3 columns: `1800 | 1800 | 22754.25`. *Why:* the two counts match, so `order_id` is unique: one row per
order. The total is S19's 22,754.25, the control total every later step must reproduce.

### 2. A join copies the figure onto every line

*INNER JOIN* (S19) gave the counting rule: a key that repeats pairs a row with every match. **Fan-out** is what that rule
does to a figure stored once per key. The join copies it onto every row it builds for that key.

To spot it, compare the row count before and after the join, and the total with the control total.

**Try it**. Before you run it: `order_totals` has 1,800 rows and there are 3,287 lines. How many rows
will the join return, and will its `SUM` match unit 1?

<RunSQL query={`WITH order_totals AS (
  SELECT oi.order_id,
         SUM(oi.quantity * p.unit_price_usd - oi.discount_usd) AS order_total_usd
  FROM order_items AS oi
  INNER JOIN products AS p ON oi.product_id = p.product_id
  GROUP BY oi.order_id
)
SELECT COUNT(*) AS joined_rows,
       SUM(t.order_total_usd) AS total_usd
FROM order_totals AS t
INNER JOIN order_items AS oi ON t.order_id = oi.order_id;`} />

Expected: 1 row, 2 columns. *Why:* **3287** rows and **48443.50**, more than twice the control total. Each order total
was added once per line, because the result has the finer grain: one row per line.

**Try it**: see the copies. Each line gets a flag for coffee (`p.category = 'coffee'` is true or
false), and order 1001 shows what the join did.

<RunSQL query={`WITH order_totals AS (
  SELECT oi.order_id,
         SUM(oi.quantity * p.unit_price_usd - oi.discount_usd) AS order_total_usd
  FROM order_items AS oi
  INNER JOIN products AS p ON oi.product_id = p.product_id
  GROUP BY oi.order_id
),
lines AS (
  SELECT oi.order_item_id, oi.order_id, p.category = 'coffee' AS is_coffee
  FROM order_items AS oi
  INNER JOIN products AS p ON oi.product_id = p.product_id
)
SELECT l.order_item_id, l.order_id, l.is_coffee, t.order_total_usd
FROM order_totals AS t
INNER JOIN lines AS l ON t.order_id = l.order_id
WHERE t.order_id = 1001
ORDER BY l.order_item_id;`} />

Expected: 3 rows, 4 columns. *Why:* order 1001 has three lines (a Croissant and two coffees), so its 14.00 appears three
times: twice among the coffee rows and once among the others. After the join one row is a line, and a per-order figure
does not belong at that grain.

### 3. Aggregates add every copy

An aggregate reads the result as it stands: `SUM` adds every copy, `COUNT(*)` counts lines, and grouping by a column of
the lines puts an order into every group where it has a line. So add a figure only at the grain where it is stored. A
line's quantity can be added over lines; an order's total cannot.

*Excel:* the same trap appears when an order total is copied beside every line and added with `SUMIFS` (E7, *Conditional
totals with SUMIFS and COUNTIFS*): it adds the sum-range cells of every row that passes the tests, copies included.

**Try it**: ask the question the naive way, one row per line joined to the totals.

<RunSQL query={`WITH order_totals AS (
  SELECT oi.order_id,
         SUM(oi.quantity * p.unit_price_usd - oi.discount_usd) AS order_total_usd
  FROM order_items AS oi
  INNER JOIN products AS p ON oi.product_id = p.product_id
  GROUP BY oi.order_id
),
lines AS (
  SELECT oi.order_item_id, oi.order_id, p.category = 'coffee' AS is_coffee
  FROM order_items AS oi
  INNER JOIN products AS p ON oi.product_id = p.product_id
)
SELECT l.is_coffee,
       COUNT(DISTINCT t.order_id) AS orders,
       SUM(t.order_total_usd) AS revenue_usd
FROM order_totals AS t
INNER JOIN lines AS l ON t.order_id = l.order_id
GROUP BY l.is_coffee
ORDER BY l.is_coffee DESC;`} />

Expected: 2 rows, 3 columns. *Why:* coffee: 1,259 orders and 23,478.75; the rest: 1,232 orders and 24,964.75. The revenues
add to 48,443.50, and the order counts add to 2,491 although there are only 1,800 orders. An order with both kinds of
line lands in both groups, and an order with two coffee lines is summed twice.

### 4. Repair: one row per key before the join

The repair comes before the join: reduce the table whose key repeats to one row per key, with `GROUP BY` on the join key
in a CTE (S13).

**Try it**: one row per order, flagged coffee or not.

<RunSQL query={`WITH order_flags AS (
  SELECT oi.order_id,
         MAX(CASE WHEN p.category = 'coffee' THEN 1 ELSE 0 END) AS has_coffee
  FROM order_items AS oi
  INNER JOIN products AS p ON oi.product_id = p.product_id
  GROUP BY oi.order_id
)
SELECT COUNT(*) AS orders,
       COUNT(DISTINCT order_id) AS distinct_ids,
       SUM(has_coffee) AS coffee_orders
FROM order_flags;`} />

<Aside type="tip" title="Remember">

- A join copies an order-level figure onto every line of that order.
- Add a figure only at the grain where it is stored.
- The repair: `GROUP BY` the join key in a CTE first, then join one row to one row.
- Check the row counts and the total against a control total taken before the join.

**Common trap: "`SUM(DISTINCT …)` fixes the inflated sum."** `DISTINCT` makes an aggregate consider each different value
once. It cannot tell a copy from a coincidence: orders 1002 and 1003 in the copy picture both total 12.50, so only one of
them would be added. Over all orders there are only 137 different totals, and adding each once gives 3,094.00, far below
the real sum. Reduce to one row per key instead.

</Aside>

Each order pairs with every one of its lines, so its figure is copied onto each of them and the sum adds every copy.

**Spot the flaw.** A colleague wants the average order value and reuses the join from unit 2:
