## How it works

*INNER JOIN* (S19) gave the pairing rule: a key that repeats pairs a row with every match. **Fan-out** is what that
rule does to an aggregate. A figure stored once per key is copied onto every row the join builds for that key, and
`SUM` adds every copy. Conceptually, four moves cause it, and a fifth, taken before the join, repairs it:

1. Start from a table whose grain is one row per order, holding a figure of the order, such as its total.
2. Join it to a table whose key repeats, such as the order lines. Each order row is paired with each of its lines.
3. The result now has the finer grain: one row per line. The order's total was copied onto each of those rows, as
   in the first picture above.
4. An aggregate reads the result as it stands: `SUM` adds every copy, `COUNT(*)` counts lines, and grouping by a column
   of the lines puts an order into every group where it has a line.
5. The repair comes before the join: reduce the table whose key repeats to one row per key, with `GROUP BY` on the
   join key in a CTE (S13). Then the join pairs one row with one row.

The rules:

- A join adds rows only for a key value that appears more than once on at least one side. If the key is unique on both
  sides, each key pairs at most once.
- Add a figure only at the grain where it is stored. A line's quantity can be added over lines; an order's total cannot.
- To diagnose a fan-out, compare the row count before and after the join, and compare the total with a control total
  taken before the join, naming the rows it covers.

**Excel.** The same trap appears when an order total is copied beside every line and added with `SUMIFS` (E7,
*Conditional totals with SUMIFS and COUNTIFS*): it adds the sum-range cells of every row that passes the tests, copies
included.

**A common misconception: "`SUM(DISTINCT …)` fixes the inflated sum."** `DISTINCT` makes an aggregate consider each
different value once. It cannot tell a copy from a coincidence: orders 1002 and 1003 in the picture both total 12.50,
so only one of them would be added. Over all orders there are only 137 different totals, and adding each once gives
3,094.00, far below the real sum. Reduce to one row per key instead.

## Worked example

Question: **how much did orders with coffee, and orders without, bring in?** Run the notebook's setup cell, then one
cell per step. Each step gives the shape of the result to expect. Every figure covers all 1,800 orders, the canceled
one included, and includes the extra-zero line of order 2075.

1. **Build `order_totals`.** Grain: one row per order.

   ```sql
   WITH order_totals AS (
     SELECT oi.order_id,
            SUM(oi.quantity * p.unit_price_usd - oi.discount_usd) AS order_total_usd
     FROM order_items AS oi
     INNER JOIN products AS p ON oi.product_id = p.product_id
     GROUP BY oi.order_id
   )
   SELECT COUNT(*) AS orders,
          COUNT(DISTINCT order_id) AS distinct_ids,
          SUM(order_total_usd) AS total_usd
   FROM order_totals;
   ```

   Expected: 1 row, 3 columns: `1800 | 1800 | 22754.25`. *Why:* the two counts match, so `order_id` is unique: one row
   per order. The total is S19's 22,754.25, the control total every later step must reproduce.

2. **Join the totals to the lines.** Before you run it: `order_totals` has 1,800 rows and there are 3,287 lines. How many
   rows will the join return, and will its `SUM` match step 1?

   ```sql
   WITH order_totals AS (/* as in step 1 */)
   SELECT COUNT(*) AS joined_rows,
          SUM(t.order_total_usd) AS total_usd
   FROM order_totals AS t
   INNER JOIN order_items AS oi ON t.order_id = oi.order_id;
   ```

   Expected: 1 row, 2 columns. *Why:* **3287** rows and **48443.50**, more than twice the control total. Each order
   total was added once per line.

3. **Ask the question the naive way.** One row per line, flagged coffee or not, joined to the totals.

   ```sql
   WITH order_totals AS (/* as in step 1 */),
   lines AS (
     SELECT oi.order_item_id, oi.order_id, p.category = 'coffee' AS is_coffee
     FROM order_items AS oi
     INNER JOIN products AS p ON oi.product_id = p.product_id
   )
   SELECT l.is_coffee,
          COUNT(DISTINCT t.order_id) AS orders,
          SUM(t.order_total_usd) AS revenue_usd
   FROM order_totals AS t
   INNER JOIN lines AS l ON t.order_id = l.order_id
   GROUP BY l.is_coffee
   ORDER BY l.is_coffee DESC;
   ```

   Expected: 2 rows, 3 columns. *Why:* coffee: 1,259 orders and 23,478.75; the rest: 1,232 orders and 24,964.75. The
   revenues add to 48,443.50, and the order counts add to 2,491 although there are only 1,800 orders. An order with
   both kinds of line lands in both groups, and an order with two coffee lines is summed twice.

4. **See the copies.**

   ```sql
   WITH order_totals AS (/* as in step 1 */),
   lines AS (/* as in step 3 */)
   SELECT l.order_item_id, l.order_id, l.is_coffee, t.order_total_usd
   FROM order_totals AS t
   INNER JOIN lines AS l ON t.order_id = l.order_id
   WHERE t.order_id = 1001
   ORDER BY l.order_item_id;
   ```

   Expected: 3 rows, 4 columns. *Why:* order 1001 has three lines (a Croissant and two coffees), so its 14.00 appears
   three times: twice among the coffee rows and once among the others. After the join one row is a line, and a
   per-order figure does not belong at that grain.

5. **Repair: reduce the many side to one row per order.**

   ```sql
   WITH order_flags AS (
     SELECT oi.order_id,
            MAX(CASE WHEN p.category = 'coffee' THEN 1 ELSE 0 END) AS has_coffee
     FROM order_items AS oi
     INNER JOIN products AS p ON oi.product_id = p.product_id
     GROUP BY oi.order_id
   )
   SELECT COUNT(*) AS orders,
          COUNT(DISTINCT order_id) AS distinct_ids,
          SUM(has_coffee) AS coffee_orders
   FROM order_flags;
   ```

   Expected: 1 row, 3 columns: `1800 | 1800 | 1259`. *Why:* `GROUP BY order_id` makes one row per order, and `MAX` is 1
   when any line of the order is coffee (conditional aggregation, S9). The unique key and the 1,259 coffee orders are
   what the join needs.

6. **Join two tables with one row per order.** Before you run it: how many rows will the join return?

   ```sql
   WITH order_totals AS (/* as in step 1 */),
   order_flags AS (/* as in step 5 */)
   SELECT f.has_coffee,
          COUNT(*) AS orders,
          SUM(t.order_total_usd) AS revenue_usd
   FROM order_totals AS t
   INNER JOIN order_flags AS f ON t.order_id = f.order_id
   GROUP BY f.has_coffee
   ORDER BY f.has_coffee DESC;
   ```

   Expected: 2 rows, 3 columns. *Why:* each side has one row per order, so the join returns 1,800 rows and cannot
   multiply them. Orders with coffee: 1,259 orders and 16,958.00. The others: 541 orders and 5,796.25. That answers the
   owner.

7. **Reconcile.** 16,958.00 + 5,796.25 = **22,754.25**, the control total of step 1, and 1,259 + 541 = 1,800. A second
   route for the coffee orders:

   ```sql
   SELECT COUNT(DISTINCT oi.order_id) AS coffee_orders
   FROM order_items AS oi
   INNER JOIN products AS p ON oi.product_id = p.product_id
   WHERE p.category = 'coffee';
   ```

   Expected: 1 row, 1 column: `1259`. E21's completed-only Sales of 22,749.25 is 5.00 lower: canceled order 1461 is a
   Mocha, so its 5.00 sits in the coffee figure here.

<details>
<summary>Explain it in your own words: why can the join in step 6 not multiply rows, while the one in step 3 did?</summary>

In step 3 the key `order_id` repeated on the lines side, so each order paired with several rows. In step 6 both sides
hold one row per `order_id`, so each order pairs with exactly one row. You made the key unique by grouping first.

</details>

<summary>Answer</summary>

Each order pairs with every one of its lines, so its figure is copied onto each of them and the sum adds every copy.
Repair it by aggregating the repeating side to one row per key before the join, and reconcile the result against a
control total taken before the join.

**Spot the flaw.** A colleague wants the average order value and reuses the join from step 2:

```sql
WITH order_totals AS (
  SELECT oi.order_id,
         SUM(oi.quantity * p.unit_price_usd - oi.discount_usd) AS order_total_usd
  FROM order_items AS oi
  INNER JOIN products AS p ON oi.product_id = p.product_id
  GROUP BY oi.order_id
)
SELECT ROUND(AVG(t.order_total_usd), 2) AS avg_order_usd
FROM order_totals AS t
INNER JOIN order_items AS oi ON t.order_id = oi.order_id;
```

Expected from that query: 1 row, 1 column: `14.74`. The colleague reports "the average order is 14.74". What went wrong, and what
is the right query?

<Solution>

The join to `order_items` is not needed, and it distorts the average. It returns 3,287 rows, one per line, so an order
with three lines is averaged three times and a one-line order once: bigger orders weigh more. The 14.74 is 48,443.50
divided by 3,287, not 22,754.25 divided by 1,800. Average the table that has one row per order:

```sql
SELECT ROUND(AVG(order_total_usd), 2) AS avg_order_usd FROM order_totals;
```

Expected: 1 row, 1 column: `12.64` (the same CTE in front). That is for all 1,800 orders; E21's 12.65 is for the 1,799
completed ones.

</Solution>
