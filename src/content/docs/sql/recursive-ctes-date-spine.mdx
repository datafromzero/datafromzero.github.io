## The question

The owner of the cafes asks:

> Someone told me cash averages 1.88 orders a day. But some days nobody paid cash at all. How many days is that, and
> what is the real average cash day?

The 1.88 comes from the CTE lesson (S13): it averages the days that have at least one completed cash order. The first
rows of that grouped query:

| order_day | cash_orders |
|---|---:|
| 2026-01-04 | 1 |
| 2026-01-05 | 3 |
| 2026-01-06 | 2 |

January 1 to 3 are not there.

   timestamp `ordered_at` into a date.

   <details>
   <summary>Answer</summary>

   `CAST(ordered_at AS DATE)`. S13 used it to count orders per day.

   </details>

2. In *NULL: unknown is not zero* (S4), `COUNT(*)` gives 1,800 on `orders` and `COUNT(customer_id)` gives 1,799. Why?

   <details>
   <summary>Answer</summary>

   `COUNT(column)` skips empty values, and the one walk-in order has no customer. You need this today.

## The big idea

A **recursive CTE** builds a table in rounds, each round starting from the rows the last one made. Here it builds a **date spine**, one row per day, so the days with no orders show up as zero.

## Learn by doing

Five small steps. Each gives you one idea, then you try it in the editor under it.

### 1. A day with no orders has no row

In a sheet you can type every date down a column and count the orders beside each one: a day with none shows 0. A query that only groups the orders cannot do that, because a group with no rows does not exist.

A **date spine**, a table with one row per day, brings the empty days back. You need one when the answer must have a row for every period: a chart of every day, or `LAG` and moving averages (S16), which look at the previous row, not the previous day. A total for the period does not.

**Try it**. Counts cover completed cash orders of all three stores, over the 181 days from January 1 to June 30. They count orders, not units, so the extra-zero line (order 2075) does not matter. Before you run it: the period has 181 days. How many rows will this query return?

<RunSQL query={`SELECT CAST(ordered_at AS DATE) AS order_day, COUNT(*) AS cash_orders
FROM orders
WHERE payment_method = 'cash' AND status = 'completed'
GROUP BY CAST(ordered_at AS DATE)
ORDER BY order_day;`} />

Expected: 2 columns.

<details>
<summary>Check your prediction</summary>

134 rows, not 181. The first row is January 4, so January 1 to 3 have no row.

</details>

### 2. Build the spine in rounds

Typing 181 dates is slow, so let the query build them. A **recursive CTE** is written `WITH RECURSIVE name AS (anchor UNION ALL recursive part)`. The DuckDB documentation: "`WITH RECURSIVE` allows the definition of CTEs which can refer to themselves." It runs in rounds:

1. The **anchor** runs once and gives the first row, January 1.
2. The **recursive part** runs next. Inside it, the CTE's name stands for the rows the previous round produced. It returns the next rows, and they join the result.
3. The rounds repeat until one returns no rows, and the CTE is then complete.

*Excel:* a date is a number (E11, *Dates as numbers*), so `=A2+1` is the next day: the first date you type is the anchor, and `=A2+1` filled down is the recursive part.

**Try it**.

<RunSQL query={`WITH RECURSIVE spine(order_day) AS (
  SELECT DATE '2026-01-01'
  UNION ALL
  SELECT order_day + 1 FROM spine WHERE order_day < DATE '2026-06-30'
)
SELECT COUNT(*) AS days, MIN(order_day) AS first_day, MAX(order_day) AS last_day
FROM spine;`} />

Expected: 1 row, 3 columns: `181`, `2026-01-01`, `2026-06-30`. *Why:* the anchor is the first day; the recursive part adds 1 to the previous day (the DuckDB documentation lists `date + integer` as "addition of days") and stops at June 30. `spine(order_day)` names the one column.

<details>
<summary>Explain it in your own words: what would happen here without the WHERE?</summary>

Every round reads a day and adds 1, so a next day always exists. Nothing else could make a round come back empty. With the `WHERE`, round 181 reads June 30, the test fails, and the rounds stop.

</details>

A recursive CTE must be written so that it ends. The documentation: "Note that the query must be formulated in a way that ensures termination, otherwise, it may run into an infinite loop." Here a `WHERE` in the recursive part does it.

DuckDB also has a shorter way to the same spine.

**Try it**.

<RunSQL query={`SELECT COUNT(*) AS days,
       MIN(CAST(generate_series AS DATE)) AS first_day,
       MAX(CAST(generate_series AS DATE)) AS last_day
FROM generate_series(TIMESTAMP '2026-01-01', TIMESTAMP '2026-06-30', INTERVAL 1 DAY);`} />

Expected: 1 row, 3 columns, the same as above. *Why:* the DuckDB documentation says `generate_series` makes "a table of timestamps in the closed range, stepping by the interval", so both ends are included; `range` leaves out the end. The column holds timestamps, hence the `CAST`.

### 3. Join the facts onto the spine

Put the spine on the left of a `LEFT JOIN`: it keeps every row of the left table, and the right table's columns are `NULL` for a row with no partner. Bring the facts to one row per day first, in a second CTE (`cash_daily`). A day with two fact rows would pair with both and appear twice (*Join fan-out*, S21).

**Try it**. The daily counts become `cash_daily`, and the spine goes on the left.

<RunSQL query={`WITH RECURSIVE spine(order_day) AS (
  SELECT DATE '2026-01-01'
  UNION ALL
  SELECT order_day + 1 FROM spine WHERE order_day < DATE '2026-06-30'
),
cash_daily AS (
  SELECT CAST(ordered_at AS DATE) AS order_day, COUNT(*) AS cash_orders
  FROM orders
  WHERE payment_method = 'cash' AND status = 'completed'
  GROUP BY CAST(ordered_at AS DATE)
)
SELECT s.order_day, c.cash_orders
FROM spine AS s
LEFT JOIN cash_daily AS c ON c.order_day = s.order_day
ORDER BY s.order_day
LIMIT 6;`} />

Expected: 6 rows, 2 columns: January 1 to 3 show `NULL`, then 1, 3 and 2. *Why:* a LEFT JOIN keeps every spine day (S20).

### 4. Turn NULL into 0

An empty day is `NULL`, not 0. `COUNT(c.cash_orders)` skips the `NULL` days, so the difference from `COUNT(*)` is the number of empty days. `AVG` also skips `NULL`, so `COALESCE` must turn the empty days into 0 first.

**Try it**.

<RunSQL query={`WITH RECURSIVE spine(order_day) AS (
  SELECT DATE '2026-01-01'
  UNION ALL
  SELECT order_day + 1 FROM spine WHERE order_day < DATE '2026-06-30'
),
cash_daily AS (
  SELECT CAST(ordered_at AS DATE) AS order_day, COUNT(*) AS cash_orders
  FROM orders
  WHERE payment_method = 'cash' AND status = 'completed'
  GROUP BY CAST(ordered_at AS DATE)
)
SELECT COUNT(*) AS days,
       COUNT(*) - COUNT(c.cash_orders) AS empty_days,
       SUM(COALESCE(c.cash_orders, 0)) AS cash_orders,
       ROUND(AVG(COALESCE(c.cash_orders, 0)), 2) AS avg_cash_day
FROM spine AS s
LEFT JOIN cash_daily AS c ON c.order_day = s.order_day;`} />

Expected: 1 row, 4 columns: `181 | 47 | 252 | 1.39`. *Why:* without the `COALESCE`, the average would be 1.88 again.

**Check**: count the same orders without the spine.

<RunSQL query={`SELECT COUNT(*) AS cash_orders FROM orders WHERE payment_method = 'cash' AND status = 'completed';`} />

Expected: 1 row, 1 column: `252`, the same as above. Also 134 days with orders plus 47 empty days make 181, and 252 ÷ 134 = 1.88 (the old figure) against 252 ÷ 181 = 1.39. Answer: **47 days had no completed cash order, and the average cash day is 1.39 orders.** The 1.88 was the average of the busy-enough days only.

### 5. The same machine on a hierarchy

Customers carry `referred_by`, the customer who brought them in. A recursive CTE can follow that chain. The anchor is one customer, and each round joins the customers whose `referred_by` is in the previous round's rows.

**Try it**. Who did customer 24 bring in, and who did they bring in?

<RunSQL query={`WITH RECURSIVE chain(customer_id, referred_by, depth) AS (
  SELECT customer_id, referred_by, 0
  FROM customers
  WHERE customer_id = 24
  UNION ALL
  SELECT c.customer_id, c.referred_by, chain.depth + 1
  FROM customers AS c
  JOIN chain ON c.referred_by = chain.customer_id
)
SELECT * FROM chain
ORDER BY depth, customer_id;`} />

Expected: 4 rows, 3 columns: customer 24 at depth 0, customers 30 and 34 at depth 1, customer 80 at depth 2. *Why:* the rounds find 30 and 34, then 80, then nobody, which ends it. No `WHERE` is needed here, because the data runs out (a referral loop in the data would never end; there is none here).

Check it another way:

<RunSQL query={`SELECT customer_id, referred_by FROM customers WHERE referred_by IN (24, 30, 34, 80);`} />

Expected: 3 rows, 2 columns: 30, 34 and 80.

<Aside type="tip" title="Remember">

- A group with no rows has no row: when the answer needs every day, build a date spine.
- A recursive CTE is an anchor, then a recursive part that repeats until a round returns no rows. It must be written to end.
- Spine on the left, facts joined on, one row per day, and `COALESCE` for 0.

**Common trap: "inside the recursive part, the CTE's name means everything found so far."** In the form used here, it means only the rows the previous round produced. That is why the recursive part can add 1 to a single day: if the name meant every day found, each round would add a day to all of them.

</Aside>

## Check yourself

1. Without looking back: in a recursive CTE, what are the anchor and the recursive part, and what ends the recursion?

   <details>
   <summary>Answer</summary>

   The anchor runs once and gives the first rows. The recursive part reads the previous round's rows and returns the
   next ones. The recursion ends when a round returns no rows, so the recursive part needs a `WHERE` (or data that runs
   out) to get there.

   </details>

<Exercise id="sql-recursive-ctes-date-spine-3">

**Spot the flaw.** A colleague joins the spine straight to `orders` and counts with `COUNT(*)`:

<RunSQL query={`WITH RECURSIVE spine(order_day) AS (
  SELECT DATE '2026-01-01'
  UNION ALL
  SELECT order_day + 1 FROM spine WHERE order_day < DATE '2026-06-30'
),
daily AS (
  SELECT s.order_day, COUNT(*) AS cash_orders
  FROM spine AS s
  LEFT JOIN orders AS o
    ON CAST(o.ordered_at AS DATE) = s.order_day
   AND o.payment_method = 'cash' AND o.status = 'completed'
  GROUP BY s.order_day
)
SELECT COUNT(*) AS days, SUM(cash_orders) AS cash_orders FROM daily;`} />

Expected: 1 row, 2 columns. Run it and compare the second number with the check of unit 4. What went wrong, and what is the fix?

<Solution>

The query returns `181 | 299`, but there are only 252 completed cash orders. On an empty day the LEFT JOIN keeps the
spine day and pairs it with one all-`NULL` row, and `COUNT(*)` counts that row as 1. The 47 empty days add 47:
252 + 47 = 299. The conditions are in `ON` on purpose (S20), so the spine days survive; the fault is the count.

Count a column of the right table, which is `NULL` on an empty day:

```sql
SELECT s.order_day, COUNT(o.order_id) AS cash_orders
```

With that change the final query returns `181 | 252`.

</Solution>
