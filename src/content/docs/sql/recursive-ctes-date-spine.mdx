that only groups the orders cannot do that, because a group with no rows does not exist. A **date spine** is a table

## How it works

The days of a report should not depend on which days had orders. A **date spine**, a table with one row per day,
supplies the days, and the facts are joined on to fill in the numbers. Conceptually, you do three things:

1. Build the spine: one row per day, from the first day to the last.
2. Give the facts the same grain, one row per day (`cash_daily` in step 3).
3. `LEFT JOIN` the facts onto the spine, with the spine on the left.

A **recursive CTE** builds the spine without typing 181 dates. It is written `WITH RECURSIVE name AS (anchor UNION ALL
recursive part)`. The DuckDB documentation: "`WITH RECURSIVE` allows the definition of CTEs which can refer to
themselves." It runs in rounds, as the round-by-round picture shows:

1. The **anchor** runs once and gives the first row, January 1.
2. The **recursive part** runs next. Inside it, the CTE's name stands for the rows the previous round produced. It
   returns the next rows, and they join the result.
3. The rounds repeat until one returns no rows, and the CTE is then complete.

The rules:

- **`LEFT JOIN` keeps every row of the left table**, here the spine, and the right table's columns are `NULL` for a row
  with no partner.
- **Group the facts before the join.** A day with two fact rows would pair twice and appear twice.
- **A recursive CTE must be written so that it ends.** The documentation: "Note that the query must be formulated in a
  way that ensures termination, otherwise, it may run into an infinite loop." Here a `WHERE` in the recursive part does
  it.
- **You need a spine when the answer must have a row for every period**: a chart of every day, or `LAG` and moving
  averages (S16), which look at the previous row, not the previous day. A total for the period does not.

**Excel.** A date is a number (E11, *Dates as numbers*), so `=A2+1` is the next day: the first date you type is the
anchor, and `=A2+1` filled down is the recursive part.

**A common misconception: "inside the recursive part, the CTE's name means everything found so far."** In the form used
here, it means only the rows the previous round produced. That is why the recursive part can add 1 to a single day: if
the name meant every day found, each round would add a day to all of them.

## Worked example

Question: **how many days had no completed cash order, and what is the average cash day?** Run the notebook's setup
cell, then one cell per step. Counts cover completed cash orders of all three stores, over the 181 days from January 1
to June 30. They count orders, not units, so the extra-zero line (order 2075) does not matter.

1. **Predict, then see the gap.** Before you run it: the period has 181 days. How many rows will this query return?

   ```sql
   SELECT CAST(ordered_at AS DATE) AS order_day, COUNT(*) AS cash_orders
   FROM orders
   WHERE payment_method = 'cash' AND status = 'completed'
   GROUP BY CAST(ordered_at AS DATE)
   ORDER BY order_day;
   ```

   Expected: 2 columns. *Why:* a group exists only if some row falls in it.

   <details>
   <summary>Check your prediction</summary>

   134 rows, not 181. The first row is January 4, so January 1 to 3 have no row.

   </details>

2. **Generate every day.**

   ```sql
   WITH RECURSIVE spine(order_day) AS (
     SELECT DATE '2026-01-01'
     UNION ALL
     SELECT order_day + 1 FROM spine WHERE order_day < DATE '2026-06-30'
   )
   SELECT COUNT(*) AS days, MIN(order_day) AS first_day, MAX(order_day) AS last_day
   FROM spine;
   ```

   Expected: 1 row, 3 columns: `181`, `2026-01-01`, `2026-06-30`. *Why:* the anchor is the first day; the recursive
   part adds 1 to the previous day (the DuckDB documentation lists `date + integer` as "addition of days") and stops
   at June 30, as in the second picture. `spine(order_day)` names the one column.

3. **Join the facts onto the spine.** The daily counts become a second CTE, `cash_daily`, and the spine goes on the
   left:

   ```sql
   WITH RECURSIVE spine(order_day) AS (...),   -- as in step 2
   cash_daily AS (
     SELECT CAST(ordered_at AS DATE) AS order_day, COUNT(*) AS cash_orders
     FROM orders
     WHERE payment_method = 'cash' AND status = 'completed'
     GROUP BY CAST(ordered_at AS DATE)
   )
   SELECT s.order_day, c.cash_orders
   FROM spine AS s
   LEFT JOIN cash_daily AS c ON c.order_day = s.order_day
   ORDER BY s.order_day
   LIMIT 6;
   ```

   Expected: 6 rows, 2 columns: January 1 to 3 show `NULL`, then 1, 3 and 2. *Why:* a LEFT JOIN keeps every spine
   day (S20). `cash_daily` has one row per day, so the join pairs one row with one row and does not multiply them
   (*Join fan-out*, S21). In the notebook the cell holds the full text.

4. **Count, and turn NULL into 0.**

   ```sql
   WITH RECURSIVE spine(order_day) AS (...),   -- as in step 2
   cash_daily AS (...)                         -- as in step 3
   SELECT COUNT(*) AS days,
          COUNT(*) - COUNT(c.cash_orders) AS empty_days,
          SUM(COALESCE(c.cash_orders, 0)) AS cash_orders,
          ROUND(AVG(COALESCE(c.cash_orders, 0)), 2) AS avg_cash_day
   FROM spine AS s
   LEFT JOIN cash_daily AS c ON c.order_day = s.order_day;
   ```

   Expected: 1 row, 4 columns: `181 | 47 | 252 | 1.39`. *Why:* `COUNT(c.cash_orders)` skips the `NULL` days, so the difference from
   `COUNT(*)` is the number of empty days. `AVG` also skips `NULL`, so `COALESCE` must turn them into 0 first; otherwise
   the average would be 1.88 again.

5. **Verify.** Count the same orders without the spine:

   ```sql
   SELECT COUNT(*) AS cash_orders FROM orders WHERE payment_method = 'cash' AND status = 'completed';
   ```

   Expected: 1 row, 1 column: `252`, the same as step 4. Also 134 days with orders plus 47 empty days make 181, and
   252 ÷ 134 = 1.88 (the old figure) against 252 ÷ 181 = 1.39. Answer: **47 days had no completed cash order, and the
   average cash day is 1.39 orders.** The 1.88 was the average of the busy-enough days only.

6. **A shorter way to the same spine.**

   ```sql
   SELECT COUNT(*) AS days,
          MIN(CAST(generate_series AS DATE)) AS first_day,
          MAX(CAST(generate_series AS DATE)) AS last_day
   FROM generate_series(TIMESTAMP '2026-01-01', TIMESTAMP '2026-06-30', INTERVAL 1 DAY);
   ```

   Expected: 1 row, 3 columns, the same as step 2. *Why:* the DuckDB documentation says `generate_series` makes
   "a table of timestamps in the closed range, stepping by the interval", so both ends are included; `range` leaves out
   the end. The column holds timestamps, hence the `CAST`.

7. **Read a recursive CTE on a hierarchy.** Customers carry `referred_by`, the customer who brought them in. Who did
   customer 24 bring in, and who did they bring in?

   ```sql
   WITH RECURSIVE chain(customer_id, referred_by, depth) AS (
     SELECT customer_id, referred_by, 0
     FROM customers
     WHERE customer_id = 24
     UNION ALL
     SELECT c.customer_id, c.referred_by, chain.depth + 1
     FROM customers AS c
     JOIN chain ON c.referred_by = chain.customer_id
   )
   SELECT * FROM chain
   ORDER BY depth, customer_id;
   ```

   Expected: 4 rows, 3 columns: customer 24 at depth 0, customers 30 and 34 at depth 1, customer 80 at depth 2.
   *Why:* the anchor is customer 24. Each round joins the customers whose `referred_by` is in the previous round: first
   30 and 34, then 80, then nobody, which ends it. No `WHERE` is needed, because the data runs out (a referral loop
   in the data would never end; there is none here).
   Check: `SELECT customer_id, referred_by FROM customers WHERE referred_by IN (24, 30, 34, 80);` returns 3 rows,
   2 columns: 30, 34 and 80.

<details>
<summary>Explain it in your own words: what would happen in step 2 without the WHERE?</summary>

The recursive part always finds a next day (`order_day + 1`), so no round would be empty and the query would never
stop. The `WHERE` is what makes round 181 return nothing.

</details>

```sql
       COUNT(*) - COUNT(m.mobile_orders) AS empty_days,
       SUM(COALESCE(m.mobile_orders, 0)) AS mobile_orders,
       ROUND(AVG(COALESCE(m.mobile_orders, 0)), 2) AS avg_mobile_day
FROM spine AS s
LEFT JOIN mobile_daily AS m ON m.order_day = s.order_day;
```

`181 | 9 | 546 | 3.02`. Mobile had no completed order on 9 days, and the average mobile day is 3.02 (the CTE lesson's
3.17 is 546 ÷ 172 days).

</Solution>

</Exercise>

```sql
WITH RECURSIVE spine(order_day) AS (
  SELECT DATE '2026-03-25'
  UNION ALL
  SELECT order_day + 1 FROM spine WHERE order_day < DATE '2026-04-07'
),
harbor_daily AS (
  SELECT CAST(ordered_at AS DATE) AS order_day, COUNT(*) AS orders
  FROM orders
  WHERE store_id = 3
  GROUP BY CAST(ordered_at AS DATE)
```

1. Without looking back: in a recursive CTE, what are the anchor and the recursive part, and what ends the recursion?

   <details>
   <summary>Answer</summary>

   The anchor runs once and gives the first rows. The recursive part reads the previous round's rows and returns the
   next ones. The recursion ends when a round returns no rows, so the recursive part needs a `WHERE` (or data that runs
   out) to get there.

<Exercise id="sql-recursive-ctes-date-spine-3">

**Spot the flaw.** A colleague joins the spine straight to `orders` and counts with `COUNT(*)`:

```sql
WITH RECURSIVE spine(order_day) AS (
  SELECT DATE '2026-01-01'
  UNION ALL
  SELECT order_day + 1 FROM spine WHERE order_day < DATE '2026-06-30'
),
daily AS (
  SELECT s.order_day, COUNT(*) AS cash_orders
  FROM spine AS s
  LEFT JOIN orders AS o
    ON CAST(o.ordered_at AS DATE) = s.order_day
   AND o.payment_method = 'cash' AND o.status = 'completed'
  GROUP BY s.order_day
)
SELECT COUNT(*) AS days, SUM(cash_orders) AS cash_orders FROM daily;
```

Expected: 1 row, 2 columns. Run it and compare the second number with step 5. What went wrong, and what is the fix?

<Solution>

The query returns `181 | 299`, but there are only 252 completed cash orders. On an empty day the LEFT JOIN keeps the
spine day and pairs it with one all-`NULL` row, and `COUNT(*)` counts that row as 1. The 47 empty days add 47:
252 + 47 = 299. The conditions are in `ON` on purpose (S20), so the spine days survive; the fault is the count.

Count a column of the right table, which is `NULL` on an empty day:

```sql
SELECT s.order_day, COUNT(o.order_id) AS cash_orders
```

With that change the final query returns `181 | 252`.

</Solution>
