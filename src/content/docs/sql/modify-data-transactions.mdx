## The question

> stock sheet without losing a change, and without a typo wiping the sheet?

| store_id | product_id | units_on_hand |

| 1 | 1 | 40 |
| 1 | 6 | 12 |
| 1 | 10 | 25 |

## The big idea

`INSERT`, `UPDATE` and `DELETE` change the rows of a table, and a **transaction** groups changes so that they all happen or
none do.

## Learn by doing

Five small steps. Run this block first; it makes `stock`:

<RunSQL query={`CREATE OR REPLACE TABLE stock (
  store_id INTEGER NOT NULL,
  product_id INTEGER NOT NULL,
  units_on_hand INTEGER NOT NULL CHECK (units_on_hand >= 0),
  PRIMARY KEY (store_id, product_id)
);
INSERT INTO stock VALUES (1, 1, 40), (1, 10, 25), (1, 6, 12);
SELECT * FROM stock ORDER BY product_id;`} />

### 1. Add rows

`INSERT ... VALUES` adds the rows you type. `INSERT ... SELECT` stores every row the `SELECT` returns.

**Try it.** The second statement copies the products of store 1 to store 2, each at 10 units. Run it
once: the key of S31 refuses the same rows a second time.

<RunSQL query={`INSERT INTO stock VALUES (1, 7, 18);
INSERT INTO stock SELECT 2, product_id, 10 FROM stock WHERE store_id = 1;
SELECT * FROM stock ORDER BY store_id, product_id;`} />

Expected: 8 rows, 3 columns (the page shows the last result). *Why:* store 1 now has four products, and store 2 got a copy of
each.

### 2. Preview, then change

`UPDATE` changes the named columns in every row that satisfies its `WHERE`, and `DELETE` removes those rows. So make a habit: **write the `WHERE` as a `SELECT` first**, read the rows it returns,
and only then change them.

**Try it.** Croissants at Old Town got a delivery of 24. Before you run it: how many rows should this
preview return?

<RunSQL query={`SELECT * FROM stock WHERE store_id = 1 AND product_id = 10;`} />

Now the `UPDATE`, with the same `WHERE`. Its `Count` must match the preview.

<RunSQL query={`UPDATE stock SET units_on_hand = units_on_hand + 24 WHERE store_id = 1 AND product_id = 10;`} />

<RunSQL query={`SELECT * FROM stock WHERE store_id = 1 AND product_id = 10;`} />

Expected: the preview returns 1 row, 3 columns; the `UPDATE` a `Count` of 1; the check 1 row, 3 columns, with 49 croissants.
*Why:* had the preview returned more rows than you meant, you would have stopped.

**Try it.** Green Tea is dropped from store 1: preview, delete, count.

<RunSQL query={`SELECT * FROM stock WHERE store_id = 1 AND product_id = 7;`} />

<RunSQL query={`DELETE FROM stock WHERE store_id = 1 AND product_id = 7;`} />

<RunSQL query={`SELECT COUNT(*) AS rows_left FROM stock;`} />

Expected: the preview returns 1 row; the `DELETE` a `Count` of 1; the last query 1 row, 1 column: 7 rows left.

### 3. A transaction you can undo

A **transaction** is a group of statements that succeed or fail as one. `BEGIN` opens it. `COMMIT` keeps every change and
`ROLLBACK` throws them all away. Without `BEGIN`, a statement that succeeds is committed at once (DuckDB calls this
auto-commit mode).

**Try it.** Make a mistake on purpose: a `DELETE` with no `WHERE`. Before you run it: what does the count
read inside the transaction, and what after the `ROLLBACK`? Run the blocks in order. If a block says a transaction is already
open or aborted, run `ROLLBACK`, or press **Reset data**.

<RunSQL query={`BEGIN;
DELETE FROM stock;
SELECT COUNT(*) AS rows_left FROM stock;`} />

<RunSQL query={`ROLLBACK;
SELECT COUNT(*) AS rows_left FROM stock;`} />

Expected: 1 row, 1 column each time. *Why:* the first block leaves the transaction open on purpose, so run the second next.
With no `WHERE`, `DELETE` removes every row, so the count inside is **0**. After `ROLLBACK` it is back to **7**: all of it, or none
(**atomicity**).

### 4. Two tills, one count

Ana and Ben each sell a croissant at the same moment. Each works in a session of their own, inside a transaction, on the
same row.

**Read it.** This needs two sessions, one for Ana and one for Ben, and a page has only one, so read it instead of
running it.

```sql
-- Ana's session
BEGIN;
UPDATE stock SET units_on_hand = units_on_hand - 1 WHERE store_id = 1 AND product_id = 10;
SELECT units_on_hand FROM stock WHERE store_id = 1 AND product_id = 10;
-- Ben's session
SELECT units_on_hand FROM stock WHERE store_id = 1 AND product_id = 10;
BEGIN;
UPDATE stock SET units_on_hand = units_on_hand - 1 WHERE store_id = 1 AND product_id = 10;
```

**Predict:** what does Ben's `SELECT` show, and what happens to his `UPDATE`?

Result: Ana sees her own change (48) and Ben still sees 49, because the changes of an open transaction are invisible to
other transactions until it completes (the PostgreSQL tutorial): isolation. DuckDB's Concurrency page describes
multi-version concurrency control with optimistic concurrency. When two transactions change the same row at the same time,
the second to try fails with a conflict error: Ben's `UPDATE` fails with the message `Conflict on update!`, and DuckDB's
advice is to rerun that transaction. The rerun: Ben runs `ROLLBACK`, Ana runs `COMMIT`, then Ben runs `BEGIN`, the
same `UPDATE` and `COMMIT`.

Four promises about transactions go by the name **ACID** (the PostgreSQL glossary). *Atomicity* you saw in unit 3.
*Consistency*: the data stays within its rules, such as the keys of S31. *Isolation* you just saw. *Durability*: a committed
change survives a crash. This database lives in memory, so durability cannot be shown.

### 5. Reload a store, then check

A load is **idempotent** if running it twice gives the same result as running it once. A reload that deletes first and
then inserts is. `campus_count` is a staging table of Campus's new counts.

**Try it.** The staging table has three rows, for products 1, 10 and 6.

<RunSQL query={`CREATE OR REPLACE TABLE campus_count (store_id INTEGER, product_id INTEGER, units_on_hand INTEGER);
INSERT INTO campus_count VALUES (2, 1, 30), (2, 10, 14), (2, 6, 9);
SELECT * FROM campus_count;`} />

Now the reload. Run it twice, then the check.

<RunSQL query={`BEGIN;
DELETE FROM stock WHERE store_id = 2;
INSERT INTO stock SELECT * FROM campus_count;
COMMIT;`} />

<RunSQL query={`SELECT COUNT(*) AS products, SUM(units_on_hand) AS units FROM stock WHERE store_id = 2;`} />

Expected: 1 row, 2 columns; the same after one run and after two. *Why:* the block deletes store 2's rows and inserts the
new ones, so a second run starts from the same place. A plain `INSERT` of rows the table already holds fails. If the
`INSERT` fails inside the block, `ROLLBACK` brings the old rows back. DuckDB also has `INSERT OR IGNORE` and `ON CONFLICT`
for this; the data engineer stage returns to them.

**Try it.** Check the whole table.

<RunSQL query={`SELECT store_id, COUNT(*) AS products, SUM(units_on_hand) AS units
FROM stock
GROUP BY store_id
ORDER BY store_id;`} />

Expected: 2 rows, 3 columns. *Why:* store 1 has 3 products and 99 units: Espresso 40, Cold Brew 12 and Croissants 47, which
is 25 + 24 delivered - 2 sold. Store 2 has 3 products and 53 units, the sum of `campus_count`.

<Aside type="tip" title="Remember">

- `SELECT` the rows first; change them only with a `WHERE` you have read.
- `BEGIN` ... `COMMIT` keeps a change, `BEGIN` ... `ROLLBACK` discards it.
- Other sessions see none of an open transaction. A clash on one row makes the second one fail: rerun it.
- A load you can run twice with the same result is idempotent.

**Common trap: "`ROLLBACK` is an undo button for anything I ran."** It discards only what the open transaction changed. A
statement run outside a transaction is already committed, and `ROLLBACK` then says `cannot rollback - no transaction is
active`.

</Aside>

## Check yourself

Without looking back: say the four ACID letters in plain words, and what an idempotent load is.

<details>
<summary>Answer</summary>

Atomicity: all of a transaction's changes happen, or none. Consistency: the data always obeys its rules. Isolation:
others do not see your changes until you commit. Durability: a committed change survives a crash. An idempotent load
leaves the same result whether you run it once or twice.

</details>

<Exercise id="sql-modify-data-transactions-3">

**Spot the flaw.** A colleague's till program counts a sale in three moves: read the count, subtract 1 in the program,
write the number back. Ana's till and Ben's till each sell a croissant at the same moment, with 49 in stock. Both read 49
before either writes, and both write 48. The block builds the table and runs the two writes (one after the other here, as a page has one session). The colleague says it worked, because no error appeared.

<RunSQL query={`CREATE OR REPLACE TABLE stock_ex3 (

Expected: 1 row, 1 column. What went wrong, and what is the fix?

<details>
<summary>Hint</summary>

Two croissants were sold. How many should be left, and which write did the second `UPDATE` overwrite?

</details>

<details>
<summary>Half-solution</summary>

Start from: "The count ends at 48, but it should be ... The second write replaced the first, because each till wrote a number it had read ..."

<Solution>

The count ends at **48**, and it should be 47. Both tills read 49, so both wrote 48, and the second write overwrote
the first: one sale vanished, with no error. Plain statements commit one at a time, so nothing made the tills wait.

Let the database do the arithmetic in one statement:

```sql
UPDATE stock_ex3 SET units_on_hand = units_on_hand - 1 WHERE store_id = 1 AND product_id = 10;
```

Each statement subtracts from the number as it is now, so two sales leave 47. When a change needs several statements,
wrap them in `BEGIN` and `COMMIT`; if DuckDB reports a conflict, roll back and rerun.

</Solution>
