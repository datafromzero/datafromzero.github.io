Three statements change data. `INSERT` adds rows, `UPDATE` changes values in rows that exist, and `DELETE` removes
rows. `UPDATE` and `DELETE` act on **every row** unless a `WHERE` narrows them. So the habit of this lesson: **write
the `WHERE` as a `SELECT` first**, read the rows it returns, and only then change them.

A **transaction** is a group of statements that succeed or fail as one. `BEGIN` opens it, `COMMIT` keeps its changes
and `ROLLBACK` throws them away. Without `BEGIN`, DuckDB commits each statement as soon as it succeeds. The four
letters of **ACID** describe what a database promises about transactions (the PostgreSQL glossary names them):

| Letter | In plain words | Where you meet it |
|---|---|---|
| Atomicity | all of a transaction's changes happen, or none | step 4, `ROLLBACK` |
| Consistency | the data always obeys its rules, such as the key of S31 | step 6 and exercise 2, a repeated key is refused |
| Isolation | others do not see your changes until you commit | step 5, Ben still sees 49 |
| Durability | once committed, a change survives a crash | cannot be shown here |

The notebook's database lives in memory, so durability cannot be shown. DuckDB's documentation says that a commit
writes the changes to disk when the database is a file.

An **idempotent** load gives the same result when you run it twice as when you run it once. It matters because jobs
are re-run after a failure, and a re-run must not double the data.

## Worked example

Question: **how do we change the stock sheet safely, and let two people edit the same count?** Run the notebook's
setup cell and the `stock` cell, then one cell per step. Each step gives the shape of the result to expect.

1. **Insert one row, then many.**

   ```sql
   INSERT INTO stock VALUES (1, 7, 18);
   INSERT INTO stock SELECT 2, product_id, 10 FROM stock WHERE store_id = 1;
   SELECT * FROM stock ORDER BY store_id, product_id;
   ```

   Expected: one notebook cell, showing the last result: 8 rows, 3 columns. *Why:* the second statement copies the
   products of store 1 to store 2, each at 10 units. `INSERT ... SELECT` stores every row the `SELECT` returns.

2. **Preview, then update.** Three cells: the preview, the `UPDATE`, the check.

   ```sql
   SELECT * FROM stock WHERE store_id = 1 AND product_id = 10;
   UPDATE stock SET units_on_hand = units_on_hand + 24 WHERE store_id = 1 AND product_id = 10;
   SELECT * FROM stock WHERE store_id = 1 AND product_id = 10;
   ```

   Expected: the preview returns 1 row, 3 columns; the `UPDATE` returns a `Count` table with 1 row, the rows it
   changed; the check returns 1 row, 3 columns. *Why:* the preview uses the same `WHERE` as the `UPDATE`. If it
   returned more rows than you meant, you would stop. The `Count` must match the preview. Croissants are now 49.

3. **Delete the same way.** Green Tea is dropped from store 1: preview with a `SELECT`, then delete.

   ```sql
   SELECT * FROM stock WHERE store_id = 1 AND product_id = 7;
   DELETE FROM stock WHERE store_id = 1 AND product_id = 7;
   SELECT COUNT(*) AS rows_left FROM stock;
   ```

   Expected: the preview returns 1 row; the `DELETE` returns a `Count` table with 1 row; the last query returns
   1 row, 1 column, which is 7.

4. **Make a mistake, then undo it.** Five cells.

   ```sql
   BEGIN;
   DELETE FROM stock;
   SELECT COUNT(*) AS rows_left FROM stock;
   ROLLBACK;
   SELECT COUNT(*) AS rows_left FROM stock;
   ```

   Expected: the first cell prints a `Success` table, the `DELETE` a `Count` table, and each `SELECT` 1 row, 1
   column. Inside the transaction the count is 0; after `ROLLBACK` it is back to 7. *Why:* a `DELETE` without a
   `WHERE` removes every row, but the transaction kept the change private until you decided. This is atomicity:
   all of it, or none.

5. **Two tills, one count.** Ana and Ben each sell a croissant at the same moment. `con.cursor()` gives each of them
   their own session on the same database.

   ```python
   ana = con.cursor()
   ben = con.cursor()
   ```

   ```sql
   -- Ana's session
   BEGIN;
   UPDATE stock SET units_on_hand = units_on_hand - 1 WHERE store_id = 1 AND product_id = 10;
   SELECT units_on_hand FROM stock WHERE store_id = 1 AND product_id = 10;
   -- Ben's session
   SELECT units_on_hand FROM stock WHERE store_id = 1 AND product_id = 10;
   BEGIN;
   UPDATE stock SET units_on_hand = units_on_hand - 1 WHERE store_id = 1 AND product_id = 10;
   ```

   Expected: Ana's `SELECT` returns 1 row, 1 column. Ben's `SELECT` returns 1 row, 1 column. Ben's `UPDATE` prints
   an error that starts `TransactionContext Error:` (the notebook catches it). *Why:* Ana sees her own change (48), Ben still sees 49: isolation.
   DuckDB's documentation says that when two transactions change the same row, the second fails and you rerun it.
   Do that: Ben runs `ROLLBACK`, Ana runs `COMMIT`, then Ben runs `BEGIN`, the same `UPDATE` and `COMMIT`. The check
   `SELECT units_on_hand ...` now returns 47, because both sales count. Notice `units_on_hand - 1`: the database
   subtracts from the number as it is now, not from one that someone read earlier.

6. **Reload one store, safely.** `campus_count` is a staging table of Campus's new counts: three rows, for products
   1, 10 and 6.

   ```sql
   BEGIN;
   DELETE FROM stock WHERE store_id = 2;
   INSERT INTO stock SELECT * FROM campus_count;
   COMMIT;
   ```

   Run this cell twice, then `SELECT COUNT(*) AS products, SUM(units_on_hand) AS units FROM stock WHERE store_id = 2;`.
   Expected: 1 row, 2 columns; the same after one run and after two. *Why:* the block deletes store 2's rows and
   inserts the new ones, so a second run starts from the same place: it is **idempotent**. A plain `INSERT` of the same
   rows into a table that already holds them fails: store 2 and product 1 are already there (the key of S31). If the
   `INSERT` fails inside the block, `ROLLBACK` brings the old rows back (consistency and atomicity at work).
   DuckDB also has `INSERT OR IGNORE` and `ON CONFLICT` for this; the data engineer stage returns to them.

7. **Verify.**

   ```sql
   SELECT store_id, COUNT(*) AS products, SUM(units_on_hand) AS units
   FROM stock GROUP BY store_id ORDER BY store_id;
   ```

   Expected: 2 rows, 3 columns. Store 1 has 3 products and 99 units: Espresso 40, Cold Brew 12 and Croissants 47,
   which is 25 + 24 delivered - 2 sold. Store 2 has 3 products and 53 units, the sum of `campus_count`.

<details>
<summary>Explain it in your own words: why does Ben's update fail instead of waiting or overwriting?</summary>

Ana's change is not committed yet, so Ben cannot build on it, and overwriting would lose it. DuckDB refuses the
second change to the same row, and Ben reruns it after Ana commits.

</details>

## Check yourself

Without looking back: say the four ACID letters in plain words, and what an idempotent load means.

<details>
<summary>Answer</summary>

Atomicity: all of a transaction's changes happen, or none. Consistency: the data always obeys its rules. Isolation:
others do not see your changes until you commit. Durability: a committed change survives a crash. An idempotent load
leaves the same result whether you run it once or twice.

</details>

<Exercise id="sql-modify-data-transactions-3">

**Spot the flaw.** A colleague's till program counts a sale in three moves: read the count, subtract 1 in the program,
write the new number back. Ana's till and Ben's till each sell a croissant at the same moment, with 49 in stock:

```sql
SELECT units_on_hand FROM stock_ex3 WHERE store_id = 1 AND product_id = 10;
UPDATE stock_ex3 SET units_on_hand = 48 WHERE store_id = 1 AND product_id = 10;
```

Both tills read 49 before either writes, and both write 48. The colleague says it worked, because no error appeared.
Expected from the final `SELECT`: 1 row, 1 column. What went wrong, and what is the fix?

<details>
<summary>Hint</summary>

Two croissants were sold. How many should be left, and which write did the second `UPDATE` overwrite?

</details>

<details>
<summary>Half-solution</summary>

Start from: "The count ends at 48, but it should be ... The second write replaced the first, because each till wrote a number it had read ..."

</details>

<Solution>

The count ends at **48**, and it should be 47. Both tills read 49, so both wrote 48, and the second write overwrote
the first: one sale vanished, and nothing reported an error. Plain statements commit one at a time, so nothing made
the tills wait for each other.

Let the database do the arithmetic in one statement:

```sql
UPDATE stock_ex3 SET units_on_hand = units_on_hand - 1 WHERE store_id = 1 AND product_id = 10;
```

Each statement subtracts from the number as it is now, so two sales leave 47. When a change needs several statements,
wrap them in `BEGIN` and `COMMIT`; if DuckDB reports a conflict, roll back and rerun.

</Solution>
