## The question

The owner is reprinting the menu and asks:

> Mark every product premium, standard or budget. Premium starts at \$4.50, standard at \$3.50, and anything cheaper
> is budget.

In Excel you would add a column with a nested `IF`. The `products` table has the prices but no tier. Its first four
rows:

| product_id | product_name | category | unit_price_usd |
|---:|---|---|---:|
| 1 | Espresso | coffee | 3.00 |
| 2 | Americano | coffee | 3.50 |
| 3 | Latte | coffee | 4.50 |
| 4 | Cappuccino | coffee | 4.50 |

## The big idea

true decides the answer.

## Learn by doing

Five small steps. Press Run on each query as you meet it.

### 1. One label per row

A `CASE` picks one value for each row, so in the `SELECT` list it works like any other column. You write it as
**branches**, each a `WHEN test THEN value`, and close it with `END`. An optional `ELSE` gives the value for a row that
none of the tests accepts. Text goes in single quotes, as in S1.

**Try it**: look at the prices before you label them.

<RunSQL query={`SELECT product_name, unit_price_usd
FROM products
ORDER BY unit_price_usd DESC, product_name;`} />

Expected: 16 rows, 2 columns; Turkey Sandwich 9.25 first, Espresso 3.00 last. *Why:* two products cost 4.50 and two
cost 3.50, so the boundaries in the question fall on real prices and the `>=` matters.

**Try it**: a first `CASE` with two outcomes.

<RunSQL query={`SELECT product_name, unit_price_usd,
       CASE WHEN unit_price_usd >= 4.50 THEN 'premium'
            ELSE 'regular'
       END AS price_tier
FROM products
ORDER BY unit_price_usd DESC, product_name;`} />

Read it: *when the price is at least 4.50, premium; otherwise regular*. Expected: 16 rows, 3 columns. *Excel:*
`=IF(B2>=4.5,"premium","regular")` filled down; the `ELSE` is the answer when the test is false.

*Why:* the `CASE` returns one value per row, and `AS price_tier` names the new column. The table itself does not change.

### 2. The first true test wins

Add a second test and the order of your lines starts to matter. SQL tries the tests from the top and stops at the first
one that is true (standard SQL; the result below shows it). *Excel:* a second `IF` nested inside the first,
`=IF(B2>=4.5,"premium",IF(B2>=3.5,"standard","budget"))`. In SQL it is one more `WHEN` line.

**Try it**:

<RunSQL query={`SELECT product_name, unit_price_usd,
       CASE WHEN unit_price_usd >= 4.50 THEN 'premium'
            WHEN unit_price_usd >= 3.50 THEN 'standard'
            ELSE 'budget'
       END AS price_tier
FROM products
ORDER BY unit_price_usd DESC, product_name;`} />

Expected: 16 rows, 3 columns, the tiers in blocks because of the sort.

*Why:* the 4.75 Cold Brew passes both tests, `>= 4.50` and `>= 3.50`. A 4.50 latte is premium too, because `>=`
includes the boundary.

In the picture, the Latte at 4.50 passes the first test, so the second is never used for it.

### 3. When no test is true

A test accepts a row only when it is true. A false test and an unknown one (a comparison with `NULL`, S4) both pass the
row to the next branch (standard SQL). Order 1335, the walk-in order, has no `customer_id`, so `customer_id > 100` is
unknown for it, and the row moves on to the `ELSE`. What does a row get when nothing accepts it and you wrote no
`ELSE`?

**Try it**. Take out the middle tier and the `ELSE`. Before you run it: how many rows show a tier, and
what do the others show?

<RunSQL query={`SELECT product_name, unit_price_usd,
       CASE WHEN unit_price_usd >= 4.50 THEN 'premium' END AS price_tier
FROM products
ORDER BY unit_price_usd DESC, product_name;`} />

Expected: 16 rows, 3 columns.

*Why:* a row that matches no `WHEN` gets `NULL`, not an empty string and not an error. You know from S4 what `NULL`
means: unknown. So write the `ELSE` every time, and a `NULL` in the output will not be a branch you forgot.

### 4. Two conditions in one test

The test after `WHEN` can join conditions with `AND`, like the `AND(...)` inside the Excel `IF` of E6.

**Try it**:

<RunSQL query={`SELECT order_id, payment_method, status,
       CASE WHEN payment_method = 'cash' AND status = 'completed' THEN 'in till'
            ELSE 'skip'
       END AS till_flag
FROM orders
WHERE order_id IN (1458, 1461)
ORDER BY order_id;`} />

Expected: 2 rows, 4 columns. Both orders were paid in cash; order 1461 is the canceled one. *Excel:*
`=IF(AND(E6="cash",F6="completed"),"in till","skip")`.

*Why:* order 1458 is in till. Order 1461 is skip, because the second condition fails.

### 5. Check with a second route

Count the same groups with `WHERE`, not `CASE`.

**Try it**:

<RunSQL query={`SELECT COUNT(*) AS premium_products FROM products WHERE unit_price_usd >= 4.50;`} />

<RunSQL query={`SELECT COUNT(*) AS in_till FROM orders WHERE payment_method = 'cash' AND status = 'completed';`} />

Expected: 1 row, 1 column each. The first returns `8`, the number of `premium` rows in unit 2. The second returns
`252`, the in-till count you got in E6. The canceled cash order is why there are 253 cash orders but 252 in till.

<Aside type="tip" title="Remember">

- A `CASE` returns one value per row, so it works like any other column.
- The first true `WHEN` wins, so write the strictest test first.
- A false test and an unknown one both pass the row on.
- No `ELSE` means `NULL`: write the `ELSE` every time.

**Common trap: "`CASE` filters rows, like `WHERE`."** A `CASE` decides what a row shows, not whether it stays: 16
products go in and 16 rows come out, each with its label. To remove rows, use `WHERE`; DuckDB applies it right after
`FROM`, before the `SELECT` list is worked out.

</Aside>
