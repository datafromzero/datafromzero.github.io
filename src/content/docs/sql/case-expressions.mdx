## How it works

A **`CASE` expression** chooses, for each row on its own, one value to put in a column. It is built from
**branches**, each a `WHEN test THEN value` pair, and it closes with `END`. An optional `ELSE` gives the value for a row
that no test accepts.

Take a query that adds a `price_tier` column to the products. Logically, SQL does this:

1. `FROM products` supplies the 16 rows. A `WHERE` would remove rows here.
2. For each row, SQL works out the `SELECT` list, and the `CASE` is one item in it. It tries the branches from the top
   and stops at the first test that is true for that row. In the picture above, the Latte at 4.50 passes the first
   test, so the second is never used for it.
3. The row gets the value after that `THEN`, or the `ELSE` value if no test is true, in a new column beside its other
   columns.

The rules:

- A `CASE` returns one value per row, so in the `SELECT` list it works like any other column.
- The order of the branches is the order of the tests. The first true test supplies the value (standard SQL; step 3
  shows it).
- A test counts only when it is true. A false test and an unknown one (a comparison with `NULL`, S4) both pass the row
  to the next branch (standard SQL). For order 1335, whose `customer_id` is `NULL`, `customer_id > 100` is unknown, so
  that row falls through to the `ELSE`.
- `ELSE` is optional. Step 4 shows what a row gets when no test is true and the `ELSE` is missing.

**Excel.** The `IF` of *Decisions with IF, AND and OR* (E6) gives one result when its comparison is true and another
when it is false, and nesting an `IF` inside it adds a branch. The picture is the nested formula
`=IF(B2>=4.5,"premium",IF(B2>=3.5,"standard","budget"))` written as lines.

**A common misconception: "`CASE` filters rows, like `WHERE`."** A `CASE` decides what a row shows, not whether it
stays: 16 products go in and 16 rows come out, each with its label. To remove rows, use `WHERE`; DuckDB applies it
right after `FROM`, before the `SELECT` list is worked out.

| Excel | SQL |
|---|---|
| `=IF(B2>=4.5,"premium","regular")` | `CASE WHEN unit_price_usd >= 4.50 THEN 'premium' ELSE 'regular' END` |
| a second `IF` inside the first | one more `WHEN` line |
| `AND(x,y)` as the test | `x AND y` after `WHEN` |
| the answer when no test is true | `ELSE` |

Text goes in single quotes in SQL, as in S1.

## Worked example

Question: **which tier does each product get, and which orders put cash in the till?** Run the notebook's setup cell,
then one cell per step. Each step shows the shape of the result to expect.

1. **Look at the prices.**

   ```sql
   SELECT product_name, unit_price_usd
   FROM products
   ORDER BY unit_price_usd DESC, product_name;
   ```

   Expected: 16 rows, 2 columns; Turkey Sandwich 9.25 first, Espresso 3.00 last. *Why:* look before you label. Two
   products cost 4.50 and two cost 3.50, so the boundaries in the question fall on real prices and the `>=` matters.

2. **A first CASE with two outcomes.**

   ```sql
   SELECT product_name, unit_price_usd,
          CASE WHEN unit_price_usd >= 4.50 THEN 'premium'
               ELSE 'regular'
          END AS price_tier
   FROM products;
   ```

   Read it: *when the price is at least 4.50, premium; otherwise regular*. Expected: 16 rows, 3 columns. *Excel:*
   `=IF(B2>=4.5,"premium","regular")` filled down. *Why:* the `CASE` returns one value per row, and `AS price_tier`
   names the new column. The table itself does not change.

3. **Add the middle tier.**

   ```sql
   SELECT product_name, unit_price_usd,
          CASE WHEN unit_price_usd >= 4.50 THEN 'premium'
               WHEN unit_price_usd >= 3.50 THEN 'standard'
               ELSE 'budget'
          END AS price_tier
   FROM products
   ORDER BY unit_price_usd DESC, product_name;
   ```

   Expected: 16 rows, 3 columns, the tiers in blocks because of the sort. *Excel:* the nested `IF`. *Why:* a 4.75
   product passes both tests, `>= 4.50` and `>= 3.50`. It is premium because that test is written first: the first
   true `WHEN` wins. A 4.50 latte is premium too, because `>=` includes the boundary.

4. **Predict what no match returns.** Take out the middle tier and the `ELSE`:

   ```sql
   SELECT product_name, unit_price_usd,
          CASE WHEN unit_price_usd >= 4.50 THEN 'premium' END AS price_tier
   FROM products
   ORDER BY unit_price_usd DESC, product_name;
   ```

   Before you run it: how many rows show a tier, and what do the others show? Expected: 16 rows, 3 columns. *Why:*
   with no `ELSE`, a row that matches no `WHEN` gets `NULL`, not an empty string and not an error. You know from S4
   what `NULL` means: unknown. So write the `ELSE` every time, and a `NULL` in the output will not be a branch you
   forgot.

5. **Two conditions, as in E6.**

   ```sql
   SELECT order_id, payment_method, status,
          CASE WHEN payment_method = 'cash' AND status = 'completed' THEN 'in till'
               ELSE 'skip'
          END AS till_flag
   FROM orders
   WHERE order_id IN (1458, 1461);
   ```

   Expected: 2 rows, 4 columns. Both orders were paid in cash; order 1461 is the canceled one. *Excel:*
   `=IF(AND(E6="cash",F6="completed"),"in till","skip")`. *Why:* `AND` after `WHEN` is the `AND(...)` of the Excel
   test. Order 1458 is in till, and order 1461 is skip.

6. **Verify with a second route.** Count the same groups with `WHERE`, not `CASE`:

   ```sql
   SELECT COUNT(*) AS premium_products FROM products WHERE unit_price_usd >= 4.50;
   SELECT COUNT(*) AS in_till FROM orders WHERE payment_method = 'cash' AND status = 'completed';
   ```

   Expected: 1 row, 1 column each. The first returns `8`, the number of `premium` rows in step 3. The second returns
   `252`, the in-till count you got in E6. The canceled cash order is why there are 253 cash orders but 252 in till.

<details>
<summary>Explain it in your own words: in step 3, why is a 4.75 product premium and not standard?</summary>

Both tests are true for it, and the first true `WHEN` wins. The premium test comes first, so it answers. If you swapped
the two `WHEN` lines, every product at 3.50 or more would be standard. Exercise 3 shows that mistake.

</details>

**Spot the flaw.** A colleague writes the price tiers with the tests in this order and says the result is fine, because
there is no error:

```sql
SELECT product_name, unit_price_usd,
       CASE WHEN unit_price_usd >= 3.50 THEN 'standard'
            WHEN unit_price_usd >= 4.50 THEN 'premium'
            ELSE 'budget'
       END AS price_tier
FROM products
ORDER BY unit_price_usd DESC, product_name;
```

Expected: 16 rows, 3 columns, and no error. Run it and compare the tiers with the price list. Which tier is missing, and
why? Then fix the query.

<Solution>

No product is premium. The first test, `>= 3.50`, is true for every product that costs 3.50 or more, including the 9.25
Turkey Sandwich, so each one gets `standard` and the premium line is never reached. Thirteen products come out
standard, where five should be, and three come out budget. Put the strictest test first:

```sql
SELECT product_name, unit_price_usd,
       CASE WHEN unit_price_usd >= 4.50 THEN 'premium'
            WHEN unit_price_usd >= 3.50 THEN 'standard'
            ELSE 'budget'
       END AS price_tier
FROM products
ORDER BY unit_price_usd DESC, product_name;
```

Expected: 16 rows, 3 columns, 8 premium, 5 standard and 3 budget. SQL gave no error because the colleague's query is
valid: it just answers a different question than the one asked.

</Solution>
