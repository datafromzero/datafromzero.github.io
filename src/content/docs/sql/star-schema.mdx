## The question

> Our reporting tool wants one tidy model it can filter by store, product and day. Today every report re-joins the

The middle of that model is one row per order line, with keys that point to descriptive tables and the numbers to add

## How it works

A **star schema** sorts the tables of a reporting model into two kinds. A **fact table** records events and their
numbers; here `fact_sales` holds the sales. A **dimension table** describes what the events happened to: who, what,
where and when; here the store, the product and the day. Kimball Group splits data the same way, into measurements and
descriptive context. A question put to a star runs in four moves:

1. `FROM` the fact table, which has one row per order line: 3,287 rows.
2. Join each dimension the question needs, matching a key column of the fact table (`store_id`, `product_id`,
   `order_date`) to the key column of that dimension. In the picture above, each connecting line has a 1 at the dimension
   and "many" at the fact table.
3. Filter and group by columns of the dimensions: a category, a weekday, a store name.
4. Add up a measure of the fact table: `SUM(amount_usd)`.

Microsoft's Power BI documentation gives the reason: dimension tables enable filtering and grouping, fact tables
enable summarization. The rules:

- The **grain** is what one fact row stands for. Say it before you build (S18): here, **one order line**. A fact table
  keeps one grain throughout, as the same documentation advises.
- A fact table has two kinds of columns, plus identifiers such as `order_item_id`: dimension keys, which point to
  dimension tables, and measures, the numbers you add up.
- A dimension table has a key column that identifies each of its rows uniquely, plus descriptive columns to filter and
  group by. Dimensions are small next to the fact table (3 to 181 rows here, against 3,287); a fact table can grow large.
- This star is made of views. DuckDB says a view is not physically materialized: its query runs each time the view is
  read. So the star is a new shape over the same tables, not a second copy of the data.

**Excel.** A PivotTable (E15, *Summarize with a PivotTable*) reads a table the same way: the fields in Rows and Columns
are what you group by, and the numeric field in Values is the measure, which Excel sums by default.

**A common misconception: "a fact table holds only numbers."** It holds dimension keys too, as the picture shows beside
the measures. Without those keys, a line's amount could not be tied to a cafe, a product or a day.

## Worked example

Question: **can we model sales as a star, and does it give the same totals as the source?** Run the notebook's setup
cell, then one cell per step. Totals include the extra-zero line (order 2075); "completed" excludes the canceled order.

1. **Declare the grain, then build the fact view.** One row per order line, so the fact view starts from
   `order_items`. It joins `orders` for the keys and `products` only to price the line.

   ```sql
   CREATE OR REPLACE VIEW fact_sales AS
   SELECT i.order_item_id, i.order_id,
          CAST(o.ordered_at AS DATE) AS order_date,
          o.store_id, o.customer_id, i.product_id,
          o.status AS order_status,
          i.quantity, i.discount_usd,
          i.quantity * p.unit_price_usd - i.discount_usd AS amount_usd
   FROM order_items AS i
   JOIN orders AS o ON o.order_id = i.order_id
   JOIN products AS p ON p.product_id = i.product_id;
   ```

   Expected: no result rows (an empty table with a `Count` column). *Why:* the view keeps every line, canceled order
   included, with its status, so its counts match the source. Filter on the status when you ask a question.

2. **Check the grain.**

   ```sql
   SELECT COUNT(*) AS lines, COUNT(DISTINCT order_item_id) AS distinct_lines,
          ROUND(SUM(amount_usd), 2) AS sales
   FROM fact_sales;
   ```

   Expected: 1 row, 3 columns: `3287 | 3287 | 22754.25`. *Why:* as many distinct line ids as rows: one row per line.
   The 3,287 equals `order_items` (S18), and 22,754.25 is all lines of every status.

3. **Build the dimensions.** Each has one row per key.

   ```sql
   CREATE OR REPLACE VIEW dim_store AS
   SELECT store_id, store_name, city FROM stores;

   CREATE OR REPLACE VIEW dim_product AS
   SELECT product_id, product_name, category FROM products;

   CREATE OR REPLACE VIEW dim_date AS
   SELECT CAST(generate_series AS DATE) AS order_date,
          year(generate_series) AS year, month(generate_series) AS month,
          dayname(generate_series) AS weekday,
          isodow(generate_series) >= 6 AS is_weekend
   FROM generate_series(TIMESTAMP '2026-01-01', TIMESTAMP '2026-06-30', INTERVAL 1 DAY);
   ```

   Expected: three cells, none with result rows. *Why:* `dim_date` is the date spine of *Complete time series and
   recursive CTEs* (S27) with the date parts of *Working with dates and time* (S11) added. Power BI's documentation:
   "The most consistent table you'll find in a star schema is a date dimension table." `isodow` is 6 or 7 on Saturday and
   Sunday.

4. **Check every key.**

   ```sql
   SELECT COUNT(*) AS dim_rows, COUNT(DISTINCT product_id) AS distinct_keys FROM dim_product;
   ```

   Expected: 1 row, 2 columns: `16 | 16`. Run it for `dim_store` (3 and 3) and `dim_date` (181 and 181, on
   `order_date`). *Why:* this is the uniqueness check of *Join fan-out* (S21): the two numbers are equal only when no key value repeats.

5. **Ask a question through the star.** Completed sales by category, weekdays against weekends:

   ```sql
   SELECT p.category, d.is_weekend, ROUND(SUM(f.amount_usd), 2) AS sales
   FROM fact_sales AS f
   JOIN dim_product AS p ON p.product_id = f.product_id
   JOIN dim_date AS d ON d.order_date = f.order_date
   WHERE f.order_status = 'completed'
   GROUP BY p.category, d.is_weekend
   ORDER BY p.category, d.is_weekend;
   ```

   Expected: 8 rows, 3 columns: for example bakery on weekdays 2341.50 and on weekends 1482.75. *Why:* the question uses one
   column of each dimension and one measure: group by the dimensions, sum the fact.

6. **Verify.** Joining the fact to the three dimensions must keep every line:

   ```sql
   SELECT COUNT(*) AS lines, ROUND(SUM(f.amount_usd), 2) AS sales
   FROM fact_sales AS f
   JOIN dim_store AS s ON s.store_id = f.store_id
   JOIN dim_product AS p ON p.product_id = f.product_id
   JOIN dim_date AS d ON d.order_date = f.order_date;
   ```

   Expected: 1 row, 2 columns: `3287 | 22754.25`, the same as step 2. Then add up step 5: its eight numbers sum to
   22,749.25, the completed-sales total of *Saving a query as a view* (S28) and of the Excel pivot lessons. Answer:
   **yes, the star gives the same totals as the source.**

<details>
<summary>Explain it in your own words: why must the step 6 join return exactly 3,287 lines?</summary>

Every line has one store, one product and one day, and each dimension has exactly one row per key, so each fact row finds
exactly one match and the join neither drops nor repeats a line.

</details>

<Exercise id="sql-star-schema-3">

**Spot the flaw.** A colleague wants a product dimension that lists only products that have sold, and builds it from the
lines:

```sql
CREATE OR REPLACE VIEW dim_product_sold AS
SELECT p.product_id, p.product_name, p.category
FROM products AS p
JOIN order_items AS i ON i.product_id = p.product_id;
```

Then they join `fact_sales` to `dim_product_sold` on `product_id` and add up `amount_usd` over all lines, and report
5,441,687.00. Expected from that query: 1 row, 2 columns (the lines and the sales). What went wrong, and what is the
fix?

<Solution>

The join returns `817661 | 5441687.00`, not `3287 | 22754.25`. The view has 3,287 rows but only 15 different
`product_id` values: it has one row per *line*, not per product, because the join to `order_items` repeats each product
once per line. Espresso, for example, appears 192 times, so every Espresso fact row is matched 192 times. The key check
of step 4 would have caught it: `COUNT(*)` and `COUNT(DISTINCT product_id)` differ.

Use `dim_product` as it is, with one row per key (Pumpkin Spice Latte, never sold, may stay on the menu), or write the
sold-products view with `SELECT DISTINCT`. Either way, check `COUNT(*) = COUNT(DISTINCT key)` after building a dimension.

</Solution>

</Exercise>
