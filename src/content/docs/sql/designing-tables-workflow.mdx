You have read tables other people built and made two of your own. Here you design a whole small database from a description, in the order a team would: on paper first, then in `CREATE TABLE`, then with rows that try to break it. The tables you create stay until you leave the page, so run the blocks in order. Run a block that makes a table twice and the database says it already exists: press **Reset data**, then start again from the top.

## The question

A community center runs evening workshops and asks you for a database. The team wrote three user stories first, because the stories decide what the model must hold and when to stop:

> - As a member, I want to join a workshop and see whether I am confirmed or on the waiting list.
> - As the organizer, I want to see which workshops are full and which have no instructor yet.
> - As the organizer, I want to find the members who have not signed up for anything.

The details behind them: each workshop has a title, a level (beginner or intermediate), a start time, a seat limit and, once we have found one, an instructor. An instructor can teach several workshops, and a member can join several. For each sign-up we keep the day and whether it is confirmed or on the waiting list.

Nothing exists yet. By the end you will have five tables that answer those three questions, and rows that prove it.

## Warm-up

From memory first, then click to check.

1. In [*Reading an entity-relationship diagram*](/sql/reading-er-diagrams/), a line has a circle with a bar at one end and a crow's foot with a circle at the other. Read it in both directions.

   <details>
   <summary>Answer</summary>

   The circle-and-bar end says "zero or one" and the foot-and-circle end says "zero or many", each counted on the table it touches. The foreign key sits in the table at the foot end.

   </details>

2. In *Normalization: one fact in one place* (S36), a wide table repeated an address on every row. What did you do to it?

   <details>
   <summary>Answer</summary>

   Moved the repeated fact into a table of its own with a key, and left a foreign key behind in the old table.

   </details>

### 1. Put the key on the many side

**Idea.** A **foreign key** goes in the table on the *many* side of a one-to-many link, and points at the *one* side. Many workshops share one instructor, so `workshops` holds `instructor_id`. A foreign key that may be empty makes the link optional. A **lookup table** is a small table of allowed values that other tables point at: here `levels`. Normalize as you go: the instructor's name lives once, in `instructors`, not on every workshop (S36).

**Try it:** build the three tables and give them rows. Workshop 3 has no instructor yet.

<RunSQL query={`CREATE TABLE levels (
  level_id INTEGER PRIMARY KEY,
  level_name VARCHAR NOT NULL UNIQUE
);
CREATE TABLE instructors (
  instructor_id INTEGER PRIMARY KEY,
  full_name VARCHAR NOT NULL,
  email VARCHAR NOT NULL UNIQUE
);
CREATE TABLE workshops (
  workshop_id INTEGER PRIMARY KEY,
  title VARCHAR NOT NULL,
  level_id INTEGER NOT NULL REFERENCES levels (level_id),
  instructor_id INTEGER REFERENCES instructors (instructor_id),
  starts_at TIMESTAMP NOT NULL,
  capacity INTEGER NOT NULL CHECK (capacity > 0)
);
INSERT INTO levels VALUES (1, 'beginner'), (2, 'intermediate');
INSERT INTO instructors VALUES
  (1, 'Maya Ortiz', 'maya@example.org'),
  (2, 'Ken Ruiz', 'ken@example.org');
INSERT INTO workshops VALUES
  (1, 'Sourdough basics', 1, 1, '2027-01-09 10:00', 2),
  (2, 'Knife skills', 1, 2, '2027-01-10 14:00', 3),
  (3, 'Laminated dough', 2, NULL, '2027-01-16 10:00', 2);
SELECT workshop_id, title, level_id, instructor_id FROM workshops ORDER BY workshop_id;`} />

Expected: 3 rows, 4 columns; the third row has an empty `instructor_id`.

**Predict:** a fourth workshop names level 9, which the lookup table does not have. Accepted or refused, and what will the message say?

<RunSQL query={`INSERT INTO workshops VALUES (4, 'Pasta by hand', 9, 1, '2027-01-17 10:00', 4);`} />

Expected: one outcome, either an inserted row or an error message. *Why:* it is refused: the message says the foreign key is violated because the key "level_id: 9" does not exist in the referenced table. The database checks every foreign key against the parent table. A `CHECK` list such as `CHECK (level IN ('beginner', 'intermediate'))` would refuse it too, but a new level then needs a schema change, while a lookup table needs only a new row, and it can carry more columns later.

### 2. Let the database make the key

**Idea.** A **surrogate key** is a number with no meaning, made by the database, such as `member_id`. A **natural key** is a real-world value that identifies a row, such as an email. Use the surrogate as the primary key and keep the natural one as `UNIQUE`: people change their emails. DuckDB makes numbers with a **sequence**, a counter you attach to a column as its `DEFAULT`: `nextval('member_seq')` gives the next number.

**Try it:**

<RunSQL query={`CREATE SEQUENCE member_seq START 1;
CREATE TABLE members (
  member_id INTEGER PRIMARY KEY DEFAULT nextval('member_seq'),
  email VARCHAR NOT NULL UNIQUE,
  joined_on DATE NOT NULL
);
INSERT INTO members (email, joined_on) VALUES
  ('ana@example.org', '2026-10-02'),
  ('ben@example.org', '2026-10-09'),
  ('chloe@example.org', '2026-10-15')
RETURNING member_id, email;`} />

Expected: 3 rows, 2 columns; the ids are 1, 2 and 3. Now a member whose email already exists:

<RunSQL query={`INSERT INTO members (email, joined_on) VALUES ('ana@example.org', '2026-11-01');`} />

Expected: an error saying the duplicate key `email: ana@example.org` violates the unique constraint.

**Predict:** the next good member is Dev. What `member_id` does Dev get?

<RunSQL query={`INSERT INTO members (email, joined_on) VALUES ('dev@example.org', '2026-11-02') RETURNING member_id;`} />

Expected: 1 row, 1 column. *Why:* the refused insert still took a number from the sequence, so ids are unique but not gap-free: never use the largest id as a count.

**Try it:** the keyword other databases use.

<RunSQL query={`CREATE TABLE guests (guest_id INTEGER PRIMARY KEY AUTOINCREMENT, email VARCHAR);`} />

Expected: an error saying there is a syntax error at or near "AUTOINCREMENT". *Why:* DuckDB takes its numbers from a sequence instead. The other engines differ: PostgreSQL has `GENERATED ... AS IDENTITY` columns, and in SQLite an `INTEGER PRIMARY KEY` column becomes the row's automatic id (see their documentation under Sources).

### 3. Make a table for the pair

**Idea.** A many-to-many link needs a table in the middle, one row for each pair, with a foreign key to each side. A fact that describes the *pair* belongs in that table, not in either parent: when someone signed up, and whether they are confirmed, describe a member and a workshop together.

**Try it:**

<RunSQL query={`CREATE TABLE signups (
  member_id INTEGER NOT NULL REFERENCES members (member_id),
  workshop_id INTEGER NOT NULL REFERENCES workshops (workshop_id),
  signed_up_on DATE NOT NULL,
  status VARCHAR NOT NULL CHECK (status IN ('confirmed', 'waitlist', 'canceled')),
  PRIMARY KEY (member_id, workshop_id)
);
INSERT INTO signups VALUES
  (1, 1, '2026-12-01', 'confirmed'),
  (2, 1, '2026-12-02', 'confirmed'),
  (3, 1, '2026-12-03', 'waitlist'),
  (1, 2, '2026-12-05', 'confirmed');
SELECT * FROM signups ORDER BY member_id, workshop_id;`} />

Expected: 4 rows, 4 columns.

**Predict:** Ana (member 1) signs up again for workshop 1, this time as `waitlist`. Accepted or refused?

<RunSQL query={`INSERT INTO signups VALUES (1, 1, '2026-12-09', 'waitlist');`} />

Expected: one outcome, either an inserted row or an error message. *Why:* it is refused: the message names the duplicate key "member_id: 1, workshop_id: 1". One pair, one row: the pair of foreign keys is the primary key, and a primary key forbids a repeat. A different status for Ana would have to change her existing row, which is what an update is for.

<Aside type="note" title="Translation patterns and their trade-offs">

| In the description | Table design | Trade-off |
|---|---|---|
| An entity: a noun with facts of its own | a table with a primary key | none |
| One-to-many | foreign key on the many side | none: the default |
| Many-to-many | junction table; facts about the pair live there | one more table to join |
| One-to-one | foreign key that is also the primary key, or `UNIQUE`; or merge the two tables | a separate table keeps rare columns out; merging saves a join |
| Optional link | nullable foreign key | every join to it must keep rows with `LEFT JOIN` |
| Categorical attribute: a fixed set of values | a lookup table that the other table points at, or a `CHECK` list | a lookup adds a value with a row; a `CHECK` list changes the table |
| Multi-valued attribute: several values for one row | its own table, one row for each value, with a foreign key back | one more table; a list inside one cell breaks the one-fact-per-cell rule of S36 |
| Generalization: a member and an instructor are both people | one table with a type column | unused columns stay empty; the Data Engineer track goes deeper into other choices |

</Aside>

**Try it:** a multi-valued attribute. An instructor can have several phone numbers, so each number gets its own row.

<RunSQL query={`CREATE TABLE instructor_phones (
  instructor_id INTEGER NOT NULL REFERENCES instructors (instructor_id),
  phone VARCHAR NOT NULL,
  PRIMARY KEY (instructor_id, phone)
);
INSERT INTO instructor_phones VALUES (1, '555-0101'), (1, '555-0102'), (2, '555-0103');
SELECT i.full_name, COUNT(*) AS phones
FROM instructors AS i
JOIN instructor_phones AS p ON p.instructor_id = i.instructor_id
GROUP BY i.full_name
ORDER BY i.full_name;`} />

Expected: 2 rows, 2 columns. *Why:* one instructor has two rows and the other one, and no cell holds a list.

### 4. Ask the design your questions

**Idea.** A design is not finished until it answers the questions it was built for. Write the three questions as queries before you trust the tables, and let the optional link tell you which join to use.

**Predict:** which workshop is full, and which has no instructor yet? The seat limit is `capacity`; a seat is taken by a `confirmed` sign-up.

**Try it:** seats taken against seats offered.

<RunSQL query={`SELECT w.title, w.capacity,
       SUM(CASE WHEN s.status = 'confirmed' THEN 1 ELSE 0 END) AS confirmed
FROM workshops AS w
LEFT JOIN signups AS s ON s.workshop_id = w.workshop_id
GROUP BY w.workshop_id, w.title, w.capacity
ORDER BY w.workshop_id;`} />

Expected: 3 rows, 3 columns. *Why:* a workshop with no sign-up must stay in the answer with a count of zero, so the join is a `LEFT JOIN` (S21). Only Sourdough basics is full: 2 of 2.

**Try it:** who teaches what, including the workshop without an instructor.

<RunSQL query={`SELECT w.title, i.full_name AS instructor
FROM workshops AS w
LEFT JOIN instructors AS i ON i.instructor_id = w.instructor_id
ORDER BY w.workshop_id;`} />

Expected: 3 rows, 2 columns. *Why:* Laminated dough has an empty instructor, and an `INNER JOIN` would have returned 2 rows: the optional link is what decides the join. The third question, members with no sign-up, is the anti join of S21, and Dev is the answer.

### 5. Read the catalog

**Idea.** The **catalog** is the database's own description of itself, in tables you can query. `information_schema.columns` lists columns, and DuckDB's `duckdb_constraints()` lists keys and checks. A design is done when the catalog matches the diagram.

**Predict:** how many foreign keys will the catalog list?

**Try it:**

<RunSQL query={`SELECT table_name, constraint_type, constraint_column_names, referenced_table
FROM duckdb_constraints()
WHERE constraint_type IN ('PRIMARY KEY', 'FOREIGN KEY', 'UNIQUE', 'CHECK')
ORDER BY table_name, constraint_type;`} />

Expected: 16 rows, 4 columns, counted for the tables of units 1 to 3 only. *Why:* the foreign keys are `workshops` to `levels` and to `instructors`, `signups` to `members` and to `workshops`, and `instructor_phones` to `instructors`. A column with no rule at all would not show up here: only what you wrote shows.

<RunSQL query={`SELECT column_name, data_type, is_nullable
FROM information_schema.columns
WHERE table_name = 'signups'
ORDER BY ordinal_position;`} />

Expected: 4 rows, 3 columns.

<Aside type="tip" title="Remember">

- Five steps: words, boxes and lines, keys (normalize as you go), `CREATE TABLE` with its constraints, then rows that try to break it. The first two are conceptual, the next logical, the `CREATE TABLE` physical; the user stories set the scope.
- A foreign key goes on the many side; a many-to-many link gets a table, and facts about the pair live in it. An optional link is a nullable foreign key that needs a `LEFT JOIN`.
- Use a generated key as the primary key and keep the natural one `UNIQUE`; generated numbers have gaps.
- Test with the questions the design was built for.

**Common trap: "a refused row leaves no trace."** The row is refused, but the sequence has already moved: ids can skip numbers.

</Aside>

```sql
CREATE TABLE books (
  book_id INTEGER PRIMARY KEY,
  title VARCHAR NOT NULL,
  author VARCHAR NOT NULL
);
CREATE TABLE copies (
  copy_id INTEGER PRIMARY KEY,
  book_id INTEGER NOT NULL REFERENCES books (book_id),
  shelf_code VARCHAR NOT NULL
);
CREATE TABLE loans (
  loan_id INTEGER PRIMARY KEY,
  member_id INTEGER NOT NULL REFERENCES members (member_id),
  copy_id INTEGER NOT NULL REFERENCES copies (copy_id),
  borrowed_on DATE NOT NULL,
  due_on DATE NOT NULL,
  returned_on DATE
);
INSERT INTO books VALUES (1, 'Bread Science', 'A. Baker');
INSERT INTO copies VALUES (1, 1, 'B-12');
INSERT INTO loans VALUES (1, 1, 1, '2026-11-01', '2026-11-22', NULL);
INSERT INTO loans VALUES (2, 1, 99, '2026-11-01', '2026-11-22', NULL);
```

The last insert is refused by the foreign key: there is no copy 99. A book to its copies is one-to-many, and a member to a copy is many-to-many through `loans`, which holds the dates because they belong to the pair. `returned_on` is empty on an open loan, so it is the only nullable column. Check:

```sql
SELECT table_name, referenced_table FROM duckdb_constraints()
WHERE constraint_type = 'FOREIGN KEY' AND table_name IN ('copies', 'loans')
ORDER BY table_name, referenced_table;
```

`copies` to `books`, `loans` to `copies`, `loans` to `members`: 3 rows.

<Exercise id="sql-designing-tables-workflow-3">

**Spot the flaw.** A colleague builds the sign-up table with its foreign keys but no primary key, and counts the seats taken in workshop 1, which has room for 2 people.

<RunSQL query={`CREATE OR REPLACE TABLE signups_loose (
  member_id INTEGER NOT NULL,
  workshop_id INTEGER NOT NULL,
  signed_up_on DATE NOT NULL,
  status VARCHAR NOT NULL
);
INSERT INTO signups_loose VALUES
  (1, 1, '2026-12-01', 'confirmed'),
  (1, 1, '2026-12-02', 'confirmed'),
  (2, 1, '2026-12-03', 'confirmed');
SELECT COUNT(*) AS seats_taken FROM signups_loose WHERE workshop_id = 1 AND status = 'confirmed';`} />

Expected from that query: 1 row, 1 column: `3`. What is wrong with the design, and what is the fix?

<Solution>

Two people hold the three seats: member 1 signed up twice and the table let it happen, because nothing says one row per pair. The count is of rows, and the rows are wrong, so a workshop that is not full looks over-full. Declare the pair as the primary key, as in unit 3, and the second row is refused:

```sql
CREATE OR REPLACE TABLE signups_loose (
  member_id INTEGER NOT NULL,
  workshop_id INTEGER NOT NULL,
  signed_up_on DATE NOT NULL,
  status VARCHAR NOT NULL,
  PRIMARY KEY (member_id, workshop_id)
);
INSERT INTO signups_loose VALUES (1, 1, '2026-12-01', 'confirmed');
INSERT INTO signups_loose VALUES (1, 1, '2026-12-02', 'confirmed');
INSERT INTO signups_loose VALUES (2, 1, '2026-12-03', 'confirmed');
SELECT COUNT(*) AS seats_taken FROM signups_loose WHERE workshop_id = 1 AND status = 'confirmed';
```

Run the lines one at a time: the second insert is refused with a duplicate key message, and the count is `2`. A constraint catches the mistake at the door; a query afterwards can only find it.

</Solution>
