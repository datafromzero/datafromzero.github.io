   <details>
   <summary>Answer</summary>

   ```sql
   SELECT p.product_name
   FROM order_items AS oi JOIN products AS p ON p.product_id = oi.product_id
   WHERE oi.order_id = 1001
   ORDER BY oi.order_item_id;
   ```

### 1. One order, three shapes

Data can outgrow a database in two ways: there can be more of it than one machine copes with, or it can have a shape other
than tables. **NoSQL** stores (databases that relax some relational behavior) mostly answer the second, and many also
scale out. They relax rules such as a fixed schema and the reach of a transaction, the changes that succeed or fail
together: for a document store that is one document, for a key-value store one key.

| Shape | Looks like | Good at | Gives up |
|---|---|---|---|
| Structured (relational) | tables, keys, joins | rules, joins, changes across many rows at once | fields that differ from row to row |
| Document | JSON objects whose fields can differ | reading or saving one whole object | ad hoc joins across documents |
| Key-value | a key and a value the store does not look inside | very fast lookup by key | any question that is not "the value for this key" |

**Try it** (order 1001 as rows). A structured store spreads one order over tables.

<RunSQL query={`SELECT o.order_id, s.store_name, p.product_name, oi.quantity
FROM orders AS o
JOIN stores AS s ON s.store_id = o.store_id
JOIN order_items AS oi ON oi.order_id = o.order_id
JOIN products AS p ON p.product_id = oi.product_id
WHERE o.order_id = 1001
ORDER BY oi.order_item_id;`} />

Expected: 3 rows, 4 columns, the table of the question. It took joins across four tables (S20). A document keeps the lines
inside the order, so reading one order needs no join. Microsoft Learn calls document and key-value stores denormalized
(related facts kept together) and relational stores normalized (each fact kept once, in its own table).

**Try it** (the same orders as documents under a key). A key and a value, here JSON text in DuckDB's `JSON` type. Order 1335
is the walk-in with no customer.

<RunSQL query={`CREATE OR REPLACE TABLE order_docs (doc_key VARCHAR PRIMARY KEY, doc JSON);
INSERT INTO order_docs VALUES
('order:1001', '{"order_id": 1001, "store": "Campus", "customer": 15, "items": [{"product": "Croissant", "qty": 1}, {"product": "Cold Brew", "qty": 1}, {"product": "Espresso", "qty": 2}]}'),
('order:1002', '{"order_id": 1002, "store": "Old Town", "customer": 46, "items": [{"product": "Croissant", "qty": 1}, {"product": "Turkey Sandwich", "qty": 1}]}'),
('order:1335', '{"order_id": 1335, "store": "Old Town", "items": [{"product": "Americano", "qty": 2}]}');
SELECT COUNT(*) AS documents FROM order_docs;`} />

Expected: 1 row, 1 column: 3 documents. (`CREATE OR REPLACE` lets you run it again.)

### 2. Read inside a document, or look it up by key

`->>` reads a field of a document as text, and `[0]` is the first item: JSON counts from 0, says the DuckDB documentation. A
field the document lacks gives `NULL`.

**Try it** (read fields, and a missing one).

<RunSQL query={`SELECT doc_key, doc->>'$.store' AS store, doc->>'$.customer' AS customer, doc->>'$.items[0].product' AS first_item
FROM order_docs
ORDER BY doc_key;`} />

Expected: 3 rows, 4 columns. *Why:* order 1335's document has no `customer` field, so its result is `NULL`.

**Try it** (a lookup by key). The key is all a key-value store needs.

<RunSQL query={`SELECT doc FROM order_docs WHERE doc_key = 'order:1001';`} />

Expected: 1 row, 1 column.

### 3. Split the orders by a key

A **single-machine** database keeps its data on one computer; by default DuckDB runs inside the program that uses it. A
**distributed** database spreads data over several machines, because one system made bigger eventually hits a hardware
limit. Partitioning splits the rows by a **partition key**: each row goes to the piece for its key value, and pieces on
separate servers (computers that store data and answer queries) are called **shards**. DuckDB's `PARTITION_BY` writes one folder per value, named like
`store_id=3`, with the rows inside.

**Try it** (partition the orders by store). The files stay in the page's memory.

<RunSQL query={`COPY (SELECT order_id, customer_id, store_id, ordered_at, status, payment_method FROM orders)
TO 'orders_by_store' (FORMAT parquet, PARTITION_BY (store_id));`} />

Expected: 1 row, 1 column: the 1,800 rows written. A folder `orders_by_store` now has a subfolder per store: `store_id=1`,
`store_id=2`, `store_id=3`, with Parquet files (a compact file format for tables) inside.

**Try it** (read the partitions). Before you run it: how many rows? Then, for a filter on store 3, how many of the three
folders will the engine open?

<RunSQL query={`SELECT store_id, COUNT(*) AS orders
FROM read_parquet('orders_by_store/*/*.parquet', hive_partitioning = true)
GROUP BY store_id
ORDER BY store_id;`} />

<RunSQL query={`EXPLAIN SELECT COUNT(*)
FROM read_parquet('orders_by_store/*/*.parquet', hive_partitioning = true)
WHERE store_id = 3;`} />

Expected: the first returns 3 rows, 2 columns. The plan has a read-Parquet step with `File Filters` on `store_id = 3` and a
`Scanning Files` line whose first number is smaller than its second. *Why:* a query that filters on the key opens only the folders with that value; the other folders are never opened.

### 4. What spreading costs, and when SQL still wins

The key decides which piece holds a row, so it decides how the work spreads. A piece that gets far more work than the rest
is a **hot partition**. A **replica** is a copy of a piece kept on another server. Copies take time to synchronize, so for
a while two of them can differ: this is **eventual consistency**.

**Try it** (check the sizes). The 729, 716 and 355 of unit 3 must add up to the whole.

<RunSQL query={`SELECT COUNT(*) AS orders FROM orders;`} />

Expected: 1 row, 1 column. *Why:* **1800**, the sum of the three folders. Harbor opened on April 1, so its folder is half the
size of the others.

<details>
<summary>Explain it in your own words: why can SQL still answer questions across the documents?</summary>

A SQL engine looks inside many rows at once, so a total by store is one query. A store that serves whole objects by key
leaves that work to the application.

</details>

**When SQL is still the answer:** for questions across many rows (totals, comparisons, joins), when rules and multi-row
changes must hold, and when the data fits one machine, as the 1,800 orders of cafe-sales do.

<Aside type="tip" title="Remember">

- Partition by a key; a query that filters on the key opens only the pieces it needs.
- Document: one whole object at a time. Key-value: a lookup by key. Tables: rules and joins.
- Copies (replicas) can differ for a while: eventual consistency.

**Common trap: "NoSQL means a database with no SQL."** NoSQL names stores that relax relational rules, not stores that cannot
be queried: Azure Cosmos DB for NoSQL (Microsoft's cloud database service) supports SQL-like querying. Microsoft's guide adds that most production systems use
several storage models.

</Aside>
