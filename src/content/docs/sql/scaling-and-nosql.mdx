A **single-machine** database keeps its data on one computer; by default DuckDB runs inside the program that uses it
(its documentation says so). A **distributed** database spreads data over several machines. Microsoft's partitioning
guidance gives the reason: a single system that you make bigger hits a hardware limit, while data divided across servers
can scale out much further.

**Partitioning** splits a table's rows by a key, such as the store, into pieces that can be stored, read and managed on
their own. Pieces on separate servers are called shards, and a bad key makes a hot partition with far more work than the rest.

**NoSQL** stores relax some relational rules for flexibility or scale, say the Microsoft Learn data-model pages:

| Shape | Looks like | Good at | Gives up |
|---|---|---|---|
| Structured (relational) | tables, keys, joins | rules, joins, changes across many rows at once | scaling out needs sharding |
| Document | JSON objects whose fields can differ | reading or saving one whole object | joins; a change usually covers one document |
| Key-value | a key and an opaque value | very fast lookup by key | any question that is not "the value for this key" |

## Worked example

Question: **what would a document store, a key-value store and partitions look like for the cafes?** Run the setup cell,
then one cell per step. Each step gives the shape of the result to expect.

1. **Order 1001 as rows.**

   ```sql
   SELECT o.order_id, s.store_name, p.product_name, oi.quantity
   FROM orders AS o
   JOIN stores AS s ON s.store_id = o.store_id
   JOIN order_items AS oi ON oi.order_id = o.order_id
   JOIN products AS p ON p.product_id = oi.product_id
   WHERE o.order_id = 1001;
   ```

   Expected: 3 rows, 4 columns, the table of the question. *Why:* a structured store spreads one order over tables.

2. **The same order as a document under a key.**

   ```sql
   CREATE TABLE order_docs (doc_key VARCHAR PRIMARY KEY, doc JSON);
   INSERT INTO order_docs VALUES ('order:1001',
     '{"order_id": 1001, "store": "Campus", "customer": 15, "items": [{"product": "Croissant", "qty": 1}, {"product": "Cold Brew", "qty": 1}, {"product": "Espresso", "qty": 2}]}');
   ```

   Expected: no error. The notebook also adds orders 1002 and 1335. *Why:* a key and a value, here JSON text in DuckDB's
   `JSON` type. Order 1335 is the walk-in with no customer.

3. **Read fields, and a missing one.**

   ```sql
   SELECT doc_key, doc->>'$.store' AS store, doc->>'$.customer' AS customer, doc->>'$.items[0].product' AS first_item
   FROM order_docs ORDER BY doc_key;
   ```

   Expected: 3 rows, 4 columns. *Why:* `->>` reads a field as text, and `[0]` is the first item (JSON counts from 0, says the
   DuckDB documentation). Order 1335's document has no `customer` field, so the result is `NULL`.

4. **A lookup by key, then a question about the contents.**

   ```sql
   SELECT doc FROM order_docs WHERE doc_key = 'order:1001';
   SELECT doc_key FROM order_docs WHERE doc->>'$.store' = 'Old Town' ORDER BY doc_key;
   ```

   Expected: the first returns 1 row, 1 column; the second 1 column, a row per matching document. *Why:* the first uses only
   the key, all a key-value store does well. The second looks inside every document, which DuckDB can as a SQL engine.

5. **Partition the orders by store.**

   ```sql
   COPY (SELECT order_id, customer_id, store_id, ordered_at, status, payment_method FROM orders)
   TO 'orders_by_store' (FORMAT parquet, PARTITION_BY (store_id));
   ```

   Expected: a `Count` table, 1 row. A folder `orders_by_store` appears with a subfolder per store: `store_id=1`, `store_id=2`,
   `store_id=3`. *Why:* `PARTITION_BY` writes a folder per value of the key, with Parquet files inside.

6. **Read the partitions.**

   ```sql
   SELECT store_id, COUNT(*) AS orders
   FROM read_parquet('orders_by_store/*/*.parquet', hive_partitioning = true)
   GROUP BY store_id ORDER BY store_id;

   EXPLAIN SELECT COUNT(*)
   FROM read_parquet('orders_by_store/*/*.parquet', hive_partitioning = true)
   WHERE store_id = 3;
   ```

   Expected: the first returns 3 rows, 2 columns. The plan has a `Read Parquet` box with `File Filters: store_id = 3` and a
   `Scanning Files` line whose first number is smaller than its second. *Why:* a filter on the partition key lets DuckDB skip
   the folders that cannot match.

7. **Verify.** The counts are 729, 716 and 355, and they add to 1,800.

   ```sql
   SELECT COUNT(*) AS orders FROM orders;
   SELECT COUNT(*) AS orders FROM read_parquet('orders_by_store/*/*.parquet', hive_partitioning = true);
   ```

   Expected: each returns 1 row, 1 column. Harbor opened on April 1, so its folder is about half the size of the others.

<details>
<summary>Explain it in your own words: why can SQL still answer questions across the documents?</summary>

A SQL engine is built to look inside many rows at once, so a total by store is one query. A store that serves whole objects
by key leaves that work to the application.

</details>

**When SQL is still the answer:** for questions across many rows (totals, comparisons, joins), when rules and multi-row
changes must hold, and when the data fits one machine. Cafe-sales has 1,800 orders and 3,287 lines; one machine holds them
easily.
