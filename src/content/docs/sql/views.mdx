## The question

The owner of the cafes asks:

> Two of you gave me total sales: 22,754.25 and 22,749.25. Which is right? And can we make sure everyone uses the same
> one?

The difference is 5.00: the one canceled order. Both figures include the extra-zero line (order 2075). Our definition of
sales is **completed orders only**, but each analyst pastes a join into every report and has to remember the filter.
The first rows of that join, with the amount of each line (some columns left out):

| order_item_id | order_id | product_name | quantity | amount_usd |
|---:|---:|---|---:|---:|
| 5001 | 1001 | Croissant | 1 | 3.25 |
| 5002 | 1001 | Cold Brew | 1 | 4.75 |
| 5003 | 1001 | Espresso | 2 | 6.00 |

## Learn by doing

Five small steps. Each gives you one idea, then you try it in the editor under it. Everything is completed orders: 3,286 lines in 1,799 orders. Views you create in one step stay for the later ones on this page.

### 1. Write the query once

Look at a query before you save it. This one joins the three tables into one row per order line, as in `order_items`, with the amount of the line: `quantity × unit_price_usd − discount_usd`. `ORDER BY` and `LIMIT` are for looking, so they stay out of the view.

**Try it**.

<RunSQL query={`SELECT i.order_item_id, o.order_id, CAST(o.ordered_at AS DATE) AS order_day, o.store_id,
       p.product_name, p.category, i.quantity,
       i.quantity * p.unit_price_usd - i.discount_usd AS amount_usd
FROM order_items AS i
JOIN orders AS o ON o.order_id = i.order_id
JOIN products AS p ON p.product_id = i.product_id
WHERE o.status = 'completed'
ORDER BY i.order_item_id
LIMIT 5;`} />

Expected: 5 rows, 8 columns, the first being line 5001. *Why:* the grain is one row per line, so check it now: it is what every reader of the view will get.

### 2. Save it as a view

`CREATE VIEW sales_lines AS …` stores the query in the database. It computes nothing and copies no rows. The DuckDB documentation: "The view is not physically materialized. Instead, the query is run every time the view is referenced in a query." If the tables change, the next read shows the change.

*Excel:* a Power Query query (E14, *Repeatable cleaning with Power Query*) is the closest thing: it records its steps and runs them again each time you refresh. A view is the same recipe, run each time a query reads it.

**Try it**: the same query without `ORDER BY` and `LIMIT`, after `CREATE OR REPLACE VIEW sales_lines AS`.

<RunSQL query={`CREATE OR REPLACE VIEW sales_lines AS
SELECT i.order_item_id, o.order_id, CAST(o.ordered_at AS DATE) AS order_day, o.store_id,
       p.product_name, p.category, i.quantity,
       i.quantity * p.unit_price_usd - i.discount_usd AS amount_usd
FROM order_items AS i
JOIN orders AS o ON o.order_id = i.order_id
JOIN products AS p ON p.product_id = i.product_id
WHERE o.status = 'completed';`} />

Expected: no result rows. *Why:* nothing is computed yet. `OR REPLACE` lets you run the block again; without it, a second `CREATE VIEW` stops with the error `View with name "sales_lines" already exists!`.

**Try it**: see what is stored.

<RunSQL query={`SELECT sql FROM duckdb_views() WHERE view_name = 'sales_lines';`} />

Expected: 1 row, 1 column: the text of the `CREATE VIEW`, not any rows. *Why:* this is what runs each time you read the view. (The DuckDB documentation shows this query.)

### 3. Read it like a table

A query that reads the view treats the result like any table: it can filter, group and join it. A CTE is the same idea with a smaller scope. The documentation: "Regular (non-recursive) common-table-expressions are essentially views that are limited in scope to a particular query."

| | CTE (S13) | View |
|---|---|---|
| Lives | for one query | in the database, until dropped |

**Try it**.

<RunSQL query={`SELECT store_id, COUNT(*) AS lines, ROUND(SUM(amount_usd), 2) AS sales
FROM sales_lines
GROUP BY store_id
ORDER BY store_id;`} />

Expected: 3 rows, 3 columns: lines 1337, 1304 and 645, sales 9144.25, 8998.75 and 4606.25. *Why:* the join and the filter are inside the view, so the report only groups. The same view feeds a query by `category`.

<RunSQL query={`SELECT category, COUNT(*) AS lines, ROUND(SUM(amount_usd), 2) AS sales
FROM sales_lines
GROUP BY category
ORDER BY category;`} />

Expected: 4 rows, 3 columns.

### 4. Share only some columns

A view exposes only the columns its query lists, so even `SELECT *` on it cannot return the rest. That is not a lock: "Regular views can expose data that the view query would filter out (for example via `stats()`)." DuckDB 2.0 added `CREATE SECURE VIEW` for that case. Treat a view as a convenient shape unless your database's documentation promises more.

**Try it**. A partner needs the orders but not who placed them.

<RunSQL query={`CREATE OR REPLACE VIEW orders_shared AS
SELECT order_id, store_id, ordered_at, status, payment_method FROM orders;

SELECT * FROM orders_shared ORDER BY order_id LIMIT 3;`} />

Expected: 3 rows, 5 columns; `orders` has 6, and `customer_id` is missing. *Why:* the view lists only the columns you chose.

### 5. Views live in one database

Your views are stored in the database that made them, and go with it. The DuckDB documentation says an in-memory database means "no tables are persisted on disk".

**Try it**: list the views in this database.

<RunSQL query={`SELECT view_name FROM duckdb_views() WHERE NOT internal ORDER BY view_name;`} />

Expected: 1 column, the views you made on this page so far, such as `orders_shared` and `sales_lines`. *Why:* open a fresh page, or use Reset data, and they are gone: run the `CREATE` blocks again.

<Aside type="note" title="Triggers: know the word">
A view runs when you read it. A **trigger** runs when data changes. The PostgreSQL documentation: "A trigger is a
specification that the database should automatically execute a particular function whenever a certain type of
operation is performed." For example, a database can write a line to a log table whenever a row is inserted into
`orders`. You will not write one here: the statement below is refused with a syntax error, and the tip under it is generic.
</Aside>

<RunSQL query={`CREATE TRIGGER log_order AFTER INSERT ON orders
BEGIN
  SELECT 1;
END`} />

<Aside type="tip" title="Remember">

- A view stores a query, not rows: the query runs every time something reads the view.
- Read a view like a table, and keep its grain in mind: here, one row per line.
- A view lists only the columns you chose. That is a convenient shape, not a lock.
- A CTE lives for one query; a view lives in the database until dropped.

**Common trap: "a view is a copy of the data, like a range pasted as values."** A pasted range is a snapshot. A view holds no rows at all, only the query, so it always reads the tables as they are now.

</Aside>

<details>
<summary>Hint</summary>

Copy the two aggregates from unit 3. A view can read another view, because a view is read like a table.

</details>

<details>
<summary>Half-solution</summary>

```sql
SELECT order_day, COUNT(*) AS lines, ... AS sales
```

</details>

<Solution>

```sql
CREATE OR REPLACE VIEW daily_sales AS
SELECT order_day, COUNT(*) AS lines, ROUND(SUM(amount_usd), 2) AS sales
FROM sales_lines
GROUP BY order_day;

SELECT COUNT(*) AS days, ROUND(SUM(sales), 2) AS sales, SUM(lines) AS lines FROM daily_sales;
```

`181 | 22749.25 | 3286`. One row per day, and the totals match unit 3: nothing was lost between the view and
the view of the view.

</Solution>


`729`, `715` and `355`. One row of the view is a line, so `COUNT(*)` would return the lines (1337, 1304 and 645).
`COUNT(DISTINCT order_id)` counts each order once. Check:
`SELECT store_id, COUNT(*) FROM orders WHERE status = 'completed' GROUP BY store_id;` gives the same three numbers. A
view keeps the grain of its query: read it with that grain in mind.

</Solution>

</Exercise>

## Check yourself

1. Without looking back: what does a view store, and when does it run?

   <details>
   <summary>Answer</summary>

   It stores the query, not the rows. The query runs every time something reads the view.

   </details>

<Exercise id="sql-views-3">

**Spot the flaw.** The team's reports all read a view `team_sales`, which is `sales_lines` under another name. Needs
`sales_lines` from unit 2. Run this first: it builds the view for you, and the total is 22,749.25.

<RunSQL query={`CREATE OR REPLACE VIEW team_sales AS
SELECT * FROM sales_lines;

SELECT ROUND(SUM(amount_usd), 2) AS sales FROM team_sales;`} />

A colleague wants the canceled lines too, for an audit, and runs the same view query without the
`WHERE o.status = 'completed'` line, under the name `team_sales`. Then they run the same check:

<RunSQL query={`CREATE OR REPLACE VIEW team_sales AS
SELECT i.order_item_id, o.order_id, CAST(o.ordered_at AS DATE) AS order_day, o.store_id,
       p.product_name, p.category, i.quantity,
       i.quantity * p.unit_price_usd - i.discount_usd AS amount_usd
FROM order_items AS i
JOIN orders AS o ON o.order_id = i.order_id
JOIN products AS p ON p.product_id = i.product_id;

SELECT ROUND(SUM(amount_usd), 2) AS sales FROM team_sales;`} />

Expected: 1 row, 1 column. What went wrong, and what should they have done?

<Solution>

The check returns `22754.25`, and the view now has 3,287 lines. `OR REPLACE` changed the definition that every report
reads, so every total on the team went up by the canceled 5.00 without anyone touching a report: the two-totals problem
of the owner's question, made by one run.

An audit view needs its own name:

```sql
CREATE OR REPLACE VIEW team_sales_audit AS
SELECT ...   -- the query without the WHERE line
```

The shared name keeps its meaning, and the audit reads `team_sales_audit`.

</Solution>
