## The question

The owner of the cafes asks:

> Two of you gave me total sales: 22,754.25 and 22,749.25. Which is right? And can we make sure everyone uses the same
> one?

The difference is 5.00: the one canceled order. Both figures include the extra-zero line (order 2075). Our definition of
sales is **completed orders only**, but each analyst pastes a join into every report and has to remember the filter.
The first rows of that join, with the amount of each line (some columns left out):

| order_item_id | order_id | product_name | quantity | amount_usd |

| 5001 | 1001 | Croissant | 1 | 3.25 |
| 5002 | 1001 | Cold Brew | 1 | 4.75 |
| 5003 | 1001 | Espresso | 2 | 6.00 |

By the end you will have saved that join once, as a view that holds the definition, and answered the owner.

`CREATE VIEW name AS query` saves a query. The DuckDB documentation: "The view is not physically materialized.
Instead, the query is run every time the view is referenced in a query." So a view keeps the question, not the answer:
read it later and you get today's rows. It looks like a CTE (S13), and the documentation says: "Regular
(non-recursive) common-table-expressions are essentially views that are limited in scope to a particular query."

| | CTE | View |
|---|---|---|
| Lives | for one query | in the database, until dropped |
| Use it when | one query needs the step | several queries or people need the same definition |

## Worked example

Question: **what is the one definition of sales, and what do the stores and categories add up to?** Run the notebook's
setup cell, then one cell per step. Everything is completed orders, 3,286 lines in 1,799 orders.

1. **Write the query once.** The amount of a line is `quantity × unit_price_usd − discount_usd`.

   ```sql
   SELECT i.order_item_id, o.order_id, CAST(o.ordered_at AS DATE) AS order_day, o.store_id,
          p.product_name, p.category, i.quantity,
          i.quantity * p.unit_price_usd - i.discount_usd AS amount_usd
   FROM order_items AS i
   JOIN orders AS o ON o.order_id = i.order_id
   JOIN products AS p ON p.product_id = i.product_id
   WHERE o.status = 'completed'
   ORDER BY i.order_item_id
   LIMIT 5;
   ```

   Expected: 5 rows, 8 columns, the first being line 5001. *Why:* look at it before you save it. The grain is one row
   per line, as in `order_items`. `ORDER BY` and `LIMIT` are for looking, so they stay out of the view.

2. **Save it as a view.** Run the same query without the last two lines, after `CREATE OR REPLACE VIEW sales_lines AS`.

   ```sql
   CREATE OR REPLACE VIEW sales_lines AS
   SELECT i.order_item_id, ...   -- the query from step 1, without ORDER BY and LIMIT
   ```

   Expected: no result rows (the notebook prints an empty table with a `Count` column). *Why:* nothing is computed yet.
   `OR REPLACE` lets you run the cell again; without it, a second `CREATE VIEW` stops with `Catalog Error: View with name
   "sales_lines" already exists!`.

3. **Read the view like a table.**

   ```sql
   SELECT store_id, COUNT(*) AS lines, ROUND(SUM(amount_usd), 2) AS sales
   FROM sales_lines
   GROUP BY store_id
   ORDER BY store_id;
   ```

   Expected: 3 rows, 3 columns: lines 1337, 1304 and 645, sales 9144.25, 8998.75 and 4606.25. *Why:* the join and the
   filter are inside the view, so the report only groups. The same view feeds a query by `category` (4 rows).

4. **Verify.**

   ```sql
   SELECT COUNT(*) AS lines, ROUND(SUM(amount_usd), 2) AS sales FROM sales_lines;
   ```

   Expected: 1 row, 2 columns: `3286 | 22749.25`. A second route, for all lines of every status, without the view:

   ```sql
   SELECT ROUND(SUM(i.quantity * p.unit_price_usd - i.discount_usd), 2) AS all_sales
   FROM order_items AS i
   JOIN products AS p ON p.product_id = i.product_id;
   ```

   Expected: 1 row, 1 column: `22754.25`. Minus the canceled 5.00 it is 22,749.25: the same. The three stores add up to
   22,749.25 too. Answer: **22,749.25 is the completed-orders total, and a view now holds that definition for everyone.**

5. **See what is stored.**

   ```sql
   SELECT sql FROM duckdb_views() WHERE view_name = 'sales_lines';
   ```

   Expected: 1 row, 1 column: the text of the `CREATE VIEW`, not any rows. *Why:* this is what runs each time you read
   the view. (The DuckDB documentation shows this query.)

6. **Share only some columns.** A partner needs the orders but not who placed them:

   ```sql
   CREATE OR REPLACE VIEW orders_shared AS
   SELECT order_id, store_id, ordered_at, status, payment_method FROM orders;
   SELECT * FROM orders_shared LIMIT 3;
   ```

   Expected: the second cell shows 3 rows, 5 columns; `orders` has 6, and `customer_id` is missing. *Why:* the view
   lists the columns it exposes, so even `SELECT *` on it cannot return the rest. It is not a lock: "Regular views can
   expose data that the view query would filter out (for example via stats())." DuckDB 2.0 added `CREATE SECURE VIEW` for
   that case. Treat a view as a convenient shape unless your database's documentation promises more.

7. **Views live in the database that made them.**

   ```python
   other = duckdb.connect()   # a second, empty in-memory database
   other.sql("SELECT COUNT(*) FROM sales_lines").show()
   ```

   Expected: an error that starts with `Catalog Error`: `Table with name sales_lines does not exist!` The notebook prints the error instead of stopping. *Why:* the DuckDB
   documentation says an in-memory database means "no tables are persisted on disk". Your views are in the notebook's
   database and go with it: after a restart, run the setup cell and the `CREATE` cells again.

<Aside type="note" title="Triggers: know the word">
A view runs when you read it. A **trigger** runs when data changes. The PostgreSQL documentation: "A trigger is a
specification that the database should automatically execute a particular function whenever a certain type of
operation is performed." For example, a database can write a line to a log table whenever a row is inserted into
`orders`. You will not write one here: in the notebook's last worked step, `CREATE TRIGGER` ends in a Parser Error on DuckDB 2.0.0. As in step 7, the notebook prints the error instead of stopping.
</Aside>

<details>
<summary>Explain it in your own words: when is a CTE enough, and when do you want a view?</summary>

A CTE is enough when one query needs the step. A view is better when several queries or people need the same
definition, because the definition then lives in one place and a fix reaches everyone.

</details>

**Save daily sales as a view, built on the view you already have.** Needs `sales_lines` from step 2. Use the Exercise 1

The first steps are done for you:

```sql
CREATE OR REPLACE VIEW daily_sales AS
```

Now finish it: replace `...` with the number of lines and the rounded sum of `amount_usd`, named `lines` and `sales`.
Then check it with one query: the number of rows of `daily_sales`, the sum of `sales` and the sum of `lines`.

<details>
<summary>Hint</summary>

Copy the two aggregates from step 3. A view can read another view, because a view is read like a table.

```sql
SELECT order_day, COUNT(*) AS lines, ... AS sales
```

<Solution>

```sql

SELECT order_day, COUNT(*) AS lines, ROUND(SUM(amount_usd), 2) AS sales
```

the view of the view.

</Solution>

**Spot the flaw.** The team's reports all read a view `team_sales`, which is `sales_lines` under another name. In the

```sql
CREATE OR REPLACE VIEW team_sales AS
```

Then they run `SELECT ROUND(SUM(amount_usd), 2) AS sales FROM team_sales;`. Expected: 1 row, 1 column. What went wrong,

<Solution>

The check returns `22754.25`, and the view now has 3,287 lines. `OR REPLACE` changed the definition that every report
reads, so every total on the team went up by the canceled 5.00 without anyone touching a report: the two-totals problem
of the owner's question, made by one cell.

An audit view needs its own name:

```sql
CREATE OR REPLACE VIEW team_sales_audit AS
SELECT ...   -- the query without the WHERE line
```

The shared name keeps its meaning, and the audit reads `team_sales_audit`.
