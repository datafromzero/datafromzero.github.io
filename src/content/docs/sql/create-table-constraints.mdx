## The question

The owner of the cafes asks:

> I want a stock sheet: how many units of each product each cafe has on the shelf. Last time someone typed a price of
> 0, a category called "dessert" that we do not have, and the same product twice. Can the database stop that?

The `products` table is plain, as *Tables, keys and grain* said: it states no rules, so it accepts anything. Its top
rows, and the first rows of the stock sheet we want (store, product, units):

| product_id | product_name | category | unit_price_usd |
|---:|---|---|---:|
| 1 | Espresso | coffee | 3.00 |
| 2 | Americano | coffee | 3.50 |
| 3 | Latte | coffee | 4.50 |

| store_id | product_id | units_on_hand |
|---:|---:|---:|
| 1 | 1 | 40 |
| 1 | 10 | 25 |
| 1 | 6 | 12 |

## The big idea

A **constraint** is a rule you write into a table's definition: the database tests every new row against it and refuses
the row that breaks it.

## Learn by doing

Five small steps.

### 1. Write the rules into the table

A table is written `CREATE TABLE name (column type rules, ...)`: each column gets a type and, beside it, its rules.
Four rules sit beside a column:

- `PRIMARY KEY` refuses a repeated or empty value. A table has at most one, and it may span several columns.
- `UNIQUE` refuses a repeated value. A table may have several, and several rows may hold `NULL`.
- `NOT NULL` refuses an empty value. Without it, a column accepts `NULL`.
- `CHECK` refuses a row that makes your true-or-false expression false.

*Excel:* data validation (E18, *Highlight and validate with rules*) limits what a user may type into a cell, for example
to a dropdown list. A `CHECK ... IN (...)` is the same idea written into the table.

**Try it.** `DECIMAL(6, 2)` is money: up to six digits, two after the point (S5). `is_active` is new: a
row that does not mention it counts as active.

<RunSQL query={`CREATE TABLE menu (
  product_id INTEGER PRIMARY KEY,
  product_name VARCHAR NOT NULL UNIQUE,
  category VARCHAR NOT NULL CHECK (category IN ('coffee', 'tea', 'bakery', 'food')),
  unit_price_usd DECIMAL(6, 2) NOT NULL CHECK (unit_price_usd > 0),
  is_active BOOLEAN DEFAULT true
);`} />

Expected: no result rows, just a note that the statement ran. *Why:* the four categories are the ones `products` uses.

**Try it.** Fill it from `products`.

<RunSQL query={`INSERT INTO menu (product_id, product_name, category, unit_price_usd)
SELECT * FROM products;`} />

Expected: 1 row, 1 column: the 16 rows stored. *Why:* naming four columns leaves `is_active` to its default. If one row of
`products` broke a rule, the whole statement would fail. Run it again to see: the rows are already there, so the primary
key refuses them.

**Try it.** Read the rules back.

<RunSQL query={`DESCRIBE menu;`} />

Expected: 5 rows, 6 columns: `key` shows `PRI` for `product_id` and `UNI` for `product_name`, and `null` shows `NO` on
four of the five columns.

### 2. Point one table at another

A **foreign key** refuses a value that has no match in another table's key. That key must be a primary key or a `UNIQUE`
column. The cafe-sales tables declare neither, so `stock` points at `menu`, the copy you just built with its rules.

`stock` also has a key of two columns: one row is one product at one store, so the pair is the key.

**Try it.**

<RunSQL query={`CREATE TABLE stock (
  store_id INTEGER NOT NULL CHECK (store_id IN (1, 2, 3)),
  product_id INTEGER NOT NULL REFERENCES menu (product_id),
  units_on_hand INTEGER NOT NULL DEFAULT 0 CHECK (units_on_hand >= 0),
  PRIMARY KEY (store_id, product_id)
);`} />

Expected: no result rows. *Why:* `store_id` has no foreign key because `stores` has no primary key to point at, so a `CHECK`
on the three store ids stands in.

### 3. Rows that obey the rules

A `DEFAULT` sets the value of a column that an `INSERT` leaves out. It refuses nothing: it only fills in a value.

**Try it.** Before you run it: the second insert names only two columns. What will the Green Tea row
show for `units_on_hand`?

<RunSQL query={`INSERT INTO stock VALUES (1, 1, 40), (1, 10, 25), (1, 6, 12);
INSERT INTO stock (store_id, product_id) VALUES (1, 7);
SELECT * FROM stock ORDER BY product_id;`} />

Expected: 4 rows, 3 columns (the page shows the last result). *Why:* the Green Tea row shows **0**, its `DEFAULT`; a column with no `DEFAULT` would get `NULL`. A
second run of the block meets the primary key: the first row is already there.

### 4. Rows that break the rules

Each new row is tested against the rules of the table, and a row that breaks one is refused with a `Constraint Error` and
not stored. A row that breaks several is refused once, and DuckDB names one of them.

**Try it.** Before you run them: which rule do you expect to refuse each of these four
rows? Run them one at a time.

<RunSQL query={`INSERT INTO stock VALUES (1, 99, 10);`} />

<RunSQL query={`INSERT INTO stock VALUES (2, 1, -5);`} />

<RunSQL query={`INSERT INTO stock VALUES (1, 1, 20);`} />

<RunSQL query={`INSERT INTO stock VALUES (NULL, 2, 20);`} />

Expected: every block shows an error instead of a table, and its message names the rule (the page shows the message without
DuckDB's `Constraint Error:` label):

| Insert | Message | Rule |
|---|---|---|
| `(1, 99, 10)` | `Violates foreign key constraint because key "product_id: 99" does not exist in the referenced table` | `FOREIGN KEY` |
| `(2, 1, -5)` | `CHECK constraint failed on table ... with expression CHECK((units_on_hand >= 0))` | `CHECK` |
| `(1, 1, 20)` | `Duplicate key "store_id: 1, product_id: 1" violates primary key constraint.` | `PRIMARY KEY` |
| `(NULL, 2, 20)` | `NOT NULL constraint failed: stock.store_id` | `NOT NULL` |

### 5. Check that nothing slipped in

A refused row leaves nothing behind. Count to see.

**Try it.**

<RunSQL query={`SELECT 'menu' AS table_name, COUNT(*) AS row_count, SUM(unit_price_usd) AS total FROM menu
UNION ALL
SELECT 'products', COUNT(*), SUM(unit_price_usd) FROM products
UNION ALL
SELECT 'stock', COUNT(*), NULL FROM stock
ORDER BY table_name;`} />

Expected: 3 rows, 3 columns. *Why:* `stock` still has the 4 rows of unit 3, so the four refused inserts left nothing behind.
`menu` matches `products`: 16 items and a price total of 75.00 in both.

<details>
<summary>Explain it in your own words: to refuse product 99, what must DuckDB look in, and what does that say about the order you create the tables?</summary>

It must look in `menu` for a `product_id` of 99 and find none. So `menu` has to exist, and be filled, before `stock` can refer
to it.

</details>

<Aside type="tip" title="Remember">

- A constraint is a rule in the table's definition. A row that breaks one is refused and not stored.
- `PRIMARY KEY` and `UNIQUE` refuse repeats, `NOT NULL` refuses empties, `CHECK` refuses a false expression, `FOREIGN KEY`
  refuses a value with no match in another table.
- `DEFAULT` refuses nothing: it fills in a missing value.

**Common trap: "a constraint guarantees the data is right."** It guarantees only the rule you wrote: `CHECK (unit_price_usd
> 0)` accepts 450.00 for a Latte that costs 4.50, because the expression is true for it.

</Aside>

inserts `'bronze'` with the perk `'free refill'` and no discount, and selects the table. (`CREATE OR REPLACE` lets you run
it again.) Run it and look at `discount_pct`.

<RunSQL query={`CREATE OR REPLACE TABLE tier_perk (
  loyalty_tier VARCHAR,
  perk VARCHAR NOT NULL,
  discount_pct INTEGER
);
INSERT INTO tier_perk (loyalty_tier, perk) VALUES ('bronze', 'free refill');
SELECT * FROM tier_perk;`} />

Now finish it: make `loyalty_tier` the primary key and accept only the three tiers; let `discount_pct` default to 0 and
accept only 0 to 50.

<details>
<summary>Hint</summary>

Copy the `CHECK ... IN (...)` of `category` in unit 1. For a range, `BETWEEN 0 AND 50` works inside a `CHECK`.

</details>

<details>
<summary>Half-solution</summary>

```sql
CREATE OR REPLACE TABLE tier_perk (
  loyalty_tier VARCHAR PRIMARY KEY CHECK (loyalty_tier IN (...)),
  perk VARCHAR NOT NULL,
  discount_pct INTEGER DEFAULT ... CHECK (discount_pct BETWEEN ... AND ...)
);
```

</details>

<Solution>

```sql
CREATE OR REPLACE TABLE tier_perk (
  loyalty_tier VARCHAR PRIMARY KEY CHECK (loyalty_tier IN ('bronze', 'silver', 'gold')),
  perk VARCHAR NOT NULL,
  discount_pct INTEGER DEFAULT 0 CHECK (discount_pct BETWEEN 0 AND 50)
);
INSERT INTO tier_perk (loyalty_tier, perk) VALUES ('bronze', 'free refill');
SELECT * FROM tier_perk;
```

The result is `bronze | free refill | 0`: `DEFAULT 0` filled in the missing discount. The table now refuses
`('platinum', 'lounge', 10)`, a tier not in the list, and `('gold', 'free pastry', 60)`, outside 0 to 50.

</Solution>

</Exercise>

## Check yourself

Without looking back: name the five rules that can refuse a row and the one that never does. Which rule needs a key
in another table?

<details>
<summary>Answer</summary>

`PRIMARY KEY`, `NOT NULL`, `UNIQUE`, `CHECK` and `FOREIGN KEY` can refuse a row. `DEFAULT` never does: it fills in a
missing value. The foreign key needs a primary key (or `UNIQUE` column) in the other table.

</details>

<Exercise id="sql-create-table-constraints-3">

**Spot the flaw.** A colleague copies the menu for a trial with the first statement below and says "it keeps the primary
key, so nothing can be entered twice". To prove it, they run the insert. It works, with no error, and puzzles them. (It
copies `menu` from units 1 and 2.)

<RunSQL query={`CREATE OR REPLACE TABLE menu_copy AS SELECT * FROM menu;
INSERT INTO menu_copy VALUES (1, 'Espresso', 'coffee', 3.00, true);`} />

Expected: 1 row, 1 column (the one row stored). What went wrong, what does `DESCRIBE menu_copy;` show, and what is the fix?

<details>
<summary>Hint</summary>

Run `DESCRIBE menu_copy;` and compare its `key` and `null` columns with `DESCRIBE menu;`.

</details>

<details>
<summary>Half-solution</summary>

Start from: "`menu_copy` has none of the rules of `menu`, because ... The fix is to create the table with its rules first and then fill it with ..."

</details>

<Solution>

A table made with `CREATE TABLE ... AS SELECT` copies the columns and the rows but not the rules, as the DuckDB
documentation says. `DESCRIBE menu_copy;` shows `YES` in the `null` column everywhere and nothing in `key`, so the second
Espresso went in: `SELECT COUNT(*) FROM menu_copy WHERE product_name = 'Espresso';` returns 2.

Write the table with its rules, then fill it:

```sql
CREATE OR REPLACE TABLE menu_copy2 (
  product_id INTEGER PRIMARY KEY,
  product_name VARCHAR NOT NULL UNIQUE,
  category VARCHAR NOT NULL CHECK (category IN ('coffee', 'tea', 'bakery', 'food')),
  unit_price_usd DECIMAL(6, 2) NOT NULL CHECK (unit_price_usd > 0),
  is_active BOOLEAN DEFAULT true
);
INSERT INTO menu_copy2 SELECT * FROM menu;
```

Now the same Espresso insert, into `menu_copy2`, is refused: `Duplicate key "product_id: 1" violates primary key constraint.`

</Solution>

</Exercise>
