## The question

The owner of the cafes asks:

> I want a stock sheet: how many units of each product each cafe has on the shelf. Last time someone typed a price of
> 0, a category called "dessert" that we do not have, and the same product twice. Can the database stop that?

The `products` table is plain, as *Tables, keys and grain* said: it states no rules, so it accepts anything. Its top
rows, and the first rows of the stock sheet we want (store, product, units):

| product_id | product_name | category | unit_price_usd |
|---:|---|---|---:|
| 1 | Espresso | coffee | 3.00 |
| 2 | Americano | coffee | 3.50 |
| 3 | Latte | coffee | 4.50 |

| store_id | product_id | units_on_hand |
|---:|---:|---:|
| 1 | 1 | 40 |
| 1 | 10 | 25 |
| 1 | 6 | 12 |

By the end you will have a `menu` and a `stock` table that refuse five kinds of bad row, and you will say which rule
refused which.

## How it works

A **constraint** is a rule written into a table's definition, next to a column, in
`CREATE TABLE name (column type rules, ...)`. DuckDB applies the rules to rows as they go in, and a row that breaks one
is refused with a `Constraint Error` and not stored. The first picture above writes a table as a form; the second shows
candidate rows meeting its rules. Conceptually, each new row goes through four steps:

1. A column the `INSERT` leaves out is filled with its `DEFAULT`, or with `NULL` if it has none.
2. `NOT NULL` and `CHECK` look at the row alone.
3. `PRIMARY KEY` and `UNIQUE` compare it with the rows already stored: in the second picture, the stored rows are listed
   under the candidates.
4. `FOREIGN KEY` looks in another table. A row that meets every rule is stored.

The rules, and what each refuses:

- `PRIMARY KEY`: a repeated value, or an empty one. A table has at most one primary key, and it may span several
  columns, as in `PRIMARY KEY (store_id, product_id)`.
- `UNIQUE`: a repeated value. A table may have several, and an empty value is allowed.
- `NOT NULL`: an empty value. Without it, a column accepts `NULL`.
- `CHECK`: a row that makes your Boolean expression false, as in `CHECK (units_on_hand >= 0)`.
- `FOREIGN KEY`: a value with no match in another table's key. That key must be a primary key or a `UNIQUE` column, so
  its table is built first. The cafe-sales tables declare neither, so `stock` points at `menu`, a copy of `products`
  that you build with its rules.
- `DEFAULT` refuses nothing: it fills in a value when you give none.

**Excel.** Data validation (E18, *Highlight and validate with rules*) restricts the values a user may enter into a cell,
for example to a dropdown list. A `CHECK ... IN (...)` is the same idea written into the table.

**A common misconception: "a constraint guarantees the data is right."** It guarantees only the rule you wrote:
`CHECK (unit_price_usd > 0)` accepts 450.00 for a Latte that costs 4.50, because the expression is true for it.

You write the table with its rules, then fill it with `INSERT INTO ... SELECT`, as step 2 does. The next lesson,
*Inserting, updating and deleting safely*, teaches `INSERT` in full.

## Worked example

Question: **can we build a menu and a stock sheet that refuse bad rows?** Run the notebook's setup cell, then one cell
per step. Each step gives the shape of the result to expect.

1. **Create `menu` with its rules.**

   ```sql
   CREATE TABLE menu (
     product_id INTEGER PRIMARY KEY,
     product_name VARCHAR NOT NULL UNIQUE,
     category VARCHAR NOT NULL CHECK (category IN ('coffee', 'tea', 'bakery', 'food')),
     unit_price_usd DECIMAL(6, 2) NOT NULL CHECK (unit_price_usd > 0),
     is_active BOOLEAN DEFAULT true
   );
   ```

   Expected: no error, and an empty `Count` table. *Why:* each column has a type and its rules beside it. The four
   categories are the ones `products` uses. `is_active` is new: a row that does not mention it counts as active.

2. **Fill it from `products`, then read the rules back.** Two notebook cells.

   ```sql
   INSERT INTO menu (product_id, product_name, category, unit_price_usd)
   SELECT * FROM products;

   DESCRIBE menu;
   ```

   Expected: the first returns 1 row, 1 column (`Count`, the rows stored). The second returns 5 rows, 6 columns:
   `key` shows `PRI` for `product_id` and `UNI` for `product_name`, and `null` shows `NO` on four of the five columns.
   *Why:* naming four columns leaves `is_active` to its default. If one row of `products` broke a rule, the whole
   statement would fail.

3. **Create `stock`, with a two-column key and a foreign key.**

   ```sql
   CREATE TABLE stock (
     store_id INTEGER NOT NULL CHECK (store_id IN (1, 2, 3)),
     product_id INTEGER NOT NULL REFERENCES menu (product_id),
     units_on_hand INTEGER NOT NULL DEFAULT 0 CHECK (units_on_hand >= 0),
     PRIMARY KEY (store_id, product_id)
   );
   ```

   Expected: no error, an empty `Count` table. *Why:* one row is one product at one store, so the pair is the key.
   `store_id` has no foreign key because `stores` has no primary key to point at; a `CHECK` on the three store ids
   stands in. A real design would constrain a copy of `stores` as step 1 does for `menu`.

4. **Add rows that obey the rules.**

   ```sql
   INSERT INTO stock VALUES (1, 1, 40), (1, 10, 25), (1, 6, 12);
   INSERT INTO stock (store_id, product_id) VALUES (1, 7);
   SELECT * FROM stock ORDER BY product_id;
   ```

   Expected: one notebook cell, showing the last result: 4 rows, 3 columns. *Why:* the second insert names only two
   columns, so `units_on_hand` takes its `DEFAULT`, and the Green Tea row shows 0.

5. **Try four rows that break the rules.** Four notebook cells, one statement each.

   ```sql
   INSERT INTO stock VALUES (1, 99, 10);
   INSERT INTO stock VALUES (2, 1, -5);
   INSERT INTO stock VALUES (1, 1, 20);
   INSERT INTO stock VALUES (NULL, 2, 20);
   ```

   Expected: every cell prints an error instead of a table (the notebook catches it, so Run all keeps going), and the message starts `Constraint Error:`. The rest names the rule:

   | Insert | Message continues | Gate |
   |---|---|---|
   | `(1, 99, 10)` | `Violates foreign key constraint because key "product_id: 99" does not exist in the referenced table` | `FOREIGN KEY` |
   | `(2, 1, -5)` | `CHECK constraint failed on table "stock" with expression CHECK((units_on_hand >= 0))` | `CHECK` |
   | `(1, 1, 20)` | `Duplicate key "store_id: 1, product_id: 1" violates primary key constraint.` | `PRIMARY KEY` |
   | `(NULL, 2, 20)` | `NOT NULL constraint failed: stock.store_id` | `NOT NULL` |

   *Why:* each row breaks exactly one rule. A row that breaks two is refused once, with one of the messages, so
   `(1, 1, -5)` would name the key, not the `CHECK`.

6. **Verify.** Three notebook cells.

   ```sql
   SELECT COUNT(*) AS stock_rows FROM stock;
   SELECT COUNT(*) AS items, SUM(unit_price_usd) AS total FROM menu;
   SELECT COUNT(*) AS items, SUM(unit_price_usd) AS total FROM products;
   ```

   Expected: each returns 1 row; the last two have 2 columns. `stock` still has the 4 rows of step 4, so the four
   refused inserts left nothing behind. `menu` matches `products`: 16 items and a price total of 75.00 in both.

<details>
<summary>Explain it in your own words: why must you create <code>menu</code> before <code>stock</code>?</summary>

The foreign key in `stock` points at `menu.product_id`, and DuckDB needs that column to be a primary key or
`UNIQUE`. It also has to exist, so the check on product 99 has something to look in.

</details>
