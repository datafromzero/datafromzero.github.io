This lesson uses the same tables as *From a spreadsheet to SQL* (S1): the five tables of **cafe-sales**, the invented
three-cafe chain we use from Excel to Python. Each query runs in the editor on this page.

## The question

The owner of the cafes asks:

> What have we sold in dollars, and which products earn the most? In Excel the total came to 22,754.25. Does the
> database agree?

Until now every query read one table. The money lives in two. Three lines of order 1001 in `order_items`, and the three
products they point at in `products`:

| order_item_id | order_id | product_id | quantity | discount_usd |
|---:|---:|---:|---:|---:|
| 5001 | 1001 | 10 | 1 | 0.00 |
| 5002 | 1001 | 6 | 1 | 0.00 |
| 5003 | 1001 | 1 | 2 | 0.00 |

| product_id | product_name | category | unit_price_usd |
|---:|---|---|---:|
| 1 | Espresso | coffee | 3.00 |
| 6 | Cold Brew | coffee | 4.75 |
| 10 | Croissant | bakery | 3.25 |

A line is worth `quantity × unit_price_usd − discount_usd`. The quantity and the discount sit on the line; the price
sits in `products`. The dollars need both tables.

## Warm-up

From memory first, then click to check.

1. In *Tables, keys and grain* (S18), which column of `order_items` links it to `products`, and what is one row of
   `order_items`?

   <details>
   <summary>Answer</summary>

   `product_id`, a foreign key that holds values of `products.product_id`, the primary key. One row of `order_items`
   is one product line inside one order.

   </details>

2. In *Counting and summing: aggregate functions* (S7), write one query for the number of lines and the units sold.

   <details>
   <summary>Answer</summary>

   ```sql
   SELECT COUNT(*) AS lines, SUM(quantity) AS units FROM order_items;
   ```

   One row, two columns: 3287 lines and 5162 units.

   </details>

## The big idea

A **join** pairs up the rows of two tables that share a value, such as a product id, and gives you one wider row for
each pair.

## Learn by doing

Five small steps. Each gives you one idea, then you try it in the editor.

### 1. Pair the rows on a key

`INNER JOIN` lays out every possible pair, one line and one product, then keeps the pairs where the `ON` condition is
true. Every possible pair is what a `CROSS JOIN` returns (every row with every row, no `ON`): 16 products and 3,287
lines make 52,592 pairs. Each kept pair becomes one wider row, with the columns of both tables. If the key is unique in
the table you join to, each row has at most one partner, so the count cannot grow.

**Try it.** Before you run it: every line has one `product_id`, and `product_id` is the primary key of
`products`. How many rows will the join return?

<RunSQL query={`SELECT COUNT(*) AS joined_rows
FROM order_items AS oi
INNER JOIN products AS p ON oi.product_id = p.product_id;`} />

Read it: `AS oi` and `AS p` are **aliases**, short names for the tables, so `oi.product_id` (table, a dot, column)
leaves no doubt about which table a column comes from. `ON` names the key on each side: the foreign key of the many
side against the primary key of the other (S18). `JOIN` alone means the same as `INNER JOIN`.

Expected: 1 row, 1 column. *Excel:* an XLOOKUP column filled down, with a price on every line, as in *Bring in a value
by key with XLOOKUP* (E8).

*Why:* each line meets exactly one product, so the answer is **3287**, the lines of `order_items` (S18). The grain (what one
row is) is still one line. A different number would mean a line was lost or doubled.

**Try it:** now look at five of the pairs.

<RunSQL query={`SELECT oi.order_item_id, oi.order_id, p.product_name,
       oi.quantity, p.unit_price_usd, oi.discount_usd
FROM order_items AS oi
INNER JOIN products AS p ON oi.product_id = p.product_id
ORDER BY oi.order_item_id
LIMIT 5;`} />

Expected: 5 rows, 6 columns; the first row is line 5001, a Croissant at 3.25. *Why:* the columns come from both tables,
named through the aliases. `ORDER BY` fixes the order, because a join promises none.

### 2. Use the wider table

After the join, every pair is one row of a wider table, and `WHERE`, `GROUP BY` and the rest of the query work on it.
The price lives in `products`, so now a line's amount can use it.

**Try it:** the amount of each line.

<RunSQL query={`SELECT oi.order_item_id,
       p.product_name,
       oi.quantity * p.unit_price_usd - oi.discount_usd AS line_amount_usd
FROM order_items AS oi
INNER JOIN products AS p ON oi.product_id = p.product_id
ORDER BY oi.order_item_id
LIMIT 5;`} />

### 3. A row with no partner disappears

Only paired rows are returned. A row with no partner, from either table, is missing from the result. That includes a
row whose key is `NULL`, an empty value: in an `=` test `NULL` is never equal to anything, not even another `NULL`, so
it pairs with nothing.

**Try it.** Grain: *one row per product sold*. Before you run it: the menu has 16 products. How many
rows?

<RunSQL query={`SELECT p.product_name,
       SUM(oi.quantity) AS units,
       SUM(oi.quantity * p.unit_price_usd - oi.discount_usd) AS sales_usd
FROM order_items AS oi
INNER JOIN products AS p ON oi.product_id = p.product_id
GROUP BY p.product_name
ORDER BY sales_usd DESC;`} />

Expected: 3 columns. *Why:* **15** rows. The Pumpkin Spice Latte is in `products` but on no line, so nothing pairs with
it and the inner join drops it: the product S18 found unsold. The Latte (product 3) leads with 2,927.00, and Green Tea
is last with 783.75. That answers the owner's second question.

**Try it.** Before you run it: there are 1,800 orders. How many rows will `orders` joined to
`order_items` return?

<RunSQL query={`SELECT COUNT(*) AS joined_rows
FROM orders AS o
INNER JOIN order_items AS oi ON o.order_id = oi.order_id;`} />

Expected: 1 row, 1 column. *Why:* **3287**. The key repeats on the `oi` side: an order pairs with each of its one to three
lines, so the grain of the result is the line, and `COUNT(*)` counts lines, not orders. The count grew from 1,800 to
3,287 because the join went from the one side to the many side.

### 5. Check the numbers

No new query. The 3,287 of unit 1 equals the lines of `order_items` and the count of unit 4, so the join to `products`
lost no line and doubled none. Two more Excel totals are slices of unit 2's 22,754.25: E7's Campus coffee in March
(completed orders only) and E21's Sales of 22,749.25 (completed orders only). Exercise 1 reproduces E21's.

<details>
<summary>Explain it in your own words: why did the join to products keep 3,287 rows while the join to order_items grew?</summary>

It depends on which side the key is unique. `product_id` is unique in `products`, so each line finds one product and
the count stays. `order_id` is unique in `orders` but repeats in `order_items`, so each order finds several lines and
the count grows.

</details>

<Aside type="tip" title="Remember">

- `INNER JOIN` makes one wider row for every pair whose `ON` is true.
- A row with no partner, or with an empty key, is missing from the result.
- Key unique on one side: the count cannot grow. Key repeated: *a* × *b* rows.
- Name the key, predict the rows, run the join, compare the count.

**Common trap: "a join is a Venn diagram of two sets."** The circles are right about which keys have a partner: an
inner join keeps the overlap. They say nothing about row counts, because a join counts pairs, not keys. Order 1001 is
one key, but its 3 lines make 3 rows.

</Aside>

## Finish it

<Exercise id="sql-inner-join-1">

**What did completed orders sell, in dollars?** E21 reported Sales of 22,749.25. Expected: 1
row, 1 column, equal to E21's figure.

Done for you: the grain is a line, and the first part of the query is unit 2's:

<RunSQL query={`SELECT SUM(oi.quantity * p.unit_price_usd - oi.discount_usd) AS sales_usd
FROM order_items AS oi
INNER JOIN products AS p ON oi.product_id = p.product_id`} />

The status lives in `orders`, and the result of one join can be joined again. Now finish it: add a second
`INNER JOIN`, to `orders` on `order_id`, and keep only the completed orders.

<details>
<summary>Hint</summary>

The second join goes on the line after the first. Copy the shape of unit 4 for the `ON`, and use `WHERE` as in
*Filtering rows with WHERE* (S3) for the status.

</details>

<details>
<summary>Half-solution</summary>

```sql
...
INNER JOIN products AS p ON oi.product_id = p.product_id
INNER JOIN orders AS o ON ... = ...
WHERE ...;
```

</details>

<Solution>

```sql
SELECT SUM(oi.quantity * p.unit_price_usd - oi.discount_usd) AS sales_usd
FROM order_items AS oi
INNER JOIN products AS p ON oi.product_id = p.product_id
INNER JOIN orders AS o ON oi.order_id = o.order_id
WHERE o.status = 'completed';
```

The result is `22749.25`, E21's Sales. It is 22,754.25 − 5.00: the canceled order 1461 is out. The figure covers 3,286
lines of 1,799 completed orders, and still includes the extra-zero line of order 2075. Chaining joins is the subject of
*Joining three tables and a table to itself* (S23).

</Solution>

## Check yourself

Without looking back: what does an `INNER JOIN` return, and how do you predict its row count before you run it?

<details>
<summary>Answer</summary>

Only the rows that got a pair. Look at which side the key is unique on: if it is unique in the table you join to, the
count cannot grow, and it falls if some rows find no partner; if the key repeats there, the count can grow. Rows with
no pair, or with an empty key, are missing.

</details>

<Exercise id="sql-inner-join-3">

**Spot the flaw.** A colleague wants each order next to its lines and runs this query. It gives an error, not a table:

<RunSQL query={`SELECT order_id, status, quantity
FROM orders AS o
INNER JOIN order_items AS oi ON o.order_id = oi.order_id;`} />

Expected: an error that says a column name is ambiguous. Read it, then fix the query.

<Solution>

The error reads `Ambiguous reference to column name "order_id" (use: "o.order_id" or
"oi.order_id")`. Both tables have an `order_id` column, so the bare name could mean either. Qualify it with an alias:

```sql
SELECT o.order_id, o.status, oi.quantity
FROM orders AS o
INNER JOIN order_items AS oi ON o.order_id = oi.order_id;
```

Expected: 3287 rows, 3 columns. `status` and `quantity` exist in one table each, so they would run bare, but qualify
every column in a join: the query stays readable and survives a new column.

</Solution>
