## The question

The owner of the cafes asks:

> What have we sold in dollars, and which products earn the most? In Excel the total came to 22,754.25. Does the
> database agree?

Three lines of order 1001 in `order_items`, and the three products they point at in `products`:

| order_item_id | order_id | product_id | quantity | discount_usd |
|---:|---:|---:|---:|---:|
| 5001 | 1001 | 10 | 1 | 0.00 |
| 5002 | 1001 | 6 | 1 | 0.00 |
| 5003 | 1001 | 1 | 2 | 0.00 |

| product_id | product_name | category | unit_price_usd |
|---:|---|---|---:|
| 1 | Espresso | coffee | 3.00 |
| 6 | Cold Brew | coffee | 4.75 |
| 10 | Croissant | bakery | 3.25 |

A line is worth `quantity × unit_price_usd − discount_usd`. The quantity and the discount sit on the line; the price
sits in `products`. The dollars need both tables. By the end you will have the total, the total for each product, and a
check against Excel.

A **join** pairs each row of one table with every row of the other table that has the same key value, and returns each
pair as one wider row. You write it in the `FROM` clause:

```sql
FROM order_items AS oi
INNER JOIN products AS p ON oi.product_id = p.product_id
```

- `AS oi` and `AS p` are **aliases**, short names for the tables. Write `oi.product_id`, the table, a dot and the
  column, so there is never doubt about which table a column comes from.
- `ON` names the key on each side: the foreign key of the many side against the primary key of the other (S18).
- `INNER` keeps only the rows that got a pair, and `JOIN` alone means the same. A row with no pair, in either table,
  does not appear in the result.

Before you run a join, **predict its row count** from the keys. If the key is unique in the table you join to, each row
pairs at most once, so the count cannot grow; it falls if some rows find no partner. If the key repeats there, a row
pairs once per match and the count can grow. In E8, `XLOOKUP` returned the item for the first match it found (Microsoft's
page says so); a join returns every match, and every match is a row.

| In Excel (E8) | In SQL |
|---|---|
| a `raw_products` sheet with codes in a column | the `products` table with its primary key |
| `=XLOOKUP(C2, codes, prices)` for one column | `INNER JOIN products AS p ON oi.product_id = p.product_id`, then any columns of `p` |
| fill down to the last line | nothing: the join covers every row |

## Worked example

Question: **what have we sold in dollars, and which products earn the most?** Run the notebook's setup cell, then one
cell per step. Each step gives the shape of the result to expect.

1. **Predict, then count the pairs.** Before you run it: every line has one `product_id`, and `product_id` is the
   primary key of `products`. How many rows will the join return?

   ```sql
   SELECT COUNT(*) AS joined_rows
   FROM order_items AS oi
   INNER JOIN products AS p ON oi.product_id = p.product_id;
   ```

   Expected: 1 row, 1 column. *Excel:* an XLOOKUP column filled down, with a price on every line. *Why:* each line meets
   exactly one product, so the answer is **3287**, the lines of `order_items` (S18). The grain is still one line. A
   different number would mean a line was lost or doubled.

2. **Look at the pairs.**

   ```sql
   SELECT oi.order_item_id, oi.order_id, p.product_name,
          oi.quantity, p.unit_price_usd, oi.discount_usd
   FROM order_items AS oi
   INNER JOIN products AS p ON oi.product_id = p.product_id
   ORDER BY oi.order_item_id
   LIMIT 5;
   ```

   Expected: 5 rows, 6 columns; the first row is line 5001, a Croissant at 3.25. *Why:* the columns come from both
   tables, named through the aliases. `ORDER BY` fixes the order, because a join promises none.

3. **Compute the line amount.**

   ```sql
   SELECT oi.order_item_id,
          p.product_name,
          oi.quantity * p.unit_price_usd - oi.discount_usd AS line_amount_usd
   FROM order_items AS oi
   INNER JOIN products AS p ON oi.product_id = p.product_id
   ORDER BY oi.order_item_id
   LIMIT 5;
   ```

   Expected: 5 rows, 3 columns; line 5003 reads 6.00, as in E8. *Excel:* `=D2*F2-E2`. *Why:* the dataset's rule is
   quantity times price, minus the discount on the line. The price needs the join; `oi.quantity` and `oi.discount_usd`
   do not.

4. **Add it up.**

   ```sql
   SELECT SUM(oi.quantity * p.unit_price_usd - oi.discount_usd) AS sales_usd
   FROM order_items AS oi
   INNER JOIN products AS p ON oi.product_id = p.product_id;
   ```

   Expected: 1 row, 1 column: `22754.25`. *Why:* this covers all 3,287 lines of all 1,800 orders. It includes the one
   canceled order, 1461 (a Mocha line of 5.00), and the extra-zero line of order 2075 (20 Turkey Sandwiches, 185.00,
   where 2 was meant). It is the total E8 reached with XLOOKUP and a `SUM`, and the status-bar Sum of *Summarize with a PivotTable* (E15), so the database agrees.

5. **Group by product.** Grain: one row per product sold. Before you run it: the menu has 16 products. How many rows?

   ```sql
   SELECT p.product_name,
          SUM(oi.quantity) AS units,
          SUM(oi.quantity * p.unit_price_usd - oi.discount_usd) AS sales_usd
   FROM order_items AS oi
   INNER JOIN products AS p ON oi.product_id = p.product_id
   GROUP BY p.product_name
   ORDER BY sales_usd DESC;
   ```

   Expected: 3 columns. *Why:* **15** rows. The Pumpkin Spice Latte is in `products` but on no line, so nothing pairs
   with it and the inner join drops it: the product S18 found unsold. The Latte leads with 2,927.00, and Green Tea is
   last with 783.75. That answers the owner's second question.

6. **Join in the other direction.** Before you run it: there are 1,800 orders. How many rows will `orders` joined to
   `order_items` return?

   ```sql
   SELECT COUNT(*) AS joined_rows
   FROM orders AS o
   INNER JOIN order_items AS oi ON o.order_id = oi.order_id;
   ```

   Expected: 1 row, 1 column. *Why:* **3287**. Here the key repeats on the `oi` side: an order pairs once with each of
   its one to three lines, so it appears one to three times, and the grain of the result is the line. A
   `COUNT(*)` on this join counts lines, not orders. The count grew from 1,800 to 3,287 because the join went from the
   one side to the many side.

7. **Verify.** Step 1's 3,287 equals the lines of `order_items` and step 6's count, so the join to `products` lost no

## Check yourself

Without looking back: what does an `INNER JOIN` return, and how do you predict its row count before you run it?

<details>
<summary>Answer</summary>

Only the rows that got a pair. Look at which side the key is unique on: if it is unique in the table you join to, the
count cannot grow, and it falls if some rows find no partner; if the key repeats there, the count can grow. Rows with
no pair, or with an empty key, are missing.

</details>
