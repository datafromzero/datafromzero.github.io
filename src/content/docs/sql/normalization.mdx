## The question

The owner of the cafes asks:

> Our analyst keeps one big table with a row for every product line sold. Someone typed "Harbor Point" on some of
> Harbor's rows but not all, and the Harbor report split in two. Why does the database keep five tables? And if we
> split the big one, do any of our numbers change?

In the big table, each store's name and city are written on every one of its lines:

| store_name | store_city | lines |
|---|---|---:|
| Old Town | Oakland | 1,337 |
| Campus | Berkeley | 1,305 |
| Harbor | Alameda | 645 |

## Learn by doing

Four small steps. Revenue counts completed orders only, all lines, including the extra-zero line of order 2075.

### 1. One wide table repeats its facts

A **normal form** is a rule about where a fact may live; there are three, and you meet them in order. The first (1NF)
asks for one row per thing and no repeating columns such as `product_1` and `product_2`: a fourth product would need a
new column. The wide table obeys it: one row per order line, whose key is the pair (`order_id`, `product_id`), 3,287 rows
and 3,287 different pairs.

**Try it** (build the wide table). It glues the five tables into one, one row per line, with the store, customer and
product facts attached. The `LEFT JOIN` keeps order 1335, which has no customer.

<RunSQL query={`CREATE OR REPLACE TABLE orders_wide AS
SELECT oi.order_item_id, oi.order_id, oi.product_id, oi.quantity, oi.discount_usd,
       o.ordered_at, o.status, o.payment_method,
       o.store_id, s.store_name, s.city AS store_city,
       o.customer_id, c.city AS customer_city, c.loyalty_tier,
       p.product_name, p.category, p.unit_price_usd
FROM order_items AS oi
JOIN orders AS o ON o.order_id = oi.order_id
JOIN stores AS s ON s.store_id = o.store_id
LEFT JOIN customers AS c ON c.customer_id = o.customer_id
JOIN products AS p ON p.product_id = oi.product_id;`} />

Expected: 1 row, 1 column: the 3,287 rows stored, in a table of 17 columns. Run it again to get a fresh copy.

**Try it** (spot the repeated facts). Count the lines of each store.

<RunSQL query={`SELECT store_id, store_name, store_city, COUNT(*) AS lines
FROM orders_wide
GROUP BY store_id, store_name, store_city
ORDER BY store_id;`} />

Expected: 3 rows, 4 columns, as in the table of the question. *Why:* the three counts add up to the whole table: every line
repeats its store's name and city.

### 2. Three ways a wide table fails

A badly shaped table fails in three ways, the **anomalies**. *Update:* a fact stored on many rows has to be changed on every
one of them. *Insert:* a fact cannot be recorded until a row for something else exists. *Delete:*
removing a row also removes a fact.

**Try it** (the update anomaly). The `UPDATE` below reaches only Harbor's lines before May 1. Before you run it: what will a
report of Harbor's lines grouped by name show? The block leaves the transaction open, so run the second block next. If a block says a transaction is already open or
aborted, run `ROLLBACK`, or press **Reset data**.

<RunSQL query={`BEGIN;
UPDATE orders_wide SET store_name = 'Harbor Point' WHERE store_id = 3 AND ordered_at < '2026-05-01';
SELECT store_name, COUNT(*) AS lines FROM orders_wide WHERE store_id = 3 GROUP BY store_name ORDER BY store_name;`} />

<RunSQL query={`ROLLBACK;
SELECT store_name, COUNT(*) AS lines FROM orders_wide WHERE store_id = 3 GROUP BY store_name ORDER BY store_name;`} />

Expected: 2 columns each time. *Why:* the `WHERE` reached 223 of Harbor's 645 lines and missed the rest, so Harbor has two names, 422 lines as
`Harbor` and 223 as `Harbor Point`, and a report grouped by name splits in two. After `ROLLBACK`, one name is left, on all
645 lines.

**Try it** (the insert and delete anomalies). Before you run it: the menu has 16 products and `customers` has 150 rows.
How many of each does the wide table know?

<RunSQL query={`SELECT COUNT(DISTINCT product_id) AS sold_products, COUNT(DISTINCT customer_id) AS ordering_customers FROM orders_wide;`} />

<RunSQL query={`SELECT COUNT(*) AS lines FROM orders_wide WHERE customer_id = 42;`} />

Expected: the first returns 1 row, 2 columns; the second 1 row, 1 column. *Why:* the wide table knows only products and
customers with a sale: the Pumpkin Spice Latte and five members who never ordered cannot be in it (insert anomaly).
Customer 42 has one line in the whole table, on the canceled order, so deleting that line would erase everything the table
knows about customer 42 (delete anomaly).

### 3. Split each fact out by its key

Move each group of facts into a table of its own, keyed by the column they depend on, and leave that column behind as a
foreign key. The second form (2NF) says no non-key column depends on only part of the key. Product facts depend on
`product_id` alone and order facts on `order_id` alone, so both leave the lines. A one-column key cannot break this rule.

**Try it** (the product facts). `DISTINCT` keeps each product once, and the primary key (S31) would refuse a product with two
different names.

<RunSQL query={`CREATE TABLE n_product (
  product_id INTEGER PRIMARY KEY,
  product_name VARCHAR NOT NULL,
  category VARCHAR NOT NULL,
  unit_price_usd DECIMAL(6, 2) NOT NULL
);
INSERT INTO n_product
SELECT DISTINCT product_id, product_name, category, unit_price_usd FROM orders_wide;`} />

Expected: 1 row, 1 column: the 15 products stored.

The third form (3NF) says no non-key column depends on another non-key column. Store name and city depend on `store_id`,
not on the order, so they leave the orders, as do customer city and tier.

**Try it** (the store facts).

<RunSQL query={`CREATE TABLE n_store (store_id INTEGER PRIMARY KEY, store_name VARCHAR NOT NULL, store_city VARCHAR NOT NULL);
INSERT INTO n_store SELECT DISTINCT store_id, store_name, store_city FROM orders_wide;`} />

Expected: 1 row, 1 column. Now the same recipe for the customer, order and line tables, each with its primary key, and
`n_order` and `n_line` with foreign keys. `n_line` keeps `order_item_id` as its key. Run it, and read the counts. `n_customer`
needs `WHERE customer_id IS NOT NULL`: without it, the walk-in's empty row hits the `NOT NULL` rule and the insert fails.

<RunSQL query={`CREATE TABLE n_customer (
  customer_id INTEGER PRIMARY KEY,
  customer_city VARCHAR NOT NULL,
  loyalty_tier VARCHAR NOT NULL
);
INSERT INTO n_customer
SELECT DISTINCT customer_id, customer_city, loyalty_tier FROM orders_wide WHERE customer_id IS NOT NULL;
CREATE TABLE n_order (
  order_id INTEGER PRIMARY KEY,
  ordered_at TIMESTAMP NOT NULL,
  status VARCHAR NOT NULL,
  payment_method VARCHAR NOT NULL,

### 4. Prove the answers did not change

Read the five tables together again with a join on the keys, and compare with the wide table.

**Try it.** `EXCEPT` lists rows in one query and not the other. Before you run the checks: what should each return?

<RunSQL query={`CREATE OR REPLACE VIEW orders_rebuilt AS
SELECT l.order_item_id, l.order_id, l.product_id, l.quantity, l.discount_usd,
       o.ordered_at, o.status, o.payment_method,
       o.store_id, s.store_name, s.store_city,
       o.customer_id, c.customer_city, c.loyalty_tier,
       p.product_name, p.category, p.unit_price_usd
FROM n_line AS l
JOIN n_order AS o ON o.order_id = l.order_id
JOIN n_store AS s ON s.store_id = o.store_id
LEFT JOIN n_customer AS c ON c.customer_id = o.customer_id
JOIN n_product AS p ON p.product_id = l.product_id;`} />

<RunSQL query={`SELECT COUNT(*) AS only_in_rebuilt FROM (SELECT * FROM orders_rebuilt EXCEPT SELECT * FROM orders_wide);`} />

<RunSQL query={`SELECT COUNT(*) AS only_in_wide FROM (SELECT * FROM orders_wide EXCEPT SELECT * FROM orders_rebuilt);`} />

Then the revenue, from the wide table and from the rebuilt one.

<RunSQL query={`SELECT store_name, SUM(quantity * unit_price_usd - discount_usd) AS revenue
FROM orders_wide WHERE status = 'completed' GROUP BY store_name ORDER BY store_name;`} />

<RunSQL query={`SELECT store_name, SUM(quantity * unit_price_usd - discount_usd) AS revenue
FROM orders_rebuilt WHERE status = 'completed' GROUP BY store_name ORDER BY store_name;`} />

Expected: the view shows no rows; each `EXCEPT` check returns 1 row, 1 column; each revenue query 3 rows, 2 columns. *Why:*
two 0s mean the same 3,287 rows both ways. Both revenue tables read Campus \$8,998.75, Harbor \$4,606.25 and Old Town
\$9,144.25: \$22,749.25 for completed orders, the same total as from the five original tables. Splitting lost nothing.

The rebuilt view is a wide table again, on purpose. **Denormalizing** stores a fact many times deliberately. Microsoft Learn
says normalization adds tables that some find cumbersome, and the Azure Architecture Center notes the join cost for
read-heavy views. Analysts build a wide view or star schema (S29) over normalized tables.

<Aside type="tip" title="Remember">

- A normal form says where a fact may live: 1NF one row per thing; 2NF no column depends on part of the key; 3NF no column
  depends on another non-key column.
- A wide table breeds update, insert and delete anomalies.
- Split by key, read back with a join, and prove the answers did not move.

**Common trap: "normalized means no value repeats."** Keys repeat: Old Town's `store_id` of 1 sits on all 729 of its orders
in `n_order`. What is stored once is each fact about the store, its name and city.

</Aside>
