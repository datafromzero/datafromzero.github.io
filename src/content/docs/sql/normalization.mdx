## How it works

**Normalization** is organizing data into tables so that each fact is stored once, in a table whose key identifies it.
Other tables point to it by key. Microsoft Learn sets three rules for it, called **normal forms**. In the first picture,
one row of the wide table is one order line, and its key is the pair (`order_id`, `product_id`): 3,287 rows, 3,287
different pairs. To normalize it:

1. Find the facts repeated from row to row: the shaded cells of the first picture.
2. Move each group of facts into a table of its own, keyed by the column they depend on, and leave that column behind as
   a foreign key.
3. Read them together again with a join on the keys.

The rules:

- **First (1NF):** one row per thing, no repeating columns such as `product_1` and `product_2`: a fourth product
  would need a new column.
- **Second (2NF):** no non-key column depends on only part of the key. Product facts depend on `product_id` alone and
  order facts on `order_id` alone, so both leave the lines. A one-column key cannot break this rule.
- **Third (3NF):** no non-key column depends on another non-key column. Store name and city depend on `store_id`, not
  on the order, so they leave the orders; so do customer city and tier, which depend on `customer_id`.
- A badly shaped table fails in three ways, the **anomalies**. *Update:* a fact stored on many rows can be changed on
  some and not others, leaving two versions. *Insert:* a fact cannot be recorded until a row for something else exists,
  as a fourth cafe cannot until it has an order. *Delete:* removing a row also removes a fact, as removing the only line
  that mentions a product erases the product.
- **Denormalizing** stores a fact many times on purpose. Microsoft Learn says normalization adds tables that some find
  cumbersome, and the Azure Architecture Center notes the join cost for read-heavy views. Analysts build a wide table as
  a view or star schema (S29) over tables that stay normalized.

**Excel.** In E8 (*Bring in a value by key with XLOOKUP*) a price sits on one sheet and each line holds only the code.
Normalizing does that for every repeated fact.

**A common misconception: "normalized means no value repeats."** Keys repeat: Old Town's `store_id` of 1 sits on all
729 of its orders in `n_order`. What is stored once is each fact about the store, its name and city.

## Worked example

Question: **what goes wrong in one wide table, and does splitting it change any answer?** Run the notebook's setup
cell, then one cell per step. Each step gives the shape of the result to expect. Revenue counts completed orders only,
all lines, including the extra-zero line of order 2075.

1. **Build the wide table.**

   ```sql
   CREATE TABLE orders_wide AS
   SELECT oi.order_item_id, oi.order_id, oi.product_id, oi.quantity, oi.discount_usd,
          o.ordered_at, o.status, o.payment_method,
          o.store_id, s.store_name, s.city AS store_city,
          o.customer_id, c.city AS customer_city, c.loyalty_tier,
          p.product_name, p.category, p.unit_price_usd
   FROM order_items AS oi
   JOIN orders AS o ON o.order_id = oi.order_id
   JOIN stores AS s ON s.store_id = o.store_id
   LEFT JOIN customers AS c ON c.customer_id = o.customer_id
   JOIN products AS p ON p.product_id = oi.product_id;
   ```

   Expected: a `Count` table, 1 row, 1 column. The new table has 17 columns. *Why:* one row per line, with the store,
   customer and product facts glued on. The `LEFT JOIN` keeps order 1335, which has no customer.

2. **Spot the repeated facts.**

   ```sql
   SELECT store_id, store_name, store_city, COUNT(*) AS lines
   FROM orders_wide
   GROUP BY store_id, store_name, store_city
   ORDER BY store_id;
   ```

   Expected: 3 rows, 4 columns, as in the table of the question. *Why:* the three lines counts add up to the whole
   table: every line repeats its store's name and city.

3. **Update anomaly, then undo it.** Four cells: `BEGIN`, the `UPDATE`, the `SELECT`, `ROLLBACK`.

   ```sql
   UPDATE orders_wide SET store_name = 'Harbor Point' WHERE store_id = 3 AND ordered_at < '2026-05-01';
   SELECT store_name, COUNT(*) AS lines FROM orders_wide WHERE store_id = 3 GROUP BY store_name ORDER BY store_name;
   ```

   Expected: the `UPDATE` reports a `Count`; the `SELECT` returns 2 rows, 2 columns. *Why:* the `WHERE` reached 223 of
   Harbor's 645 lines, so Harbor now has two names, 422 lines as `Harbor` and 223 as `Harbor Point`. A report grouped
   by name splits in two. After `ROLLBACK`, the name is `Harbor` everywhere again.

4. **Insert and delete anomalies.** Two cells.

   ```sql
   SELECT COUNT(DISTINCT product_id) AS sold_products, COUNT(DISTINCT customer_id) AS ordering_customers FROM orders_wide;
   SELECT COUNT(*) AS lines FROM orders_wide WHERE customer_id = 42;
   ```

   Expected: the first returns 1 row, 2 columns; the second 1 row, 1 column. *Why:* the menu has 16 products and
   `customers` has 150 rows, but the wide table knows only products and customers with a sale: the Pumpkin Spice Latte
   and five members who never ordered cannot be in it (insert anomaly). Customer 42 has one line in the whole table, on
   the canceled order, so deleting that line would erase everything the table knows about customer 42 (delete anomaly).

5. **Split out the product facts (2NF).**

   ```sql
   CREATE TABLE n_product (
     product_id INTEGER PRIMARY KEY,
     product_name VARCHAR NOT NULL,
     category VARCHAR NOT NULL,
     unit_price_usd DECIMAL(6, 2) NOT NULL
   );
   INSERT INTO n_product
   SELECT DISTINCT product_id, product_name, category, unit_price_usd FROM orders_wide;
   ```

   Expected: a `Count` table with 1 row. *Why:* `DISTINCT` keeps each product once, and the primary key
   (from S31) would refuse a product with two different names. The new table has 15 rows, not 16, for the reason of step 4.

6. **Split out the store facts (3NF), then the rest.**

   ```sql
   CREATE TABLE n_store (store_id INTEGER PRIMARY KEY, store_name VARCHAR NOT NULL, store_city VARCHAR NOT NULL);
   INSERT INTO n_store SELECT DISTINCT store_id, store_name, store_city FROM orders_wide;
   ```

   Expected: a `Count` table, 1 row. The next notebook cell, done for you, builds `n_customer`, `n_order` and `n_line`
   with the same recipe, each with its primary key, and `n_order` and `n_line` with foreign keys as in the picture; `n_line`
   keeps `order_item_id` as its key. *Why:* `n_customer` needs `WHERE customer_id IS NOT NULL`: without it, the walk-in's empty row hits the `NOT NULL`
   rule and the insert fails.

7. **Prove the answers did not change.** Rebuild the wide table as a view over the five new tables, then compare.

   ```sql
   CREATE VIEW orders_rebuilt AS
   SELECT l.order_item_id, l.order_id, l.product_id, l.quantity, l.discount_usd,
          o.ordered_at, o.status, o.payment_method,
          o.store_id, s.store_name, s.store_city,
          o.customer_id, c.customer_city, c.loyalty_tier,
          p.product_name, p.category, p.unit_price_usd
   FROM n_line AS l
   JOIN n_order AS o ON o.order_id = l.order_id
   JOIN n_store AS s ON s.store_id = o.store_id
   LEFT JOIN n_customer AS c ON c.customer_id = o.customer_id
   JOIN n_product AS p ON p.product_id = l.product_id;

   SELECT COUNT(*) AS only_in_rebuilt FROM (SELECT * FROM orders_rebuilt EXCEPT SELECT * FROM orders_wide);
   SELECT COUNT(*) AS only_in_wide FROM (SELECT * FROM orders_wide EXCEPT SELECT * FROM orders_rebuilt);
   SELECT store_name, SUM(quantity * unit_price_usd - discount_usd) AS revenue
   FROM orders_wide WHERE status = 'completed' GROUP BY store_name ORDER BY store_name;
   ```

   Expected: the view returns a `Count` table; each `EXCEPT` check returns 1 row, 1 column; the revenue query returns
   3 rows, 2 columns. Run the revenue query again with `orders_rebuilt` in place of `orders_wide`. *Why:* `EXCEPT`

   Campus \$8,998.75, Harbor \$4,606.25 and Old Town \$9,144.25: \$22,749.25 for completed orders, the same total as from
