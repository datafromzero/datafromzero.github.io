## The big idea

An **aggregate function** folds many rows into one value: it reads a column down all the rows it is given and hands
back a single number.

{/* CONCEPT: concept-aggregate */}

## Learn by doing

Five small steps. Press Run on each query as you meet it.

### 1. Many rows in, one row out

An aggregate reads one column, or `*` for whole rows, and returns a single result. A query that selects nothing but
aggregates, and has no `GROUP BY`, returns exactly one row, however many rows it read. Each aggregate is its own pass
over the rows, so one query can hold several.

**Try it**: count the lines.

<RunSQL query={`SELECT COUNT(*) AS order_lines FROM order_items;`} />

Expected: 1 row, 1 column: `3287`. *Excel:* the status-bar Count (E15), or of a full column (E1). *Why:* one row of
`order_items` is one line, so the number of rows is the number of lines.

**Try it**: five aggregates in one query.

<RunSQL query={`SELECT COUNT(*) AS lines,
       SUM(quantity) AS units,
       ROUND(AVG(quantity), 2) AS avg_units,
       MIN(quantity) AS min_units,
       MAX(quantity) AS max_units
FROM order_items;`} />

Expected: 1 row, 5 columns: 3287 lines, 5162 units, an average of 1.57, a smallest line of 1 and a largest of 20.
*Excel:* `SUM`, `AVERAGE`, `MIN` and `MAX` of the quantity column.

*Why:* each function collapses all 3,287 rows into one value, so the result has one row however many columns you ask
for. `ROUND(value, 2)` keeps two decimals. These figures include every line: the one on the canceled order 1461 and the
extra-zero line (order 2075). Read the `MAX`: most lines have 1 to 3 units, so 20 stands out. `MIN` and `MAX` are a quick
check for odd values.

### 2. Three ways to count

`COUNT(*)` counts rows. `COUNT(col)` counts the rows where `col` is not `NULL` (S4). `COUNT(DISTINCT col)` counts each
different value once. `DISTINCT` is not special to `COUNT`: DuckDB says that with it, an aggregate considers only the
distinct values.

Here are the three counts on eight real orders. Order 1335 has no customer, and order 1334 repeats customer 9.

**Try it**: now on the whole table.

<RunSQL query={`SELECT COUNT(*) AS orders,
       COUNT(customer_id) AS with_customer,
       COUNT(DISTINCT customer_id) AS customers
FROM orders;`} />

Expected: 1 row, 3 columns: 1800, 1799, 145. *Excel:* `COUNTA` counts the cells that are not empty (E4 sets `COUNT` and
`COUNTA` side by side); for the different values, list them with `UNIQUE` (E19), then count the list.

*Why:* 145 different customers placed those 1,799 orders with a customer. That answers the last question.

<details>
<summary>Explain it in your own words: why are the three counts in unit 2 different?</summary>

The walk-in order is a row, so the star counts it, but it has no customer, so the other two skip it. The `DISTINCT`
version also merges repeats: 145 customers placed 1,799 orders, so most of them ordered many times.

</details>

### 3. What `NULL` does to an aggregate

An aggregate has its own rule for `NULL`, and for an input with no rows. Test the first on a table you build on the
spot: a `VALUES` list makes three rows of one column named `x`, one of them `NULL`. It sits in the `FROM` as a table
typed inline; *Subqueries and EXISTS* (S23) explains the form.

**Try it**. Before you run it: will `average` be 5 or 3.33?

<RunSQL query={`SELECT COUNT(*) AS n,
       COUNT(x) AS non_null,
       SUM(x) AS total,
       AVG(x) AS average
FROM (VALUES (4), (6), (NULL)) AS t(x);`} />

Expected: 1 row, 4 columns.

*Why:* `SUM` and `AVG` skip the `NULL`. The total is 4 + 6 = 10, and `AVG` divides by the two values it saw, not by the
three rows. A zero would have pulled the average down to 3.33; you know from S4 that `NULL` is not zero.

### 4. When no rows are left

`WHERE` throws rows away before any aggregate runs, so each aggregate sees only the rows that are left. What does an
aggregate return when none are left?

**Try it**. Before you run it: what will each column show?

<RunSQL query={`SELECT COUNT(*) AS lines, SUM(quantity) AS units
FROM order_items
WHERE quantity > 20;`} />

Expected: 1 row, 2 columns.

*Why:* no line has more than 20 units, so no rows are left. The count of nothing is 0, but the `SUM` of nothing is
`NULL`, not 0: "no data" and "zero" are different answers. The DuckDB documentation says every general aggregate except
`COUNT` returns `NULL` on empty input.

### 5. Check against Excel and a second route

**Try it**:

<RunSQL query={`SELECT SUM(quantity) AS units FROM order_items WHERE order_id <> 1461;`} />

<RunSQL query={`SELECT COUNT(*) AS customers_in_table FROM customers;`} />

Expected: 1 row, 1 column each: `5161` and `150`. *Why:* the product sales sheet of *Relative and absolute references*
(E3) counted the units of completed orders, and its total was 5,161. The SQL total of all lines, 5,162, minus the one
unit on the canceled order 1461, gives the same number. The 3,287 lines of unit 1 are the Count of E15. For the 145
customers: the `customers` table has 150, and five of them signed up but never ordered. A total in dollars needs the
price from the `products` table, so it waits for *INNER JOIN: pairing rows on a key* (S19).

<Aside type="tip" title="Remember">

- An aggregate folds many rows into one value; with no `GROUP BY`, one row comes back.
- `COUNT(*)` counts rows, `COUNT(col)` skips `NULL`, and `COUNT(DISTINCT col)` counts each value once.
- `SUM` and `AVG` skip `NULL`, and `AVG` divides by the values it saw.
- Over no rows, `COUNT` returns 0 and `SUM` returns `NULL`.

**Common trap: "SQL's `COUNT(col)` is Excel's `COUNT`."** Excel's `COUNT` counts only the cells that hold numbers
(dates are numbers too). `COUNT(col)` in SQL counts every row with a value in `col`, text included:
`COUNT(payment_method)` on the `orders` table returns 1,800, and `payment_method` is text. SQL's `COUNT(col)` is the
closer cousin of `COUNTA`.

</Aside>

<Exercise id="sql-aggregate-functions-3">

**Spot the flaw.** A colleague wants the average discount on a discounted line. They run this query and report "about 3
cents":

<RunSQL query={`SELECT AVG(discount_usd) AS avg_discount FROM order_items;`} />

Expected: 1 row, 1 column, a number near 0.0256. What did the average include that it should not have? Then fix the
query.

<Solution>

`discount_usd` holds `0.00` on a line with no discount. That is a zero, not a `NULL`, so `AVG` counts it: the query
averages all 3,287 lines, and the 84.00 of total discount is spread over all of them (84.00 / 3,287 = 0.0256). Only
168 lines carry a discount. Keep those lines with `WHERE`:

```sql
SELECT AVG(discount_usd) AS avg_discount
FROM order_items
WHERE discount_usd > 0;
```

Expected: 1 row, 1 column: `0.5`. Every discounted line is 0.50 off. An aggregate skips `NULL`, never zero, so you
choose the rows it sees with `WHERE`.

</Solution>

</Exercise>
