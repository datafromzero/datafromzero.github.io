An **aggregate function** turns many rows into one value. A query that has aggregates and nothing else returns exactly
one row, however many rows it read. All of them skip `NULL`, except `COUNT(*)`, which counts rows.

| SQL | Reads as | In Excel |
|---|---|---|
| `COUNT(*)` | how many rows | the status-bar Count of a full column (E1) |
| `COUNT(col)` | how many rows have a value in `col` (not `NULL`) | `COUNTA`, which counts cells that are not empty |
| `COUNT(DISTINCT col)` | how many different values | list them with `UNIQUE` (E19), then count the list |
| `SUM(col)` | add the values | `SUM` |
| `AVG(col)` | the average of the values | `AVERAGE` |
| `MIN(col)`, `MAX(col)` | the smallest and the largest | `MIN`, `MAX` |

The picture shows the three counts on eight real orders. On the whole table the same three queries return 1,800, 1,799
and 145; you run them in step 3.

## Worked example

Question: **how many lines and units have we sold, how big is a typical line, and how many customers have ordered?**
Run the notebook's setup cell, then one cell per step. Each step shows the shape of the result to expect.

1. **Count the lines.**

   ```sql
   SELECT COUNT(*) AS order_lines FROM order_items;
   ```

   Expected: 1 row, 1 column: `3287`. *Excel:* the status-bar Count (E15). *Why:* one row of `order_items` is one
   line, so the number of rows is the number of lines.

2. **Five aggregates in one query.**

   ```sql
   SELECT COUNT(*) AS lines,
          SUM(quantity) AS units,
          ROUND(AVG(quantity), 2) AS avg_units,
          MIN(quantity) AS min_units,
          MAX(quantity) AS max_units
   FROM order_items;
   ```

   Expected: 1 row, 5 columns: 3287 lines, 5162 units, an average of 1.57, a smallest line of 1 and a largest of 20.
   *Why:* each function collapses all 3,287 rows into one value, so the result has one row however many columns you
   ask for. `ROUND(value, 2)` keeps two decimals. These figures include every line: the one on the canceled order 1461
   and the extra-zero line (order 2075). Read the `MAX`: most lines have 1 to 3 units, so 20 stands out. `MIN` and
   `MAX` are a quick check for odd values.

3. **Three counts on one column.**

   ```sql
   SELECT COUNT(*) AS orders,
          COUNT(customer_id) AS with_customer,
          COUNT(DISTINCT customer_id) AS customers
   FROM orders;
   ```

   Expected: 1 row, 3 columns: 1800, 1799, 145. *Why:* `COUNT(*)` counts rows: 1,800 orders. `COUNT(customer_id)` skips
   the `NULL` of the walk-in order 1335 and returns 1,799. `COUNT(DISTINCT customer_id)` counts each customer once:
   145 different customers placed those 1,799 orders. That answers the last question.

4. **Predict what `NULL` does.** Test it on a table you build on the spot. The `VALUES` list makes three rows of one
   column named `x`, one of them `NULL`:

   ```sql
   SELECT COUNT(*) AS n,
          COUNT(x) AS non_null,
          SUM(x) AS total,
          AVG(x) AS average
   FROM (VALUES (4), (6), (NULL)) AS t(x);
   ```

   Before you run it: will `average` be 5 or 3.33? Expected: 1 row, 4 columns. *Why:* `SUM` and `AVG` skip the `NULL`.
   The total is 4 + 6 = 10, and `AVG` divides by the two values it saw, not by the three rows. A zero would have pulled
   the average down to 3.33; you know from S4 that `NULL` is not zero.

5. **An empty group.**

   ```sql
   SELECT COUNT(*) AS lines, SUM(quantity) AS units
   FROM order_items
   WHERE quantity > 20;
   ```

   Expected: 1 row, 2 columns: `0` and `NULL`. *Why:* no line has more than 20 units, so no rows are left. The count
   of nothing is 0, but the `SUM` of nothing is `NULL`, not 0: "no data" and "zero" are different answers. The
   DuckDB documentation says every general aggregate except `COUNT` returns `NULL` on empty input.

6. **Verify against Excel and a second route.**

   ```sql
   SELECT SUM(quantity) AS units FROM order_items WHERE order_id <> 1461;
   SELECT COUNT(*) AS customers_in_table FROM customers;
   ```

   Expected: 1 row, 1 column each: `5161` and `150`. *Why:* the product sales sheet of *Relative and absolute
   references* (E3) counted the units of completed orders, and its total was 5,161. The SQL total of all lines, 5,162,
   minus the one unit on the canceled order 1461, gives the same number. The 3,287 lines of step 1 are the Count of
   E15. For the 145 customers: the `customers` table has 150, and five of them signed up but never ordered. A total in
   dollars needs the price from the `products` table, so it waits for *INNER JOIN: pairing rows on a key* (S19).

<details>
<summary>Explain it in your own words: why are the three counts in step 3 different?</summary>

`COUNT(*)` counts rows, so the walk-in order counts. `COUNT(customer_id)` counts only rows that have a customer, so it
skips the `NULL`. `COUNT(DISTINCT customer_id)` also merges repeats: 145 customers placed 1,799 orders, so most of them
ordered many times.

</details>

## Check yourself

1. Without looking back: which of `COUNT(*)`, `COUNT(col)` and `COUNT(DISTINCT col)` counts a row whose `col` is `NULL`,
   and what does `SUM` return when no rows are left?

   <details>
   <summary>Answer</summary>

   Only `COUNT(*)` counts that row. `SUM` over no rows returns `NULL`, while `COUNT(*)` over no rows returns 0.

   </details>

<Exercise id="sql-aggregate-functions-3">

**Spot the flaw.** A colleague wants the average discount on a discounted line. They run this query and report "about 3
cents":

```sql
SELECT AVG(discount_usd) AS avg_discount FROM order_items;
```

Expected: 1 row, 1 column, a number near 0.0256. What did the average include that it should not have? Then fix the
query.

<Solution>

`discount_usd` holds `0.00` on a line with no discount. That is a zero, not a `NULL`, so `AVG` counts it: the query
averages all 3,287 lines, and the 84.00 of total discount is spread over all of them (84.00 / 3,287 = 0.0256). Only
168 lines carry a discount. Keep those lines with `WHERE`:

```sql
SELECT AVG(discount_usd) AS avg_discount
FROM order_items
WHERE discount_usd > 0;
```

Expected: 1 row, 1 column: `0.5`. Every discounted line is 0.50 off. An aggregate skips `NULL`, never zero, so you
choose the rows it sees with `WHERE`.

</Solution>

</Exercise>
