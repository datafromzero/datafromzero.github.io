## Warm-up

Answer from memory before you open anything. Then click to check.

1. In *GROUP BY and HAVING* (S8), what is the difference between `WHERE` and `HAVING`?

   <details>
   <summary>Answer</summary>

   `WHERE` keeps or drops rows, before the grouping. `HAVING` keeps or drops groups, after it.

   </details>

2. In *SELECT, ORDER BY and LIMIT* (S2), write a query that returns the three dearest products, with their name and
   price. Break price ties by name.

   <details>
   <summary>Answer</summary>

   ```sql
   SELECT product_name, unit_price_usd
   FROM products
   ORDER BY unit_price_usd DESC, product_name
   LIMIT 3;
   ```

   It returns Turkey Sandwich, Avocado Toast and Pumpkin Spice Latte.

   </details>

3. In S2, what does `AS` do in `COUNT(*) AS items`?

   <details>
   <summary>Answer</summary>

   It gives the result column a name, an alias. The table is not changed.

   </details>

## The question

The owner is writing a menu board for the cafes:

> Among the items under \$5, which two categories have the most items, counting only categories with at least three?

The top of the `products` table, which has 16 rows:

| product_id | product_name | category | unit_price_usd |
|---:|---|---|---:|
| 1 | Espresso | coffee | 3.00 |
| 2 | Americano | coffee | 3.50 |
| 3 | Latte | coffee | 4.50 |
| 4 | Cappuccino | coffee | 4.50 |

One query answers it, but only if each clause does its own job. By the end you will know the order the clauses run in,
and you will have read the answer: **coffee with 5 items and bakery with 3**.

## How it works

You write `SELECT` first, but the engine does not read a query from the top. DuckDB's documentation describes a fixed
**logical order**: the order in which each clause behaves as if it ran. Each clause works on the rows the previous one
left and hands its own result to the next. The picture above follows the same order, one clause at a time.

1. `FROM` takes the table: 16 rows with all four columns.
2. `WHERE` keeps or drops single rows, judged by the table's own columns. Here 12 rows are left.
3. `GROUP BY` sorts the remaining rows into groups, one for each value of the key.
4. `HAVING` keeps or drops whole groups, judged by what a group holds, such as its row count.
5. `SELECT` builds the output columns from the surviving rows and names them.
6. `ORDER BY` sorts the output rows, and `LIMIT` cuts the sorted list.

The rules:

- `WHERE` chooses rows and `SELECT` chooses columns. They never swap jobs.
- A clause cannot use what a later clause creates. At step 2 no group exists yet, so a count is out of reach for
  `WHERE`; `HAVING` runs after the grouping and is made for it.
- A name you give with `AS` is created at step 5, so the clauses before it have no such name yet. DuckDB goes further
  and accepts the name early for a plain expression. Step 7 of the worked example shows where that stops.
- `ORDER BY` and `LIMIT` are **output modifiers**: they work on the finished result, at the very end.

**Excel.** A sheet makes the same moves by hand: a filter shows only the rows that meet your criteria and hides the
rest, and a sort rearranges the rows (E5, *Tables, sorting and filtering*).

**A common misconception: "`LIMIT` takes the first rows of the table, and then `ORDER BY` sorts them."** The order is
the other way round: the sort runs first and `LIMIT` cuts the sorted list. `ORDER BY product_name LIMIT 2` returns
Americano and Avocado Toast, although the first two rows of `products` are Espresso and Americano.

## Worked example

Question: **among the items under \$5, which two categories have the most items, counting only those with at least
three?** Run the notebook's setup cell, then one cell per step. We build the query in running order.

1. **FROM: start with the whole table.**

   ```sql
   SELECT * FROM products;
   ```

   Expected: 16 rows, 4 columns. *Why:* every query starts with the rows of its table.

2. **WHERE chooses rows.**

   ```sql
   SELECT * FROM products WHERE unit_price_usd < 5;
   ```

   Expected: 12 rows, 4 columns. *Why:* rows are dropped, columns are untouched.

3. **SELECT chooses columns.**

   ```sql
   SELECT category FROM products WHERE unit_price_usd < 5;
   ```

   Expected: 12 rows, 1 column. *Why:* the same 12 rows, one column.

4. **GROUP BY turns rows into groups.**

   ```sql
   SELECT category, COUNT(*) AS items
   FROM products
   WHERE unit_price_usd < 5
   GROUP BY category;
   ```

   Expected: 4 rows, 2 columns. *Why:* `food` counts 1 item, not 3, because `WHERE` ran first and dropped the dear ones.

5. **An aggregate cannot go in WHERE.** The natural first try is to filter the count in `WHERE`:

   ```sql
   SELECT category, COUNT(*) AS items
   FROM products
   WHERE unit_price_usd < 5 AND COUNT(*) >= 3
   GROUP BY category;
   ```

   Expected: an error that starts `Binder Error: WHERE clause cannot contain aggregates!`. *Why:* when `WHERE` runs there are no
   groups yet, so there is no count to test. `HAVING` runs after the grouping:

   ```sql
   SELECT category, COUNT(*) AS items
   FROM products
   WHERE unit_price_usd < 5
   GROUP BY category
   HAVING COUNT(*) >= 3;
   ```

   Expected: 3 rows, 2 columns; `food` drops out.

6. **ORDER BY and LIMIT run last.**

   ```sql
   SELECT category, COUNT(*) AS items
   FROM products
   WHERE unit_price_usd < 5
   GROUP BY category
   HAVING COUNT(*) >= 3
   ORDER BY items DESC, category
   LIMIT 2;
   ```

   Expected: 2 rows, 2 columns: coffee 5, bakery 3. *Why:* `ORDER BY items` can use the alias because `SELECT` has already
   run. `category` breaks the tie between bakery and tea (S2).

7. **What about an alias in WHERE?**

   ```sql
   SELECT product_name, unit_price_usd * 100 AS cents
   FROM products
   WHERE cents < 400;
   ```

   Expected: 7 rows, 2 columns. DuckDB accepts this: its documentation lists "Column aliases in WHERE, GROUP BY, and
   HAVING" among its friendly features. PostgreSQL does not accept it. Its documentation says:
   "An output column's name can be used to refer to the column's value in ORDER BY and GROUP BY clauses, but not in the
   WHERE or HAVING clauses; there you must write out the expression instead." The portable habit is to write it out:
   `WHERE unit_price_usd * 100 < 400` returns the same 7 rows. Even DuckDB stops for an alias of an aggregate:
   `WHERE items >= 3` gives the error of step 5.

8. **Verify.** Follow the counts in the picture: 16 rows, 12 rows, 4 groups, 3 groups, then 2 rows; each notebook step gave
   them. A second method: coffee has 7 products, and 2 of them (Mocha at \$5.00 and Pumpkin Spice Latte at \$5.50) cost
   \$5 or more, which leaves the 5 in the result. Answer: **coffee 5 and bakery 3**.

<details>
<summary>Explain it in your own words: why can `WHERE unit_price_usd < 5` use a column that the output does not show?</summary>

`WHERE` runs on the full table, before `SELECT` chooses the output columns. Every column of the table is still there.

</details>

**Spot the flaw.** A colleague wants the products over \$4 shown in cents. The query runs without an error but returns no
rows:

```sql
SELECT product_name, unit_price_usd * 100 AS unit_price_usd
FROM products
WHERE unit_price_usd > 400;
```

Expected: 0 rows, 2 columns. Nine products cost more than \$4. Find the flaw and fix the query.

<Solution>

The alias has the same name as a table column, and DuckDB uses the column. `WHERE` runs before `SELECT`, so it reads the
table's column, in dollars (4.50), not the alias in cents (450.00), and `> 400` matches nothing. Give the alias another name, or write the
expression out:

```sql
SELECT product_name, unit_price_usd * 100 AS cents
FROM products
WHERE unit_price_usd * 100 > 400;
```

Expected: 9 rows, 2 columns.

</Solution>
