This lesson teaches no new function. You write `SELECT` first, but the engine reads a query in a different order, and
that order explains most of the errors you meet. Each query runs in the editor on this page, with the five tables of
**cafe-sales**, the invented three-cafe chain we use from Excel to Python.

## The question

The owner is writing a menu board for the cafes:

> Among the items under \$5, which two categories have the most items, counting only categories with at least three?

The top of the `products` table, which has 16 rows:

| product_id | product_name | category | unit_price_usd |
|---:|---|---|---:|
| 1 | Espresso | coffee | 3.00 |
| 2 | Americano | coffee | 3.50 |
| 3 | Latte | coffee | 4.50 |
| 4 | Cappuccino | coffee | 4.50 |

One query answers it, if each clause does its own job. You will build it one clause at a time.

## Warm-up

From memory first, then click to check.

1. In *GROUP BY and HAVING* (S8), what is the difference between `WHERE` and `HAVING`?

   <details>
   <summary>Answer</summary>

   `WHERE` keeps or drops rows, before the grouping. `HAVING` keeps or drops groups, after it.

   </details>

2. In *SELECT, ORDER BY and LIMIT* (S2), write a query that returns the three dearest products, with their name and
   price. Break price ties by name.

   <details>
   <summary>Answer</summary>

   ```sql
   SELECT product_name, unit_price_usd
   FROM products
   ORDER BY unit_price_usd DESC, product_name
   LIMIT 3;
   ```

   It returns Turkey Sandwich, Avocado Toast and Pumpkin Spice Latte.

   </details>

## The big idea

A query runs its clauses in a fixed order, not the order you write them, and each clause works on the rows the one
before it left.

## Learn by doing

Five small steps. Each gives you one idea, then you try it in the editor.

### 1. Rows first, then columns

`FROM` goes first and takes the whole table. Then `WHERE` keeps or drops single rows, judged by the table's own
columns, and `SELECT` chooses the columns to show. `WHERE` chooses rows, `SELECT` chooses columns, and they never swap
jobs.

*Excel:* a filter shows only the rows that meet your criteria and hides the rest (E5, *Tables, sorting and filtering*).

**Try it:** the whole table.

<RunSQL query={`SELECT * FROM products;`} />

Expected: 16 rows, 4 columns.

**Try it:** keep the items under \$5.

<RunSQL query={`SELECT * FROM products WHERE unit_price_usd < 5;`} />

Expected: 12 rows, 4 columns. Rows went away, the columns stayed.

**Try it:** show one column.

<RunSQL query={`SELECT category FROM products WHERE unit_price_usd < 5;`} />

Expected: 12 rows, 1 column: the same rows, fewer columns. The picture shows the two choices meeting.

### 2. Groups, then a filter for them

`GROUP BY` sorts the remaining rows into groups. A clause cannot use what a later clause creates (DuckDB bends this for plain aliases, unit 4). `WHERE` runs before any
group exists, so it has no count to test; `HAVING` runs after the grouping and keeps or drops whole groups, judged by
what a group holds, such as its row count.

**Try it:** count the cheap items of each category.

<RunSQL query={`SELECT category, COUNT(*) AS items
FROM products
WHERE unit_price_usd < 5
GROUP BY category;`} />

Expected: 4 rows, 2 columns, in any order. *Why:* `food` counts 1 item, not 3, because `WHERE` ran first and dropped
the dear ones.

**Try it:** the natural first try filters the count in `WHERE`.

<RunSQL query={`SELECT category, COUNT(*) AS items
FROM products
WHERE unit_price_usd < 5 AND COUNT(*) >= 3
GROUP BY category;`} />

Expected: an error that says `WHERE clause cannot contain aggregates!`. Now the same test in `HAVING`:

<RunSQL query={`SELECT category, COUNT(*) AS items
FROM products
WHERE unit_price_usd < 5
GROUP BY category
HAVING COUNT(*) >= 3;`} />

Expected: 3 rows, 2 columns, in any order; `food` drops out.

### 3. Sort and cut come last

`ORDER BY` and `LIMIT` are **output modifiers**: they work on the finished result, at the very end. `ORDER BY` sorts
the rows, then `LIMIT` cuts the sorted list.

*Excel:* a sort rearranges the rows of a table (E5).

**Try it:**

<RunSQL query={`SELECT category, COUNT(*) AS items
FROM products
WHERE unit_price_usd < 5
GROUP BY category
HAVING COUNT(*) >= 3
ORDER BY items DESC, category
LIMIT 2;`} />

Expected: 2 rows, 2 columns: coffee 5, bakery 3. *Why:* `category` breaks the tie between bakery and tea (S2).

### 4. Names you give

`AS` gives an output column a name, an **alias**. The name is created when `SELECT` runs, so the clauses before it,
such as `WHERE`, have no such name yet. `ORDER BY` runs after it, which is why `ORDER BY items` worked in unit 3. DuckDB also accepts an alias earlier, for a plain expression.

**Try it:**

<RunSQL query={`SELECT product_name, unit_price_usd * 100 AS cents
FROM products
WHERE cents < 400;`} />

Expected: 7 rows, 2 columns. DuckDB's documentation lists "Column aliases in WHERE, GROUP BY, and HAVING" among its
friendly features. PostgreSQL does not accept this. Its documentation allows an output column's name in "ORDER BY and
GROUP BY clauses, but not in the WHERE or HAVING clauses; there you must write out the expression instead."

The portable habit is to write it out: `WHERE unit_price_usd * 100 < 400` returns the same 7 rows. Even DuckDB stops for
an alias of an aggregate: `WHERE items >= 3` gives the error of unit 2.

<Aside type="tip" title="Remember">

- The clauses run in this order: `FROM`, `WHERE`, `GROUP BY`, `HAVING`, `SELECT`, `ORDER BY`, `LIMIT`.
- `WHERE` chooses rows and `SELECT` chooses columns.
- A clause cannot use what a later clause creates: a count belongs in `HAVING`, not `WHERE`.
- An alias exists from `SELECT` on; to be portable, write the expression out.

**Common trap: "`LIMIT` takes the first rows of the table, and then `ORDER BY` sorts them."** The sort runs first and
`LIMIT` cuts the sorted list. `ORDER BY product_name LIMIT 2` returns Americano and Avocado Toast, although the first two
rows of `products` are Espresso and Americano.

</Aside>

**Spot the flaw.** A colleague wants the products over \$4 shown in cents. The query runs without an error but returns no

<RunSQL query={`SELECT product_name, unit_price_usd * 100 AS unit_price_usd

SELECT product_name, unit_price_usd * 100 AS cents
FROM products
WHERE unit_price_usd * 100 > 400;
