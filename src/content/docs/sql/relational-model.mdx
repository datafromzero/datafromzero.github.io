## Learn by doing

Five small steps. Press Run on each query. Counts cover all 1,800
orders (the canceled one included) and all 3,287 lines (the quantity-20 line on order 2075 included).

### 1. Say what one row is

A database keeps each kind of thing in its own **table**: one **column** for each kind of fact and one **row** for each
thing, the tidy shape of *Rows, columns and tidy layout* (E1). *Excel:* an Excel Table (E5, *Tables, sorting and
filtering*) is one table.

Before you count anything, say what one row stands for, in one sentence that starts "One row is…". That sentence is the
table's **grain**, and `COUNT(*)` counts whatever a row stands for.

**Try it**: what is in the database?

<RunSQL query={`SHOW TABLES;`} />

Expected: 5 rows, 1 column (`name`): `customers`, `order_items`, `orders`, `products`, `stores`.

**Try it**: the columns of `orders`.

<RunSQL query={`DESCRIBE orders;`} />

Expected: 6 rows, one per column, and 6 columns (`column_name`, `column_type`, `null`, `key`, `default`, `extra`).
The `key` column shows `NULL` in every row; the next unit says why.

**Try it**: a few rows.

<RunSQL query={`SELECT * FROM orders ORDER BY order_id LIMIT 5;`} />

Expected: 5 rows, 6 columns; the first is order 1001, customer 15, store 2. *Why:* each row carries its own
`order_id`, so: **one row of `orders` is one order, one visit to the till.**

### 2. A primary key identifies each row

A **primary key** (PK) is a column, or a set of columns, whose values identify each row, so no value repeats. DuckDB
also refuses an empty value in a primary key.

The cafe-sales tables declare no constraints, so here the keys describe the data and nothing checks them (*Creating
tables and constraints* shows how to enforce them). You prove a key by counting.

**Try it**: compare the number of rows with the number of different `order_id` values.

<RunSQL query={`SELECT COUNT(*) AS row_count,
       COUNT(DISTINCT order_id) AS distinct_ids
FROM orders;`} />

Expected: 1 row, 2 columns: `1800 | 1800`. *Why:* a repeated or empty id would make the second number smaller. Equal
counts prove `order_id` is unique and always filled, so it can be the primary key. Since one row is one order, **1,800
is the number of orders**, the same as the Count in E1.

### 3. A foreign key points at a primary key

A **foreign key** (FK) is a column whose values are values of another table's primary key. Line 5003 of `order_items`
holds 1001 in `order_id`: look in `orders` for the row whose primary key is 1001, and you find at most one.

Go the other way and ask which lines hold 1001: a foreign key may repeat, so you may find many. When DuckDB enforces a
foreign key, it checks that the value exists in the other table. *Excel:* in *Bring in a value by key with XLOOKUP* (E8),
the code you searched *with* plays the foreign key and the column you searched *in* plays the primary key.

**Try it**: follow order 1001, first the order.

<RunSQL query={`SELECT * FROM orders WHERE order_id = 1001;`} />

Now its lines.

<RunSQL query={`SELECT * FROM order_items WHERE order_id = 1001;`} />

Expected: first query 1 row, 6 columns; second query 3 rows, 5 columns, with `order_item_id` 5001, 5002 and 5003.
*Why:* `order_items.order_id` is a foreign key, and one order is matched by three lines. The picture follows the same keys.

### 4. One-to-many and many-to-many

In a **one-to-many** link, one row of table A matches many rows of table B, and each row of B matches one row of A: one
store has many orders, and each order has one store. The foreign key sits on the *many* side.

When many match many, a single column cannot hold several values in one row, so a third table sits between the two, with
a foreign key to each: `order_items` sits between `orders` and `products`.

**Try it**: look at the many side.

<RunSQL query={`SELECT COUNT(*) AS row_count,
       COUNT(DISTINCT order_item_id) AS distinct_line_ids,
       COUNT(DISTINCT order_id) AS distinct_order_ids
FROM order_items;`} />

Expected: 1 row, 3 columns: `3287 | 3287 | 1800`. *Why:* `order_item_id` is unique, so it is the key and **one row of
`order_items` is one product line inside one order**. `order_id` repeats, once per line of the same order, so it takes
only 1,800 values over 3,287 rows. That is why the owner saw two numbers: 1,800 orders, 3,287 lines.

<details>
<summary>Explain it in your own words: why does order_items have more rows than orders?</summary>

A line belongs to one order, and an order has one to three lines here, so counting lines must give at least as many as
counting orders. The extra rows are not new orders; they are lines that share an `order_id`.

</details>

### 5. Check the numbers

No new query. 1,800 orders equals the Count in E1, and 3,287 lines equals the lines you counted in E8. The grains, in one
table:

| Table | Grain: one row is… |
|---|---|
| `stores` | a store |
| `customers` | a loyalty-program customer |
| `products` | a menu item |
| `orders` | an order, one visit to the till |
| `order_items` | one product line inside an order |

<Aside type="tip" title="Remember">

- Say what one row is before you count: "One row is…".
- A primary key never repeats and is never empty. Prove it by counting rows against different values.
- A foreign key holds values of another table's primary key, and it may repeat.
- One-to-many: the foreign key sits on the many side. Many-to-many: a third table sits between.

**Common trap: "a column with `id` in its name is a key."** Whether a column is a key depends on its table: it is one
only if its values never repeat there. `store_id` is the primary key of `stores`, but in `orders` it is a foreign key and
repeats: Campus, store 2, took 716 orders, of any status.

</Aside>

## Finish it

<Exercise id="sql-relational-model-1">

**Is `customer_id` a key of `customers`, and is `city`?** Expected: 1 row, 3 columns:
`150 | 150 | 3`.

Done for you: one row is one loyalty-program customer, and this gives 5 rows, one per column:

<RunSQL query={`DESCRIBE customers;`} />

Now finish it: replace it with one query with three counts (all rows, different `customer_id` values, different `city`
values), run it, and say which column can be the primary key.

<details>
<summary>Hint</summary>

Copy the shape of unit 2 and add a third count. If a column is a key, its two counts match.

</details>

<details>
<summary>Half-solution</summary>

```sql
SELECT COUNT(*) AS row_count,
       COUNT(DISTINCT customer_id) AS distinct_ids,
       COUNT(DISTINCT ...) AS distinct_cities
FROM customers;
```

</details>

<Solution>

```sql
SELECT COUNT(*) AS row_count,
       COUNT(DISTINCT customer_id) AS distinct_ids,
       COUNT(DISTINCT city) AS distinct_cities
FROM customers;
```

`150 | 150 | 3`. The 150 different `customer_id` values over 150 rows make it the primary key, so **one row of
`customers` is one loyalty-program customer**. `city` has 3 values over 150 rows: it repeats, so it cannot identify a
customer.

</Solution>

</Exercise>

<RunSQL query={`-- Write your query here, then press Run.`} />

<details>
<summary>Hint</summary>

Which table has one row per menu item, and which one row per sale? The question is about sales.

</details>

<details>
<summary>Half-solution</summary>

Expected output: *"Three single numbers: the rows of `products`, the different `product_id` values in
`order_items`, and the `order_items` rows whose `product_id` is 16."*

</details>

<Solution>

```sql
SELECT COUNT(*) AS menu_items FROM products;
SELECT COUNT(DISTINCT product_id) AS products_sold FROM order_items;
SELECT COUNT(*) AS lines_for_product_16 FROM order_items WHERE product_id = 16;
```

The results are `16`, `15` and `0`. **We sold 15 different products.** The 16 counts menu
items, and one never appears on a line. Product 16, found with
`SELECT product_name FROM products WHERE product_id = 16;`, is the Pumpkin Spice Latte: a row in `products` with no
row in `order_items`. A question about sales belongs to the table whose grain is a sale line, `order_items`.

`products` and `orders` are **many-to-many**: an order holds several products, and a product such as Espresso is on
192 different orders. `order_items` sits between them, one row per pairing.

</Solution>

</Exercise>

## Check yourself

Without looking back: what are a primary key and a foreign key, and what does the grain of `order_items` say?

<details>
<summary>Answer</summary>

A primary key is a column whose values identify one row each: none repeats, none is empty. A foreign key holds
values of another table's primary key and links the two tables. The grain of `order_items`: one row is one product
line inside one order.

</details>

Expected: 1 row, 1 column: `1800`.

</Solution>
