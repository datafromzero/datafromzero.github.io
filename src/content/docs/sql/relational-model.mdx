Read the first picture like a map. Each box is a **table**. The names inside it are its **columns**: one column is
one kind of fact. The table itself is made of **rows**: one row is one record, and the boxes do not draw them, the
second picture does. You know this shape from the lesson *Rows, columns and tidy layout* (E1): one header row, one
record per row, one fact per cell.

- A **primary key** (PK) is a column whose value identifies exactly one row: no value is repeated, and none is
  empty. `order_id` is the primary key of `orders`.
- A **foreign key** (FK) is a column that holds values of another table's primary key. `orders.store_id` holds
  values from `stores.store_id`, so every order points at the store that took it. The line between two boxes joins
  a foreign key to the primary key it points at.
- **One-to-many:** one store has many orders, and each order has exactly one store. The foreign key always sits
  on the *many* side, here in `orders`. Customers and orders work the same way: customer 15 placed 16 orders, and
  each order names at most one customer.
- **Many-to-many:** one order holds several products, and one product appears on many orders. A single column
  cannot store that, so a third table sits between them. `order_items` has one row for each pairing of an order and a
  product, with the quantity and discount of that pairing, and two foreign keys: `order_id` and `product_id`.
  In a relational database, many-to-many is built from two one-to-many links.
- The **grain** of a table is what one row stands for, said in one sentence that starts with "One row is…". You
  say it before you count or total anything.

| Table | Grain: one row is… |
|---|---|
| `stores` | a store |
| `customers` | a loyalty-program customer |
| `products` | a menu item |
| `orders` | an order, one visit to the till |
| `order_items` | one product line inside an order |

You have met the keys before, in the lessons *Tables, sorting and filtering* (E5) and *Bring in a value by key with
XLOOKUP* (E8). An Excel Table is one table, and the cafe-sales workbook keeps each of its five tables on its own
sheet. When you wrote an XLOOKUP, the code you searched *with*, `product_id` on the order line, was a foreign key,
and the column you searched *in*, `product_id` on the products sheet, was a primary key. A lookup is two tables
paired on a key; a later lesson does the same pairing in SQL.

<Aside type="note" title="Keys in this database are declared by us, not enforced">
A database can enforce keys: DuckDB's documentation says a primary key constraint also keeps the key from being
empty, and a foreign key constraint makes sure the key exists in the other table. The load script for cafe-sales
creates plain tables without those constraints, so `DESCRIBE` will show an empty `key` column. The keys in the
picture come from the dataset's description, and you will prove them by counting. The lesson *Creating tables and
constraints* shows how to make a database enforce them.
</Aside>

<Aside type="tip" title="One link is not drawn">
`customers` has a column `referred_by`: the `customer_id` of the customer who recommended them (30 of the 150
customers have one). It is a foreign key that points back at its own table. It is folded into the "4 more columns"
in the picture to keep the map readable.
</Aside>

<Aside type="note" title="Where other databases differ">
`SHOW TABLES` and `DESCRIBE` are the commands DuckDB gives you for looking at a database. Other systems list tables
and columns in their own ways; DuckDB's documentation also mentions the SQL-standard `information_schema` views.
Every SQL lesson here names its engine, so you always know which wording applies.
</Aside>

## Worked example

Question: **how many orders are there, and why does `order_items` show a different number?** Open the notebook, run
the first cell, and follow along. Each step shows the query, then the shape of the result you should see. Every
count below covers all 1,800 orders, the one canceled order included, and all 3,287 lines, including the line with
quantity 20 on order 2075 (it is one line either way).

1. **List the tables.**

   ```sql
   SHOW TABLES;
   ```

   `SHOW TABLES` lists the tables in the database. Expected: 5 rows, 1 column (`name`): `customers`,
   `order_items`, `orders`, `products` and `stores`. *Why:* before you ask anything, know what is there. These are
   the five boxes of the picture.

2. **List the columns of `orders`.**

   ```sql
   DESCRIBE orders;
   ```

   `DESCRIBE` lists the columns of a table with their types. Expected: 6 rows (one per column) and 6 columns:
   `column_name`, `column_type`, `null`, `key`, `default`, `extra`. The `column_name` values are `order_id`,
   `customer_id`, `store_id`, `ordered_at`, `status` and `payment_method`. *Why:* you now know the names to use.
   The `key` column is empty for every row (shown as `NULL`), because this database does not enforce keys. The
   dataset's description names `order_id` as the primary key; the next steps check it.

3. **Look at a few rows.**

   ```sql
   SELECT * FROM orders LIMIT 5;
   ```

   Read it left to right: `SELECT *` means *show every column*, `FROM orders` says *from this table*, and `LIMIT 5`
   means *only the first five rows*. Expected: 5 rows, 6 columns; the first row is order 1001, customer 15, store 2.
   Here the rows come back as orders 1001 to 1005, but SQL promises no particular order until you ask for one, which
   the next lesson covers. *Why:* say what one row is. Each row has its own `order_id`, so the grain is: **one row of
   `orders` is one order, one visit to the till.**

4. **Prove that `order_id` is a key.**

   ```sql
   SELECT COUNT(*) AS row_count,
          COUNT(DISTINCT order_id) AS distinct_ids
   FROM orders;
   ```

   `COUNT(*)` counts rows. `COUNT(DISTINCT order_id)` counts the different values of `order_id` that are not empty.
   `AS` names the result column. Expected: 1 row, 2 columns: `1800 | 1800`. *Why:* if every row has an id that no
   other row shares, the two numbers match. A repeated id would make the second number smaller, and so would an
   empty one. Equal counts prove that `order_id` is unique and always filled, so it can be the primary key. And
   because one row is one order, **1,800 is the number of orders**, the same as the Count in the status bar in the
   lesson *Rows, columns and tidy layout* (E1).

5. **Follow order 1001 across the foreign key.**

   ```sql
   SELECT * FROM orders WHERE order_id = 1001;
   SELECT * FROM order_items WHERE order_id = 1001;
   ```

   `WHERE order_id = 1001` keeps only the rows whose `order_id` equals 1001; the lesson *Filtering rows with WHERE*
   covers it fully. Expected for the first query: 1 row, 6 columns (customer 15, store 2). Expected for the second:
   3 rows, 5 columns, with `order_item_id` 5001, 5002 and 5003, all carrying `order_id` 1001, and `product_id`
   10, 6 and 1. *Why:* `order_items.order_id` is a foreign key. It holds values from `orders.order_id`, and here one
   order is matched by three lines. That is one-to-many, with the foreign key on the many side.

6. **Look at the many side.**

   ```sql
   SELECT COUNT(*) AS row_count,
          COUNT(DISTINCT order_item_id) AS distinct_line_ids,
          COUNT(DISTINCT order_id) AS distinct_order_ids
   FROM order_items;
   ```

   Expected: 1 row, 3 columns: `3287 | 3287 | 1800`. *Why:* `order_item_id` is unique on every row, so it is the key
   of this table and **one row of `order_items` is one product line inside one order**. `order_id` is not a key
   here: it takes only 1,800 different values over 3,287 rows, because it repeats, once for every line of the same
   order. That is why the owner saw two numbers: 1,800 is the number of orders, and 3,287 is the number of lines.
   They answer different questions.

7. **See that it works both ways.**

   ```sql
   SELECT COUNT(DISTINCT order_id) AS orders_with_espresso
   FROM order_items
   WHERE product_id = 1;
   ```

   Expected: 1 row, 1 column: `192`. *Why:* product 1 is Espresso. Order 1001 holds three different products, and
   Espresso is on 192 different orders. Many products per order and many orders per product make **many-to-many**,
   which is why `order_items` sits between `orders` and `products`.

8. **Verify.** Check each grain statement against a number you already know. The 1,800 orders equal the Count of
   the order ids in E1. The 3,287 lines equal the 3,287 lines you counted in the XLOOKUP lesson (E8). Two tools,
   one dataset, the same counts. The step 4 and step 6 results also agree with the row counts in the dataset's
   description.

<details>
<summary>Explain it in your own words: why does order_id take 1,800 different values in both tables, while order_items has 3,287 rows?</summary>

Every order has at least one line, so all 1,800 orders show up in `order_items`. But an order can have more than
one line (in this data between one and three), so there are more lines than orders. The extra rows are repeats of
an `order_id`, which is exactly what a foreign key on the many side does.

</details>


The result is `150 | 150 | 3`. There are 150 rows and 150 different `customer_id` values, so `customer_id` is unique
and always filled: it is the primary key, and **one row of `customers` is one loyalty-program customer**. `city` has
only 3 different values over 150 rows, so it repeats and cannot identify a customer.

A primary key value may also have no rows on the many side. Only 145 of the 150 customers have ever placed an
order; five signed up and never ordered. That is allowed in a one-to-many link.

</Solution>

</Exercise>

**Spot the flaw.** A colleague runs this query in the notebook, gets `1799`, and reports "we took 1,799 orders":

```sql
SELECT COUNT(customer_id) AS orders FROM orders;
```

Expected from that query: 1 row, 1 column: `1799`. What went wrong, and what is the right query?

<Solution>

The real number is 1,800. `COUNT(customer_id)` counts the rows where `customer_id` is **not empty** (DuckDB's
documentation: the number of rows where the argument is not NULL). One order has no customer: order **1335** is a
walk-in customer without a loyalty card, the same order that gave `#N/A` in the XLOOKUP lesson. In the picture,
`customer_id` is a foreign key, and a foreign key may be empty when an order has no partner row. The colleague counted
orders that name a customer, not orders. It is the same 1,799 as the spot-the-flaw exercise in the first Excel
lesson, in a new tool.

To see the cause:

```sql
SELECT COUNT(*) AS all_orders, COUNT(customer_id) AS with_customer FROM orders;
SELECT * FROM orders WHERE order_id = 1335;
```

The first query gives `1800 | 1799` (1 row, 2 columns). The second returns 1 row, 6 columns, with an empty
`customer_id`, store 1 and status `completed`. The fix is to count rows, or to count the primary key, which is filled
on every row:

```sql
SELECT COUNT(*) AS orders FROM orders;
```

Expected: 1 row, 1 column: `1800`.

</Solution>
