Each box is a **table**; the names inside are its **columns**, one kind of fact each. The rows are the records,
drawn in the second picture. This is the tidy shape from E1.

- A **primary key** (PK) is a column whose value identifies exactly one row: never repeated, never empty.
  `order_id` is the primary key of `orders`.
- A **foreign key** (FK) is a column that holds values of another table's primary key. `orders.store_id` holds
  values from `stores.store_id`, so each order points at the store that took it. Each line in the picture joins a
  foreign key to its primary key.
- **One-to-many:** one store has many orders; each order has one store. The foreign key sits on the *many* side.
  Customers and orders work the same way: customer 15 placed 16 orders, and each order names at most one customer.
- **Many-to-many:** one order holds several products, and one product is on many orders. A single column cannot
  store that, so a third table sits between them: `order_items`, one row per pairing of an order and a product.
- The **grain** of a table is what one row stands for, in one sentence that starts "One row is…". Say it before
  you count or total anything.

| Table | Grain: one row is… |
|---|---|
| `stores` | a store |
| `customers` | a loyalty-program customer |
| `products` | a menu item |
| `orders` | an order, one visit to the till |
| `order_items` | one product line inside an order |

You have used keys already. In *Tables, sorting and filtering* (E5), an Excel Table was one table. In E8, the code
you searched *with* was a foreign key, and the column you searched *in* was a primary key.

<Aside type="note" title="Keys here are declared by us, not enforced">
DuckDB can enforce keys: a primary key constraint also keeps the key from being empty, and a foreign key
constraint makes sure the key exists in the other table. The cafe-sales tables are plain, without those
constraints, so you prove the keys by counting. The lesson *Creating tables and constraints* shows how to enforce them.
</Aside>

## Worked example

Question: **how many orders are there, and why does `order_items` show a different number?** Run the notebook's
setup cell, then one cell per step. Each step gives the shape of the result to expect. Counts cover all 1,800 orders
(the canceled one included) and all 3,287 lines (including the quantity-20 line on order 2075).

1. **List the tables.**

   ```sql
   SHOW TABLES;
   ```

   Expected: 5 rows, 1 column (`name`): `customers`, `order_items`, `orders`, `products`, `stores`. *Why:* know what
   is there first: the five boxes of the picture.

2. **List the columns of `orders`.**

   ```sql
   DESCRIBE orders;
   ```

   Expected: 6 rows, one per column, and 6 columns (`column_name`, `column_type`, `null`, `key`, `default`,
   `extra`). *Why:* now you know the names to use. The `key` column shows `NULL` in
   every row, because this database does not enforce keys. The dataset's description names `order_id` as the key; the
   next steps check it.

3. **Look at a few rows.**

   ```sql
   SELECT * FROM orders LIMIT 5;
   ```

   Expected: 5 rows, 6 columns; the first is order 1001, customer 15, store 2. *Why:* say what one row is. Each row has its own `order_id`, so: **one
   row of `orders` is one order, one visit to the till.**

4. **Prove that `order_id` is a key.**

   ```sql
   SELECT COUNT(*) AS row_count,
          COUNT(DISTINCT order_id) AS distinct_ids
   FROM orders;
   ```

   Compare the number of rows with the number of different `order_id` values. Expected: 1 row, 2 columns: `1800 | 1800`. *Why:* a repeated or empty id would
   make the second number smaller. Equal counts prove `order_id` is unique and always filled, so it can be the
   primary key. Since one row is one order, **1,800 is the number of orders**, the same as the Count in E1.

5. **Follow order 1001 across the foreign key.** Two notebook cells.

   ```sql
   SELECT * FROM orders WHERE order_id = 1001;
   SELECT * FROM order_items WHERE order_id = 1001;
   ```

   Expected: first query 1 row, 6 columns; second query 3 rows, 5 columns, with `order_item_id` 5001, 5002 and
   5003. *Why:* `order_items.order_id` is a foreign key, and one order is matched by three lines:
   one-to-many, with the foreign key on the many side.

6. **Look at the many side.**

   ```sql
   SELECT COUNT(*) AS row_count,
          COUNT(DISTINCT order_item_id) AS distinct_line_ids,
          COUNT(DISTINCT order_id) AS distinct_order_ids
   FROM order_items;
   ```

   Expected: 1 row, 3 columns: `3287 | 3287 | 1800`. *Why:* `order_item_id` is unique, so it is the key and **one
   row of `order_items` is one product line inside one order**. `order_id` repeats, once per line of the same order,
   so it takes only 1,800 values over 3,287 rows. That is why the owner saw two numbers: 1,800 orders, 3,287 lines.

7. **Verify.** 1,800 orders equals the Count in E1, and 3,287 lines equals the lines you counted in E8.

<details>
<summary>Explain it in your own words: why does order_items have more rows than orders?</summary>

Every order has at least one line, and some have several (here one to three). The extra rows repeat an `order_id`,
which is what a foreign key on the many side does.

</details>
