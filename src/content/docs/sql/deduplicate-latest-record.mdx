## The question

The owner of the cafes asks:

> Our loyalty app writes a row every time a customer's record is saved, and sometimes it writes the same save twice.
> I want one current row for each customer.

The cafe-sales tables hold no repeated ids, so this lesson uses a small practice table, `customer_updates`: 10 invented
rows for 5 customers, built by one notebook cell (step 2).

| update_id | customer_id | loyalty_tier | city | updated_at |
|---:|---:|---|---|---|
| 1 | 301 | bronze | Oakland | 2026-03-02 09:15:00 |
| 2 | 301 | silver | Oakland | 2026-05-10 14:02:00 |
| 3 | 302 | bronze | Berkeley | 2026-03-05 10:30:00 |
| 4 | 302 | bronze | Berkeley | 2026-03-05 10:30:00 |
| 5 | 303 | silver | Alameda | 2026-04-01 08:00:00 |
| 6 | 303 | gold | Alameda | 2026-04-01 08:00:00 |
| 7 | 304 | bronze | Oakland | 2026-04-20 16:45:00 |

| 9 | 305 | silver | Berkeley | 2026-06-01 09:30:00 |

Some rows are history (customer 301 moved up a tier), some are copies (customer 302, and the last two of customer 305)

A **duplicate** is an entity that appears more than once in a table where it should appear once. Removing duplicates
means choosing which row survives, and that is a rule about the business, not a trick of SQL:

1. Find the repeats: `GROUP BY` the id, `HAVING COUNT(*) > 1`.
2. State the **survivor rule** in words: which column orders the rows, in which direction, and what breaks a tie.
3. Number each entity's rows with `ROW_NUMBER()` in that order and keep number 1 (S15).
4. Verify: one row for each entity.

The same steps return the **latest record per entity**, such as each customer's most recent order: the rule is "newest
first".

**Excel and Google Sheets.** Excel's Remove Duplicates (Data, Data Tools) keeps the first occurrence in the list, so
the order of your rows is the survivor rule: sort newest first to keep the latest. Google Sheets has a similar command
(Data, Data cleanup, Remove duplicates); SQL writes the rule down and leaves the source table as it was.

## Worked example

Question: **what is the current row for each customer in `customer_updates`?** Run the setup cell and the
practice-table cell, then one cell per step.

1. **Check a table that has no repeats.**

   ```sql
   SELECT order_id, COUNT(*) AS copies
   FROM orders
   GROUP BY order_id
   HAVING COUNT(*) > 1;
   ```

   Read it: *show the order ids that appear more than once*. Expected: 0 rows, 2 columns: no rows. *Excel:* a COUNTIF
   column for the ids, filtered above 1. *Why:* a clean table returns nothing, and you can run this check on any id
   column.

2. **Look at the practice table.**

   ```sql
   SELECT * FROM customer_updates ORDER BY update_id;
   ```

   Expected: 10 rows, 5 columns, the table from the question. *Why:* one row is one save, so a customer can have several
   rows by design. The practice-table cell:

   <details>
   <summary>The practice-table cell</summary>

   ```sql
   CREATE OR REPLACE TEMP TABLE customer_updates AS
   SELECT * FROM (VALUES
     (1,  301, 'bronze', 'Oakland',  TIMESTAMP '2026-03-02 09:15:00'),
     (2,  301, 'silver', 'Oakland',  TIMESTAMP '2026-05-10 14:02:00'),
     (3,  302, 'bronze', 'Berkeley', TIMESTAMP '2026-03-05 10:30:00'),
     (4,  302, 'bronze', 'Berkeley', TIMESTAMP '2026-03-05 10:30:00'),
     (5,  303, 'silver', 'Alameda',  TIMESTAMP '2026-04-01 08:00:00'),
     (6,  303, 'gold',   'Alameda',  TIMESTAMP '2026-04-01 08:00:00'),
     (7,  304, 'bronze', 'Oakland',  TIMESTAMP '2026-04-20 16:45:00'),
     (8,  305, 'bronze', 'Berkeley', TIMESTAMP '2026-02-11 11:11:00'),
     (9,  305, 'silver', 'Berkeley', TIMESTAMP '2026-06-01 09:30:00'),
     (10, 305, 'silver', 'Berkeley', TIMESTAMP '2026-06-01 09:30:00')
   ) AS t(update_id, customer_id, loyalty_tier, city, updated_at);
   ```

   `VALUES` lists the rows, `TIMESTAMP '...'` types a timestamp, and `t(update_id, ...)` names the columns. `TEMP`
   means the table lives only in this session. *Creating tables and constraints* (S31) explains `CREATE TABLE`.

   </details>

3. **Find the repeated customer ids.**

   ```sql
   SELECT customer_id, COUNT(*) AS records
   FROM customer_updates
   GROUP BY customer_id
   HAVING COUNT(*) > 1
   ORDER BY customer_id;
   ```

   Expected: 4 rows, 2 columns: customers 301, 302 and 303 with 2 rows each, and customer 305 with 3. *Excel:* a COUNTIF column
   for the ids, filtered above 1. *Why:* a repeated id is a question, not yet an error: customer 301's rows are
   history, 302's are an exact copy, and 303's conflict.

4. **See why `SELECT DISTINCT` is not the fix.**

   ```sql
   SELECT DISTINCT customer_id, loyalty_tier, city, updated_at
   FROM customer_updates
   ORDER BY customer_id, updated_at;
   ```

   Expected: 8 rows, 4 columns, with `update_id` left out. *Why:* `DISTINCT` keeps only the unique rows of the result, rows
   identical in every selected column. It merged the copies of customers 302 and 305, but
   customers 301 and 303 still have two rows, and it chose no survivor.

5. **State the rule, then number the rows.** The rule, in words: *the survivor is the record with the latest
   `updated_at`; if two share the same time, the one that arrived later, the higher `update_id`.*

   ```sql
   SELECT *,
          ROW_NUMBER() OVER (PARTITION BY customer_id
                             ORDER BY updated_at DESC, update_id DESC) AS rn
   FROM customer_updates
   ORDER BY customer_id, rn;
   ```

   Read it: *for each customer, number the records newest first, and break a tie by the higher update_id*. Expected:
   10 rows, 6 columns, as in the first picture. *Why:* `PARTITION BY customer_id` makes each customer a group, and the
   `ORDER BY` is the rule. Customer 303's rows share an `updated_at`, so `update_id` decides: update 6 (gold) gets 1.

6. **Keep number 1.**

   ```sql
   WITH numbered AS (
     SELECT *,
            ROW_NUMBER() OVER (PARTITION BY customer_id
                               ORDER BY updated_at DESC, update_id DESC) AS rn
     FROM customer_updates
   )
   SELECT update_id, customer_id, loyalty_tier, city, updated_at
   FROM numbered
   WHERE rn = 1
   ORDER BY customer_id;
   ```

   Expected: 5 rows, 5 columns: updates 2, 4, 6, 7 and 10. *Why:* the numbering sits in its own stage so the final `WHERE`
   can use it. DuckDB's shortcut `QUALIFY` filters on a window function the way
   `HAVING` filters on an aggregate, without the extra stage:

   ```sql
   SELECT update_id, customer_id, loyalty_tier, city, updated_at
   FROM customer_updates
   QUALIFY ROW_NUMBER() OVER (PARTITION BY customer_id
                              ORDER BY updated_at DESC, update_id DESC) = 1
   ORDER BY customer_id;
   ```

   Expected: 5 rows, 5 columns, the same five rows. Learn the two-stage form first.

7. **Verify.**

   ```sql
   WITH numbered AS (
     SELECT *,
            ROW_NUMBER() OVER (PARTITION BY customer_id
                               ORDER BY updated_at DESC, update_id DESC) AS rn
     FROM customer_updates
   ),
   latest AS (
     SELECT * FROM numbered WHERE rn = 1
   )
   SELECT COUNT(*) AS rows_kept, COUNT(DISTINCT customer_id) AS customers
   FROM latest;
   ```

   Expected: 1 row, 2 columns: `5` and `5`. *Why:* rows kept equal customers, so each customer has exactly one row. The
   count alone is not enough, as Exercise 3 shows: also read the rows where the rule had to decide, here customer 303.

```sql
WITH numbered AS (
  SELECT customer_id, order_id, ordered_at,
         ROW_NUMBER() OVER (PARTITION BY customer_id
                            ORDER BY ordered_at DESC, order_id DESC) AS rn
  FROM orders
  WHERE customer_id IS NOT NULL AND status = 'completed'
)
SELECT customer_id, order_id, ordered_at
FROM numbered
WHERE rn = 1
ORDER BY customer_id;
```
