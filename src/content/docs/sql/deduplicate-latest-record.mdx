## The question

The owner of the cafes asks:

> Our loyalty app writes a row every time a customer's record is saved, and sometimes it writes the same save twice.
> I want one current row for each customer.

The cafe-sales tables hold no repeated ids, so this lesson uses a small practice table, `customer_updates`: 10 invented
rows for 5 customers, built by one block in unit 1.

## Warm-up

From memory first, then click to check.

1. Write a query that lists the stores with more than 500 orders (*GROUP BY and HAVING*, S8). Expected:
   2 rows, 2 columns.

   <details>
   <summary>Answer</summary>

   ```sql
   SELECT store_id, COUNT(*) AS orders
   FROM orders
   GROUP BY store_id
   HAVING COUNT(*) > 500
   ORDER BY store_id;
   ```

   Stores 1 and 2 have 729 and 716 orders. `HAVING` filters groups after they are counted.

   </details>

2. In *Ranking and top-N per group* (S15), which ranking function gives every row a different number, and why does
   that matter when you want exactly one row per group?

   <details>
   <summary>Answer</summary>

   `ROW_NUMBER`: tied rows still get different numbers, so number 1 is exactly one row per group. `RANK` can give
   several rows rank 1.

   </details>

## The big idea

Deduplication keeps exactly one row for each entity: you write down which row survives, number each entity's rows by
that rule, and keep number 1.

## Learn by doing

Five small steps. Each gives you one idea, then you try it in the editor.

### 1. Find the repeats

A **duplicate** is an entity that appears more than once in a table where it should appear once. To find repeats,
`GROUP BY` the key and keep `HAVING COUNT(*) > 1`.

**Try it:** check a table that should have no repeats.

<RunSQL query={`SELECT order_id, COUNT(*) AS copies
FROM orders
GROUP BY order_id
HAVING COUNT(*) > 1;`} />

Read it: *show the order ids that appear more than once*. Expected: 0 rows, 2 columns. *Excel:* a COUNTIF column for the
ids, filtered above 1. *Why:* a clean table returns nothing, and you can run this check on any id column.

Now the practice table. This block builds it, and every later block of this lesson uses it; if you press Reset data, run
it again. `VALUES` lists the rows, `TIMESTAMP '...'` types a timestamp, `t(update_id, ...)` names the columns, and `TEMP`
keeps the table for this session only (*Creating tables and constraints*, S31).

**Try it:**

<RunSQL query={`CREATE OR REPLACE TEMP TABLE customer_updates AS
SELECT * FROM (VALUES
  (1,  301, 'bronze', 'Oakland',  TIMESTAMP '2026-03-02 09:15:00'),
  (2,  301, 'silver', 'Oakland',  TIMESTAMP '2026-05-10 14:02:00'),
  (3,  302, 'bronze', 'Berkeley', TIMESTAMP '2026-03-05 10:30:00'),
  (4,  302, 'bronze', 'Berkeley', TIMESTAMP '2026-03-05 10:30:00'),
  (5,  303, 'silver', 'Alameda',  TIMESTAMP '2026-04-01 08:00:00'),
  (6,  303, 'gold',   'Alameda',  TIMESTAMP '2026-04-01 08:00:00'),
  (7,  304, 'bronze', 'Oakland',  TIMESTAMP '2026-04-20 16:45:00'),
  (8,  305, 'bronze', 'Berkeley', TIMESTAMP '2026-02-11 11:11:00'),
  (9,  305, 'silver', 'Berkeley', TIMESTAMP '2026-06-01 09:30:00'),
  (10, 305, 'silver', 'Berkeley', TIMESTAMP '2026-06-01 09:30:00')
) AS t(update_id, customer_id, loyalty_tier, city, updated_at);

SELECT * FROM customer_updates ORDER BY update_id;`} />

Expected: 10 rows, 5 columns, the table from the question. *Why:* one row is one save, so a customer can have several
rows by design.

**Try it:** the repeated customer ids.

<RunSQL query={`SELECT customer_id, COUNT(*) AS records
FROM customer_updates
GROUP BY customer_id
HAVING COUNT(*) > 1
ORDER BY customer_id;`} />

Expected: 4 rows, 2 columns: customers 301, 302 and 303 with 2 rows each, and customer 305 with 3. *Why:* a repeated id is a question, not yet an error.

### 2. `DISTINCT` is not the fix

`SELECT DISTINCT` returns only the unique rows of the result: rows identical in every selected column. It chooses no
survivor, so two rows of one entity that differ in a selected column both stay.

**Try it:**

<RunSQL query={`SELECT DISTINCT customer_id, loyalty_tier, city, updated_at
FROM customer_updates
ORDER BY customer_id, updated_at, loyalty_tier;`} />

Expected: 8 rows, 4 columns, with `update_id` left out. *Why:* `DISTINCT` merged the copies of customers 302 and 305, but
customers 301 and 303 still have two rows.

### 3. State the rule, then number the rows

Which row survives is a rule about the business, not a trick of SQL, so write it down first. A **survivor rule** says
which column orders the rows, in which direction, and what breaks a tie. `ROW_NUMBER()` (*Ranking and top-N per group*,
S15) then numbers each customer's rows by that rule.

*Excel:* Remove Duplicates (E13, *A cleaning workflow you can defend*) keeps the first occurrence of a value in the list
and deletes the others, so the order of your rows is the survivor rule.

Our rule, in words: *the survivor is the record with the latest `updated_at`; if two share the same time, the one that
arrived later, the higher `update_id`.*

**Try it:**

<RunSQL query={`SELECT *,
       ROW_NUMBER() OVER (PARTITION BY customer_id
                          ORDER BY updated_at DESC, update_id DESC) AS rn
FROM customer_updates
ORDER BY customer_id, rn;`} />

Read it: *for each customer, number the records newest first, and break a tie by the higher update_id*. Expected: 10
rows, 6 columns, as in the picture. *Why:* `PARTITION BY customer_id` makes each customer a group, and the `ORDER BY` is
the rule. Customer 303's rows share an `updated_at`, so `update_id` decides: update 6 (gold) gets 1. The rows numbered 1
are the ones to keep.

### 4. Keep number 1

rule "newest first", these steps give the **latest record per entity**.

<Aside type="tip" title="Remember">

- Find repeats with `GROUP BY` the key and `HAVING COUNT(*) > 1`.
- Write the survivor rule first: which column orders the rows, which direction, what breaks a tie.
- Number the rows by that rule with `ROW_NUMBER()` and keep number 1 in the next stage.
- `DISTINCT` merges only identical rows; it picks no survivor.

**Common trap: "removing duplicates in SQL deletes the extra rows."** A `SELECT` only reads: after the query that keeps
number 1, the practice table still holds its ten rows. Deleting needs `DELETE` (S32).

</Aside>

<RunSQL query={`-- Write your query here, then press Run.`} />

<details>

<details>
<summary>Half-solution</summary>

<Solution>

```sql
WITH numbered AS (
  SELECT customer_id, order_id, ordered_at,
         ROW_NUMBER() OVER (PARTITION BY customer_id
                            ORDER BY ordered_at DESC, order_id DESC) AS rn
  FROM orders
  WHERE customer_id IS NOT NULL AND status = 'completed'
)
SELECT customer_id, order_id, ordered_at
FROM numbered
WHERE rn = 1
ORDER BY customer_id;
```

The result has 144 rows. Of the 150 customers, 145 placed an order (customers 140, 147, 148, 149 and 150 never did),
and customer 42 has only the canceled order, so 144 have a completed one. No customer has two orders in the same minute, but `order_id` stays in the `ORDER BY` as a
tie-breaker, so the rule never depends on luck. Showing the five customers who never ordered takes a join: *LEFT JOIN
and finding rows with no match* (S20).

</Solution>
