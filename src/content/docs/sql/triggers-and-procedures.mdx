## The big idea

## Learn by doing

Six small steps. Press Run on the blocks that run; read the others. The scratch tables you make leave the cafe-sales tables alone.

### 1. Do it by hand first

**Idea.** A change and its log row are two statements. A transaction (S32) makes two statements succeed or fail as one.

**Try it:** raise Espresso by 25 cents and log it, in one transaction.

<RunSQL query={`CREATE OR REPLACE TABLE menu AS
SELECT product_id, product_name, category, unit_price_usd FROM products;
CREATE OR REPLACE TABLE price_log (
  product_id INTEGER,
  old_price_usd DECIMAL(5,2),
  new_price_usd DECIMAL(5,2)
);
BEGIN;
INSERT INTO price_log
SELECT product_id, unit_price_usd, unit_price_usd + 0.25 FROM menu WHERE product_id = 1;
UPDATE menu SET unit_price_usd = unit_price_usd + 0.25 WHERE product_id = 1;
COMMIT;
SELECT * FROM price_log;`} />

Expected: 1 row, 3 columns: `1 | 3.00 | 3.25`.

**Predict:** a colleague raises Americano by 25 cents with only the `UPDATE`. How many rows will `price_log` hold afterwards?

**Try it** (needs `menu` and `price_log` from the block above):

<RunSQL query={`UPDATE menu SET unit_price_usd = unit_price_usd + 0.25 WHERE product_id = 2;
SELECT COUNT(*) AS log_rows FROM price_log;`} />

Expected: 1 row, 1 column. *Why:* the log still holds only Espresso. Nothing tied the log to the table: only the person writing the statements keeps the two together, so the price changed and no row says so.

### 2. A trigger runs the second statement for you

**Idea.** A trigger belongs to a table. It names an **event** (`INSERT`, `UPDATE` or `DELETE`), a **timing** (`BEFORE` or `AFTER` the change) and a **granularity**: `FOR EACH ROW` runs once for every changed row, `FOR EACH STATEMENT` runs once per statement. The DuckDB documentation: "The CREATE TRIGGER statement registers a trigger: a set of SQL statements that run automatically in response to INSERT, UPDATE, or DELETE events on a table." A statement-level trigger can read the rows that changed, as they were before and after, through **transition tables**.

**Read only.** DuckDB 2.0, on a fresh copy of `menu` (the first statement of unit 1) and an empty `price_log`:

```sql
CREATE TRIGGER log_price
AFTER UPDATE ON menu
REFERENCING OLD TABLE AS o NEW TABLE AS n
FOR EACH STATEMENT
  INSERT INTO price_log
  SELECT n.product_id, o.unit_price_usd, n.unit_price_usd
  FROM o JOIN n ON o.product_id = n.product_id
  WHERE o.unit_price_usd <> n.unit_price_usd;
```

**Predict:** one `UPDATE menu SET unit_price_usd = unit_price_usd + 0.25 WHERE category = 'coffee';` changes every coffee row. How many rows will `price_log` hold afterwards? And after a second `UPDATE` with `WHERE category = 'soda'`, which matches nothing?

<details>
<summary>Reveal the result</summary>

Run on DuckDB 2.0.0, on the fresh `menu` and empty `price_log` above, `SELECT COUNT(*) FROM price_log;` after each `UPDATE`:

```text
after the coffee update: 7
after the soda update:   7
```

The first three log rows, by `product_id`: `1 | 3.00 | 3.25`, `2 | 3.50 | 3.75`, `3 | 4.50 | 4.75`.

</details>

*Why:* the trigger ran once for the statement and its transition tables held the seven coffee rows, so seven log rows appeared with no second statement from anyone. The soda update changed nothing, so there was nothing to log.

### 3. The same job in three engines

**Idea.** Every engine has its own syntax for the same rule. Compare the three, and note what each can and cannot do.

**Read only.** SQLite 3.53.1, through Python's `sqlite3` (a fresh `menu` and an empty `price_log`, as above):

```sql
CREATE TRIGGER log_price AFTER UPDATE OF unit_price_usd ON menu
WHEN OLD.unit_price_usd <> NEW.unit_price_usd
BEGIN
  INSERT INTO price_log VALUES (OLD.product_id, OLD.unit_price_usd, NEW.unit_price_usd);
END;
```

**Read only.** PostgreSQL 16: the trigger calls a function written in its own language, PL/pgSQL.

```sql
CREATE FUNCTION log_price_change() RETURNS trigger LANGUAGE plpgsql AS $$
BEGIN
  INSERT INTO price_log (product_id, old_price_usd, new_price_usd)
  VALUES (OLD.product_id, OLD.unit_price_usd, NEW.unit_price_usd);
  RETURN NULL;
END;
$$;

CREATE TRIGGER log_price
AFTER UPDATE OF unit_price_usd ON menu
FOR EACH ROW
WHEN (OLD.unit_price_usd IS DISTINCT FROM NEW.unit_price_usd)
EXECUTE FUNCTION log_price_change();
```

Both logged the same 7 rows for the coffee update.

| | DuckDB 2.0 | SQLite | PostgreSQL |
|---|---|---|---|
| What the trigger runs | one SQL statement | statements between `BEGIN` and `END` | a function, usually PL/pgSQL |
| Per row, per statement | both, with limits: row-level `BEFORE` and row-level `UPDATE` triggers are not supported yet | per row only | both |
| Stored procedures | none: macros (unit 5) | none in its list of statements | `CREATE PROCEDURE` and `CALL` |

A trigger written for one engine is rewritten for the next. That is the first cost.

### 4. Keep a total in sync

**Idea.** A **derived value** is one you can always compute from other rows, such as the total of an order. You can keep it in a table or compute it in a view (S28).

**Predict:** order 1001 has three lines. You add a fourth line, one Americano, to a copy of its lines. What total does the stored table show, and what total does the view show?

**Try it:**

<RunSQL query={`CREATE OR REPLACE TABLE lines_copy AS
SELECT * FROM order_items WHERE order_id = 1001;
CREATE OR REPLACE TABLE totals_copy AS
SELECT i.order_id, SUM(i.quantity * p.unit_price_usd - i.discount_usd) AS total_usd
FROM lines_copy AS i JOIN products AS p ON p.product_id = i.product_id
GROUP BY i.order_id;
CREATE OR REPLACE VIEW totals_view AS
SELECT i.order_id, SUM(i.quantity * p.unit_price_usd - i.discount_usd) AS total_usd
FROM lines_copy AS i JOIN products AS p ON p.product_id = i.product_id
GROUP BY i.order_id;
INSERT INTO lines_copy VALUES (9001, 1001, 2, 1, 0.00);
SELECT 'stored table' AS source, total_usd FROM totals_copy
UNION ALL
SELECT 'view', total_usd FROM totals_view;`} />

Expected: 2 rows, 2 columns. *Why:* the stored table never heard about the new line, so something has to update it whenever a line changes, while the view reads the lines each time it runs. A trigger on `lines_copy` would have rewritten the stored total on every insert, update and delete of a line, which is more work on every change and logic that no one sees when they read the table. The view needs neither.

### 5. A procedure is a saved bundle you call

**Idea.** A **stored procedure** is a named set of statements kept in the database. You run it with `CALL`, passing values, and everything in it can change data. DuckDB has no `CREATE PROCEDURE` in its list of statements. Its nearest tool is a **macro**: a saved expression or query with parameters. The DuckDB documentation says a table macro's expression "can be a SELECT statement", so a macro reads and returns; it does not bundle changes.

**Try it:** two macros, one for a calculation and one for a query, then a macro that tries to change data.

<RunSQL query={`CREATE OR REPLACE MACRO line_amount(qty, price, discount) AS qty * price - discount;
CREATE OR REPLACE MACRO store_sales(s) AS TABLE
  SELECT o.order_id, o.status, SUM(line_amount(i.quantity, p.unit_price_usd, i.discount_usd)) AS amount_usd
  FROM orders AS o
  JOIN order_items AS i ON i.order_id = o.order_id
  JOIN products AS p ON p.product_id = i.product_id
  WHERE o.store_id = s
  GROUP BY o.order_id, o.status;
SELECT COUNT(*) AS orders, ROUND(SUM(amount_usd), 2) AS amount_usd FROM store_sales(3);`} />

Expected: 1 row, 2 columns. *Why:* `store_sales(3)` runs the saved query for store 3. Now the macro that changes data:

<RunSQL query={`CREATE OR REPLACE MACRO log_change(p) AS TABLE
  INSERT INTO price_log SELECT product_id, unit_price_usd, unit_price_usd FROM menu WHERE product_id = p;`} />

Expected: an error saying there is a syntax error at or near "INSERT". *Why:* a macro's body is a query or an expression, not a statement that changes data.

**Read only.** PostgreSQL 16 has procedures. This one bundles the log row and the update, and `CALL` runs both:

```sql
CREATE PROCEDURE change_price(p_id integer, new_price numeric)
LANGUAGE SQL
BEGIN ATOMIC
  INSERT INTO price_log (product_id, old_price_usd, new_price_usd)
  SELECT product_id, unit_price_usd, new_price FROM menu WHERE product_id = p_id;
  UPDATE menu SET unit_price_usd = new_price WHERE product_id = p_id;
END;

CALL change_price(1, 3.50);
```

Run on PostgreSQL 16, with Espresso at 3.00: the log holds `1 | 3.00 | 3.50`, and `menu` holds 3.50. The PostgreSQL documentation: "While a function is called as part of a query or DML command, a procedure is called in isolation using the CALL command." A procedure is run on purpose; a trigger runs whether you remember it or not.

### 6. What they cost

**Idea.** A trigger or procedure moves rules from the queries into the database. That saves repeating them, and it hides them. Each cost below comes from the documentation of the engine named.

| Cost | What the documentation shows |
|---|---|
| A write does more than it says | PostgreSQL: a trigger "can skip the operation for the current row, or change the row being inserted" when it fires before the change |
| Other statements are limited | DuckDB 2.0: `MERGE INTO` "is not supported on tables with triggers" |
| Rules differ by vendor | unit 3: DuckDB, SQLite and PostgreSQL write the same rule three ways |
| Security | PostgreSQL: a trigger runs "with the privileges of users who modify" the table, so who may create one matters |
| Hard to see | the table definition does not show triggers; DuckDB lists them in `duckdb_triggers()` |

An analytics team usually rebuilds its numbers from the raw tables each time, with views and scheduled transformations, so logic in a trigger is a hidden second source of numbers. A transactional system that must log every change, as in unit 2, is where triggers still earn their keep.

<Aside type="tip" title="Remember">

- A trigger is a rule on a table: event, timing (before or after), and granularity (per row or per statement).
- A stored procedure is a saved bundle you `CALL`; DuckDB has macros, which read and return but do not change data.
- A stored total goes stale unless something updates it; a view never does.
- Every engine writes triggers its own way, so they do not move between databases.

**Common trap: "a trigger is free, it just runs."** It runs inside your `INSERT`, `UPDATE` or `DELETE`, in the same transaction, on every change, and nobody reading the table sees it.

</Aside>

CREATE OR REPLACE TABLE deleted_menu AS SELECT * FROM menu WHERE false;

## Check yourself

Without looking back: what are the three parts of a trigger's definition, and what does a macro do that a stored procedure also does?

<details>
<summary>Answer</summary>

Event (`INSERT`, `UPDATE`, `DELETE`), timing (`BEFORE` or `AFTER`) and granularity (per row or per statement). A macro, like a procedure, is a saved, named piece of SQL with parameters that you call by name; unlike a procedure, it only returns a value or rows.

</details>

**Spot the flaw.** A colleague logs a price change by hand, for Latte only, and checks the log: it should hold one row for one change.

<RunSQL query={`CREATE OR REPLACE TABLE menu_b AS

INSERT INTO log_b
SELECT product_id, unit_price_usd, unit_price_usd + 0.50 FROM menu_b;
UPDATE menu_b SET unit_price_usd = unit_price_usd + 0.50 WHERE product_id = 3;
COMMIT;
SELECT COUNT(*) AS log_rows FROM log_b;`} />

Expected from that query: 1 row, 1 column: `16`. What went wrong, and what is the fix?

<Solution>

The `UPDATE` has a `WHERE`, and the `INSERT` that logs it does not: it logged all 16 products, 15 of them with a change that never happened. Two statements, two `WHERE` clauses, and nothing makes them agree. The fix is the same condition on both:

```sql
CREATE OR REPLACE TABLE menu_b AS
SELECT product_id, product_name, unit_price_usd FROM products;
CREATE OR REPLACE TABLE log_b (
  product_id INTEGER,
  old_price_usd DECIMAL(5,2),
  new_price_usd DECIMAL(5,2)
);
BEGIN;
INSERT INTO log_b
SELECT product_id, unit_price_usd, unit_price_usd + 0.50 FROM menu_b WHERE product_id = 3;
UPDATE menu_b SET unit_price_usd = unit_price_usd + 0.50 WHERE product_id = 3;
COMMIT;
SELECT COUNT(*) AS log_rows FROM log_b;
```

Expected: `1`. This is the job a trigger takes over: it reads exactly the rows the statement changed, through `OLD` and `NEW`, so there is no second `WHERE` to get wrong.

</Solution>
