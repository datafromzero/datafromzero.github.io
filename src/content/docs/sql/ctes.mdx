## The question

The owner of the cafes asks:

> Old Town took 729 orders and Harbor only 355. Is Harbor really that much slower?

Harbor opened on April 1, 2026, so the totals do not cover the same days. A fair comparison is the **average day** of
each store. That takes two steps: first the orders of each store on each day, then the average of those daily counts.

| order_day | store_id | orders |
|---|---:|---:|
| 2026-01-01 | 1 | 2 |
| 2026-01-01 | 2 | 2 |
| 2026-01-02 | 1 | 3 |

This is the start of the first step. By the end you will have the second step too: each store's average day, with every
stage checked.

A CTE is written with `WITH name AS (query)`. Later steps follow after a comma, and a last `SELECT` reads the result. The
DuckDB documentation: "Regular (non-recursive) common-table-expressions are essentially views that are limited in scope
to a particular query." and "CTEs can reference each other and can be nested." Each step reads only the steps written
before it.

| In a sheet | In SQL |
|---|---|
| a helper column per step | a CTE per step |
| the column header | the CTE name |
| the next column reads the one before | the next CTE reads the one before |

<details>
<summary>What it replaces (read only: you do not write this yet)</summary>

Without `WITH`, the only way to use one result inside another query is to paste the first query, in parentheses, into the
second:

```sql
SELECT store_id, COUNT(*) AS days, ROUND(AVG(orders), 2) AS avg_orders
FROM (
  SELECT CAST(ordered_at AS DATE) AS order_day, store_id, COUNT(*) AS orders
  FROM orders
  GROUP BY CAST(ordered_at AS DATE), store_id
)
GROUP BY store_id
ORDER BY store_id;
```

This works and returns the same table as the chain below, but you read it from the inside out. It is called a nested
query; *Subqueries and EXISTS* (S23) teaches it. The CTE chain says the same thing top to bottom.

</details>

## Worked example

Question: **what is the average day of each store?** Run the notebook's setup cell, then one cell per step. `ROUND(x, 2)`
keeps two decimals.

1. **Write the first step on its own.**

   ```sql
   SELECT CAST(ordered_at AS DATE) AS order_day, store_id, COUNT(*) AS orders
   FROM orders
   GROUP BY CAST(ordered_at AS DATE), store_id
   ORDER BY order_day, store_id
   LIMIT 5;
   ```

   Expected: 5 rows, 3 columns. *Why:* state the grain first: one row per store per day.

2. **Name it.**

   ```sql
   WITH daily AS (
     SELECT CAST(ordered_at AS DATE) AS order_day, store_id, COUNT(*) AS orders
     FROM orders
     GROUP BY CAST(ordered_at AS DATE), store_id
   )
   SELECT * FROM daily
   ORDER BY order_day, store_id
   LIMIT 5;
   ```

   Expected: 5 rows, 3 columns, the same as step 1. *Excel:* a helper column with a header. *Why:* the step moves into
   `WITH daily AS (...)`, and the last `SELECT` reads `daily` like a table. Sorting and `LIMIT` stay in the last
   `SELECT`.

3. **Check the grain and the row count.**

   ```sql
   WITH daily AS (
     SELECT CAST(ordered_at AS DATE) AS order_day, store_id, COUNT(*) AS orders
     FROM orders
     GROUP BY CAST(ordered_at AS DATE), store_id
   )
   SELECT COUNT(*) AS store_days, SUM(orders) AS orders
   FROM daily;
   ```

   Expected: 1 row, 2 columns: `453` and `1800`. *Why:* `orders` has 1,800 rows and `daily` has 453, one per store per
   day; the daily counts add back up to all 1,800 orders, so no order was lost.

4. **Add the second step.**

   ```sql
   WITH daily AS (
     SELECT CAST(ordered_at AS DATE) AS order_day, store_id, COUNT(*) AS orders
     FROM orders
     GROUP BY CAST(ordered_at AS DATE), store_id
   ),
   average_day AS (
     SELECT store_id, COUNT(*) AS days, ROUND(AVG(orders), 2) AS avg_orders
     FROM daily
     GROUP BY store_id
   )
   SELECT * FROM average_day
   ORDER BY store_id;
   ```

   Expected: 3 rows, 3 columns. *Why:* a comma, then the next name. `average_day` reads `daily`, not `orders`: its grain
   is one row per store, and `days` counts the store-days.

5. **Debug by looking at one step.** Harbor's `days` is smaller than the others. To see why, point the last `SELECT` at
   `daily`:

   ```sql
   WITH daily AS (
     SELECT CAST(ordered_at AS DATE) AS order_day, store_id, COUNT(*) AS orders
     FROM orders
     GROUP BY CAST(ordered_at AS DATE), store_id
   )
   SELECT MIN(order_day) AS first_day, COUNT(*) AS days
   FROM daily
   WHERE store_id = 3;
   ```

   Expected: 1 row, 2 columns: first day `2026-04-01`, `91` days. *Why:* running one CTE at a time shows where a number
   comes from. Harbor was open 91 days, the others 181.

6. **Verify.** A second method, without a CTE:

   ```sql
   SELECT store_id, ROUND(COUNT(*) * 1.0 / COUNT(DISTINCT CAST(ordered_at AS DATE)), 2) AS avg_orders
   FROM orders
   GROUP BY store_id
   ORDER BY store_id;
   ```

   Expected: 3 rows, 2 columns, the same `avg_orders` as step 4: 4.03, 3.96 and 3.90 (the notebook prints 3.9). Answer: Harbor took 355 orders
   against Old Town's 729 because it was open 91 days against 181. The **average day** is 4.03 orders at Old Town, 3.96
   at Campus and 3.90 at Harbor: Harbor is not much slower. Every open day has at least one order at every store
   (`days` equals the days open), so the averages are over all open days.

<details>
<summary>Explain it in your own words: why does `daily` have 453 rows when `orders` has 1,800?</summary>

Each row of `daily` stands for a store on a day, not an order. Several orders of the same store on the same day become
one row, and Harbor has no rows before April. 181 + 181 + 91 days make 453.

</details>

```sql
WITH daily AS (
  SELECT CAST(ordered_at AS DATE) AS order_day, payment_method, COUNT(*) AS orders
  FROM orders
  WHERE status = 'completed'
  GROUP BY CAST(ordered_at AS DATE), payment_method
),
average_day AS (
  SELECT payment_method, COUNT(*) AS days, ROUND(AVG(orders), 2) AS avg_orders
  FROM daily
  GROUP BY payment_method
```

would show 135 days and 1.87, because the canceled order is a cash order on a day with no completed cash order. Here the
average is over days with at least one order of that method, so cash and mobile have fewer days.
