In a sheet you build a long calculation in steps, each in its own helper column, so you can see every step. A query can
do the same. Each query runs in the editor on this page, with the five tables of **cafe-sales**, the invented
three-cafe chain we use from Excel to Python.

## The question

The owner of the cafes asks:

> Old Town took 729 orders and Harbor only 355. Is Harbor really that much slower?

Harbor opened on April 1, 2026, so the totals do not cover the same days. A fair comparison is the **average day** of
each store. That takes two steps: first the orders of each store on each day, then the average of those daily counts.

| order_day | store_id | orders |
|---|---:|---:|
| 2026-01-01 | 1 | 2 |
| 2026-01-01 | 2 | 2 |
| 2026-01-02 | 1 | 3 |

## Learn by doing

Five small steps. Each gives you one idea, then you try it in the editor.

### 1. Write a step, then name it

Write a step as an ordinary query first, and say its **grain**, what one row stands for (S8). A step's grain follows
from its own `GROUP BY`: grouping `orders` by day and store gives one row per store per day.

**Try it:** the step on its own. `LIMIT 5` shows only the top.

<RunSQL query={`SELECT CAST(ordered_at AS DATE) AS order_day, store_id, COUNT(*) AS orders
FROM orders
GROUP BY CAST(ordered_at AS DATE), store_id
ORDER BY order_day, store_id
LIMIT 5;`} />

Expected: 5 rows, 3 columns.

Now give it a name. `WITH daily AS (...)` wraps the step, the rest of the statement can use `daily` like a table, and
the last `SELECT`, with no parentheses, reads it. Only that last result comes back.

The name lasts for this one statement. DuckDB's documentation calls a regular CTE essentially a view (a saved query)
limited in scope to one query.

**Try it:**

<RunSQL query={`WITH daily AS (
  SELECT CAST(ordered_at AS DATE) AS order_day, store_id, COUNT(*) AS orders
  FROM orders
  GROUP BY CAST(ordered_at AS DATE), store_id
)
SELECT * FROM daily
ORDER BY order_day, store_id
LIMIT 5;`} />

Expected: 5 rows, 3 columns, the same as before. *Excel:* a helper column with a header (E10, *Cleaning text with TRIM, LEFT and TEXTSPLIT*). *Why:* the sorting and the
`LIMIT` stay in the last `SELECT`.

### 2. Check each step

After each step, check its row count and that its numbers add back up. A right step loses no rows and counts none twice.

**Try it:**

<RunSQL query={`WITH daily AS (
  SELECT CAST(ordered_at AS DATE) AS order_day, store_id, COUNT(*) AS orders
  FROM orders
  GROUP BY CAST(ordered_at AS DATE), store_id
)
SELECT COUNT(*) AS store_days, SUM(orders) AS orders
FROM daily;`} />

Expected: 1 row, 2 columns: `453` and `1800`. *Why:* `orders` has 1,800 rows and `daily` has 453; the daily counts add back up to all 1,800 orders, so no order was lost.

<details>
<summary>Explain it in your own words: why does <code>daily</code> have 453 rows when <code>orders</code> has 1,800?</summary>

Each row of `daily` stands for a store on a day, not an order. Several orders of the same store on the same day become
one row, and Harbor has no rows before April. 181 + 181 + 91 days make 453.

</details>

### 3. Chain a second step

After a comma, the next step is defined the same way, and it reads the step before it by name in its `FROM`. One `WITH`
opens the chain, commas separate the steps, and there is no comma after the last one.

**Try it.** `ROUND(x, 2)` keeps two decimals.

<RunSQL query={`WITH daily AS (
  SELECT CAST(ordered_at AS DATE) AS order_day, store_id, COUNT(*) AS orders
  FROM orders
  GROUP BY CAST(ordered_at AS DATE), store_id
),
average_day AS (
  SELECT store_id, COUNT(*) AS days, ROUND(AVG(orders), 2) AS avg_orders
  FROM daily
  GROUP BY store_id
)
SELECT * FROM average_day
ORDER BY store_id;`} />

Expected: 3 rows, 3 columns. *Excel:* the next column reads the one before it. *Why:* `average_day` reads `daily`, not
`orders`; its grain is one row per store, and `days` counts the store-days. The picture shows the chain with the grain
and row count of each step.

<details>
<summary>What it replaces (read only: you do not write this yet)</summary>

Without `WITH`, one way to use one result inside another query is to paste the first query, in parentheses, into the
second:

```sql
SELECT store_id, COUNT(*) AS days, ROUND(AVG(orders), 2) AS avg_orders
FROM (
  SELECT CAST(ordered_at AS DATE) AS order_day, store_id, COUNT(*) AS orders
  FROM orders
  GROUP BY CAST(ordered_at AS DATE), store_id
)
GROUP BY store_id
ORDER BY store_id;
```

This works and returns the same table, but you read it from the inside out. It is called a nested query; *Subqueries and
EXISTS* (S24) teaches it. The chain says the same thing top to bottom.

</details>

### 4. Debug by looking at one step

When a number looks odd, point the last `SELECT` at one step and run it. Harbor's `days` in unit 3 are smaller than the
others.

**Try it:**

<RunSQL query={`WITH daily AS (
  SELECT CAST(ordered_at AS DATE) AS order_day, store_id, COUNT(*) AS orders
  FROM orders
  GROUP BY CAST(ordered_at AS DATE), store_id
)
SELECT MIN(order_day) AS first_day, COUNT(*) AS days
FROM daily
WHERE store_id = 3;`} />

Expected: 1 row, 2 columns: first day `2026-04-01`, `91` days. *Why:* Harbor was open 91 days, the others 181.

### 5. Check the answer

A second method, without a CTE, must agree with the chain.

**Try it:**

<RunSQL query={`SELECT store_id, ROUND(COUNT(*) * 1.0 / COUNT(DISTINCT CAST(ordered_at AS DATE)), 2) AS avg_orders
FROM orders
GROUP BY store_id
ORDER BY store_id;`} />

Expected: 3 rows, 2 columns, the same `avg_orders` as unit 3: 4.03, 3.96 and 3.9, which is 3.90. Answer: Harbor
took 355 orders against Old Town's 729 because it was open 91 days against 181. The **average day** is 4.03 orders at
Old Town, 3.96 at Campus and 3.90 at Harbor: Harbor is not much slower. Every open day has at least one order at every
store (`days` equals the days open), so the averages are over all open days.

<Aside type="tip" title="Remember">

- `WITH name AS (query)` names a step; the rest of the statement uses `name` like a table.
- One `WITH`, commas between the steps, no comma after the last.
- A step's grain comes from its own `GROUP BY`. Check each step's row count.
- To debug, point the last `SELECT` at one step.

**Common trap: "a CTE is a table the database keeps."** It lives for one statement. Run `SELECT * FROM daily;` on its
own and you get an error: the table does not exist. To keep a result you save it: *Saving a query as a view* (S29) and
*Creating tables and constraints* (S33) show how.

</Aside>

**Count the busy days of each store.** A busy day is a store-day with 6 or more orders. Expected: 3 rows, 2 columns (the
store and its number of busy days).

The first steps are done for you: the `daily` step is the one from unit 1, and the second step counts the store-days of
each store. Now finish it: add the line that keeps only the busy store-days.

<RunSQL query={`WITH daily AS (
  SELECT CAST(ordered_at AS DATE) AS order_day, store_id, COUNT(*) AS orders
  FROM orders
  GROUP BY CAST(ordered_at AS DATE), store_id
),
busy_days AS (
  SELECT store_id, COUNT(*) AS busy_days
  FROM daily
  GROUP BY store_id
)
SELECT * FROM busy_days
ORDER BY store_id;`} />

<details>
<summary>Hint</summary>

Each row of `daily` is a store-day, with its `orders`. Filter the rows first, then group, as in *How a query runs: the
order of the clauses* (S12). Does your new line go before or after `GROUP BY`?

</details>

<details>
<summary>Half-solution</summary>

```sql
WHERE orders ...
```

</details>

<Solution>

```sql
WITH daily AS (
  SELECT CAST(ordered_at AS DATE) AS order_day, store_id, COUNT(*) AS orders
  FROM orders
  GROUP BY CAST(ordered_at AS DATE), store_id
),
busy_days AS (
  SELECT store_id, COUNT(*) AS busy_days
  FROM daily
  WHERE orders >= 6
  GROUP BY store_id
)
SELECT * FROM busy_days
ORDER BY store_id;
```

Store 1 has 22 busy days, store 2 has 17 and store 3 has 14. Harbor's 14 came in only 91 days.

</Solution>

## On your own

<Exercise id="sql-ctes-2">

**What is the average day for each payment method, completed orders only?**

Before you run anything, write one sentence as a comment in the editor: the grain of each step. Then build two CTEs: the
first counts completed orders for each payment method on each day, the second averages them for each payment method.

Expected shape, to check your sentence against: the final query returns 3 rows, 3 columns (the method, the number of days
and the average). The first step has 486 rows.

<RunSQL query={`-- Write your query here, then press Run.`} />

<details>
<summary>Hint</summary>

Copy the two steps of unit 3, swap `store_id` for `payment_method`, and add the `WHERE` on `status` to the first step.
Run the first step alone to check that it has 486 rows.

</details>

<details>
<summary>Half-solution</summary>

Expected output: *"Daily: one row per payment method per day. Average day: three rows, one per method, with the number of days and the average orders on those days."*

</details>

<Solution>

```sql
WITH daily AS (
  SELECT CAST(ordered_at AS DATE) AS order_day, payment_method, COUNT(*) AS orders
  FROM orders
  WHERE status = 'completed'
  GROUP BY CAST(ordered_at AS DATE), payment_method
),
average_day AS (
  SELECT payment_method, COUNT(*) AS days, ROUND(AVG(orders), 2) AS avg_orders
  FROM daily
  GROUP BY payment_method
)
SELECT * FROM average_day
ORDER BY avg_orders DESC;
```

Card averages 5.56 orders over 180 days, mobile 3.17 over 172 days and cash 1.88 over 134 days. Without the `WHERE`, cash
would show 135 days and 1.87, because the canceled order is a cash order on a day with no completed cash order. Here the
average is over days with at least one order of that method, so cash and mobile have fewer days.

</Solution>

</Exercise>
