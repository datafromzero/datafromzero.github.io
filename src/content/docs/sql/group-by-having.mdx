`GROUP BY` sorts the rows into buckets by the value of a column, or of several columns together. Then every aggregate
in `SELECT` works inside its own bucket, and the result has one row per bucket. What one result row means is the
**grain** of the result. Say it in words before you write the query: *one row per store*. A bucket exists only if at
least one row falls into it. Every column in `SELECT` is either in `GROUP BY` or inside an aggregate.

`WHERE` and `HAVING` both filter, but at different moments. `WHERE` keeps or drops **rows**, before grouping. `HAVING`
keeps or drops **groups**, after the counting. So only `HAVING` can test `COUNT(*)`. The engine works through the
clauses in this order: `FROM` first, then `WHERE`, then `GROUP BY`, then `HAVING`, then the `SELECT` list, and `ORDER BY`
and `LIMIT` at the very end. The DuckDB documentation says that `FROM` is where a query starts, that `WHERE` comes
right after it, that `HAVING` comes after the grouping, and that `ORDER BY` and `LIMIT` are applied at the very end. The
lesson *How a query runs: the order of the clauses* (S12) goes deeper.

| SQL | In the PivotTable (E15) |
|---|---|
| `GROUP BY store_id` | `store` in Rows |
| `GROUP BY store_id, payment_method` | `store` in Rows and `payment_method` in Columns, as a list instead of a grid |
| `COUNT(*)` | a count in Values |
| `WHERE status = 'completed'` | `status` in Filters, set to completed |

## Worked example

Question: **how many orders did each cafe take, how did customers pay, and which cafes passed 500 completed orders?**
Run the notebook's setup cell, then one cell per step. Each step starts with the grain and shows the shape of the
result to expect.

1. **Group by one column.** Grain: *one row per store*.

   ```sql
   SELECT store_id, COUNT(*) AS orders
   FROM orders
   GROUP BY store_id
   ORDER BY store_id;
   ```

   Expected: 3 rows, 2 columns: store 1 has 729 orders, store 2 has 716 and store 3 has 355. *Excel:* a PivotTable
   with `store` in Rows. *Why:* there are three stores, so there are three groups and three rows. The counts add up to
   1,800, every order, the canceled one included.

2. **Group by two columns.** Grain: *one row per store and payment method*. Before you run it: how many rows?

   ```sql
   SELECT store_id, payment_method, COUNT(*) AS orders
   FROM orders
   GROUP BY store_id, payment_method
   ORDER BY store_id, payment_method;
   ```

   Expected: 3 columns. *Excel:* `payment_method` in Columns, read as a list. *Why:* a group is one combination of
   the two values: 3 stores times 3 methods is 9, because every store has orders in all three methods. A combination
   with no orders would not appear at all. Store 1 reads card 421, cash 91, mobile 217.

3. **Filter rows before grouping with `WHERE`.** Grain: *one row per store, completed orders only*.

   ```sql
   SELECT store_id, COUNT(*) AS orders
   FROM orders
   WHERE status = 'completed'
   GROUP BY store_id
   ORDER BY store_id;
   ```

   Expected: 3 rows, 2 columns: 729, 715 and 355. *Excel:* `status` in Filters, set to completed. *Why:* `WHERE` runs
   before the grouping, so the canceled order 1461 never reaches a bucket. Campus, store 2, goes from 716 to 715.

4. **Filter groups after counting with `HAVING`.**

   ```sql
   SELECT store_id, COUNT(*) AS orders
   FROM orders
   WHERE status = 'completed'
   GROUP BY store_id
   HAVING COUNT(*) >= 500
   ORDER BY store_id;
   ```

   Expected: 2 rows, 2 columns: store 1 with 729 and store 2 with 715. *Why:* `HAVING` looks at one row per group,
   after the count exists. Harbor's group has 355, so the whole group is dropped. `WHERE` could not do this, because
   when it runs there is no count yet. This answers the owner: Old Town and Campus.

5. **Verify with a second route.**

   ```sql
   SELECT COUNT(*) AS completed_orders FROM orders WHERE status = 'completed';
   ```

   Expected: 1 row, 1 column: `1799`. *Why:* it equals 729 + 715 + 355 from step 3, and the 1,799 completed orders
   the till system reported in *A cleaning workflow you can defend* (E13). The groups lost no rows and counted none twice.

<details>
<summary>Explain it in your own words: why can step 4 drop Harbor, when step 3 could only drop single orders?</summary>

`WHERE` sees one order at a time and has no idea how many orders a store has. `HAVING` runs after the grouping, so it
sees the finished count per store and can drop a whole store at once.

</details>

<Exercise id="sql-group-by-having-3">

**Spot the flaw.** A colleague wants the stores with more than 500 orders and writes this. It gives an error, not a table:

```sql
SELECT store_id, COUNT(*) AS orders
FROM orders
WHERE COUNT(*) > 500
GROUP BY store_id;
```

Expected: an error that starts with `Binder Error`. Read it, then fix the query.

<Solution>

The first line of the error reads `Binder Error: WHERE clause cannot contain aggregates!`. `WHERE` runs right after
`FROM`, before any group exists, so there is no count to compare. A condition on a count belongs to `HAVING`:

```sql
SELECT store_id, COUNT(*) AS orders
FROM orders
GROUP BY store_id
HAVING COUNT(*) > 500;
```

Expected: 2 rows, 2 columns: store 1 with 729 orders and store 2 with 716 (all orders, canceled included). Harbor, with
355, is dropped.

</Solution>

</Exercise>
