## The question

The owner is redoing the menu board and asks:

> Which five items cost the most? Show the item, its category and its price, most expensive first. Where two items cost
> the same, list them in alphabetical order.

In E5 you would sort the price list and read off the top rows. Here you do the same in SQL, and you decide in the query
what happens when two prices are equal. Four of the 16 rows of the `products` table, in table order:

| product_id | product_name | category | unit_price_usd |
|---:|---|---|---:|
| 3 | Latte | coffee | 4.50 |
| 4 | Cappuccino | coffee | 4.50 |
| 6 | Cold Brew | coffee | 4.75 |
| 8 | Chai Latte | tea | 4.75 |

Two pairs share a price. By the end you will have put the five most expensive items on the board, with no doubt about
which item takes the fifth place.

## How it works

`SELECT` chooses and names the columns of the result, `ORDER BY` puts its rows in order, and `LIMIT` keeps only the
first rows of that order. Together they turn a stored table into a short, sorted **result table**. Logically the engine
runs them in this order, and the second picture above follows it from top to bottom:

1. `FROM` starts with every row of the table.
2. `SELECT` builds the result's columns: the ones you name, each under the name you give it with `AS`.
3. `ORDER BY` sorts the rows by the first sort column; rows that tie there are compared on the second, and so on.
4. `LIMIT 5` keeps the first five rows of the sorted list and drops the rest.

In the first picture above, the dashed line is where that cut falls on the sorted list. The rules:

- DuckDB's SELECT page calls `ORDER BY` and `LIMIT` output modifiers and says they apply "at the very end of the query".
  So `LIMIT` cuts the sorted list, never the table.
- A direction belongs to the one sort column it follows, because DuckDB lets each expression in `ORDER BY` carry its own
  `ASC` or `DESC`.
- Another sort column is the only thing that settles a tie. Two rows that tie on every sort column have no promised
  order.
- A `LIMIT` with no `ORDER BY` has no promised answer: DuckDB's page says the results "might not be deterministic".
- A name made with `AS` belongs to the result only. The stored table keeps its own column names, so the next query
  starts from those.

**Excel.** In *Tables, sorting and filtering* (E5), **Add Level** is, in Microsoft Support's words, "another column to
sort by": the second sort column of `ORDER BY`. A sheet has no step that cuts the list. You read the top rows yourself,
and `LIMIT` keeps them for you.

**A common misconception: "`LIMIT 2` takes the first two rows of the table, and `ORDER BY` then sorts those."**
`SELECT product_name FROM products ORDER BY product_name LIMIT 2` returns Americano and Avocado Toast, the first two names
of the whole menu in alphabetical order. A cut made before the sort would return Americano and Espresso, the first two rows
as stored. `LIMIT` runs last, so the sort sees every row.

The new pieces map to what you do in a sheet:

| SQL | Reads as | In Excel |
|---|---|---|
| `column AS name` | call this result column `name` | type a new header over the old one |
| `FROM products AS p` | call this table `p`, in this query only | no equivalent |
| `ORDER BY a DESC, b` | sort by `a`, then by `b` inside equal `a` | **Data > Sort**, then **Add Level** (E5) |
| `LIMIT 5` | keep only the first five rows of the result | read the top five rows after sorting |

## Worked example

Question: **which five items cost the most, most expensive first, with ties in alphabetical order?** Run the notebook's
setup cell, then one cell per step. Each step names the shape of the result to expect.

1. **Name the columns you want, and rename them.**

   ```sql
   SELECT product_name AS item, category, unit_price_usd AS price_usd
   FROM products;
   ```

   Read it: *show the name as `item`, the category, and the price as `price_usd`, from products*. Expected: 16 rows,
   3 columns, headed `item`, `category` and `price_usd`. *Excel:* type new headers. *Why:* `SELECT *` shows whatever the table holds today, so if someone adds
   a column, your result changes. Naming the columns pins it. A new name with spaces goes in double quotes
   (`AS "Price USD"`); single quotes are for text values, as in S1.

2. **Give the table a short name.**

   ```sql
   SELECT p.product_name, p.unit_price_usd
   FROM products AS p;
   ```

   Read it: *call the products table `p`, and take its name and price*. Expected: 16 rows, 2 columns. *Why:* `p.product_name`
   says which table a column comes from. With one table you never need it. In later lessons a query reads two
   tables, and the short names tell their columns apart. DuckDB's documentation says a table joined to itself must be
   aliased.

3. **Sort by one column.**

   ```sql
   SELECT product_name AS item, unit_price_usd AS price_usd
   FROM products
   ORDER BY price_usd DESC;
   ```

   Expected: 16 rows, 2 columns, highest price first. *Excel:* sort largest to smallest. *Why:* `ORDER BY` accepts the new name
   `price_usd`. Look at the rows: two pairs of items share a price, and this query does not say which item of a pair comes
   first. Nothing in it decides.

4. **Add a tie-breaker.**

   ```sql
   SELECT product_name AS item, unit_price_usd AS price_usd
   FROM products
   ORDER BY price_usd DESC, item;
   ```

   Expected: 16 rows, 2 columns. *Excel:* a second sort level. *Why:* each column gets its own direction: `DESC` belongs to `price_usd`, and `item` has none, so it
   sorts ascending, A to Z. Now the order is the same on every run.

5. **Cut the list.**

   ```sql
   SELECT product_name AS item, category, unit_price_usd AS price_usd
   FROM products
   ORDER BY price_usd DESC, item
   LIMIT 5;
   ```

   Expected: 5 rows, 3 columns: Turkey Sandwich, Avocado Toast, Pumpkin Spice Latte, Mocha and Chai Latte. *Excel:* sort,
   then read the top five rows. *Why:* `LIMIT` cuts after the sort. Place 5 is a tie at 4.75, and the tie-breaker
   gives it to Chai Latte, not Cold Brew. That answers the owner's
   question: **Turkey Sandwich, Avocado Toast, Pumpkin Spice Latte, Mocha and Chai Latte**.

6. **Use the same pattern on another table: the latest five orders.**

   ```sql
   SELECT order_id, ordered_at
   FROM orders
   ORDER BY ordered_at DESC, order_id DESC
   LIMIT 5;
   ```

   Expected: 5 rows, 2 columns, the newest order first. *Excel:* sort the order list newest first. *Why:* the
   pattern is the same: sort, tie-breaker, cut. The tie-breaker matters here too: the 1,800 orders carry only 1,788
   different timestamps, so a few orders share a minute, and `order_id` settles them.

7. **Verify.** Compare the five rows of step 5 with the first five rows you get when you rerun step 4: they must be the
   same. Then check that `LIMIT` cut the result and not the table:

   ```sql
   SELECT COUNT(*) AS items FROM products;
   ```

   Expected: 1 row, 1 column: `16`. Two checks, one answer.

<details>
<summary>Explain it in your own words: why does step 5 still need the tie-breaker when step 3 already sorted by price?</summary>

Sorting by price leaves the order of equal prices undecided, and place 5 is a tie. Without a second sort column, either
Chai Latte or Cold Brew could take it. The tie-breaker makes the result the same every time.

</details>
