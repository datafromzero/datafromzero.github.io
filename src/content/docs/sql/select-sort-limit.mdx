This lesson builds on *From a spreadsheet to SQL* (S1), where you picked columns, sorted with `DESC` and cut a result
with `LIMIT`. Here you control all three. Press **Run** under any query on this page; the tables are **cafe-sales**
again.

## The question

The owner is redoing the menu board and asks:

> Which five items cost the most? Show the item, its category and its price, most expensive first. Where two items cost
> the same, list them in alphabetical order.

In E5 you would sort the price list and read off the top rows. Here you do the same in SQL, and you decide in the query
what happens when two prices are equal. Four of the 16 rows of the `products` table, in table order:

| product_id | product_name | category | unit_price_usd |
|---:|---|---|---:|
| 3 | Latte | coffee | 4.50 |
| 4 | Cappuccino | coffee | 4.50 |
| 6 | Cold Brew | coffee | 4.75 |
| 8 | Chai Latte | tea | 4.75 |

Two pairs share a price. Keep an eye on them.

## Warm-up

Answer from memory before you open anything. Then click to check.

1. In *From a spreadsheet to SQL* (S1) you listed bakery items. Write a query that shows `product_name` and
   `unit_price_usd` for the bakery items, highest price first.

   <details>
   <summary>Answer</summary>

   ```sql
   SELECT product_name, unit_price_usd
   FROM products
   WHERE category = 'bakery'
   ORDER BY unit_price_usd DESC;
   ```

   </details>

2. In Excel or Google Sheets (*Tables, sorting and filtering*, E5), how do you sort a list by `category` and then, inside
   each category, by price?

   <details>
   <summary>Answer</summary>

   Open **Data > Sort**, then **Add Level** for the second column (in Google Sheets open the sort options in the
   **Data** menu and choose **Add another sort column**).

   </details>

## The big idea

`SELECT` chooses and names the columns, `ORDER BY` puts the rows in order, and `LIMIT` keeps only the first rows of that
order, so together they turn a stored table into a short, sorted **result table**.

## Learn by doing

Five small steps. Press Run under each query. Each one works on its own, so you can come back to any step.

### 1. Name things with AS

`AS` gives something a new name. `product_name AS item` calls the result column `item`, and `FROM products AS p` calls
the table `p`, for this query only. The names belong to the result: the stored table keeps its own column names, so the
next query starts from those.

**Try it**:

<RunSQL query={`SELECT product_name AS item, category, unit_price_usd AS price_usd
FROM products;`} />

Read it: *show the name as `item`, the category, and the price as `price_usd`, from products*. Expected: 16 rows,
3 columns, headed `item`, `category` and `price_usd`. *Excel:* type new headers.

*Why:* `SELECT *` shows whatever the table holds today, so if someone adds a column, your result changes. Naming the
columns pins it. A new name with spaces goes in double quotes (`AS "Price USD"`); single quotes are for text values, as in S1.

**Try it.** Now the table gets a short name:

<RunSQL query={`SELECT p.product_name, p.unit_price_usd
FROM products AS p;`} />

Read it: *call the products table `p`, and take its name and price*. Expected: 16 rows, 2 columns.

*Why:* `p.product_name` says which table a column comes from. With one table you never need it. In later lessons a query
reads two tables, and the short names tell their columns apart. DuckDB's documentation says a table joined to itself must
be aliased.

### 2. Sort with ORDER BY

`ORDER BY` sorts the rows of the result. `DESC` after a column means highest first. With neither `ASC` nor `DESC`, the
default is ascending, lowest first.

**Try it**:

<RunSQL query={`SELECT product_name AS item, unit_price_usd AS price_usd
FROM products
ORDER BY price_usd DESC;`} />

Expected: 16 rows, 2 columns, highest price first. *Excel:* sort largest to smallest.

*Why:* `ORDER BY` accepts the new name `price_usd`. Look at the rows: two pairs of items share a price, and this query does
not say which item of a pair comes first. Nothing in it decides.

### 3. Settle ties with a second column

Rows that **tie** have equal values in the sort column. Add a second sort column, a **tie-breaker**, and SQL compares the
tied rows on it, then on a third, and so on. Each sort column carries its own direction: `DESC` belongs to the one column it follows.
If rows tie on every sort column, your query does not say their order.

**Try it.** Before you run it: at 4.75, which item comes first?

<RunSQL query={`SELECT product_name AS item, unit_price_usd AS price_usd
FROM products
ORDER BY price_usd DESC, item;`} />

Expected: 16 rows, 2 columns. *Excel:* a second sort level. Microsoft Support calls **Add Level** "another column to sort
by".

*Why:* `item` has no direction, so it sorts ascending, A to Z. Now the order is the same on every run.

### 4. Cut with LIMIT

`LIMIT 5` keeps the first five rows of the sorted list and drops the rest. DuckDB's SELECT page calls `ORDER BY` and
`LIMIT` output modifiers and says they apply "at the very end of the query", so `LIMIT` cuts the sorted list, never the
table. A `LIMIT` with no `ORDER BY` has no promised answer: DuckDB's page says the results "might not be deterministic".

**Try it**:

<RunSQL query={`SELECT product_name AS item, category, unit_price_usd AS price_usd
FROM products
ORDER BY price_usd DESC, item
LIMIT 5;`} />

Expected: 5 rows, 3 columns: Turkey Sandwich, Avocado Toast, Pumpkin Spice Latte, Mocha and Chai Latte. *Excel:* sort,
then read the top five rows. That answers the owner's question: **Turkey Sandwich, Avocado Toast, Pumpkin Spice Latte,
Mocha and Chai Latte**.

*Why:* Chai Latte comes before Cold Brew, A to Z. The dashed line in the first picture is where the cut falls.

### 5. The same pattern, and a check

The pattern works on any table: sort, tie-breaker, cut. Here are the latest five orders.

**Try it**:

<RunSQL query={`SELECT order_id, ordered_at
FROM orders
ORDER BY ordered_at DESC, order_id DESC
LIMIT 5;`} />

Expected: 5 rows, 2 columns, the newest order first. *Excel:* sort the order list newest first.

*Why:* the tie-breaker matters here too: the 1,800 orders carry only 1,788 different timestamps, so a few orders share a
minute, and `order_id` settles them.

Now check the menu answer two ways. Run the unit 3 query again: its first five items must be the same as the five items of
unit 4. Then check that `LIMIT` cut the result and not the table:

<RunSQL query={`SELECT COUNT(*) AS items FROM products;`} />

Expected: 1 row, 1 column: `16`. Two checks, one answer.

<Aside type="tip" title="Remember">

- `SELECT` names the columns (`AS` renames them), `ORDER BY` sorts, and `LIMIT` cuts last.
- Each sort column has its own direction, and ascending is the default.
- Add a second sort column so tied rows have a fixed order.
- `LIMIT` cuts the sorted list, never the table; with no `ORDER BY` it has no promised answer.
- A name made with `AS` belongs to the result only.

**Common trap: "`LIMIT 2` takes the first two rows of the table, and `ORDER BY` then sorts those."**
`SELECT product_name FROM products ORDER BY product_name LIMIT 2` returns Americano and Avocado Toast, the first two names
of the whole menu in alphabetical order. A cut made before the sort would return Americano and Espresso, the first two rows
as stored. `LIMIT` runs last, so the sort sees every row.

</Aside>
