## How it works

An **outer join** is a join that also returns the rows that found no partner. Conceptually, it builds the joined table
as in *INNER JOIN: pairing rows on a key* (S19), then adds those unpaired rows back:

1. For each row of the left table (the one written before `JOIN`), find the rows of the right table for which `ON` is
   true. Every match is one joined row.
2. A left row with no match is kept, as one row whose columns from the right table are all `NULL`. In the first
   picture above, customers 140 and 147 come out this way.
3. `RIGHT` and `FULL` do the same for the right table's unpaired rows. A `LEFT` join drops them.
4. Only then does `WHERE` run, on the finished rows, the padded ones included (*How a query runs: the order of the
   clauses*, S12).

The rules:

- Each join is a policy about unpaired rows, as the second picture shows. `INNER` keeps neither side's, `LEFT` keeps
  the left table's, `RIGHT` the right table's and `FULL` both. Every row of a kept side appears at least once.
- `ON` decides which rows pair. `WHERE` only filters the finished rows, and it sees the `NULL`s of the padded ones.
- To list the rows of one table with no partner in another, keep the unpaired rows: after a `LEFT JOIN`, the rows where
  a column that is never empty on a real right-table row, such as its primary key, is `NULL`. Test it with `IS NULL`,
  never `= NULL` (S4).
- DuckDB also has `ANTI JOIN` (the left rows with no match) and `SEMI JOIN` (the left rows with at least one). Neither
  returns more rows than the left table has.

**Excel.** When `XLOOKUP` finds nothing (E8, *Bring in a value by key with XLOOKUP*), the row stays and shows `#N/A`,
or the text you gave for that case. A `LEFT JOIN` does the same with `NULL`.

**A common misconception: "`NOT IN` is just another way to write an anti join."** DuckDB's page says an anti join has
the logic of `NOT IN`, except that it ignores `NULL` values from the right table. That exception matters here: the
customer ids of `orders` include a `NULL` (the walk-in order 1335), and a comparison with `NULL` is never true, so a
`NOT IN` over those ids gives wrong results, although some customers never ordered. *Subqueries and EXISTS* (S23)
goes further.

## Worked example

Question: **which customers have never ordered, and which have no completed order?** Run the notebook's setup cell, then
one cell per step. Each step gives the shape of the result to expect. Counts cover all 1,800 orders, the canceled one
included, unless a step says otherwise, and count rows, not dollars, so order 2075 does not matter.

1. **Count what an inner join keeps.**

   ```sql
   SELECT COUNT(*) AS joined_rows,
          COUNT(DISTINCT c.customer_id) AS customers_paired
   FROM customers AS c
   INNER JOIN orders AS o ON o.customer_id = c.customer_id;
   ```

   Expected: 1 row, 2 columns. *Why:* **1799** rows, the orders that name a customer (S19), and **145** customers. The
   other 5 of the 150 pair with nothing, so the inner join dropped them without a word.

2. **Keep everyone with LEFT JOIN.** Before you run it: how many rows?

   ```sql
   SELECT COUNT(*) AS joined_rows,
          COUNT(o.order_id) AS paired_rows,
          COUNT(DISTINCT c.customer_id) AS customers
   FROM customers AS c
   LEFT JOIN orders AS o ON o.customer_id = c.customer_id;
   ```

   Expected: 1 row, 3 columns. *Why:* **1804** rows: the 1,799 pairs plus one row for each of the 5 customers with no
   order. `COUNT(o.order_id)` skips `NULL` (S7), so it counts only the pairs. **150** customers: none lost. Order 1335
   is not here, because `customers` is the left table.

3. **See the NULLs.**

   ```sql
   SELECT c.customer_id, c.loyalty_tier, o.order_id, o.status
   FROM customers AS c
   LEFT JOIN orders AS o ON o.customer_id = c.customer_id
   WHERE c.customer_id IN (42, 140, 141, 147)
   ORDER BY c.customer_id, o.order_id;
   ```

   Expected: 5 rows, 4 columns. *Why:* customer 141 has two orders and so two rows. Customers 140 and 147 have one row
   each, with `NULL` in `order_id` and `status`. Customer 42's only order, the canceled order 1461, pairs normally.

4. **Keep only the unpaired rows: the anti-join.**

   ```sql
   SELECT c.customer_id, c.signup_date, c.loyalty_tier
   FROM customers AS c
   LEFT JOIN orders AS o ON o.customer_id = c.customer_id
   WHERE o.order_id IS NULL
   ORDER BY c.customer_id;
   ```

   Expected: 3 columns. *Why:* **5** rows: customers 140, 147, 148, 149 and 150, who all signed up between June 10 and
   June 26. That answers the first question.

5. **Verify with a second route.**

   ```sql
   SELECT c.customer_id
   FROM customers AS c
   ANTI JOIN orders AS o ON o.customer_id = c.customer_id
   ORDER BY c.customer_id;
   ```

   Expected: 1 column, the same customers as step 4. *Why:* a second route to the same list, with no `NULL` test to
   write. The arithmetic agrees: S8 counted 145 customers who ordered, and 150 − 145 = 5.

6. **The tempting way to ask about completed orders.**

   ```sql
   SELECT COUNT(*) AS joined_rows,
          COUNT(DISTINCT c.customer_id) AS customers
   FROM customers AS c
   LEFT JOIN orders AS o ON o.customer_id = c.customer_id
   WHERE o.status = 'completed';
   ```

   Expected: 1 row, 2 columns. *Why:* **1798** rows and **144** customers. The 5 customers with no order are gone,
   and so is customer 42. On an unpaired row `o.status` is `NULL`, and `NULL = 'completed'` is not true, so the row
   leaves. The LEFT JOIN has become an inner join.

7. **Put the condition in `ON`.** Before you run it: how many customers have no completed order?

   ```sql
   SELECT c.customer_id
   FROM customers AS c
   LEFT JOIN orders AS o
          ON o.customer_id = c.customer_id AND o.status = 'completed'
   WHERE o.order_id IS NULL
   ORDER BY c.customer_id;
   ```

   Expected: 1 column. *Why:* **6** customers: the five from step 4, and customer 42, whose only order was canceled.
   Now `status` only decides who pairs, and customer 42 stays unpaired. "Never ordered" gives 5 and "no completed
   order" gives 6: say which question you answer.

8. **Check the picture.** Run step 2's count with `RIGHT JOIN` and with `FULL JOIN` in place of `LEFT JOIN`.

   ```sql
   SELECT COUNT(*) AS right_rows
   FROM customers AS c
   RIGHT JOIN orders AS o ON o.customer_id = c.customer_id;
   ```

   ```sql
   SELECT COUNT(*) AS full_rows
   FROM customers AS c
   FULL JOIN orders AS o ON o.customer_id = c.customer_id;
   ```

   Expected: 1 row, 1 column each. *Why:* **1800** and **1805**, as in the picture. `RIGHT` keeps every order, with
   order 1335 paired to nobody. `FULL` keeps all three kinds of rows: 1,799 + 5 + 1.

<details>
<summary>Explain it in your own words: why does the WHERE in step 6 lose the five customers, while the same condition in ON keeps them?</summary>

`WHERE` runs on the joined rows, and an unpaired row has `NULL` in every column of `orders`, so a test on `o.status`
cannot be true for it. In `ON` the condition only decides which orders pair. A customer with no pairing order still
comes out once, with `NULL`s.

</details>

```sql
LEFT JOIN orders AS o
       ON o.store_id = s.store_id
      AND o.ordered_at >= DATE '2026-01-01'
      AND o.ordered_at < DATE '2026-02-01'
GROUP BY s.store_name
ORDER BY s.store_name;
```

The result is Campus 114, Harbor 0 and Old Town 128. Harbor opened on April 1, so it has no January orders, and it still
appears. 114 + 128 = 242, the January order count in E21 (no January order was canceled).

The dates belong in `ON`: in `WHERE`, Harbor's `NULL` dates would drop its row, and the answer would show two stores.
`COUNT(o.order_id)` gives Harbor 0, because it skips `NULL`; `COUNT(*)` would give 1, counting Harbor's unpaired row.

</Solution>

</Exercise>

## Check yourself

Without looking back: what do INNER, LEFT, RIGHT and FULL joins do with unpaired rows, and how do you list the rows of
one table that have no partner in another?

<details>
<summary>Answer</summary>

INNER drops unpaired rows from both tables. LEFT keeps those of the left table, RIGHT those of the right table, FULL
those of both, with `NULL` in the other table's columns. To list rows with no partner: `LEFT JOIN`, then `WHERE` the
right table's key `IS NULL`.

</details>

<Exercise id="sql-left-join-anti-join-3">

**Spot the flaw.** A colleague wants the customers with no completed order and runs this:

```sql
SELECT c.customer_id
FROM customers AS c
LEFT JOIN orders AS o ON o.customer_id = c.customer_id
WHERE o.status <> 'completed';
```

Expected from that query: 1 row, 1 column: `42`. The colleague reports "only customer 42". What went wrong, and what is the right
query?

<Solution>

The right answer is 6 customers. The five who never ordered have `NULL` in `o.status`, and `NULL <> 'completed'` is not
true, so `WHERE` drops them. Only customer 42, whose canceled order has a real status, survives. Put the condition in
`ON` and test the key for `NULL`, as in step 7:

```sql
SELECT c.customer_id
FROM customers AS c
LEFT JOIN orders AS o
       ON o.customer_id = c.customer_id AND o.status = 'completed'
WHERE o.order_id IS NULL
ORDER BY c.customer_id;
```

Expected: 6 rows, 1 column: 42, 140, 147, 148, 149 and 150.

</Solution>

</Exercise>
