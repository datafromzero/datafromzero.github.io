## The question

The owner of the cafes asks:

> An assistant wrote me a query for the average order value of each store. It says Old Town 6.84, Campus 6.90 and
> Harbor 7.14. Someone told me last month it was about 12. Can I trust the query?

The draft ran without an error and returned this:

| store_name | orders | avg_order_value |
|---|---:|---:|
| Campus | 1304 | 6.9 |
| Harbor | 645 | 7.14 |
| Old Town | 1337 | 6.84 |

A table is not a verdict.

## Warm-up

From memory first, then click to check.

1. In *Join fan-out* (S21), a query joins `orders` to `order_items`. One row of the result is what?

   <details>
   <summary>Answer</summary>

   One order line, because an order with three lines is paired with three rows. Counting rows then counts lines, not
   orders.

   </details>

2. In *NULL: unknown is not zero* (S4), write the query that shows the orders with no customer.

   <details>
   <summary>Answer</summary>

   `SELECT * FROM orders WHERE customer_id IS NULL;` It returns 1 row: order 1335, the walk-in.

   </details>

## Learn by doing

Five small steps. Counts cover completed
orders (1,799 of the 1,800); amounts include the extra-zero line (order 2075).

### 1. Ask with the schema and the grain

An assistant has never seen your tables. Tell it what it cannot see: your columns, what one row of each table is (the
**grain**, S18), how an amount is worked out, and what one row of the answer should stand for.

**Try it.** Send this prompt to any assistant. It holds column names and no customer data; the caution
box in E22 lists what never to paste.

> *I use DuckDB. Tables: orders(order_id, customer_id, store_id, ordered_at, status, payment_method);
> order_items(order_item_id, order_id, product_id, quantity, discount_usd); products(product_id, product_name,
> category, unit_price_usd); stores(store_id, store_name, city, opened_on). One row of orders is one order; one row
> of order_items is one product line. A line's amount is quantity × unit_price_usd − discount_usd. status is
> 'completed' or 'canceled'. Question: the average order value of completed orders for each store. Output: one row
> per store with store_name, orders and avg_order_value. Give only the SQL.*

*Why:* every fact the assistant would otherwise guess is on the page. What comes back is a draft: the next unit has it.

### 2. Read the draft, then run it

Running a draft proves only that it runs. NIST's generative AI profile (NIST AI 600-1) calls content that is "confidently
stated but erroneous or false" *confabulation*, and says people may believe it, often because the response sounds sure.
The assistant's own explanation is no help: NIST notes that generated explanations can be confabulated too, and may lead people to trust a wrong answer.

So **read** first. Say what each clause does, `FROM` first. A join returns one row for each matched pair of rows (DuckDB:
it "uses a rule to match pairs of rows"), so after a join ask what one row now stands for. Then check the **rows**: work
out how many rows the output grain you asked for must give.

**Try it.** Before you run it: the prompt asked for one row per store. How many rows must come back?

<RunSQL query={`SELECT s.store_name,
       COUNT(*) AS orders,
       ROUND(SUM(i.quantity * p.unit_price_usd - i.discount_usd) / COUNT(*), 2) AS avg_order_value
FROM orders AS o
JOIN order_items AS i ON i.order_id = o.order_id
JOIN products AS p ON p.product_id = i.product_id
JOIN stores AS s ON s.store_id = o.store_id
WHERE o.status = 'completed'
GROUP BY s.store_name
ORDER BY s.store_name;`} />

Expected: 3 columns, as asked. *Why:* the joins give one row per line (S21), so `COUNT(*)` counts lines, not orders. That
is a suspicion, not yet a proof.

### 3. Reconcile with one table

**Reconcile**: compare a count or total from the draft with the same figure from one table, where no join can repeat a
row.

**Try it.**

<RunSQL query={`SELECT COUNT(*) AS orders FROM orders WHERE status = 'completed';`} />

Expected: 1 row, 1 column: `1799`. *Why:* the draft's `orders` column adds up to 1,304 + 645 + 1,337 = 3,286, the completed
lines. The one-table count has no join to go wrong, so the draft loses. **Reject.**

### 4. Work the known answer first

A **known answer** is a small frame you total on paper before you run the draft on it. Work it first, so the draft's
number cannot sway yours. The frame is seven orders, 1458 to 1464, with the canceled one among them.

### 5. Fix it, then check again

A fix is another draft, so run the checks again. Here the cause is `COUNT(*)`: count distinct orders instead. Then hunt
for rows with an empty key: DuckDB says an inner join returns only the rows that get paired, so such a row vanishes
silently. This question has none.

**Try it.**

<RunSQL query={`SELECT s.store_name,
       COUNT(DISTINCT o.order_id) AS orders,
       ROUND(SUM(i.quantity * p.unit_price_usd - i.discount_usd) / COUNT(DISTINCT o.order_id), 2) AS avg_order_value
FROM orders AS o
JOIN order_items AS i ON i.order_id = o.order_id
JOIN products AS p ON p.product_id = i.product_id
JOIN stores AS s ON s.store_id = o.store_id
WHERE o.status = 'completed'
GROUP BY s.store_name
ORDER BY s.store_name;`} />

Expected: 3 rows, 3 columns: Campus 715 and 12.59, Harbor 355 and 12.98, Old Town 729 and 12.54. *Why:* the orders add up to
1,799. With the `BETWEEN` line of unit 4 it gives 10.58 and 14.83, the hand answers. A second route: Old Town's sales of
9,144.25 divided by its 729 orders is 12.54. The answer to the owner: **6.84 was the average line; the average order at
Old Town is 12.54.**

<details>
<summary>Explain it in your own words: why did the row count pass while the draft was wrong?</summary>

The output grain was right: one row per store. The error was in what `COUNT(*)` counted. A row count checks the shape;
only a total or a known answer checks the numbers.

</details>

<Aside type="tip" title="Remember">

- Running a draft proves only that it runs. Test it against something the draft did not produce.
- The five checks: read, rows, reconcile, known answer, empty keys.
- Work your own answer before you look at the draft's.

**Common trap: "a clear explanation means the query is right."** The explanation is more text from the same source, and it
can be wrong in the same confident way. Only a comparison with something else counts.

</Aside>

## Finish it

<Exercise id="sql-ai-assisted-queries-1">

**An assistant drafts "customers who never ordered". Do you accept it?** The dataset's description says five customers
signed up and never ordered. Expected shape: 1 column. The number of rows is what you check.

The first steps are done for you: the prompt gave the schema and "customers with no order", and you read the draft: it tests
each customer against the `customer_id` values of `orders`.

<RunSQL query={`SELECT customer_id
FROM customers
WHERE customer_id NOT IN (SELECT customer_id FROM orders);`} />

Now finish it: compare its row count with the five, find out why with one query on `orders`, and write a draft that passes.

<details>
<summary>Hint</summary>

Use the check of *NULL: unknown is not zero* (S4): how many rows of `orders` have an empty `customer_id`? Then use the
anti-join of *LEFT JOIN and finding rows with no match* (S20).

</details>

<details>
<summary>Half-solution</summary>

```sql
SELECT c.customer_id
FROM customers AS c
LEFT JOIN orders AS o ON ...
WHERE o.order_id IS NULL;
```

</details>

<Solution>

The draft returns 0 rows, not 5. `SELECT COUNT(*) - COUNT(customer_id) FROM orders;` returns `1`: order 1335, the
walk-in, has no customer, so the list inside `NOT IN` contains an empty value. A comparison with an empty value is
neither true nor false, so no customer passes the "differs from every value" test (a standard-SQL rule; the result shows
it).

```sql
SELECT c.customer_id
FROM customers AS c
LEFT JOIN orders AS o ON o.customer_id = c.customer_id
WHERE o.order_id IS NULL
ORDER BY c.customer_id;
```

It returns 5 rows: customers 140, 147, 148, 149 and 150.

</Solution>

</Exercise>

## On your own

<Exercise id="sql-ai-assisted-queries-2">

**An assistant drafts the running total of completed sales, one row per day.** Work in the Exercise 2 blocks.

Before you run anything, write one sentence: how many rows the result should have, and its last value. Then run the
draft, check it, and write a fixed query and the prompt that states the output grain.

Expected shape: 2 columns (the day and the running total). The draft is a window function (S14).

<RunSQL query={`SELECT CAST(o.ordered_at AS DATE) AS order_day,
       SUM(i.quantity * p.unit_price_usd - i.discount_usd) OVER (ORDER BY CAST(o.ordered_at AS DATE)) AS running_sales
FROM orders AS o
JOIN order_items AS i ON i.order_id = o.order_id
JOIN products AS p ON p.product_id = i.product_id
WHERE o.status = 'completed'
ORDER BY order_day;`} />

<details>
<summary>Hint</summary>

What grain does this query return? The window runs over the rows that reach it: build one row per day first, in a CTE
(S13).

</details>

<details>
<summary>Half-solution</summary>

Expected output: *"One row for each day of the period, with the running total beside it; the last value equals the completed-sales total."*
Write a `daily` step with `GROUP BY` the day, then the window over `daily`.

</details>

<Solution>

The draft returns 3,286 rows, one per line, not 181: its last value is 22,749.25, the right total, so an end-of-series
check passes while the grain is wrong. A prompt that would help says: *"Output: one row per day with order_day and
running_sales, 181 rows."* Fixed:

```sql
WITH daily AS (
  SELECT CAST(o.ordered_at AS DATE) AS order_day,
         SUM(i.quantity * p.unit_price_usd - i.discount_usd) AS sales
  FROM orders AS o
  JOIN order_items AS i ON i.order_id = o.order_id
  JOIN products AS p ON p.product_id = i.product_id
  WHERE o.status = 'completed'
  GROUP BY CAST(o.ordered_at AS DATE)
)
SELECT order_day, ROUND(SUM(sales) OVER (ORDER BY order_day), 2) AS running_sales
FROM daily
ORDER BY order_day;
```

181 rows; the first three values are 45.50, 121.25 and 186.75, and the last is 22,749.25. The total was right and the row
count wrong, which is why you run more than one check.

</Solution>

</Exercise>

## Check yourself

Without looking back: name the five checks, and say what each compares the draft with.

<details>
<summary>Answer</summary>

Read (the clauses against what you asked), rows (the output grain you expect), reconcile (a one-table count or total),
known answer (your hand work on a small frame), empty keys. None uses the assistant's own claims as the standard.

</details>

<Exercise id="sql-ai-assisted-queries-3">

**Spot the flaw.** For the sales of each store, an assistant drafts the query below. A colleague checks that it returns 3
rows and that Harbor's 4,606.25 matches the pivot, and accepts it. Expected: 3 rows, 2 columns. What went wrong, and which
check would have caught it?

<RunSQL query={`SELECT s.store_name,
       ROUND(SUM(i.quantity * p.unit_price_usd - i.discount_usd), 2) AS sales
FROM orders AS o
JOIN order_items AS i ON i.order_id = o.order_id
JOIN products AS p ON p.product_id = i.product_id
JOIN stores AS s ON s.store_id = o.store_id
GROUP BY s.store_name
ORDER BY s.store_name;`} />

<Solution>

The draft has no filter on `status`, so it adds the canceled line too. The checks passed by luck: three stores are
three rows, and Harbor has no canceled lines. Campus has the canceled order 1461 (5.00): the draft gives 9,003.75, not the
completed 8,998.75.

A known-answer frame has to contain the trap. On orders 1458 to 1464, which include 1461, the draft gives Campus 49.50;
by hand the completed orders add up to 44.50. Reconciling the three stores with the completed total fails too: 22,754.25
against 22,749.25. The fix is `WHERE o.status = 'completed'`.

</Solution>

</Exercise>
