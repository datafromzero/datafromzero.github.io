## The question

The owner of the cafes asks:

> An assistant wrote me a query for the average order value of each store. It says Old Town 6.84, Campus 6.90 and
> Harbor 7.14. Someone told me last month it was about 12. Can I trust the query?

The draft ran without an error and returned this:

| store_name | orders | avg_order_value |
|---|---:|---:|
| Campus | 1304 | 6.90 |
| Harbor | 645 | 7.14 |
| Old Town | 1337 | 6.84 |

NIST's generative AI profile (NIST AI 600-1) lists *confabulation*: "The production of confidently stated but erroneous
or false content". A wrong query arrives in the same calm tone as a right one, and this one has no error message to
warn you. By the end you will have caught what is wrong with a number worked out by hand.

Five checks, each comparing the draft with something the draft did not produce: **read** it clause by clause; count the
**rows** you expect; **reconcile** a total or count against a one-table query; work a **known answer** by hand on a small
frame and run the draft on it; and look for **NULL** cases, rows with an empty key that a join may drop. The second picture
is the frame: seven orders small enough to total on paper, with the awkward case, a canceled order (1461).

## Worked example

Question: **what is the average completed order of each store, and is the draft right?** Run the notebook's setup cell,
then one cell per step. Counts cover completed orders (1,799 of the 1,800), and amounts include the extra-zero line
(order 2075).

1. **Write the prompt: schema, question, output grain.** An example:

   > *I use DuckDB. Tables: orders(order_id, customer_id, store_id, ordered_at, status, payment_method);
   > order_items(order_item_id, order_id, product_id, quantity, discount_usd); products(product_id, product_name,
   > category, unit_price_usd); stores(store_id, store_name, city, opened_on). One row of orders is one order; one row
   > of order_items is one product line. A line's amount is quantity × unit_price_usd − discount_usd. status is
   > 'completed' or 'canceled'. Question: the average order value of completed orders for each store. Output: one row
   > per store with store_name, orders and avg_order_value. Give only the SQL.*

   *Why:* the assistant cannot see your data, so you say the columns, what one row is, the rule for an amount and the
   output grain. It holds column names and no customer data; the caution box in E22 lists what never to paste.

2. **Read the draft clause by clause, then run it.** The reply:

   ```sql
   SELECT s.store_name,
          COUNT(*) AS orders,
          ROUND(SUM(i.quantity * p.unit_price_usd - i.discount_usd) / COUNT(*), 2) AS avg_order_value
   FROM orders AS o
   JOIN order_items AS i ON i.order_id = o.order_id
   JOIN products AS p ON p.product_id = i.product_id
   JOIN stores AS s ON s.store_id = o.store_id
   WHERE o.status = 'completed'
   GROUP BY s.store_name
   ORDER BY s.store_name;
   ```

   Expected: 3 rows, 3 columns, one per store as asked. *Why read first:* the joins give one row per line (S21), the
   `WHERE` keeps completed orders, and `COUNT(*)` counts rows of that result, so `orders` counts lines. That is a
   suspicion, not yet a proof, and the right shape alone proves little.

3. **Reconcile the count.**

   ```sql
   SELECT COUNT(*) AS orders FROM orders WHERE status = 'completed';
   ```

   Expected: 1 row, 1 column: `1799`. The draft's `orders` column adds up to 1,304 + 645 + 1,337 = 3,286, the number of
   completed lines. **Reject.** *Why:* the draft's count and a one-table count disagree, and the one-table count has no
   join to go wrong.

4. **Known answer, by hand first.** In the frame, completed Old Town is 14.25, 13.50 and 4.00: 31.75 over 3 orders is
   10.58; Campus is 44.50 over 3 orders, 14.83. Now run the draft on the frame, by adding
   `AND o.order_id BETWEEN 1458 AND 1464` after the `WHERE`. Expected: 2 rows, 3 columns. The draft gives Old Town 5
   "orders" and 6.35, Campus 5 and 8.90: both rejected, and the cause is visible, 31.75 ÷ 5 lines.

5. **Fix it and verify again.** Count distinct orders:

   ```sql
   SELECT s.store_name,
          COUNT(DISTINCT o.order_id) AS orders,
          ROUND(SUM(i.quantity * p.unit_price_usd - i.discount_usd) / COUNT(DISTINCT o.order_id), 2) AS avg_order_value
   FROM orders AS o
   JOIN order_items AS i ON i.order_id = o.order_id
   JOIN products AS p ON p.product_id = i.product_id
   JOIN stores AS s ON s.store_id = o.store_id
   WHERE o.status = 'completed'
   GROUP BY s.store_name
   ORDER BY s.store_name;
   ```

   Expected: 3 rows, 3 columns: Campus 715 and 12.59, Harbor 355 and 12.98, Old Town 729 and 12.54. The orders add up to
   1,799. On the frame it gives 10.58 and 14.83, the hand answers. A second route: Old Town's sales of 9,144.25 divided
   by its 729 orders is 12.54. Answer: **6.84 was the average line; the average order at Old Town is 12.54.** (DuckDB's
   documentation: "A join uses a rule to match pairs of rows from each relation." Pairs, one per line.)

<details>
<summary>Explain it in your own words: why did the row count pass while the draft was wrong?</summary>

The output grain was right: one row per store. The error was in what `COUNT(*)` counted. A row count checks the shape;
only a total or a known answer checks the numbers.

</details>

<Exercise id="sql-ai-assisted-queries-1">

**An assistant drafts "customers who never ordered". Do you accept it?** Use the Exercise 1 cells. The dataset's
description says five customers signed up and never ordered. The draft:

```sql
SELECT customer_id
FROM customers
WHERE customer_id NOT IN (SELECT customer_id FROM orders);
```

Expected shape: 1 column. The number of rows is what you check.

The first steps are done for you: the prompt gave the schema and "customers with no order", and you read the draft: it
tests each customer against the `customer_id` values of `orders`. Now finish it: run it, compare its row count with the
five, find out why with one query on `orders`, and write a draft that passes.

<details>
<summary>Hint</summary>

Think of the NULL check. How many rows of `orders` have an empty `customer_id`? Then use the anti-join of *LEFT JOIN and
finding rows with no match* (S20).

</details>

<details>
<summary>Half-solution</summary>

```sql
SELECT c.customer_id
FROM customers AS c
LEFT JOIN orders AS o ON ...
WHERE o.order_id IS NULL;
```

</details>

<Solution>

The draft returns 0 rows, not 5. `SELECT COUNT(*) - COUNT(customer_id) FROM orders;` returns `1`: order 1335, the
walk-in, has no customer, so the list inside `NOT IN` contains an empty value. `NOT IN` asks whether a customer differs
from every value in the list, and a comparison with an empty value is neither true nor false, so no customer passes (a
standard-SQL rule; the result shows it).

```sql
SELECT c.customer_id
FROM customers AS c
LEFT JOIN orders AS o ON o.customer_id = c.customer_id
WHERE o.order_id IS NULL
ORDER BY c.customer_id;
```

It returns 5 rows: customers 140, 147, 148, 149 and 150.

</Solution>

</Exercise>

## On your own

<Exercise id="sql-ai-assisted-queries-2">

**An assistant drafts the running total of completed sales, one row per day.** Work in the Exercise 2 cells.

Before you run anything, write one sentence in the first cell: how many rows the result should have and what its last
value should be. Then run the draft, check it, and write a fixed query and the prompt that states the output grain.

Expected shape: 2 columns (the day and the running total).

The draft (a window function, *Window functions*, S14):

```sql
SELECT CAST(o.ordered_at AS DATE) AS order_day,
       SUM(i.quantity * p.unit_price_usd - i.discount_usd) OVER (ORDER BY CAST(o.ordered_at AS DATE)) AS running_sales
FROM orders AS o
JOIN order_items AS i ON i.order_id = o.order_id
JOIN products AS p ON p.product_id = i.product_id
WHERE o.status = 'completed'
ORDER BY order_day;
```

<details>
<summary>Hint</summary>

What grain does this query return? The window runs over the rows that reach it: build one row per day first, in a CTE
(S13).

</details>

<details>
<summary>Half-solution</summary>

Expected output: *"One row for each day of the period, with the running total beside it; the last value equals the completed-sales total."*
Write a `daily` step with `GROUP BY` the day, then the window over `daily`.

</details>

<Solution>

The draft returns 3,286 rows, one per line, not 181: its last value is 22,749.25, the right total, so an end-of-series
check passes while the grain is wrong. Lines of the same day repeat the same running total. A prompt that would help
says: *"Output: one row per day with order_day and running_sales, 181 rows."* Fixed:

```sql
WITH daily AS (
  SELECT CAST(o.ordered_at AS DATE) AS order_day,
         SUM(i.quantity * p.unit_price_usd - i.discount_usd) AS sales
  FROM orders AS o
  JOIN order_items AS i ON i.order_id = o.order_id
  JOIN products AS p ON p.product_id = i.product_id
  WHERE o.status = 'completed'
  GROUP BY CAST(o.ordered_at AS DATE)
)
SELECT order_day, ROUND(SUM(sales) OVER (ORDER BY order_day), 2) AS running_sales
FROM daily
ORDER BY order_day;
```

181 rows; the first three values are 45.50, 121.25 and 186.75, and the last is 22,749.25. One check passed and one failed,
independently: the total was right and the row count was wrong, which is why you run more than one.

</Solution>

</Exercise>

**Spot the flaw.** For the sales of each store, an assistant drafts:

```sql
SELECT s.store_name,
       ROUND(SUM(i.quantity * p.unit_price_usd - i.discount_usd), 2) AS sales
FROM orders AS o
JOIN order_items AS i ON i.order_id = o.order_id

```

A colleague checks that it returns 3 rows and that Harbor's 4,606.25 matches the pivot, and accepts it. Expected: 3 rows,
2 columns. What went wrong, and which check would have caught it?

<Solution>

The draft has no filter on `status`, so it adds the canceled line too. The checks passed by luck: three stores are
three rows, and Harbor has no canceled lines, so its total is the same with or without the filter. Campus has the one
canceled order (1461, 5.00): the draft gives 9,003.75, not the completed 8,998.75.

A known-answer frame has to contain the trap. On orders 1458 to 1464, which include 1461, the draft gives Campus 49.50;
by hand the completed orders add up to 14.00 + 13.50 + 17.00 = 44.50. Reconciling the three stores with the completed
total also fails: 22,754.25 against 22,749.25. The fix is `WHERE o.status = 'completed'`.

</Solution>
