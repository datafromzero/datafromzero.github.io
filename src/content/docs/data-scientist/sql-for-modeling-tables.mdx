## The question

The table that lesson DS2 modeled arrived ready. This lesson builds it, from the raw events, so that nothing in it comes from after the moment of prediction. The raw material is the event log: one row for each thing the app recorded, with the time it happened and the time the collector stored it. The first events of person 17471, as stored:

| event_id | event_ts | received_at | event_name |
|---:|---|---|---|
| 1056762 | 2026-03-19 17:13:33 | 2026-03-19 17:13:36 | signup_complete |
| 1056778 | 2026-03-19 17:30:13 | 2026-03-19 17:30:15 | add_expense |
| 1056779 | 2026-03-19 17:30:13 | 2026-03-19 17:30:33 | add_expense |

The question is how to turn a log like this into one row for each person, as of seven days after signup, with a label from days 8 to 30. By the end you can build the table in SQL, say for each column what the app knew when the row was cut, and reconcile the table to its source.

## Learn by doing

About 30 minutes, 4 new ideas: a cutoff for each row, counting only what was known, features as filtered counts, a label from the other side. A last unit reconciles the table and teaches nothing new. The setup cell loaded `users` and `events` into DuckDB; the queries run through `show()`, which prints their rows.

<OpenInColab />

### 1. One row per person, and a cutoff for each

**Idea.** A modeling table has one row for each *entity*, here a person, and a *cutoff* for each row: the moment of prediction. The cutoff is a timestamp, the person's own signup time plus 7 days, not a calendar date, so that everyone has had the same seven days to show what they do. Write the entity, the cutoff and the end of the label window first; every feature and the label are measured against them.

**Try it:** build `people`, one row for each person who signed up from January 1 to May 31, and check that the join to the signup event keeps every user once.

```python
con.execute("""CREATE OR REPLACE VIEW people AS
SELECT u.user_id, u.signup_date, u.channel, u.region, s.platform,
       s.event_ts AS signup_ts,
       s.event_ts + INTERVAL 7 DAY AS cutoff,       -- the prediction moment
       s.event_ts + INTERVAL 30 DAY AS horizon      -- the end of the label window
FROM users AS u
JOIN events AS s ON s.user_id = u.user_id AND s.event_name = 'signup_complete'
WHERE u.signup_date BETWEEN DATE '2026-01-01' AND DATE '2026-05-31'""")
show("""SELECT COUNT(*) AS people, COUNT(DISTINCT user_id) AS distinct_people,
       (SELECT COUNT(*) FROM users WHERE signup_date BETWEEN DATE '2026-01-01' AND DATE '2026-05-31') AS users_in_window
FROM people""")
```

**Predict:** The query joins `users` to the signup event of each user. Will it return fewer rows than there are users in the window, the same number, or more?

<details>
<summary>Reveal the result</summary>

```text
people | distinct_people | users_in_window
17816 | 17816 | 17816
```

</details>

*Why:* The same: 17,816 people, each once, as many as there are users in the window. Every user in the window has one signup event, so the join neither loses nor repeats anyone (the 10 users with no event signed up in June, outside the window). Each row carries its own cutoff, a column of `people`.

### 2. Count only what the app knew

**Idea.** An event counts at the cutoff only if the app could have known it. Three rules: it is not a retry copy; it had happened by the cutoff (`event_ts`); and it had arrived by the cutoff (`received_at`). The last two are two clocks, when it happened and when the collector stored it. `ROW_NUMBER() OVER (PARTITION BY …)` numbers the rows of each partition from 1, and `QUALIFY` filters on that number, so `= 1` keeps the first copy of each event.

**Try it:** build `clean` (copies removed) and `known` (both clocks), then count what each rule leaves of the first week.

```python
con.execute("""CREATE OR REPLACE VIEW clean AS
SELECT *
FROM events
QUALIFY ROW_NUMBER() OVER (PARTITION BY user_id, event_ts, event_name, platform ORDER BY received_at, event_id) = 1""")
con.execute("""CREATE OR REPLACE VIEW known AS
SELECT p.user_id, c.event_name, c.event_ts, p.cutoff
FROM people AS p
JOIN clean AS c ON c.user_id = p.user_id
WHERE c.event_ts <= p.cutoff AND c.received_at <= p.cutoff""")
show("""SELECT
  (SELECT COUNT(*) FROM people AS p JOIN events AS e ON e.user_id = p.user_id WHERE e.event_ts <= p.cutoff) AS happened_by_cutoff,
  (SELECT COUNT(*) FROM people AS p JOIN clean AS c ON c.user_id = p.user_id WHERE c.event_ts <= p.cutoff) AS without_copies,
  (SELECT COUNT(*) FROM known) AS known_at_cutoff""")
show("""SELECT (SELECT COUNT(*) FROM events) - (SELECT COUNT(*) FROM clean) AS copies_removed""")
```

**Predict:** Which rule takes more events out of the first week: removing the retry copies, or keeping only what had arrived by the cutoff? Roughly how many events does each take?

<details>
<summary>Reveal the result</summary>

```text
happened_by_cutoff | without_copies | known_at_cutoff
90391 | 90050 | 89999
copies_removed
835
```

</details>

*Why:* Of the 90,391 events that had happened by the cutoff, the copy rule removes 341 and the arrival rule 51 more, leaving 89,999. Over the whole table the copy rule removes 835 rows, the number DS1 counted with pandas. The arrival rule changes little here (Exercise 2 counts the people it touches); a collector that runs late more often would show it.

### 3. Features as counts of what was known

**Idea.** A feature is a summary of `known`, one row for each person. `COUNT(*) FILTER (WHERE …)` counts only the rows that pass the test, so one pass gives several counts: the whole week, and the last 3 days before the cutoff, a window of time measured back from the cutoff and not forward from signup. `COUNT(DISTINCT …)` counts days.

**Try it:** build `features` and look at its totals.

```python
con.execute("""CREATE OR REPLACE VIEW features AS
SELECT user_id,
       COUNT(*) FILTER (WHERE event_name = 'session_start') AS sessions_7d,
       COUNT(*) FILTER (WHERE event_name = 'add_expense') AS expenses_7d,
       COUNT(*) FILTER (WHERE event_name IN ('session_start', 'add_expense') AND event_ts > cutoff - INTERVAL 3 DAY) AS recent_3d,
       COUNT(DISTINCT CAST(event_ts AS DATE)) FILTER (WHERE event_name IN ('session_start', 'add_expense')) AS active_days_7d,
       CAST(COUNT(*) FILTER (WHERE event_name = 'onboarding_complete') > 0 AS INTEGER) AS onboarded,
       CAST(COUNT(*) FILTER (WHERE event_name IN ('view_paywall', 'paywall_viewed')) > 0 AS INTEGER) AS saw_paywall,
       CAST(COUNT(*) FILTER (WHERE event_name = 'purchase') > 0 AS INTEGER) AS bought_plus
FROM known
GROUP BY user_id""")
show("""SELECT COUNT(*) AS people, COUNT(*) FILTER (WHERE active_days_7d = 0) AS with_no_activity,
       SUM(recent_3d) AS recent_events, SUM(sessions_7d + expenses_7d) AS week_events
FROM features""")
```

**Predict:** How many of the 17,816 people have no visit and no expense in their first 7 days: about 5 percent, about a quarter, or about half?

<details>
<summary>Reveal the result</summary>

```text
people | with_no_activity | recent_events | week_events
17816 | 4531 | 10965 | 45648
```

</details>

*Why:* 4,531 people, 25.4 percent, have no activity in the week: about a quarter. They keep a row, because the signup event itself is in `known`; a person with nothing known would vanish from `features`, and the row check of unit 5 would show it. The last 3 days hold 10,965 of the 45,648 visits and expenses of the week.

### 4. The label comes from the other side

**Idea.** The label reads the events after the cutoff, up to the horizon, straight from `events`, and it is never joined into a feature. What counts as activity is part of the definition, so it is written in the query.

**Try it:** build `label`, then count the churn share under three definitions of activity.

```python
con.execute("""CREATE OR REPLACE VIEW label AS
SELECT p.user_id,
       CAST(NOT EXISTS (SELECT 1 FROM events AS e
                        WHERE e.user_id = p.user_id AND e.event_name IN ('session_start', 'add_expense')
                          AND e.event_ts > p.cutoff AND e.event_ts <= p.horizon) AS INTEGER) AS churned
FROM people AS p""")
show("""SELECT ROUND(100.0 * AVG(churned), 1) AS churn_both_events FROM label""")
for names in ("('session_start', 'add_expense')", "('session_start')", "('add_expense')"):
    print(names, rows(f"""SELECT ROUND(100.0 * AVG(CAST(NOT EXISTS (SELECT 1 FROM events AS e
        WHERE e.user_id = p.user_id AND e.event_name IN {names} AND e.event_ts > p.cutoff AND e.event_ts <= p.horizon) AS INTEGER)), 1) FROM people AS p""")[0][0])
```

**Predict:** Count only `add_expense` as activity instead of both events. Will the share of people who churned go up, stay about the same, or go down?

<details>
<summary>Reveal the result</summary>

```text
churn_both_events
54.4
('session_start', 'add_expense') 54.4
('session_start') 54.4
('add_expense') 66.3
```

</details>

*Why:* With a visit or an expense as activity, 54.4 percent churned. With expenses alone it is 66.3, 11.8 points more, because a visit can add no expense. With visits alone it is 54.4, the same to one decimal: only 4 people have an expense after day 7 and no visit, because a visit is where expenses are added (the dataset README), so expenses add almost nothing to visits. The definition moves the target, so it is written in the query.

### 5. Reconcile before anyone fits it

**Idea.** Reconcile the table before it is used: the rows against the source, a total against a second route, and a table by cohort, the people who signed up in the same month, against what you know. A check that cannot fail is not a check, so the second route is written another way.

**Try it:** assemble `modeling_table`, then run the checks and hand the table to pandas.

```python
con.execute("""CREATE OR REPLACE VIEW modeling_table AS
SELECT p.user_id, p.signup_date, p.channel, p.platform, p.region,
       f.sessions_7d, f.expenses_7d, f.recent_3d, f.active_days_7d, f.onboarded, f.saw_paywall, f.bought_plus,
       l.churned
FROM people AS p
JOIN features AS f ON f.user_id = p.user_id
JOIN label AS l ON l.user_id = p.user_id""")
# check 1: one row per person, none lost
show("""SELECT COUNT(*) AS table_rows, COUNT(DISTINCT user_id) AS distinct_people, (SELECT COUNT(*) FROM people) AS people FROM modeling_table""")
# check 2: the same totals from a second route, in pandas, straight from the raw events
ev = con.sql("SELECT user_id, event_ts, event_name, platform, received_at FROM events").df()
pe = con.sql("SELECT user_id, cutoff FROM people").df()
ev = ev.drop_duplicates(["user_id", "event_ts", "event_name", "platform"]).merge(pe, on="user_id", validate="many_to_one")
ev = ev[(ev["event_ts"] <= ev["cutoff"]) & (ev["received_at"] <= ev["cutoff"])]
print(int((ev["event_name"] == "session_start").sum()), int((ev["event_name"] == "add_expense").sum()))
show("""SELECT SUM(sessions_7d) AS sessions, SUM(expenses_7d) AS expenses FROM modeling_table""")
# check 3: each signup month, with its share of the table
show("""SELECT month(signup_date) AS month, COUNT(*) AS people, ROUND(100.0 * COUNT(*) / SUM(COUNT(*)) OVER (), 1) AS pct_of_table,
       ROUND(100.0 * AVG(churned), 1) AS pct_churned
FROM modeling_table GROUP BY month ORDER BY month""")
# check 4: hand the table to pandas; the next lessons build the same table with one statement
table = con.sql("SELECT * FROM modeling_table ORDER BY user_id").df()
print(table.shape, table.equals(con.sql(ONE_STATEMENT).df()))
```

**Predict:** The second route removes the copies in pandas and applies the same two clocks. Will its totals of visits and expenses equal the SQL totals exactly?

*Why:* They do: 12,913 visits and 32,735 expenses on both routes, and one row for each of the 17,816 people. The cohort table shows what the first rows could not: 49.9 percent of the January signups churned and 60.7 percent of the May signups, and May is 28.5 percent of the table, so the table is not one stable population (lesson DS5 cuts by time). The last line shows that the pieces build the same table as the one-statement query of the other lessons.

<Aside type="tip" title="Remember">

- One row for each entity, with a cutoff timestamp for each row.
- An event counts only if it is not a retry copy, had happened by the cutoff and had arrived by it.
- `COUNT(*) FILTER (WHERE …)` gives several counts in one pass, including a window measured back from the cutoff.
- The label reads after the cutoff and never feeds a feature; the definition of activity is in the query.
- Reconcile: the rows against the source, a total by a second route, a table by cohort.

**Common trap:** trusting a table that was not reconciled. A join can lose or repeat people without an error.

</Aside>

first_expense = """SELECT p.user_id, p.signup_ts, MIN(k.event_ts) FILTER (WHERE k.event_name = 'add_expense') AS first_expense
FROM people AS p JOIN known AS k ON k.user_id = p.user_id GROUP BY p.user_id, p.signup_ts"""      # given: the time of each person's first known expense, NULL when there is none
answer_1 = None  # replace None with [people whose first expense came within an hour of signup, people with an expense in the week]: rows(...)[0] of a query over first_expense
```

<details>
<summary>Hint</summary>

Wrap the query in parentheses after `FROM`. `COUNT(*) FILTER (WHERE first_expense <= signup_ts + INTERVAL 1 HOUR)` counts the people within the hour; for the second number use a count that skips `NULL`.

</details>

<details>

```python
answer_1 = rows(f"""SELECT COUNT(*) FILTER (WHERE ...), COUNT(...)
FROM ({first_expense})""")[0]

answer_1 = rows(f"""SELECT COUNT(*) FILTER (WHERE first_expense <= signup_ts + INTERVAL 1 HOUR), COUNT(first_expense)

A feature built on a wrong denominator would call everyone without an expense slow.

SELECT COUNT(*) FROM raw_week AS r JOIN features AS f ON f.user_id = r.user_id
WHERE r.n <> f.sessions_7d + f.expenses_7d""")[0][0]
```

46 people have a different count when the arrival rule is dropped, 0.26 percent of the table: a late event matters for a few people only. Against the raw events, with the copies in, the count is 318: a different question.
