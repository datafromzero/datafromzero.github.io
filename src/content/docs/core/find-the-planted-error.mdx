## Learn by doing

About 35 minutes, 4 new ideas: a fan-out, a name that does not exist, a filter that drops nulls and a percent change on the wrong base. The SQL blocks run in the page. The Python block of drill 2 is read only: run it in a notebook or a terminal.

### 1. A fan-out counts a number once for each line

**Idea.** A *fan-out* is a join that returns one row for every match (*Join fan-out*, S22). The check counts the rows around the join and adds the same quantity up a second way.

<Aside type="note" title="An answer written for this lesson">

**Revenue by category, April to June, completed orders.** I worked out the total of each order first and joined it to the order lines, so that every total could be split by category. Coffee 14,256.25, bakery 5,660.00, food 5,526.50 and tea 4,469.25: 29,912.00 dollars in all.

</Aside>

**Try it.** The assistant's query, as it wrote it:

<RunSQL query={`WITH order_totals AS (
  SELECT order_id, SUM(quantity * unit_price_usd - discount_usd) AS order_total
  FROM order_items JOIN products USING (product_id)
  GROUP BY order_id
)
SELECT p.category, SUM(t.order_total) AS revenue
FROM orders o
JOIN order_totals t ON t.order_id = o.order_id
JOIN order_items oi ON oi.order_id = o.order_id
JOIN products p ON p.product_id = oi.product_id
WHERE o.status = 'completed'
  AND o.ordered_at >= '2026-04-01' AND o.ordered_at < '2026-07-01'
GROUP BY p.category
ORDER BY revenue DESC;`} />

Expected: 4 rows, 2 columns.

**Predict:** the revenue of the same orders added from the order lines alone, with nothing else joined. Roughly how many dollars, to the nearest thousand?

**Try it.** The second route, with the rows that go through the join:

<RunSQL query={`SELECT COUNT(DISTINCT o.order_id) AS orders,
       COUNT(*) AS lines,
       SUM(oi.quantity * p.unit_price_usd - oi.discount_usd) AS revenue
FROM orders o
JOIN order_items oi ON oi.order_id = o.order_id
JOIN products p ON p.product_id = oi.product_id
WHERE o.status = 'completed'
  AND o.ordered_at >= '2026-04-01' AND o.ordered_at < '2026-07-01';`} />

Expected: 1 row, 3 columns.

*Why:* 1,082 orders, 1,979 lines and 13,974.00 dollars, with order 2075 (the 20-sandwich extra zero of the README) inside: the assistant's total is 2.14 times the real one. Each order's total was repeated once for each of its lines, so an order with three lines was added three times. The query ran, returned four tidy rows and raised no error.

**Write the check.** In a sentence or two of your own: which check catches this, and what does it show?

<details>
<summary>A check in words</summary>

Count the rows around the join: 1,082 orders go in and 1,979 rows come out, so anything per order is repeated. Add the revenue a second way, from the lines: 13,974.00.

</details>

### 2. A name that does not exist

**Idea.** An assistant writes names (a function, a method, a package, a column) that look right and may not exist in your installed version. The check is the documentation of that version, or asking the object itself.

<Aside type="note" title="An answer written for this lesson">

**Daily totals of the cafes.** I added the amount of each order to the orders and used the daily totals method to get one number for each day.

</Aside>

The assistant's code, with the table `sales` it builds first (one row for each of the 1,800 orders, with its `amount`):

```python
import pandas as pd

BASE = "https://raw.githubusercontent.com/datafromzero/datafromzero.github.io/v0.1.0/datasets/cafe-sales/v1/"
orders = pd.read_csv(BASE + "orders.csv", parse_dates=["ordered_at"])
lines = pd.read_csv(BASE + "order_items.csv").merge(pd.read_csv(BASE + "products.csv"), on="product_id", validate="many_to_one")
lines["amount"] = lines["quantity"] * lines["unit_price_usd"] - lines["discount_usd"]
sales = orders.merge(lines.groupby("order_id", as_index=False)["amount"].sum(), on="order_id", validate="one_to_one")

daily = sales.daily_totals("amount", by="ordered_at")
```

**Predict:** the last line asks for a method by name. Which will Python raise: `NameError`, `KeyError`, `AttributeError` or `TypeError`?

<details>
<summary>Reveal the result</summary>

```text
AttributeError: 'DataFrame' object has no attribute 'daily_totals'
```

</details>

**Try it.** Ask the object, then use a method that exists:

```python
print(hasattr(sales, "daily_totals"))
print(hasattr(pd.DataFrame, "append"))
daily = sales.groupby(sales["ordered_at"].dt.date)["amount"].sum()
print(daily.head(3))
print(len(daily), daily.sum())
```

**Predict:** `hasattr(x, "name")` says whether `x` has something of that name. What do the first two lines print, one for the invented name and one for `append`, a method that older code used?

<details>
<summary>Reveal the result</summary>

```text
False
False
ordered_at
2026-01-01    45.50
2026-01-02    75.75
2026-01-03    65.50
Name: amount, dtype: float64
181 22754.25
```

</details>

*Why:* there is no such method, and `append` is gone too: the pandas 2.0 release notes list it among the removed methods and point to `concat`. The output is from pandas 2.2.3 and 3.0.5; your installed version decides. The DataFrame page lists `groupby` under function application and `resample` under time series, and no `daily_totals`. The fix gives 181 days and 22,754.25 dollars, the canceled order and order 2075 included.

**Write the check.** In a sentence or two of your own: how do you catch an invented name?

<details>
<summary>A check in words</summary>

Look up every name in the documentation of the installed version, or ask the object with `hasattr` or `dir`. A name neither has does not exist, however natural it sounds.

</details>

### 3. A filter on a column that a join left empty

**Idea.** After a `LEFT JOIN`, a customer with no orders has `NULL` in every column of `orders`. A comparison with `NULL` returns `NULL`, even `NULL = NULL` (the DuckDB page on NULL values), and in standard SQL a `WHERE` keeps a row only when its test is true. A test on a column of the right-hand table can therefore take the join's added rows away again.

<Aside type="note" title="An answer written for this lesson">

**How many of our 150 loyalty customers have never had an order canceled?** I joined every customer to their orders, kept the rows whose order is not canceled and counted the customers: 144.

</Aside>

**Try it.** The assistant's query, as it wrote it:

<RunSQL query={`SELECT COUNT(DISTINCT c.customer_id) AS customers_without_a_canceled_order
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.customer_id
WHERE o.status <> 'canceled';`} />

Expected: 1 row, 1 column.

**Predict:** the orders table holds one canceled order, and its customer has no other order. Without running anything, how many of the 150 customers should the answer be?

**Try it.** Profile the join the assistant used:

<RunSQL query={`SELECT COUNT(*) AS joined_rows,
       COUNT(o.status) AS with_status,
       COUNT(DISTINCT c.customer_id) AS customers
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.customer_id;`} />

Expected: 1 row, 3 columns.

*Why:* the answer is 149, and the assistant's 144 is 5 short. The join has 1,804 rows but only 1,799 have a status: five customers never ordered, their rows carry `NULL`, and the `WHERE` removed them. `COUNT(column)` skips empty values, as the DuckDB aggregates page says. A `NOT EXISTS` subquery gives 149 without the join.

**Write the check.** In a sentence or two of your own: what do you count, and where?

<details>
<summary>A check in words</summary>

Count rows and non-empty values around the filter: 1,804 rows after the join, 1,799 with a status, so a `WHERE` on that column drops five.

</details>

### 4. A percent change on the wrong base

**Idea.** A percent change compares a change with its starting figure, the *base*: the earlier of the two. Divide by another figure and the percent changes. The check works the percent back onto the base.

<Aside type="note" title="An answer written for this lesson">

**Old Town mobile orders, January to February, completed orders.** I counted the mobile orders of each month and compared the two: they fell 42.9 percent.

</Aside>

**Try it.** The assistant's query, as it wrote it:

<RunSQL query={`WITH m AS (
  SELECT COUNT(*) FILTER (WHERE month(ordered_at) = 1) AS jan,
         COUNT(*) FILTER (WHERE month(ordered_at) = 2) AS feb
  FROM orders
  WHERE store_id = 1 AND status = 'completed' AND payment_method = 'mobile'
)
SELECT ROUND(100.0 * (feb - jan) / feb, 1) AS pct_change FROM m;`} />

Expected: 1 row, 1 column.

**Predict:** the same change measured against January. Will its size be bigger or smaller than 42.9?

**Try it.** The two counts, the change, and the percent against each month:

<RunSQL query={`WITH m AS (
  SELECT COUNT(*) FILTER (WHERE month(ordered_at) = 1) AS jan,
         COUNT(*) FILTER (WHERE month(ordered_at) = 2) AS feb
  FROM orders
  WHERE store_id = 1 AND status = 'completed' AND payment_method = 'mobile'
)
SELECT jan, feb, feb - jan AS change,
       ROUND(100.0 * (feb - jan) / jan, 1) AS pct_of_jan,
       ROUND(100.0 * (feb - jan) / feb, 1) AS pct_of_feb
FROM m;`} />

Expected: 1 row, 5 columns.

*Why:* Old Town took 40 mobile orders in January and 28 in February, a fall of 12: 30.0 percent of January, the base. The assistant divided by February and got 42.9. Applied to January, 30.0 percent lands on 28, February's count, and 42.9 percent on 22.8. Both months come before order 2075.

**Write the check.** In a sentence or two of your own: how do you catch it?

<details>
<summary>A check in words</summary>

Divide the change by the earlier figure: 12 over 40 is 30.0 percent. Then apply the claimed percent to that base: it must land on the later figure, and 42.9 does not.

</details>

<Aside type="note" title="As of 2026-11-22: what published research measured">

**Package names.** Spracklen and colleagues (USENIX Security 2025, preprint revised March 2025) had 16 models write Python and JavaScript. Of 2.23 million package names, 440,445 (19.7 percent) did not exist: 5.2 percent for the GPT-series models and 21.7 percent for open-source ones. These are package names from 2024 models, not method names as in drill 2.

**Joins and names in SQL.** Pourreza and Rafiei (NeurIPS 2023) sampled 500 queries from the training set of the Spider benchmark, kept those whose results differed from the gold query and classified the failures of few-shot prompting with CodeX Davinci. Schema linking (the model did not find the right columns, tables or entities) was the largest class and JOIN the second.

Newer models change these rates; the checks stay. This box is reviewed every six months.

</Aside>

<Aside type="tip" title="Remember">

- Name the class first: it picks the check.
- Fan-out: count rows around each join, and add the total a second way.
- A name: look it up in the documentation of the installed version, or ask the object.
- A filter on a column that can be empty, even one a join emptied, drops those rows: count rows and non-empty values around it.
- A percent change: divide by the earlier figure, then apply the percent back to it; it must land on the later one.

**Common trap:** trusting an answer because it ran, returned tidy rows and raised no error.

</Aside>

**Class: a fan-out.** An assistant was asked how many orders contained a coffee at each cafe, completed orders. Its query counts the rows after the join. Run it, then fix it so that it counts orders. Expected: 3 rows, 2 columns (`store_name`, `orders`).

<RunSQL query={`SELECT s.store_name, COUNT(*) AS orders
FROM orders o
JOIN stores s ON s.store_id = o.store_id
JOIN order_items oi ON oi.order_id = o.order_id
JOIN products p ON p.product_id = oi.product_id

GROUP BY s.store_name
ORDER BY s.store_name;`} />

<details>
<summary>Hint</summary>

Unit 1: after the join to `order_items`, what is one row, an order or a line? Count what the question asks for, once each.

</details>

<details>
<summary>Half-solution</summary>

```sql
SELECT s.store_name, COUNT(DISTINCT ...) AS orders
FROM orders o
JOIN stores s ON s.store_id = o.store_id
```

</details>

<Solution>

```sql
SELECT s.store_name, COUNT(DISTINCT o.order_id) AS orders
FROM orders o
JOIN stores s ON s.store_id = o.store_id
JOIN order_items oi ON oi.order_id = o.order_id
JOIN products p ON p.product_id = oi.product_id
WHERE o.status = 'completed' AND p.category = 'coffee'
GROUP BY s.store_name
ORDER BY s.store_name;
```

Campus 483, Harbor 243 and Old Town 532 orders, 1,258 together. The starter gave 637, 313 and 704, which add to 1,654: the completed coffee lines, not orders. An order with two coffees was counted twice.

</Solution>

<Exercise id="core-find-the-planted-error-2">

**Class: a name that does not exist.** An assistant answered "the 90th percentile of the amount of an order line at each cafe, completed orders" (the amount that 90 of every 100 lines are at or below) with a query that begins `SELECT s.store_name, PERCENTILE(oi.quantity * p.unit_price_usd - oi.discount_usd, 0.9) AS p90`. Before you start, say what the result looks like: three rows, a cafe and an amount. Run it, then find the right function in the DuckDB documentation and write the query, rounded to 2 decimals. Expected: first a message saying the function does not exist; then 3 rows, 2 columns (`store_name`, `p90`).

<RunSQL query={`SELECT s.store_name,
       PERCENTILE(oi.quantity * p.unit_price_usd - oi.discount_usd, 0.9) AS p90
FROM orders o
JOIN stores s ON s.store_id = o.store_id
JOIN order_items oi ON oi.order_id = o.order_id
JOIN products p ON p.product_id = oi.product_id
WHERE o.status = 'completed'
GROUP BY s.store_name
ORDER BY s.store_name;`} />

<details>
<summary>Hint</summary>

Open the aggregate functions page of the DuckDB documentation and look for the interpolated quantile.

</details>

<details>
<summary>Half-solution</summary>

```sql
SELECT s.store_name,
       ROUND(...(oi.quantity * p.unit_price_usd - oi.discount_usd, 0.9), 2) AS p90
FROM orders o
```

</details>

<Solution>

```sql
SELECT s.store_name,
       ROUND(quantile_cont(oi.quantity * p.unit_price_usd - oi.discount_usd, 0.9), 2) AS p90
FROM orders o
JOIN stores s ON s.store_id = o.store_id
JOIN order_items oi ON oi.order_id = o.order_id
JOIN products p ON p.product_id = oi.product_id
WHERE o.status = 'completed'
GROUP BY s.store_name
ORDER BY s.store_name;
```

```text
store_name  p90
Campus      12.75
Harbor      13.50
Old Town    11.25
```

<Solution>

```sql
SELECT o.order_id, o.ordered_at, o.status, SUM(oi.quantity * p.unit_price_usd - oi.discount_usd) AS amount
FROM orders o
JOIN order_items oi ON oi.order_id = o.order_id
JOIN products p ON p.product_id = oi.product_id
WHERE o.store_id = 2 AND o.payment_method = 'cash' AND o.status <> 'completed'
GROUP BY o.order_id, o.ordered_at, o.status;
```

One row: order 1461, canceled on March 1, a single Mocha of 5.00. Every price and discount has two decimals, so a sum of them hides nothing in rounding: a gap is rows. The second route kept the canceled order and the first did not. Revenue counts completed orders, so 1,347.50 stands, and the check should have matched it to the cent.
