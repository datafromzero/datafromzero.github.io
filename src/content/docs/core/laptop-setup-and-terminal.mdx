1. A script contains `open("data/orders.csv")`. It runs when you start it from the project folder, and stops with `FileNotFoundError` when you start it from another folder. Why, and how can a user give it any path?

   <details>
   <summary>Answer</summary>

   A path that does not start with a slash is read from the folder the terminal stands in, not from the folder of the script. Let the user pass the path on the command line, for example with `argparse`.

   Missed it? Study [*A real Python project: modules, packages and arguments*](/core/python-project-layout/) (C24).

   </details>

2. A colleague clones your project and runs it. It stops with `ModuleNotFoundError: No module named 'pandas'`. Name two likely causes.

   <details>
   <summary>Answer</summary>

   pandas was installed by hand on your machine and never declared in `pyproject.toml` and `uv.lock`; or the command ran with another Python than the project's environment. Declare it with `uv add pandas`, commit both files, and run the project with `uv run`.

   Missed it? Study [*Environments and dependencies, for real*](/core/environments-and-dependencies/) (C25).

   </details>

3. A script prints `done`, but its output file is empty. The whole job sits inside `try:` with `except: pass`. What is wrong, and what do you write instead?

   <details>
   <summary>Answer</summary>

   A bare `except:` catches every error, also the ones you did not expect, and `pass` hides it, so a failure looks like success. Catch the one error you expect, by name, and let every other error stop the script.

   Missed it? Study [*When it breaks: errors, retries and debugging*](/core/debugging-and-retries/) (C26).

   </details>

4. A function should keep one row for each order id. How do you check it before you trust it on 1,800 orders?

   <details>
   <summary>Answer</summary>

   Give it a small table whose answer you know by hand, such as 5 rows of which 2 repeat an id, and assert the result: 3 rows and no repeated id. A test runner (a tool that runs such checks for you; pytest is the usual one for Python) runs that check again every time you change the code.

   Missed it? Study [*Testing on known answers with pytest*](/core/testing-with-pytest/) (C27).

   </details>

5. A teammate commits (saves into the project's history) a file `.env` that holds a password, sees the mistake and deletes the file in the next commit. Is the password safe now? What do you do?

   <details>
   <summary>Answer</summary>

   No. The first commit still holds the file, and anyone who can read the repository can read its history. Treat the password as exposed: revoke or rotate it, and add `.env` to `.gitignore` so that it is not added again.

   Missed it? Study [*Logging, configuration and secrets*](/core/logging-config-secrets/) (C28).

   </details>

6. `def line_total(price: float, quantity: int) -> float: return price * quantity`. What does `line_total("3", 2)` return?

   <details>
   <summary>Answer</summary>

   `'33'`. Python does not enforce hints when the code runs; editors and type checkers read them and warn. A hint documents the code; it does not guard it.

   Missed it? Study [*Readable code, reading docs and classes*](/core/readable-code-and-classes/) (C29).

   </details>

## Learn by doing

About 55 minutes, 4 new ideas: three tools and a check script, folders and relative paths, small tools joined by pipes, and the codespace fallback (a coding workspace that runs in your browser). Every command is typed in the terminal of VS Code, and each unit adds a file to the folder `cafe-report`.

### 1. Three tools and a check script

**Idea.** The setup is three tools with one job each: **VS Code**, an editor with a terminal inside it; **<Term id="glossary-git">Git</Term>**, which keeps the history of your project (the next lesson); and **<Term id="glossary-uv">uv</Term>**, which installs Python and runs it. A short script, `check_environment.py`, tests all three and prints the fix for each failure. Install them for your system:

- **Windows.** VS Code: download the User Installer (`.exe`) from the download page and run it; it needs no administrator rights. Git: download Git for Windows from git-scm.com/download/win; it provides Git Bash, a BASH emulation for running Git from the command line. uv: in PowerShell (the Windows command window), run `powershell -ExecutionPolicy ByPass -c "irm https://astral.sh/uv/install.ps1 | iex"`. Then, in VS Code, open a terminal, choose **Terminal: Select Default Profile** (the command of that name, or the dropdown next to the new-terminal button) and pick **Git Bash**. From here on, every command on this page is the same on Windows, macOS and Linux.
- **macOS.** VS Code: open the `.dmg` file and drag Visual Studio Code to the Applications folder. Git: run `git` in the Terminal; the first time, macOS offers to install the Xcode Command Line Tools (Apple's set of developer tools; accept). uv: `curl -LsSf https://astral.sh/uv/install.sh | sh`.
- **Linux.** VS Code: install the `.deb` package (`sudo apt install ./<file>.deb`) or the `.rpm` package (`sudo dnf install ./<file>.rpm`). Git: `sudo apt install git-all` or `sudo dnf install git-all`. uv: the same `curl` line as on macOS.

After an install, close the terminal and open a new one. Then tell Git who you are, once: Git writes the name and email into every commit you make.

```console
git config --global user.name "Your Name"
git config --global user.email "you@example.com"
```

**Try it.** Make a folder `cafe-report` in your home folder, open it in VS Code (File menu, Open Folder) and open a terminal (Terminal menu, New Terminal; the shortcut that shows the terminal is ``Ctrl+` `` on Windows and Linux and ``Control+` `` on a Mac). The terminal opens at the folder that is open in the Explorer. Save this as `check_environment.py` in the folder, then run it with `uv run check_environment.py`:

```python
"""Check this computer for Part 4. Run it with: uv run check_environment.py"""
import subprocess
import sys


def first_line(*command):
    """The first line a command prints, or None if it cannot run."""
    try:
        done = subprocess.run(command, capture_output=True, text=True, check=True)
    except (OSError, subprocess.CalledProcessError):
        return None
    return done.stdout.strip().split("\n")[0] or None


version = ".".join(str(part) for part in sys.version_info[:3])
named = first_line("git", "config", "user.name") and first_line("git", "config", "user.email")
checks = [
    ("Python 3.11 or newer", version if sys.version_info >= (3, 11) else None, "uv run --python 3.13 check_environment.py"),
    ("Git", first_line("git", "--version"), "install Git, then open a new terminal"),
    ("Git name and email", "set" if named else None, 'git config --global user.name "Your Name" (and user.email)'),
    ("uv", first_line("uv", "--version"), "install uv, then open a new terminal"),
]
passed = 0
for label, found, fix in checks:
    if found:
        passed += 1
        print(f"PASS  {label}: {found}")
    else:
        print(f"FAIL  {label}\n      Fix: {fix}")
print(f"{passed} of {len(checks)} checks passed.")
sys.exit(0 if passed == len(checks) else 1)
```

**Predict:** will all four lines pass on your laptop? If a line fails, what do you expect the script to print under it?

On the machine of this page, all four pass (your Python, Git and uv versions will differ):

```console

PASS  Git: git version 2.43.0
PASS  Git name and email: set
PASS  uv: uv 0.11.32 (x86_64-unknown-linux-gnu)
4 of 4 checks passed.
```

*Why:* each check asks one tool for its version, or for your name, and a tool that is missing counts as a failure with its fix printed under it. By default uv downloads a Python when it cannot find one on the system, and `uv run --python 3.13` asks for a version by number. Repeat the run until you see four `PASS` lines, then go on.

### 2. Folders and relative paths

**Idea.** A terminal stands in a *working folder*. `pwd` prints it, `ls` lists what it holds, `cd name` moves into a folder and `cd ..` moves up, because `..` means the folder above. A path that does not start with a slash is a *relative path*: it is read from the working folder. A path that starts with a slash, such as the one `pwd` prints, is an *absolute path*.

**Try it.** Save two files next to `check_environment.py`. The first downloads the orders from the course data into `data/orders.csv`. Save it as `download_data.py`:

```python
"""Download the cafe-sales orders into data/orders.csv. Run it with: uv run download_data.py"""
from pathlib import Path
from urllib.request import urlretrieve

URL = "https://raw.githubusercontent.com/datafromzero/datafromzero.github.io/v0.1.0/datasets/cafe-sales/v1/orders.csv"
OUT = Path("data/orders.csv")

OUT.parent.mkdir(exist_ok=True)
urlretrieve(URL, OUT)
print("saved", OUT, "with", OUT.stat().st_size, "bytes")
```

The second prints how many orders the file holds. Save it as `peek.py`:

```python
lines = open("data/orders.csv").read().splitlines()
print(len(lines) - 1, "orders; columns:", lines[0])
```

Run `uv run download_data.py`, then `ls`, `cd data`, `pwd`, `ls` and `cd ..`.

### 3. Small tools joined by pipes

**Idea.** Many terminal programs do one small job on text. `head -3 file` prints the first 3 lines, `wc -l file` counts lines, `cut -d, -f3 file` keeps the third comma-separated column, `tail -n +2` skips the first line, `sort` puts lines in order and `uniq -c` collapses repeated lines into one line with a count. A pipe, `|`, feeds the output of one program to the next. This is for a quick look at a file; the analysis stays in Python.

**Try it.** Look at the file, then count its lines. `data/orders.csv` holds 1,800 orders.

```console
head -3 data/orders.csv
wc -l data/orders.csv
```

**Predict:** what do the two commands print?

<details>
<summary>Reveal the result</summary>

```console
$ head -3 data/orders.csv
order_id,customer_id,store_id,ordered_at,status,payment_method
1001,15,2,2026-01-01 08:02:00,completed,mobile
1002,46,1,2026-01-01 15:38:00,completed,mobile
$ wc -l data/orders.csv
1801 data/orders.csv
```

</details>

*Why:* the first line is the header, so 1,800 orders make 1,801 lines.

**Try it.** Count the orders of each store, one stage at a time. The store is the third column.

```console
cut -d, -f3 data/orders.csv | head -3
cut -d, -f3 data/orders.csv | tail -n +2 | head -3
cut -d, -f3 data/orders.csv | tail -n +2 | sort | uniq -c
```

**Predict:** what does each of the three lines print?

<details>
<summary>Reveal the result</summary>

```console
$ cut -d, -f3 data/orders.csv | head -3
store_id
2
1
$ cut -d, -f3 data/orders.csv | tail -n +2 | head -3
2
1
2
$ cut -d, -f3 data/orders.csv | tail -n +2 | sort | uniq -c
    729 1
    716 2
    355 3
```

</details>

*Why:* the first stage keeps one column, header included; `tail -n +2` drops the header; `sort` and `uniq -c` turn 1,800 store numbers into three counts that add up to 1,800. The counts include the canceled order.

### 4. The fallback: a codespace

**Idea.** If you have no laptop you can install on, or you work on a Chromebook or a phone, use a *codespace*: a development environment hosted in the cloud, which you open from a browser. It runs in a Linux environment, so the Linux commands of unit 1 apply. GitHub Free includes 120 compute hours a month, and without a payment method on file, usage is blocked once the quota is used up. A codespace stops after 30 minutes without activity by default.

**Try it.** On GitHub, click the plus icon, choose New repository, name it `cafe-report`, turn Add README on and create it. On the repository page, click Code, then the Codespaces tab, then the plus icon. In the terminal of the codespace, save `check_environment.py` as in unit 1 and run it with `python3 check_environment.py`. If it reports that uv is missing, run the Linux install line of unit 1 and open a new terminal.

**Predict:** you commit a change in the codespace on Monday but never push it, and you never open the codespace again. Two months later, is your commit on GitHub, and is the codespace still there?

<details>
<summary>Reveal the result</summary>

Neither. The commit exists only in the codespace, and the codespace is deleted automatically after it has been stopped and inactive for 30 days (the default; you can set 0 to 30 days). The deletion happens whether or not the codespace holds unpushed changes.

</details>

*Why:* a codespace is a machine that GitHub hosts and may delete; only what you pushed to the repository survives. From a codespace, the Source Control view offers Commit & Push, and its token can write to the repository it was created from. The next lesson shows what a commit is and practices `git push`.

- With no laptop, use a codespace, and push before you leave: stopped codespaces are deleted.

**Common trap:** treating a terminal as if it stood in the folder of the file you are working on. The script that ran from one folder fails from the next.

</Aside>

## On your own

**Which hour of the day is busiest?** Before you start, say what the result looks like: one line, a count and an hour. The fourth column holds the time, such as `2026-01-01 08:02:00`. Count the orders of each hour of the day over the whole file and print only the busiest one. Work in the terminal, in the project folder.

<details>
<summary>Hint</summary>

`cut -c12-13` keeps characters 12 and 13 of each line, which are the hour. `sort -rn` sorts numbers, largest first, and `head -1` keeps one line.

</details>

<details>
<summary>Half-solution</summary>

Expected output in words: *"One line: a count of a bit under 200 orders, then an hour of the day."*

```console
cut -d, -f4 data/orders.csv | tail -n +2 | cut -c12-13 | ...
```

</details>

<Solution>

```console
$ cut -d, -f4 data/orders.csv | tail -n +2 | cut -c12-13 | sort | uniq -c | sort -rn | head -1
    181 10
```

The busiest hour is 10, with 181 of the 1,800 orders; hour 07 follows with 172. The first `sort` groups the hours, `uniq -c` counts them, and `sort -rn` puts the largest count first.

</Solution>

</Exercise>

**Spot the flaw.** A colleague counts the orders of each store and reports "1,135 stores", then shrugs and says the file must be messy. The command was:

```console
cut -d, -f3 data/orders.csv | tail -n +2 | uniq -c | wc -l
```

Run it and say what the command counted and what a correct count needs. Expected: one number, 1135.

<details>
<summary>Hint</summary>

Run it without `| wc -l` and look at the first lines. Does each store appear once?

</details>

<details>
<summary>Half-solution</summary>

```console
cut -d, -f3 data/orders.csv | tail -n +2 | uniq -c | head -4
```

</details>

<Solution>

```console
$ cut -d, -f3 data/orders.csv | tail -n +2 | uniq -c | head -4
      1 2
      1 1
      1 2
      1 1
$ cut -d, -f3 data/orders.csv | tail -n +2 | sort | uniq -c | wc -l
3
```

`uniq` compares only neighboring lines, so a store number that comes back after another one starts a new line: 1,135 stretches of equal numbers, not 3 stores. Sorting first puts equal lines next to each other, and the count becomes 3.

</Solution>
