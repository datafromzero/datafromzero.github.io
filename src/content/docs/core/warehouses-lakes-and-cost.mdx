## The question

The owner of the three cafes has an offer from a supplier: a data warehouse, billed at about six dollars for each terabyte a query reads. The sales live in a CSV file of 1,800 orders and in the till's own database.

> Why isn't the till's database the warehouse, what is a "data lake", and what would my weekly report cost?

Two kinds of work already show in the cafes:

| the work | what it touches | who does it |
|---|---|---|
| ring up an order | one whole row, written the moment the customer pays | the till, all day |
| the weekly report | two or three columns of every row, read once | the owner, on Monday |

## The big idea

A warehouse is a database built to read a few columns of many rows, a lake is files kept as they arrived, and a cloud query is billed by the bytes it scans.

### 1. Two kinds of work, two ways to store a table

**Idea.** AWS describes OLTP, online transaction processing, as storing and updating transactional data reliably in high volumes, and OLAP, online analytical processing, as combining and grouping data to analyze it. A *row store* keeps the values of one row together, which suits the till: an order is written and read in one place. A *column store* keeps the values of one column together, which suits the report. Parquet is a column-oriented file format, and DuckDB's Parquet reader pushes filters and projections into the file scan, so a column the query does not use is not read.

**Try it.** Save as `peek_parquet.py` in the project folder and run it with `uv run python peek_parquet.py`. DuckDB's `parquet_metadata` lists what is inside a Parquet file, and `total_compressed_size` is the bytes of each column's data:

```python
import duckdb

print(
    duckdb.sql("""
    SELECT path_in_schema AS column_name, total_compressed_size AS bytes
    FROM parquet_metadata('data/orders.parquet')
    ORDER BY bytes DESC
""")
)
```

**Predict:** Which column takes the most space in the file, and which the least?

<details>
<summary>Reveal the result</summary>

```text
┌────────────────┬───────┐
│  column_name   │ bytes │
│    varchar     │ int64 │
├────────────────┼───────┤
│ ordered_at     │ 14453 │
│ order_id       │  9791 │
│ customer_id    │  2509 │
│ store_id       │   570 │
│ payment_method │   550 │
│ status         │   104 │
└────────────────┴───────┘
```

These numbers come from the file that `--parquet` of C31 writes (pandas with pyarrow 26.0.1); other versions may give other sizes.

</details>

*Why:* `ordered_at`, a different time for almost every order, is the largest, and `status`, which holds only two words, is the smallest by far. The values of one column look alike, so they compress well when they sit together. The whole file is 31,526 bytes against 82,348 for the CSV. A report that needs `store_id` and `status` reads two of the six columns, and the other four are not touched. Delete `peek_parquet.py`. *Goes deeper:* the Data Engineer track lesson *Storage shapes: rows, columns and files*.

### 2. A warehouse and a lake

**Idea.** AWS describes a *data lake* as a repository that stores structured and unstructured data as it is, without first structuring it, and says its schema is not defined when the data is captured. A *data warehouse* is the other way round: the structure is defined in advance, to make SQL queries fast, and the data is cleaned and transformed so that people can trust it. So the lake decides the shape when you read, and the warehouse decides it when you load.

**Try it.** Save as `lake_demo.py` and run it. The first two lines read the same CSV file twice, as a reader would from a lake; the rest loads a value into a table that declared its type, as into a warehouse:

```python
import duckdb


def types(query):
    return {name: kind for name, kind, *_ in duckdb.sql("DESCRIBE " + query).fetchall()}


print(types("SELECT * FROM read_csv('data/orders.csv')"))
print(types("SELECT * FROM read_csv('data/orders.csv', all_varchar=true)"))

duckdb.sql("CREATE TABLE stage (order_id INTEGER, ordered_at TIMESTAMP)")
duckdb.sql("INSERT INTO stage VALUES (1, '2026-01-01 08:02:00')")
try:
    duckdb.sql("INSERT INTO stage VALUES ('twelve', '2026-01-01 09:00:00')")
except duckdb.ConversionException as error:
    print(str(error).splitlines()[0])
```

**Predict:** What types does each read give, and what happens to the row with `'twelve'`?

<details>
<summary>Reveal the result</summary>

```text
{'order_id': 'BIGINT', 'customer_id': 'BIGINT', 'store_id': 'BIGINT', 'ordered_at': 'TIMESTAMP', 'status': 'VARCHAR', 'payment_method': 'VARCHAR'}
{'order_id': 'VARCHAR', 'customer_id': 'VARCHAR', 'store_id': 'VARCHAR', 'ordered_at': 'VARCHAR', 'status': 'VARCHAR', 'payment_method': 'VARCHAR'}
Conversion Error: Could not convert string 'twelve' to INT32
```

</details>

*Why:* each reader chose the types, guessed in the first read and all text in the second: that is a lake, files read where they lie, with the shape decided by the reader. The declared `INTEGER` column refused `'twelve'` at the door, so wrong data cannot get in: that is the warehouse, shape first, load second. A lake fits when data arrives in many shapes and the questions are not known; a warehouse fits when the owner needs numbers that reconcile. Delete `lake_demo.py`. *Goes deeper:* the Data Engineer track lesson *File formats and partitioning*.

### 3. What a scan costs

**Idea.** On BigQuery's on-demand model you are charged for the bytes each query processes, and the pricing page says you are charged for the data in the columns you select. It counts *logical* bytes, which are uncompressed and fixed by the type: the BigQuery data types page gives 8 bytes for a whole number or a date, 16 for a decimal, 1 for a BOOL, and 2 bytes plus the UTF-8 size for text, with a null counting as 0. A tebibyte (TiB) is 2^40 bytes.

<Aside type="note" title="Price box, read on 2026-11-22">

BigQuery on-demand queries: **$6.25 per TiB** processed; the first 1 TiB each month is free; charges are rounded up to the nearest MB, with a minimum of 10 MB processed per table a query references and per query; the page does not say how many bytes an MB is. Source: the BigQuery pricing page, read on 2026-11-22. Prices change: read the page again before you rely on a number.

</Aside>

**Try it.** The logical bytes of each column of `orders`. Whole numbers and the timestamp are 8 bytes each, a null is free, and text is 2 bytes plus its length:

<RunSQL query={`WITH sizes AS (
  SELECT 'order_id' AS column_name, 8 * COUNT(order_id) AS bytes FROM orders
  UNION ALL SELECT 'customer_id', 8 * COUNT(customer_id) FROM orders
  UNION ALL SELECT 'store_id', 8 * COUNT(store_id) FROM orders
  UNION ALL SELECT 'ordered_at', 8 * COUNT(ordered_at) FROM orders
  UNION ALL SELECT 'status', SUM(2 + strlen(status)) FROM orders
  UNION ALL SELECT 'payment_method', SUM(2 + strlen(payment_method)) FROM orders
)
SELECT column_name, bytes, ROUND(bytes / POWER(2, 40) * 6.25 * 1000000, 2) AS micro_dollars
FROM sizes
ORDER BY bytes DESC;`} />

**Predict:** Unit 1 ranked the columns by their size in the Parquet file. Which column is the largest by this count?

Expected: 6 rows, 3 columns; `micro_dollars` is the price in millionths of a dollar.

*Why:* `status` comes first with 19,799 bytes, although it was the smallest column in the file. Every `'completed'` counts 2 + 9 bytes, and compression does not change the count: BigQuery's cost page says on-demand queries are always charged by logical, uncompressed bytes. `customer_id` has 14,392 bytes, not 14,400, because one order has no customer.

All six columns come to 89,283 bytes. A report that reads only `store_id` and `status` reads 14,400 + 19,799 = 34,199 bytes, about 38 percent of that: naming the columns you need is the first way to cut a bill, and the same table costs very different amounts depending on how it is read. The pricing page names a second way: partitioning and clustering a table reduce the data a query processes. At this size every price is far below a cent and the first TiB each month is free, so the minimum of about 10 MB per table matters more than the data; the ratio is what carries to a table a million times larger. *Goes deeper:* the Data Engineer track lesson *File formats and partitioning*.

### 4. Totals that add up, and totals that do not

**Idea.** Kimball Group calls a measure *additive* when it can be summed across any dimension of its fact table, and *non-additive* when it cannot, such as a ratio. Units and sales are additive: the sum of the days is the week. For a measure that is not, their advice is to store its additive components, and to sum them before the final calculation.

**Try it.** For Monday April 6 to Sunday April 12, add up the number of different customers who ordered on each day, and compare it with the number of different customers in the whole week (completed orders; a walk-in order with no customer is not counted):

<RunSQL query={`WITH daily AS (
  SELECT CAST(ordered_at AS DATE) AS day, COUNT(DISTINCT customer_id) AS customers
  FROM orders
  WHERE status = 'completed' AND CAST(ordered_at AS DATE) BETWEEN DATE '2026-04-06' AND DATE '2026-04-12'
  GROUP BY day
)
SELECT SUM(customers) AS sum_of_daily,
       (SELECT COUNT(DISTINCT customer_id) FROM orders
        WHERE status = 'completed' AND CAST(ordered_at AS DATE) BETWEEN DATE '2026-04-06' AND DATE '2026-04-12') AS week_distinct
FROM daily;`} />

**Predict:** Will the sum of the daily counts be smaller than, equal to, or larger than the count of the week?

Expected: 1 row, 2 columns.

*Why:* 80 against 58. A customer who comes on three days is counted three times in the sum and once in the week, so the daily counts measure visits by different people, not people. A table that stores the daily count cannot give the weekly one; store what does add, here the orders with their customer, and count again for any week. An average has the same trouble: store the total sales and the number of orders, and divide at the end. *Goes deeper:* the Data Engineer track lesson *Dimensional models and slowly changing dimensions*.

<Aside type="tip" title="Remember">

- OLTP writes whole rows all day; OLAP reads a few columns of many rows. Column storage suits the second.
- A lake keeps files as they arrived and the reader decides the shape; a warehouse decides the shape when it loads.
- On-demand pricing follows the logical bytes of the columns a query reads, so name the columns you need.
- Units and sales add up; distinct counts, averages and ratios do not.

**Common trap:** adding up daily distinct counts to get a weekly one. 80 daily customers were 58 customers.

</Aside>

<details>
<summary>A model of <code>logical_bytes</code></summary>

```python
def logical_bytes(con: duckdb.DuckDBPyConnection, table: str, columns: list[str]) -> int:
    """Count the bytes BigQuery would see in `columns` of `table`, with its size for each type.

    A whole number or a date is 8 bytes, a decimal 16, a boolean 1, text 2 bytes plus its UTF-8
    size, and a null 0.
    """
    types = dict(
        con.execute(
            "SELECT column_name, data_type FROM information_schema.columns WHERE table_name = ?",
            [table],
        ).fetchall()
    )
    total = 0
    for column in columns:
        if types[column] == "VARCHAR":
            size = f"COALESCE(SUM(2 + strlen({column})), 0)"
        elif types[column].startswith("DECIMAL"):
            size = f"16 * COUNT({column})"
        elif types[column] == "BOOLEAN":
            size = f"COUNT({column})"
        else:
            size = f"8 * COUNT({column})"
        total += con.execute(f"SELECT {size} FROM {table}").fetchone()[0]
    return total
```

`PRICE_PER_TIB` is `6.25`, `BYTES_PER_TIB` is `2**40` and `MINIMUM_BYTES` is `10 * 2**20`, an assumption about the unit of the page's "10 MB".

</details>
