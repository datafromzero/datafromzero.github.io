## The question

The Harbor manager asks the analyst two things on the same day:

> Which version of the script gave me last week's numbers? And yesterday someone edited `peek.py`: can we get the old one back?

Nobody can answer, because the folder keeps only the latest copy of each file. This is the folder from the last lesson:

| file | what it holds |
|---|---|
| `check_environment.py` | the setup check |
| `download_data.py` | downloads `data/orders.csv` |
| `peek.py` | prints the number of orders |
| `data/orders.csv` | the 1,800 orders, downloaded |

By the end you can save the folder as a history of snapshots, read what changed, go back to an earlier version, and keep data and passwords out of it.

<Aside type="note" title="You already know this">

**Match.** In [*Your laptop setup and the terminal*](/core/laptop-setup-and-terminal/) (C22) you ran `git config --global` so that Git knows your name and email; Git writes both into every <Term id="glossary-commit-git">commit</Term>. Here you make the commits.

**Diverge.** You may have saved files as `orders_v2_final.xlsx`, one copy for each version. Git keeps one folder and a list of snapshots of it, and unit 1 shows what a snapshot holds.

</Aside>

## Learn by doing

About 50 minutes, 4 new ideas: commits and the staging area, reading changes and history, restoring files, and keeping files out. Run every command in the terminal of VS Code, in `cafe-report`, the project folder you made in [*Your laptop setup and the terminal*](/core/laptop-setup-and-terminal/#1-three-tools-and-a-check-script) (C22). Your hashes, dates and byte counts differ from the ones printed here.

### 1. A commit saves what you staged

**Idea.** A *repository* is a project folder with a hidden `.git` folder that keeps its history. A *commit* is a saved snapshot of the files you chose, with your name, a date and a message that says what changed and why. Git saves a file only after you *stage* it: `git add` stages, and `git commit -m "message"` saves what is staged. `git status` shows where each file stands.

**Try it.** Start the repository, stage the three scripts, and commit:

```console
git init -b main
git status
git add check_environment.py download_data.py peek.py
git status -s
git commit -m "Add the environment check, the download script and peek"
```

**Predict:** what does the first `git status` say about the four items of the folder, and what does `git status -s` show for the three scripts and for `data/` after the `git add`?

<details>
<summary>Reveal the result</summary>

```console
$ git init -b main
Initialized empty Git repository in /home/ana/cafe-report/.git/
$ git status
On branch main

No commits yet

Untracked files:
  (use "git add <file>..." to include in what will be committed)
        check_environment.py
        data/
        download_data.py
        peek.py

nothing added to commit but untracked files present (use "git add" to track)
$ git add check_environment.py download_data.py peek.py
$ git status -s
A  check_environment.py
A  download_data.py
A  peek.py
?? data/
$ git commit -m "Add the environment check, the download script and peek"
[main (root-commit) f12d4b4] Add the environment check, the download script and peek
 3 files changed, 43 insertions(+)
 create mode 100644 check_environment.py
 create mode 100644 download_data.py
 create mode 100644 peek.py
```

</details>

*Why:* Git does not put a file into a snapshot until you stage it, so all four items began untracked. After the `git add`, `A` in the left column marks a staged new file, and `data/` is still `??`: the commit holds exactly the three files you staged. The code in brackets names the commit, and `(root-commit)` marks the first commit of a repository, the one with no parent; the later commits print only the branch and the code.

### 2. Read the changes and the history

**Idea.** Between your folder and the last commit sits the staging area, and Git can compare either pair: `git diff` and `git diff --staged` each show one comparison, as lines marked `+` (added) and `-` (removed). `git log` lists the commits, newest first, and `git log --oneline` prints one line each.

**Try it.** Add a third line to `peek.py`, `print("first order at", lines[1].split(",")[3])`, then look at the change before and after you stage it, commit it, and read the history:

```console
git status -s
git diff
git add peek.py
git diff
git diff --staged
git commit -m "Print the time of the first order"
git log --oneline
git log -1
```

**Predict:** what does `git diff` print before the `git add`, and what do `git diff` and `git diff --staged` print right after it?

<details>
<summary>Reveal the result</summary>

```console
$ git status -s

?? data/
$ git diff
diff --git a/peek.py b/peek.py
```

*Why:* before the `git add`, `git status -s` shows the change as `M` in the second column, after a space: modified, not staged. `git diff` compares your folder with the staging area, so it printed nothing once the change was staged; `git diff --staged` compares the staging area with the last commit, so it showed the change. The log lists the newest commit first, and its `Author` line is the name and email of C22. A message that says what changed keeps this list readable a month later.

### 3. Go back with `git restore`

**Idea.** `git restore file` replaces the file in your folder with the version in the staging area, or in the last commit when nothing is staged. With `--source=` it takes the file from any commit you name, and `HEAD~1` names the commit before the last one. A change that was never committed is almost certainly lost, so use `git restore` on purpose.

**Try it.** Overwrite `peek.py` with the word `oops`, then restore it, then pull the older version of the file from the commit before the last one, and look at the file each time:

```console
echo "oops" > peek.py
cat peek.py
git restore peek.py
cat peek.py
git restore --source=HEAD~1 peek.py
cat peek.py
git status -s
git restore peek.py
```

**Predict:** what does `cat peek.py` print after each of the three steps, and what does `git status -s` say after the `--source` step?

<details>
<summary>Reveal the result</summary>

```console
$ echo "oops" > peek.py
$ cat peek.py
oops
$ git restore peek.py
$ cat peek.py
lines = open("data/orders.csv").read().splitlines()
print(len(lines) - 1, "orders; columns:", lines[0])
print("first order at", lines[1].split(",")[3])
$ git restore --source=HEAD~1 peek.py
$ cat peek.py
lines = open("data/orders.csv").read().splitlines()
print(len(lines) - 1, "orders; columns:", lines[0])
$ git status -s
 M peek.py
?? data/
$ git restore peek.py
```

</details>

*Why:* the plain `git restore` brought back the last commit's version, and `--source=HEAD~1` the older, shorter one, which differs from the last commit, so `git status -s` calls the file modified. Both versions were in commits; the word `oops` was in none, so it is almost certainly lost.

### 4. Keep out what you can fetch and what you must not share

**Idea.** A file named `.gitignore` lists patterns of files that Git leaves alone: `data/` for a folder, `*.log` for every file that ends in `.log`, `.env` for one file. Commit it, so that every copy of the project shares the rules. Three kinds of file stay out: data you can download again, environments and caches, and secrets such as passwords and keys.

**Try it.** Save this as `.gitignore` in the project folder, look at the status, and commit it:

```text
# the data is downloaded again when needed; never commit it
data/

# environments and caches
.venv/
__pycache__/

# secrets
.env
```

```console
git status -s
git add .gitignore
git commit -m "Ignore the data, environments and secrets"
git status
```

**Predict:** what does `git status -s` list now, and what does `git status` say after the commit?

<details>
<summary>Reveal the result</summary>

```console
$ git status -s
?? .gitignore
$ git add .gitignore
$ git commit -m "Ignore the data, environments and secrets"
[main d566b21] Ignore the data, environments and secrets
 1 file changed, 9 insertions(+)
 create mode 100644 .gitignore
$ git status
On branch main
nothing to commit, working tree clean
```

</details>

*Why:* `data/` no longer shows as untracked, and the download script is the recipe for the data. Your project now has three commits.

**Try it.** Now see what a mistake costs. In a scratch folder next to the project, commit a file `.env` that holds a made-up key, delete it in the next commit, and read the log with the patches (`-p`):

```console
cd ..
mkdir secret-demo
cd secret-demo
git init -b main
echo "API_KEY=not-a-real-key" > .env
git add .env
git commit -m "Add settings"
git rm .env
git commit -m "Remove the key"
ls -a
git log --oneline -p
```

**Predict:** after the second commit, is the key in the folder? Is it anywhere `git log --oneline -p` shows?

<details>
<summary>Reveal the result</summary>

```console
$ ls -a
.  ..  .git
$ git log --oneline -p
7b090d2 Remove the key
diff --git a/.env b/.env
deleted file mode 100644
index 883ebd1..0000000
--- a/.env
+++ /dev/null
@@ -1 +0,0 @@
-API_KEY=not-a-real-key
449e194 Add settings
diff --git a/.env b/.env
new file mode 100644
index 0000000..883ebd1
--- /dev/null
+++ b/.env
@@ -0,0 +1 @@

```

</details>

*Why:* the folder no longer has the file, and both commits still show the key: the second one as a deleted line, the first one as an added line. Pro Git says that anything committed can almost always be recovered, which is the point of a history and the problem for a secret. GitHub's advice is to revoke or rotate the secret first. Go back with `cd ../cafe-report`; the scratch folder can be deleted.

<Aside type="tip" title="Remember">

- A commit is a snapshot of the files you staged: `git add` first, then `git commit -m "what changed and why"`.
- `git status -s` shows where each file stands; `git diff` and `git diff --staged` show the two comparisons.
- `git log --oneline` reads the history, newest first.
- `git restore file` brings back the last commit's version; `--source=HEAD~1` takes it from the commit before.
- `.gitignore` keeps out data you can fetch, environments, caches and secrets, and you commit it.

**Common trap:** thinking that deleting a committed secret removes it. The key stays in the history and works until you revoke it.

</Aside>

<Exercise id="core-git-save-history-1">

**Keep a copy somewhere else.** A repository can send its commits to another repository, called a *remote*; the usual name for the one you cloned from or push to is `origin`. Here the other copy is a second, bare repository in a folder next to the project, made with `git init --bare`. On GitHub you would paste the address of a new repository instead. In the project folder, the first two steps are given; finish the push and read the status. Expected: output that contains a line ending in `main -> main`, and a `git status` that says the branch is up to date with `origin/main`.

```console
git init --bare -b main ~/cafe-report-backup.git
git remote add origin ~/cafe-report-backup.git
```

The first `git status -s` listed seven entries, all untracked. Four rules hide five of them: `*.log` covers both log files, and the folder rule hides `__pycache__/` with the file inside. The scratch folder can be deleted; then `cd ~/cafe-report`.

<details>
<summary>Hint</summary>

<Solution>

```console
$ git rm --cached data/orders.csv
rm 'data/orders.csv'
$ git status -s
D  data/orders.csv
?? .gitignore
$ ls data
orders.csv
```

A `.gitignore` rule does not affect files that Git already tracks, and the file was committed last week, so Git went on reporting its changes. `git rm --cached` removes the file from tracking and leaves it in the folder; after a commit, the rule hides it. The old commit still holds the data, which is why `.gitignore` comes before the first `git add`.
