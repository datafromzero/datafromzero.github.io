## The question

The owner of the three cafes asks:

> I want to see what the report did when it ran, and change the file name and a warning limit without touching code. I will also give you the key to the mailing service. It must never end up on GitHub, even by accident.

Three kinds of thing live in the repository, with three different homes:

| thing | example | where it lives |
|---|---|---|
| code | the function `orders_per_store` | in Git |
| a setting | the orders file, the lowest number of orders before a warning | a file in Git |
| a secret | the key of the mailing service | outside Git |

By the end you can make the report say what it did, read its settings from a file, read a key from the environment, and search the history for a key.

Settings in a file and logging are their grown-up forms.

**Diverge.** A parameter at the top of a script travels with the code. Unit 2 moves it to a file an argument can override; unit 3 moves a secret out of the repository.

## Learn by doing

About 35 minutes, 4 new ideas: logging with levels, settings in a file, a secret from the environment, and a search of the history for a key. Work in `cafe-report` after C27 (repository clean), in the terminal; unit 4 uses a throwaway folder outside it.

### 1. Log with levels, not print

**Idea.** `print` has one level: always. The `logging` module has five, from `DEBUG` to `CRITICAL`: the Python HOWTO calls `INFO` confirmation that things are working as expected, `WARNING` an indication that something unexpected happened, and `ERROR` a function that could not be performed. Each module gets its own logger with `logging.getLogger(__name__)`, and the entry point configures once what is shown and how it looks.

**Try it.** In `cafe_report/load.py` and `cafe_report/summary.py`, add `import logging` and a logger below the imports, and two messages:

```python
log = logging.getLogger(__name__)
```

```python
# load.py: the end of read_orders
    with open(path, newline="") as file:
        orders = list(csv.DictReader(file))
    log.info("read %d orders from %s", len(orders), path)
    return orders
```

```python
# summary.py: before `return counts`
    log.info("%d completed orders since %s", sum(counts.values()), since)
    if not counts:
        log.warning("no completed orders since %s", since)
```

Run the report from April 1 and from a day after the last order, with nothing configured yet:

```bash
uv run python -m cafe_report data/orders.csv --since 2026-04-01
uv run python -m cafe_report data/orders.csv --since 2026-07-01
```

**Predict:** Which of the two runs prints a log line, and which one?


*Why:* the HOWTO says the default level is `WARNING`, and the logging module page says the root logger is created with `WARNING`, so the `INFO` lines stay hidden and the July warning gets through. `basicConfig(level=logging.INFO)` lets `INFO` and above through, and the `format` names the parts of each line: level, logger name (the module) and message; add `%(asctime)s` for the time. The values are passed as arguments, which the HOWTO says are merged into the message only when it is shown. The call to `basicConfig` should come before any logger call, so it is the first line of `main`.

### 2. Move settings into a file

**Idea.** A setting is a value that differs between runs or machines while the logic stays the same: a file name, a level, a limit. The Twelve-Factor App asks for a strict separation of config from code. Keep the settings in a TOML file next to the code, give each one a default in code, and let the command line carry the same settings. `tomllib` reads TOML from a file opened in binary mode and returns a dictionary.

**Try it.** Create `cafe-report.toml` in the project folder, and `cafe_report/config.py`:

```toml
orders_file = "data/orders.csv"
log_level = "INFO"
min_orders = 360
```

```python
import tomllib
from pathlib import Path

DEFAULTS = {"orders_file": "data/orders.csv", "log_level": "WARNING", "min_orders": 0}


def load_config(path="cafe-report.toml"):
    config = dict(DEFAULTS)
    if Path(path).exists():
        with open(path, "rb") as f:
            config.update(tomllib.load(f))
    return config
```

In `cli.py`, import `load_config` from `cafe_report.config` and add `log = logging.getLogger(__name__)` below the imports. In `main`, the file argument becomes optional, there is a new `--log-level` option, the settings choose the file and the level (the fixed `basicConfig` line of unit 1 moves below `config`), and `orders_file` replaces `args.orders_file` in both branches and both messages:

```python
    parser.add_argument("orders_file", nargs="?", help="path to orders.csv (default: the file in cafe-report.toml)")
    parser.add_argument("--log-level", help="DEBUG, INFO, WARNING or ERROR (default: the level in cafe-report.toml)")
    args = parser.parse_args(argv)
    config = load_config()
    logging.basicConfig(level=args.log_level or config["log_level"], format="%(levelname)s %(name)s: %(message)s")
    orders_file = args.orders_file or config["orders_file"]
```

The first line replaces the old `orders_file` argument. Each store under `min_orders` gets a warning, so the end of `main` becomes:

```python
    for store_id in sorted(counts):
        if counts[store_id] < config["min_orders"]:
            log.warning("store %s has %d orders since %s, under %d", store_id, counts[store_id], args.since, config["min_orders"])
        print(f"store {store_id}: {counts[store_id]} orders")
```

Run the report with no file and no level, then with the level on the command line:

### 3. A secret comes from the environment

**Idea.** A secret is a value that must not be readable by everyone who can read the repository. The Twelve-Factor App gives a test: the codebase could be made open source at any moment without compromising any credentials. A running program reads the environment variables of its process with `os.getenv("NAME")`, which returns the value as a string, or a default if the variable does not exist. Keep the value in a file named `.env`, commit `.env.example` with a placeholder, and have uv load the file for one run with `uv run --env-file .env`.

**Try it.** The mailing service does not exist yet, so `--send` only checks that the key is there and logs that the report would be sent; `demo-key-not-real` stands for a real key. Add `import os` at the top of `config.py` and this function:

```python
def get_token():
    token = os.getenv("CAFE_REPORT_TOKEN")
    if not token:
        raise SystemExit("cafe_report: set CAFE_REPORT_TOKEN (see .env.example)")
    return token
```

In `cli.py`, import `get_token` with `load_config`, add `parser.add_argument("--send", action="store_true", help="check the key of the mailing service")` after `--log-level`, add `if args.send: get_token()` as the first lines after `args = parser.parse_args(argv)`, and these as the last lines of `main`:

```python
    if args.send:
        log.info("the report would be sent now")
```

### 4. Search the whole history for a key

**Idea.** Git keeps every commit, and everyone who clones the repository gets the history. `git log -S"text"` lists the commits that add or remove that text, in any file, so it answers one question before you share a repository: did this key ever go in?

**Try it.** In a throwaway folder outside your project, commit a settings file with the made-up key, take the key out in the next commit, add one more file, and search; then search your own project for the same text:

```bash
cd ~
mkdir leak-demo
cd leak-demo
git init -b main
echo 'token = "demo-key-not-real"' > settings.toml
git add settings.toml
git commit -m "Add settings"
echo 'month = "2026-04"' > settings.toml
git commit -am "Take the key out of the settings"
echo notes > notes.txt
git add notes.txt
git commit -m "Add notes"
git log --oneline -S"demo-key-not-real"
cd ~/cafe-report
git log --all --oneline -S"demo-key-not-real"
```

**Predict:** How many commits does the search list in the throwaway folder, which ones, and what does it print in your project?

<details>
<summary>Reveal the result</summary>

```text
$ git log --oneline -S"demo-key-not-real"
abc1234 Take the key out of the settings
abc1234 Add settings
$ cd ~/cafe-report
$ git log --all --oneline -S"demo-key-not-real"
```

Your project prints nothing. Your hashes differ; these are masked.

</details>

*Why:* the git-log page describes `-S` as a search for differences that change the number of occurrences of the string, an addition or a deletion, so the commit that added the key and the one that removed it both show. `--all` searches every branch. Your project prints nothing: no commit ever changed that text. If a real repository lists a commit, treat the key as exposed: GitHub says the first step is to revoke or rotate it; removing the data from the history takes four steps, starting with `git filter-repo`, and commits with the data may stay accessible in forks, clones and cached views. GitHub's push protection blocks pushes that contain supported secrets, and its page says it is on by default for users pushing to public repositories; it is a net, not a replacement for the search. Delete the throwaway folder.

<Aside type="tip" title="Remember">

- Use `logging` with levels, a logger for each module, and configure it once in the entry point; the default level is `WARNING`.
- Settings go in a file with defaults in code, and an argument beats the file.
- A secret comes from the environment, loaded from a `.env` that Git ignores; commit only `.env.example`.
- `git log -S"text"` searches the whole history; a key that shows up there is rotated first.

**Common trap:** a real key in the file you commit as the example.

</Aside>
