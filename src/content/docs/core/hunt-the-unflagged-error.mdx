## The question

In *Find the planted error* (C39) every answer came with its class named. Now nothing is flagged. An assistant sends answers about the cafes. Some are wrong, and none says which. For each you end with a decision, accept, revise or reject, and one sentence of reason. The OECD / European Union (2026) AI literacy framework, written for school learners, names this competence: "Evaluate whether AI outputs should be accepted, revised or rejected." Its advanced level adds that learners "justify decisions" to accept, revise or reject.

Every AI answer here was written for this lesson, in the style of an assistant, and none is a real transcript or comes from a product. The schema and data-dictionary parts of your context pack:

## Learn by doing

About 35 minutes, 3 new ideas: a name that is almost right, a number from nowhere and accepting on evidence. Every block runs in the page, complete on its own.

### 1. The column that almost exists

**Idea.** Check every name an answer uses against the schema, and every name that exists against what the column means.

<Aside type="note" title="An answer written for this lesson">

**A. Revenue by category.** I summed quantity times price for each category, and coffee comes first.

</Aside>

**Try it.** The query of answer A, as written:

<RunSQL query={`SELECT p.category, SUM(oi.qty * p.price) AS revenue
FROM order_items oi
JOIN products p ON p.product_id = oi.product_id
GROUP BY p.category
ORDER BY revenue DESC;`} />

Expected: an error saying that table `oi` has no column named `qty`.

**Predict:** the schema above is the standard. How many names does this query use that the schema does not have? The error names only one.

*Why:* two: `qty` should be `quantity`, and `price` should be `unit_price_usd`. The engine stops at the first unknown name. Even with both fixed the query is wrong, because the dictionary says a line's amount takes the discount off, and `discount_usd` is nowhere in it.

<Aside type="note" title="An answer written for this lesson">

**B. Which home city of our customers brings in the most revenue?** Oakland, at 9,144.25 dollars, then Berkeley and Alameda.

</Aside>

**Try it.** The query of answer B, as written:

<RunSQL query={`SELECT s.city, SUM(oi.quantity * p.unit_price_usd - oi.discount_usd) AS revenue
FROM orders o
JOIN stores s ON s.store_id = o.store_id
JOIN order_items oi ON oi.order_id = o.order_id
JOIN products p ON p.product_id = oi.product_id
WHERE o.status = 'completed'
GROUP BY s.city
ORDER BY revenue DESC;`} />

Expected: 3 rows, 2 columns.

**Predict:** every name in B is in the schema and the query runs. In the dictionary, is `s.city` the column the question needs? If you put the right one in, will the three cities come in the same order?

**Try it.** The same query with the city of the customer:

<RunSQL query={`SELECT c.city, SUM(oi.quantity * p.unit_price_usd - oi.discount_usd) AS revenue
FROM orders o
JOIN customers c ON c.customer_id = o.customer_id
JOIN order_items oi ON oi.order_id = o.order_id
JOIN products p ON p.product_id = oi.product_id
WHERE o.status = 'completed'
GROUP BY c.city
ORDER BY revenue DESC;`} />

Expected: 3 rows, 2 columns.

*Why:* `stores.city` is where the cafe is; the question asked for the home city, `customers.city`. By home city Berkeley leads with 8,815.25, then Oakland with 8,750.50 and Alameda with 5,176.50, so the answer's winner is wrong. The walk-in order has no customer and no home city, so the total is 22,742.25 and not 22,749.25 (order 2075, the 20-sandwich extra zero, is inside both). The engine catches a name that is missing, never one that exists and means something else: a diff of names finds nothing here, and only the meaning in the dictionary separates the two.

**Decide.** For each answer, accept, revise or reject, with one sentence.

<details>
<summary>A decision in words</summary>

A: revise, because two names are wrong and the amount ignores the discount. B: reject, because it answers a question about stores, not customers; the revised query changes the leader.

</details>

### 2. A number from nowhere

**Idea.** A number counts only if code that ran on the real data, in this session, produced it. An assistant can state a figure without running anything; the figure may be right or wrong, and either way it is not yet yours.

<Aside type="note" title="An answer written for this lesson">

**C. How did the second quarter go?** The average order was $18.40 in the second quarter, up 7.6 percent on the first. Coffee brought in the most revenue.

</Aside>

**Predict:** no query has run behind answer C. Completed orders only, what are the average orders of the first quarter (January to March) and of the second (April to June), to the nearest dollar?

**Try it.** Reproduce the first claim:

<RunSQL query={`WITH order_totals AS (
  SELECT o.order_id, o.ordered_at, SUM(oi.quantity * p.unit_price_usd - oi.discount_usd) AS amount
  FROM orders o
  JOIN order_items oi ON oi.order_id = o.order_id
  JOIN products p ON p.product_id = oi.product_id
  WHERE o.status = 'completed'
  GROUP BY o.order_id, o.ordered_at
)
SELECT CASE WHEN ordered_at < '2026-04-01' THEN 'Q1' ELSE 'Q2' END AS quarter,
       COUNT(*) AS orders,
       ROUND(AVG(amount), 2) AS average_order
FROM order_totals
GROUP BY quarter
ORDER BY quarter;`} />

Expected: 2 rows, 3 columns.

**Try it.** Reproduce the second claim, for the second quarter:

<RunSQL query={`SELECT p.category, SUM(oi.quantity * p.unit_price_usd - oi.discount_usd) AS revenue
FROM orders o
JOIN order_items oi ON oi.order_id = o.order_id
JOIN products p ON p.product_id = oi.product_id
WHERE o.status = 'completed' AND o.ordered_at >= '2026-04-01' AND o.ordered_at < '2026-07-01'
GROUP BY p.category
ORDER BY revenue DESC;`} />

Expected: 4 rows, 2 columns.

*Why:* the averages are 12.24 and 12.91 (order 2075, the 20-sandwich extra zero, is in the second), a rise of 5.5 percent, so neither $18.40 nor 7.6 percent came from the data. Coffee does lead, with 6,470.25. The second claim was right and no code had produced it: it counts once you have reproduced it, and not before.

**Decide.** Accept, revise or reject answer C, with one sentence.

<details>
<summary>A decision in words</summary>

Revise: replace the average with 12.91 and the rise with 5.5 percent, and keep the claim about coffee, now reproduced. Only a number that code produced counts.

</details>

### 3. Accept only on evidence

**Idea.** Accept an answer only after the checks you can run have run, and say which.

<Aside type="note" title="An answer written for this lesson">

**D. The three products that sold the most units, completed orders.** Latte 653, Croissant 503, Cappuccino 472.

</Aside>

**Try it.** The query of answer D, as written, and then a second route that never joins `products`:

<RunSQL query={`SELECT p.product_name, SUM(oi.quantity) AS units
FROM order_items oi
JOIN orders o ON o.order_id = oi.order_id
JOIN products p ON p.product_id = oi.product_id
WHERE o.status = 'completed'
GROUP BY p.product_name
ORDER BY units DESC, p.product_name
LIMIT 3;`} />

Expected: 3 rows, 2 columns.

<RunSQL query={`SELECT oi.product_id, SUM(oi.quantity) AS units
FROM order_items oi
JOIN orders o ON o.order_id = oi.order_id
WHERE o.status = 'completed'
GROUP BY oi.product_id
ORDER BY units DESC, oi.product_id
LIMIT 3;`} />

Expected: 3 rows, 2 columns.

**Predict:** the first query joins `products`, the second does not. Will the three unit counts be the same, or will the join have changed one of them?

*Why:* the same three counts, for product ids 3, 10 and 4. Every name is in the schema, and the join to `products` is by its key, so a product matches one row and nothing repeats. The routine can end in accept, once the checks have run.

**Decide.** Accept, revise or reject answer D, with one sentence.

<details>
<summary>A decision in words</summary>

Accept: every name matches the schema, and the units agree with a route that skips the join.

</details>

<Aside type="note" title="As of 2026-11-22: what a published benchmark measured">

Lei and colleagues (ICLR 2025) gave one code agent, built on o1-preview, three SQL tests. It solved 91.2 percent of Spider 1.0, 73.0 percent of BIRD and 21.3 percent of Spider 2.0, 632 problems built from real enterprise workflows. The more realistic the setting, the less an answer can be taken as it comes. A newer system may score higher; the checks of this lesson do not depend on the score. This box is reviewed every six months.

</Aside>

<Aside type="tip" title="Remember">

- Diff every name against the schema, then read what each name means in the dictionary.
- A number counts only if code that ran on the real data produced it, even when it is right.
- Run the same checks on every answer, including the ones that look fine.
- End every answer with accept, revise or reject and one sentence of reason.

**Common trap:** taking a name's existence as proof that it is the right column, and an answer with no error as proof that it is right.

</Aside>

**E. How many different customers shopped at each cafe?** Old Town 728, Campus 716, Harbor 355.

<RunSQL query={`SELECT s.store_name, COUNT(*) AS customers
FROM orders o
JOIN stores s ON s.store_id = o.store_id

GROUP BY s.store_name

**F. How many orders were paid by credit card? None: the query below returned 0.**

<RunSQL query={`SELECT COUNT(*) AS orders
FROM orders
WHERE payment_method = 'credit card';`} />

**G. Which product was never sold?** Pumpkin Spice Latte.

<RunSQL query={`SELECT product_name
FROM products
WHERE product_id NOT IN (SELECT product_id FROM order_items);`} />

**H. Payments.** Mobile payments were 32.9 percent of completed orders, and Harbor had the highest share at 36 percent.

<RunSQL query={`-- Write your query here, then press Run.`} />

<details>
<summary>Hint</summary>

For E, count rows against distinct customers. For F, list the distinct values of the column it filters. For G, count the empty values in the column inside the `NOT IN`. For H, no query has run: reproduce both numbers.

</details>

<details>
<summary>Half-solution</summary>

```sql
SELECT s.store_name,
       ROUND(100.0 * COUNT(*) FILTER (WHERE o.payment_method = 'mobile') / COUNT(*), 1) AS mobile_pct
FROM orders o JOIN stores s ON s.store_id = o.store_id
WHERE o.status = 'completed'
GROUP BY ...
```

</details>

<Solution>

E: revise. `COUNT(*)` counts orders, not customers (716, 355 and 728); `COUNT(DISTINCT c.customer_id)` gives Campus 108, Harbor 90 and Old Town 108. F: revise. `payment_method` holds `card`, `cash` and `mobile`; `'credit card'` matches no row, so the count is 0 and no error appears. With `'card'` it is 1,001 orders, all completed. G: accept. `NOT IN` goes wrong when the subquery's column holds an empty value (DuckDB's IN page says `x NOT IN y` is `NOT (x IN y)`, and its NULL page says a comparison with `NULL` returns `NULL`); `order_items.product_id` is never empty, so the pattern is safe, and the one row is the real answer. H: revise. The figures are 30.4 percent overall and 33.8 percent at Harbor, still the highest (Campus 29.2, Old Town 29.8): keep the order, replace both numbers. These share orders, so order 2075 counts once like any other.

</Solution>

</Exercise>

**Spot the flaw.** An assistant answered "revenue on weekends, completed orders, January to June" with the query below: 340 orders and 4,302.75 dollars. A reviewer wrote: "Accepted. Every name is in the schema, `dayofweek` is a DuckDB function, the amount follows the dictionary, and a weekend is Saturday and Sunday." Run it. What can those checks not see, and what is the real weekend revenue? Expected: 1 row, 2 columns.

<RunSQL query={`SELECT COUNT(DISTINCT o.order_id) AS orders,
       SUM(oi.quantity * p.unit_price_usd - oi.discount_usd) AS revenue
FROM orders o
JOIN order_items oi ON oi.order_id = o.order_id
JOIN products p ON p.product_id = oi.product_id
WHERE o.status = 'completed' AND dayofweek(o.ordered_at) IN (6, 7);`} />

<details>
<summary>Hint</summary>

List the weekday numbers that `dayofweek` returns, each with its `dayname`, and compare them with the numbers the `WHERE` keeps.

</details>

<details>
<summary>Half-solution</summary>

```sql
SELECT DISTINCT dayofweek(ordered_at) AS number, dayname(ordered_at) AS name
FROM orders
ORDER BY number;
```

</details>

<Solution>

The list runs from 0 (Sunday) to 6 (Saturday): DuckDB's `dayofweek` counts Sunday as 0, and there is no day 7. `IN (6, 7)` keeps Saturday only. The fix uses `isodow`, which counts Monday as 1 and Sunday as 7 (the DuckDB page on date part functions):

```sql
SELECT COUNT(DISTINCT o.order_id) AS orders,
       SUM(oi.quantity * p.unit_price_usd - oi.discount_usd) AS revenue
FROM orders o
JOIN order_items oi ON oi.order_id = o.order_id
JOIN products p ON p.product_id = oi.product_id
WHERE o.status = 'completed' AND isodow(o.ordered_at) IN (6, 7);
```

```text
orders  revenue
654     8390.25
```

The assistant's figure is Saturday alone: 340 of the 654 orders. The reviewer's checks read names, meaning and the shape of the result, and the shape is the same with the slip. A count of the days the filter keeps finds it, and so does a prediction: two days of seven should hold more than one fifth of the orders, and 340 of 1,799 is less. Order 2075 is a Friday, so it is in neither figure. Decision: revise, with the right function.

</Solution>
