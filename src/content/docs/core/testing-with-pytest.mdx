## The question

Last week the owner changed the month filter, and nobody saw that March had lost 8 orders until the till report disagreed. The owner asks:

> Can the program check itself every time I change it? And can it catch the kind of mistake that only shows on the first and last day of a month?

A tiny table is enough to show where such a mistake hides. These five orders have a known April: the first moment and the last second of the month, a walk-in with no customer, and the first moment of May.

| order_id | customer_id | store_id | ordered_at |
|---:|---:|---:|---|
| 1 | 7 | 1 | 2026-03-31 23:59:59 |
| 2 | 8 | 1 | 2026-04-01 00:00:00 |
| 3 | | 2 | 2026-04-15 12:30:00 |
| 4 | 8 | 2 | 2026-04-30 23:59:59 |
| 5 | 9 | 3 | 2026-05-01 00:00:00 |

By the end you can write tests that run on tables like this one, see what a failed test tells you, and trust a test because its answer came from somewhere else.

## Learn by doing

About 30 minutes, 4 new ideas: a test function, edge rows and a fixture, guards against dropped and doubled rows, and an answer from another route. Work in the repository of C26 (`cafe-report`), in the terminal.

### 1. A test is a function with an assert

**Idea.** A test is a function that builds a small input, calls your code and asserts the answer you know. pytest finds your tests, runs each one and prints a dot for every test that holds. It is a development tool, so it goes in the development group of the project and never into what the program needs to run.

**Try it.** Add pytest, then save the first test as `tests/test_report.py`:

```bash
uv add --dev pytest
```

```python
import pandas as pd

from cafe_report.report import order_totals


def test_order_totals_is_quantity_times_price_minus_discount():
    items = pd.DataFrame(
        {
            "order_id": [1, 1, 2],
            "product_id": [10, 1, 10],
            "quantity": [1, 2, 3],
            "discount_usd": [0.0, 0.0, 1.0],
        }
    )
    products = pd.DataFrame({"product_id": [1, 10], "unit_price_usd": [3.0, 3.25]})
    totals = order_totals(items, products)
    assert totals["amount"].tolist() == [9.25, 8.75]
```

Run `uv run pytest -q`. Then rename the file to `tests/check_report.py` and run it again. Rename it back.

**Predict:** What do the two runs print?

```text
$ uv run pytest -q
```

The time differs on your machine. After the first command, `pyproject.toml` has a new group:

```toml

    "pytest>=9.2.0",
```

*Why:* the answer was worked out by hand from two prices of the menu, Espresso 3.00 and Croissant 3.25: order 1 is 1 × 3.25 + 2 × 3.00 = 9.25 and order 2 is 3 × 3.25 − 1.00 = 8.75. pytest runs files of the form `test_*.py` or `*_test.py`, and functions whose names start with `test_`, so `check_report.py` was never looked at. A file pytest does not collect gives "no tests ran", not a pass. The uv page says that a development dependency is local only and is not part of the requirements when the project is published, and that `uv run` includes the `dev` group by default.

### 2. Edge rows, a fixture, and a failure report

**Idea.** The mistakes that survive a first look sit at the edges of a rule: the first moment and the last second of a month, a value that is missing. Put those rows in the table. A fixture is a function marked `@pytest.fixture` that builds a table once for each test; a test asks for it by writing its name as an argument.

**Try it.** Add the five orders of the question as a fixture, and a test that April keeps orders 2, 3 and 4. Put `import pytest` at the top, change the import to `from cafe_report.report import in_month, order_totals`, and keep the first test.

```python
@pytest.fixture
def orders():
    return pd.DataFrame(
        {
            "order_id": [1, 2, 3, 4, 5],
            "customer_id": [7, 8, None, 8, 9],
            "store_id": [1, 1, 2, 2, 3],
            "ordered_at": pd.to_datetime(
                [
                    "2026-03-31 23:59:59",
                    "2026-04-01 00:00:00",
                    "2026-04-15 12:30:00",
                    "2026-04-30 23:59:59",
                    "2026-05-01 00:00:00",
```

### 3. Guard the joins that drop or double rows

**Idea.** A merge can change the number of rows without an error: a key that repeats in one table matches a line twice, and an inner join drops every row that finds no partner. Two guards cover it. The first is the check you ask pandas to make (`validate="many_to_one"` in `order_totals` makes it refuse a repeated key in `products`), and a test that the check fires, with `pytest.raises`. The second is a count: the rows that went in come out.

**Try it.** Add two tests, with `import pytest` and `store_sales` in the import. The second takes the orders 2, 3 and 4 of the fixture, and gives totals only for 2 and 3, so order 4 has no lines:

```python
def test_a_repeated_product_row_is_refused():
    items = pd.DataFrame(
        {"order_id": [1], "product_id": [1], "quantity": [2], "discount_usd": [0.0]}
    )
    products = pd.DataFrame({"product_id": [1, 1], "unit_price_usd": [3.0, 3.0]})
    with pytest.raises(pd.errors.MergeError):
        order_totals(items, products)


def test_an_order_without_lines_still_counts(orders):
    totals = pd.DataFrame({"order_id": [2, 3], "amount": [6.0, 4.5]})
    result = store_sales(orders.iloc[1:4], totals)
    assert result["orders"].tolist() == [1, 2]
    assert result["sales"].tolist() == [6.0, 4.5]
```

Four tests pass. Now break both guards in `report.py`: delete `, validate="many_to_one"` from the merge in `order_totals`, and change `how="left"` to `how="inner"` in `store_sales`. Run `uv run pytest -q`.

### 4. The answer comes from another route

**Idea.** A test on the real file needs an answer you did not get from the code under test. Take it from a second route on the same data: a SQL query, or a PivotTable. For the sums of money, compare with `pytest.approx`, which the pytest page describes for floating-point values where small rounding errors are expected.

**Try it.** Run this query in the SQL playground of this site, at `/sql/playground/`, which has the five tables loaded. It gives the completed orders and the sales of each cafe in April:

```sql
SELECT o.store_id,
       COUNT(*) AS orders,
       ROUND(SUM(t.amount), 2) AS sales
FROM orders AS o
LEFT JOIN (SELECT i.order_id, SUM(i.quantity * p.unit_price_usd - i.discount_usd) AS amount
           FROM order_items AS i
           JOIN products AS p ON p.product_id = i.product_id
           GROUP BY i.order_id) AS t ON t.order_id = o.order_id
WHERE o.status = 'completed'
  AND o.ordered_at >= '2026-04-01' AND o.ordered_at < '2026-05-01'
GROUP BY o.store_id
ORDER BY o.store_id;
```

Expected: 3 rows, 3 columns: stores 1, 2 and 3 with 123, 103 and 123 orders and 1,542.25, 1,252 and 1,596.5 dollars. Now add the same numbers as a test on the real files, with `from pathlib import Path` at the top of the file, `read_orders` in the import and this line below the imports:

```python
DATA = Path(__file__).resolve().parent.parent / "data"
```

```python
def test_april_matches_the_answer_from_sql():
    orders = in_month(read_orders(DATA / "orders.csv"), "2026-04")
    items = pd.read_csv(DATA / "order_items.csv")
    products = pd.read_csv(DATA / "products.csv")
    result = store_sales(orders, order_totals(items, products))
    assert result["store_id"].tolist() == [1, 2, 3]
    assert result["orders"].tolist() == [123, 103, 123]
    assert result["sales"].tolist() == pytest.approx([1542.25, 1252.00, 1596.50])
```

**Predict:** With the five tests of this lesson in the file, how many does `uv run pytest -q` report, and do they all pass?

*Why:* 1 + 1 + 2 + 1 = 5 tests, one dot each. The numbers in the last test were never produced by `store_sales`, so a mistake in it cannot hide in them: the SQL joined the lines to the prices on its own. April has 349 orders, all completed, and 123 + 103 + 123 is 349. Continuous integration is what GitHub's documentation describes as frequently committing code to a shared repository and building and testing it each time; its workflows can start when new code is pushed, and run linters and functional tests. You do not build one here. What makes it possible is that `uv run pytest` needs only the repository (code, lockfile and data), so a clean machine can run the same command and report the same dots.

<Aside type="tip" title="Remember">

- A test builds a small input, calls the code and asserts an answer you know.
- Put the edge rows in the table: the first moment, the last second, a missing value.
- A merge can drop or double rows without an error: test that its check fires, and count the rows.
- Take the expected answer from another route, not from the code under test.
- Read a failure from the `E` lines: the result, the known answer and what differs.

```python
def test_in_month_gives_three_orders_in_april(orders):
```

```python
    assert in_month(orders, "2026-04")["order_id"].tolist() == ...
```

<Solution>

```python
def test_in_month_gives_the_right_orders_in_april(orders):
    assert in_month(orders, "2026-04")["order_id"].tolist() == [2, 3, 4]
```

With `>` the order at exactly midnight on April 1 is lost, and with `<=` the order at exactly midnight on May 1 is gained. The filter returns orders 3, 4 and 5, which are three rows, so the count test passes while the answer is wrong. Compared with `[2, 3, 4]`, the new test fails and reports `[3, 4, 5]`, with the first difference at index 0. A count says how many; a list of ids says which.
