## The question

The owner wants to change the order counts again, and writes:

> Last time I changed the first day of the count, nobody noticed that a day was missing until I added the numbers by hand. Can the program check itself every time I change it, also on the first day and the last second of a month?

A tiny list is enough to show where such a mistake hides. These five orders have a known answer for a count from April 1: the last second of March, the first moment of April, a walk-in with no customer, a canceled order, and the first moment of May.

| order_id | customer_id | store_id | ordered_at | status |
|---:|---:|---:|---|---|
| 1 | 7 | 1 | 2026-03-31 23:59:59 | completed |
| 2 | 8 | 1 | 2026-04-01 00:00:00 | completed |
| 3 | | 2 | 2026-04-15 12:30:00 | completed |
| 4 | 9 | 2 | 2026-04-30 23:59:59 | canceled |
| 5 | 9 | 3 | 2026-05-01 00:00:00 | completed |

By the end you can write tests that run on lists like this one, see what a failed test tells you, and trust a test because its answer came from somewhere else.

## Learn by doing

About 30 minutes, 4 new ideas: a test function and where pytest looks for your code, edge rows and a fixture, a count that doubles a repeated row, and an answer from another route. Work in the folder `cafe-report` after C26, in the terminal, with the changes of C26 committed.

### 1. A test is a function with an assert

**Idea.** A test is a function that builds a small input, calls your code and asserts the answer you know. pytest runs the files named `test_*.py` or `*_test.py` and the functions whose names start with `test_`, and prints a dot for every test that holds. It is a development tool, so it goes in the development group of the project and never into what the program needs to run.

**Try it.** Add pytest, then save the first test as `tests/test_summary.py` (make the folder `tests`):

```bash
uv add --dev pytest
```

```python
from datetime import date

from cafe_report.summary import orders_per_store


def test_orders_per_store_counts_the_completed_orders_from_the_day():
    orders = [
        {"order_id": "1", "store_id": "1", "ordered_at": "2026-04-02 08:00:00", "status": "completed"},
        {"order_id": "2", "store_id": "1", "ordered_at": "2026-04-03 09:30:00", "status": "completed"},
        {"order_id": "3", "store_id": "2", "ordered_at": "2026-04-03 10:00:00", "status": "canceled"},
    ]
    assert orders_per_store(orders, date(2026, 4, 1)) == {"1": 2}
```

Run `uv run pytest -q`.

**Predict:** The code holds and the answer is right: store 1 has two completed orders, and the canceled order does not count. Does the run print a dot?

### 2. Edge rows, a fixture, and a failure report

**Idea.** The mistakes that survive a first look sit at the edges of a rule: the first moment of a day, the last second before it, a canceled order, a customer that is missing. Put those rows in the list. A fixture is a function marked `@pytest.fixture` that builds the list once for each test; a test asks for it by writing its name as an argument.

**Try it.** Add the five orders of the question as a fixture, and a test that a count from April 1 keeps orders 2, 3 and 5. Put `import pytest` at the top, the fixture above the first test, and the new test at the end:

### 3. A count that doubles a repeated row

**Idea.** A count can change the number of rows without an error. When an export is written twice, an order appears on two rows, and a loop that adds one for each row counts it twice. A test finds this only when the list contains a repeated row on purpose.

**Try it.** Add a test that repeats order 2, and run `uv run pytest -q`:

```python
def test_a_repeated_order_row_counts_once(orders):
    again = orders + [orders[1]]  # the export wrote order 2 twice
    assert orders_per_store(again, date(2026, 4, 1)) == {"1": 1, "2": 1, "3": 1}
```

**Predict:** The answer is the same as in unit 2, because it is the same orders. Does the test pass? If not, what do the `E` lines say?

```python
def orders_per_store(orders, since):
    """Count the completed orders of each store on or after the day `since`."""
    counts = {}
    seen = set()
    for order in orders:
        if order["order_id"] in seen:
            continue
        seen.add(order["order_id"])
        day = datetime.fromisoformat(order["ordered_at"]).date()
        if order["status"] == "completed" and day >= since:
            counts[order["store_id"]] = counts.get(order["store_id"], 0) + 1
    return counts
```

Now `uv run pytest -q` prints `...` and `3 passed`. Commit the tests and the fix: `git add pyproject.toml uv.lock tests cafe_report`, then `git commit -m "Test the order counts and skip a repeated order row"`.

### 4. The answer comes from another route

**Idea.** A test on the real file needs an answer from a second route on the same data: a SQL query, a PivotTable, a `uniq -c` pipeline. The numbers that C24 printed for the count from April 1 came out of this function, so they cannot check it.

**Try it.** Run this query in the SQL playground of this site, at `/sql/playground/`, which has the five tables loaded. It counts the completed orders of each store from April 1:

```sql
SELECT store_id, COUNT(*) AS orders
FROM orders
WHERE status = 'completed' AND ordered_at >= '2026-04-01'
GROUP BY store_id
ORDER BY store_id;
```

Expected: 3 rows, 2 columns: stores 1, 2 and 3 with 365, 362 and 355 orders. Now add the same numbers as a test on the real file, with `from pathlib import Path` and `from cafe_report.load import read_orders` in the imports and this line below them:

```python
DATA = Path(__file__).resolve().parent.parent / "data"
```

```python
def test_april_matches_the_answer_from_sql():
    orders = read_orders(DATA / "orders.csv")
    assert orders_per_store(orders, date(2026, 4, 1)) == {"1": 365, "2": 362, "3": 355}
```

**Predict:** With the four tests of this lesson in the file, how many does `uv run pytest -q` report, and do they all pass?

<details>
<summary>Reveal the result</summary>

```text
$ uv run pytest -q
....                                                                     [100%]
4 passed in 0.02s
```

</details>

*Why:* 1 + 1 + 1 + 1 = 4 tests, one dot each. The numbers in the last test were not produced by `orders_per_store`, so a mistake in it cannot hide in them: the query filtered and counted on its own. The store numbers are text in the dictionary and numbers in SQL, which is why the keys have quotes. The file is ignored by Git, so on a clean clone this test needs `uv run download_data.py` first, as in C25. Continuous integration is what GitHub's documentation describes as frequently committing code to a shared repository and building and testing it each time; its workflows can start when new code is pushed, and run linters and functional tests. You do not build one here. What makes it possible is that `uv run pytest` needs only the repository and the data script, so a clean machine can run the same commands and report the same dots.

<Aside type="tip" title="Remember">

- A test builds a small input, calls the code and asserts an answer you know.
- The tests folder is not the project folder: tell pytest where the package is with `pythonpath`.
- Put the edge rows in the list: the first moment, the last second, a canceled order, a missing value, a repeated row.
- A count can double a repeated row without an error: test it with a repeated row.
- Read a failure from the `E` lines: the result, the known answer and what differs.

**Common trap:** a green run that tested nothing. Make a test fail once, on purpose, before you trust it.

</Aside>
