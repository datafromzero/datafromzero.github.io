## The question

The Harbor manager runs `cafe-report` every Monday. Last month it stopped twice with a wall of text: once because a month was typed wrongly, once because the till export was still being copied. The owner of the three cafes asks:

> The report broke twice. Can it say what went wrong in a line, try again when that helps, and can you show me how you find the line that is at fault when it does not?

This is what a good run prints today, for April, with `uv run cafe-report data --month 2026-04` (orders are the completed orders of the month; sales are in US dollars):

| store_id | orders | sales |
|---:|---:|---:|
| 1 | 123 | 1542.25 |
| 2 | 103 | 1252.00 |
| 3 | 123 | 1596.50 |

By the end you can find your own line in a long error report, catch the one error you expect, retry a step a few times, and stop the program on a line to look at its values.

<Aside type="note" title="You already know this">

**Match.** In [*Reading errors and debugging*](/python/errors-and-debugging/) (P8) you read a traceback from the last line up and handled an expected failure with `try` and `except`, the Python twin of `IFERROR` in *Formula errors and auditing* (E12). The report of a project is the same report, only longer.

`src/cafe_report/report.py`:

```python
import pandas as pd


def read_orders(path):
    return pd.read_csv(path, parse_dates=["ordered_at"])


def in_month(orders, month):
    start = pd.Timestamp(f"{month}-01")
    end = start + pd.offsets.MonthBegin(1)
    return orders[(orders["ordered_at"] >= start) & (orders["ordered_at"] < end)]


def order_totals(items, products):
    prices = products[["product_id", "unit_price_usd"]]
    lines = items.merge(prices, on="product_id", validate="many_to_one")
    lines["amount"] = lines["quantity"] * lines["unit_price_usd"] - lines["discount_usd"]
    return lines.groupby("order_id", as_index=False)["amount"].sum()


def store_sales(orders, totals):
    done = orders[orders["status"] == "completed"]
    joined = done.merge(totals, on="order_id", how="left", validate="one_to_one")
    return joined.groupby("store_id", as_index=False).agg(
        orders=("order_id", "count"), sales=("amount", "sum")
    )
```

</details>

### 1. Find your own line in a long report

**Idea.** A traceback lists the calls that were running, oldest first, and ends with the error. Files you wrote and files of libraries are mixed in it. Start from the last line, then walk up to the last frame that is in your own code: that is the line of your program that was running when the library gave up.

**Try it.** Give the report a month that does not exist:

```bash
uv run cafe-report data --month 2026-13
```

**Predict:** The report will be long. Which function of your own code is the last one it names before the libraries take over, and what does the error say is wrong?

The report has two parts because pandas raised one error from another, the chaining that the Python tutorial describes for `raise ... from`; read the last part first.

### 2. Catch the one error you expect

**Idea.** An `except` clause names the class of error it handles. Catch the failure you can explain to the person who runs the program, and turn it into one line with `raise SystemExit("text")`.

**Try it.** A missing data folder is the failure the Harbor manager meets most. In `cli.py`, put the line that reads the orders in a `try`:

```python
    data = Path(args.data_dir)
    try:
        orders = read_orders(data / "orders.csv")
    except FileNotFoundError:
        raise SystemExit(f"cafe-report: no orders.csv in {data}")
    orders = in_month(orders, args.month)
```

Run it on a folder that does not exist, ask the shell for the exit code of the last command, and then run the month of unit 1 again:

```bash
uv run cafe-report nodata --month 2026-04
echo $?
uv run cafe-report data --month 2026-13
```

**Predict:** What do the first two commands print, and does the third still end in the long report?

<details>
<summary>Reveal the result</summary>

```text
cafe-report: no orders.csv in nodata
1
```

The third command prints the report of unit 1 again, and its last line is still:


</details>

*Why:* `sys.exit` documents that an object that is not a number or `None` is printed to standard error and the exit code is 1; `raise SystemExit(...)` does the same, which the run shows. The month error is not a `FileNotFoundError`, so it passes through. The `try` holds only the line that can fail, as PEP 8 asks.

*Why:* the misspelled name is a bug, a `NameError`, and the bare `except:` caught it and blamed a file that is there. ### 3. Retry a step, with a limit

**Idea.** Some steps fail for a reason that goes away on its own: a network request that times out, a file another program is still writing. A retry calls the step again after a wait, up to a limit, and only for the errors you list. Save this as `src/cafe_report/retry.py`:

```python
import time


def retry(call, attempts=3, wait=1.0, errors=(OSError,)):
    for attempt in range(1, attempts + 1):
        try:
            return call()
        except errors:
            if attempt == attempts:
                raise
            time.sleep(wait)
```

To make a call fail on cue, the demo uses `Mock` from the standard library: given a list as `side_effect`, each call returns or raises the next item, and `call_count` counts the calls.

**Try it.** Save as `scratch/retry_demo.py` and run it with `uv run python scratch/retry_demo.py`:

```python
from unittest.mock import Mock

from cafe_report.retry import retry


def run(label, call, attempts):
    try:
        result = retry(call, attempts=attempts, wait=0.1)
    except (OSError, ValueError) as err:
        result = f"{type(err).__name__}: {err}"
    print(f"{label}: {result} (calls: {call.call_count})")


busy = OSError("file is busy")
run("run 1", Mock(side_effect=[busy, busy, "ok"]), attempts=3)
run("run 2", Mock(side_effect=[busy, busy, "ok"]), attempts=2)
run("run 3", Mock(side_effect=ValueError("bad month")), attempts=3)
```

**Predict:** What does each of the three lines print, and how many calls does each make?

<details>
<summary>Reveal the result</summary>

```text
run 1: ok (calls: 3)
run 2: OSError: file is busy (calls: 2)
run 3: ValueError: bad month (calls: 1)
```

</details>

*Why:* in run 1 the third call works. In run 2 the limit comes first: on the last try the bare `raise` raises the error that `except` caught, so the caller still sees it. In run 3 a `ValueError` is not in `errors`, so nothing catches it and nothing waits: a retry that caught every error would try a typo three times and wait twice before saying so. Nothing in `cafe-report` calls `retry` yet, because its data is a local file; it waits for the first step that really can fail and then pass, a download or a database call.

### 4. Stop on a line and look

**Idea.** `breakpoint()` stops the program at that line and opens the debugger, where you can print any variable (`p`) and go on (`c`). VS Code does the same without editing the file: a breakpoint on a line, then Start Debugging.

**Try it.** A colleague's script counts the March orders and prints 250, but the till says 258. Save it as `scratch/march_bug.py`, with the `breakpoint()` on line 13, and run it with `uv run python scratch/march_bug.py`:

```python
from pathlib import Path

import pandas as pd

from cafe_report.report import read_orders

DATA = Path(__file__).resolve().parent.parent / "data"


def in_month(orders, month):
    start = pd.Timestamp(f"{month}-01")
    end = start + pd.offsets.MonthEnd(0)
    breakpoint()
    return orders[(orders["ordered_at"] >= start) & (orders["ordered_at"] <= end)]


orders = read_orders(DATA / "orders.csv")
march = in_month(orders, "2026-03")
print(len(march))
```

At the `(Pdb)` prompt, type `p end`, then `p int((orders["ordered_at"].dt.normalize() == end).sum())`, which counts the orders dated on that day, and then `c`.

**Predict:** What time of day does `end` hold, and how many orders are dated on that day?

<details>
<summary>Reveal the result</summary>

```text
$ uv run python scratch/march_bug.py
> ~/cafe-report/scratch/march_bug.py(13)in_month()
-> breakpoint()
(Pdb) p end

(Pdb) p int((orders["ordered_at"].dt.normalize() == end).sum())
```

</details>

*Why:* `end` is March 31 at midnight, the start of that day, so `<= end` drops every order after midnight on the 31st: 8 orders, and 258 minus 8 is 250. The fix is to cut at the first moment of April with `<`, as `in_month` in `report.py` does. The debugger showed it where a `print` would have needed a second run; the next lesson, *Testing on known answers with pytest* (C27), turns this day into a test.

To stop on the same line in VS Code, as the two VS Code pages describe:

1. Click the editor margin next to line 13, or press F9 on it, and remove the `breakpoint()` line.
2. Open the arrow beside the run button of the editor and choose "Python Debugger: Debug Python File". The program stops on the line.
3. The VARIABLES list shows the local and global variables of the selected frame, hovering over a name shows its value, and the Debug Console evaluates expressions such as the one you typed after `p`.
4. Continue is F5, Step Over F10, Step Into F11, Step Out ⇧F11 on macOS and Shift+F11 on Windows and Linux, Stop ⇧F5 on macOS and Shift+F5 on Windows and Linux.

<Aside type="tip" title="Remember">

- Read a long traceback from the last line up to the last frame in your own code.
- `except` names a class; a bare `except:` also hides bugs and Ctrl+C.
- Put in the `try` only the line that can fail, and raise one plain line for the person running the program.
- A retry needs a limit, a wait, a list of errors worth another try, and a final `raise`.
- A breakpoint shows the real values; print them before you guess.

**Common trap:** wrapping the whole run in a catch-all "to make it robust". A typo in the `try` was reported as a missing file.

</Aside>
