## The question

The Harbor manager runs the report every Monday. Last month she fed the monthly table a file from another export, and it stopped with a wall of text. Another time the till export was still being copied when she ran it. The owner of the three cafes asks:

> The report broke twice. Can it say what went wrong in a line, try again when that helps, and can you show me how you find the line that is at fault when it does not?

This is what a good run prints today, with `uv run python -m cafe_report data/orders.csv --since 2026-04-01` (the completed orders of each store from April 1):

| store | orders |
|---:|---:|
| 1 | 365 |
| 2 | 362 |
| 3 | 355 |

By the end you can find your own line in a long error report, catch the one error you expect, retry a step a few times, and stop the program on a line to look at its values.

<Aside type="note" title="You already know this">

**Match.** In [*Reading errors and debugging*](/python/errors-and-debugging/) (P8) you read a traceback from the last line up and handled an expected failure with `try` and `except`, the Python twin of `IFERROR` in *Formula errors and auditing* (E12). The report of a project is the same report, only longer.

**Diverge.** `IFERROR` catches every error, and `except` catches the class you name. Unit 2 shows what a catch-all costs.

</Aside>

```python
import pandas as pd


def orders_by_store_month(path):
    """A table of completed orders: one row for each store, one column for each month."""
    orders = pd.read_csv(path)
    completed = orders[orders["status"] == "completed"]
    month = pd.to_datetime(completed["ordered_at"]).dt.strftime("%Y-%m").rename("month")
    return completed.groupby(["store_id", month]).size().unstack(fill_value=0)
```

### 1. Find your own line in a long report

**Idea.** A traceback lists the calls that were running, oldest first, and ends with the error. Files you wrote and files of libraries are mixed in it. Start from the last line, then walk up to the last frame that is in your own code: that is the line of your program that was running when the library gave up.

**Try it.** The file from another export has two columns only. Make it, and ask for the monthly table of it:

```bash

uv run python -m cafe_report data/short.csv --monthly
```

### 2. Catch the one error you expect

**Idea.** An `except` clause names the class of error it handles. Catch the failure you can explain to the person who runs the program, and turn it into one line with `raise SystemExit("text")`.

**Try it.** A mistyped file name is the failure the Harbor manager meets most. In `cli.py`, put the line that reads the orders in a `try`, and give the counting its own line below it:

```python
    try:
        orders = read_orders(args.orders_file)
    except FileNotFoundError:
        raise SystemExit(f"cafe_report: no file {args.orders_file}")
    counts = orders_per_store(orders, args.since)
```

Run it on a file that does not exist, ask the shell for the exit code of the last command, and then run the report on the two-column file again:

```bash
uv run python -m cafe_report data/nothing.csv
echo $?
uv run python -m cafe_report data/short.csv
```

**Predict:** What do the first two commands print, and does the third still end in a long report?

<details>
<summary>Reveal the result</summary>

```text
cafe_report: no file data/nothing.csv
1
```

The third command prints a report again, and its last line is:

```text
KeyError: 'ordered_at'
```

</details>

*Why:* `sys.exit` documents that an object that is not a number or `None` is printed to standard error and the exit code is 1; `raise SystemExit(...)` does the same, which the run shows. The missing column is not a `FileNotFoundError`, so it passes through and still stops the program with its own line. The `try` holds only the line that can fail, as PEP 8 asks.

**Try it, broken on purpose.** Change `except FileNotFoundError:` to a bare `except:`, and misspell `read_orders` as `read_ordrs` inside the `try`. The file is right this time:

```bash
uv run python -m cafe_report data/orders.csv --since 2026-04-01
```

**Predict:** What does this run print?

*Why:* the misspelled name is a bug, a `NameError`, and the bare `except:` caught it and blamed a file that is there. PEP 8 warns that a bare `except:` can disguise other problems and also catches `SystemExit` and `KeyboardInterrupt`, which is what Ctrl+C raises. The Python tutorial says the same in other words: be as specific as possible and let the unexpected errors go on up. Put both lines back before you go on.

### 3. Retry a step, with a limit

**Idea.** Some steps fail for a reason that goes away on its own: a network request that times out, a file another program is still writing. A retry calls the step again after a wait, up to a limit, and for the errors you name. Save this as `cafe_report/retry.py`:

```python
import time


def retry(call, attempts=3, wait=1.0, errors=(OSError,)):
    for attempt in range(1, attempts + 1):
        try:
            return call()
        except errors:
            if attempt == attempts:
                raise
            time.sleep(wait)
```

To make a call fail on cue, the demo uses `Mock` from the standard library: given a list as `side_effect`, each call returns or raises the next item, and `call_count` counts the calls.

**Try it.** Save as `retry_demo.py` in the project folder and run it with `uv run python retry_demo.py`:

```python
from unittest.mock import Mock

from cafe_report.retry import retry


def run(label, call, attempts):
    try:
        result = retry(call, attempts=attempts, wait=0.1)
    except (OSError, ValueError) as err:
        result = f"{type(err).__name__}: {err}"
    print(f"{label}: {result} (calls: {call.call_count})")


busy = OSError("file is busy")
run("run 1", Mock(side_effect=[busy, busy, "ok"]), attempts=3)
run("run 2", Mock(side_effect=[busy, busy, "ok"]), attempts=2)
run("run 3", Mock(side_effect=ValueError("bad month")), attempts=3)
```

**Predict:** What does each of the three lines print, and how many calls does each make?

<details>
<summary>Reveal the result</summary>

```text
run 1: ok (calls: 3)
run 2: OSError: file is busy (calls: 2)
run 3: ValueError: bad month (calls: 1)
```

</details>

*Why:* in run 1 the third call works. In run 2 the limit comes first: on the last try the bare `raise` raises the error that `except` caught, so the caller still sees it. In run 3 a `ValueError` is not in `errors`, so nothing catches it and nothing waits: a retry that caught every error would try a typo three times and wait twice before saying so. Nothing in `cafe_report` calls `retry` yet, because its data is a local file; it waits for the first step that really can fail and then pass, a download or a database call.

### 4. Stop on a line and look

**Idea.** `breakpoint()` stops the program at that line and opens the debugger, where you can print any variable (`p`) and go on (`c`). VS Code does the same without editing the file: a breakpoint on a line, then Start Debugging.

**Try it.** A colleague's script counts the orders of March from the text of the time, and prints 250, but the till says March had more. Save it as `march_bug.py` in the project folder, with the `breakpoint()` on line 7, and run it with `uv run python march_bug.py`:

```python
from pathlib import Path

from cafe_report.load import read_orders

orders = read_orders(Path(__file__).resolve().parent / "data" / "orders.csv")
march = [o for o in orders if "2026-03-01" <= o["ordered_at"] <= "2026-03-31"]
breakpoint()
print(len(march))
```

At the `(Pdb)` prompt, type these four lines one by one, and then `c`:

```text
p len(march)
p sum(o["ordered_at"].startswith("2026-03") for o in orders)
p [o["ordered_at"] for o in orders if o["ordered_at"].startswith("2026-03-31")][:2]
p "2026-03-31 10:01:00" <= "2026-03-31"
```

**Predict:** How many orders does the file hold for March, how does that compare with `len(march)`, and what does the last comparison give?

<details>
<summary>Reveal the result</summary>

```text
$ uv run python march_bug.py
> /home/ana/cafe-report/march_bug.py(7)<module>()
-> breakpoint()
(Pdb) p len(march)
250
(Pdb) p sum(o["ordered_at"].startswith("2026-03") for o in orders)
258
(Pdb) p [o["ordered_at"] for o in orders if o["ordered_at"].startswith("2026-03-31")][:2]
['2026-03-31 10:01:00', '2026-03-31 10:10:00']
(Pdb) p "2026-03-31 10:01:00" <= "2026-03-31"
False
(Pdb) c
250
```

</details>

*Why:* the file holds 258 orders for March and the list kept 250. Text compares character by character, and `"2026-03-31 10:01:00"` is longer than `"2026-03-31"` with the same start, so it is greater: every order after midnight on the 31st fails `<= "2026-03-31"`, and the 8 orders of that day are lost. The fix is to compare the day, as `orders_per_store` does with `datetime.fromisoformat(...).date()`. The debugger showed it where a `print` would have needed a second run; the next lesson, *Testing on known answers with pytest* (C27), turns a boundary day like this into a test.

To stop on the same line in VS Code, as the two VS Code pages describe:

2. Open the arrow beside the run button of the editor and choose "Python Debugger: Debug Python File". The program stops on the line.

<Aside type="tip" title="Remember">

- Read a long traceback from the last line up to the last frame in your own code.
- `except` names a class; a bare `except:` also hides bugs and Ctrl+C.
- Put in the `try` only the line that can fail, and raise one plain line for the person running the program.
- A retry needs a limit, a wait, a list of errors worth another try, and a final `raise`.
- A breakpoint shows the real values; print them before you guess.

**Common trap:** wrapping the whole run in a catch-all "to make it robust". A typo in the `try` was reported as a missing file.

</Aside>

**Spot the flaw.** A colleague wants the program to say something helpful for each way the orders file can fail. Save this as `handlers.py` in the project folder and run it with `uv run python handlers.py`; the file `data/nothing.csv` does not exist. Expected: one line, then exit code 1. Which line does it print, is it the one the second clause was written for, and what is the fix?

```python
from cafe_report.load import read_orders

try:
    orders = read_orders("data/nothing.csv")
except OSError:
    raise SystemExit("cafe_report: cannot read the orders file")
except FileNotFoundError:
    raise SystemExit("cafe_report: no file data/nothing.csv")
```

<details>
<summary>Hint</summary>

The Python tutorial says that the first matching `except` clause is the one that runs. Check which classes `FileNotFoundError` is built on with `print([c.__name__ for c in FileNotFoundError.__mro__])`.

</details>

<details>
<summary>Half-solution</summary>

```python
except FileNotFoundError:
    ...
except OSError:
    ...
```

</details>

<Solution>

```text
$ uv run python handlers.py
cafe_report: cannot read the orders file
$ echo $?
1
```

`FileNotFoundError` is built on `OSError` (the list is `['FileNotFoundError', 'OSError', 'Exception', 'BaseException', 'object']`), and an `except` clause matches a class and the classes built on it, so the first clause catches the missing file and the second can never run. Put the specific clause first and the general one after it:

```python
try:
    orders = read_orders("data/nothing.csv")
except FileNotFoundError:
    raise SystemExit("cafe_report: no file data/nothing.csv")
except OSError:
    raise SystemExit("cafe_report: cannot read the orders file")
```

</Solution>
