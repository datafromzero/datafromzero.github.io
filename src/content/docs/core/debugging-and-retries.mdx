## The question

The Harbor manager fed the monthly table a file from another export, and it stopped with a wall of text. The owner asks:

> The report broke twice. Can it say what went wrong in a line, try again when that helps, and can you show me how you find the line that is at fault when it does not?

A good run, `uv run python -m cafe_report data/orders.csv --since 2026-04-01`, prints this:

|---:|---:|
| 1 | 365 |
| 2 | 362 |

### 1. Find your own line in a long report

**Idea.** A traceback lists the calls that were running, oldest first, and ends with the error. Start from the last line, then walk up to the last frame in your own code: the line of your program that was running when the library gave up.

**Try it.** A file from another export has two columns only. Make it and ask for the monthly table of it:

```bash
printf 'order_id,store_id\n1,1\n' > data/short.csv
uv run python -m cafe_report data/short.csv --monthly
```

**Predict:** The report will be long. Which function of your own code is the last one it names before pandas takes over, and what does the error say is wrong?

### 2. Catch the one error you expect

**Idea.** An `except` clause names the class of error it handles. Catch the failure you can explain to the person who runs the program, and turn it into one line with `raise SystemExit("text")`.

**Try it.** A mistyped file name is the most common failure. In `cli.py`, put the line that reads the orders in a `try`:

```python
    try:
        orders = read_orders(args.orders_file)
    except FileNotFoundError:
        raise SystemExit(f"cafe_report: no file {args.orders_file}")
    counts = orders_per_store(orders, args.since)
```

Run it on a file that does not exist, ask the shell for the exit code, then run the two-column file again:

```bash
uv run python -m cafe_report data/nothing.csv
echo $?
uv run python -m cafe_report data/short.csv
```

**Predict:** What do the first two commands print, and does the third still end in a long report?

<details>
<summary>Reveal the result</summary>

```text
cafe_report: no file data/nothing.csv
1
```

The third command prints a report whose last line is `KeyError: 'ordered_at'`.

</details>

*Why:* `sys.exit` documents that an object that is not a number or `None` is printed to standard error with exit code 1; `raise SystemExit(...)` does the same. The missing column is not a `FileNotFoundError`, so it passes through. The `try` holds only the line that can fail, as PEP 8 asks.

**Try it, broken on purpose.** Change `except FileNotFoundError:` to a bare `except:`, and misspell `read_orders` as `read_ordrs` inside the `try`. The file is right this time:

```bash
uv run python -m cafe_report data/orders.csv --since 2026-04-01
```

**Predict:** What does this run print?

<details>
<summary>Reveal the result</summary>

```text
cafe_report: no file data/orders.csv
```

</details>

*Why:* the misspelled name is a `NameError`; the bare `except:` caught it and blamed a file that is there. PEP 8 warns that a bare `except:` can disguise other problems and also catches `SystemExit` and `KeyboardInterrupt`. Put both lines back.

### 3. Retry a step, with a limit

**Idea.** Some steps fail for a reason that goes away on its own, such as a file another program is still writing. A retry calls the step again after a wait, up to a limit, for the errors you name. Save this as `cafe_report/retry.py`:

```python
import time


def retry(call, attempts=3, wait=1.0, errors=(OSError,)):
    for attempt in range(1, attempts + 1):
        try:
            return call()
        except errors:
            if attempt == attempts:
                raise
            time.sleep(wait)
```

The demo's `Mock` fails on cue: given a list as `side_effect`, each call returns or raises the next item, and `call_count` counts the calls.

**Try it.** Save as `retry_demo.py` in the project folder and run it with `uv run python retry_demo.py`:

```python
from unittest.mock import Mock

from cafe_report.retry import retry


def run(label, call, attempts):
    try:
        result = retry(call, attempts=attempts, wait=0.1)
    except (OSError, ValueError) as err:
        result = f"{type(err).__name__}: {err}"
    print(f"{label}: {result} (calls: {call.call_count})")


busy = OSError("file is busy")
run("run 1", Mock(side_effect=[busy, busy, "ok"]), attempts=3)
run("run 2", Mock(side_effect=[busy, busy, "ok"]), attempts=2)
run("run 3", Mock(side_effect=ValueError("bad month")), attempts=3)
```

**Predict:** What does each of the three lines print, and how many calls does each make?

<details>
<summary>Reveal the result</summary>

```text
run 1: ok (calls: 3)
run 2: OSError: file is busy (calls: 2)
run 3: ValueError: bad month (calls: 1)
```

</details>

*Why:* in run 1 the third call works. In run 2 the limit comes first: on the last try the bare `raise` raises the error `except` caught, so the caller still sees it. In run 3 a `ValueError` is not in `errors`, so nothing catches it and nothing waits: a retry that caught every error would try a typo three times.

### 4. Stop on a line and look

**Idea.** `breakpoint()` stops the program at that line and opens the debugger, where you print any variable (`p`) and go on (`c`).

**Try it.** A colleague's script counts the orders of March from the text of the time and prints 250, but the till says more. Save it as `march_bug.py` in the project folder, with `breakpoint()` on line 7, and run it with `uv run python march_bug.py`:

```python
from pathlib import Path

from cafe_report.load import read_orders

orders = read_orders(Path(__file__).resolve().parent / "data" / "orders.csv")
march = [o for o in orders if "2026-03-01" <= o["ordered_at"] <= "2026-03-31"]
breakpoint()
print(len(march))
```

At the `(Pdb)` prompt, type these four lines one by one, then `c`:

```text
p len(march)
p sum(o["ordered_at"].startswith("2026-03") for o in orders)
p [o["ordered_at"] for o in orders if o["ordered_at"].startswith("2026-03-31")][:2]
p "2026-03-31 10:01:00" <= "2026-03-31"
```

**Predict:** How many orders does the file hold for March, how does that compare with `len(march)`, and what does the last comparison give?

<details>
<summary>Reveal the result</summary>

```text
(Pdb) p len(march)
250
(Pdb) p sum(o["ordered_at"].startswith("2026-03") for o in orders)
258
(Pdb) p [o["ordered_at"] for o in orders if o["ordered_at"].startswith("2026-03-31")][:2]
['2026-03-31 10:01:00', '2026-03-31 10:10:00']
(Pdb) p "2026-03-31 10:01:00" <= "2026-03-31"
False
```

</details>

*Why:* the file holds 258 orders for March and the list kept 250. `"2026-03-31 10:01:00"` is longer than `"2026-03-31"` with the same start, so it is greater: every order after midnight on the 31st fails the test, and the 8 orders of that day are lost. The fix is to compare the day, as `orders_per_store` does; the next lesson, *Testing on known answers with pytest* (C27), turns a boundary day into a test.

To stop on the same line in VS Code, as the two VS Code pages describe:

1. Click the editor margin next to line 7, or press F9 on it, and remove the `breakpoint()` line.
2. Open the arrow beside the run button and choose "Python Debugger: Debug Python File". The program stops on the line.
3. VARIABLES lists the variables of the selected frame, and hovering over a name shows its value.
4. Continue is F5, Step Over F10, Step Into F11, Step Out ⇧F11 (macOS) or Shift+F11 (Windows, Linux), Stop ⇧F5 (macOS) or Shift+F5 (Windows, Linux).

<Aside type="tip" title="Remember">

- Read a long traceback from the last line up to the last frame in your own code.
- `except` names a class; a bare `except:` also hides bugs and Ctrl+C. Put only the line that can fail in the `try`.
- A retry needs a limit, a wait, a list of errors worth another try, and a final `raise`.
- A breakpoint shows the real values; look before you guess.

**Common trap:** wrapping the whole run in a catch-all "to make it robust". A typo in the `try` was reported as a missing file.

</Aside>


`FileNotFoundError` is built on `OSError` (the list is `['FileNotFoundError', 'OSError', 'Exception', 'BaseException', 'object']`), and an `except` clause matches a class and the classes built on it, so the first clause catches the missing file and the second never runs. Swap the two clauses: the specific one goes first.
