## The question

The owner of the three cafes will hand the repository to a new analyst on Monday:

> Can they read your code without asking you, and how do I know it works?

A reader opening `report.py` today meets, for example, this line, and has three questions about it:

```python
def in_month(orders, month):
```

| the reader asks | what the code says today |
|---|---|
| What do I pass for `orders`? | nothing: you read the body to find out |
| What do I pass for `month`? | nothing: a number, a date or text? |
| What comes back, and what does it do? | nothing: read the last line |

By the end you can answer all three on the line itself, let a tool tidy the code, read how a library class is built, give a cafe record a class of its own, and check that the whole repository is done.

**Match.** In [*Functions and imports*](/python/functions-and-modules/) (P7) you wrote functions with `def`, parameters and a `return`. Hints and a docstring are notes on that same `def` line and the line below it.

**Diverge.** A test of C27 fails when the result is wrong. A note beside the function is not a test; unit 1 shows what happens when a call breaks its own hint.

</Aside>

### 1. Hints and docstrings

**Idea.** A *type hint* says what a parameter or a result is meant to be: `month: str`, `-> pd.DataFrame`. A *docstring* says what a function does. PEP 257 defines it as a string literal that is the first statement of a function, in triple quotes, and asks for a phrase that ends with a period and says what the function does as a command, "Return that", not as a description.

**Try it.** Save as `scratch/hints.py` and run it with `uv run python scratch/hints.py`:

```python
def double(quantity: int) -> int:
    return quantity * 2


print(double(3))
print(double("ab"))
```

**Predict:** What do the two lines print?

<details>
<summary>Reveal the result</summary>

```text
6
abab
```

</details>

*Why:* the second call broke the hint and nothing stopped it: the typing page says the Python runtime does not enforce type annotations, and that third-party tools such as type checkers, IDEs and linters can use them. `"ab" * 2` is a legal Python expression, so it ran. A hint is a statement to the reader and to such tools; the tests of C27 are the check.

Now give `in_month` and `store_sales` in `report.py` their hints and docstrings (add `from pathlib import Path` and a one-line docstring for the module at the top of the file as well), and ask Python for its help text:

```python
def in_month(orders: pd.DataFrame, month: str) -> pd.DataFrame:
    """Return the orders placed in a month such as "2026-04".

    The month runs from its first moment up to, but not including, the first
    moment of the next month.
    """
    ...


def store_sales(orders: pd.DataFrame, totals: pd.DataFrame) -> pd.DataFrame:
    """Count the completed orders and add up their sales for each store."""
    ...
```

```bash
uv run python -c 'from cafe_report.report import in_month; help(in_month)'
```

<details>
<summary>Reveal the result</summary>

```text
Help on function in_month in module cafe_report.report:

in_month(orders: pandas.DataFrame, month: str) -> pandas.DataFrame
    Return the orders placed in a month such as "2026-04".

    The month runs from its first moment up to, but not including, the first
    moment of the next month.
```

</details>

*Why:* the three questions of the table are answered on the function itself: both parameters, the result and one sentence. The docstring has a summary line, a blank line and then more, which is the multi-line layout of PEP 257. Do the same for every other function of `report.py`; the project step lists them.

### 2. Let ruff check and format

**Idea.** Ruff is a Python linter and code formatter. `ruff check` reports problems in the code, and `--fix` applies the fixes it marks safe. `ruff format` rewrites the layout of the files in place, and `--check` only reports whether it would change anything, with a non-zero exit status when it would. Both can read their settings from `pyproject.toml`, as the run below shows, and ruff goes in the development group like pytest.

**Try it.** Add ruff, then add its settings at the end of `pyproject.toml`. `select` names the rule families to apply by their code prefix: `E` for style errors, `F` for plain mistakes such as unused names and `I` for the order of imports.

```bash
uv add --dev ruff
```

```toml
[tool.ruff]
line-length = 100

[tool.ruff.lint]
select = ["E", "F", "I"]
```

Save this untidy file as `scratch/messy.py`, run `uv run ruff check scratch/messy.py`, then `uv run ruff check --fix scratch/messy.py`, and look at the file with `cat scratch/messy.py`:

```python
import os, sys
import pandas as pd
def line_total(price,qty ,discount = 0):
    total = price*qty-discount
    return(total)
print( line_total(3.25,2) )
```

**Predict:** How many problems does the first command report, and which names does it call unused?

<details>
<summary>Reveal the result</summary>

```text
$ uv run ruff check scratch/messy.py
E401 [*] Multiple imports on one line
I001 [*] Import block is un-sorted or un-formatted
F401 [*] `os` imported but unused
F401 [*] `sys` imported but unused
F401 [*] `pandas` imported but unused
Found 5 errors.
[*] 5 fixable with `--fix`.
```

Under each problem ruff prints the code and the fix it suggests; they are left out here, and the last summary line of `--fix` is left out too.

</details>

*Why:* five problems, one per rule hit: the imports on one line, their order, and three names that are never used. `--fix` removed all three imports, which is a safe change, and left the layout alone: that is the formatter's job. Run `uv run ruff format scratch/messy.py` and it prints `1 file reformatted`; the file becomes:

```python
def line_total(price, qty, discount=0):
```

Then `uv run ruff check scratch/messy.py` prints `All checks passed!` and `uv run ruff format --check scratch/messy.py` prints `1 file already formatted`. ### 3. Read a class from its docs

**Idea.** A *class* is a recipe for objects. Calling the class makes one object, an *instance*, which holds values (attributes) and functions that act on it (methods). You have used classes since C24 without writing one: `argparse.ArgumentParser`, `Path`, `pd.Timestamp`, `pd.DataFrame`. To read one, start at its documentation page: the signature first (a parameter with `=` has a default), then the parameters, then the methods. Then ask the terminal the same questions.

**Try it.** Print the signature of `ArgumentParser`, and save this as `scratch/parser_demo.py`:

```bash
uv run python -c 'import argparse, inspect; print(inspect.signature(argparse.ArgumentParser))'
```

```python
import argparse

parser = argparse.ArgumentParser(prog="cafe-report")
parser.add_argument("--month", required=True)
args = parser.parse_args(["--month", "2026-04"])
print(args)
print(args.month)
print(type(args).__name__)
```

**Predict:** What do the three lines of the script print?

<details>
<summary>Reveal the result</summary>

```text
Namespace(month='2026-04')
2026-04
Namespace
```

The signature on Python 3.13 reads `(prog=None, usage=None, description=None, epilog=None, parents=[], formatter_class=<class 'argparse.HelpFormatter'>, prefix_chars='-', fromfile_prefix_chars=None, argument_default=None, conflict_handler='error', add_help=True, allow_abbrev=True, exit_on_error=True)`; a later Python prints more parameters.

</details>

*Why:* the argparse page lists the same parameters, all with defaults, and says they should be passed as keyword arguments, which is why `ArgumentParser(prog="cafe-report")` names `prog`. `inspect.signature` returns the signature of any callable, so the terminal gives it without the page. The page also says `parse_args` returns the populated namespace, and `Namespace` is a simple class that holds attributes: `args.month` is an attribute of an instance, the same kind of thing as the `args.data_dir` that your `cli.py` reads. To read how a class is built, `inspect.getsource` returns the text of its source code, and unit 4 uses it.

### 4. One dataclass, and inheritance when you meet it

**Idea.** A record is a small class that holds a few named values. The `@dataclass` decorator writes `__init__`, `__repr__` and `__eq__` for a class from its list of fields. `frozen=True` is an option of the decorator, explained below.

**Try it.** Save the record in `src/cafe_report/models.py`, and use it in a script `scratch/record.py`:

```python
from dataclasses import dataclass


@dataclass(frozen=True)
class StoreSales:
    """One cafe's completed orders and sales for a month."""

    store_id: int
    orders: int
    sales: float

    def average_order(self) -> float:
        """Return the sales divided by the orders, rounded to cents."""
        return round(self.sales / self.orders, 2)
```

```python
from cafe_report.models import StoreSales

record = StoreSales(2, 103, 1252.0)
print(record)
print(record == StoreSales(2, 103, 1252.0))
print(record.average_order())
record.orders = 5
```

**Predict:** What do the first three lines print, and what happens at the last line?

<details>
<summary>Reveal the result</summary>

```text
StoreSales(store_id=2, orders=103, sales=1252.0)
True
12.16
```

The last line stops the script with this error:

```text
dataclasses.FrozenInstanceError: cannot assign to field 'orders'
```

</details>

*Why:* the class has three fields and one method, and you wrote no `__init__`, `__repr__` or `__eq__`: `print` shows every field by name, and two records with equal fields are equal. The dataclasses page says that `frozen` makes assigning to a field raise an exception. It also says that nothing in `@dataclass` examines the type in an annotation (two special cases aside, which do not matter here), so `StoreSales("two", 103, 1252.0)` is accepted too: the fields are a list of names, and their types are notes. Add this function to `report.py`, with `from cafe_report.models import StoreSales` at the top, because a test can then compare records with `==`:

```python
def summarize(sales: pd.DataFrame) -> list[StoreSales]:
    """Turn each row of store_sales into a StoreSales record."""
    return [
        StoreSales(int(row.store_id), int(row.orders), float(row.sales))
        for row in sales.itertuples()
    ]
```

Now the inheritance you have already used. The merge guard of C27 raised `pd.errors.MergeError`. Print the first line of its source:

```bash
uv run python -c 'import inspect, pandas as pd; print(inspect.getsource(pd.errors.MergeError).splitlines()[0])'
```

**Predict:** What does the line say, and what does that mean for an `except ValueError`?

<details>
<summary>Reveal the result</summary>

```text
class MergeError(ValueError):
```

</details>

*Why:* a class that takes another class in brackets, `class A(B):`, is built on `B` and inherits what `B` has. So `MergeError` is built on `ValueError`: the class in brackets is its parent, so a `MergeError` is a kind of `ValueError`, which the pandas docstring also says. The Python tutorial says an `except` clause matches an exception that is an instance of the class or of one of its derived classes, so `except ValueError` also catches a `MergeError`, the way it caught the `DateParseError` of C26. You will read this line often, in library code and in error messages; writing such classes comes in the later tracks.

<Aside type="tip" title="Remember">

- Hints and a docstring answer the reader's three questions on the function itself; a hint is not a check.
- `ruff check` finds problems, `--fix` repairs the safe ones, `ruff format` sets the layout; name the rules in `pyproject.toml`.
- A class makes objects: attributes hold values, methods act on them; read the signature, then the parameters, then the methods.
- `@dataclass` writes `__init__`, `__repr__` and `__eq__` from the fields, and `frozen=True` stops assignment.
- `class A(B):` reads "A is a kind of B".

**Common trap:** believing a hint is a check. `double("ab")` ran and printed `abab`.

</Aside>

## Finish it

<Exercise id="core-readable-code-and-classes-1">

**A record for a menu item.** Finish the dataclass for one row of `products.csv`, which has the columns `product_id`, `product_name`, `category` and `unit_price_usd`. Save the script as `scratch/product.py` and run it. Starting point (two fields are missing, and the row is read for you):

```python
from dataclasses import dataclass
from pathlib import Path

import pandas as pd


@dataclass(frozen=True)
class Product:
    product_id: int
    product_name: str
    ...  # the two missing fields, with their types


DATA = Path(__file__).resolve().parent.parent / "data"
row = pd.read_csv(DATA / "products.csv").iloc[13]
product = Product(int(row["product_id"]), row["product_name"], row["category"], float(row["unit_price_usd"]))
print(product)
print(product == Product(14, "Avocado Toast", "food", 8.5))
```

Expected: two lines, the record with its four fields by name, and `True`.

<details>
<summary>Hint</summary>

The call passes four values in the order of the file. A field is a name, a colon and a type: the category is text and the price has cents.

</details>

<details>
<summary>Half-solution</summary>

```python
    category: str
    unit_price_usd: ...
```

</details>

<Solution>

```python
@dataclass(frozen=True)
class Product:
    product_id: int
    product_name: str
    category: str
    unit_price_usd: float
```

```text
Product(product_id=14, product_name='Avocado Toast', category='food', unit_price_usd=8.5)
True
```

The order of the fields is the order of the arguments of the generated `__init__`, which is why the call and the class agree. Row 14 of the file, counting from 1, is the Avocado Toast at 8.50 dollars.

</Solution>

</Exercise>

**Spot the flaw.** A colleague writes a dataclass for the lines of an order, and it fails as soon as the file is imported. Save it as `scratch/basket.py` and run it. Expected: an error that stops the script. What does its last line say, and what is the fix?


<details>
<summary>Hint</summary>

Read the last line of the traceback from the bottom up, as in C26. The dataclasses page has a section on mutable default values and says what to use for a field that starts as an empty list.

</details>

<details>
<summary>Half-solution</summary>

```python
from dataclasses import dataclass, field
...
    products: list = field(...)
```

</details>

<Solution>

```text
ValueError: mutable default <class 'list'> for field products is not allowed: use default_factory
```

```python
from dataclasses import dataclass, field


@dataclass
class Basket:
    order_id: int
    products: list = field(default_factory=list)
```

The dataclasses page says that a `field` with a `default_factory` calls it with no arguments whenever a default is needed, which gives each record its own new list. A plain `[]` would be one list shared by every record, so Python refuses it at the moment the class is made. With the fix, `Basket(1)` and `Basket(2)` each start with an empty list, and adding a product to the first leaves the second empty.

</Solution>
