## Can you skip Part 5?

Part 5, Teamwork, scale and the platform, has six lessons, C30 to C35. Try these five questions without looking anything up; the examples are made up. If all five answers are right, go on to Part 6. If not, start here.

1. Your pull request and a teammate's both changed the same two lines of `cli.py`. Theirs was merged first, and GitHub says your branch has conflicts. What do you do?

   <details>
   <summary>answer</summary>

   Fetch and merge `main` into your branch, keep the text you want, delete the marker lines, then `git add`, `git commit`, test and push.

   </details>

2. A reviewer asks for a test on your pull request. Do you open a new one?

   <details>
   <summary>answer</summary>

   No. Commit the test on the same branch and push it.

   </details>

3. Each order record holds a list of lines. Which pandas call gives one row for each line, with the order's id on it?

   <details>
   <summary>answer</summary>

   `pd.json_normalize(orders, record_path="items", meta=["order_id"])`.

   </details>

4. Checking 100,000 order ids against a list of 100,000 known ids takes about a minute. What small change makes it fast?

   <details>
   <summary>answer</summary>

   Make the known ids a set (or dict keys): a set finds an id from its value, and a list is searched item by item.

   </details>

5. An analyst must read the files in one storage folder for a report. What access do you give?

   <details>
   <summary>answer</summary>

   Read-only access to that folder: the least that does the job.

   </details>

## The question

Two people work on the report at once. The owner asks you for a total line, and the teammate Sam is adding an option that prints one store.

> Can you both change `cli.py` without overwriting each other, and can I read what you changed before it goes into `main`?

This is what `main` prints today for the orders since April 1:

| store | orders |
|---:|---:|
| 1 | 365 |
| 2 | 362 |
| 3 | 355 |

By the end you can change the code on a branch, ask for a review in a pull request, answer a comment, settle a conflict with Sam's work, and merge.

**Diverge.** C23 had one line of history. Unit 1 shows where a commit goes when you are on a branch, and unit 3 shows what Git does when two lines changed the same text.

</Aside>

## Learn by doing

About 35 minutes, 4 new ideas: a branch, a pull request with a review, a conflict, and the merge. Work in `cafe-report` after C29, with `git status` clean and `origin` set to the bare repository of C23: a folder on your disk that stands in for GitHub. A second clone plays Sam. GitHub adds a web page around the same steps, described below from its documentation. Your hashes differ, and Git's progress lines are left out.

### 1. A branch is a label on a commit

**Idea.** A *branch* is a movable label on a commit. `HEAD` marks the label you are on. `git switch -c name` makes a branch and moves to it; `git switch name` moves to an existing one.

**Try it.** In `cafe_report/cli.py`, add this line below the `--monthly` argument, and the two lines under it just above `if args.send:` at the end of `main`:

```python
    parser.add_argument("--total", action="store_true", help="also print the total of all stores")
```

```python
    if args.total:
        print(f"all stores: {sum(counts.values())} orders")
```

Make the branch first, then run, commit, and look at the labels. Switch to `main` and count the lines with `total`, then switch back and count again:

```bash
git switch -c add-total-line
uv run python -m cafe_report --since 2026-04-01 --total --log-level WARNING
git commit -am "Add --total: print the total of all stores"
git log --oneline --decorate -3
git switch main
grep -c total cafe_report/cli.py
git switch add-total-line
grep -c total cafe_report/cli.py
```

**Predict:** which commit does each label point to after the commit, and what does `grep -c total` print on `main` and on your branch?

<details>
<summary>Reveal the result</summary>

```console
$ git commit -am "Add --total: print the total of all stores"
[add-total-line 13bc3ff] Add --total: print the total of all stores
 1 file changed, 3 insertions(+)
$ git log --oneline --decorate -3
13bc3ff (HEAD -> add-total-line) Add --total: print the total of all stores
e418a53 (origin/main, main) Add the record, the tests of the settings and the command line, and a README
e53b505 Add type hints and docstrings, and format the code with ruff
$ git switch main
$ grep -c total cafe_report/cli.py
0
$ git switch add-total-line
$ grep -c total cafe_report/cli.py
2
```

The run printed the three store lines, the `WARNING` of C28 about store 3 (355 orders, under 360) and `all stores: 1082 orders`.

</details>

*Why:* a commit moves only the label you are on: it moved `add-total-line` and left `main`, and `origin/main` (the copy of `main` on the remote), where they were. `git switch` rewrote the file in your folder to match the branch. Pro Git calls a branch a lightweight movable pointer to a commit, and `HEAD` the pointer to the local branch you are on.

### 2. A pull request asks for a review

**Idea.** `git push -u origin name` sends the branch and remembers it. A *pull request* is a proposal to merge a branch into another, usually `main`, with a page where the team talks about it. On the repository page you choose your branch and click **Compare & pull request** in the yellow banner, choose the base branch (where the change goes) and the compare branch (yours), write a title and a description, and click **Create Pull Request**. The page has a **Conversation** tab, a **Commits** tab that shows how the branch changed over time, and a **Files changed** tab with the diff.

A reviewer hovers over a line in **Files changed**, clicks the blue comment icon and writes; **Review changes** then offers **Comment**, **Approve** and **Request changes**. Sam reviews yours and writes on the new line:

> Looks right. Please add a test for `--total`: from April 1, the last line should say 1082.

**Try it.** Push the branch and look at the status:

```bash
git push -u origin add-total-line
git status -sb
```

Then answer the comment with a new commit on the same branch. Save this at the end of `tests/test_cli.py`:

```python
def test_the_total_line_adds_up_the_stores(capsys):
    main([str(DATA / "orders.csv"), "--since", "2026-04-01", "--total"])
    assert capsys.readouterr().out.splitlines()[-1] == "all stores: 1082 orders"
```

```bash
uv run pytest -q
git add tests/test_cli.py
git commit -m "Test the total line"
git push
git log --oneline origin/main..add-total-line
```

**Predict:** what does `git status -sb` show after the first push, how many tests pass, and which commits does the last command list?

<details>
<summary>Reveal the result</summary>

*Why:* `-u` links your branch to `origin/add-total-line`, so a plain `git push` knows where to go. `origin/main..add-total-line` means the commits your branch has and `origin/main` lacks, which is what a reviewer reads. No second pull request is needed: the Commits tab of a pull request shows how its branch changed over time, and the new commit is on that branch.

### 3. Two branches changed the same lines

**Idea.** While your pull request waited, Sam's was merged, so `main` moved. Git merges two lines of history by itself when they changed different lines. When both changed the same place it stops with a *conflict* and asks you; GitHub says this often happens when people change the same line of the same file, and that it can often settle simple ones on GitHub while complex ones need a local clone. In a local clone, `git fetch origin` updates `origin/main` without touching your branches, and `git merge origin/main` brings Sam's work into yours.

**Try it.** First Sam's side, in a second clone. Sam adds an option in the same place as you, below `--monthly`, and two lines at the top of the loop, then merges the way the Merge button does:

```bash
git clone ~/cafe-report-backup.git ~/cafe-report-sam
cd ~/cafe-report-sam
git switch -c add-store-option
```

```python
    parser.add_argument("--store", help="print only this store, for example 2")
```

```python
    for record in summarize(counts):
        if args.store and record.store_id != args.store:
            continue
```

```bash
git commit -am "Add --store: print only one store"
git push -u origin add-store-option
git switch main
git merge --no-ff add-store-option -m "Merge branch 'add-store-option'"
git push origin main
cd ~/cafe-report
```

Now yours: bring `main` into your branch and look at the file.

```bash

git status -s
```

### 4. Merge, update main, tidy up

**Idea.** GitHub's default **Merge pull request** keeps every commit of the branch and adds a merge commit to the base branch. `git merge --no-ff` makes the same merge commit locally, even when Git could just move the label forward. Afterwards your own `main` is behind: `git switch main` and `git pull` catch it up, and `git branch -d name` deletes a merged branch.

**Try it.** The owner clicks the button; in Sam's clone, run what it does, then catch up in yours:

```bash
cd ~/cafe-report-sam
git fetch origin
git merge --no-ff origin/add-total-line -m "Merge pull request: add --total"
git push origin main
cd ~/cafe-report
git switch main
git pull
git log --oneline --graph -6
git branch -d add-total-line
git status -sb
```

**Predict:** what does `git pull` say about how it caught up, and what does `git branch -d` print?

<details>
<summary>Reveal the result</summary>

```console
$ git pull
```

</details>

*Why:* `main` had only commits to receive, so Git moved the label forward, a fast-forward (Pro Git). The history keeps every commit of both branches and both merge commits. `git branch -d` refuses a branch that is not fully merged, which is its safety. Your option and Sam's now live on `main`.

<Aside type="tip" title="Remember">

- A branch is a label on a commit; a new commit moves only the branch you are on.
- A pull request proposes a merge; answer a review comment with a new commit on the same branch.
- `git fetch`, then `git merge origin/main`, brings the team's work into your branch; a conflict marks both sides.
- Resolve it by editing the file to the text you want, then `git add` and `git commit`.
- After the merge: `git switch main`, `git pull`, `git branch -d name`.

**Common trap:** starting a change without switching: the commit lands on `main`. Read the branch name in `git status -sb` before you edit.

</Aside>

**Spot the flaw.** A colleague commits an edit to `main` and runs `git push`. Sam had pushed to `main` a few minutes earlier. They write: "I will add `--force`, so my work goes up." Say what `--force` would do here and what to run instead. Expected: a push that ends in `main -> main` without `forced`, and a history with both people's commits.

```console
$ git push
 ! [rejected]        main -> main (fetch first)
hint: Updates were rejected because the remote contains work that you do not
hint: have locally.
```

<details>
<summary>Hint</summary>

The git-push page says what `--force` can do to the remote. Which two commands of unit 3 bring Sam's commit in?

</details>

<details>
<summary>Half-solution</summary>

```bash
git fetch
git merge --no-edit ...
git push
```

</details>

<Solution>

`--force` switches off the check that refused the push, and the git-push page says it can make the remote lose commits. On a copy of this case it did:

```console
$ git push --force
 + 03d58b4...6613d2d main -> main (forced update)
$ git log --oneline origin/main
6613d2d Add espresso
1483ae6 Add the prices
```

Sam's commit `Add tea` is gone from the remote. The fix is the one of unit 3:

```console
$ git fetch
$ git merge --no-edit origin/main
$ git push
   03d58b4..bfeeba9  main -> main
$ git log --oneline
bfeeba9 Merge remote-tracking branch 'origin/main'
6613d2d Add espresso
03d58b4 Add tea
1483ae6 Add the prices
```

The two commits changed different lines of `prices.txt`, so the merge needed no settling, and both are in the history. A pull request avoids the race: the work waits on its own branch until it is reviewed and merged.

</Solution>
