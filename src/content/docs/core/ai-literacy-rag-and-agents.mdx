## The question

A supplier sells a chatbot that "answers from your documents and cites its sources". The cafe owner loads the handbook notes below, twelve lines. Save them as `cafe-notes.txt`:

```text
Refunds: a drink can be returned within 14 days for a refund.
If a cup arrives cold, the cafe gives the money back, no questions asked.
Order 2075 was typed with 20 units of one item; the till should have read 2.
Oat milk adds 0.60 to any drink.
Harbor opened on April 1, 2026.
Gold loyalty members earn double points on tea.
A refund over 20 dollars needs a manager's signature.
Walk-in customers without a loyalty card have no row in the customers table.
The Pumpkin Spice Latte is a fall item and is not on the menu yet.
A canceled order can be refunded only at the till where it was taken.
Campus closes at 6 pm on weekdays.
Old Town shuts at 4 pm on Sundays.
```

> It names a line for every answer. Can I trust it?

By the end you can say what happens between a question and a cited answer, score such a bot, tell a workflow from an agent, and say when SQL beats both.

## Learn by doing

About 45 minutes, 4 new ideas: retrieval, three scores, workflows and agents, and when not to use RAG. The terminal lines run in Git Bash, Terminal or any Linux shell; the SQL runs in the page. The cafe bot's replies were written for this lesson; none is a real transcript.

### 1. Retrieval finds passages by words or by meaning

**Idea.** RAG stands for retrieval-augmented generation, the name Lewis and colleagues (2020) gave to a text generator paired with a searchable index of Wikipedia. The first step, retrieval, picks the few passages worth showing the model. It can pick in two ways. By **words**: look for the question's words in the text, as `grep` does. By **meaning**: turn the question and every passage into an embedding, a list of numbers built so that passages close in meaning end up close together, and return the nearest ones.

Each way misses a different kind of passage. A words search misses a passage that says the same thing in other words. A meaning search has trouble with the opposite kind. One way to see it: an exact code, name or number has little meaning to place. Sciavolino and colleagues (EMNLP 2021) wrote simple questions about named entities and found that "dense retrievers drastically underperform sparse methods"; the dense kind generalized only to common entities, unless the question pattern appeared in its training. So a wrong answer can come from retrieval, not from the model: the model never saw the passage that held the answer.

**Try it.** `grep` prints the lines of a file that contain a word; `-i` ignores upper and lower case (the GNU grep manual's wording: "Ignore case distinctions in patterns and input data") and `-n` puts the line number first. In the folder that holds `cafe-notes.txt`:

```bash
grep -i -n refund cafe-notes.txt
grep -n 2075 cafe-notes.txt
```

**Predict:** How many lines does each command print, and which line that a question about refunds needs is not among them?

### 2. Judge a RAG product on three scores

**Idea.** Grounding means the answer rests on retrieved passages, so it invents less than an answer from memory. It does not stop invention. Magesh and colleagues (2025) tested research tools for lawyers whose makers said retrieval avoided hallucinations; the claims were overstated, and the LexisNexis and Thomson Reuters tools each hallucinated between 17 and 33 percent of the time in their tests, less than a general chatbot but far from never. Judge a RAG bot as you would a new analyst: with questions whose answers you already know, and three scores for each. **Correct**: is the answer right? **Citation correct**: does the cited passage support what the answer says? **Refusal**: when the notes do not hold the answer, does it say so, and does it refuse only then?

**Try it.** The bot answered six questions about `cafe-notes.txt`. Each reply names its line, or says the notes are silent:

| # | question | reply |
|---|---|---|
| 1 | How long do customers have to return a drink? | Within 14 days. (line 1) |
| 2 | When did Harbor open? | April 1, 2026. (line 6) |
| 3 | How many units were typed for order 2075? | 2 units. (line 3) |
| 4 | Is almond milk available? | Almond milk adds 0.60 to any drink. (line 4) |
| 5 | Do students get a discount? | The notes do not say. |
| 6 | Does a cold cup get the money back? | The notes do not say. |

**Predict:** Score each reply on the three scores, using the twelve lines. How many are right on every score that applies?

*Why:* each score catches what the other two let through. A right answer with a wrong citation is luck you cannot check; a refusal is right only when the notes really are silent.

### 3. A workflow follows steps; an agent chooses them

**Idea.** Anthropic (December 2024) draws the line: "Workflows are systems where LLMs and tools are orchestrated through predefined code paths", while agents are "systems where LLMs dynamically direct their own processes and tool usage". In the cafes, a workflow is a script that runs one fixed query every Monday and asks the model for two sentences about the result. An agent is told "find out why June was slow" and picks its own queries, reads the results and picks more. The more the model decides, the more steps you did not see.

In our terms, an agent loop has four parts: generation, execution, feedback, revision. The model writes code, the code runs, the real output or error goes back, and the model revises; loops such as self-debugging (Chen et al., 2023) improved a text-to-SQL baseline. Feedback from running code comes from outside the model. **Consistency is not correctness**: an agent that gives the same total five times agrees with itself, not with the data; C38 called it the same formula run a second way. A loop is also only as good as what scores it. OWASP names the risk of excessive agency: more functions, more permissions or more autonomy than the task needs. For data work, give an agent read access to a copy, and let only a person send, write or delete.

**Try it.** On realistic data analysis the numbers are lower than a demo suggests.

**Predict:** DSBench is a benchmark for data science agents. On its 466 data analysis tasks, about how many of 100 does the best agent solve?

<details>
<summary>Reveal the result</summary>

About 34. The DSBench abstract (arXiv version 3, April 2025) reports the best agent "solving only 34.12% of data analysis tasks". DABstep (arXiv version 1, 30 June 2025) draws its tasks from a financial analytics platform, and its best agent reached 14.55% on the hardest ones. Both papers are older than today's agents; these figures are as of 2026-11-23, to review by 2027-05-23.

</details>

*Why:* an agent that fails about two of three such tasks is useful as a drafter and dangerous as an authority, which is the reason for the five checks of C38 and the stop rule of C42.

Three kept, one discarded, one crash, and the best score only went up: each kept change beat the best so far, and the discarded one did not. A cycle, in the list at the top of `run.py`, proposes a change, implements it, evaluates it, keeps or discards it and writes a lesson after a mistake; the next cycle builds on what was kept. In our terms that is generation, execution, feedback and revision. `run.py` says the evaluation "lives outside the workspace", away from what the loop edits. A person chose that number: if it measured the wrong thing, the loop would get better at the wrong thing every cycle.

</details>

</Aside>

### 4. When SQL or a plain prompt beats RAG

**Idea.** Retrieval finds text. Two jobs do not need it. A question about the rows of a table, such as a count, a sum or a share, has no passage that holds the answer, and SQL computes it exactly. And a small set of material that fits in the prompt, such as the twelve lines above, is better pasted whole, as in a context pack (C37): nothing is left for a retrieval step to miss. RAG pays off when the material is too large to paste and each answer sits in a few passages.

**Try it.** The units of each category sold in June, completed orders:

<RunSQL query={`SELECT p.category, SUM(i.quantity) AS units
FROM orders o
JOIN order_items i ON i.order_id = o.order_id
JOIN products p ON p.product_id = i.product_id
WHERE o.status = 'completed' AND o.ordered_at >= '2026-06-01' AND o.ordered_at < '2026-07-01'
GROUP BY p.category
ORDER BY units DESC, p.category;`} />

Expected: 4 rows, 2 columns.

**Predict:** How many of the twelve notes could a retrieval step hand to a model so that it can give these four numbers?

*Why:* none. Coffee 489, bakery 257, food 141 and tea 133 come from adding about 1,020 units on 644 lines, which no passage of text holds. Retrieval for a rule in prose, SQL for a number in a table, the whole file in the prompt when it fits.

<Aside type="tip" title="Remember">

- RAG is retrieve, ground, answer. A wrong answer can come from retrieval, before the model starts.
- A words search misses other words; a meaning search can miss an exact code or number.
- Judge a bot on three scores: correct, citation correct, refusal.
- A workflow follows steps you wrote; an agent chooses its own, so give it less access and check more.
- A number in a table is for SQL; a small set of notes goes whole into the prompt.

**Common trap:** "It cites a source, so it is grounded, so it is right." A citation is a claim: open the line it names and read it.

</Aside>
