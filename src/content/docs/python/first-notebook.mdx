**Where do you write Python?** Almost anywhere.

You can save a plain text file that ends in `.py` and ask Python to run it. You can write that file in an editor such as VS Code. You can open a notebook on your own computer. Or you can open a notebook that lives on someone else's computer and use it from your browser.

This course starts with the notebook, because you already know the feeling. On the SQL pages you typed a query, pressed Run and read the result in the output box. In Excel you type in a cell and the answer shows up there. A notebook is that same feeling for code: a page where you type, press Run and see the answer under what you typed.

The idea comes from the lab. Scientists keep notebooks: what they tried, what happened and why, all on one page. Programmers borrowed it. The computer scientist Donald Knuth popularized writing plain-English explanation and code together, an idea called literate programming. Scientists and engineers often have to run a calculation and explain it to someone else, so notebooks that mix code, text and charts became a popular way to share their work.

Python got a better place to type in 2001. A graduate student, Fernando Pérez, started IPython because he wanted a better prompt and easy access to earlier output. In 2014 the project grew into Project Jupyter, which builds tools for interactive computing, notebooks included, for many languages. Today Jupyter works with over 40 programming languages, including Python, R and Julia. The name Jupyter comes from the three languages the project originally supported: Julia, Python and R.

Then the notebook moved into the browser. Google Colab, short for Colaboratory, is a hosted Jupyter notebook service. Hosted means someone else runs the computer: your code runs on a virtual machine that is private to your account, and your notebook is saved in your Google Drive. Colab needs no setup and is free of charge to use. Its free resources are not guaranteed and its limits change, so this course never depends on a number from it.

## The question

The owner of the cafes asks:

> How many orders did the cafes take, and how many at each one?

You have answered this twice: once with a PivotTable, once with `GROUP BY`. This page answers it a third time, in a notebook, and the three answers will agree. The three cafes:

| store_id | store_name | city |
|---:|---|---|
| 1 | Old Town | Oakland |
| 2 | Campus | Berkeley |
| 3 | Harbor | Alameda |

<Aside type="note" title="You already know this">

**Match.** A notebook cell works like the editor on the SQL pages: you type, press Run and read the result under it. `len(orders)` is `SELECT COUNT(*) FROM orders`, from *GROUP BY and HAVING* (S8) and *Counting and summing: aggregate functions* (S7), and it gives the same count. The store totals match the PivotTable of *Summarize with a PivotTable* (E15).

**Diverge.** A query and a refreshed PivotTable start from the table every time. A notebook remembers: a value that one cell sets is still there when the next cell runs, so the order in which you run cells matters. Unit 3 shows it.

</Aside>

## Learn by doing

About 25 minutes, 4 new ideas: cells, Run, run order and your first line. You write nothing until unit 4.

<OpenInColab />

### 1. A page of cells

**Idea.** A notebook is made of cells. A text cell holds words, like this page. A code cell holds Python, and Python runs only code cells. A cell is a spreadsheet cell with a Run button: you put something in it and read the answer there.

**Try it.** Press the Run button of the first code cell. It holds one line, two lattes at \$4.50 each:

```python
4.50 * 2
```

**Predict:** what appears under the cell?

<details>
<summary>Reveal the result</summary>

```text
9.0
```

</details>

*Why:* the output is the value of the last line of the cell. Python keeps the decimal point, so it shows 9.0, not 9.

### 2. Run, one cell at a time

**Idea.** Run sends one cell to Python and shows the answer under that cell. No other cell runs. A cell can write a line with `print`, and it shows the value of its last line by itself.

**Try it.** Run the data cell first, then this cell:

```python
print("Three cafes: Old Town, Campus and Harbor")
len(orders)
```

**Predict:** this cell does two things. What appears under it?

<details>
<summary>Reveal the result</summary>

```text
Three cafes: Old Town, Campus and Harbor
1800
```

</details>

*Why:* `print` wrote the first line. The last line, `len(orders)`, was shown after it. `len` counts rows, as `COUNT(*)` does, and `orders` is the table that the data cell loaded.

### 3. Run order, and Run all from the top

**Idea.** A name keeps its value in memory until a cell sets it again. Editing the text of a cell changes nothing in memory until you run that cell. Cell A sets a number and cell B uses it, as a formula uses an input cell:

```python
store_number = 1
```

```python
stores[stores.store_id == store_number]
```

**Try it.** Run A, then B. Then change A to `store_number = 2` and do not run it. Run only B.

**Predict:** which store does B show now?

<details>
<summary>Reveal the result</summary>

```text
   store_id store_name     city   opened_on
0         1   Old Town  Oakland  2023-05-12
```

Still Old Town. Now run A and then B, and B shows Campus:

```text
   store_id store_name      city   opened_on
1         2     Campus  Berkeley  2024-09-03
```

</details>

*Why:* B reads the memory, not the text on the page. The page said 2, but memory said 1 until A ran. The habit that fixes this has a name: **Run all from the top.** Restart the session so that memory is empty, then run every cell from the first to the last. The answers then come only from what is written on the page. Do it before you trust a number and before you send a notebook to anyone. In Colab it is one click: open the **Runtime** menu and choose **Restart session and run all**.

### 4. Write your first line

**Idea.** You have run lines that others wrote. Now you write one. `len(...)` is a function: a name, then brackets that hold what it works on. It gives a value back.

**Try it.** In the notebook, the cell holds `rows = len(orders)`. On the next line, write the same for `customers` and call it `customer_rows`.

**Predict:** how many customers will it count?

<details>
<summary>Reveal the result</summary>

```text
150
```

</details>

*Why:* it is `SELECT COUNT(*) FROM customers`: 150 loyalty customers.

Now the match you were promised. Run this pre-written cell. It uses pandas, which comes later, so only read it. The PivotTable and `GROUP BY` both gave one count per store.

**Predict:** will the notebook agree?

```python
orders["store_id"].value_counts().sort_index()
```

<details>
<summary>Reveal the result</summary>

```text
store_id
1    729
2    716
3    355
Name: count, dtype: int64
```

</details>

*Why:* 729, 716 and 355 are the three totals of the PivotTable and of `GROUP BY` store (S8), and they add up to 1,800. Three tools, one answer. Without `.sort_index()` the stores would come back with the largest count first.

<Aside type="tip" title="Remember">

- A notebook is a page of text cells and code cells.
- Run sends one cell to Python and shows the answer under it.
- A name keeps its value in memory until a cell sets it again.
- Before you trust a number: Run all from the top.
- `len(table)` counts rows, as `COUNT(*)` does.

**Common trap:** a cell you changed but did not run. The page shows one value and the memory holds another.

</Aside>
