## The question

The owner asks:

> How did each cafe sell, month by month, and which cafe did best in which month?

The lines of order 1001, one row for each line, with the cafe and the month beside them:

| order_item_id | order_id | store_id | month | amount |
|---:|---:|---:|---:|---:|
| 5001 | 1001 | 2 | 1 | 3.25 |
| 5002 | 1001 | 2 | 1 | 4.75 |
| 5003 | 1001 | 2 | 1 | 6.00 |

The owner wants one row for each cafe and one column for each month, as in a PivotTable. By the end of this page you will switch a table between that shape and one row for each fact, build it with `pivot_table`, and check that no money got lost on the way.

<Aside type="note" title="You already know this">

**Diverge.** In E15 the PivotTable showed a grand total without being asked. `pivot_table` adds totals only when you ask, and unit 4 shows what they add.

## The big idea

`melt` turns the headings of columns into the values of one column, `pivot` turns the values of a column back into headings, and `pivot_table` also adds up the rows that land in one cell.

### 1. melt: columns into rows

**Idea.** A table is **wide** when the headings of its columns are values of something, here a payment method, and **long** when one column holds those values and every fact has its own row. Tidy data, in Wickham's words, has each variable in a column and each observation in a row, and a long table is usually the tidy one. `table.melt(id_vars="store_id")` keeps `store_id` and turns every other column into rows.

**Try it.** A wide table as a colleague's PivotTable export arrives: the orders of each store, one column for each payment method (typed here from the cafe-sales counts).

```python
wide_orders = pd.DataFrame({
    "store_id": [1, 2, 3],
    "card": [421, 400, 180],
    "cash": [91, 107, 55],
    "mobile": [217, 209, 120],
})
long = wide_orders.melt(id_vars="store_id")
print(long.shape)
print(long.columns.tolist())
```

**Predict:** how many rows will `long` have, and what will its three columns be called?

<details>
<summary>Reveal the result</summary>

```text
(9, 3)
['store_id', 'variable', 'value']
```

</details>

*Why:* 9 rows, one for each of the 3 stores and 3 payment methods. The old headings became the cells of a column, and the old cells became the cells of another. `melt` names them `variable` and `value` unless you say otherwise. Now with names that mean something, and a total for each method:

```python
long = wide_orders.melt(id_vars="store_id", var_name="payment_method", value_name="orders")
print(long.groupby("payment_method")["orders"].sum())
print(long["orders"].sum())
```

**Predict:** what will the three totals be, and what will their sum be?

<details>
<summary>Reveal the result</summary>

```text
payment_method
card      1001
cash       253
mobile     546
Name: orders, dtype: int64
1800
```

</details>

*Why:* 1,001 card, 253 cash and 546 mobile orders, and 1,800 in all: the counts of unit 4 of lesson P14, from another table. The long shape suits `groupby`: one column names the group, one column holds the numbers to add. In the wide shape there was no single column to add.

### 2. Group by two keys

**Idea.** `groupby(["store_id", "month"])` takes a list of keys and groups by them together. The two keys together are the row label of the result, and `reset_index()` turns them back into ordinary columns. It is the `GROUP BY store_id, month` of *GROUP BY and HAVING* (S8).

**Try it.** The sales of each store in each month:

```python
store_month = sales.groupby(["store_id", "month"])["amount"].sum().reset_index()
print(store_month.shape)
print(store_month.head(4))
```

**Predict:** there are 3 stores and 6 months. How many rows will `store_month` have?

<details>
<summary>Reveal the result</summary>

```text
(15, 3)
   store_id  month   amount
0         1      1  1591.00
1         1      2  1162.00
2         1      3  1554.50
3         1      4  1542.25
```

</details>

*Why:* 15 rows, not 18: the result has one row for each pair of keys that occurs in the table. Harbor opened on April 1, so its pairs for January, February and March are not in the data, and a group exists only for a pair that is. The three keys of each row are in columns now, so `store_month` is a long table: one row for each store and month.

### 3. pivot: rows into columns

**Idea.** `table.pivot(index="store_id", columns="month", values="amount")` turns the values of `columns` into headings, the values of `index` into row labels, and puts in each cell the `values` of the row with that pair. It undoes a `melt`.

**Try it.** The table the owner asked for, from `store_month`:

```python
wide = store_month.pivot(index="store_id", columns="month", values="amount")
print(wide.shape)
print(wide.loc[3].tolist())
```

**Predict:** what shape will `wide` have, and what will the row of Harbor, store 3, hold in its first three months?

<details>
<summary>Reveal the result</summary>

```text
(3, 6)
[nan, nan, nan, 1596.5, 1546.5, 1463.25]
```

</details>

*Why:* 3 rows and 6 columns: all 18 cells exist. The three pairs that had no row in unit 2 are empty cells, shown as `nan`, the missing value of lesson P16: no orders, not 0. Now `pivot` on the order lines themselves, which have many rows for each store and month:

```python
show_error('sales.pivot(index="store_id", columns="month", values="amount")', short=True)
```

**Predict:** `sales` has many rows for the same store and month. What will `pivot` do with them: add them up, keep the first, or stop?

<details>
<summary>Reveal the result</summary>

```text
ValueError: Index contains duplicate entries, cannot reshape
```

</details>

*Why:* it stops, with a `ValueError`: pandas does not choose between rows for you, and the pandas page for `pivot` says that duplicates raise this error. Adding the rows up is a decision, and the next unit is the tool that makes it.

### 4. pivot_table: the PivotTable in code

**Idea.** `table.pivot_table(index=..., columns=..., values=..., aggfunc=...)` builds the wide table straight from the long one and adds up the rows that land in one cell with `aggfunc`, such as `"sum"` or `"count"`. It is the PivotTable of E15: Rows, Columns, Values and the summary of the value. `margins=True` asks for the totals that a PivotTable draws on its own.

**Try it.** The sales of each store in each category, with totals:

```python
by_category = sales.pivot_table(index="store_id", columns="category", values="amount", aggfunc="sum", margins=True)
print(by_category.shape)
print(by_category.round(2))
```

**Predict:** the table has 3 stores and 4 categories. What shape will it really have, and what will the cell in the bottom right corner hold?

<details>
<summary>Reveal the result</summary>

```text
(4, 5)
category   bakery    coffee     food     tea       All
store_id                                              
1         1511.00   4507.75  1810.50  1315.0   9144.25
2         1584.25   4134.75  2038.75  1246.0   9003.75
3          729.00   2164.50  1041.25   671.5   4606.25
All       3824.25  10807.00  4890.50  3232.5  22754.25
```

</details>

*Why:* 4 rows and 5 columns: the totals are a row and a column named `All`, and their corner is the grand total of all 3,287 lines, the same figure as the PivotTable of E15 when it counts every row. They are cells of the table, not a note beside it. Now the same call without `aggfunc` and without `margins`:

```python
by_default = sales.pivot_table(index="store_id", columns="category", values="amount")
print(by_default.round(2).loc[1])
```

**Predict:** for store 1, the coffee cell of the table above was 4,507.75. What kind of number will the coffee cell hold now?

<details>
<summary>Reveal the result</summary>

```text
category
bakery     5.44
coffee     6.40
food      11.91
tea        6.48
Name: 1, dtype: float64
```

</details>

*Why:* about 6.40, the average of one coffee line of store 1, not a total. The pandas page for `pivot_table` says that `aggfunc` is `"mean"` unless you give one. The table looks like the other one, and its cells mean something else.

### 5. Check: there and back

Write down what you expect, then run the cell. `wide` is the table of unit 3.

```python
back = wide.reset_index().melt(id_vars="store_id", var_name="month", value_name="amount")
print(len(back), back["amount"].notna().sum(), back["amount"].sum())
```

**Predict:** how many rows will `back` have, how many of them hold a number, and what will the numbers add up to?

<details>
<summary>Reveal the result</summary>

```text
18 15 22754.25
```

</details>

*Why:* 18 rows, 15 numbers, 22,754.25: `melt` kept the three empty cells as rows, and the sum skips them. The total is the control total of lessons P14, P13 and E15, all 3,287 lines, the canceled order and the extra-zero line included. Nothing was lost between the lines and the wide table and back.

<Aside type="tip" title="Remember">

- `melt(id_vars=...)` turns the other columns into rows: a wide table becomes long.
- `groupby([key1, key2])` gives one row for each pair of keys that occurs, so a pair that never happened has no row.
- `pivot` turns rows into columns, needs one row for each pair and stops on duplicates. A pair with no row is an empty cell.
- `pivot_table` adds up the rows of each cell with `aggfunc`. `margins=True` adds the totals row and column, named `All`.
- Check the total: the cells of a table made by reshaping must add up to the total of the lines.

**Common trap:** `pivot_table` without `aggfunc` averages, so a table that looks like totals holds averages.

</Aside>

**What share of the orders of the customers who live in Alameda were taken at Harbor, store 3?** `counts` holds the orders of each home city and store, one row for each pair; the walk-in order has no city, so it is in no group. Replace the first `None` with `counts` as a wide table, one row for each city and one column for each store, then set `answer_1` to the share, a number between 0 and 1. Expected: one decimal number between 0 and 1.

```python
home = orders.merge(customers[["customer_id", "city"]], on="customer_id", how="left", validate="many_to_one")
counts = home.groupby(["city", "store_id"]).size().reset_index(name="orders")  # given: one row for each city and store
wide_home = None  # replace None: counts as a wide table, one row for each city
answer_1 = None  # then set answer_1 to the Alameda orders taken at store 3, divided by all Alameda orders
```

<details>
<summary>Hint</summary>

A pair of city and store is one row of `counts`, and `pivot` makes the stores the columns. Which total do you want, the one down a column or the one along a row?

</details>

<details>
<summary>Half-solution</summary>

```python
wide_home = counts.pivot(index="city", columns="store_id", values=...)
answer_1 = wide_home.loc["Alameda", 3] / ...
```

</details>

<Solution>

```python
home = orders.merge(customers[["customer_id", "city"]], on="customer_id", how="left", validate="many_to_one")
counts = home.groupby(["city", "store_id"]).size().reset_index(name="orders")
wide_home = counts.pivot(index="city", columns="store_id", values="orders")
answer_1 = wide_home.loc["Alameda", 3] / wide_home.loc["Alameda"].sum()
```

The answer is 0.7772: 314 of the 404 orders of Alameda's customers were taken at Harbor. The row of Alameda holds 47, 43 and 314. Dividing by the column of store 3 gives 0.8845, the share of Harbor's orders that came from Alameda's customers, another question; the check cell says so.
