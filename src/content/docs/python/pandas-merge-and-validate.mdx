## The question

The owner asks:

> Attach the name of its store to every order, and tell me which customers have no orders and which orders have no customer.

The first three orders hold a store number, and the store names live in another table:

| order_id | customer_id | store_id |
|---:|---:|---:|
| 1001 | 15 | 2 |
| 1002 | 46 | 1 |
| 1003 | 61 | 2 |

| store_id | store_name |
|---:|---|
| 1 | Old Town |
| 2 | Campus |
| 3 | Harbor |

The two tables share a key, `store_id`, and a merge uses it to bring the rows together. By the end of this page you will merge three times, say how many rows to expect before each run, and read where every row of the result came from.

<Aside type="note" title="You already know this">

**Match.** In *INNER JOIN: pairing rows on a key* (S19), `JOIN ... ON` paired the rows that had the same key, and `LEFT JOIN` (S20) also kept the rows without a partner. `orders.merge(stores, on="store_id")` pairs rows the same way, and `how="left"` is the `LEFT JOIN`.

**Diverge.** `map`, the twin of VLOOKUP in *New columns from old: assign, map and apply* (P13), gives one value for each row and never adds rows. A merge can add rows, as *Join fan-out: aggregate before you join* (S21) showed in SQL, and pandas does not say so unless you ask. Unit 4 shows what happens.

</Aside>

## Learn by doing

<OpenInColab />

### 1. merge, and validate what you expect

**Idea.** `left.merge(right, on="key", validate="many_to_one")` pairs each row of `left` with the row of `right` that has the same key and adds the columns of `right`. `validate` is a promise about the keys: `"many_to_one"` says that each key is unique in `right`, so a row of `left` finds at most one partner. Write the promise, and the number of rows you expect, before you run it.

**Try it.** Each order gets its store:

```python
orders_stores = orders.merge(stores, on="store_id", validate="many_to_one")
print(orders.shape, stores.shape, orders_stores.shape)
```

**Predict:** each order has one store. How many rows and columns will `orders_stores` have? `orders` has 6 columns, `stores` has 4, and the key is in both.

<details>
<summary>Reveal the result</summary>

```text
(1800, 6) (3, 4) (1800, 9)
```

</details>

*Why:* 1,800 rows, the rows of `orders`, because each order found exactly one store, and 9 columns: 6 and 4, with the key counted once. With `many_to_one` the rows of the left table are the number to expect. A wrong promise:

```python
try:
    orders.merge(stores, on="store_id", validate="one_to_one")
except pd.errors.MergeError as error:
    print(error.args[0].split("\n")[0])
```

**Predict:** `one_to_one` says that every key is unique on both sides, but a store appears many times in `orders`. Does `merge` return a smaller table, print a warning, or stop?

<details>
<summary>Reveal the result</summary>

```text
Merge keys are not unique in left dataset; not a one-to-one merge
```

</details>

*Why:* it stopped with a `MergeError`, and the message says which side repeats its keys. The pandas page for `merge` lists the four promises: `"one_to_one"` checks both tables, `"one_to_many"` the left one, `"many_to_one"` the right one, and `"many_to_many"` is allowed and checks nothing. A merge that stops is better than one that runs and returns the wrong rows.

### 2. how: what happens to a row with no partner

**Idea.** `how` decides what a merge does with the rows that have no partner. `"inner"`, the default, keeps only the rows whose key is in both tables. `"left"` keeps every row of the left table and fills the columns of the right table with `NaN` where there is no partner. `"outer"` keeps the unmatched rows of both tables. They are the `INNER JOIN` and the `LEFT JOIN` of S19 and S20, and the pandas page for `merge` calls `"left"` similar to a SQL left outer join.

**Try it.** Each customer with their orders, one customer to many orders:

```python
inner = customers.merge(orders, on="customer_id", how="inner", validate="one_to_many")
left = customers.merge(orders, on="customer_id", how="left", validate="one_to_many")
print(len(customers), len(orders))
print(len(inner), len(left))
```

**Predict:** `orders` holds one walk-in order with no customer id, and some customers have never ordered. Will `inner` have 1,800 rows? Which of `inner` and `left` has more rows?

<details>
<summary>Reveal the result</summary>

```text
150 1800
1799 1804
```

</details>

*Why:* `inner` has 1,799 rows, one for each order that has a customer: the walk-in order found no partner and was left out. `left` has 1,804, more than `inner`, because the customers without an order are kept, and their order columns are `NaN`. The row counts differ because `how` decides what happens to the unmatched rows, and the walk-in order is lost in both.

### 3. indicator: where each row came from

**Idea.** `indicator=True` adds a column called `_merge` that says where each row of the result came from: `"both"` when the key was in both tables, `"left_only"` or `"right_only"` when it was in one. It is the margin column of the picture above, and it turns the unmatched rows into something you can count.

**Try it.** An outer merge keeps the unmatched rows of both tables:

```python
audit = customers.merge(orders, on="customer_id", how="outer", validate="one_to_many", indicator=True)
print(audit["_merge"].value_counts())
print(len(audit))
```

**Predict:** how many rows of `audit` are `both`, how many `left_only` and how many `right_only`?

<details>
<summary>Reveal the result</summary>

```text
_merge
both          1799
left_only        5
right_only       1
Name: count, dtype: int64
1805
```

</details>

*Why:* 1,799 rows are `both`, the orders with a customer. The 5 `left_only` rows are customers who never ordered. The 1 `right_only` row is the walk-in order, whose blank customer id found no customer. The three add up to the 1,805 rows, and each one has a reason. Read the `_merge` counts before you use a merged table: they say what was lost.

### 4. many to many: the rows that multiply

**Idea.** When a key repeats in both tables, a merge pairs every row of one with every row of the other that has the same key. The pandas guide calls it the Cartesian product of the rows that share the key. It is the fan-out of S21. The promise `"many_to_many"` is allowed and checks nothing, so no error appears.

**Try it.** A small promo list typed here, not cafe-sales data: Latte, product 3, has two promotions, and Mocha, product 5, has one. Latte has 420 order lines.

```python
promo = pd.DataFrame({"product_id": [3, 3, 5], "promo": ["student", "staff", "student"]})
with_promo = order_items.merge(promo, on="product_id", how="left", validate="many_to_many")
print(len(order_items), len(with_promo))
```

**Predict:** each Latte line meets both Latte rows of `promo`, and each other line finds one row or none. How many rows will `with_promo` have?

<details>
<summary>Reveal the result</summary>

```text
3287 3707
```

</details>

*Why:* 3,707 rows: 3,287 plus 420, because every Latte line appears twice. Nothing stopped and nothing was printed. A sum over the merged table now counts those lines twice:

```python
priced = lines.merge(promo, on="product_id", how="left", validate="many_to_many")
print(priced["amount"].sum(), lines["amount"].sum())
```

**Predict:** do the two totals agree? The second is the control total of the order lines.

<details>
<summary>Reveal the result</summary>

```text
25681.25 22754.25
```

</details>

*Why:* they differ: the total of the merged table is 2,927.00 too big, which is the sales of all the Latte lines, counted a second time. The row count was the warning, and the control total confirmed it.

### 5. Check: a merge instead of map

The price of each line, by merge this time, where lesson P13 used `map`. Write down what you expect, then run the cell.

```python
with_price = order_items.merge(products[["product_id", "unit_price_usd"]], on="product_id", how="left", validate="many_to_one")
amount = with_price["quantity"] * with_price["unit_price_usd"] - with_price["discount_usd"]
print(len(with_price), len(order_items))
print(amount.sum())
```

**Predict:** is the row count unchanged, and what do the amounts add up to?

<details>
<summary>Reveal the result</summary>

```text
3287 3287
22754.25
```

</details>

*Why:* 3,287 rows, as many as before, and the total of lesson P13, *Summarize with a PivotTable* (E15) and *Counting and summing: aggregate functions* (S7): all lines, the canceled order and the extra-zero line included. `map` and `merge` reach the same price. `merge` brings in as many columns as you list, and it is the tool to use when the other table is a table.

<Aside type="tip" title="Remember">

- Write `validate` on every merge, and the number of rows you expect before you run it.
- `how="inner"` keeps rows with a partner in both tables, `"left"` keeps all the left rows, `"outer"` keeps everything.
- `indicator=True` adds `_merge`: `both`, `left_only` or `right_only`. Count it.
- A key that repeats on both sides multiplies the rows, and `"many_to_many"` checks nothing.
- After the merge, compare the row count and a total with what you knew.

**Common trap:** a merge does not complain about a repeated key unless `validate` promises that it is unique, and the extra rows inflate every total.

</Aside>
