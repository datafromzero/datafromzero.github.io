## The big idea

A file format is a choice about what a table costs to store and to read, and a partition is a choice about how many files that table is.

### 1. One table in three formats

**Idea.** JSON and CSV are text. Parquet is a column-oriented file format: the Apache Parquet page calls it a format designed for efficient data storage and retrieval, with compression and encoding schemes, and the DuckDB page says that when a query reads a Parquet file, only the columns the query needs are read. A CSV file has no types: DuckDB's reader guesses them by trying candidate types on a sample of the file, 20,480 rows by default.

**Try it.** Staging comes first. Save this as `src/pipeline/stage.py` and read it once: it reads the landed pages with the columns spelled out (including `channel`, the field of DE2: pages without it give `NULL`), keeps the latest version of each key, and writes the lines, products and stores as Parquet.

```python
"""Turn the raw pages into typed, de-duplicated tables in the staging layer."""

import duckdb

from pipeline.config import RAW_DIR, SOURCE_FILES, STAGING_DIR
from pipeline.ingest import window_name

LINE_FIELDS = """STRUCT(
    order_item_id BIGINT, order_id BIGINT, ordered_at TIMESTAMP, store_id BIGINT, customer_id BIGINT,
    status VARCHAR, payment_method VARCHAR, product_id BIGINT, quantity BIGINT, discount_usd DECIMAL(8, 2),
    updated_at TIMESTAMP, channel VARCHAR
)"""


def staged_lines(con, pages_glob):
    """One row for each order line: typed columns, and the latest version when a key repeats."""
    return con.sql(f"""
        WITH pages AS (
            SELECT unnest(data) AS line
            FROM read_json('{pages_glob}', columns = {{data: '{LINE_FIELDS}[]'}})
        ),
        lines AS (SELECT line.* FROM pages)
        SELECT * FROM lines
        QUALIFY row_number() OVER (PARTITION BY order_item_id ORDER BY updated_at DESC) = 1
        ORDER BY order_item_id
    """)


def write_staging(con, pages_glob=None, out_dir=STAGING_DIR):
    """Write order_lines, products and stores as Parquet files in the staging folder."""
    pages_glob = pages_glob or str(RAW_DIR / "order_lines" / window_name(None, None) / "page-*.json")
    out_dir.mkdir(parents=True, exist_ok=True)
    lines = staged_lines(con, pages_glob)
    lines.write_parquet(str(out_dir / "order_lines.parquet"))
    for name, types in {
        "products": {"product_id": "INTEGER", "unit_price_usd": "DECIMAL(6, 2)"},
        "stores": {"store_id": "INTEGER", "opened_on": "DATE"},
    }.items():
        csv_path = SOURCE_FILES / f"{name}.csv"
        con.read_csv(str(csv_path), dtype=types).write_parquet(str(out_dir / f"{name}.parquet"))


if __name__ == "__main__":
    write_staging(duckdb.connect())
```

It writes the staged lines as CSV in a temporary folder and, for each format, times the same query three ways. Its core is this function:

```python
def median_ms(con, sql):
    times = []
    for _ in range(RUNS):
        start = time.perf_counter()
        con.sql(sql).fetchall()
        times.append((time.perf_counter() - start) * 1000)
    return statistics.median(times)
```

**Predict:** (a) Which file is the smallest of the JSON pages, the CSV and the Parquet file, and the Parquet file is about how many times smaller than the CSV: 1.5, 4 or 15? (b) The table's `discount_usd` is `DECIMAL(8,2)`. Which type does DuckDB report for it when it reads the CSV back, and which for the Parquet file?

<details>
<summary>Reveal the result</summary>

```console
$ uv run python -m pipeline.formats formats
format          bytes  read ms
json pages    874,526     31.6
csv           274,462     40.6
parquet        62,362      1.4
csv gives back: [('discount_usd', 'DOUBLE'), ('ordered_at', 'TIMESTAMP')]

```

Your times will differ.

</details>

*Why:* Parquet is the smallest: 62,362 bytes, 4.4 times smaller than the CSV and 14 times smaller than the JSON pages (which also hold the repeated record and every field name on every record). The CSV came back with `discount_usd` as `DOUBLE`, a type DuckDB guessed from the text and not the one you chose, and the Parquet file came back `DECIMAL(8,2)`. The query read in 1.4 ms from Parquet and 40.6 ms from CSV on this run, a ratio of 29; on three runs here it was 29, 29 and 32. The run cannot say how much of that is the column layout and how much is the CSV's type guessing and text parsing, so do not carry the ratio to other data: Exercise 3 shows why.

### 2. Partitions: files split by the value of a column

**Idea.** A **partition** is one slice of a table kept in its own folder, named after the value of a column, such as `part=2026-05-01/`. DuckDB writes this layout with `PARTITION_BY` in `COPY`, and its Hive-partitioning page says that a filter on the partition column is pushed down so that files that are not needed are not read. `PARTITION_BY` takes column names, not expressions, so the script first computes the month as a column called `part`.

**Try it.** `uv run python -m pipeline.formats month` writes the lines unsplit and split by month, and runs a query for May only. The last column is the plan's line `Scanning Files: a/b`.

**Predict:** For the May query, how many of the 6 monthly files does DuckDB open? And is the monthly layout faster for it than the single file?

<details>
<summary>Reveal the result</summary>

```console
$ uv run python -m pipeline.formats month
partitioned by   files    bytes  all ms  May ms  May files
nothing              1   62,362     1.7     2.1        n/a
month                6   78,384     2.3     2.0        1/6
```

</details>

*Why:* the plan opened 1 of 6 files, so the partitioning did its job, yet the May query took 2.0 ms against 2.1 ms on the single file: no gain, and the 6 files hold 78,384 bytes against 62,362, a quarter more. Partitioning saves work when a file is large. The DuckDB page recommends at least 100 MB of data per partition, and this whole table is 62 KB.

### 3. The small-files trap

**Idea.** Every file costs something to open, and each Parquet file has its own metadata at its end. A partition key with many values turns one table into many tiny files, and the costs add up faster than the savings.

**Try it.** `uv run python -m pipeline.formats day` adds a third layout: one folder for each day, 181 days.

**Predict:** With a file for each day, how many files are there, and are their bytes in total about the same as the single file's, about twice or about eight times as many?

<details>
<summary>Reveal the result</summary>

```console
$ uv run python -m pipeline.formats day
partitioned by   files    bytes  all ms  May ms  May files
nothing              1   62,362     1.9     2.1        n/a
month                6   78,384     2.3     2.0        1/6
day                181  485,976    14.9     8.9     31/181
```

</details>

*Why:* 181 files hold 485,976 bytes, 7.8 times the single file, because each day holds only about 18 lines and each file carries its own metadata. Reading everything took 14.9 ms against 1.9, and the May query opened 31 of 181 files and took 8.9 ms, four times slower than the same question on the single file, although it read less of the data. The DuckDB page warns that it can be very expensive to write a larger number of partitions, as many files are created.

<Aside type="tip" title="Remember">

- JSON and CSV are text; CSV has no types, and the reader guesses them. Parquet is column-oriented, and a query reads only the columns it needs.
- A partition is a folder for each value of a column; a filter on that column lets the reader skip folders.
- Partition when files are large, and by a column with few values that queries filter on.
- A measured ratio belongs to the size and the machine it was measured on.

**Common trap:** partitioning small data. More files, more bytes and slower reads, for a saving that needs far more data.

</Aside>

**Spot the flaw.** A colleague runs the benchmark below, sees `22 times`, and writes in the pipeline notes: "Parquet is 22 times faster than CSV, so the full-year file of 100 times more lines will also read 22 times faster." Save it as `exercises/de03_ex3.py`, run it with `COPIES = 1`, then change the constant to `100` and run it again. Expected: one line each time. What is wrong with the note?

```python
import tempfile
from pathlib import Path

import duckdb

from pipeline.config import STAGING_DIR
from pipeline.formats import median_ms

COPIES = 1  # the lines repeated this many times; run it again with 100
LINES = STAGING_DIR / "order_lines.parquet"
QUERY = "SELECT store_id, sum(quantity) FROM {} GROUP BY store_id"
con = duckdb.connect()
with tempfile.TemporaryDirectory() as scratch:
    csv, parquet = Path(scratch) / "lines.csv", Path(scratch) / "lines.parquet"
    repeated = f"(SELECT l.* FROM '{LINES}' l, range({COPIES}))"
    con.execute(f"COPY (SELECT * FROM {repeated}) TO '{csv}' (FORMAT csv, HEADER)")
    con.execute(f"COPY (SELECT * FROM {repeated}) TO '{parquet}' (FORMAT parquet)")
    csv_ms = median_ms(con, QUERY.format(f"read_csv('{csv}')"))
    parquet_ms = median_ms(con, QUERY.format(f"read_parquet('{parquet}')"))
    print(f"{COPIES} copies: csv {csv_ms:.1f} ms, parquet {parquet_ms:.1f} ms, {csv_ms / parquet_ms:.0f} times")
```
