## The question

The owner writes:

> Every morning someone runs the pipeline by hand, and last Tuesday nobody did. Can it run itself, and tell us when it cannot?

The pipeline you have is a set of functions. A schedule needs three more things: which steps run in which order, which day a run is about, and what happens when a step fails. By the end you can say all three in one Airflow file and read the result.

<Aside type="note" title="You already know this">

**Match.** *Quality gates: stop a run or quarantine a line* (DE6b) decided what a bad line does to a run. Airflow decides what a failed step does to the day.

**Diverge.** Until now you started every run and watched it. A scheduler starts it when you are not there, so everything you would have seen must be in a log you can read later.

</Aside>

## The big idea

An orchestrator runs your functions in order, on a schedule, retries the ones that fail, and keeps a log of each try; the work stays in your code.

### 1. A DAG: tasks and arrows

**Idea.** A **DAG** (directed acyclic graph) is a Python file that names tasks and the arrows between them. The Dags page says that declaring the dependencies between tasks is what makes up the Dag structure. Airflow reads the file; it runs each task when the tasks before it have succeeded. Keep the work out of the file: the Airflow best-practices page says top-level code should not do database access, heavy computation or networking. The work is in `src/pipeline/daily.py`, three steps that take one day, each of which you can test and run without Airflow.

**Try it.** `daily.py` and the new `merge` of `load.py` are given files; the DAG is yours to save. Fetch the two, and read the heart of the first:

```bash
git show de-07-done:src/pipeline/daily.py > src/pipeline/daily.py
git show de-07-done:src/pipeline/load.py > src/pipeline/load.py
git show de-07-done:tests/test_daily.py > tests/test_daily.py
```

```python
def window(day):
    """The API's since and until for the lines updated during one day. since is exclusive and until is inclusive, so both stop one second early."""
    start = datetime.combine(day, datetime.min.time())
    return [(moment - timedelta(seconds=1)).strftime("%Y-%m-%d %H:%M:%S") for moment in (start, start + timedelta(days=1))]
```

```python
def run_step(step, day):
    """Run one step for one day. This is the only place the DAG file has to know about."""
    if step == "extract":
        return extract(day)
    con = load.connect()
    try:
        {"check": check, "publish": publish}[step](day, con)
    finally:
        con.close()
```

`extract` lands the day's pages, `check` stages them and passes them through the gate of DE6b, and `publish` merges the clean lines. `load.py` now keeps the merge in a function of its own, `merge`, which both the incremental load and `publish` call. Save the DAG as `airflow/dags/cafe_pipeline.py`:

```python
"""The nightly job as a DAG. The order of the steps and the schedule live here; the work lives in pipeline.daily."""

from datetime import datetime, timedelta

from airflow.sdk import CronDataIntervalTimetable, dag, task


def alert(context):
    """Runs when a task has failed for good. A real one would send a message; this one prints the line the message would carry."""
    ti = context["task_instance"]
    print(f"ALERT: {ti.dag_id}.{ti.task_id} failed on try {ti.try_number}, day {context['data_interval_start']:%Y-%m-%d}")


@dag(
    schedule=CronDataIntervalTimetable("0 0 * * *", timezone="UTC"),
    start_date=datetime(2026, 4, 30),
    catchup=False,
    default_args={"retries": 2, "retry_delay": timedelta(seconds=5), "on_failure_callback": alert},
)
def cafe_pipeline():
    @task
    def extract(data_interval_start=None):
        from pipeline import daily

        daily.run_step("extract", data_interval_start.date())

    @task
    def check(data_interval_start=None):
        from pipeline import daily

        daily.run_step("check", data_interval_start.date())

    @task
    def publish(data_interval_start=None):
        from pipeline import daily

        daily.run_step("publish", data_interval_start.date())

    extract() >> check() >> publish()


cafe_pipeline()
```

Run the DAG once for the date May 2, with the mock API running in terminal 1:

```bash
uv run airflow dags test cafe_pipeline 2026-05-02 2>&1 | short
```

*Why:* `publish` inserts one line fewer: the gate of DE6b held the line with the quantity of 20 in quarantine, and the rest of the day loaded. The DAG file imports `pipeline` inside each task, not at the top, so that Airflow can read the file without running anything. The file gives every task the same two settings through `default_args`, which the next unit uses.

### 2. Retries and an alert

**Idea.** A task that raises an error is tried again: `retries` says how many more times and `retry_delay` how long to wait. The Airflow task page names the states: a task that failed but has tries left is `up_for_retry`, and one that has none left is `failed`. An **alert** is a function Airflow calls with the run's context; `on_failure_callback` is called when the task fails. A real alert would send a message, and here it prints the line a message would carry.

**Try it.** Make the API unreachable for one run, by pointing the pipeline at a port where nothing listens (the mock API stays up), and ask for the day after:

```bash
API_URL=http://127.0.0.1:9 uv run airflow dags test cafe_pipeline 2026-05-03 2>&1 | short
```

**Predict:** How many tries does `extract` get, how many times does the alert print, and do `check` and `publish` run?

### 3. The schedule, and the day a run covers

**Idea.** `schedule` says when a run starts, and also what the run is about. `CronDataIntervalTimetable("0 0 * * *")`, which the DAG uses, makes an interval between two triggers and starts the run at its end. The tasks read `data_interval_start` and never the clock; the best-practices page says to read and write a specific partition and not to use `now()` inside a task.

**Try it.** `airflow/examples/de07_bare.py` is the same DAG with the bare cron string and another name. Copy it into the DAGs folder, see how it differs, run it for May 4, and delete it:

```bash

diff dags/cafe_pipeline.py dags/de07_bare.py

*Why:* in Airflow 3 a bare cron string such as `"0 0 * * *"` makes a timetable with no data interval: the Timetables page says `data_interval_start` and `data_interval_end` are the same moment, the time the run is triggered. So the bare string loaded May 4, the day of the trigger, which is a day that has only just begun when a run starts at midnight: a nightly job on that schedule would always load a day that is empty. The first DAG, run for May 2 in unit 1, loaded May 1, the day that had just ended. The date you give `dags test` stands for the moment the run is triggered, and the interval is the one that ends there. A scheduler running the interval timetable starts the run for May 1 just after midnight on May 2. DE8 runs it through the scheduler, and shows that a backfill names its runs the other way.

How Dagster says the same thing: its documentation defines an asset as a logical unit of data such as a table, and says assets can depend on other assets, forming the data lineage. In Dagster you would declare `order_lines` and the marts built from it as assets, and the arrows run between data, not between tasks. Airflow here names the steps; Dagster names what they make. Dagster was not run for this lesson.

<Aside type="tip" title="Remember">

- A DAG file names tasks, arrows, a schedule and retries; the work stays in functions you can test without Airflow.
- A task that fails is tried again `retries` times; the alert runs when it has failed for good.
- A run is about an interval: tasks read `data_interval_start`, never the clock.
- A run for a past day must leave the same table as a run on the day: that is why the steps are idempotent.

**Common trap:** a schedule written as a bare cron string, with a pipeline that assumes the day of the trigger is the day to load.

</Aside>

<details>
<summary>Half-solution</summary>

if try_number < ...:
    raise RuntimeError(...)
```

</details>

<Solution>

```python
from datetime import datetime, timedelta

from airflow.sdk import dag, get_current_context, task


@dag(
    schedule=None,
    start_date=datetime(2026, 5, 1),
    catchup=False,
    default_args={"retries": 2, "retry_delay": timedelta(seconds=2)},
)
def de07_ex2():
    @task
    def flaky():
        try_number = get_current_context()["ti"].try_number
        if try_number < 3:
            raise RuntimeError(f"the source was down on try {try_number}")
        print(f"the source answered on try {try_number}")

    flaky()


de07_ex2()
```

```console
$ uv run airflow dags test de07_ex2 2026-05-02 2>&1 | short
RuntimeError: the source was down on try 1
   task state: up_for_retry
RuntimeError: the source was down on try 2
   task state: up_for_retry
   task state: success
run state: success
```

`retries=2` means two more tries after the first, three in all. A retry heals a fault that goes away, such as a source that was down; it does nothing for a fault in the code, which fails the same way each time and only delays the alert.
