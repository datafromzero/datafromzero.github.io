## The question

The owner of the three cafes asks:

> The report of yesterday's sales is instant, but the same report for the whole spring is slow on the big copy. Does the database use a different method?

The two tables behind the report, with 500,000 orders and 950,414 lines in the big copy (the first lines of each):

| order_id | ordered_at | store_id |
|---:|---|---:|
| 1 | 2026-01-01 00:00:31 | 1 |
| 2 | 2026-01-01 00:01:02 | 1 |

| order_item_id | order_id | product_id | quantity |
|---:|---:|---:|---:|
| 1 | 1 | 2 | 2 |
| 2 | 2 | 1 | 2 |

By the end you can find the method a plan uses, ask for each of the others, and say where a join's row estimate goes wrong.

<Aside type="note" title="You already know this">

**Match.** [*Indexes, honestly*](/data-engineer/indexes-honestly/) (DE21) priced a scan against an index lookup, and [*Inner join*](/sql/inner-join/) (S20) gave the rule for what a join returns.

**Diverge.** The rule says what comes out. It says nothing about how the rows are paired, and that is the part with three methods and different costs.

</Aside>

## The big idea

A join is a way of pairing rows, and the planner picks one of three: loop over one side and look up the other, build a hash table, or merge two sorted lists.

## Learn by doing

About 50 minutes, 3 new ideas: the three methods as plan nodes, the winner as the number of rows changes, and a row estimate at the join node. The lab built in [*Reading the machine: plans and operators*](/data-engineer/query-plans-and-operators/) (DE20) must exist (`psql -d lab`, then `\pset footer off`). Create the two indexes the joins use:

```sql
CREATE INDEX order_items_big_order_idx ON order_items_big (order_id);
CREATE INDEX orders_big_ordered_idx ON orders_big (ordered_at);
ANALYZE order_items_big;
ANALYZE orders_big;
```

### 1. Three methods, three plan nodes

**Idea.** The PostgreSQL documentation describes three join methods. In a **nested loop**, the right relation is scanned once for every row found in the left relation. In a **merge join**, each relation is sorted on the join attributes (by a sort step or by scanning an index in order), then the two are scanned in parallel and matching rows combined. In a **hash join**, the right relation is loaded into a hash table keyed on the join attributes, then the left relation is scanned and each row looks up its matches. The settings `enable_nestloop`, `enable_hashjoin` and `enable_mergejoin` enable or disable each method for the planner; for nested loops the documentation adds that it is impossible to suppress them entirely and that turning the setting off discourages the planner from using one.

**Try it.** The lines of one day, March 1, run with the planner's own choice, then with nested loops off, then with hash joins off as well:

```sql
EXPLAIN (ANALYZE, TIMING OFF)
SELECT count(*), sum(i.quantity)
FROM orders_big o JOIN order_items_big i ON i.order_id = o.order_id
WHERE o.ordered_at >= '2026-03-01' AND o.ordered_at < '2026-03-02';
SET enable_nestloop = off;
-- run the same EXPLAIN again
SET enable_hashjoin = off;
-- and once more
```

**Predict:** Which join method does the first plan use, and which of the three plans finishes first? About how many times faster than the slowest is it?

### 2. The winner follows the number of rows

**Idea.** A nested loop pays for one lookup for each row of its outer side, and a hash join or a merge join pays to read both sides. The same query on more rows can therefore rank the methods differently. The helper `join_report` (given in `setup.sql`) runs a query under `EXPLAIN ANALYZE` and prints one row: its first join node, that node's cost and the run time in ms.

**Try it.** The same query for the week of March 1 to 7, first as the planner would run it, then forcing each method. Run each `join_report` line twice and read the second line (the first run may read pages from disk):

```sql
\set q '$$SELECT count(*), sum(i.quantity) FROM orders_big o JOIN order_items_big i ON i.order_id = o.order_id WHERE o.ordered_at >= ''2026-03-01'' AND o.ordered_at < ''2026-03-08''$$'
SELECT 'default' AS setting, * FROM join_report(:q);
SET enable_hashjoin = off; SET enable_mergejoin = off;
SELECT 'nested loop' AS setting, * FROM join_report(:q);
RESET enable_hashjoin; RESET enable_mergejoin;
SET enable_nestloop = off; SET enable_mergejoin = off;
SELECT 'hash' AS setting, * FROM join_report(:q);
RESET enable_nestloop; RESET enable_mergejoin;
SET enable_nestloop = off; SET enable_hashjoin = off;
SELECT 'merge' AS setting, * FROM join_report(:q);
RESET enable_nestloop; RESET enable_hashjoin;
```

**Predict:** For the week, which method does the planner choose on its own, and which of the three runs fastest?

### 3. A row estimate at the join node

**Idea.** A join's row estimate starts from the sizes of its two inputs. Here the inputs are the big lines table (950,414 rows) and `products` filtered to one product.

**Try it.** The lines of one product, for Latte and for Turkey Sandwich:

```sql
EXPLAIN (ANALYZE, TIMING OFF, SUMMARY OFF)
SELECT p.category, count(*)
FROM order_items_big i JOIN products p ON p.product_id = i.product_id
WHERE p.product_name = 'Latte' GROUP BY p.category;
-- and again with 'Turkey Sandwich'
```

**Predict:** At the join node, is the estimate (`rows=`) above or below the actual rows for Latte, and for Turkey Sandwich?

*Why:* the planner expected 59,401 rows for both products. Latte found 285,307, which is 4.8 times more, and Turkey Sandwich 24,838, which is 2.4 times fewer. The lab's lines are skewed on purpose, a few products sell most of them: Latte (product 3) has 30 percent of the 950,414 lines and Turkey Sandwich 2.6 percent.

A wrong estimate has a price further up. Join `orders_big` to the Latte query, grouped by store, and look at the `Hash` node that holds the Latte lines:

```sql
EXPLAIN (ANALYZE, TIMING OFF, SUMMARY OFF)
SELECT o.store_id, count(*)
FROM order_items_big i
JOIN products p ON p.product_id = i.product_id
JOIN orders_big o ON o.order_id = i.order_id
WHERE p.product_name = 'Latte'
GROUP BY o.store_id;
```

It prints `Buckets: 262144 (originally 65536)  Batches: 2 (originally 1)`. The node began with 65,536 buckets and one batch and grew to 262,144 buckets and two batches, because 285,307 rows did not fit in the working memory (`work_mem`, 4 MB here). In the runs behind this lesson the same query took about 1.5 times longer than with `SET work_mem = '64MB'` (medians 384 ms and 258 ms over seven runs; ranges 287 to 457 and 239 to 306 ms); a single run of yours can show a smaller gap, and one run here gave 1.2 times.

<Aside type="tip" title="Remember">

- A nested loop looks up the inner side once for each outer row, a hash join builds a table from one side, a merge join walks two sorted inputs.
- `enable_nestloop`, `enable_hashjoin` and `enable_mergejoin` ask for another method so you can compare; they do not forbid one.
- The planner ranks plans by cost, a number in its own units; compare the clock too.
- Look for the join node where `rows=` and `actual rows` part.

**Common trap:** trusting the planner's cost as the speed of a plan. The cheapest plan by cost was not the fastest in four of the five windows of this lab.

</Aside>

```console
         ->  Seq Scan on order_items_big i  (cost=0.00..15568.14 rows=950414 width=4) (actual rows=950414 loops=1)
         ->  Hash  (cost=1.20..1.20 rows=7 width=4) (actual rows=7 loops=1)
               Buckets: 1024  Batches: 1  Memory Usage: 9kB
               ->  Seq Scan on products p  (cost=0.00..1.20 rows=7 width=4) (actual rows=7 loops=1)
                     Filter: (category = 'coffee'::text)
                     Rows Removed by Filter: 9
```

The estimate is 415,806, which is 950,414 times 7 / 16, and the join found 673,836, 1.6 times more. The seven coffee products sell 71 percent of the lines in this lab, and the estimate gave them seven sixteenths, 44 percent.

**Spot the flaw.** A colleague reads the plan of unit 3 and says: "The estimate of 59,401 is far from the 285,307 found, so the statistics are stale. Run `ANALYZE` on both tables and the estimate will be right." Run his steps and read the join node again. Expected: one plan. What does his fix change, and what does the result say about the cause?

```sql
ANALYZE order_items_big;
ANALYZE products;
EXPLAIN (ANALYZE, TIMING OFF, SUMMARY OFF)
SELECT p.category, count(*)
FROM order_items_big i JOIN products p ON p.product_id = i.product_id
WHERE p.product_name = 'Latte' GROUP BY p.category;
```

Compare `rows=` at the join with the 59,401 of unit 3. Then look at what the statistics of `order_items_big.product_id` hold.

<details>
<summary>Half-solution</summary>

```sql
SELECT most_common_vals::text, most_common_freqs::text
FROM pg_stats WHERE tablename = 'order_items_big' AND attname = 'product_id';
```

<Solution>

```console
   ->  Hash Join  (cost=1.21..18725.03 rows=59401 width=6) (actual rows=285307 loops=1)
```

The estimate is still 59,401. The statistics were not stale: `pg_stats` already lists product 3 first among the common values of `order_items_big.product_id`, with a frequency near 0.30 (the last digits come from `ANALYZE`'s random sample). The estimate did not use that list. It is 950,414 lines times the 1 product kept, times 1/16:

```console
   ->  Hash Join  (cost=1.21..18725.03 rows=59401 width=6) (actual rows=285307 loops=1)
```

`products.product_id` is unique and the filter is on another column, `product_name`, so the join estimate falls back to one over the 16 distinct product ids, and the product that the filter keeps does not matter: Turkey Sandwich gave the same 59,401, and the coffee filter of Exercise 2 gave 7/16 of the lines for the same reason. The error comes from how a join's estimate is made, not from old numbers, so another `ANALYZE` has nothing to correct. A filter on the key of the lines table (`WHERE i.product_id = 3`) is the form the statistics can answer: it was estimated at about 281,671 rows against the 285,307 found.
