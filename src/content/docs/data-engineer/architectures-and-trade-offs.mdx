## The question

The data engineer's manager asks four questions in one meeting:

> We have a replica, so we are covered if someone deletes the wrong rows, right? Would splitting the orders table by month make the monthly report faster? Why does the warehouse team want a different database for reports? And the interviewer asked me about CAP: what do I say?

By the end you can answer each one with something you ran or a source you can name.

<Aside type="note" title="You already know this">

**Match.** In *WAL and recovery: the contract* the server replayed its own log after a crash, and in *File formats and partitioning* (DE3) a query skipped the files of the stores it did not need.

**Diverge.** Here a second server replays the first server's log, and a PostgreSQL table, not a folder of files, is cut into pieces.

</Aside>

## The big idea

Every way of spreading data over more copies or more pieces buys one thing and pays with another, and the plan or the log shows which.

## Learn by doing

About 30 minutes, 4 new ideas: a replica, partitions, two shapes of work, and two interview ideas. Unit 1 uses the throwaway server of the previous lesson; units 2 and 3 run in `psql -d lab` (with `\pset footer off`).

### 1. A second server from the log

**Idea.** The PostgreSQL documentation says standby servers can be kept current by reading a stream of WAL records, and that this can only be done for the entire database server. `pg_basebackup` copies a running server, and with `-R` it writes the settings that make the copy a standby that follows the original. A **hot standby** answers read-only queries. A **backup** is different: the documentation describes `pg_dump` as writing SQL commands that recreate the database in the state it had at the time of the dump.

**Try it.** In the folder of the previous lesson (it must also hold `lab/cafe/orders.csv` from the first lesson of this module), start the throwaway server, give it the cafe orders, take a dump, and start a replica on port 5434:

```bash
pg_ctl -D crashlab -o "-p 5433" -l crashlab.log start
psql -p 5433 -d postgres -c "CREATE TABLE orders (order_id integer PRIMARY KEY, customer_id integer, store_id integer, ordered_at timestamp, status text, payment_method text);"
psql -p 5433 -d postgres -c "\copy orders FROM 'lab/cafe/orders.csv' CSV HEADER"
pg_dump -p 5433 -d postgres -t orders -f orders_backup.sql
pg_basebackup -p 5433 -D replica -R
pg_ctl -D replica -o "-p 5434" -l replica.log start
```

The first line prints `server started`; the run of the other lines printed:

```console
$ psql -p 5433 -d postgres -c "CREATE TABLE orders (order_id integer PRIMARY KEY, customer_id integer, store_id integer, ordered_at timestamp, status text, payment_method text);"
CREATE TABLE
$ psql -p 5433 -d postgres -c "\copy orders FROM 'lab/cafe/orders.csv' CSV HEADER"
COPY 1800
$ pg_dump -p 5433 -d postgres -t orders -f orders_backup.sql
$ pg_basebackup -p 5433 -D replica -R
$ pg_ctl -D replica -o "-p 5434" -l replica.log start
waiting for server to start.... done
server started
```

Now count Harbor's orders on the replica, delete them by mistake on the primary, wait a second, count again on the replica, and try to delete on the replica:

```bash
psql -p 5434 -d postgres -c "SELECT count(*) FROM orders WHERE store_id = 3;"
psql -p 5433 -d postgres -c "DELETE FROM orders WHERE store_id = 3;"
psql -p 5434 -d postgres -c "SELECT count(*) FROM orders WHERE store_id = 3;"
psql -p 5434 -d postgres -c "DELETE FROM orders WHERE store_id = 1;"
```

**Predict:** What is the replica's second count? What does the `DELETE` on the replica print?

<details>
<summary>Reveal the result</summary>

```console
$ psql -p 5434 -d postgres -c "SELECT count(*) FROM orders WHERE store_id = 3;"

-------
   355
(1 row)
$ psql -p 5433 -d postgres -c "DELETE FROM orders WHERE store_id = 3;"

$ psql -p 5434 -d postgres -c "SELECT count(*) FROM orders WHERE store_id = 3;"
```

*Why:* the replica replayed the primary's WAL, and the mistaken `DELETE` was in it, so the replica lost Harbor's orders within a second, as faithfully as it copies good work. It refuses writes of its own, because a hot standby runs read-only queries. A replica protects against losing a server; it does nothing against a wrong statement. That is the job of a backup, a copy of a past moment: Exercise 1 uses the dump.

### 2. Partitions the planner can skip

**Idea.** A partitioned table is one name over several tables, its **partitions**, each holding a range of a key column. The documentation calls **partition pruning** the planner's proof, from each partition's definition, that a partition cannot contain any row that meets the `WHERE` clause; such partitions are left out of the plan.

**Try it.** Partition the 1,800 cafe orders by month of `ordered_at`. The second statement writes one `CREATE TABLE` for each month, and `\gexec` runs each line of its result as a statement:

```sql
CREATE TABLE orders_part (LIKE orders) PARTITION BY RANGE (ordered_at);
SELECT format('CREATE TABLE orders_part_%s PARTITION OF orders_part FOR VALUES FROM (%L) TO (%L)',
              to_char(m, 'MM'), m, m + interval '1 month')
FROM generate_series(timestamp '2026-01-01', timestamp '2026-06-01', interval '1 month') AS m \gexec
INSERT INTO orders_part SELECT * FROM orders;
ANALYZE orders_part;
```

### 3. Two shapes of work

**Idea.** A till writes and reads single orders by their key, thousands of times a day: many small statements, each touching a few rows. This shape is called **OLTP** (online transaction processing). A report reads many rows, often only a few columns, and returns a short summary: few statements, each touching much of the table. This is **OLAP** (online analytical processing).

**Try it.** Read how many rows each of two typical statements touches:

```sql
EXPLAIN (ANALYZE, COSTS OFF, TIMING OFF, SUMMARY OFF)
SELECT status FROM orders WHERE order_id = 1580;
EXPLAIN (ANALYZE, COSTS OFF, TIMING OFF, SUMMARY OFF)
SELECT store_id, count(*) FROM orders GROUP BY store_id;
```

**Predict:** How many rows does each scan read, and how many rows come out at the top?

<details>
<summary>Reveal the result</summary>

```console
A> EXPLAIN (ANALYZE, COSTS OFF, TIMING OFF, SUMMARY OFF)
SELECT status FROM orders WHERE order_id = 1580;
                           QUERY PLAN
----------------------------------------------------------------
 Index Scan using orders_pkey on orders (actual rows=1 loops=1)
   Index Cond: (order_id = 1580)
A> EXPLAIN (ANALYZE, COSTS OFF, TIMING OFF, SUMMARY OFF)
SELECT store_id, count(*) FROM orders GROUP BY store_id;
                     QUERY PLAN
-----------------------------------------------------
 HashAggregate (actual rows=3 loops=1)
   Group Key: store_id
   Batches: 1  Memory Usage: 24kB
   ->  Seq Scan on orders (actual rows=1800 loops=1)
```

</details>

*Why:* the till's lookup went through the index and read 1 row to return 1; the report read all 1,800 to return 3. Indexes, row storage and small transactions serve the first shape; column storage and scans serve the second, as *Storage shapes: rows, columns and files* measured. That is why teams copy the sales from the OLTP database into a separate analytical one: neither layout serves both shapes well, and the reports should not slow the tills.

### 4. Interview depth: CAP and sharding

This unit is the vocabulary interviewers ask for. You will rarely set these trade-offs yourself on a managed warehouse, but you should be able to explain them.

**Idea.** Kleppmann describes a **network partition** as a fault that splits the network into groups of nodes that cannot communicate. Gilbert and Lynch state the **CAP theorem** as: in a network subject to communication failures, it is impossible for any web service to implement an atomic read/write shared memory that guarantees a response to every request. **C** is consistency (every response is correct, as if there were one copy), **A** is availability (every request eventually gets a response), and **P** is the partition.

**Predict:** Imagine that the replica of unit 1 sits in another city, and the network between the two servers breaks. A manager asks the replica for Harbor's orders. What are the replica's two possible behaviors?

<details>
<summary>Reveal the answer</summary>

Answer with the data it has, which may be missing the latest changes (available, not consistent), or refuse or wait until the network is back (consistent, not available).

</details>

*Why:* Gilbert and Lynch draw the practical consequence: since both cannot be guaranteed in an unreliable system, a system must give up one of them during a partition, and systems differ in which. **Sharding** is the related idea of splitting the rows of one table across servers by a key. The PostgreSQL documentation describes it as data partitioning, where each set of data can be modified by only one server, for example one server per office. Read it like unit 2: a query that names the key goes to one server, a query that does not must ask them all.

<Aside type="tip" title="Remember">

- A replica replays the primary's WAL, mistakes included: it protects against losing a server, not against a wrong statement. A backup is a copy of a past moment.
- Partition pruning leaves out the partitions whose bounds cannot match the `WHERE` clause; a filter that says nothing about the key scans every partition.
- OLTP: many small statements, few rows each, by key. OLAP: few statements, many rows each, few columns.
- (Interview depth.) CAP: during a network partition, a system chooses between answering every request and answering only with correct data. Sharding splits rows across servers by a key.

**Common trap:** "we have a replica, so we have a backup." The replica deleted Harbor's orders a second after the primary did.

</Aside>

```console
               Filter: (date_trunc('month'::text, ordered_at) = '2026-03-01 00:00:00'::timestamp without time zone)
         ->  Seq Scan on orders_part_06 orders_part_6
               Filter: (date_trunc('month'::text, ordered_at) = '2026-03-01 00:00:00'::timestamp without time zone)
```

All six partitions are scanned. The query returns the same count as unit 2's March query, but the planner could not prove from the partitions' bounds that `date_trunc('month', ordered_at)` misses them, so it pruned nothing. Write the filter on the key itself, as a range: `ordered_at >= '2026-03-01' AND ordered_at < '2026-04-01'`. On a table of millions of rows, the readable version reads six months to report one.
