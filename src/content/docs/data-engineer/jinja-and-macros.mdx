## The question

The owner of the cafes writes:

> Every new report copies the formula for the amount of a line, and one day someone will change it in one place and forget the other. Can the rule be written once, and can I still read the SQL that runs?

A dbt model is a text file, so dbt can write parts of it for you before it runs. By the end you can make a loop write the columns of a model, put a shared rule in one macro, and read what dbt actually sent to the database.

<Aside type="note" title="You already know this">

**Match.** [*Readable queries with CTEs*](/sql/ctes/) (S24) gave a piece of a query a name inside one query, so that you could read it and use it more than once. A macro gives a piece of text a name for the whole project.

**Diverge.** A common table expression is SQL, and the database runs it. A macro is Jinja, and dbt runs it first.

</Aside>

## The big idea

dbt writes your SQL before it runs it: Jinja is the text that writes the text.

### 1. A list and a loop

**Idea.** dbt runs Jinja on a model before the database sees it. The dbt documentation says an expression in `{{ }}` prints a value, and a statement in `{% %}` prints nothing: it sets a variable, or repeats text in a loop. `{% set statuses = [...] %}` makes a list, and `{% for status_name in statuses %}` repeats everything up to `{% endfor %}` once for each item. The page recommends setting a variable at the top of a model.

**Try it.** Save the net amount of each store, with one column for each status in the list, as `dbt/models/marts/fct_store_status_amounts.sql`:

```sql
{% set statuses = ['completed', 'canceled'] %}
-- Grain: one row for each store. One column of net amount for each status in the list above.
select
    store_id,
{% for status_name in statuses %}
    sum(line_amount_usd) filter (where status = '{{ status_name }}') as {{ status_name }}_usd{{ "," if not loop.last }}
{% endfor %}
from {{ ref('int_order_lines_priced') }}
group by store_id
```

```bash
uv run dbt show --quiet --select fct_store_status_amounts
```

**Predict:** What will `canceled_usd` show for each of the three stores?

<details>
<summary>Reveal the result</summary>

```console
$ uv run dbt show --quiet --select fct_store_status_amounts
| store_id | completed_usd | canceled_usd |
| -------- | ------------- | ------------ |
|        1 |      8,996.75 |              |
|        2 |      9,017.75 |            5 |
|        3 |      4,611.25 |              |
```

</details>

*Why:* the sum of no rows is empty (`NULL`), and the data has one canceled line, in store 2, for \$5.00. The loop ran twice and wrote one column each time; `{{ "," if not loop.last }}` prints a comma after every column but the last, which is what keeps the generated list valid. Build the model and open what dbt wrote:

```bash
uv run dbt build --select fct_store_status_amounts 2>&1 | grep -E "Done"
cat -s target/compiled/cafe/models/marts/fct_store_status_amounts.sql
```

```console
$ uv run dbt build --select fct_store_status_amounts 2>&1 | grep -E "Done"
20:07:47  Done. PASS=1 WARN=0 ERROR=0 SKIP=0 NO-OP=0 REUSED=0 TOTAL=1
```

```console
$ cat -s target/compiled/cafe/models/marts/fct_store_status_amounts.sql

-- Grain: one row for each store. One column of net amount for each status in the list above.
select
    store_id,

    sum(line_amount_usd) filter (where status = 'completed') as completed_usd,

    sum(line_amount_usd) filter (where status = 'canceled') as canceled_usd

from "analytics"."main"."int_order_lines_priced"
group by store_id
```

The compiled file is plain SQL: no braces, one `sum` for each item, the `ref` replaced by the table's full name, and blank lines where the Jinja statements were.

### 2. A macro: one rule, called from several models

**Idea.** A **macro** is Jinja saved in the `macros` folder with a name and arguments, the way a function is. The dbt documentation says macros are pieces of code that can be reused many times, and you call one inside `{{ }}`; the text it returns replaces the call. Use one for a rule that must be the same in several models. The rule here is the one of DE9: the amount of a line is units times price, minus the discount.

**Try it.** First note what the incremental table holds now. Then save the macro as `dbt/macros/line_amount.sql`:

```sql
{% macro line_amount(units, unit_price, discount) %}
    ({{ units }} * {{ unit_price }} - {{ discount }})
{% endmacro %}
```

In `int_order_lines_priced.sql`, replace the expression `l.units * p.unit_price_usd - l.discount_usd` by `{{ line_amount('l.units', 'p.unit_price_usd', 'l.discount_usd') }}`. Save a second model that uses the same call, as `dbt/models/marts/fct_store_discounts.sql`:

```sql
-- Grain: one row for each store. The list amount, the discounts and the net amount of the completed lines.
select
    l.store_id,
    sum(l.units * p.unit_price_usd) as list_usd,
    sum(l.discount_usd) as discount_usd,
    sum({{ line_amount('l.units', 'p.unit_price_usd', 'l.discount_usd') }}) as net_usd
from {{ ref('stg_order_lines') }} as l
join {{ ref('stg_products') }} as p using (product_id)
where l.status = 'completed'
group by l.store_id
```

```bash
uv run dbt show --quiet --inline "select count(*) as lines, sum(line_amount_usd) as amount from {{ ref('int_order_lines_priced') }}"
```

```console
$ uv run dbt show --quiet --inline "select count(*) as lines, sum(line_amount_usd) as amount from {{ ref('int_order_lines_priced') }}"
| lines |    amount |
| ----- | --------- |
|  3287 | 22,630.75 |
```

**Predict:** What text does dbt leave in the compiled `int_order_lines_priced` in place of the macro call, and will the line count or the total of the table change after the build?

### 3. Read the compiled SQL

**Idea.** The database never sees your Jinja: dbt sends it the compiled text, and keeps a copy in `target/compiled/`. The dbt documentation says to run `dbt compile` and open the file there to see what a model turns into. When a model that uses Jinja fails or gives an odd result, that file is where you look.

**Try it.** Call the macro in `fct_store_discounts.sql` with only two arguments, leaving out `'l.discount_usd'`, and build the model:

```bash
uv run dbt build --select fct_store_discounts 2>&1 | grep -E "Parser Error|LINE|compiled|Done"
grep -B2 -A1 "unit_price_usd - )" target/compiled/cafe/models/marts/fct_store_discounts.sql
```

**Predict:** Which line does the error name, and what does the compiled file show there?

<details>
<summary>Reveal the result</summary>

```console
$ uv run dbt build --select fct_store_discounts 2>&1 | grep -E "Parser Error|LINE|compiled|Done"
  Parser Error: syntax error at or near ")"
  LINE 16:     (l.units * p.unit_price_usd - )
20:08:08    compiled code at target/compiled/cafe/models/marts/fct_store_discounts.sql
20:08:08  Done. PASS=0 WARN=0 ERROR=1 SKIP=2 NO-OP=0 REUSED=0 TOTAL=3
```

```console
$ grep -B2 -A1 "unit_price_usd - )" target/compiled/cafe/models/marts/fct_store_discounts.sql
    sum(l.discount_usd) as discount_usd,
    sum(
    (l.units * p.unit_price_usd - )
) as net_usd
```

</details>

*Why:* an argument that is not passed has no value, and Jinja prints nothing for a name without one, like the undefined name in the quoting tip of the dbt page. The database then received `(l.units * p.unit_price_usd - )`, and the error names a line of the compiled file, not of your model. Put the third argument back and build again; it passes.

When is a macro worth it? The dbt page warns that Jinja can make a model harder for others to read, and advises favoring readability even when that means repeating some lines of SQL. A macro earns its place when the same rule appears in several models and has to change in all of them together, as `line_amount` does. The list of statuses of unit 1 is used once, and a macro around it would only hide it.

<Aside type="tip" title="Remember">

- `{{ }}` prints a value and `{% %}` does something and prints nothing; dbt runs both before the database sees the model.
- A loop writes the same text once for each item of a list; the last pass needs no comma.
- A macro is a named piece of text with arguments, and its call is replaced by what it returns; write one when several models share a rule that must change together.
- When a model that uses Jinja fails or surprises, read the file in `target/compiled/`.

**Common trap:** a change to a macro reaches every model that calls it, and an incremental table does not recompute its old rows, so refresh the table when the meaning changed.

</Aside>

<details>
<summary>Hint</summary>

The missing line is a `count(*)` with the same `filter` as the line above it, named `{{ status_name }}_lines`. The comma now belongs after the last expression of each pass, not after the first.

</details>

<details>
<summary>Half-solution</summary>

```sql
    count(*) filter (where status = '{{ status_name }}') as {{ status_name }}_lines...
```

</details>

<Solution>

```sql
{% set statuses = ['completed', 'canceled'] %}
select
    store_id,
{% for status_name in statuses %}
    sum(line_amount_usd) filter (where status = '{{ status_name }}') as {{ status_name }}_usd,
    count(*) filter (where status = '{{ status_name }}') as {{ status_name }}_lines{{ "," if not loop.last }}
{% endfor %}
from {{ ref('int_order_lines_priced') }}

```

```console
$ uv run dbt show --quiet --select scratch_status_counts
| store_id | completed_usd | completed_lines | canceled_usd | canceled_lines |
| -------- | ------------- | --------------- | ------------ | -------------- |
|        1 |      8,996.75 |            1337 |              |              0 |
|        2 |      9,017.75 |            1304 |            5 |              1 |
|        3 |      4,611.25 |             645 |              |              0 |
```

The first expression of a pass is always followed by a comma, so the test for the last pass moves to the second. A sum of no rows is empty and a count of no rows is 0: the stores without canceled lines show an empty `canceled_usd` and a `canceled_lines` of 0.

</Solution>

## On your own

<Exercise id="data-engineer-jinja-and-macros-2">

**A macro of your own.** Before you start, say in a sentence what the result will look like for the three stores. Then, from blank files, write a macro `share(part, whole)` in `dbt/macros/share.sql` that gives the sum of one column as a percentage of the sum of another, rounded to one decimal, and a model `dbt/models/marts/scratch_discount_share.sql` that uses it to show each store's discounts in `fct_store_discounts` as a share of its list amount. Expected: 3 rows, 2 columns. When you are done, delete both files.

<details>
<summary>Hint</summary>

The macro returns one expression: `round(100.0 * sum(...) / sum(...), 1)`, with the two arguments in the places of the columns. The model selects `store_id` and the macro call, from `fct_store_discounts`, grouped by `store_id`.

</details>

<details>
<summary>Half-solution</summary>

Expected output in words: *"Three rows; store 1 gives its discounts as a little under half a percent of its list amount."*

</details>

<Solution>

```sql
{% macro share(part, whole) %}
    round(100.0 * sum({{ part }}) / sum({{ whole }}), 1)
{% endmacro %}
```

```sql
select
    store_id,
    {{ share('discount_usd', 'list_usd') }} as discount_pct
from {{ ref('fct_store_discounts') }}
group by store_id
```

```bash
uv run dbt show --quiet --select scratch_discount_share
```

```console
$ uv run dbt show --quiet --select scratch_discount_share
| store_id | discount_pct |
| -------- | ------------ |
|        1 |          0.4 |
|        2 |          0.2 |
|        3 |          0.7 |
```

The macro is one expression, called with column names as text; because the model groups by store, the `sum` inside it adds the one row of each store. A macro this small is at the edge of what unit 3 allows: it names one idea and keeps its rounding in one place, but a reader has to open it to see the formula.

</Solution>

## Check yourself

1. Without looking back: what is the difference between `{{ ... }}` and `{% ... %}` in a model?

   <details>
   <summary>answer</summary>

**Spot the flaw.** A colleague turns the two columns of unit 1 into a macro, so that a model can ask for any status by name. The macro and a model that uses it are saved, the model builds, and the colleague says it works:

</Solution>
