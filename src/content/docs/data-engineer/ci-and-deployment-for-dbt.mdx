## The question

The owner of the cafes writes:

> Last week a change to the product model went live and the store report was wrong for a day. Can something check every change before it reaches the main branch, without touching our real tables?

A person reads the diff of a pull request, and cannot run a build of dozens of steps in their head. By the end you can write the check that runs the build and its tests on every pull request, run it the way GitHub would, and make it build only what a change touches.

<Aside type="note" title="You already know this">

**Match.** [*Git: branches, pull requests and review*](/core/git-branches-and-pull-requests/) (C30) proposed a change on a branch for others to review before it joined the main branch. CI adds a second reviewer that runs the project.

**Diverge.** A reviewer reads what changed. A CI run builds and tests the whole project as the change leaves it, in a place of its own.

</Aside>

## The big idea

A check on a pull request builds the project from nothing in a place of its own, so that a failure is found before the merge and costs no one's data.

### 1. A workflow that builds the project from nothing

**Idea.** The GitHub documentation says a workflow is defined by a YAML file checked in to the repository, in `.github/workflows`. An **event** triggers it, a **job** is a set of steps run on the same **runner**, a server, and a step is a shell script or an action. For the `pull_request` event the default is to run when a pull request is opened, when commits are pushed to it, and when it is reopened. Each workflow run starts in a freshly provisioned machine, so everything the build needs has to be made by the run itself.

**Try it.** Fetch the workflow, the script it calls, the profile with two new targets, and the ignore file of the dbt folder:

```bash
mkdir -p ci .github/workflows
git show de-14-done:.github/workflows/dbt-ci.yml > .github/workflows/dbt-ci.yml
git show de-14-done:ci/dbt_ci.sh > ci/dbt_ci.sh
git show de-14-done:dbt/profiles.yml > dbt/profiles.yml
git show de-14-done:dbt/.gitignore > dbt/.gitignore
```

The workflow, `.github/workflows/dbt-ci.yml`:

```yaml
name: dbt CI

on:
  pull_request:

jobs:
  dbt-build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1 # v7.0.1
      - name: Install uv
        uses: astral-sh/setup-uv@c771a70e6277c0a99b617c7a806ffedaca235ff9 # v9.0.0
        with:
          version: "0.11.32"
          enable-cache: true
      - name: Install the project
        run: uv sync --locked
      - name: Build, snapshot and test every model
        run: bash ci/dbt_ci.sh
```

It checks out the repository, installs uv at a fixed version (the uv guide calls pinning a version best practice, and pins the two actions by commit, as here), installs the locked dependencies, and runs one script. The script, `ci/dbt_ci.sh`, is the part you can run yourself. It starts the mock API if none answers, and these are its first and last lines:

```bash
#!/usr/bin/env bash
set -euo pipefail

export DATA_DIR="$PWD/data/ci"
export STAGING_DIR="$DATA_DIR/staging"
export PARTNER_DIR="$DATA_DIR/partner"
export CI_DB="$DATA_DIR/ci.duckdb"
rm -rf "$DATA_DIR"
mkdir -p "$DATA_DIR"
```

```bash
uv run python -m pipeline.ingest
uv run python -m pipeline.stage

# The snapshot keeps history only from the runs it has seen, so CI shows it the partner's file twice: first, then as it is now.
uv run python scripts/partner_files.py 1
(cd dbt && uv run dbt snapshot --target ci)
uv run python scripts/partner_files.py 3
(cd dbt && uv run dbt build --target ci)
```

Every step of DE2, DE3 and DE13 is in it: land, stage, replay the partner's file, build. Run it, and compare a fingerprint of your own database before and after:

```bash

md5sum data/serving/analytics.duckdb | cut -c1-12
ls data/ci
```

**Predict:** Does this run change `analytics.duckdb`, the database you have been building in, and where does it build?

### 2. Build only what the change touches

**Idea.** The dbt documentation says `state:modified` selects the nodes that are new or changed, by comparing the project with a manifest (the file `target/manifest.json` that a run writes) given with `--state`; a `+` after it adds everything downstream. `--defer`, with `--state`, resolves a `ref` to a model that was not selected by using the other environment's version, when it does not exist in the target database. The dbt page on CI jobs describes the same shape: only the modified assets and their downstream dependencies are built and tested, in a schema of their own for the pull request. Here your full build, `analytics.duckdb`, stands in for production, and the `ci_defer` target attaches it read-only, which the dbt-duckdb README says the `attach` setting of a profile does.

**Try it.** Build, keep the manifest as the state, and change one file, the comment of `stg_stores.sql`:

```bash
cd dbt
uv run dbt build 2>&1 | grep -E "FAIL|SKIP|Done"
mkdir -p prod-state && cp target/manifest.json prod-state/ && ls prod-state
```

Change the first line of `models/staging/stg_stores.sql` to `-- Grain: one row for each store, as the partner file lists it.`, and ask dbt which models that touches:

```bash
uv run dbt ls --quiet --select "state:modified+" --state prod-state --resource-type model
```

**Predict:** Which models does it list?

Build them, and read what the `ci_defer` database holds:


```console
20:10:15  Done. PASS=20 WARN=0 ERROR=0 SKIP=0 NO-OP=0 REUSED=0 TOTAL=20
```

```console
$ uv run python ../scripts/sql.py "SELECT string_agg(table_name, ', ' ORDER BY table_name) AS built FROM information_schema.tables WHERE table_catalog = 'ci_defer'" --db ../data/serving/ci_defer.duckdb

-------------------------------------------------------------
```

*Why:* the edited model is `stg_stores`, and the `+` adds the models after it: `dim_store` and `fct_store_daily_sales`, which read it, and `fct_order_lines`, which reads `dim_store`. The build ran 20 of the 46 nodes, the four models and their tests, and `ci_defer` holds only those four relations: the models they read, such as `dim_product` and the incremental `int_order_lines_priced`, came from `analytics.duckdb` because `--defer` told dbt to read the unchanged models there. Put the comment back before you go on:

```bash

```

The workflow of unit 1 does not use this, on purpose: the machine of GitHub has no production database to defer to, and at this size the full build takes seconds. State and defer pay when the build takes minutes and the production tables live in a warehouse; the commands are the same.

### 3. What a green check proves

**Idea.** A check proves what its commands ran: here, that the project builds and that its tests pass on the data the run was given. Change a model in a way a reviewer could miss, and see whether the check says so.

**Try it.** In `dbt/models/marts/fct_order_lines.sql`, delete the two `and` lines of the join to `dim_product`, the ones that compare `ordered_at` with `valid_from` and `valid_to`, so that it joins on `product_id` alone. Run the script, from the repository root:

```bash
cd ..
bash ci/dbt_ci.sh 2>&1 | grep -E "FAIL|SKIP|Done"; echo "exit status ${PIPESTATUS[0]}"
```

**Predict:** Which tests fail, and what exit status does the script end with?

<details>
<summary>Reveal the result</summary>

```console
$ bash ci/dbt_ci.sh 2>&1 | grep -E "FAIL|SKIP|Done"; echo "exit status ${PIPESTATUS[0]}"
20:10:25  Done. PASS=1 WARN=0 ERROR=0 SKIP=0 NO-OP=0 REUSED=0 TOTAL=1
20:10:29  40 of 46 FAIL 1 assert_the_fact_keeps_every_line ............................... [FAIL 1 in 0.01s]
20:10:29  46 of 46 FAIL 351 unique_fct_order_lines_order_line_id ......................... [FAIL 351 in 0.02s]
20:10:29  Done. PASS=44 WARN=0 ERROR=2 SKIP=0 NO-OP=0 REUSED=0 TOTAL=46
exit status 1
```

</details>

*Why:* a product whose category changed has two rows in `dim_product` (the snapshot saw version 1 and then version 3 of the file), so every line of products 11 and 14 matched both and was counted twice: 351 line keys, the lines of those two products, failed the `unique` test on the key of the fact, and the test that every staged line is in the fact failed on the count. The script stops with status 1 because `set -e` ends it at the first failing command, and a `run` step on a Linux runner uses `bash -e`, as the workflow syntax page lists, so a step like this one stops there. It caught the mistake only because the CI database had history to join: had the script shown the snapshot only version 1 of the file, every product would have had one version and the broken join would have passed. Put the file back and run it once more:

```bash
git show de-13-done:dbt/models/marts/fct_order_lines.sql > dbt/models/marts/fct_order_lines.sql
bash ci/dbt_ci.sh > /dev/null 2>&1; echo "exit status $?"
```

```console
$ bash ci/dbt_ci.sh > /dev/null 2>&1; echo "exit status $?"
exit status 0
```

<Aside type="tip" title="Remember">

- A workflow is a YAML file that an event triggers; a job runs steps on a fresh machine, so the run builds everything it needs, in a database of its own.
- `state:modified+` with `--state` selects what changed and what is after it; `--defer` takes the unchanged models from the other environment.
- A green check proves only what it ran, on the data it was given. Pin the tools of the workflow.

**Common trap:** a check that sees data without the history your tests need can pass a change that is wrong.

</Aside>

## Check yourself

1. Without looking back: what does `--defer` do, and what must you give it besides?

   <details>
   <summary>answer</summary>

   It resolves a `ref` to a model that was not selected by using the other environment's relation, when that model does not exist in the target database. It needs `--state`, the manifest of that other environment.

   </details>

<Exercise id="data-engineer-ci-and-deployment-for-dbt-3">

**Spot the flaw.** A colleague wants the check to build only what a pull request changes. In the CI job they save the manifest as the state after the pull request's own files are in place, and then select the changes: edit `dim_store.sql` as in Exercise 1, run `dbt parse`, copy `target/manifest.json` to `prod-state`, and select `state:modified+`. The job passes. Do the same and read what ran. Expected: the job is green. How many models did it test, and what does the state have to be instead? When you are done, put the line back.

```bash
cd dbt
rm -rf prod-state && mkdir prod-state && uv run dbt parse --quiet && cp target/manifest.json prod-state/ && ls prod-state
uv run dbt ls --quiet --select "state:modified+" --state prod-state --resource-type model | wc -l
uv run dbt build --select "state:modified+" --defer --state prod-state --target ci_defer 2>&1 | grep -E "FAIL|SKIP|Nothing|Done"; echo "exit status ${PIPESTATUS[0]}"
```

<details>
<summary>Hint</summary>

Read the number the second command prints, and the warning of the third.

</details>

<details>
<summary>Half-solution</summary>

`state:modified` compares the project with the manifest. Ask what the manifest was made from, and what it was compared with.

</details>

<Solution>

```console
$ rm -rf prod-state && mkdir prod-state && uv run dbt parse --quiet && cp target/manifest.json prod-state/ && ls prod-state
manifest.json
```

```console
$ uv run dbt ls --quiet --select "state:modified+" --state prod-state --resource-type model | wc -l
0
```

```console
$ uv run dbt build --select "state:modified+" --defer --state prod-state --target ci_defer 2>&1 | grep -E "FAIL|SKIP|Nothing|Done"; echo "exit status ${PIPESTATUS[0]}"
20:11:18  [WARNING]: Nothing to do. Try checking your model configs and model specification args
exit status 0
```

The state was made from the very files it is compared with, so nothing is modified: no model is listed, dbt warns that there is nothing to do, and the command ends with status 0. The job is green and tested nothing. The state has to be the manifest of the code in production, made before the change, like the one you saved in unit 2: from the main branch, not from the pull request's branch. Put the line back, save the state from the unchanged project, edit the line again, and select again:



A check that can select zero nodes and still pass is worth a second look: have the job print how many it selected.

</Solution>
