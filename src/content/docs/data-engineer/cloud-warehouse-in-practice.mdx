## The question

The owner of the cafes writes:

> Finance asks what the sales model costs to run in the cloud, and whether laying the tables out differently would make it cheaper. I have no money to spend on finding out.

By the end you can count what a query is billed for, say what a partition and a cluster change, and write the sentence that answers finance. Every number comes from your laptop; the free BigQuery sandbox is an extra.

<Aside type="note" title="You already know this">

**Match.** [*From a logical model to physical tables*](/data-engineer/logical-to-physical-design/) (DE12) skipped row groups whose smallest and largest value ruled a filter out. A warehouse skips blocks the same way.

**Diverge.** In DuckDB a skipped block saves time. On an on-demand warehouse the reader pays for the bytes it reads, so a skipped block also leaves the bill.

</Aside>

## The big idea

An on-demand warehouse bills for the bytes a query reads, so a table is laid out to let the queries that matter skip blocks, and the cost line says how many.

## Learn by doing

About 31 minutes, 3 new ideas: what a query is billed for, partition and cluster and the order of the cluster columns, and the cost line of a model. Work in `de-pipeline-starter` with the dbt project built (46 nodes) and `data/serving/design.duckdb` of DE12 holding `lines_arrival` and `lines_by_date`, the 986,100 invented lines. To catch up, run `git checkout de-15-start`, then `uv run python scripts/sql.py sql/physical_design.sql` and `sql/layout.sql`. Run commands from the repository root unless a block says `cd dbt`.

### 1. What a query is billed for

**Idea.** The BigQuery cost page says that on-demand queries are billed by the bytes they read; the clustering page says those are the bytes of each column the query references, in the blocks it scans. A column is sized in **logical bytes** by its type: the data types page gives 8 for `INT64` and `DATE`, 16 for `NUMERIC`, and 2 plus the UTF-8 size for `STRING`. The pricing page says charges are rounded up to the nearest MB, with a minimum of 10 MB per table referenced and per query.

**Try it.** A small script is given. It applies the filter the way a zone map does and reports the blocks it reads and the logical bytes of the columns you name in them; it stops if its block count differs from the plan of DuckDB. A block here is one row group of 122,880 rows, the stand-in for a warehouse block. Ask the week of September for two columns on both copies, then for all five on the sorted copy:

```bash
git show de-15-done:scripts/blocks.py > scripts/blocks.py
uv run python scripts/blocks.py lines_arrival store_id,quantity --range order_date 2026-09-01 2026-09-07
uv run python scripts/blocks.py lines_by_date store_id,quantity --range order_date 2026-09-01 2026-09-07
uv run python scripts/blocks.py lines_by_date order_item_id,store_id,status,quantity,order_date --range order_date 2026-09-01 2026-09-07
```

**Predict:** For each of the three commands, what share of the table's bytes does it read? The week holds 23,009 of the 986,100 lines.

<details>
<summary>Reveal the result</summary>

```console
$ uv run python scripts/blocks.py lines_arrival store_id,quantity --range order_date 2026-09-01 2026-09-07
lines_arrival: 9 of 9 blocks read (986,100 rows); engine: 9 of 9
columns store_id,quantity: 15,777,600 bytes read of 15,777,600 (100.0 percent)
```

```console
$ uv run python scripts/blocks.py lines_by_date store_id,quantity --range order_date 2026-09-01 2026-09-07
lines_by_date: 2 of 9 blocks read (245,760 rows); engine: 2 of 9
columns store_id,quantity: 3,932,160 bytes read of 15,777,600 (24.9 percent)
```

```console
$ uv run python scripts/blocks.py lines_by_date order_item_id,store_id,status,quantity,order_date --range order_date 2026-09-01 2026-09-07
lines_by_date: 2 of 9 blocks read (245,760 rows); engine: 2 of 9
columns order_item_id,store_id,status,quantity,order_date: 10,567,606 bytes read of 42,402,000 (24.9 percent)
```

</details>

*Why:* the unsorted copy reads everything; the sorted one reads two blocks, about a quarter, although the week is 2.3 percent of the lines, because a block is read whole and the week sits across the edge of two. Two columns instead of five cut the sorted read from 10,567,606 to 3,932,160 bytes: bytes follow columns as well as blocks. A `LIMIT` is neither lever: the cost page says that on a table that is not clustered it does not reduce the cost. Your last count can differ by a byte: rows of one day and store have no fixed order.

### 2. Partition and cluster

**Idea.** The partitioning page says a partitioned table is divided into segments, and that a filter on the partitioning column lets BigQuery scan the matching partitions and skip the rest, so a dry run can give a cost before the run, an upper bound that the cost page says can exceed the bytes billed. The clustering page says a clustered table sorts its blocks by up to four columns, that a filter or an aggregate on them scans only the relevant blocks, so BigQuery may not estimate its bytes accurately, and that the order of the cluster columns affects performance. A partition is the folder of DE3; a cluster is the sort order of DE12.

**Try it.** Two more copies of the same lines are given: sorted by date and then store, and by store and then date. Ask three filters of each, and keep the first line of each answer:

```bash
git show de-15-done:sql/clustered.sql > sql/clustered.sql
uv run python scripts/sql.py sql/clustered.sql
for table in lines_by_date_store lines_by_store_date; do
  for filter in "--range order_date 2026-09-01 2026-09-07" "--range store_id 3 3" "--range store_id 3 3 --range order_date 2026-09-01 2026-09-07"; do
    uv run python scripts/blocks.py $table quantity $filter | head -1
  done
done
```

The three filters, in order, are the week, store 3, and both.

**Predict:** On each copy, which of the three filters reads the fewest blocks, and which the most?

<details>
<summary>Reveal the result</summary>

```console
$ for table in lines_by_date_store lines_by_store_date; do
  for filter in "--range order_date 2026-09-01 2026-09-07" "--range store_id 3 3" "--range store_id 3 3 --range order_date 2026-09-01 2026-09-07"; do
    uv run python scripts/blocks.py $table quantity $filter | head -1
  done
done
lines_by_date_store: 2 of 9 blocks read (245,760 rows); engine: 2 of 9
lines_by_date_store: 9 of 9 blocks read (986,100 rows); engine: 9 of 9
lines_by_date_store: 2 of 9 blocks read (245,760 rows); engine: 2 of 9
lines_by_store_date: 5 of 9 blocks read (614,400 rows); engine: 5 of 9
lines_by_store_date: 3 of 9 blocks read (248,820 rows); engine: 3 of 9
lines_by_store_date: 2 of 9 blocks read (245,760 rows); engine: 2 of 9
```

</details>

*Why:* the first column of the sort decides. Sorted by date first, a store filter alone reads every block, because every stretch of dates holds every store. Sorted by store first, the week sits in three blocks, and two more blocks hold the end of one store's dates and the start of the next, so their smallest and largest dates reach the week: five blocks. The clustering page gives the same rule with its own example: a table clustered by order date, country and status is optimized for a filter on date and country, and not for one on only country and status.

Now read the pages against this table's size. The clustering page says unpartitioned tables over 64 MB are likely to benefit and smaller ones usually gain little; the 986,100 lines are 42,402,000 logical bytes, so a warehouse would show little gain here, and DuckDB's blocks are not BigQuery's. The layout below is for a table that has grown. The file is not run:

```sql
-- BigQuery, for the free sandbox. Not run: no account was used.
-- The shapes follow the Google Cloud pages named in the lesson. Load lines_arrival.parquet first (see the lesson), then:
CREATE TABLE cafe.lines
PARTITION BY DATE_TRUNC(order_date, MONTH)
CLUSTER BY store_id
AS (SELECT * FROM cafe.lines_arrival);
```

To try it in the sandbox, write the lines to a file, load it into a dataset you created (`cafe` here), make the partitioned copy, and compare two dry runs, which report an upper bound on the bytes a query would process without running it (the batch loading and cost pages give both commands). The second should report less: its filter is on the partitioning column. A filter on `store_id` would not show its gain in a dry run; that shows in the bytes billed after the run. The sandbox has 10 GiB of storage and tables expire after 60 days. If the statement is refused, the partitioning page describes **Partition by field** in the Create table form.

```bash
uv run python scripts/sql.py "COPY lines_arrival TO 'data/serving/lines_arrival.parquet' (FORMAT parquet)"
bq load --source_format=PARQUET --autodetect cafe.lines_arrival data/serving/lines_arrival.parquet
bq query --use_legacy_sql=false --dry_run "SELECT store_id, quantity FROM cafe.lines_arrival WHERE order_date BETWEEN DATE '2026-09-01' AND DATE '2026-09-07'"
bq query --use_legacy_sql=false --dry_run "SELECT store_id, quantity FROM cafe.lines WHERE order_date BETWEEN DATE '2026-09-01' AND DATE '2026-09-07'"
```

### 3. The cost line of a model on a warehouse

**Idea.** The dbt page for BigQuery sets partitioning and clustering in a model's config: `partition_by`, `cluster_by`, and optionally `require_partition_filter`, which makes any query on the model fail without a partition filter. It says the `merge` strategy of an incremental model scans all the source tables of the model and the destination, and that `insert_overwrite` replaces whole partitions and needs a `partition_by`. By default both write with a `merge` statement (the page's `copy_partitions` option copies partitions instead), which the DML page lists as DML, and the sandbox page lists DML as unsupported: a model like the DE11 one needs a project with billing enabled (a reading, not a run).

**Try it.** First count what the sales mart reads: five columns of `int_order_lines_priced`, 3,287 lines in `analytics.duckdb`, with the decimal counted as `NUMERIC`, 16 bytes, when it fits (the Parquet page maps decimals to `NUMERIC`, `BIGNUMERIC` or `STRING`):

```bash
uv run python scripts/blocks.py int_order_lines_priced store_id,order_date,status,units,line_amount_usd --db data/serving/analytics.duckdb
```

```console
$ uv run python scripts/blocks.py int_order_lines_priced store_id,order_date,status,units,line_amount_usd --db data/serving/analytics.duckdb
int_order_lines_priced: 1 of 1 blocks read (3,287 rows); engine: 1 of 1
columns store_id,order_date,status,units,line_amount_usd: 167,636 bytes read of 167,636 (100.0 percent)
```

The model of DE11 filtered with `where updated_at >= (select max(updated_at) from {{ this }})`. Ask DuckDB for the last 7 days of the sorted copy with a date typed in, and with that kind of subquery:

```bash
uv run python scripts/row_groups.py "order_date >= DATE '2027-04-19'" lines_by_date
uv run python scripts/row_groups.py "order_date >= (SELECT max(order_date) FROM lines_by_date) - 6" lines_by_date
```

**Predict:** Does DuckDB read more blocks for the subquery than for the date typed in?

<details>
<summary>Reveal the result</summary>

```console
$ uv run python scripts/row_groups.py "order_date >= DATE '2027-04-19'" lines_by_date
lines_by_date      602 rows matched, 1 of 9 row groups scanned
$ uv run python scripts/row_groups.py "order_date >= (SELECT max(order_date) FROM lines_by_date) - 6" lines_by_date
lines_by_date      602 rows matched, 1 of 9 row groups scanned
```

</details>

*Why:* DuckDB computes the subquery first and prunes with its value. The dbt page says BigQuery does not: pruning there works only when partitions are filtered with literal values, and a subquery does not help. This stand-in is kinder than the warehouse, so a model that passes here can read every partition there. The page's remedies are a static list of partitions for `insert_overwrite`, which it calls the fastest and cheapest way to update a table with dbt, and the variable `_dbt_max_partition`. Neither was run.

Now put the answer for finance in the model. The mart reads all of history on every run; the cheaper rewrite is a table partitioned by `order_date` that rebuilds only the days a run changes. The given `schema.yml` already holds this description and its cost line. Fetch it and build:

```yaml
      Cost line: a table, rebuilt in full on every run. It reads every line of int_order_lines_priced
      and writes one row for each store and day. On a warehouse it reads 5 of the 10 columns of that table,
      167,636 bytes for 3,287 lines (BigQuery logical bytes), and is billed at least 10 MB for each of the
      two tables it references, 20 MB in all. Cheaper once history is large: partition by order_date and rebuild only the days a run changes.
```

```bash
git show de-15-done:dbt/models/marts/schema.yml > dbt/models/marts/schema.yml
cd dbt
uv run dbt build 2>&1 | grep -E "FAIL|SKIP|Done"
```

```console
$ uv run dbt build 2>&1 | grep -E "FAIL|SKIP|Done"
21:16:22  Done. PASS=46 WARN=0 ERROR=0 SKIP=0 NO-OP=0 REUSED=0 TOTAL=46
```

The line names no price: a price is a dated row of a pricing page, so look it up on the day you write the line.

<Aside type="tip" title="Remember">

- A warehouse bills the bytes of the columns a query reads, in the blocks it scans, with a minimum of 10 MB for each table referenced.
- A partition is a segment a filter on its column can skip, with an upper-bound estimate before the run; a cluster sorts the blocks inside it, and its gain shows in the bytes billed.
- A stand-in can prune where the warehouse does not: say what was not run.

**Common trap:** adding a `LIMIT` to cut the bill: on a table that is not clustered it does not reduce the bytes read.

</Aside>

<Exercise id="data-engineer-cloud-warehouse-in-practice-3">

**Spot the flaw.** A colleague proposes partitioning the 986,100 lines by day, 2026-01-01 to 2027-04-25. Her note: "A week query reads 7 partitions, 2.3 percent of the bytes, so partitioning by day is the right layout for this table." Check what the partitions would hold: the days, and the fewest, average and most lines for a day; and the logical bytes of all five columns. Expected: two outputs. What is wrong with the note?

```bash
uv run python scripts/sql.py "SELECT count(*) AS days, min(n) AS fewest, round(avg(n)) AS average, max(n) AS most FROM (SELECT order_date, count(*) AS n FROM lines_by_date GROUP BY order_date)"
uv run python scripts/blocks.py lines_by_date order_item_id,store_id,status,quantity,order_date
```

<details>
<summary>Hint</summary>

The 2.3 percent is right. Divide the table's bytes by the number of days, and compare one day with the partition size the partitioning page has in mind.

</details>

<details>
<summary>Half-solution</summary>

Ask how many partitions there would be, and how many bytes each would hold.

</details>

<Solution>

```console
$ uv run python scripts/sql.py "SELECT count(*) AS days, min(n) AS fewest, round(avg(n)) AS average, max(n) AS most FROM (SELECT order_date, count(*) AS n FROM lines_by_date GROUP BY order_date)"
days | fewest | average | most
-----+--------+---------+-----
480  | 8      | 2054.0  | 3287
```

```console
$ uv run python scripts/blocks.py lines_by_date order_item_id,store_id,status,quantity,order_date
lines_by_date: 9 of 9 blocks read (986,100 rows); engine: 9 of 9
columns order_item_id,store_id,status,quantity,order_date: 42,402,000 bytes read of 42,402,000 (100.0 percent)
```

The pruning is real: a week reads 7 of the 480 partitions. The flaw is their size: 42,402,000 bytes over 480 days is about 88,000 bytes a partition, where the partitioning page suggests clustering instead when partitioning leaves under about 10 GB for each, because many small partitions increase the table's metadata. Partitioning pays for a table that has grown; at this size the pages point to clustering by date.

</Solution>

</Exercise>
