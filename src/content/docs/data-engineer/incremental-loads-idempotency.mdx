## The question

The owner asks:

> Why does the pipeline fetch all of January again every night? And when a till corrects a line it has already sent, will my sheet ever show the fix?

A line, as the API sends it (the first line of the first page):

| order_item_id | order_id | ordered_at | quantity | updated_at |
|---:|---:|---|---:|---|
| 5001 | 1001 | 2026-01-01 08:02:00 | 1 | 2026-01-01 08:07:00 |

By the end you can load only what changed, apply a fix to a line you loaded before, and show that running the load again changes nothing.

<Aside type="note" title="You already know this">

**Match.** [*Inserting, updating and deleting safely*](/sql/modify-data-transactions/) (S34) wrapped statements in a transaction so that all of them happen or none.

**Diverge.** In S34 you chose which rows to change. Here the source decides: it sends a line again with a new version, and the load must tell a new line from a changed one.

</Aside>

## Warm-up

   </details>

   <details>
   <summary>answer</summary>

   The path came from the request and the page number, so the second run wrote the same names with the same bytes.

   </details>

## The big idea

A load is safe to repeat when running it again, on the same input or on an overlap, leaves the table exactly as it was.

## Learn by doing

About 30 minutes, 3 new ideas: a watermark, a merge by key, and a fingerprint that proves a rerun. Work in `de-pipeline-starter` with the mock API running (`uv run python mock_api.py`) and the pages of DE2 landed. To catch up, run `git checkout de-04-start`.

### 1. A watermark: ask only for what changed

**Idea.** A **watermark** is the largest `updated_at` you have loaded. The next run asks the API only for versions updated after it (the `since` parameter of the starter's README) and ends by saving the new mark. The API can also answer as of a time (`until`), which lets one dataset play the source on an earlier day.

**Try it.** Save this as `src/pipeline/load.py`; units 2 and 3 read parts of it.

```python
"""Load only the lines that changed since the last run, so that running it again changes nothing."""

import argparse
import logging
from datetime import timedelta

import duckdb

from pipeline.config import RAW_DIR, SERVING_DIR
from pipeline.ingest import land, window_name
from pipeline.stage import staged_lines

log = logging.getLogger("pipeline.load")
DB_PATH = SERVING_DIR / "cafe.duckdb"
LOOKBACK = timedelta(hours=1)  # ask again for the last hour before the watermark; the merge makes that safe
COLUMNS = [
    "order_item_id", "order_id", "ordered_at", "store_id", "customer_id", "status",
    "payment_method", "product_id", "quantity", "discount_usd", "updated_at", "channel",
]


def connect(path=DB_PATH):
    SERVING_DIR.mkdir(parents=True, exist_ok=True)
    con = duckdb.connect(str(path))
    con.execute("""
        CREATE TABLE IF NOT EXISTS order_lines (
            order_item_id BIGINT PRIMARY KEY, order_id BIGINT, ordered_at TIMESTAMP, store_id BIGINT,
            customer_id BIGINT, status VARCHAR, payment_method VARCHAR, product_id BIGINT,
            quantity BIGINT, discount_usd DECIMAL(8, 2), updated_at TIMESTAMP, channel VARCHAR
        )
    """)
    con.execute("CREATE TABLE IF NOT EXISTS load_state (source VARCHAR PRIMARY KEY, watermark TIMESTAMP)")
    return con


def fingerprint(con):
    """Rows, the sum of quantity and a short code that changes when any value of any row changes."""
    return con.execute("""
        SELECT count(*), sum(quantity), left(md5(string_agg(l::VARCHAR, '|' ORDER BY order_item_id)), 8)
        FROM order_lines l
    """).fetchall()[0]


def run(con, until=None, replay=False):
    saved = con.execute("SELECT watermark FROM load_state WHERE source = 'order_lines'").fetchall()
    watermark = None if replay or not saved else saved[0][0]
    since = None if watermark is None else (watermark - LOOKBACK).strftime("%Y-%m-%d %H:%M:%S")
    land(since, until)
    pages = RAW_DIR / "order_lines" / window_name(since, until) / "page-*.json"
    staged_lines(con, str(pages)).create_view("incoming", replace=True)
    new, newer, same = con.execute("""
        SELECT count(*) FILTER (WHERE t.order_item_id IS NULL),
               count(*) FILTER (WHERE t.order_item_id IS NOT NULL AND i.updated_at > t.updated_at),
               count(*) FILTER (WHERE t.order_item_id IS NOT NULL AND i.updated_at <= t.updated_at)
        FROM incoming i LEFT JOIN order_lines t USING (order_item_id)
    """).fetchall()[0]
    assignments = ", ".join(f"{c} = excluded.{c}" for c in COLUMNS[1:])
    con.execute("BEGIN")
    con.execute(f"""
        INSERT INTO order_lines SELECT * FROM incoming
        ON CONFLICT (order_item_id) DO UPDATE SET {assignments}
        WHERE excluded.updated_at > order_lines.updated_at
    """)
    con.execute("""
        INSERT INTO load_state SELECT 'order_lines', max(updated_at) FROM order_lines
        ON CONFLICT (source) DO UPDATE SET watermark = excluded.watermark
    """)
    con.execute("COMMIT")
    log.info("window since=%s: %d inserted, %d updated, %d unchanged", since, new, newer, same)
    rows, quantity, check = fingerprint(con)
    log.info("order_lines now: %d rows, quantity %d, fingerprint %s", rows, quantity, check)


if __name__ == "__main__":
    logging.basicConfig(level=logging.INFO, format="%(levelname)s %(message)s")
    parser = argparse.ArgumentParser(description="Load the order lines that changed since the last run.")
    parser.add_argument("--until", help="ask for the world as of this time, for example '2026-05-02 23:59:59'")
    parser.add_argument("--replay", action="store_true", help="ignore the saved watermark and pull everything again")
    args = parser.parse_args()
    run(connect(), until=args.until, replay=args.replay)
```

### 2. A merge key: insert what is new, update what changed

**Idea.** A **merge key** is a column that identifies a row of the target table; here `order_item_id`, declared `PRIMARY KEY`. An **upsert** inserts a row whose key is new and updates the row whose key exists, in one statement: `INSERT … ON CONFLICT (key) DO UPDATE SET …`. The DuckDB page says that `DO UPDATE` turns the insert into an update of the conflicting row, that the virtual table `EXCLUDED` holds the conflicting values, and that conflicting rows that do not meet the `WHERE` condition are left unchanged: in `load.py`, `excluded.updated_at > order_lines.updated_at` keeps an older version from replacing a newer one. The page also warns that when one `INSERT` holds several rows with the same key, DuckDB applies one update per key and the winner is not guaranteed to be the last, so staging keeps one row for each key before the merge.

**Try it.** The starter has a script that does what the merge does not: a plain `INSERT` of lines that are already loaded. Fetch it from the checkpoint and run it:

```bash

uv run python scripts/naive_append.py
```

It inserts the 3,287 staged lines of the full pull from DE2 into `order_lines`, which already holds them.

**Predict:** Does the plain `INSERT` add rows, add nothing, or stop? How many rows does the table hold afterwards?

rows before 3287, after 3287

</details>

*Why:* the primary key made the database refuse the first key that it already held, and the whole statement was undone: 3,287 rows before and after. The key is what turns a rerun that would have loaded everything twice into an error you can see. The merge is the other answer: it does not refuse, it decides for each key, and an unchanged line stays unchanged.

### 3. A fingerprint: prove that a rerun changes nothing

**Idea.** A step is **idempotent** when running it again on the same input leaves the same result. Do not argue it: compute a **fingerprint** of the table before and after. `fingerprint` in `load.py` is the number of rows, the sum of `quantity` and the first 8 characters of an MD5 code of every row in key order, so a change in any value of any row changes the code.

**Try it.** Run the load again, as it would run the next night, and then replay everything: `--replay` ignores the saved watermark and pulls all 33 pages again.

```bash
uv run python -m pipeline.load
uv run python -m pipeline.load --replay
```

**Predict:** The saved watermark is the last update of June 30. What does the next night's run insert, update and leave unchanged? And does the replay of all 33 pages change the fingerprint of 8c3ca150 that run B left?

The replay pulled all 3,287 lines, found every one unchanged, and left the fingerprint at 8c3ca150, so a run that crashes and starts again from scratch lands the same table.

<Aside type="tip" title="Remember">

- A watermark on `updated_at` asks only for what changed; one on the event time misses a fix.
- A merge key and `ON CONFLICT DO UPDATE` insert new rows, update changed ones and leave the rest; a `WHERE` on the version keeps an old version from winning.
- Staging keeps one row for each key before the merge.
- Prove idempotence with a fingerprint before and after a rerun and after a full replay.

**Common trap:** a watermark on `ordered_at`, the time of the sale. A corrected line keeps its sale time, so no later run asks for it.

</Aside>

<Exercise id="data-engineer-incremental-loads-idempotency-3">

**Spot the flaw.** A colleague writes the two statements of a load in the other order: first save the watermark, then load the lines. They say it is safe, because "if the second statement fails, the run fails, and we run it again". Save the script as `exercises/de04_ex3.py`, run it and read the four lines. Expected: four lines. What is wrong, and what is the fix?

```python
import duckdb

con = duckdb.connect()
con.execute("CREATE TABLE order_lines (order_item_id BIGINT PRIMARY KEY, updated_at TIMESTAMP)")
con.execute("CREATE TABLE load_state (watermark TIMESTAMP)")
con.execute("""
    CREATE TABLE incoming AS
    SELECT * FROM (VALUES (1, TIMESTAMP '2026-05-01 10:00:00'), (2, TIMESTAMP '2026-05-01 11:00:00')) AS t(order_item_id, updated_at)
""")


def flawed_load(crash):
    con.execute("INSERT INTO load_state SELECT max(updated_at) FROM incoming")  # step 1: remember how far we got
    if crash:
        raise RuntimeError("the connection dropped")
    con.execute("INSERT INTO order_lines SELECT * FROM incoming")  # step 2: load the lines


try:
    flawed_load(crash=True)
except RuntimeError as error:
    print("run 1 failed:", error)
watermark = con.execute("SELECT max(watermark) FROM load_state").fetchall()[0][0]
print("watermark:", watermark)
print("lines to ask for next:", con.execute(f"SELECT count(*) FROM incoming WHERE updated_at > TIMESTAMP '{watermark}'").fetchall()[0][0])
print("lines loaded:", con.execute("SELECT count(*) FROM order_lines").fetchall()[0][0])
```

<details>
<summary>Hint</summary>

After the failure, which lines does the next run ask for, and where are the two lines that the failed run was loading?

</details>

<details>
<summary>Half-solution</summary>

```python
con.execute("BEGIN")
...  # the two statements, in the order of load.py
con.execute("COMMIT")
```

</details>

<Solution>

```console
$ uv run python exercises/de04_ex3.py
run 1 failed: the connection dropped
watermark: 2026-05-01 11:00:00
lines to ask for next: 0
lines loaded: 0
```

The watermark moved to 11:00 and the lines did not load, so the next run asks for lines updated after 11:00 and gets none: the two lines are lost, and nobody is told, because the next run succeeds. The statements are separate, and DuckDB commits each one as soon as it succeeds, so the watermark is saved before the load. The fix is the order and the transaction of `load.py`, where the merge and the new watermark sit between `BEGIN` and `COMMIT`: load the lines, save the watermark, and make the two one unit. The DuckDB transactions page says that to make a batch atomic you wrap it in an explicit transaction. If anything fails in between, the rollback leaves the table and the watermark as they were, and the rerun asks for the same lines again.

</Solution>
