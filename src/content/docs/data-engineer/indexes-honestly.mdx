## The big idea

An index is a second, sorted copy of one column, cut into pages that point to the table's rows, and the planner uses it only when its price is lower than reading the table.

## Learn by doing

About 30 minutes, 4 new ideas: an index as pages, the price of a scan against a lookup, a function that hides a column, and what each index costs on writes. The lab of the previous lesson must exist (`psql -d lab`, then `\pset footer off`).

### 1. An index is pages in levels

**Idea.** The PostgreSQL documentation describes its B-tree index as a multi-level tree whose levels are linked lists of pages: one metapage at the start, leaf pages on the lowest level and internal pages above them. Indexes and tables are stored as pages of a fixed size, usually 8 kB. The leaf pages hold the keys in order, each with the location of its table row; an internal page holds a pointer to each page below it, with the first key of that page; the top page is the root. The extension `pageinspect` shows the pages themselves, and the helper `bt_key` (given in `setup.sql`) turns a key into a number.

**Try it.** In `psql`, the index behind the primary key of `orders` (1,800 rows):

```sql
CREATE EXTENSION IF NOT EXISTS pageinspect;
SELECT root, level FROM bt_metap('orders_pkey');
SELECT s.blkno, s.type, s.live_items
FROM generate_series(1, 6) AS b(n), LATERAL bt_page_stats('orders_pkey', b.n) AS s;
```

**Predict:** Which block is the root, how many levels does the index have above its leaves, and how many leaf pages (type `l`) are there?

<details>
<summary>Reveal the result</summary>

```console

------+-------

-------+------+------------

     2 | l    |        367

     4 | l    |        367
     5 | l    |        367
     6 | l    |        336
```

</details>

*Why:* block 3 is the root (`r`) and the index has one level above the leaves, with five leaf pages next to it (block 0 is a page of bookkeeping). The root holds five entries. Walk down by hand to find order 1900: read the root, choose the entry whose first key is the largest one not above 1900, open that leaf, and read the row's location.

```sql
SELECT itemoffset, ctid, bt_key(data) AS first_key FROM bt_page_items('orders_pkey', 3);
SELECT itemoffset, ctid, bt_key(data) AS order_id FROM bt_page_items('orders_pkey', 4) WHERE bt_key(data) = 1900;
SELECT ctid, order_id, ordered_at FROM orders WHERE order_id = 1900;
```

```console

          3 | (4,1) |      1733
          4 | (5,1) |      2099
          5 | (6,1) |      2465

--------+----------+---------------------
```

In the root, `ctid` names the child block (the first entry has no key: it takes everything below 1367). Key 1900 lies between 1733 and 2099, so the walk goes to block 4. There the same column holds a table location: block 7, row 89 of `orders`, which is where the last query finds the order. Three pages (root, leaf, table block) found one row.

### 2. A scan costs pages, a lookup costs a few

**Idea.** The planner prices both ways and takes the cheaper. The PostgreSQL documentation gives the price of a sequential scan as the pages read times `seq_page_cost` plus the rows scanned times `cpu_tuple_cost`, with defaults 1.0 and 0.01, and a filter adds the rows times `cpu_operator_cost` (0.0025). It sets the cost of a non-sequential page fetch, `random_page_cost`, at 4.0 by default. An index lookup pays for a few such fetches, and their number grows only slowly with the size of the table.

**Try it.** A lookup by primary key in four tables of the lab, then the number of pages each table has:

```sql
SELECT relname, relpages, reltuples FROM pg_class
WHERE relname IN ('customers', 'orders', 'order_items', 'orders_big') ORDER BY reltuples;
EXPLAIN SELECT * FROM customers WHERE customer_id = 54;
EXPLAIN SELECT * FROM orders WHERE order_id = 1580;
EXPLAIN SELECT * FROM order_items WHERE order_item_id = 5100;
EXPLAIN SELECT * FROM orders_big WHERE order_id = 123456;
```

**Predict:** Which of the four lookups use the index?

<details>
<summary>Reveal the result</summary>

```console
   relname   | relpages | reltuples
-------------+----------+-----------
 customers   |        1 |       150
 orders      |       16 |      1800
 order_items |       21 |      3287
 orders_big  |     4360 |    500000

                        QUERY PLAN
----------------------------------------------------------
 Seq Scan on customers  (cost=0.00..2.88 rows=1 width=26)
   Filter: (customer_id = 54)

                                QUERY PLAN
---------------------------------------------------------------------------
 Index Scan using orders_pkey on orders  (cost=0.28..8.29 rows=1 width=34)
   Index Cond: (order_id = 1580)

                                     QUERY PLAN
-------------------------------------------------------------------------------------
 Index Scan using order_items_pkey on order_items  (cost=0.28..8.30 rows=1 width=19)
   Index Cond: (order_item_id = 5100)

                                    QUERY PLAN
-----------------------------------------------------------------------------------
 Index Scan using orders_big_pkey on orders_big  (cost=0.42..8.44 rows=1 width=34)
   Index Cond: (order_id = 123456)
```

</details>

*Why:* only `customers` takes a scan, and the formula says why. A scan of `customers` costs 1 page + 150 rows × 0.01 + 150 × 0.0025 = 2.88, below the price of the index plan, which the planner puts at 8.16 for this table. A scan of `orders` would cost 16 + 18 + 4.5 = 38.5, above 8.29. The index price barely moves with size (8.29 for 1,800 rows, 8.44 for 500,000), and the scan price grows with the table: 38.5 for `orders`, 10,610 for `orders_big`. In a sweep of tables cut from `orders_big`, the switch came between 300 and 350 rows (4 pages), as the picture shows.

### 3. A function around a column hides it

**Idea.** An index holds the values of the column it was built on. The PostgreSQL documentation describes an index on an expression such as `lower(col1)` as one that finds rows by a computed value, and notes that index expressions are computed at insert and update time and not for each search.

**Try it.** An ordinary index on `name`, then the slow search, then an index on `lower(name)`, then `ANALYZE` and the same search again:

```sql
CREATE INDEX customers_big_name_idx ON customers_big (name);
EXPLAIN (ANALYZE, TIMING OFF) SELECT * FROM customers_big WHERE lower(name) = 'ana lopez';
CREATE INDEX customers_big_lower_name_idx ON customers_big (lower(name));
EXPLAIN (ANALYZE, TIMING OFF) SELECT * FROM customers_big WHERE lower(name) = 'ana lopez';
ANALYZE customers_big;
EXPLAIN (ANALYZE, TIMING OFF) SELECT * FROM customers_big WHERE lower(name) = 'ana lopez';
```

**Predict:** Does the first plan use the index on `name`? What does the second plan expect for `rows=`, and what does the third expect?

*Why:* the first plan ignores the index on `name`: it holds names as stored, in order, and the filter asks for the lower-cased value of each. Only the index on `lower(name)` can answer it, and it took the search from 36 ms to 0.3 ms here (over nine runs: 38 to 49 ms for the scan and 0.08 to 0.27 ms for the index). The estimate in the second plan, 1,000 rows, is the fixed guess of the previous lesson, 0.5 percent of the 200,000 rows: statistics for the expression did not exist until `ANALYZE` ran, which is why the third plan expects 220. The index on `name` does answer `name = 'Ana Lopez'`, but it finds 156 customers where `lower(name)` finds 220, because 36 are stored as `ANA LOPEZ` and 28 as `ana lopez`.

### 4. Every index is written on every insert

**Idea.** Each index is a separate tree, so a new row must add an entry to every one of them. The documentation calls the write-ahead log (WAL) the record of every change, written before the data files change; the number of bytes it receives measures how much was written.

**Try it.** Insert 200,000 orders into an empty table, with no index, then with one, two and three. Run the script as it is, then remove the two dashes at the start of the first index line and run it again, then of the first two lines, then of all three (`CHECKPOINT` needs a superuser):

```sql
\timing on
DROP TABLE IF EXISTS ins_t;
CREATE TABLE ins_t (LIKE orders_big);
-- ALTER TABLE ins_t ADD PRIMARY KEY (order_id);
-- CREATE INDEX ON ins_t (ordered_at);
-- CREATE INDEX ON ins_t (customer_id);
CHECKPOINT;
SELECT pg_current_wal_lsn() AS before \gset
INSERT INTO ins_t SELECT * FROM orders_big WHERE order_id <= 200000;
SELECT round(pg_wal_lsn_diff(pg_current_wal_lsn(), :'before') / 1e6, 1) AS wal_mb;
```

**Predict:** Compared with the table without indexes, how many times more WAL and how many times more time does the table with all three indexes need: about 1.5, 3 or 6?

<details>
<summary>Reveal the result</summary>

| indexes | WAL written (MB) | INSERT time, five runs (ms) |
|---|---:|---|
| none | 19.2 | 141 to 189 |
| primary key | 32.5 | 285 to 344 |
| and `ordered_at` | 45.8 | 427 to 488 |
| and `customer_id` | 60.9 | 778 to 924 |

</details>

*Why:* the WAL grew 3.2 times (60.9 against 19.2 MB) and the time about 5 times (medians 865 and 170 ms). Each index added about 13 to 15 MB of WAL, and the one on `customer_id` added the most time. A likely reason is that its keys arrive in random order, while `order_id` and `ordered_at` arrive in order and land at the right edge of their trees; this lesson did not test that. The times are medians of five runs on one machine; the WAL bytes were the same in every run. An index is a trade: a search that took 36 ms takes 0.3 ms, and every insert pays a little more.

<Aside type="tip" title="Remember">

- A B-tree index is pages in levels: a root, maybe a middle level, then leaves that point at table rows. A lookup reads one page on each level, then the table page.
- The planner compares prices: a scan pays for every page of the table, a lookup for a few. The switch point depends on the table's size.
- An index serves the expression it was built on; `ANALYZE` after creating one gives the planner statistics for it.
- Each index adds work to every insert and update.

**Common trap:** judging an index on a small table. The planner's price there is right, and the winner changes with size.

</Aside>
