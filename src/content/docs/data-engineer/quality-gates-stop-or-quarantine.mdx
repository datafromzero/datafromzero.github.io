## The question

The owner of the cafes writes:

> The pipeline can now say when the data breaks a rule. What should it do about it: refuse the day, or carry on without the bad part, and how will I know which one happened?

The checks of [*Data quality checks that fail loudly*](/data-engineer/data-quality-checks/) (DE6a) print a report, and a report changes nothing: the load still ran with the bad line in it, or did not run at all. By the end you can decide what each rule does to a run, put that decision in front of the load, and show with counts that no line fell out unseen.

<Aside type="note" title="You already know this">

**Match.** DE6a wrote each rule as a query for the bad lines, and each rule carried an action. Here the load acts on it.

**Diverge.** A report is read afterwards. A gate acts before a single line is written, so what each rule does must be decided before the data arrives.

</Aside>

## The big idea

A gate decides what a failed rule does: a rule that protects the merge stops the run, a rule about one line sets the line aside, and the counts of each run show where every line went.

### 1. Stop or quarantine

**Idea.** A failed rule does one of two kinds of damage. If it protects the merge (a key that is empty or repeated), loading anything is unsafe, so the run **stops**. If it makes one line suspect, the line goes to a **quarantine** table with the name of the rule, and the rest loads. Too many held lines is a signal of its own: above the share the contract allows, the run stops, because that many bad lines point at the rule or the source, not at the lines.

**Try it.** The gate is a given file, `src/pipeline/gate.py`. Fetch it and read its two halves: the first stops the run before anything is written, the second sets lines aside and checks the share:

```bash
git show de-06-done:src/pipeline/gate.py > src/pipeline/gate.py
```

```python
    for name, action, sql in checks:  # stop rules first, before anything is written
        bad = con.execute(f"SELECT count(*) FROM ({sql.format(t='batch')})").fetchall()[0][0]
        if bad and action == "stop":
            raise CheckFailed(f"{name}: {bad} bad lines, the run stops")
```

```python
    clean = con.sql("""
        SELECT b.* FROM batch b
        ANTI JOIN held h ON h.order_item_id = b.order_item_id AND h.updated_at = b.updated_at
    """)
    read = con.execute("SELECT count(*) FROM batch").fetchall()[0][0]
    kept = clean.count("*").fetchall()[0][0]
    if read - kept > contract["max_quarantine_share"] * read:
        raise CheckFailed(f"{read - kept} of {read} lines would be quarantined, over the share the contract allows: look at the rule before the data")
```

The anti join keeps the lines of the batch that have no match in `held`, the table of lines the quarantine rules caught (the DuckDB documentation: an anti join returns the rows of the left table with no match in the right one). The held lines are written to the `quarantine` table only after the share check has passed, so a stopped run leaves nothing behind. The table's key is the rule, the line and its version, and the write is `INSERT ... ON CONFLICT DO NOTHING`: the DuckDB documentation says DO NOTHING ignores the conflict and inserts nothing, so a held line that arrives again is not stored twice.

### 2. Counts that add up

**Idea.** A check can only catch what a run reports. Every run says how many lines it read, passed and held, and how many it inserted, updated and left unchanged. Two sums must hold: lines read equal clean plus held, and clean lines equal inserted plus updated plus unchanged. The failure that must never be silent is a line that was read and is nowhere: not in `order_lines` and not in quarantine.

**Try it.** The tests of the gate are a given file. Fetch it and read its first test, which asserts the log line, as in DE5:

```bash
git show de-06-done:tests/test_gate.py > tests/test_gate.py
```

```python
def test_a_line_with_a_wild_quantity_is_held_back_and_counted(con, caplog):
    with caplog.at_level(logging.INFO, logger="pipeline.gate"):
        clean = gate(con, batch(con, line(1), line(2, quantity=20), line(3, quantity=1), line(4), line(5)))
    assert sorted(key for (key,) in clean.project("order_item_id").fetchall()) == [1, 3, 4, 5]
    assert con.execute("SELECT check_name, order_item_id FROM quarantine").fetchall() == [("quantity_in_range", 2)]
    assert "5 lines read, 4 clean, 1 quarantined" in caplog.text
```

```bash
uv run pytest -q --tb=short
```

**Predict:** DE5 ended with 17 passing tests. How many pass now?

<details>
<summary>Reveal the result</summary>

```console
$ uv run pytest -q --tb=short

```

</details>

*Why:* 17 and the three of the gate. Add up the first run of unit 1 the same way: 1,989 read are 1,988 clean and 1 held, and the 1,988 clean are 1,988 inserted, 0 updated and 0 unchanged. When a sum fails, the data changed, the code lost a line or the rule is wrong, and [*Backfills, reruns and recovering from failure*](/data-engineer/backfills-and-failure-recovery/) (DE8) teaches how to tell which.

<Aside type="tip" title="Remember">

- A rule that protects the merge stops the run; a rule about one line quarantines it; too many held lines stop the run.
- Nothing is written before the stop rules and the share have passed, so a stopped run leaves nothing behind.
- Lines read equal clean plus held, and clean equal inserted plus updated plus unchanged.

**After every load:** read the counts of the run against what you expect before you trust the table.

</Aside>

from pathlib import Path

import duckdb

from pipeline.gate import gate

contract = json.loads(Path("contracts/order_lines.json").read_text())
# Why this action: ...
contract["rules"] = [
    {"name": "store_known", "on_fail": ..., "bad_rows": "SELECT * FROM {t} WHERE ..."}

con = duckdb.connect()
# The batch: the staged lines, with line 5500 sold in store 9.
lines = con.sql("""
    SELECT * REPLACE (CASE WHEN order_item_id = 5500 THEN 9 ELSE store_id END AS store_id)
    FROM read_parquet('data/staging/order_lines.parquet')

import json
import logging
import sys
from pathlib import Path

import duckdb

from pipeline.gate import gate

logging.basicConfig(level=logging.INFO, format="%(levelname)s %(message)s")

N = int(sys.argv[1])  # how many lines the new store sells
contract = json.loads(Path("contracts/order_lines.json").read_text())
contract["rules"] = [
    {
        "name": "store_known",
        "on_fail": "quarantine",
        "bad_rows": "SELECT * FROM {t} WHERE store_id NOT IN (SELECT store_id FROM read_parquet('data/staging/stores.parquet'))",

lines = con.sql(f"""
    SELECT * REPLACE (CASE WHEN order_item_id IN (

## Check yourself

1. Without looking back: what do a failed `stop` rule and a failed `quarantine` rule each do to the rest of the batch?

   <details>
   <summary>answer</summary>

   A stop rule loads nothing from the batch and raises. A quarantine rule holds only its own lines, and the rest of the batch loads.

<Exercise id="data-engineer-quality-gates-stop-or-quarantine-3">

**Spot the flaw.** A colleague wraps the gate for the nightly job. If a stop rule fails, the script prints a warning and skips the night, "so the check is loud". Tonight's batch lost the key of line 5500. Save the script as `exercises/de06b_ex3.py`, run it and read the two lines. Expected: two lines. What is wrong, and what is the fix? Write the fixed script, run it, and read the same two things. Expected: the same two lines, now different.

```python
import duckdb

from pipeline.checks import CheckFailed
from pipeline.gate import gate

con = duckdb.connect()
# Tonight's delivery lost the key of line 5500.
lines = con.sql("""
    SELECT * REPLACE (CASE WHEN order_item_id = 5500 THEN NULL ELSE order_item_id END AS order_item_id)
    FROM read_parquet('data/staging/order_lines.parquet')
""")
try:
    clean = gate(con, lines)
    print("loaded", clean.count("*").fetchall()[0][0], "lines")
except CheckFailed as error:
    print("warning:", error, "- skipping tonight, the next run will catch up")
```

```bash
uv run python exercises/de06b_ex3.py; echo "exit code $?"
```

<details>
<summary>Hint</summary>

Whatever starts a job later, a scheduler for example, has only two things to go by: what the job printed and the exit code it ended with. `echo $?` shows the exit code of the last command, and 0 means success.

</details>

<details>
<summary>Half-solution</summary>

The gate did its work: it stopped the run. Ask what the script did with the stop, and what the exit code told whoever started the script.

</details>

<Solution>

```console
$ uv run python exercises/de06b_ex3.py; echo "exit code $?"
warning: order_item_id_not_null: 1 bad lines, the run stops - skipping tonight, the next run will catch up
exit code 0
```

The warning is a line of text, and the job ended with exit code 0, success: to whatever started it, tonight looks like any other night. A stop exists to end the run in a way that others can see, and the `try` hid it. The fix is to let the failure out: remove the `try` and the `except`, or print the warning and raise again.

```python
clean = gate(con, lines)  # a stop rule raises, and nothing catches it: the run fails
print("loaded", clean.count("*").fetchall()[0][0], "lines")
```

```console
$ uv run python exercises/de06b_ex3_fix.py 2>&1 | tail -1; echo "exit code ${PIPESTATUS[0]}"
pipeline.checks.CheckFailed: order_item_id_not_null: 1 bad lines, the run stops
exit code 1
```

The tests of the gate would not have caught this, because the gate does stop. What would catch it is a test of the whole job: run the script on a batch with a missing key and assert that its exit code is not 0.

</Solution>
