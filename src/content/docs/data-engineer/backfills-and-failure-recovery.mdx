## The question

The owner writes:

> The first week of May looks thin in the sales chart, and I think the job failed on a few nights. Can you fix it, be sure that nothing is counted twice, and tell the team what happened?

You have three jobs, and they come in this order: run the missing days again, prove the table is right, and write down what went wrong. By the end you can do all three without touching the table by hand.

<Aside type="note" title="You already know this">

**Match.** *Incremental loads and idempotent reruns* (DE4) proved with a fingerprint that loading the same lines twice changes nothing. A backfill is that promise used on purpose.

**Diverge.** In DE4 one load asked for everything that had changed. A backfill is many runs, one for each past day, and some of them can fail.

</Aside>

## The big idea

A backfill is the same DAG run once for each past interval, safe only because every step gives the same table when it is run again.

### 1. The interval a run covers

**Idea.** A **backfill** runs a DAG again for past intervals, one run for each. The Dag Runs page says the logical date "denotes the start of the data interval, not when the Dag is actually executed", and warns that for a manual run you should not assume the interval equals the logical date. `backfill create` takes a first and a last date.

**Try it.** In terminal 2, unpause the DAG (new DAGs start paused) and backfill five days. `--max-active-runs 5` lets the five run at the same time. Wait about a minute and a half, then list the backfill's runs. Unpausing also lets the scheduler start its own run for yesterday, which `grep backfill` leaves out. `read_log.py` is a given file that prints a task log the short way:

```bash
cd airflow
source env.sh
uv run airflow dags unpause cafe_pipeline
uv run airflow backfill create --dag-id cafe_pipeline --from-date 2026-05-01 --to-date 2026-05-05 --max-active-runs 5
```

```bash
uv run airflow dags list-runs cafe_pipeline | grep backfill | cut -d"|" -f2,3,5
git show de-08-done:airflow/read_log.py > read_log.py
uv run python read_log.py "home/logs/dag_id=cafe_pipeline/run_id=backfill__2026-05-02T00:00:00+00:00/task_id=extract/attempt=1.log"
```

**Predict:** How many runs does the command create? Which logical date has the run named `backfill__2026-05-02T00:00:00+00:00`, and which day's lines does its `extract` land?

### 2. Reading a failed run

**Idea.** A failed run is one of three things, and each has another fix and another person to tell. The **data**: a line broke a rule, and the gate says so. The **pipeline**: the code or its environment failed. The **definition**: a rule, a schedule or a setting is wrong, so the run fails or passes for the wrong reason. Airflow keeps one log file for each attempt of each task, and the error of a failed attempt is in it.

**Try it.** From the `airflow` folder, list the attempt logs that hold an error, and read one of them with `read_log.py`. Use a path from your own list:

```bash
grep -l '"level":"error"' home/logs/dag_id=cafe_pipeline/run_id=backfill*/task_id=*/attempt=*.log
uv run python read_log.py "home/logs/dag_id=cafe_pipeline/run_id=backfill__2026-05-03T00:00:00+00:00/task_id=check/attempt=1.log"
```

**Predict:** The failed tasks are all `check`. What does the error say, and which of the three kinds is it?

<details>
<summary>Reveal the result</summary>

```console
$ uv run python read_log.py "home/logs/dag_id=cafe_pipeline/run_id=backfill__2026-05-03T00:00:00+00:00/task_id=check/attempt=1.log"
error   task: Task failed with exception
        IOException: IO Error: Could not set lock on file ".../data_de8/serving/cafe.duckdb": Conflicting lock is held in /usr/local/bin/python3.13 (PID 30033). See also https://duckdb.org/docs/current/connect/concurrency
```

</details>

*Why:* the path of the file is shortened to `...` here. This is the pipeline kind: nothing is wrong with a line or a rule. The DuckDB documentation says that in read-write mode one process can both read and write the database, so five runs that write the table at the same moment collide, and the retries, five seconds apart, collide again. The fix is in the DAG, one line after `catchup=False,`: one run at a time.

```python
    max_active_runs=1,  # the table is a DuckDB file, and one process at a time may write to it
```

The Airflow configuration reference says that the scheduler will not create more Dag runs once the limit is reached, and that `max_active_runs` sets that limit for one Dag. Save the DAG with that line (the checkpoint has it: `git show de-08-done:airflow/dags/cafe_pipeline.py > dags/cafe_pipeline.py`), and wait about a minute for Airflow to read the file again.

### 3. Rerun what failed, and prove nothing doubled

**Idea.** The same backfill command with `--reprocess-behavior failed` creates runs again for the days whose run failed. A rerun starts from the first task of the day, so the steps that already ran for it run again. The steps were written to be idempotent (DE4), and that is a claim to test, not to trust: take the same days through another route and compare fingerprints.

**Try it.** Rerun with one run at a time, wait for the runs to finish, and then fingerprint the lines whose current version was updated from May 1 to May 5. `range_fingerprint.py` is a given file. The other route is the incremental load of DE4 into a folder of its own, asked for the world as of May 5:

```bash
uv run airflow backfill create --dag-id cafe_pipeline --from-date 2026-05-01 --to-date 2026-05-05 --reprocess-behavior failed --max-active-runs 1
cd ..
git show de-08-done:scripts/range_fingerprint.py > scripts/range_fingerprint.py
DATA_DIR=data_de8 uv run python scripts/range_fingerprint.py 2026-05-01 2026-05-05
DATA_DIR=data_ref uv run python -m pipeline.load --until "2026-05-05 23:59:59"
DATA_DIR=data_ref uv run python scripts/range_fingerprint.py 2026-05-01 2026-05-05
DATA_DIR=data_de8 uv run python scripts/quarantined.py
DATA_DIR=data_ref uv run python scripts/quarantined.py
```

**Predict:** Do the two tables have the same fingerprint for May 1 to 5? Do their quarantines hold the same lines?

*Why:* the two tables agree to the last value: 107 lines, 172 units and the same fingerprint, reached by five daily runs that partly failed and were rerun, and by one load. The quarantines differ. The backfill saw line 6952 on May 1 with its quantity of 20, and held it; the load asked the API for the world as of May 5, where only the corrected version of the line exists, and never saw the held one. A table can be right while its history differs, which is why the incident note below says what was seen, not only what remains. The `--reprocess-behavior failed` run started the two failed days again from their first task and left the three that had succeeded alone: their logs gained no new attempt.

<Aside type="tip" title="Remember">

- A backfill is one run for each past interval; a run's id names the end of its interval, its logical date the start.
- Triage a failed run as data, pipeline or definition before fixing anything.
- Read the log of the failed attempt first: the last line of the error usually names the cause.
- Prove a backfill with a second route: the same fingerprint for the same days.

**Common trap:** running five days at once into a store that lets one process write: some runs fail, and the table fills unevenly until you look.

</Aside>

<Solution>

```markdown
**Where things stand.** The table is correct for May 1 to 5. We re-ran the days that failed and checked the result against a second load: 107 lines, 172 units, fingerprint 9d0ef5b3 in both.

**Impact.** Two of the five daily runs (the days of May 2 and May 5) failed in the `check` step after three tries, so those days were missing from `order_lines` until the re-run.

**Cause.** The DAG let all five runs write the DuckDB file at once. DuckDB lets one process write at a time, and the others stopped with a lock error. The data was not at fault: the gate held the same one line as the second load saw.

**Fix.** The DAG now allows one run at a time. Only the two failed runs were run again.

**Prevention.** The DAG's test checks the setting, and backfills run one run at a time.
```

The first line gives the decision and the proof, so a reader who stops there knows the table is right. The cause names the kind of failure (the pipeline's environment, not the data or a rule), and the note blames no one: it says what the DAG allowed, not who started the backfill.

</Solution>
