## The question

The owner of the cafes writes:

> When a day's lines arrive, how much of the sales tables has to be built again, and how will I know the answer is still right?

Every model of the project is built from scratch on every run, and nobody asked what a run costs. By the end you can say what each way of building a model stores, make one model add only what is new, and write down what a run reads and writes.

<Aside type="note" title="You already know this">

**Match.** [*Incremental loads and idempotent reruns*](/data-engineer/incremental-loads-idempotency/) (DE4) loaded only the lines changed since a saved time and wrote them by key, so that a second run changed nothing. An incremental dbt model is that pattern written as a `select`.

**Diverge.** In DE4 the loader's Python chose what to read. Here the model's own SQL chooses, and dbt writes the rows.

</Aside>

## The big idea

Every model is a `select`; its materialization, the choice of what dbt stores for it, decides what dbt keeps of it, and so what each run pays to keep it current.

### 2. An incremental model with a key

**Idea.** An **incremental** model builds the whole table on its first run. The dbt documentation says `is_incremental()` is true only when the table exists, `--full-refresh` is not passed and the model is configured as incremental; inside `{% if is_incremental() %}` the `select` can be narrowed to what is new. A **unique key** names the column that identifies a row: dbt replaces a row that has the same key and inserts the others. Without a key, most adapters only append. The `merge` strategy does this matching in one statement; with dbt-duckdb it needs DuckDB 1.4.0 or later (the project has 2.0.0).

**Try it.** Make three changes to `dbt/models/intermediate/int_order_lines_priced.sql`. Put this at the top:

```sql
{{
    config(
        materialized='incremental',
        incremental_strategy='merge',
        unique_key='order_line_id'
    )
}}
```

Add a comma after the `line_amount_usd` line and the column `l.updated_at` as the last one. Add this at the end:

```sql
{% if is_incremental() %}
-- On a later run: only the lines posted since the newest one this table holds.
where l.updated_at >= (select max(updated_at) from {{ this }})
{% endif %}
```

The model was a view and becomes a table, so the first build creates it. Stage the world of May 2, build, and look at line 6952, the extra-zero line that the API corrects later:

The mart is still a table, rebuilt in full from the intermediate model: it went from 276 to 453 rows.

### 3. A model that changes, a full refresh and the cost line

**Idea.** An incremental run reads only the rows its filter selects, so the rows already in the table keep what they were built with. The dbt documentation says `--full-refresh` drops the target table and builds it again for all time. A **cost line** is one sentence in a model's description that says what a run reads, what it writes and when a full rebuild is needed; write it before you choose a materialization, and read it when a run gets slow.

**Try it.** Add the payment method: put the line `l.payment_method,` after `l.status,` in `int_order_lines_priced.sql`, and build the model.

```bash
uv run dbt build --select int_order_lines_priced 2>&1 | grep -E "Binder Error|Done"
```

**Predict:** What does the build do?

<details>
<summary>Reveal the result</summary>

```console
$ uv run dbt build --select int_order_lines_priced 2>&1 | grep -E "Binder Error|Done"
  Binder Error: Table "int_order_lines_priced" does not have a column with name "payment_method"
20:07:02  Done. PASS=0 WARN=0 ERROR=1 SKIP=0 NO-OP=0 REUSED=0 TOTAL=1
```

</details>

*Why:* the table was built before the column existed, and the merge writes by column name, so dbt stops with an error and leaves the table as it was. The Incremental models page lists a setting for this, `on_schema_change`, whose value `append_new_columns` adds the column. A full refresh is how every row gets the new meaning:

```bash
uv run dbt build --full-refresh --select int_order_lines_priced 2>&1 | grep -E "Done"
uv run dbt show --quiet --inline "select count(*) as lines, count(payment_method) as with_method from {{ ref('int_order_lines_priced') }}"
```

```console
$ uv run dbt build --full-refresh --select int_order_lines_priced 2>&1 | grep -E "Done"
20:07:04  Done. PASS=1 WARN=0 ERROR=0 SKIP=0 NO-OP=0 REUSED=0 TOTAL=1
```

```console
$ uv run dbt show --quiet --inline "select count(*) as lines, count(payment_method) as with_method from {{ ref('int_order_lines_priced') }}"
| lines | with_method |
| ----- | ----------- |
|  3287 |        3287 |
```

Now write the cost line. This is the description of the intermediate model; the file also keeps the key unique and filled, so that a repeated or empty row would fail a test (DE10), and it is given:

```yaml
    description: >
      One row for each order line, priced with the product's price and net of the line's discount.
      Cost line: an incremental merge on order_line_id. Each run reads the lines posted since the newest one the table
      holds and writes only those; a change to what a row means needs dbt build --full-refresh.
```

```bash
git show de-11-done:dbt/models/intermediate/schema.yml > models/intermediate/schema.yml
uv run dbt build 2>&1 | grep -E "FAIL|SKIP|Done"
```

```console
$ uv run dbt build 2>&1 | grep -E "FAIL|SKIP|Done"
20:07:11  Done. PASS=23 WARN=0 ERROR=0 SKIP=0 NO-OP=0 REUSED=0 TOTAL=23
```

The three kinds of this project read like this. The view `stg_order_lines` reads the Parquet file at every query and writes nothing. The incremental model reads the lines since the newest one (1,301 on the second build) and writes those. The builds in the logs took well under a second, so at this size time does not decide; the rows a run reads do. That is why the dbt page says to move to incremental when runs become too slow, and not to start there.

<Aside type="tip" title="Remember">

- A view stores the query, a table the result, an incremental table the result and a rule for adding to it, an ephemeral model nothing.
- Start with a view, move to a table when it is slow to read, and to incremental when the rebuild is slow.
- `is_incremental()` is false on the first run and with `--full-refresh`; a unique key replaces the row that has it and adds the rest.
- A cost line says what a run reads and writes and when a full rebuild is needed.

**Common trap:** changing what a row means and not refreshing the table: the old rows keep the old meaning.

</Aside>
