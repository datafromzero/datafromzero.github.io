## The question

The owner of the three cafes writes:

> I read a sales sheet every morning. Last week the numbers for one store did not match what the till showed, and nobody could tell me where the sheet's numbers came from. Can you build whatever fills the sheet, and build it so someone can check it?

The sheet has one row for each store and day. The stores are in a file that a partner drops each month:

| store_id | store_name | city | opened_on |
|---:|---|---|---|
| 1 | Old Town | Oakland | 2023-05-12 |
| 2 | Campus | Berkeley | 2024-09-03 |
| 3 | Harbor | Alameda | 2026-04-01 |

The sales themselves live in the tills (the cash registers), behind an API. By the end you can sketch the pipeline that connects the two to the sheet, say which steps happen where, and defend one choice of how often it runs. The title's *ETL* and *ELT* are the same three steps in two orders: extract, transform, load, and extract, load, transform; unit 2 explains them.

<Aside type="note" title="You already know this">

**Match.** [*Warehouses, data lakes and what things cost*](/core/warehouses-lakes-and-cost/) (C35) separated a lake of files from a warehouse of tables. A pipeline uses both: files where data lands, tables where it is read.

**Diverge.** In C35 the data was already in the place you queried. Here the first job is to get it there from a system you do not control.

</Aside>

## The big idea

A pipeline is a promise that data moves from a source you do not control to a reader who needs it, every time it is asked.

### 1. Five stages, and the three you own

**Idea.** Data goes through five stages. A **source** makes it (a till), **ingestion** copies it out of the source, **storage** keeps it, **transformation** reshapes it, and **serving** hands it to a reader. A data engineer owns ingestion, storage and transformation, and the promise that all five run every day. The AWS exam guide for data engineers lists, among the tasks its target candidate is not expected to perform, ML training and inference and drawing business conclusions from data; the data scientist and data analyst tracks of this site teach that side.

**Try it.** Clone the starter and check it. The check script is the one of [*Your laptop setup and the terminal*](/core/laptop-setup-and-terminal/) (C22), extended for this project.

### 2. ETL or ELT: where the transformation runs

**Idea.** ETL stands for extract, transform, load: the data is reshaped on its way, and only the result is loaded. ELT stands for extract, load, transform: the data is loaded as it arrived and reshaped inside the place where it now lives. Read the starter's script before you run it:

```python
"""The first page of the API, summed two ways. Run it with: uv run python scripts/tour.py"""

import json
from urllib.request import urlopen

import duckdb

from pipeline.config import API_URL, RAW_DIR

with urlopen(f"{API_URL}/order-lines?limit=100", timeout=10) as response:
    body = response.read()

# ETL: transform in Python, keep only the result.
rows = [(line["order_item_id"], line["quantity"]) for line in json.loads(body)["data"]]
print(f"ETL: {sum(quantity for _, quantity in rows)} units on {len(rows)} lines; raw bytes kept: none")

# ELT: land the bytes first, then transform with SQL where the data now lives.
page = RAW_DIR / "tour" / "page-0001.json"
page.parent.mkdir(parents=True, exist_ok=True)
page.write_bytes(body)
units = duckdb.sql(f"SELECT sum(line.quantity) FROM (SELECT unnest(data) AS line FROM read_json('{page}'))").fetchall()[0][0]
print(f"ELT: {units} units; raw bytes kept: {page.stat().st_size:,} in data/raw/tour/page-0001.json")
```

**Try it.** Run `uv run python scripts/tour.py`.

**Predict:** Both routes read the same 100 lines. Do the two totals match? And tomorrow the owner asks for the quantity of coffee only: which route can answer without asking the API again?

<details>
<summary>Reveal the result</summary>

```console
$ uv run python scripts/tour.py
ETL: 148 units on 100 lines; raw bytes kept: none
ELT: 148 units; raw bytes kept: 25,736 in data/raw/tour/page-0001.json
```

</details>

*Why:* the totals match: 148 units on both routes. The new question needs a column the ETL route never kept, `product_id`, so it would have to call the API again, while the ELT route reads the file it saved. The article is from dbt Labs, the makers of dbt, a tool that transforms data with SQL (taught in [*A dbt project, from source to mart*](/data-engineer/dbt-project-and-first-model/) (DE9)). It says ELT leaves the source data on hand so that a team can revise how it is transformed without extracting again. It adds that ELT suits cloud warehouses (online services that store tables and run SQL on them) such as Snowflake, BigQuery and Amazon Redshift, because the transformation uses the warehouse's own computing power. The same article says ETL suits industries with strict data governance, such as finance and healthcare, where data needs to be transformed, cleaned and validated before it enters the warehouse.

### 3. Three layers: raw, staging, serving

**Idea.** Data sits in a layer that says what has been done to it. **Raw** holds the data as it arrived. **Staging** holds it cleaned up, with typed columns and clear names. **Serving** holds the tables that readers connect to.

**Try it.** Here are the steps of the pipeline for the owner's sheet, in the order they run. Save a file `docs/pipeline-sketch.md`: a title, the consumer and sources, and a table with one row for each step and the columns `#`, `Step`, `Layer` and `ETL or ELT`. Fill the last two yourself.

1. Save every page of the API exactly as it arrives.
2. Save `products.csv` and `stores.csv` exactly as they are.
3. Give each column of the lines its type and a clear name.
4. Do the same for the two files, one table for each file.
5. Join lines to products (the price) and to stores (the name).
6. Add up units and dollars for each store and day.
7. Publish the table `sales_by_store_day` for the sheet.

**Predict:** Which layer does step 5 belong to? And does any step after step 2 need to call the API again?

<details>
<summary>Reveal the result</summary>

```markdown
# Sketch: sales for each store and day

Consumer: the owner's morning sheet. Question: how many units and how many dollars did each store sell each day?
Sources: the sales API (order lines) and two files, `products.csv` and `stores.csv`.

| # | Step | Layer | ETL or ELT |
|---|------|-------|------------|
| 1 | Save every page of the API exactly as it arrives | raw | load first |
| 2 | Save `products.csv` and `stores.csv` exactly as they are | raw | load first |
| 3 | Give each column of the lines its type and a clear name | staging | ELT, in SQL |
| 4 | Do the same for the two files, one staged table for each file | staging | ELT, in SQL |
| 5 | Join lines to products (the price) and to stores (the name) | serving | ELT, in SQL |
| 6 | Add up units and dollars for each store and day | serving | ELT, in SQL |
| 7 | Publish the table `sales_by_store_day` for the sheet | serving | ELT, in SQL |

Batch or stream: batch, once a night, because the sheet is read once a morning.
```

</details>

*Why:* step 5 is serving, because a join makes a table shaped for one question. The dbt guide says staging models should have a 1-to-1 relationship to their source tables, and that their goal is to clean and prepare individual source-conformed concepts. No step after step 2 calls the API: everything after the raw copy reads files, so a changed question never touches the source. The last line chooses a batch; the next unit prices that choice.

### 4. Batch or stream, priced in hours alive

**Idea.** A **batch** run starts on a schedule, reads a window of data and stops. A **stream** stays alive and handles each event as it arrives. Price each in two numbers: the hours a month the program has to be alive, and how old the owner's answer may be.

**Try it.** Count how often the cafes' orders arrive, from the file behind the mock API: `uv run python scripts/arrivals.py`.

**Predict:** Across the six months, what is the largest number of orders in a single hour: about 2, about 5 or about 20?

<details>
<summary>Reveal the result</summary>

```console
$ uv run python scripts/arrivals.py
1,800 orders on 181 days
per day: fewest 4, median 9.0, most 19
most orders in one hour: 5
```

</details>

*Why:* the busiest hour of six months has 5 orders, and a typical day has 9. A stream alive all month is alive for 24 × 30 = 720 hours to handle about 300 orders. A nightly batch that runs 5 minutes (an assumption; the next lesson times a real run) is alive 30 × 5 minutes = 2.5 hours, about 288 times fewer. The sheet is read once a morning, so an answer that is a day old costs the owner nothing, and the batch wins. A stream would earn its hours if someone had to act within minutes, for example a call to a store that has had no order for two hours. These are hours of a program you keep alive; a service that bills for each event has its own price page, which you read before you choose it.

<Aside type="tip" title="Remember">

- A pipeline has five stages: source, ingestion, storage, transformation and serving. You own the middle three.
- ETL reshapes data on its way to the store; ELT stores it first and reshapes it inside.
- Raw holds the data as it arrived, staging is one typed table for each source table, serving is shaped for a question.
- Price batch against stream in hours alive and in how old the answer may be.

**Common trap:** calling a stream cheap because the data is small. A stream costs the hours it stays alive, not the rows it handles.

</Aside>

**Spot the flaw.** A colleague sketches the pipeline for the owner's sheet in four lines and calls it "clean and short". What is wrong with it, and what would you change?

```markdown
| # | Step | Layer | ETL or ELT |
|---|------|-------|------------|
| 1 | Save every page of the API, keeping only the lines whose status is completed | raw | load first |
| 2 | Save `products.csv` and `stores.csv` exactly as they are | raw | load first |
| 3 | Give each column of the lines and of the two files its type and a clear name | staging | ELT, in SQL |
| 4 | Join the lines to products and stores, add up each store and day, and publish `sales_by_store_day` | serving | ELT, in SQL |
```

<details>
<summary>Hint</summary>

The owner's first message said that one store's numbers did not match the till. Which lines could you not look at, to find out why?

</details>

<details>
<summary>Half-solution</summary>

```markdown
| 1 | Save every page of the API ... | raw | load first |
| 4 | ... | serving | ELT, in SQL |
```

</details>

<Solution>

Step 1 filters on the way in. The sheet counts completed orders, but the rule is applied before the bytes are kept, so the one canceled order of the six months is gone from raw, and so is any question about it: whether the till or the sheet is right about a store, or how many lines were canceled. A rule applied before landing cannot be undone, and a changed rule means asking the API for everything again. The dbt article gives the same reason for ELT: with the source data on hand, a team can revise how it is transformed without extracting again. The fix is to land every page exactly as it arrives, and to keep the completed lines where the rule can change: in the serving step, in SQL.

</Solution>
