## The question

A teammate who reads the pipeline's log writes:

> Last month someone changed the retry, and on a night with rate limits half the pages never loaded. Nobody noticed for a week. Can the pipeline check itself every time we change it?

The retry's wait has three cases that you can work out by hand:

| the answer says | the wait, in seconds |
|---|---:|
| nothing, on the first try | 0.5 |
| `Retry-After: 3` | 3 |
| `Retry-After: Tue, 24 Nov 2026 08:00:10 GMT`, asked at 08:00:00 | 10 |

By the end you can write a test before the code, test a step on a handful of rows, and decide whether to trust a function that an assistant wrote, by what your tests say.

## The big idea

### 1. The test first

**Idea.** Write the test of the behavior you want before the code, run it, and read why it fails: it must fail for the reason you expect, or it tells you nothing when it passes. Then change the code as little as you can until it passes. The RFC allows the `Retry-After` header to hold a date as well as a number of seconds, and the `wait_time` of DE2 reads only seconds.

**Try it.** Save the three cases as `tests/test_ingest.py`, with a stand-in for a response that has only the header that `wait_time` reads, and run it:

```python
from datetime import datetime, timezone
from types import SimpleNamespace

from pipeline.ingest import wait_time


def reply(retry_after=None):
    """A stand-in for a response: only the header that wait_time reads."""
    return SimpleNamespace(headers={} if retry_after is None else {"Retry-After": retry_after})


def test_a_number_of_seconds_is_obeyed():
    assert wait_time(reply("3"), attempt=1) == 3.0


def test_no_header_means_a_doubling_wait():
    assert [wait_time(reply(), attempt=n) for n in (1, 2, 3)] == [0.5, 1.0, 2.0]


def test_a_date_means_the_seconds_until_then():
    now = datetime(2026, 11, 24, 8, 0, 0, tzinfo=timezone.utc)
    assert wait_time(reply("Tue, 24 Nov 2026 08:00:10 GMT"), attempt=1, now=now) == 10.0
```

```python
from email.utils import parsedate_to_datetime
```

```python
def wait_time(response, attempt, base=0.5, now=None):
    """How long to wait before trying again: what the server asked for, else a doubling wait."""
    value = response.headers.get("Retry-After", "")
    if value.isdigit():
        return float(value)  # a number of seconds
    try:
        when = parsedate_to_datetime(value)  # or a date
    except (TypeError, ValueError):
        return base * 2 ** (attempt - 1)
    return max(0.0, (when - (now or datetime.now(timezone.utc))).total_seconds())
```

The Python page says `parsedate_to_datetime` reads a date by the rules of RFC 2822 (the format of email dates), as `parsedate` does, but returns a `datetime`, and raises `ValueError` for an invalid value.

### 2. A small function: rows in, rows out

**Idea.** A step you can test is a function that takes rows and returns rows, with no network and no files in it. `stage.py` keeps the latest version of each key inside a SQL string, where no test can reach it. Pull it out as `dedupe_latest(rows, key, version)` and give it three tests whose answers you know by hand: a repeated record is kept once, the latest version wins even when it comes first, and different keys all stay.

**Try it.** Save the tests as `tests/test_transform.py` and run them before `transform.py` exists:

```python
import duckdb
import pytest

from pipeline import transform


@pytest.fixture
def lines():
    """Build a tiny relation of (order_item_id, quantity, updated_at) rows from a list of tuples."""
    con = duckdb.connect()

    def build(*rows):
        values = ", ".join(f"({key}, {quantity}, TIMESTAMP '{updated}')" for key, quantity, updated in rows)
        return con.sql(f"SELECT * FROM (VALUES {values}) AS t(order_item_id, quantity, updated_at)")

    return build


def keep(relation):
    return sorted((key, quantity) for key, quantity, _ in relation.fetchall())


def test_a_repeated_record_is_kept_once(lines):
    rows = lines((1, 2, "2026-05-01 10:00:00"), (1, 2, "2026-05-01 10:00:00"), (2, 1, "2026-05-01 10:05:00"))
    assert keep(transform.dedupe_latest(rows)) == [(1, 2), (2, 1)]


def test_the_latest_version_wins_even_when_it_comes_first(lines):
    rows = lines((1, 2, "2026-05-03 09:00:00"), (1, 20, "2026-05-01 13:30:00"))
    assert keep(transform.dedupe_latest(rows)) == [(1, 2)]


def test_different_keys_all_stay(lines):
    rows = lines((1, 1, "2026-05-01 10:00:00"), (2, 1, "2026-05-01 10:00:00"), (3, 1, "2026-05-01 10:00:00"))
    assert keep(transform.dedupe_latest(rows)) == [(1, 1), (2, 1), (3, 1)]
```

```python
"""Small steps that turn rows into other rows. Each one is tested on a handful of rows."""


def dedupe_latest(rows, key="order_item_id", version="updated_at"):
    """Keep one row for each key: the one with the latest version."""
    return rows.query(
        "rows",
        f"SELECT * FROM rows QUALIFY row_number() OVER (PARTITION BY {key} ORDER BY {version} DESC) = 1",
    )
```

The DuckDB page says that `QUALIFY` filters the results of window functions, here the rank of each version within its key, and that a relation's `query` method runs SQL over it. The second test is the one that matters: in a file sorted by `updated_at` the old version comes first; here it comes last, so a function that kept the last row it saw would fail it.

### 3. A log line a test can assert

**Idea.** A line in the log that says how many rows went in and how many came out lets a person see at a glance that a night lost half its rows. A test can check the same line: pytest's `caplog` fixture holds everything logged during the test, as records and as text, and the pytest page says it is useful when you want to assert on the contents of a message.

**Try it.** Save the test as `tests/test_stage.py`: it writes a page of three records, one of them repeated, and stages it. Run it against the `stage.py` of DE3, which logs nothing.

```python
    "product_id": 15,
```

```python
def raw_lines(con, pages_glob):
    """Every record of every landed page, with typed columns. A repeated record stays repeated."""
    return con.sql(f"""
        WITH pages AS (
            SELECT unnest(data) AS line
            FROM read_json('{pages_glob}', columns = {{data: '{LINE_FIELDS}[]'}})
        )
        SELECT line.* FROM pages
    """)


def staged_lines(con, pages_glob):
    """One row for each order line, and a log line that says how many records became how many lines."""
    records = raw_lines(con, pages_glob)
    lines = transform.dedupe_latest(records)
    log.info("%d records read, %d lines kept", records.count("*").fetchall()[0][0], lines.count("*").fetchall()[0][0])
    return lines.order("order_item_id")
```

```python
"""Written for the lesson, in the style of an assistant's answer. Not produced by a model."""


def dedupe_latest(rows, key="order_item_id", version="updated_at"):
    """Keep the latest version of each key."""
    ranked = rows.project(f"*, row_number() OVER (PARTITION BY {key} ORDER BY {version} DESC) AS rank_in_key")
    return ranked.filter("rank_in_key = 1").project("* EXCLUDE (rank_in_key)")
```

<Aside type="tip" title="Remember">

- Write the test first and read why it fails: the right failure shows the test can fail.
- A step you can test takes rows and returns rows, and a clock or a file it needs is passed in.
- A log line of rows in and rows out is a check a person reads and `caplog` asserts.
- Run your tests against an assistant's code without touching yours; what they do not cover is still open.

**Common trap:** trusting a check on the real data. A count on today's data passed a function that a three-row test with a corrected line rejects.

</Aside>
