## The question

The owner of the cafes writes:

> You have kept our sales in files and views so far. If I ask you to build the tables that people will query for the next five years, what do you decide before you write a single `CREATE TABLE`?

The sales API has a contract (DE6): what each column is, whether it may be empty, which values it accepts. A table can enforce that or only record it. By the end you can turn the contract into tables that refuse bad rows, and choose the order of a table from the questions it must answer.

<Aside type="note" title="You already know this">

**Match.** [*Creating tables and constraints*](/sql/create-table-constraints/) (S33) declared `NOT NULL`, `CHECK`, a primary key and a foreign key on a table, and [*Designing tables: a workflow*](/sql/designing-tables-workflow/) (S37) went from questions to columns. *Data quality checks that fail loudly* (DE6) wrote the same rules as queries over the incoming lines.

**Diverge.** A DE6 check reports a bad line after it arrived. A constraint is part of the table, so what it can do depends on the database that holds the table.

</Aside>

## The big idea

A logical model says what must hold; the physical model is the table that holds it, and only the database that stores it decides which of those rules are enforced.

### 1. The contract as a table

**Idea.** The **logical** model of `order_lines` is the contract of DE6: a key, columns that may not be empty, accepted values, a range. The **physical** table is the `CREATE TABLE` that a database can check: a type for each column, `NOT NULL`, `CHECK`, `PRIMARY KEY`. Choose the type that holds every legitimate value and no more. The DuckDB documentation says `DECIMAL` is exact and `FLOAT` and `DOUBLE` are approximate, and that a value outside an integer type's range is an error.

**Try it.** A small script is given that runs SQL against a database file of its own, `data/serving/design.duckdb`, and prints what comes back. Fetch it, save the table as `sql/physical_order_lines.sql`, create it, and load the real lines:

```bash
git show de-12-done:scripts/sql.py > scripts/sql.py
mkdir -p sql
```

```sql
-- The contract of DE6 as a table: a row that breaks a rule is refused.
CREATE OR REPLACE TABLE order_lines (
    order_item_id INTEGER PRIMARY KEY,
    order_id INTEGER NOT NULL,
    ordered_at TIMESTAMP NOT NULL,
    store_id INTEGER NOT NULL,
    customer_id INTEGER,
    status VARCHAR NOT NULL CHECK (status IN ('completed', 'canceled')),
    payment_method VARCHAR NOT NULL CHECK (payment_method IN ('card', 'mobile', 'cash')),
    product_id INTEGER NOT NULL,
    quantity INTEGER NOT NULL CHECK (quantity BETWEEN 1 AND 10),
    discount_usd DECIMAL(8, 2) NOT NULL CHECK (discount_usd >= 0),
    updated_at TIMESTAMP NOT NULL,
    channel VARCHAR CHECK (channel IN ('counter', 'app'))
);
```

### 2. Keys between tables, and who enforces them

**Idea.** A **foreign key** says that a column must hold a value that exists in a key of another table. An **alternate key** is a second set of columns that identifies a row; you declare it with `UNIQUE`, and a table has one primary key but many unique constraints. A **composite key** has several columns; for a table whose grain is a store and a day, the key is both. The DuckDB documentation says each of these also creates an index to check it.

**Try it.** The whole design is given as `sql/physical_design.sql`: three tables with their keys, the table of store-days, and the loads in the order the keys need. These are the parts that matter. In `stores` the name is an alternate key next to the primary key, and `products` does the same with `product_name`:

```sql
CREATE TABLE stores (
    store_id INTEGER PRIMARY KEY,
    store_name VARCHAR NOT NULL UNIQUE,
    city VARCHAR NOT NULL,
    opened_on DATE NOT NULL
);
```

In `order_lines`, `store_id` and `product_id` each `REFERENCES` the key of their table. The table of store-days has a composite key, its grain:

```sql
-- One row for each store and day: the key is the grain.
CREATE TABLE store_daily_sales (
    store_id INTEGER NOT NULL REFERENCES stores (store_id),
    order_date DATE NOT NULL,
    lines INTEGER NOT NULL,
    units INTEGER NOT NULL,
    PRIMARY KEY (store_id, order_date)
);
```

### 3. The order of a big table

**Idea.** Rows have to be stored in some order, and the order is a physical choice. The DuckDB documentation says it creates min-max indexes (zonemaps) automatically, skips a row group whose range cannot hold the filter value, and that the more ordered a column is, the more valuable its zonemap. A warehouse that lets you declare the layout gives it a name: the BigQuery documentation says a partitioned table is divided into segments that a filter on the partition column can skip, and that clustered tables sort data in storage blocks by the clustered columns.

**Try it.** At 3,287 lines a table is one row group and nothing can be skipped, so the lesson uses an invented table built from the real lines: they are copied 300 times, copy k dated k days later, which gives 986,100 lines. Two tables hold the same rows: `lines_arrival` in a shuffled order, and `lines_by_date`, made like this from it:

```sql
CREATE OR REPLACE TABLE lines_by_date AS
SELECT * FROM lines_arrival ORDER BY order_date, store_id;
```

The script that makes both is given as `sql/layout.sql`, with one that prints the line "Row Groups Scanned" of a plan:

```bash
git show de-12-done:sql/layout.sql > sql/layout.sql
git show de-12-done:scripts/row_groups.py > scripts/row_groups.py
uv run python scripts/sql.py sql/layout.sql
uv run python scripts/row_groups.py "order_date BETWEEN DATE '2026-09-01' AND DATE '2026-09-07'"
uv run python scripts/row_groups.py "store_id = 3"
uv run python scripts/row_groups.py "store_id = 3 AND order_date BETWEEN DATE '2026-09-01' AND DATE '2026-09-07'"
```

**Predict:** The table has nine row groups. For each of the three filters, how many does each of the two tables scan?

*Why:* the shuffled table has every date and every store in every row group, so no range excludes anything and all nine are read. The sorted table puts a week of dates in two row groups, so a filter on date reads two. A filter on the store alone gets nothing from it. Counting the stores in each row group of the sorted table, 122,880 rows at a time, shows why:

```bash
uv run python scripts/sql.py "SELECT count(*) AS row_groups, min(stores) AS fewest_stores FROM (SELECT rowid // 122880 AS g, count(DISTINCT store_id) AS stores FROM lines_by_date GROUP BY g)"
```

```console
$ uv run python scripts/sql.py "SELECT count(*) AS row_groups, min(stores) AS fewest_stores FROM (SELECT rowid // 122880 AS g, count(DISTINCT store_id) AS stores FROM lines_by_date GROUP BY g)"
row_groups | fewest_stores
-----------+--------------
9          | 3
```

Every row group holds all three stores, so no range of `store_id` excludes store 3; the filter on both gets what the date gave. The order of the sort serves its first column. BigQuery's page says the same of clustering: the order of the clustered columns affects performance, and a table can have up to four. The choice is made from the filters of the queries the table must answer, which is why you ask for them before you create it.

The BigQuery clustering page adds that the cost of a query on a clustered table can be known only after it has run; no price is quoted here, because none was read.

<Aside type="tip" title="Remember">

- A contract becomes a table: a type, `NOT NULL`, `CHECK` and a primary key for each rule; the table then refuses a row that breaks one.
- `PRIMARY KEY` once, `UNIQUE` for each alternate key, `REFERENCES` for a foreign key, a composite key at the grain.
- BigQuery does not enforce primary and foreign keys and Snowflake does not on standard tables: there the check is a test.
- The sort order of a table serves its first column; choose it, like a partition or a cluster, from the filters of the queries.

**Common trap:** reading a declared key as a guarantee on a warehouse that does not enforce it.

</Aside>

The key is true of the data and false of the business: no order so far has repeated a product, but nothing in the cafe forbids it, and a second croissant on its own line, perhaps with its own discount, is a valid sale. The constraint turns it into an error at the till, and in a pipeline into a failed load. A key is a rule you choose: declare an alternate key only for a rule the business states (no two stores share a name, the menu has one row for each name), and let the primary key, `order_item_id`, identify the line.
