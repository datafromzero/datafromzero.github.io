## The question

The owner writes:

> The new sales table looked fine for a week, and then a number was wrong for two days before anyone said so. How do we know the table is right every time it is built, and who is hurt when we change a model?

Both questions have the same answer: the project says, in files, what must hold and what depends on what, and dbt checks the first and shows the second. A rule you wrote in DE6 for the incoming lines is a test here, on the models.

<Aside type="note" title="You already know this">

**Match.** [*Data quality checks that fail loudly*](/data-engineer/data-quality-checks/) (DE6) wrote each rule as a query for the bad lines and broke the data on purpose. A dbt test is the same idea: a `select` for failing rows, zero rows to pass.

**Diverge.** The gate of DE6b sat in front of the load. These run on the models, after they are built.

</Aside>

## The big idea

A model is trusted when its rules are written as tests that fail on bad data, and when anyone can see what it depends on and what depends on it.

## Learn by doing

About 30 minutes, 3 new ideas: the built-in tests, tests of your own, and documentation with lineage. Work in `de-pipeline-starter` with the dbt project of DE9 built (`cd dbt` and `uv run dbt build` pass) and the full pull staged. To catch up, run `git checkout de-10-start`. Every dbt command runs from the `dbt` folder.

### 1. The four built-in tests

**Idea.** The dbt documentation says data tests are `select` statements that grab failing records: zero failing rows, and the test passes. dbt ships four **generic tests**: `unique`, `not_null`, `accepted_values` and `relationships`, and you apply them to a column in a YAML file. Tests that need inputs take them under `arguments`.

**Try it.** Save the tests of the staging models as `dbt/models/staging/schema.yml`. They also hold the first documentation, a `description` for each model and for the columns that matter:

```yaml
version: 2

models:
  - name: stg_order_lines
    description: One row for each order line, the latest version of it that the pipeline staged.
    columns:
      - name: order_line_id
        description: Key of the line, as the sales API sends it.
        data_tests:
          - unique
          - not_null
      - name: status
        description: "completed or canceled: whether the order was paid."
        data_tests:
          - accepted_values:
              arguments:
                values: [completed, canceled]
      - name: product_id
        description: The product sold on the line.
        data_tests:
          - not_null
          - relationships:
              arguments:
                to: ref('stg_products')
                field: product_id
      - name: store_id
        description: The store that took the order.
        data_tests:
          - relationships:
              arguments:
                to: ref('stg_stores')
                field: store_id

  - name: stg_stores
    description: One row for each store.
    columns:
      - name: store_id
        data_tests:
          - unique
          - not_null

  - name: stg_products
    description: One row for each product on the menu.
    columns:
      - name: product_id
        data_tests:
          - unique
          - not_null
```

Two files change too, and they are given: `sources.yml` reads the folder of the staged files from the variable `STAGING_DIR` (default: the real one), and `profiles.yml` gains a second target, `scratch`, with a database of its own. Together they let dbt build on a broken copy of the data without touching your tables. `scripts/break_staging.py` writes six broken copies of the three staged files, one fault each, like DE6's. Fetch them, run the tests, and make the copies:

```bash
git show de-10-done:dbt/models/staging/sources.yml > dbt/models/staging/sources.yml
git show de-10-done:dbt/profiles.yml > dbt/profiles.yml
git show de-10-done:scripts/break_staging.py > scripts/break_staging.py
cd dbt
uv run dbt test --select stg_order_lines 2>&1 | grep -E "PASS|FAIL|Done"
cd ..
uv run python scripts/break_staging.py
```

*Why:* the `unique` test of the key fails with one bad row, and `build` skips the two models that come after `stg_order_lines`, so a table made from a repeated line is never built. That is the stop of DE6b, done by the order of the graph. The tests of the other columns still pass, as in DE6: one fault trips one test.

### 2. Tests of your own

**Idea.** A **singular test** is a SQL file in the `tests` folder that returns the failing rows; its name is the file's name. Use one for a rule no generic test states. Two kinds are worth writing: a rule of the business, and a **reconciliation**, which compares a count before and after a model.

**Try it.** Make the folder, and save the business rule as `dbt/tests/assert_no_sales_before_a_store_opens.sql`: a store cannot sell before the day it opened.

```sql
-- A store cannot sell before the day it opened. The test passes when this returns no rows.
select
    f.store_id,
    f.order_date,
    s.opened_on
from {{ ref('fct_store_daily_sales') }} as f
join {{ ref('stg_stores') }} as s using (store_id)
where f.order_date < s.opened_on
```

Save the reconciliation as `dbt/tests/assert_the_mart_keeps_every_completed_line.sql`:

```sql
-- Every completed line of staging must be in the mart. A row here is the count on both sides when they differ.
select
    s.completed_lines,
    m.mart_lines
from (select count(*) as completed_lines from {{ ref('stg_order_lines') }} where status = 'completed') as s
cross join (select sum(lines) as mart_lines from {{ ref('fct_store_daily_sales') }}) as m
where s.completed_lines <> m.mart_lines
```

```bash
mkdir -p tests
uv run dbt build 2>&1 | grep -E "FAIL|SKIP|Done"
STAGING_DIR=../data/broken_staging/late_opening uv run dbt build --target scratch 2>&1 | grep -E "FAIL|SKIP|Done"
```

**Predict:** The copy `late_opening` says that store 3 opened on May 1, though it sold from April 1. How many rows does the opening-date test return?

<details>
<summary>Reveal the result</summary>

```console
$ uv run dbt build 2>&1 | grep -E "FAIL|SKIP|Done"
13:51:44  Done. PASS=17 WARN=0 ERROR=0 SKIP=0 NO-OP=0 REUSED=0 TOTAL=17
$ STAGING_DIR=../data/broken_staging/late_opening uv run dbt build --target scratch 2>&1 | grep -E "FAIL|SKIP|Done"
13:51:49  16 of 17 FAIL 30 assert_no_sales_before_a_store_opens .......................... [FAIL 30 in 0.02s]
13:51:49  Done. PASS=16 WARN=0 ERROR=1 SKIP=0 NO-OP=0 REUSED=0 TOTAL=17
```

</details>

*Why:* 30 rows, one for each store-day of April 1 to 30 that now falls before the new opening date. On the real data both tests pass: `build` runs five models, ten tests of columns and these two. The first rule is about the world and no column test could state it; the second compares two counts, so that a join that drops lines cannot pass unnoticed.

### 3. Documentation and lineage

**Idea.** The dbt documentation says to add a `description:` key to the same YAML files where you declare tests. `dbt docs generate` builds the documentation from them and from the project, including a graph of the project; dbt also lists columns you did not describe, so a gap shows. The **lineage** is the same graph `ref` and `source` build, and the command line can read it: `dbt ls --select stg_stores+` selects a model and everything after it.

**Try it.** Save the mart's documentation as `dbt/models/marts/schema.yml`:

```yaml
version: 2

models:
  - name: fct_store_daily_sales
    description: >
      Sales of completed order lines, for each store and each day on which it sold something.
      A day without a sale has no row.
    columns:
      - name: store_id
        description: The store, as in stg_stores.
        data_tests:
          - not_null
      - name: order_date
        description: The day of the orders, in the cafe's local time.
        data_tests:
          - not_null
      - name: lines
        description: Completed order lines sold that day.
      - name: units
        description: Units on those lines.
      - name: sales_usd
        description: "Amount of those lines in US dollars: units times the product's price, minus the line's discount."
```

```bash
uv run dbt docs generate 2>&1 | tail -2
uv run dbt ls --quiet --select stg_stores+ --resource-type model
uv run dbt ls --quiet --select stg_products+ --resource-type model
```

**Predict:** You change a column of `stg_stores`, and then one of `stg_products`. Which models does each change touch?

<details>
<summary>Reveal the result</summary>

```console
$ uv run dbt docs generate 2>&1 | tail -2
13:50:38  Building catalog
13:50:38  Catalog written to .../dbt/target/catalog.json
$ uv run dbt ls --quiet --select stg_stores+ --resource-type model
cafe.marts.fct_store_daily_sales
cafe.staging.stg_stores
$ uv run dbt ls --quiet --select stg_products+ --resource-type model
cafe.marts.fct_store_daily_sales
cafe.intermediate.int_order_lines_priced
cafe.staging.stg_products
```

</details>

*Why:* the path of the file is shortened to `...`. A change to the stores touches the store model and the mart, which joins it directly, and not the intermediate model; a change to the products touches the intermediate model and, through it, the mart. The same graph is drawn as boxes in the documentation site that `dbt docs generate` builds into `target/`, with each description beside its model; that site was not opened for this lesson. The command line gives the list a reviewer needs before approving a change to a model.

<Aside type="tip" title="Remember">

- A test is a select for failing rows: none, and it passes. The four generic tests go in YAML; a rule of your own is a file in `tests`.
- Break the data on purpose, on a copy and in a scratch database, and watch the right test fail and the models after it skip.
- A reconciliation test compares a count before and after a model.
- A description sits beside the test it belongs to, and `dbt ls` with a `+` lists what a change reaches.

**Common trap:** trusting a test you have never seen fail.

</Aside>

## Check yourself

1. Without looking back: what does `dbt build` do with a model whose test fails, and with the models that read it?

   <details>
   <summary>answer</summary>

   The failing test is reported as an error. The models and tests that depend on that model are skipped.

   </details>

<Exercise id="data-engineer-dbt-tests-and-documentation-3">

**Spot the flaw.** A colleague adds a `not_null` test for `customer_id` in `stg_order_lines`. The build fails, because one line has no customer, a walk-in. "Fixed it": the colleague adds `where customer_id is not null` to the staging model, and the whole build passes. Make both changes and run the build after each, then run the counts script. Expected: the first build fails one test and skips what follows, the second passes everything, and the counts show what the fix cost. What is wrong, and what would catch it? When you are done, undo both changes.

```bash
uv run dbt build 2>&1 | grep -E "FAIL|SKIP|Done"
uv run python ../scripts/dbt_counts.py
```

<summary>Hint</summary>

</details>

```sql
    s.source_lines,
    t.staged_lines
from (select count(*) as source_lines from {{ source('pipeline', 'order_lines') }}) as s
cross join (select count(*) as staged_lines from {{ ref('stg_order_lines') }}) as t
where s.source_lines <> t.staged_lines
```
