## The question

The owner of the cafes writes:

> In April we moved the Blueberry Muffin from the bakery to the food section of the menu. Now the bakery total for March in the new report does not match the one we sent then. Which is right?

Both can be, and the table has to say which question it answers. By the end you can keep the history of a changing attribute, point a fact at the version that was true on the day, and show a report both ways.

<Aside type="note" title="You already know this">

**Match.** [*Grain, facts and dimensions*](/core/grain-facts-and-dimensions/) (C17) and [*Designing a star schema from business questions*](/core/designing-a-star-schema/) (C18) put measures in a fact at one grain, with descriptive columns in dimensions around it. Here that star is built in dbt.

**Diverge.** The dimension of C18 has one row for each product. Here a product may have several rows, one for each time it changed.

</Aside>

   <details>

## The big idea

A dimension that changes can overwrite its past or keep it; a fact that points at the row that was true on the day lets a report choose.

### 1. A snapshot: history from a file that changes

**Idea.** A **slowly changing dimension** has attributes that change now and then. **Type 1** overwrites the old value, which the Kimball Group page says destroys history. **Type 2** adds a row with the new values, with at least a row effective date, a row expiration date and a current-row indicator. A dbt **snapshot** records Type 2 changes of a table that gets overwritten: it adds `dbt_valid_from` and `dbt_valid_to`, and with the `timestamp` strategy a newer `updated_at` makes dbt close the old row and insert the new one (the dbt documentation).

**Try it.** The real product file never changes, so its history is invented here. A script is given that writes the partner's file as it was at version 1, 2 or 3: version 1 is today's file stamped January 1, and version 2 moves the Blueberry Muffin from bakery to food on April 15 at noon. Fetch it, the new source and the snapshot, and take the first version:

```bash
git show de-13-done:scripts/partner_files.py > scripts/partner_files.py
git show de-13-done:dbt/models/partner_sources.yml > dbt/models/partner_sources.yml
mkdir -p dbt/snapshots
```

`dbt/snapshots/products_snapshot.yml`:

```yaml
snapshots:
  - name: products_snapshot
    relation: source('partner', 'products')
    config:
      schema: snapshots
      unique_key: product_id
      strategy: timestamp
      updated_at: updated_at
```

```bash
uv run python scripts/partner_files.py 1
cd dbt
uv run dbt snapshot 2>&1 | grep -E "ERROR|Done"
uv run dbt show --quiet --inline "select count(*) as versions, count(distinct product_id) as products, count(dbt_valid_to) as closed from {{ ref('products_snapshot') }}"
```

```console
$ uv run dbt show --quiet --inline "select count(*) as versions, count(distinct product_id) as products, count(dbt_valid_to) as closed from {{ ref('products_snapshot') }}"
| versions | products | closed |
| -------- | -------- | ------ |
|       16 |       16 |      0 |
```

The partner sends a new file. Write version 2, take the snapshot, and take it once more without a new file:


### 2. Dimensions with surrogate keys, and a fact that points at a version

**Idea.** A **surrogate key** is a key the warehouse makes in place of one from the source: the Kimball page calls it an artificial key that substitutes for a natural key, and says every join between a fact and a dimension should use it. A Type 2 dimension needs one, because `product_id` no longer identifies a row: product 11 has two. The snapshot makes one for each row, `dbt_scd_id`. The fact holds the key of the version true when the line was ordered, found by the product and the time.

**Try it.** The product dimension reads the snapshot, and the fact reuses the macro of [*Jinja and macros*](/data-engineer/jinja-and-macros/) (DE11b). `dbt/models/marts/dim_product.sql`:

```sql
-- Grain: one row for each version of a product. A change in the partner's file adds a row (type 2).
select
    dbt_scd_id as product_key,
    product_id,
    product_name,
    category,
    unit_price_usd,
    dbt_valid_from as valid_from,
    dbt_valid_to as valid_to,
    dbt_valid_to is null as is_current
from {{ ref('products_snapshot') }}
```

`dbt/models/marts/fct_order_lines.sql`: the line is ordered at or after the version's start and before its end, and a current row has no end.

```sql
-- Grain: one row for each order line. It holds the keys of the dimension rows that were true when the line was ordered.
select
    l.order_line_id,
    p.product_key,
    s.store_key,
    l.order_date,
    l.status,
    l.units,
    l.discount_usd,
    {{ line_amount('l.units', 'p.unit_price_usd', 'l.discount_usd') }} as line_amount_usd
from {{ ref('stg_order_lines') }} as l
join {{ ref('dim_product') }} as p
    on l.product_id = p.product_id
    and l.ordered_at >= p.valid_from
    and l.ordered_at < coalesce(p.valid_to, timestamp '9999-12-31')
join {{ ref('dim_store') }} as s using (store_id)
```

The store dimension is Type 1 (a rebuild overwrites it) with a hash of the store id as its key, and the descriptions, tests and a reconciliation test (every staged line is in the fact, as in DE10) are given. Fetch them and build:

```bash
git show de-13-done:dbt/models/marts/dim_store.sql > models/marts/dim_store.sql

git show de-13-done:dbt/tests/assert_the_fact_keeps_every_line.sql > tests/assert_the_fact_keeps_every_line.sql
uv run dbt build 2>&1 | grep -E "FAIL|SKIP|Done"
uv run dbt show --quiet --inline "select count(*) as fact_lines, count(distinct product_key) as versions_used, round(sum(line_amount_usd) filter (where status = 'completed'), 2) as completed_usd from {{ ref('fct_order_lines') }}"
```

**Predict:** How many rows will the fact hold, and how many different product keys will its lines use?

The Kimball page says a surrogate key should be a simple integer; the keys here are hashes, which need no counter and are the same after a rebuild.

### 3. Type 1 and Type 2: what each tells a report

**Idea.** With Type 2, each fact points at the version of its product that was true then, so a report can group by the category *as it was*, from the version the fact points at, or *as it is now*, from the current version of the same product, which is what a Type 1 dimension gives. They are different questions. The Kimball Type 1 page warns that after an overwrite the aggregates built on the old value must be recomputed.

**Try it.** Sum the completed lines by category both ways, and split the muffin by version:

```bash
uv run dbt show --quiet --inline "select p.category, round(sum(f.line_amount_usd), 2) as completed_usd from {{ ref('fct_order_lines') }} as f join {{ ref('dim_product') }} as p using (product_key) where f.status = 'completed' group by p.category order by p.category"
uv run dbt show --quiet --inline "select cur.category, round(sum(f.line_amount_usd), 2) as completed_usd from {{ ref('fct_order_lines') }} as f join {{ ref('dim_product') }} as p using (product_key) join {{ ref('dim_product') }} as cur on cur.product_id = p.product_id and cur.is_current where f.status = 'completed' group by cur.category order by cur.category"
uv run dbt show --quiet --inline "select p.category, count(*) as lines, round(sum(f.line_amount_usd), 2) as completed_usd from {{ ref('fct_order_lines') }} as f join {{ ref('dim_product') }} as p using (product_key) where p.product_id = 11 and f.status = 'completed' group by p.category order by p.category"
```

**Predict:** Which bakery total is higher, as it was or as it is now, and by how much?

*Why:* the bakery total as it was is higher by \$586.50, exactly the muffin's sales before April 15 (108 lines); as it is now, they sit under food. The muffin's history is the same in both; what changed is the question. The report sent in March used the category of the day, which the Type 2 dimension reproduces; a Type 1 dimension would have moved the muffin's whole past to food. A correction of a typo is a change to overwrite (Type 1); a product that moved on the menu is a change to keep the past of (Type 2). The choice is made for each attribute.

<Aside type="tip" title="Remember">

- Type 1 overwrites an attribute and loses its past; Type 2 adds a row for each version, with a start and an end.
- A snapshot turns a table that is overwritten into Type 2 history, one run at a time.
- A surrogate key is made by the warehouse; a Type 2 dimension needs one, because the natural key repeats.
- The fact joins the version true at the event: the natural key, and the time between `valid_from` and `valid_to`.

**Common trap:** joining a fact to a Type 2 dimension on the natural key alone: every version matches, and lines are counted once for each.

</Aside>

```bash
  uv run python scripts/partner_files.py $version

done
cd dbt
uv run dbt build 2>&1 | grep -E "FAIL|SKIP|Done"
```
