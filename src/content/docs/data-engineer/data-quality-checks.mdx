## The question

The owner of the cafes writes:

> The sales chart showed nothing for Saturday, March 14, and nobody told me. Can the pipeline tell me before I have to tell it?

Three lines of the staged file, as they are:

| order_item_id | ordered_at | store_id | status | quantity |
|---:|---|---:|---|---:|
| 5001 | 2026-01-01 08:02:00 | 2 | completed | 1 |
| 5002 | 2026-01-01 08:02:00 | 2 | completed | 1 |
| 5003 | 2026-01-01 08:02:00 | 2 | completed | 2 |

Nothing in the pipeline so far would notice a line with no key, a quantity of 20, or a day with no lines. By the end you can write down what the data must be, let the pipeline check it, and decide what happens to a line that breaks a rule.

## The big idea

A check is a query that returns the lines that break a rule, and a loud pipeline either stops or sets those lines aside, and says how many.

### 1. A contract, and the checks it makes

**Idea.** A **data contract** is a short file, written before the checks, that says what a table must be: its key, which columns may be empty, which values are allowed, how new it must be, how big a day is. The UK government's data quality framework names six dimensions: completeness, uniqueness, consistency, timeliness, validity and accuracy. This contract asks four, in the lesson's own mapping: uniqueness of the key, validity of values and ranges, completeness of values and of days, and timeliness. A **check** is a query that returns the lines that break a rule; the dbt documentation says the same of its data tests: no failing rows, the test passes.

**Try it.** Save the contract as `contracts/order_lines.json`:

```json
{
  "table": "order_lines",
  "producer": "the sales API",
  "key": "order_item_id",
  "columns": {
    "order_item_id": {"nullable": false},
    "order_id": {"nullable": false},
    "ordered_at": {"nullable": false},
    "store_id": {"nullable": false},
    "customer_id": {"nullable": true},
    "status": {"nullable": false, "accepted": ["completed", "canceled"]},
    "payment_method": {"nullable": false, "accepted": ["card", "mobile", "cash"]},
    "product_id": {"nullable": false},
    "quantity": {"nullable": false, "min": 1, "max": 10, "on_fail": "quarantine"},
    "discount_usd": {"nullable": false},
    "updated_at": {"nullable": false},
    "channel": {"nullable": true, "accepted": ["counter", "app"]}
  },
  "freshness_hours": 36,
  "lines_per_day": {"min": 5, "max": 50},
  "max_quarantine_share": 0.25,
  "never_silent": "a line that was read and is neither in order_lines nor in quarantine"
}
```

The code that turns a contract into checks, and runs them on a Parquet file, is a given file, `src/pipeline/checks.py`. Fetch it and read its two functions:

```bash
git show de-06-done:src/pipeline/checks.py > src/pipeline/checks.py
```

```python
def row_checks(contract):
    """One (name, action, SQL) for each rule about single rows. {t} stands for the table; the SQL returns the rows that break the rule."""
    key = contract["key"]
    checks = [(f"{key}_unique", "stop", f"SELECT {key}, count(*) AS copies FROM {{t}} GROUP BY {key} HAVING count(*) > 1")]
    for column, rule in contract["columns"].items():
        action = rule.get("on_fail", "stop")
        if not rule["nullable"]:
            checks.append((f"{column}_not_null", "stop", f"SELECT * FROM {{t}} WHERE {column} IS NULL"))
        if "accepted" in rule:
            values = ", ".join(f"'{value}'" for value in rule["accepted"])
            checks.append((f"{column}_accepted", action, f"SELECT * FROM {{t}} WHERE {column} NOT IN ({values})"))
        if "min" in rule:
            checks.append((f"{column}_in_range", action, f"SELECT * FROM {{t}} WHERE {column} NOT BETWEEN {rule['min']} AND {rule['max']}"))
    return checks + [(rule["name"], rule["on_fail"], rule["bad_rows"]) for rule in contract.get("rules", [])]


def table_checks(contract, as_of):
    """Rules about a whole table: how new its newest line is and how many lines each day holds."""
    hours, per_day = contract["freshness_hours"], contract["lines_per_day"]
    return [
        ("fresh", "warn", f"SELECT max(updated_at) AS newest FROM {{t}} HAVING max(updated_at) < TIMESTAMP '{as_of}' - INTERVAL {hours} HOUR"),
        (
            "lines_per_day",
            "warn",
            f"""
            SELECT g.day, count(t.order_item_id) AS lines
            FROM (SELECT unnest(generate_series(min(ordered_at)::DATE, max(ordered_at)::DATE, INTERVAL 1 DAY))::DATE AS day FROM {{t}}) g
            LEFT JOIN {{t}} t ON t.ordered_at::DATE = g.day
            GROUP BY g.day
            HAVING count(t.order_item_id) NOT BETWEEN {per_day['min']} AND {per_day['max']}
            """,
        ),
    ]
```

The rest of the file reads the contract and prints a report. The data ends on June 30, so the clock for `fresh` is set with `--as-of`; without it the check measures from now.

### 3. Stop or quarantine

**Idea.** A failed rule does one of two kinds of damage. If it protects the merge (a key that is empty or repeated), loading anything is unsafe, so the run **stops**. If it makes one line suspect, the line goes to a **quarantine** table with the name of the rule, and the rest loads. Too many held lines is a signal of its own: above the share the contract allows, the run stops, because that many bad lines point at the rule or the source, not at the lines.

**Try it.** The gate is a given file, `src/pipeline/gate.py`. Fetch it and read its two halves: the first stops the run before anything is written, the second sets lines aside and checks the share:

```bash
git show de-06-done:src/pipeline/gate.py > src/pipeline/gate.py
```

```python
    for name, action, sql in checks:  # stop rules first, before anything is written
        bad = con.execute(f"SELECT count(*) FROM ({sql.format(t='batch')})").fetchall()[0][0]
        if bad and action == "stop":
            raise CheckFailed(f"{name}: {bad} bad lines, the run stops")
```

```python
    clean = con.sql("""
        SELECT b.* FROM batch b
        ANTI JOIN held h ON h.order_item_id = b.order_item_id AND h.updated_at = b.updated_at
    """)
    read = con.execute("SELECT count(*) FROM batch").fetchall()[0][0]
    kept = clean.count("*").fetchall()[0][0]
    if read - kept > contract["max_quarantine_share"] * read:
        raise CheckFailed(f"{read - kept} of {read} lines would be quarantined, over the share the contract allows: look at the rule before the data")
```

The anti join keeps the lines of the batch that have no match in `held`, the table of lines the quarantine rules caught (the DuckDB documentation: an anti join returns the rows of the left table with no match in the right one). The held lines are written to the `quarantine` table only after the share check has passed, so a stopped run leaves nothing behind.

### 4. Counts that add up

**Idea.** A check can only catch what a run reports. Every run says how many lines it read, passed and held, and how many it inserted, updated and left unchanged. Two sums must hold: lines read equal clean plus held, and clean lines equal inserted plus updated plus unchanged. The failure that must never be silent is a line that was read and is nowhere: not in `order_lines` and not in quarantine. A test can assert the log line, as in DE5.

**Try it.** The tests of the gate are a given file. Fetch it and read its first test, which asserts the log line, as in DE5:

```bash

```

def test_a_line_with_a_wild_quantity_is_held_back_and_counted(con, caplog):

    assert con.execute("SELECT check_name, order_item_id FROM quarantine").fetchall() == [("quantity_in_range", 2)]

A person can read these counts, the size of the quarantine and the table checks of unit 1 without opening a row.

<Aside type="tip" title="Remember">

- A contract is written before the checks; the checks come from it.
- A check is a query for the bad lines: none, and it passes. Break the data on purpose and watch the right check fire.
- Rules that protect the merge stop the run; a rule about one line quarantines it; too many held lines stop the run.
- Lines read equal clean plus held, and clean equal inserted plus updated plus unchanged.

**Common trap:** a not-null check on a column that is empty on purpose, such as `channel` before May. It fails on every run until nobody reads it.

</Aside>

import json
from pathlib import Path

import duckdb

# The broken copy: line 5500 is sold in store 9, which is not in the stores file.
duckdb.sql("""
    COPY (
        SELECT * REPLACE (CASE WHEN order_item_id = 5500 THEN 9 ELSE store_id END AS store_id)
        FROM read_parquet('data/staging/order_lines.parquet')
    ) TO 'data/broken/unknown_store.parquet' (FORMAT parquet)

        "on_fail": "quarantine",

The check asks its question about the whole file, so one store that still has lines on other days passes it: the grain of the check is coarser than the fault. The fix asks it for each store and each day since the store opened. In a copy of the script, `exercises/de06_ex3_fix.py`, replace the colleague's query and the loop with:

```python
# A store is missing on a day when it has no line that day, counted from the day it opened.
fixed = """
    SELECT s.store_id, d.day
    FROM read_parquet('data/staging/stores.parquet') AS s
    CROSS JOIN (SELECT unnest(generate_series(DATE '2026-01-01', DATE '2026-06-30', INTERVAL 1 DAY))::DATE AS day) AS d
    WHERE d.day >= s.opened_on
      AND NOT EXISTS (SELECT 1 FROM {t} AS l WHERE l.store_id = s.store_id AND l.ordered_at::DATE = d.day)
    ORDER BY s.store_id, d.day
"""
for table in ("lines", "store_gap"):
    print(table, "- store-days with no lines:", len(con.sql(fixed.format(t=table)).fetchall()))
```
