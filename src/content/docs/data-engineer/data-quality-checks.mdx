## The question

The owner of the cafes writes:

> The sales chart showed nothing for Saturday, March 14, and nobody told me. Can the pipeline tell me before I have to tell it?

Three lines of the staged file, as they are:

| order_item_id | ordered_at | store_id | status | quantity |
|---:|---|---:|---|---:|
| 5001 | 2026-01-01 08:02:00 | 2 | completed | 1 |
| 5002 | 2026-01-01 08:02:00 | 2 | completed | 1 |
| 5003 | 2026-01-01 08:02:00 | 2 | completed | 2 |

Nothing in the pipeline so far would notice a line with no key, a quantity of 20, or a day with no lines. By the end you can write down what the data must be, let the pipeline check it, and see each check fire on data you broke on purpose.

<Aside type="note" title="You already know this">

**Match.** *Pipelines as small, testable functions* (DE5) checked the code against answers you knew by hand. The checks here do the same for the data.

**Diverge.** A test of code runs when you change the code. A check on data runs every time data arrives, and the data can change without you touching anything.

</Aside>

## The big idea

A check is a query that returns the lines that break a rule, and a contract is where those rules are written down before the data arrives.

### 1. A contract, and the checks it makes

**Idea.** A **data contract** is a short file, written before the checks, that says what a table must be: its key, which columns may be empty, which values are allowed, how new it must be, how big a day is. The Open Data Contract Standard defines a YAML format for one, with sections such as Data Quality and Service-Level Agreement; this one is a small JSON file of its own. The UK government's data quality framework names six dimensions: completeness, uniqueness, consistency, timeliness, validity and accuracy. This contract asks four, in the lesson's own mapping: uniqueness of the key, validity of values and ranges, completeness of values and of days, and timeliness. A **check** is a query that returns the lines that break a rule; the dbt documentation says the same of its data tests: no failing rows, the test passes. Each rule also names an action for when it fails: `stop`, `quarantine` or, for the table checks, `warn`. The next lesson, *Quality gates: stop a run or quarantine a line* (DE6b), makes the first two do something; here the action only shows in the report.

**Try it.** Save the contract as `contracts/order_lines.json`:

```json
{
  "table": "order_lines",
  "producer": "the sales API",
  "key": "order_item_id",
  "columns": {
    "order_item_id": {"nullable": false},
    "order_id": {"nullable": false},
    "ordered_at": {"nullable": false},
    "store_id": {"nullable": false},
    "customer_id": {"nullable": true},
    "status": {"nullable": false, "accepted": ["completed", "canceled"]},
    "payment_method": {"nullable": false, "accepted": ["card", "mobile", "cash"]},
    "product_id": {"nullable": false},
    "quantity": {"nullable": false, "min": 1, "max": 10, "on_fail": "quarantine"},
    "discount_usd": {"nullable": false},
    "updated_at": {"nullable": false},
    "channel": {"nullable": true, "accepted": ["counter", "app"]}
  },
  "freshness_hours": 36,
  "lines_per_day": {"min": 5, "max": 50},
  "max_quarantine_share": 0.25,
  "never_silent": "a line that was read and is neither in order_lines nor in quarantine"
}
```

The numbers in it (a quantity of 1 to 10, 36 hours, 5 to 50 lines a day, a quarter of the lines held) are this contract's choices, not facts of the data.

The code that turns a contract into checks, and runs them on a Parquet file, is a given file, `src/pipeline/checks.py`. Fetch it and read `row_checks`, which turns each column's rules into a query:

```bash
git show de-06-done:src/pipeline/checks.py > src/pipeline/checks.py
```

```python
def row_checks(contract):
    """One (name, action, SQL) for each rule about single rows. {t} stands for the table; the SQL returns the rows that break the rule."""
    key = contract["key"]
    checks = [(f"{key}_unique", "stop", f"SELECT {key}, count(*) AS copies FROM {{t}} GROUP BY {key} HAVING count(*) > 1")]
    for column, rule in contract["columns"].items():
        action = rule.get("on_fail", "stop")
        if not rule["nullable"]:
            checks.append((f"{column}_not_null", "stop", f"SELECT * FROM {{t}} WHERE {column} IS NULL"))
        if "accepted" in rule:
            values = ", ".join(f"'{value}'" for value in rule["accepted"])
            checks.append((f"{column}_accepted", action, f"SELECT * FROM {{t}} WHERE {column} NOT IN ({values})"))
        if "min" in rule:
            checks.append((f"{column}_in_range", action, f"SELECT * FROM {{t}} WHERE {column} NOT BETWEEN {rule['min']} AND {rule['max']}"))
    return checks + [(rule["name"], rule["on_fail"], rule["bad_rows"]) for rule in contract.get("rules", [])]
```

`table_checks`, the other function, adds two checks about the whole table: `fresh` (the newest `updated_at` must be within `freshness_hours` of the clock) and `lines_per_day` (each day, even an empty one, must hold an allowed number of lines). The rest of the file reads the contract and prints a report. The data ends on June 30, so the clock for `fresh` is set with `--as-of`; without it the check measures from now.

```bash
uv run python -m pipeline.checks data/staging/order_lines.parquet --as-of "2026-07-01 08:00:00"
```

**Predict:** How many checks does the contract make, and how many pass on the real file? Count the rules against the loop of `row_checks`, then add the two table checks.

<details>
<summary>Reveal the result</summary>

```console
$ uv run python -m pipeline.checks data/staging/order_lines.parquet --as-of "2026-07-01 08:00:00"
data/staging/order_lines.parquet
  17 of 17 checks passed
```

</details>

*Why:* 17 is one uniqueness check, ten not-null checks (twelve columns, two of them allowed to be empty), three accepted-value checks, one range check and the two table checks. The two columns that may be empty really are: one walk-in line has no `customer_id`, and 1,940 lines have no `channel`, because the API added it from May 1. A not-null check on them would fail on every run, and people stop reading a check that fails every run. The ranges are wide on purpose: the largest quantity in the file is 3, and a day holds 6 to 38 lines.

### 2. Break the data on purpose

**Idea.** A check you have never seen fail may not be able to. The given file `scripts/break_data.py` writes five copies of the staged file, each with one fault, and the checks should name each fault and nothing else.

**Try it.** Fetch the script, make the copies and check all of them:

```bash
git show de-06-done:scripts/break_data.py > scripts/break_data.py
uv run python scripts/break_data.py
uv run python -m pipeline.checks data/broken/*.parquet --as-of "2026-07-01 08:00:00"
```

**Predict:** For the copy with the missing day, which check fails and what action does it carry? Which of the five copies would stop a load?

<details>
<summary>Reveal the result</summary>

```console
$ uv run python scripts/break_data.py

data/broken/repeated_key.parquet: 3288 rows; line 5500 comes twice, with two versions

data/broken/odd_status.parquet: 3287 rows; line 5600 has the status 'completd'
data/broken/silent_day.parquet: 3272 rows; every line of March 14 is missing
$ uv run python -m pipeline.checks data/broken/*.parquet --as-of "2026-07-01 08:00:00"
data/broken/extra_zero.parquet
  FAIL quantity_in_range (quarantine): 1 bad rows, order_item_id 6952
  16 of 17 checks passed
data/broken/null_key.parquet
  FAIL order_item_id_not_null (stop): 1 bad rows, order_item_id None
  16 of 17 checks passed
data/broken/odd_status.parquet
  FAIL status_accepted (stop): 1 bad rows, order_item_id 5600
  16 of 17 checks passed
data/broken/repeated_key.parquet
  FAIL order_item_id_unique (stop): 1 bad rows, order_item_id 5500
  16 of 17 checks passed
data/broken/silent_day.parquet
  FAIL lines_per_day (warn): 1 bad rows, day 2026-03-14
  16 of 17 checks passed
```

</details>

*Why:* each copy trips one check and the other sixteen stay quiet, so a check that fires says where to look. The two table checks carry `warn`: a day with no lines does not make any line wrong, so it is a signal for a person and not a reason to refuse a load (dbt's source freshness has the same two levels, `warn_after` and `error_after`). A sixth fault is not in any file: the source stopped delivering. Run the clean file with the clock four days later:

```bash
uv run python -m pipeline.checks data/staging/order_lines.parquet --as-of "2026-07-05 08:00:00"
```

```console
$ uv run python -m pipeline.checks data/staging/order_lines.parquet --as-of "2026-07-05 08:00:00"
data/staging/order_lines.parquet
  FAIL fresh (warn): 1 bad rows, newest 2026-06-30 16:35:00
  16 of 17 checks passed
```

<Aside type="tip" title="Remember">

- A contract is written before the checks; the checks come from it.
- A check is a query for the bad lines: none, and it passes. Break the data on purpose and watch the right check fire.
- Each rule carries an action, and the report names it; the table checks (freshness, lines a day) carry `warn`.

**Common trap:** a not-null check on a column that is empty on purpose, such as `channel` before May. It fails on every run until nobody reads it.

</Aside>

**A line updated before it was ordered.** Before you start, say in one sentence what the report will look like. Then, from a blank file `exercises/de06_ex2.py`, write the two things the check needs: a broken copy `data/broken/updated_early.parquet` in which line 5500 was updated a day before it was ordered, and a copy of the contract, `exercises/de06_ex2_contract.json`, with a rule that returns the lines whose `updated_at` is earlier than their `ordered_at`. Give it the action `stop`. Run the checks on the broken copy with your contract. Expected: one check fails, and it names line 5500.

<details>
<summary>Hint</summary>

Write the contract copy from Python: `json.loads` the original, set `contract["rules"]`, and write it with `json.dumps`. The broken copy is a `COPY (...) TO ... (FORMAT parquet)` with a `REPLACE`, as in `scripts/break_data.py`.

</details>

<details>
<summary>Half-solution</summary>

Expected output in words: *"One line of the broken copy fails my rule, the report shows the name of the rule, `stop` and order_item_id 5500, and the other 17 checks pass."*

```python
contract["rules"] = [{"name": "updated_after_ordered", "on_fail": "stop", "bad_rows": "SELECT * FROM {t} WHERE ..."}]
```

</details>

<Solution>

```python
import json
from pathlib import Path

import duckdb

# The broken copy: line 5500 was updated a day before it was ordered.
duckdb.sql("""
    COPY (
        SELECT * REPLACE (CASE WHEN order_item_id = 5500 THEN ordered_at - INTERVAL 1 DAY ELSE updated_at END AS updated_at)
        FROM read_parquet('data/staging/order_lines.parquet')
    ) TO 'data/broken/updated_early.parquet' (FORMAT parquet)
""")

# The rule, as a copy of the contract. Nothing downstream should read a line with an impossible history, so it stops the run.
contract = json.loads(Path("contracts/order_lines.json").read_text())
contract["rules"] = [
    {"name": "updated_after_ordered", "on_fail": "stop", "bad_rows": "SELECT * FROM {t} WHERE updated_at < ordered_at"}
]
Path("exercises/de06_ex2_contract.json").write_text(json.dumps(contract, indent=2))
```

```console
$ uv run python exercises/de06_ex2.py
$ uv run python -m pipeline.checks data/broken/updated_early.parquet --contract exercises/de06_ex2_contract.json --as-of "2026-07-01 08:00:00"
data/broken/updated_early.parquet
  FAIL updated_after_ordered (stop): 1 bad rows, order_item_id 5500
  17 of 18 checks passed
```

A rule that compares two columns of one row needs no new code in `checks.py`: any query that returns the bad rows is a check.

</Solution>

<Exercise id="data-engineer-data-quality-checks-3">

**Spot the flaw.** A colleague writes a check for a missing store: a store is missing when it has no lines in the file. Save the script as `exercises/de06_ex3.py`, run it and read the two lines. In the second table the lines of store 1 are gone for the week of March 9 to 15. Expected: two lines. What is wrong with the check, and what is the fix? Write the fixed query and run it. Expected: 0 rows for the real file and 7 for the second.

```python
import duckdb

con = duckdb.connect()
con.execute("CREATE VIEW lines AS SELECT * FROM read_parquet('data/staging/order_lines.parquet')")
# The week of March 9 to 15 without a single line of store 1: the till of Old Town sent nothing.
con.execute("""
    CREATE VIEW store_gap AS
    SELECT * FROM lines WHERE NOT (store_id = 1 AND ordered_at::DATE BETWEEN DATE '2026-03-09' AND DATE '2026-03-15')
""")

# A colleague's check: a store is missing when it has no lines in the file.
colleague = """
    SELECT s.store_id FROM read_parquet('data/staging/stores.parquet') AS s
    WHERE s.store_id NOT IN (SELECT store_id FROM {t})
"""
for table in ("lines", "store_gap"):
    print(table, "- stores with no lines:", con.sql(colleague.format(t=table)).fetchall())
```

<details>
<summary>Hint</summary>

Ask what a week without a store looks like to a check of the whole file. Then list the days since each store opened. Store 3 opened on April 1, so the days before that are not missing.

</details>

<details>
<summary>Half-solution</summary>

Put every day from January 1 to June 30 beside every store, keep the days from `opened_on` on, and keep the pairs with no line:

```sql
SELECT s.store_id, d.day
FROM stores AS s CROSS JOIN days AS d
WHERE d.day >= s.opened_on AND NOT EXISTS (...)
```

</details>

<Solution>

```console
$ uv run python exercises/de06_ex3.py
lines - stores with no lines: []
store_gap - stores with no lines: []
```

The check asks its question about the whole file, so one store that still has lines on other days passes it: the grain of the check is coarser than the fault. The fix asks it for each store and each day since the store opened. In a copy of the script, `exercises/de06_ex3_fix.py`, replace the colleague's query and the loop with:

```python
# A store is missing on a day when it has no line that day, counted from the day it opened.
fixed = """
    SELECT s.store_id, d.day
    FROM read_parquet('data/staging/stores.parquet') AS s
    CROSS JOIN (SELECT unnest(generate_series(DATE '2026-01-01', DATE '2026-06-30', INTERVAL 1 DAY))::DATE AS day) AS d
    WHERE d.day >= s.opened_on
      AND NOT EXISTS (SELECT 1 FROM {t} AS l WHERE l.store_id = s.store_id AND l.ordered_at::DATE = d.day)
    ORDER BY s.store_id, d.day
"""
for table in ("lines", "store_gap"):
    print(table, "- store-days with no lines:", len(con.sql(fixed.format(t=table)).fetchall()))
```

```console
$ uv run python exercises/de06_ex3_fix.py
lines - store-days with no lines: 0
store_gap - store-days with no lines: 7
```

Without the `opened_on` condition the real file would show 90 days for store 3, before it opened, and a check that is red on every run is the trap of unit 1 again.

</Solution>
