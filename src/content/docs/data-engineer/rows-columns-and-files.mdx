## The big idea

A table is stored one row at a time or one column at a time, and a row store makes a whole row cheap while a column store makes a whole column cheap.

### 1. The bytes a query needs

**Idea.** The PostgreSQL documentation says every table is stored as an array of pages of a fixed size, usually 8 kB, and that in a table an item on a page is a row. Apache Parquet is a column-oriented file format, and the DuckDB documentation says it can push projections into Parquet file scans. The aggregation below needs five of the twelve columns: `store_id`, `status`, `quantity`, `unit_price_usd` and `discount_usd`.

```sql
SELECT store_id, sum(quantity * unit_price_usd - discount_usd) AS revenue
FROM lines_big WHERE status = 'completed' GROUP BY store_id ORDER BY store_id;
```

**Try it.** The script above wrote the lines as one Parquet file and printed the bytes of each column. In `psql`, count the pages the aggregation touches (`\pset footer off` first, then run it twice and read the second `Buffers` line of the scan):

```sql
EXPLAIN (ANALYZE, BUFFERS, TIMING OFF, SUMMARY OFF)
SELECT store_id, sum(quantity * unit_price_usd - discount_usd) AS revenue
FROM lines_big WHERE status = 'completed' GROUP BY store_id ORDER BY store_id;
```

**Predict:** What share of the Parquet file's column bytes do the five columns take: about 7 percent, 40 percent or 80 percent? And does PostgreSQL touch about 1,000 pages, or the whole table?

*Why:* the five columns take 1,042,799 of the 14,499,086 bytes in the column chunks (the summed compressed sizes; the file itself has 14,512,102), 7.2 percent, although they are five of twelve columns: a column that holds a few repeated values (`status`, `store_id`, `discount_usd`) compresses to almost nothing. PostgreSQL's scan touched 3,860 + 7,684 = 11,544 pages, which is every page of the table (`SELECT relpages FROM pg_class WHERE relname = 'lines_big'` prints 11,544, about 90 MB), because each page holds whole rows of all twelve columns, and a row store therefore reads whole pages of whole rows. The split between `hit` and `read` changes from run to run; their sum does not. DuckDB's own file format also stores row groups, which its documentation calls equivalent to Parquet's, and the Parquet sizes here are an illustration of column storage, not a measurement of DuckDB's own file. University database courses give whole lectures to these layouts: the schedule of CMU 15-445 lists one titled "Storage Models & Compression".

### 2. Two questions, two winners

**Idea.** The same table sits in all three engines, loaded from the same CSV file with a primary key on `order_item_id`. Two questions can be asked of it: an aggregation over a whole column, and the lookup of one line by its key. The script `storage_shapes.py` times both, in Python, for each engine.

**Try it.** The aggregation first (median of seven runs after one warm-up), then 2,000 single-line lookups with keys drawn from seed 2026:

```bash
uv run --with duckdb==2.0.0 --with "psycopg[binary]==3.3.9" python storage_shapes.py aggregation
uv run --with duckdb==2.0.0 --with "psycopg[binary]==3.3.9" python storage_shapes.py lookup
```

The first call builds `lab/lines.duckdb` and `lab/lines.sqlite` from the CSV file, which takes a few seconds.

*Why:* the order reverses. DuckDB finished the aggregation in 7.7 ms against 332.9 for PostgreSQL, 43 times faster, and SQLite took 338.1. ### 3. A database file you can read

**Idea.** SQLite keeps a whole database in one file made of pages. Its documentation gives the first 100 bytes of the file as a header: the string `SQLite format 3` at offset 0, the page size in the two bytes at offset 16, the size of the file in pages at offset 28 and the text encoding at offset 56 (1 means UTF-8), all as big-endian numbers. It adds that page 1 is always a table b-tree, the one that holds the schema, and that the pages of a b-tree have a header, a pointer array and a cell content area.

**Try it.** Save this as `read_header.py`. It builds a small database of the three cafes, asks SQLite which page holds the table, and reads the header from the raw bytes:

```python
import sqlite3

con = sqlite3.connect("stores.sqlite")
con.execute("CREATE TABLE stores (store_id INTEGER PRIMARY KEY, store_name TEXT, city TEXT, opened_on TEXT)")
con.executemany("INSERT INTO stores VALUES (?, ?, ?, ?)", [
    (1, "Old Town", "Oakland", "2023-05-12"), (2, "Campus", "Berkeley", "2024-09-03"), (3, "Harbor", "Alameda", "2026-04-01")])
con.commit()
print(con.execute("SELECT name, rootpage FROM sqlite_schema").fetchall())
con.close()

data = open("stores.sqlite", "rb").read()
print(len(data), data[:16])
print("page size", int.from_bytes(data[16:18], "big"), "pages in header", int.from_bytes(data[28:32], "big"),
      "text encoding", int.from_bytes(data[56:60], "big"))
```

Run it with `uv run python read_header.py`.

**Predict:** How many bytes does the file have, and which page holds the rows of `stores`?

<details>
<summary>Reveal the result</summary>

```console
$ uv run python read_header.py
[('stores', 2)]
8192 b'SQLite format 3\x00'
page size 4096 pages in header 2 text encoding 1
```

</details>

*Why:* the file has 8,192 bytes, two pages of 4,096 (2 × 4,096), the header says so, and the rows of `stores` are on page 2: page 1 holds the header and the schema table. The default page size is 4,096 in the SQLite that Python 3.13 carried here (3.53.1); other versions may differ, and the header would say so. Now look for text inside the file, and see where the rows are (add these lines to `read_header.py` and run it again):

```python
import re
print([m.group().decode() for m in re.finditer(rb"[ -~]{6,}", data)])
```

**Predict:** In which order do the three cafes appear in the file?

<details>
<summary>Reveal the result</summary>

</details>

*Why:* page 1 holds the text of the `CREATE TABLE` statement, and the three rows are on page 2 with their bytes packed together, row after row, with no names of columns beside them: the schema is stored once, on page 1. Harbor, the last row inserted, comes first in the file and Old Town, the first, comes last, so in this run the rows filled the page from its end towards its front; the documentation's layout of a page puts the cell content area after the cell pointer array and the unallocated space, which fits it, but it does not say in which order cells are placed. Delete `stores.sqlite` when you are done.

<Aside type="tip" title="Remember">

- A row store keeps whole rows on a page and reads whole pages; a column store keeps each column together and reads the columns a query names.
- Compression is strongest on columns with few distinct values, which is why a few columns can be a small part of the bytes.
- The same table answered a whole-column question fastest in the column store and a one-line lookup fastest in a row store here; read the direction, because the sizes carry the machine's fixed costs.
- A SQLite database is a file of pages, and its first 100 bytes say how big they are and how many there are.

**Common trap:** a timing quoted without saying what it includes.

</Aside>

**Spot the flaw.** A colleague writes the benchmark below to see how much faster DuckDB is than PostgreSQL on the aggregation of unit 1, runs it twice, and writes in the notes: "the column store is only about twice as fast, so it is not worth a second system." Save it as `flawed_benchmark.py`, run it from the folder that holds `lab/`, and compare the number with unit 2's. Expected: one line each time. What is wrong with the measurement?

```python
import statistics
import time

import duckdb
import psycopg

AGG = """SELECT store_id, sum(quantity * unit_price_usd - discount_usd) AS revenue
FROM {src} WHERE status = 'completed' GROUP BY store_id"""


def median_ms(run, runs=7):
    run()  # warm-up
    times = []
    for _ in range(runs):
        start = time.perf_counter()
        run()
        times.append((time.perf_counter() - start) * 1000)
    return statistics.median(times)


duck = duckdb.connect()
pg = psycopg.connect(dbname="lab", autocommit=True)
duck_ms = median_ms(lambda: duck.execute(AGG.format(src="read_csv('lab/big/lines_big.csv')")).fetchall())
pg_ms = median_ms(lambda: pg.execute(AGG.format(src="lines_big")).fetchall())
print(f"DuckDB {duck_ms:.0f} ms, PostgreSQL {pg_ms:.0f} ms: DuckDB is {pg_ms / duck_ms:.1f} times faster")
```
