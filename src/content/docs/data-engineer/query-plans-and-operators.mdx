## The question

The owner of the three cafes asks the data engineer:

> The report for Harbor before April came back with no rows, and the database printed a plan for it. Can I trust a plan?

The table in question holds the first three of 1,800 orders:

| order_id | customer_id | store_id | ordered_at | status | payment_method |
|---:|---:|---:|---|---|---|
| 1001 | 15 | 2 | 2026-01-01 08:02:00 | completed | mobile |
| 1002 | 46 | 1 | 2026-01-01 15:38:00 | completed | mobile |
| 1003 | 61 | 2 | 2026-01-01 15:47:00 | completed | mobile |

By the end you can set what a plan expects beside what it found, say where the expectation comes from, and tell two joins in a different order apart by their cost.

## The big idea

A plan is a tree of boxes, and every box carries a guess: how many rows the planner expects to come out of it.

### 1. The planner's guess beside the real count

**Idea.** `EXPLAIN` prints a plan with the number of rows the planner expects from each node, and the PostgreSQL documentation says the rows value is the number a node emits, estimated. `EXPLAIN ANALYZE` adds the true row counts of each node beside the estimates, and the documentation calls the question of whether the estimated counts are reasonably close to reality the thing that is usually most important to look for. DuckDB marks its estimates with a `~`.

**Try it.** In `psql`, the orders of store 3 placed before April 1 (`TIMING OFF` and `SUMMARY OFF` leave out the times, which this lesson does not read):

```sql
EXPLAIN (ANALYZE, TIMING OFF, SUMMARY OFF)
SELECT * FROM orders WHERE store_id = 3 AND ordered_at < '2026-04-01';
```

**Predict:** What does the scan expect (`rows=`), and how many rows does it find (`actual rows=`)? Is the planner's number the larger?

<details>
<summary>Reveal the result</summary>

```console
                                            QUERY PLAN
--------------------------------------------------------------------------------------------------
 Seq Scan on orders  (cost=0.00..43.00 rows=142 width=34) (actual rows=0 loops=1)
   Filter: ((ordered_at < '2026-04-01 00:00:00'::timestamp without time zone) AND (store_id = 3))
   Rows Removed by Filter: 1800
```

</details>

*Why:* the planner expected 142 rows and found 0. The `stores` table says Harbor opened on 2026-04-01, so it has no orders before April, but the planner does not know that two conditions are linked. The documentation says the planner normally assumes that multiple conditions are independent, and multiplies their chances: Harbor has 355 of the 1,800 orders and 718 orders are from before April, so $$355 \times 718 / 1800 = 141.6$$, which prints as 142. DuckDB makes its own guess, by a different rule that its source code shows: for an equality test such as `store_id = 3` it divides the table's row count by the number of distinct values it has recorded for that column (an approximate count that the table keeps for the column), and for a filter that is not an equality it takes a fixed 20 percent of the rows. Here the recorded count for `store_id` is 2 although there are 3 stores, so the guess is 1,800 / 2 = 900, and the date condition does not change it. It is a guess from summaries, as in PostgreSQL, not a look at the rows. In the editor, the first block prints the plan with `~` estimates and the second the plan with true counts. Expected: the scan box ends with `~900 rows` in the first plan and with `0 rows` in the second (the page's engine and DuckDB 2.0.0 print the same two numbers):

<RunSQL query={`EXPLAIN SELECT * FROM orders WHERE store_id = 3 AND ordered_at < '2026-04-01';`} />

<RunSQL query={`EXPLAIN ANALYZE SELECT * FROM orders WHERE store_id = 3 AND ordered_at < '2026-04-01';`} />

Two engines, two different wrong numbers, one right count. A plan tells you what the planner believes, and `EXPLAIN ANALYZE` tells you where the belief is wrong.

### 2. Where the guess comes from

**Idea.** PostgreSQL keeps statistics: the planner's guesses come from the number of rows of each table and from a summary of each column (the most common values and how often they occur), and the `ANALYZE` command collects them. The table `orders_fresh` below is a copy of `orders` whose automatic upkeep is switched off, so nothing has collected its statistics yet.

**Try it.** In `psql`:

```sql
CREATE TABLE orders_fresh (LIKE orders) WITH (autovacuum_enabled = false);
INSERT INTO orders_fresh SELECT * FROM orders;
EXPLAIN (ANALYZE, TIMING OFF, SUMMARY OFF) SELECT * FROM orders_fresh WHERE payment_method = 'cash';
ANALYZE orders_fresh;
EXPLAIN (ANALYZE, TIMING OFF, SUMMARY OFF) SELECT * FROM orders_fresh WHERE payment_method = 'cash';
```

**Predict:** For cash orders, what does the first plan expect, and what does the second expect?

<details>
<summary>Reveal the result</summary>

```console
                                       QUERY PLAN
----------------------------------------------------------------------------------------
 Seq Scan on orders_fresh  (cost=0.00..30.40 rows=6 width=84) (actual rows=253 loops=1)
   Filter: (payment_method = 'cash'::text)
   Rows Removed by Filter: 1547

ANALYZE
                                        QUERY PLAN
------------------------------------------------------------------------------------------
 Seq Scan on orders_fresh  (cost=0.00..38.50 rows=253 width=34) (actual rows=253 loops=1)
   Filter: (payment_method = 'cash'::text)
   Rows Removed by Filter: 1547
```

</details>

*Why:* before `ANALYZE` the planner expected 6 rows and found 253; after it, the estimate is 253. The PostgreSQL documentation says `ANALYZE` collects statistics about the contents of tables and stores them where the planner reads them. You can see the first gap in the catalog too: `SELECT reltuples FROM pg_class WHERE relname = 'orders_fresh'` prints -1, which the documentation reads as a row count that is unknown because the table has never been vacuumed or analyzed. In the default setup a background process (autovacuum) analyzes tables for you, which is why most plans are not like the first one. Drop the copy with `DROP TABLE orders_fresh;`.

### 3. Join order changes the cost, not the rows

**Idea.** For inner joins the PostgreSQL documentation says the planner is free to join the tables in any order, and that the possibilities give semantically equivalent results but might have hugely different execution costs. The setting `join_collapse_limit = 1` makes the planner follow the order you wrote the joins in, so you can ask for two orders and compare. A join has two inputs, and the cost of the next join depends on how many rows the lower one sends up.

**Try it.** Units sold at Harbor for each category, joined in two written orders. Run both (the second starts from `order_items`):

```sql
SET join_collapse_limit = 1;
EXPLAIN (ANALYZE, TIMING OFF, SUMMARY OFF)
SELECT p.category, sum(i.quantity) AS units
FROM orders o
JOIN order_items i ON i.order_id = o.order_id
JOIN products p ON p.product_id = i.product_id
WHERE o.store_id = 3
GROUP BY p.category;

EXPLAIN (ANALYZE, TIMING OFF, SUMMARY OFF)
SELECT p.category, sum(i.quantity) AS units
FROM order_items i
JOIN products p ON p.product_id = i.product_id
JOIN orders o ON o.order_id = i.order_id
WHERE o.store_id = 3
GROUP BY p.category;
```

**Predict:** In each plan, how many rows does the lower of the two joins send up to the join above it? And which plan has the lower cost on the top line?

<Aside type="tip" title="Remember">

- Every node of a plan shows the rows the planner expects; `EXPLAIN ANALYZE` adds the rows it found. A large gap is the clue.
- PostgreSQL's estimates come from statistics that `ANALYZE` collects for each column; a table that was never analyzed has none.
- The planner multiplies the chances of separate conditions as if they were independent.
- Inner joins in any order return the same rows; the cost follows the number of rows each join sends up.

**Common trap:** reading a plan's cost and ignoring its row counts. A cost is the planner's estimate in its own units, and the rows beside it say whether the estimate rests on the data.

</Aside>

**Join order on three other tables.** The orders of gold-tier customers, with the city of each store, joined in the order customers, orders, stores. ## On your own

<Exercise id="data-engineer-query-plans-and-operators-2">

**One week of orders.** A report filters the orders of the week of May 11 with `date_trunc('week', ordered_at) = '2026-05-11'`. Before you start, say in one sentence whether you expect the planner's estimate for this filter to be close. From a blank file or the `psql` prompt, run `EXPLAIN (ANALYZE, TIMING OFF, SUMMARY OFF)` on it, then write the same filter as a range of `ordered_at` and run that. Expected: two plans, each with `rows=` and `actual rows=` on the scan.

<details>
<summary>Hint</summary>

A week starting on May 11 ends before May 18. Write the second filter with `>=` and `<` on the bare column.

</details>

<details>
<summary>Half-solution</summary>

Expected output in words: *"In the first plan the estimate is far below the actual rows; in the second it equals them."*

```sql
WHERE ordered_at >= '2026-05-11' AND ordered_at < ...
```

</details>

<Solution>

```sql
EXPLAIN (ANALYZE, TIMING OFF, SUMMARY OFF)
SELECT * FROM orders WHERE date_trunc('week', ordered_at) = '2026-05-11';

EXPLAIN (ANALYZE, TIMING OFF, SUMMARY OFF)
SELECT * FROM orders WHERE ordered_at >= '2026-05-11' AND ordered_at < '2026-05-18';
```

```console
 Seq Scan on orders  (cost=0.00..43.00 rows=9 width=34) (actual rows=86 loops=1)
   Filter: (date_trunc('week'::text, ordered_at) = '2026-05-11 00:00:00'::timestamp without time zone)
   Rows Removed by Filter: 1714

 Seq Scan on orders  (cost=0.00..43.00 rows=86 width=34) (actual rows=86 loops=1)
   Filter: ((ordered_at >= '2026-05-11 00:00:00'::timestamp without time zone) AND (ordered_at < '2026-05-18 00:00:00'::timestamp without time zone))
   Rows Removed by Filter: 1714
```

The statistics are kept for the column `ordered_at`, not for the value of a function of it, so the first filter gets a fixed guess: 9 rows, which is 0.5 percent of 1,800 (the filters on `extract(month ...)` and `ordered_at::date` also got 9 in the run behind this lesson). The range uses the column's own statistics and the estimate equals the 86 rows found. The rows are the same either way; only what the planner believes changed.

</Solution>

<Exercise id="data-engineer-query-plans-and-operators-3">

**Spot the flaw.** A colleague wants to know what a cleanup costs before running it, so she types the line below on a scratch copy of the orders (a throwaway copy made only for trying things), reads the plan, and then runs the real `DELETE` on the same copy, which reports `DELETE 0`. She says the database is broken. Run her steps. Expected: one plan and a count. What went wrong, and how do you look at the plan without changing the table?

```sql
CREATE TABLE orders_scratch AS SELECT * FROM orders;
EXPLAIN (ANALYZE, TIMING OFF, SUMMARY OFF) DELETE FROM orders_scratch WHERE store_id = 3;
SELECT count(*) AS harbor_orders FROM orders_scratch WHERE store_id = 3;
```

<details>
<summary>Hint</summary>

Look at the count after her first plan, before she runs anything else. Then read the top line of the plan.

</details>

<details>
<summary>Half-solution</summary>

```sql
BEGIN;
EXPLAIN (ANALYZE, ...) DELETE ...;
...
```

</details>

<Solution>

```console
                                          QUERY PLAN
-----------------------------------------------------------------------------------------------
 Delete on orders_scratch  (cost=0.00..30.40 rows=0 width=0) (actual rows=0 loops=1)
   ->  Seq Scan on orders_scratch  (cost=0.00..30.40 rows=6 width=6) (actual rows=355 loops=1)
         Filter: (store_id = 3)
         Rows Removed by Filter: 1445


 harbor_orders
---------------
             0
```

The count is already 0 before her `DELETE`: `EXPLAIN ANALYZE` carried the statement out (the scan found 355 rows and the `Delete` node removed them). The PostgreSQL documentation says that because it actually runs the query, any side effects happen as usual, and it shows the remedy: begin a transaction, run `EXPLAIN ANALYZE`, and `ROLLBACK`. After `BEGIN; EXPLAIN (ANALYZE, TIMING OFF, SUMMARY OFF) DELETE ...; ROLLBACK;` the same count prints 355. Plain `EXPLAIN` without `ANALYZE` shows only estimates and changes nothing. (The first plan's `rows=6` is the guess of a table that was never analyzed, as in unit 2.)

</Solution>
