## The question

The owner writes:

> Two of us asked for sales by store and day, and got different totals. Can the logic live in one place, where someone can read it and check it?

The staged files the pipeline lands are the source. The store file is three lines:

| store_id | store_name | city | opened_on |
|---:|---|---|---|
| 1 | Old Town | Oakland | 2023-05-12 |
| 2 | Campus | Berkeley | 2024-09-03 |
| 3 | Harbor | Alameda | 2026-04-01 |

By the end you can build, from the staged Parquet files, a table of sales for each store and each day in a dbt project, and say what one row of every model stands for.

<Aside type="note" title="You already know this">

**Match.** [*Readable queries with CTEs*](/sql/ctes/) (S24) split a long query into named steps. A dbt model is one such step, saved as a file that other models can build on.

**Diverge.** A CTE lives inside one query. A model is a file of its own, in Git, with a name that other files call.

</Aside>

## The big idea

A dbt project is SQL written as files, each one a `select` that names what it reads, so that the order, the history and the review are all in plain text.

### 1. A project of files

**Idea.** **Transformation as code** means each table is made by a SQL file in version control, so a change is a diff that someone reviews, and tests (DE10) can run on every change. dbt is the program that turns the files into tables. It needs two settings files in the project folder: `dbt_project.yml` names the project, and `profiles.yml` says where to build, here a DuckDB file. dbt-duckdb, the adapter that lets dbt work on DuckDB, takes the `path` of the file relative to `profiles.yml`.

**Try it.** dbt goes into the starter's main environment, pinned: `pyproject.toml` and `uv.lock` are given files. Fetch them, install, make the project folder and save the two settings files:

```bash
git show de-09-done:pyproject.toml > pyproject.toml
git show de-09-done:uv.lock > uv.lock
uv sync
mkdir -p dbt/models/staging dbt/models/intermediate dbt/models/marts
```

The two lines the first file adds, in `dependencies`:

```toml
    "dbt-core==1.12.6",
    "dbt-duckdb==1.11.1",
```

Save `dbt/dbt_project.yml`:

```yaml
name: cafe
version: "0.1.0"
profile: cafe

flags:
  send_anonymous_usage_stats: false
  use_colors: false

model-paths: ["models"]
test-paths: ["tests"]

models:
  cafe:
    staging:
      +materialized: view
    intermediate:
      +materialized: view
    marts:
      +materialized: table
```

Save `dbt/profiles.yml`:

```yaml
cafe:
  target: dev
  outputs:
    dev:
      type: duckdb
      path: ../data/serving/analytics.duckdb
      threads: 1
```

Also fetch `dbt/.gitignore`, which keeps dbt's `target/` and `logs/` out of Git, and ask dbt to check the project, from the `dbt` folder. Every dbt command of this lesson runs from there:

```bash

cd dbt
uv run dbt debug 2>&1 | grep -E "OK|ERROR|All checks|FAIL"
```

**Predict:** `dbt debug` checks the files, a tool and a connection. Which four checks print OK, and what is the last line?

*Why:* dbt found both settings files, found Git (it records which commit a build came from), and opened the DuckDB file named in the profile; the connection test would fail on a wrong path. The `models` block says how each folder is built: staging and intermediate models as views, which are saved queries, and marts as tables, which are stored results. The names `staging`, `intermediate` and `marts` are the layers the dbt guide recommends: building blocks from source data, then logic that prepares them to join, then the tables the organization cares about.

### 2. A source and a staging model

**Idea.** A **source** is a table dbt did not build, declared once in YAML and read with `source()`. Here the sources are the three Parquet files of the staging layer: the dbt-duckdb README says an `external_location` under `meta` gives a pattern for the location of every table of the source, with `{name}` replaced by the table's name. A **staging model** takes one source and does only light work: it renames, casts and cleans, and it keeps every row.

**Try it.** Save `dbt/models/staging/sources.yml`:

```yaml
version: 2

sources:
  - name: pipeline
    meta:
      external_location: "../data/staging/{name}.parquet"
    tables:
      - name: order_lines
      - name: products
      - name: stores
```

Save `dbt/models/staging/stg_order_lines.sql`. It renames the key and the quantity, takes the day out of the timestamp and lowercases the status:

```sql
-- Grain: one row for each order line, the latest version of it that the pipeline staged.
select
    order_item_id as order_line_id,
    order_id,
    ordered_at,
    cast(ordered_at as date) as order_date,
    store_id,
    customer_id,
    lower(status) as status,
    payment_method,
    product_id,
    quantity as units,
    discount_usd,
    updated_at
from {{ source('pipeline', 'order_lines') }}
```

The staging models of the other two files have the same shape and are given:

```bash
git show de-09-done:dbt/models/staging/stg_products.sql > models/staging/stg_products.sql
git show de-09-done:dbt/models/staging/stg_stores.sql > models/staging/stg_stores.sql
uv run dbt run --select staging 2>&1 | grep -E "Found|OK created|Done"
cat target/compiled/cafe/models/staging/stg_stores.sql
```

**Predict:** How many models and sources does dbt find, and what does the `source()` in `stg_stores` turn into in the compiled file?

*Why:* three models and three sources, each built as a view. dbt wrote the compiled file by replacing `{{ source('pipeline', 'stores') }}` with the path of the Parquet file, so a model is a template and the compiled SQL is what DuckDB ran. The times are those of one run here. The staging model keeps all 3,287 lines: it renames `order_item_id` to `order_line_id` so that later models speak of lines, and it cleans nothing away.

### 3. `ref` and the order of the models

**Idea.** A model that reads another model writes `ref('name')` in place of a table name. The dbt documentation says dbt uses `ref` to determine the order to run the models, by building a directed acyclic graph, the same shape as the DAG of DE7. You never write the order down; the calls give it.

**Try it.** Save the intermediate model `dbt/models/intermediate/int_order_lines_priced.sql`. It joins each line to its product and computes the amount of the line:

```sql
-- Grain: one row for each order line, with its product and the amount of the line.
select
    l.order_line_id,
    l.order_date,
    l.store_id,
    l.status,
    l.units,
    p.product_name,
    p.category,
    l.units * p.unit_price_usd - l.discount_usd as line_amount_usd
from {{ ref('stg_order_lines') }} as l
join {{ ref('stg_products') }} as p using (product_id)
```

Save the mart `dbt/models/marts/fct_store_daily_sales.sql`. It counts completed lines and adds their units and amounts for each store and each day:

```sql
-- Grain: one row for each store and each day on which it sold something. Completed lines only.
select
    l.store_id,
    s.store_name,
    l.order_date,
    count(*) as lines,
    sum(l.units) as units,
    sum(l.line_amount_usd) as sales_usd
from {{ ref('int_order_lines_priced') }} as l
join {{ ref('stg_stores') }} as s using (store_id)
where l.status = 'completed'
group by l.store_id, s.store_name, l.order_date
```

Build everything, and ask dbt which models and sources the mart rests on:

```bash
uv run dbt build 2>&1 | grep -E "Found|OK created|Done"
uv run dbt ls --quiet --select +fct_store_daily_sales
```

**Predict:** In which order does `dbt build` make the five models, and which one is a table? What does the `+` in front of the mart's name select?

The `+` before a name selects the model and everything it depends on, back to the sources: the mart rests on four models and three sources. `build` also runs tests, and DE10 adds some; here there are none.

### 4. The grain of each model

**Idea.** The **grain** of a table says what one row stands for. The Kimball Group calls declaring it the pivotal step in a dimensional design, because it establishes exactly what a single fact table row represents. Every model of the project states its grain in the comment on its first line, and the check is that rows equal different grains: a model whose grain is broken counts something twice.

**Try it.** `dbt_counts.py` counts the rows of three models and the different values of each one's grain. It is a given file, and it runs from the `dbt` folder, because the staging views read the Parquet files by a path relative to it:

```bash
git show de-09-done:scripts/dbt_counts.py > ../scripts/dbt_counts.py
uv run python ../scripts/dbt_counts.py
```

**Predict:** How many rows does each of the three models have? Harbor opened on April 1 and the other two stores sold on all 181 days of January to June.

<details>
<summary>Reveal the result</summary>

```console
$ uv run python ../scripts/dbt_counts.py
stg_order_lines: 3287 rows, 3287 different grains
int_order_lines_priced: 3287 rows, 3287 different grains
fct_store_daily_sales: 453 rows, 453 different grains
```

</details>

*Why:* 3,287 order lines in the first two models, and 453 store-days in the mart: 181 days for each of two stores and the 91 days that Harbor was open. One of the 3,287 lines is canceled, so the mart counts 3,286 lines in its `lines` column. The mart's grain is coarser than the line's, and each mart row is the sum of its lines. The sales in the mart come to $22,625.75; this is the API's total, with its 12 corrected lines, and not the total of the cafe-sales files.

<Aside type="tip" title="Remember">

- A dbt model is a `select` in a file; `source()` reads what dbt did not build and `ref()` reads another model.
- `ref` gives the build order, so the order is never written down.
- A staging model renames, casts and cleans one source and keeps every row.
- Every model states its grain in its first comment, and rows equal different grains.

**Common trap:** a mart that reads staging through a join on the wrong key, which counts a line more than once and still builds without an error.

</Aside>

<Exercise id="data-engineer-dbt-project-and-first-model-3">

**Spot the flaw.** A colleague shortens `stg_stores.sql`: the last line becomes `from read_parquet('../data/staging/stores.parquet')`, with no `source()`. "It builds and the counts are the same, so the shortcut is fine." Make the change, build, run the counts, and then ask dbt which models rest on the source `stores`. Expected: a passing build, the same three counts, and a difference in the last command. What was lost? Put the `source()` line back when you are done.

```bash
uv run dbt ls --quiet --select source:pipeline.stores+ --resource-type model
sed -i "s#from {{ source('pipeline', 'stores') }}#from read_parquet('../data/staging/stores.parquet')#" models/staging/stg_stores.sql
uv run dbt build 2>&1 | grep -E "Found|Done"
uv run python ../scripts/dbt_counts.py
uv run dbt ls --quiet --select source:pipeline.stores+ --resource-type model
```

<details>
<summary>Hint</summary>

Run the first `dbt ls` before the edit and the last one after it, and compare the two lists. On macOS, `sed -i` needs an empty argument after it (`sed -i ''`), or make the edit in your editor.

</details>

<details>
<summary>Half-solution</summary>

Compare the two lists: the models that rest on the source `stores` before and after the edit. A model that dbt cannot see depending on a source is one that no selection of the source reaches.

</details>

<Solution>

```console
$ uv run dbt ls --quiet --select source:pipeline.stores+ --resource-type model
cafe.marts.fct_store_daily_sales
cafe.staging.stg_stores
$ uv run dbt build 2>&1 | grep -E "Found|Done"
13:46:31  Found 5 models, 3 sources, 512 macros
13:46:31  Done. PASS=5 WARN=0 ERROR=0 SKIP=0 NO-OP=0 REUSED=0 TOTAL=5
$ uv run python ../scripts/dbt_counts.py
stg_order_lines: 3287 rows, 3287 different grains
int_order_lines_priced: 3287 rows, 3287 different grains
fct_store_daily_sales: 453 rows, 453 different grains
$ uv run dbt ls --quiet --select source:pipeline.stores+ --resource-type model
```

The build passes and the counts do not change, because the SQL does the same work. What changed is what dbt knows: with a path written into the model, no model depends on the source `stores` any more, so a selection from the source finds nothing and the last command prints nothing, a change to that source cannot be traced to the models it affects, and the source stays declared and unused. Reading through `source()` costs nothing and keeps the lineage that DE10 reads.

</Solution>
